# F-293: tests await what they check on a loaded host

## What was asked

On a host at load 20 to 45, the gates failed tests that had passed alone. The unit is tests and
test aids only, and a flake that turns out to be a product bug is reported, not fixed. It covers
five flakes:

1. `subscribe_test.exs` could pick a port another process takes (F-289's new-7).
2. `delegates_interactive_test.exs:431`, and every Mailbox and Delegates test that reads right
   after `message`, `cue` or `:sys.get_state`.
3. `tmux_contract_test.exs:153` captured before its text showed.
4. `mains_test.exs:431` and `:529` timed out at 60 s.
5. Delivery_Interactive and Delivery_Forced may pass 30 s (F-289's new-8).

## What was built

- **`TestHost.free_port/0`** picks a port in 20000..32767, below the ephemeral range of Linux
  (32768-60999) and macOS (49152-65535). The kernel picks ports in that range when a socket
  connects out or listens on port 0, so a socket the kernel places never takes a port here in between. Each call
  in a VM takes a later port than the last, from a start set by the OS pid, so two tests never
  get one port. A port in use is skipped. The check listens with `reuseaddr`, as Bandit does, so
  a port whose old connections wait out TIME_WAIT counts as free. The tree reads its ports from
  its config, which its hooks embed, so it cannot bind port 0 itself. Seven test files and
  `RealCase` each had their own port-0 `free_port/0`, and they now use this one.
- **A cue waits for its pass.** Since F-289, `Mailbox.cue/2` starts a pass that reads in a
  task, and the pass applies its reads after later calls have answered. A
  `Mailbox.status(m, 0)` after a cue answered before the pass ended, so the next read saw the
  row as it was before. Each Mailbox and Delegates file, and `mover_test.exs`, now has a `cued/2`
  helper. It cues, then awaits `:sys.get_state(mailbox).pass == nil`. A cue that comes during a
  pass starts the next pass before that one ends, so `nil` means no pass is left. A Mailbox the
  test stopped or restarted counts as passed, since its successor settles when it starts.
  Delegates settles in its own process, so a `:sys.get_state` of it stays a true barrier.
  `delegates_test.exs`'s `cue/2` now awaits Mailbox's pass before it cues Delegates.
- **`delegates_interactive_test.exs`**: `message/3` waits 10 s, not 5 s, for the hand-on and for
  `delivered`. `answered/2` returns the row's status and the marks Delegates holds as answered
  when it times out, so a failure says which side held the answer.
- **`tmux_contract_test.exs`**: the capture test waits 15 s for its text, not 5 s. On a timeout
  it shows the last screen it read.

## Tests

No test was added. The changed helpers are `TestHost.free_port/0`, `cued/2` and its
`passed?/1` in seven files, `message/3` and `answered/2` in `delegates_interactive_test.exs`,
and the capture await in `tmux_contract_test.exs`.

The first gate round ran before `passed?/1` existed. In each of its six runs,
`mailbox_test.exs:185` and `delegates_test.exs:1095` failed: each restarts its Mailbox, and
`cued/2` then read a pid that had exited. `passed?/1` now counts a stopped Mailbox as passed.
The same round showed a type warning at `mailbox_test.exs:279` and `:319`. `cue(ctx) && …` is
always true now that `cue/1` answers `{:ok, _}`, so the cue is a statement of its own there.

## Findings

### new-1. A test can see a cue's pass end only in Mailbox's private state

What happened: since F-289, `Mailbox.cue/2` returns before its pass ends, and nothing tells the
caller when the pass ends. Tests read `:sys.get_state(mailbox).pass` to wait for it.

Why: a pass reads in a task and applies its answer later. No call or event marks the end.

What I did: `cued/2` in each test file awaits `pass == nil`. That ties the tests to a private
field name.

What the design should change: I recommend that Mailbox announce a pass's end, or answer a call
once the pending pass applied, so tests wait on an announced event as CLAUDE.md asks.

### new-2. `delegates_interactive_test.exs:446` failed once at load 47

What happened: in the first round's gate-test 4, the test that was `:431` on ee24c01 failed:
`answered/2` met `{:refused, :no_answer}` for 10 s. Run 10 times alone at load 35 to 48, and in
the other five runs of that round, it passed.

Why: not found. `Delegates` tries `Mailbox.answered/4` again at each cue until Mailbox stores the
answer, so the test does await the effect. The failure printed no state.

What I did: a timeout of `answered/2` now shows the row's status and the marks Delegates holds as
answered.

What the design should change: nothing yet. If it fails again, its output says whether the row
was not delivered or Delegates never sent the answer.

### new-3. `mains_test.exs` did not time out again, and the 60 s bound was ExUnit's

What happened: `:431` and `:529` had timed out at 60 s. Here they passed in all ten runs alone at
load 40 to 76, and in every gate run.

Why: the 60 s is ExUnit's default test timeout. The product's own bounds are longer:
`start_main/5` waits up to 300 s, and `end_main/3` waits at least 90 s
(`Sessions.stop_bound/2` plus 60 s). So a slow call there ends the test at 60 s before the
product answers `{:unknown, {:timeout, _}}`. What took 60 s was not found.

What I did: nothing.

What the design should change: I recommend that these tests pass a `timeout:` under 60 s, so a
slow call ends in the product's own outcome and its output names the step.

### new-4. A sample during the tmux server's own exit answers unknown

What happened: `devenv test` failed `sessions_test.exs:384` once. `TmuxSampler.sample/1` answered
`{:unknown, {:tmux, {:unknown, {:tmux, 1, "server exited unexpectedly\n"}}}}`, where the test
expects `{:ok, %{held: 0}}`.

Why: the test's server holds one session. When it ends, tmux exits by itself, and a command that
reaches the server as it exits gets "server exited unexpectedly". `Tmux.CLI`'s `no_server?/1`
takes only "no server running on" and "error connecting to" as no server, so this case is
`unknown`, not `{:refused, :no_server}`. This is product behavior, so I did not change it.

What I did: nothing.

What the design should change: I recommend deciding whether that output means no server. If it
does, `no_server?/1` takes it as well. If not, the test awaits a sample that is not `unknown`.

### new-5. Six more test files had the port-0 `free_port/0`

What happened: besides `subscribe_test.exs`, three surface tests, the services test, two example
tests and `RealCase` each opened a socket on port 0 and closed it.

What I did: all of them use `TestHost.free_port/0` now.

What the design should change: nothing.

### new-6. The two Delivery configurations were not timed

What happened: the brief asks to time Delivery_Interactive and Delivery_Forced with
`TLC_WORKERS=auto` at a load under 6 on 12 cores. The load stayed at 16 to 90.

In the final `devenv test`, on the 2 workers `bin/check-model` picks at that load (F-290),
Delivery_Interactive took 54 s at load 29 and Delivery_Forced took 58 s at load 33. Each found 832 816 distinct states. On 2
workers, the 30 s rule does not judge them.

What I did: nothing. No configuration moved or changed, so `bin/check-model` ran only as part
of `devenv test`.

What the design should change: nothing. They still need timing with every core on a quiet host.

### new-7. At load 110, a tree's delegate starts did not finish within the tests' bounds

What happened: the last gate-test ran at load 78 to 110 on 12 cores, and three
`surface_test.exs` tests failed. `:1286` read `{:refused, :no_session}` for a delegate. `:1203`
found no session row in 20 s. `:867` hit ExUnit's 60 s. Run 10 times alone at load 19 to 31, the
file passed each time.

Why: each test waits for a delegate's start, and at that load a start took longer than the
test's bound. I did not find which step was slow.

What I did: nothing. Raising each bound to fit any load would hide a slow start, not wait on an
event.

What the design should change: nothing, I recommend, unless starts this slow also show on the
live tree. The shared gate lock now keeps gate runs one at a time.
