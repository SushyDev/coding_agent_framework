# F-265: an app reads agent rows by session id or by a meta key, with their turn state

## What was built

- `CodingAgentFramework.agent_rows(instance, by)`, with `by` one of `session_id: id` or
  `meta: {key, value}`. It answers `{:ok, rows}`, oldest first. Each row is as `agent_rows/1`
  gives it, plus `turn`: the agent's `state` in `Tracker.agents/2`'s tree (`"idle"`,
  `"working"`, `"waiting"` while a prompt is open, `"dialog"`, `"starting"`, `"gone"`,
  `"ended"`), read with `all: true` so an ended row has its turn. A row the tree has not read
  is `"unread"`. No match is `{:ok, []}`, and the tree is then not read at all.
- `by` is one pair, not a list. An app keys a record by one thing, and one pair keeps one
  query shape and one index per shape. A list of none or of two pairs is `{:refused, {:bad,
  :by}}`. A key of no read is `{:refused, {:bad, key}}`, and a value out of shape is
  `{:refused, {:bad, :session_id}}` or `{:refused, {:bad, :meta}}`. `by` is checked before
  anything is read.
- `Sessions.Table.by/3` and `where/1`, and `Sessions.Agents.read_only/3`: the filter runs in
  SQLite through the same read-only connection `agent_rows/1` uses, so the app's process never
  holds the other rows.
- The `Tracker` takes a `name:`, and the tree registers it in the instance's `Registry` as
  `:tracker`, as `Watch` is registered. That is how the facade reaches the same tree
  `Tracker.agents/2` reads. `agent_rows/1` now shares the config lookup with `agent_rows/2`.

## How `meta` is matched

`meta` is stored as JSON text (`Table.meta_text/1`). A match is
`json_type(meta, '$."key"') = type AND json_extract(meta, '$."key"') = value`, nested in
`CASE` under `json_valid(meta)`. SQLite does not promise the order an `AND` runs in, and
`json_type` raises on text that is not JSON. The type check makes `41` match only the integer
41, never `"41"` or `true` (SQLite reads `true` as 1). Values are strings or 64-bit integers.
The key is one quoted label, so `unit.x` is one key, not a path. SQLite's path has no escape
for `"`, so a key that contains one is refused. An atom key is its string, as `meta_text/1`
writes it.

## Indexes

- Session id: new index `agents_session ON agents (host, session_id)`. The table is never
  pruned, and an app reads by session id on each record it shows. The test reads `EXPLAIN QUERY
  PLAN` to check the index is used. `CREATE INDEX IF NOT EXISTS` adds it to an existing file
  at the tree's next start.
- `meta`: no index. Its keys are the app's, so no one expression index covers them. The read
  uses the `(host, name)` unique index for the host and evaluates the JSON on each of that
  host's rows inside SQLite. It is linear in the host's rows, and only matches leave the store.
  See new-1.

## A session id that moved

The row's `session_id` is the current one. A headless delegate's resume keeps its id. An
interactive session's id is rewritten from its session file at each start, so a resume that
gets a new id is found by the new id (tested). An earlier id is not kept as a history: the
`resume` column holds only the id the latest start resumed, so matching it would find a row by
its last id but not by older ones. Earlier ids do not find the row, and nothing was built for
them. See new-2.

## Tests

- `apps/caf_sessions/test/by_test.exs` (store level): by session id (with another host's row of
  the same id left out), by a meta key with two rows matching, JSON type kept apart, no match, a
  row with no meta, a key with a dot, each refusal (also for a missing file), a resumed row found
  by its new id and not the old one, and the session-id index in the query plan. Also doctests
  of `by/3` and `where/1`.
- `apps/caf_surface/test/surface_test.exs`, "an app reads agent rows by session id or by a meta
  key, with their turn": a whole tree with the headless stand-in. Two delegates are given the
  same `meta`. One is idle after its report. The other has a `bg` brief and stays `working`
  while its background command runs. By session id, the row has `agent_rows/1`'s keys plus
  `turn`. The idle one is then stopped and ended, and its turn reads `ended`. The test also
  covers no match, bad keys and values, and no instance.

## Measured

Nothing timed. The session-id read uses its index, per the query plan.

## Findings

### new-1. A meta read scans the host's rows

What happened: `meta: {key, value}` cannot use an index, since the keys are the app's.
Why: `meta` is one JSON column, and an expression index needs a fixed key.
What I did: the scan runs in SQLite and returns only matches. It is linear in the host's agent
rows, which are never pruned.
What the design should change: if an app reads by one key often on a large table, either the
app declares the keys it reads by (an expression index per declared key), or `meta` moves to a
side table `(agent_id, key, value)` indexed on `(key, value)`. Neither was built.

### new-2. Earlier session ids are not kept

What happened: a row resumed into a new id is found only by its current id. The `resume`
column keeps one earlier id, the one the latest start resumed.
Why: nothing records the full chain of ids an agent had.
What I did: matched only `session_id`. Matching `resume` too would find a row by its last id
and not by older ones, which is inconsistent.
What the design should change: if an app keys records by an id from before a resume, keep each
id an agent row had (a small table of `(agent_id, session_id)` written at each start that names
a new id) and match against it. Not built.
