# F-31: how a headless delegate is held and spoken to, and `Stream.tla`

Research and the model only; no Elixir code.

## The source

I read the devenv Claude Code 2.1.322 (`$CAF_CLAUDE`, a wrapper around
`bin/.claude-wrapped`): its `--help`, and the strings of the binary, which hold the SDK's
message schemas (zod, with their descriptions) and the minified code of the stdin reader. No
session was started, and no credential or person's config directory was read. Quotes are from
the strings unless marked `--help`.

**Flags.** `--input-format stream-json` is "realtime streaming input"; `--replay-user-messages`
"Re-emit user messages from stdin back on stdout for acknowledgment"; `--permission-prompts
host` sends prompts to "the SDK host", and is the default (`--help`). With `-p` and stream-json
output, `--verbose` is required: `if(P.outputFormat==="stream-json"&&!P.verbose)` writes "Error:
When using --print, --output-format=stream-json requires --verbose" and exits 1.

**Input lines.** The reader splits stdin on `\n` and skips blank lines.
- A user message: `{"type":"user","uuid":"<uuid>","session_id":"","parent_tool_use_id":null,
  "message":{"role":"user","content":"<text>"}}`. Its schema says "A client writes one to the
  CLI to submit a prompt (this starts a turn)".
- An answer to a permission request: `{"type":"control_response","response":{"subtype":
  "success","request_id":"<id>","response":{"behavior":"allow"}}}`, or `{"behavior":"deny",
  "message":"…"}`; `updatedInput`, `updatedPermissions` and `interrupt` are optional.
- An interrupt: `{"type":"control_request","request_id":"<id>","request":{"subtype":
  "interrupt"}}`. An end: the same with `"subtype":"end_session"` and an optional `reason`;
  Claude Code's own helper host writes it and then closes stdin.
- A line that does not parse, a user line whose role is not `user`, or a `control_request`
  with no `request` ends the session: "Error parsing streaming input line (type=…, N chars)",
  then `process.exit(1)` with `invalid_stream_input`. A line of an unknown type is ignored with
  a warning. A line over 268,435,456 characters (`Ce`) ends it too.
- A user line whose uuid the transcript already holds is not run again (`skipDuplicate`, which
  checks `persisted(uuid)` and the uuids received); with replays on it answers "Sending
  acknowledgment for duplicate user message".

**Output events.** Every event carries `session_id` and `uuid`.
- `system`/`init`: `session_id`, `cwd`, `model`, `tools`, `permissionMode`,
  `claude_code_version`, `capabilities`, and more.
- `assistant`: one per finished content block; "the turn's stop reason and total usage arrive
  on the result message".
- `user` with `isReplay: true` and the uuid the line carried, for each line taken. With replays
  on, an answer that settled a pending request is passed on as well (`if(this.replayUserMessages
  &&…)return r7i(Yes(s))`); the release check confirms it reaches stdout.
- `result`: "The CLI emits exactly one result message per turn … treat it as the turn-complete
  signal". `subtype` is `success` or `error_during_execution`, `error_max_turns`,
  `error_max_budget_usd`, `error_max_structured_output_retries`; fields include `is_error`,
  `num_turns`, `result`, `stop_reason`, `total_cost_usd`, `usage`, `modelUsage`,
  `permission_denials`, `terminal_reason`, and `user_message_uuids`: "every user message whose
  prompt this turn consumed … then any queued user message folded into the running turn".
- A permission request: `{"type":"control_request","request_id":…,"request":{"subtype":
  "can_use_tool","tool_name","input","tool_use_id",…}}`. A request Claude Code withdraws comes
  as `{"type":"control_cancel_request","request_id":…}`. An answer to an id no longer pending is
  dropped, and a second answer to one id is ignored ("Ignoring duplicate control_response").
  I found no deadline on a request read from stdin.
- `rate_limit_event`: "emitted when rate limit info changes", with `rate_limit_info`:
  `status`, `rateLimitType`, `utilization`, `resetsAt`, and `unifiedWindows.seven_day`
  `{utilization, resetsAt}` ("utilization is the fraction of the window used … resetsAt is unix
  epoch seconds"; marked internal; "absent for API-key, Bedrock, and Vertex sessions").

**Ending.** `end_session` sets `endSessionRequested`, aborts a running turn
(`abort(Wl("shutdown"))`) and leaves the loop. At end of file on stdin, the run ends once the
running turn and its queued work are done ("the host has ended its input"), and a pending
permission request fails ("Tool permission stream closed before response received").

**Resume.** In `-p` mode `--resume <id>` loads the transcript and keeps the id; an unknown id
writes "No conversation found with session ID: <id>" and exits 1. "--session-id can only be used
with --continue or --resume if --fork-session is also specified."

## What was built

- **`docs/design.md`**, "Headless delegates": the command with `--verbose` and
  `--permission-prompts host`, `--resume` in place of `--session-id`; the wrapper (three lines
  of `sh`) that holds stdin as a FIFO opened read-write and appends stdout to
  `<home>/streams/<session>/events.jsonl`; a line written by a claim command
  (`exec 3<spool && rm spool && cat <&3 >fifo`) that outlives the framework, so a line goes in
  once and whole; the lines and events above; ending by `end_session`; rate limits.
- **`model/tla/Stream.tla`**: messages marked, spooled, claimed and written; the delegate's
  turns, `result` events, replays and permission requests; a log read from a persisted offset;
  partial lines on both sides; restarts between any two steps; the exit. Invariants:
  `NoDoubleRead`, `NoSkippedEvent`, `NoPartialRead`, `NeverMalformed`, `WrittenOnce`,
  `TakenOnce`, `IntoEndedTurn`, `OneWaiting` (defense in depth), `DeliveredWasTaken`,
  `UndeliveredWasNotTaken`, `OnlyNamedRequest`, `AnswerOnce`, `AnsweredWasTaken`. Liveness:
  `ReplayedOrFound`, `AnswerSettles`.
- Nine `Break` values, each with a configuration TLC fails: `OffsetAfterHandle`,
  `OffsetBeforeHandle`, `ReadPartial`, `WriteInFramework`, `NoClaim`, `NoResultWait`,
  `ByNewest`, `LogOnlyAtExit`, `NoReclaim` (liveness).
- `Stream_Messages.cfg` and `Stream_Requests.cfg` in the gate, `slow/Stream_Large.cfg` by
  hand, and a section in `model/tla/READING.md`.

## Measured

With `TLC_WORKERS=2` on a busy laptop:

- `Stream_Messages` (two messages, one request, two restarts): 3,381 distinct states, depth
  34, 6 s.
- `Stream_Requests` (one message, two requests, two restarts): 4,467 distinct states, depth
  33, 5 s.
- Each `Break_Stream_*`: under 140 distinct states, 3-4 s.
- `slow/Stream_Large` (three messages, three requests, four restarts): 439,218 distinct states,
  depth 65, 279 s. With two requests and three restarts it was 64,497 states in 27 s.

## What I ran into

- The design's command lacked `--verbose`, without which a `-p` session with stream-json
  output exits at once. The section now has it.
- A partial line is fatal on the input side: Claude Code exits on a line that does not parse.
  A writer that dies mid-line leaves the start of a line in the pipe, and the next line joins
  it. That is why the line is written by a claim command and not by the framework itself
  (`WriteInFramework` shows the failure).
- A FIFO does not keep data across its last reader. The wrapper's read-write open makes the
  delegate its own writer, so neither end-of-file nor a lost line follows a writer's exit.

## Findings

### new-1. `Programs` has no `mkfifo`

What happened: the wrapper needs a FIFO, made before dtach starts, and `Programs` lists no
program that makes one.

What the design should change: add `mkfifo` to `Programs`' list.

### new-2. Claude Code can start a turn by itself

What happened: a background task that ends wakes the session into a turn with no message from
the framework, and a message written then joins that turn (`user_message_uuids` lists it).

What I did: `Stream.tla` leaves such turns out, and says so.

What the design should change: say that a message joining a turn the delegate started itself
is still delivered once, by its replay, and is accepted; or require the reader to be at the
log's end, with no turn under way, before a write. I recommend accepting it.

### new-3. A claim command can hang on a dead delegate's FIFO

What happened: opening a FIFO for writing blocks while no process holds it for reading, so a
claim command started after the delegate exited waits forever.

What the design should change: the writer starts a claim only for a live delegate, under a
deadline, and `Recoveries` ends a stuck claim command by its pid and start time.

### new-4. `Usage` can read rate limits from a delegate's log

What happened: `rate_limit_event` carries the seven-day window's share and reset. Its
`unifiedWindows` field is marked internal.

What the design should change: let `Usage` read the latest `rate_limit_event` of a delegate's
log as it reads a status line, and replace the rule that `Usage` reads only interactive
sessions until `Stream` is built. Add the field to the check against each pinned release.

### new-5. A resend under the same uuid is dropped by Claude Code

What happened: Claude Code drops a user line whose uuid its transcript already holds.

What I did: the design does not rely on it; a line is claimed once.

What the design should change: when a message found undelivered goes to the resumed process,
it keeps its uuid, so a message the transcript holds after all is not run twice.

### new-6. A permission request outlives a restart of the framework

What happened: a request read from stdin waits in Claude Code, with no deadline I could find,
through a restart of the framework; a hook's request does not.

What I did: the design keeps a held row answerable after a restart, unlike "Intake".

What the design should change: say how long a held request may wait before a view flags it,
since nothing ends it but an answer, a cancel or the exit.
