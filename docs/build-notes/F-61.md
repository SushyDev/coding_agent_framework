# F-61: `Sessions` settles a running row whose process is gone

## What was built

F-59 new-5: nothing moved a `running` row when its process exited by itself. `Sessions`
settled `starting`, `unknown` and `stopping` rows only, and `Start.tla`'s `ProcExits` left the
row as it was. So a delegate killed before its last reply could not be resumed:
`Sessions.resume/6` answered `{:refused, {:exists, "running"}}`.

- **`Start.tla`**: a new step, `RunningSettled`, takes a `running` row with no call under way to
  `stopped` once its process is gone by the row's pid and start time and its socket is dead. A
  new property, `RunningSettles`, says such a row always settles, under weak fairness of the
  step. A new `Break`, `SettleRunningByPid`, judges the process by its pid alone, without its
  start time. `Break_Start_SettleRunningByPid.cfg` (one pid, one program of another kind) fails
  `RunningSettles`: the process exits, another program takes its pid, and the row stays running
  forever. The header names the module change and the socket's half of the check as defense in
  depth (new-1). `RunningSettles` is added to the four design configurations and to
  `slow/Start_Large`.
- **`docs/design.md`**, "The delegate protocol": a running row with no call under way whose
  process exited by itself is settled `stopped`, with reason `exited`, once its process is gone
  by pid and start time and its socket is read as dead; a pid another program took does not
  keep it running; a read that fails decides nothing; `Sessions` takes the step at each settle
  a `Registry` or `Stream` cue starts. "The model" lists the new property. `READING.md` says
  the same for `RunningSettled`.
- **`Sessions`**: each settle (at start, at a starting row's deadline, and at each `Registry` or
  `Stream` cue) also takes the running rows of the cued set with no call under way. One `ps`
  judges all of them (`Registry.Liveness`, by `{pid, procStart}`). A row whose process is
  `:gone` or `:replaced` then has its socket read (`Holder.state/2`), and only `:absent` or
  `:stale` writes `stopped` with reason `exited`. A `ps` that fails, a socket read that fails,
  or a live socket decides nothing. A running row with no pid or no start time is skipped, as
  `Liveness` would answer `:unknown` for it. The moduledoc lists the new case.
- **Tests**, on the stand-ins, each killing only the pids its own stand-in recorded:
  - `SessionsTest`, "F-61: RunningSettled …": a parent's process is killed, a `Registry` cue
    settles its row `stopped` with reason `exited`, a live parent's row stays `running` in the
    same settle, and a resume of the killed name is accepted and runs. The live row's start
    time is then set to another one: with its socket live, the row still stays `running`.
  - `SessionsHeadlessTest`, "a running delegate killed before its last reply …": the same for a
    delegate, with a `Stream` cue, and a resume of the same session id.

row whose process is gone.

## What I ran into

- In `Start.tla` a socket ends in the same step as its process (`ProcExits`), so the two halves
  of the check cannot fail alone (new-1).
- dtach removes its socket a moment after its process exits. The headless resume test already
  waits for `:absent` after a stop for this reason ("its dtach master ends a moment later").
  The new tests' `kill_held` waits for it too before the cue.

## Findings

### new-1. The socket's half of the check cannot fail in `Start.tla`, so it has no `Break`

What happened: the brief asked for one `Break` that settles a running row by the socket alone
and one that settles it by the pid alone, each failed by TLC. In `Start.tla` a socket ends in
the same step as its process, and a running row's process is the one its socket holds. So the
process is gone by pid and start time exactly when the socket is dead. I checked both in a
scratch copy of the spec (not committed): `BySocket` (no pid check) and `ByLiveness` (pid and
start time, no socket read) each pass all four design configurations, with the same states as
the design.

What I did: followed "The model": a guard that cannot fail on its own is defense in depth, with
no `Break`, named in the header. The header names the socket's read in `RunningSettled` as
defense in depth behind the pid and start time, and says why the code reads it anyway. The one
`Break` that does fail is the pid without its start time (new-2). The code reads both, and the
parent's test shows the socket read keeps a row running whose start time reads as another
process's.

What the design should change: to show the socket's half with TLC, a unit should model a
socket apart from its process. In the code they part two ways: a socket stays live a moment
after its process exits, until dtach exits; and a dtach killed hard leaves a stale socket, while
its process may run on for a while. Modeling that would also show two gaps in what is built now,
which this unit did not change:

- `StopSettled` judges by pid and start time alone. A stop can answer `stopped` while the socket
  is still live, and a resume right after it is refused `{:live, name}` by the hold. The
  headless resume test waits for `:absent` to step around this.
- `ReRead` and `Adopt` read only the socket: an `unknown` or `starting` row has no pid yet. A
  process that outlives its hard-killed dtach is then read as gone: `stopped` or
  `refused{interrupted}` while it runs.

I recommend one unit that models the socket apart from its process in `Start.tla`, with a
`Break` for each half of `RunningSettled`'s check, adds the socket read to `StopSettled`, and
decides what `ReRead` and `Adopt` do with a stale socket while the session file names a live
process.

### new-2. "By the pid alone" read as "without its start time"

What happened: "settles it by the pid alone" can mean the pid without its start time, as the
existing `SettleByPid` means, or the pid and start time without the socket.

What I did: the first, `SettleRunningByPid`, named and described as `SettleByPid` is. The
second is the `ByLiveness` of new-1, which cannot fail here. A pid without its start time only
errs toward "alive", so this `Break` fails a liveness property, not an invariant: a reused pid
keeps the row running.

What the design should change: nothing.

### new-3. A cue that meets a socket dtach has not removed yet settles nothing until the next cue

What happened: `RunningSettles` assumes `Sessions` takes the step while it stays possible. The
code takes it at each settle: at start, at a starting row's deadline, and at each `Registry` or
`Stream` cue. A reader cues only when its rows change. When a process is killed, the reader's
next read cues once (its row of the process is now gone). If that settle reads the socket as
still live, the row stays `running` until some later cue, which may not come for a long time.

What I did: nothing more; the step decides only on what it reads, as the brief asks, and the
tests wait for the socket to be absent before they cue.

What the design should change: say who takes the step again in that case. Two ways I see: the
host's `Registry` interval read cues `Sessions` at each read rather than only on a change; or a
`Holder` cue when a socket goes away. A fixed retry inside `Sessions` would be a hidden wait.
