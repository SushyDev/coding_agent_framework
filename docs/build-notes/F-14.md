# F-14: `Delegate.tla`

## What was built

- **`model/tla/Delegate.tla`**: a parent, its delegates and restarts of the framework. Steps:
  `StartAsked` (the checks and the cap), `DelegateFinishes`, `DelegateKilled`, `StopHandled`,
  `TranscriptRead` (the fallback when a restart lost the Stop event), `KillSeen` (resume once,
  report the second kill), `DeliveryAsked`, `DeliveryTyped` / `DeliveryRefused` (`Control`'s
  checked write), `DeliveryMarked`, `SendingResolved` (a send a restart cut off), `DelegateEnds`;
  the parent's `PromptSent`, `TurnEnds`, `ParentStops`, `ParentRuns`; `FrameworkDies` and
  `FrameworkStarts`. Its header names `Delegates`, `Parents`, `Sessions` and `Control` (only
  `Control` is built), what it leaves abstract, its fairness, and its defense in depth.
- **Configurations**: `Delegate_Design`, `Delegate_Restarts` and eight `Break_Delegate_*` in the
  fast set; `slow/Delegate_Large`.
- **`model/tla/READING.md`** reads the spec in the order of a report's path; **`docs/design.md`**
  notes under "The model" what the spec settles.

## The model

Invariants: `DeliveredAtMostOnce`, `OnlyIntoEndedTurn`, `EndsAfterDelivery`, `ReportKept`,
`ResumedAtMostOnce`, `SecondKillNotRetried`, `CapHeld`, `TypeOK`. Liveness: `ReportArrives`
(every finished delegate's report, and every second kill's, reaches the parent's transcript) and
`DeliveredDelegateEnds`.

| Configuration | Removes | TLC reports |
|---|---|---|
| `Break_Delegate_RedeliverAfterRestart` | reading the parent's transcript after a cut-off send | `DeliveredAtMostOnce` |
| `Break_Delegate_IntoRunningTurn` | the write's check that the turn has ended | `OnlyIntoEndedTurn` |
| `Break_Delegate_NoParentCheck` | the write's check that a parent process runs | `OnlyIntoEndedTurn` |
| `Break_Delegate_EndBeforeDelivery` | the end's wait for delivery | `EndsAfterDelivery` |
| `Break_Delegate_ResumeAgain` | the resume's once | `ResumedAtMostOnce` |
| `Break_Delegate_HeldInMemory` | the held report in the table | `ReportKept` |
| `Break_Delegate_NoTranscriptFallback` | the transcript's last reply for a lost Stop event | `ReportArrives` (exit 13) |
| `Break_Delegate_NoCap` | the cap check at start | `CapHeld` |

Scratch copies, not committed, checked the header's claims against `Delegate_Design`: without
`StopHandled`'s status check it passes, and without `TranscriptRead`'s wait for no held Stop
event it passes, but without both it fails `CapHeld` (a late Stop event revives an ended
delegate), so the two are defense in depth for each other. Without `DeliveryAsked`'s wait for an
ended turn, or with `DeliveryTyped` only weakly fair, it fails `ReportArrives` (exit 13), so the
liveness check is not vacuous.

## What I ran into

- No invariant of the design failed while writing the spec, and every break failed on its first
  run.
- The report must go out under strong fairness: with weak fairness alone, a user whose prompt
  lands between the ask and the write each time starves the report forever.

## Findings

### new-1. "Delivered once" needs a mark before the write and a read after a restart

What happened: the design says a report is delivered once and survives restarts, but not how.
Typing a report and recording it are two steps; a restart between them leaves a report that
was typed but reads as held, and `Break_Delegate_RedeliverAfterRestart` types it twice in 14
steps. The rule "an unknown write is never resent" alone would instead lose it.

Why: the write's outcome is held in memory, which a restart drops.

What I did: the row says `"sending"` before the write; after a restart, a `"sending"` row with no
send under way is settled by reading the parent's transcript: delivered if the report is there,
held again if not.

What the design should change: add to step 5 that the row is marked before the write and that a
restart settles a marked row from the parent's transcript, so each report needs a mark of its
own that the transcript shows. The spec assumes the transcript holds the report in the step it
is typed; the code should confirm how long Claude Code takes to write it, and settle only after
the parent's turn that took it has ended.

### new-2. The Stop event and the transcript fallback must give one report

What happened: "When a restart lost the stop event, it delivers the transcript's last reply"
does not say how the framework knows the event was lost, nor what keeps a late event and the
fallback from both giving a report. With neither guard, a late Stop event revives an ended
delegate (`CapHeld` fails).

What I did: the row leaves `"running"` once, by whichever comes first; the fallback reads only a
delegate whose transcript ends with its last reply and whose Stop event the framework does not
hold. Each guard alone suffices, and the header names them as defense in depth.

What the design should change: say the delegate's row moves from running to finished once, by
its Stop event or by its transcript's last reply, and later ones are ignored.

### new-3. A kill after the last reply is a finish, and a second kill's report is a report

What happened: step 6 resumes a killed delegate once and "reports a second kill", but does not
say whether that report is held, delivered once and ends the delegate like a finished one, nor
what a kill after the last reply is.

What I did: a kill before the last reply is resumed once; a second such kill holds a report on
the same path as a finish. A kill after the last reply is a finish, read from the transcript.

What the design should change: say both in step 6.

### new-4. A report waits for the parent's turn to end, again and again

What happened: a report goes in only when the parent's turn has ended, and the user's prompts
may take the parent's turn each time. The liveness holds only if the framework tries at each turn
end, and checks the turn again in the write.

What I did: `DeliveryAsked` waits for an ended turn, `Control`'s write checks it again, and both
are strongly fair.

What the design should change: say the framework tries a held report at each of the parent's
turn ends (its Stop event), the same as a message, and that a refused write holds it again.

### new-5. A restart in the middle of a start is not modeled

What happened: the start's worktree, setup and dtach steps are one step here. A restart between
them could leave a worktree or a held process with no row.

What I did: left it abstract, and named it in the header.

What the design should change: say how `Delegates` adopts or ends a start a restart cut off
("make a restarted step adopt or end the work it started"), and model it then.
