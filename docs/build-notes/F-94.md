# F-94: `Copies.Held`'s tests end what they hold

## What was built

`apps/caf_copies/test/held_test.exs` holds a program (a `bash -c` that prints the synced file,
then waits up to the stand-in's idle bound). Its wrapper records the program's pid, and the
test's end (`end_recorded/2`, F-66) signals a recorded pid only while its command line names the
test's directory. The program's command line named none (`bash -c "cat a.txt …"`), so the end
skipped it, and each run left five holds (`s1` to `s4` on the workstation and the stand-in host)
until the idle bound, 90 s. The program now gets a `$0` inside the test's directory, so its
command line names it and the end reaches it.

## What was measured

- Before: `mix test apps/caf_copies/test/held_test.exs` passed and left five `dtach` holds of
  its VM running after the run. After: none, over two runs.
- It was found by `gate-test`'s check (F-66) failing three runs of F-90 in a row, which does not
  touch `caf_copies`. Earlier gates passed with the same leak because `caf_copies` runs early and
  its holds reached their 90 s bound before the run's end; the check is only as good as the
  timing allows when a leak is bounded.

## Findings

### new-1. A fetch's rsync can outlive its `caf_jobs` test by up to 30 s

What happened: after `mix test apps/caf_jobs/test`, a fetch's `rsync` and its stand-in ssh, and
on the host side `flock -w 30 … rsync --server`, still ran for a VM that had ended. Why: a test
ends while its fetch waits for the copy's lock; the lock's wait (30 s) bounds it. What I did:
nothing here. What the design should change: nothing; a unit should have that test end its
fetch (or its lock wait shorter than the test), so `gate-test`'s check cannot catch it when the
test runs last.
