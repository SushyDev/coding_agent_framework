# F-104: a stopped delegate is `ended`; a late end is kept without a crash

F-103's new-2 and new-3, built.

## What was built

1. **`ended`** (`Delegates`). A `finished` delegate whose report is `answered` (or `delivered`)
   and whose `Sessions` row has ended is written `ended` at the next cue, and the write is
   announced. `fix(… :stop …)` now casts that cue to `Delegates` itself once `Sessions.stop/4`
   answers, so the row does not wait for the app's routing. `ended` is not in `Table`'s cap
   statuses, so the parent's cap is free again. A second `:stop` of an `ended` delegate is
   refused as `{:status, "ended"}`; `fix_state` still reads such a row. A report not yet
   answered keeps the row `finished` even when its process is gone.
   In `caf_example`, `ended` (for `Services.owner_ended/3`) and the `Ends` process's `ended_ids`
   read `refused`, `failed` and `ended` as an end.
2. **A late end kept** (`Jobs`). `:on_late_end` answers `:ok` or `{:unknown, reason}`. On `:ok`
   the row is `told`; on `{:unknown, reason}` it stays `owed` with its end written, and the next
   cue hands it again. Any other answer raises, as a raise did before: it is the app's bug.
   The app's `late_end` answers `{:unknown, {:not_stored, other}}` when `Mailbox` does not
   answer, where it raised; a refusal of the call (no caller, unknown agent) is logged and is
   `:ok`, as nothing will ever store it.

## Tests

- `Delegates`: a delegate stopped after its report is `ended` with no cue from the test, its
  cap is free, and a second stop is refused; a stop before the report is answered is refused.
- `Jobs`: a late end whose first hand-on is unknown is handed again at a cue and told once.
- `caf_example`: a delegate stopped after its report ends its services; a late end that
  `Mailbox` (suspended) did not answer stays owed, raises nothing, and is stored once when it
  answers.

## What I ran into

- F-103 was not on `main` when this was built, so the branch sits on F-103's branch
  (`framework/f-103-app-wiring`) and needs `main` to take F-103 first.
- `caf_mcp`'s test passes `on_late_end: & &1`, which answers the end itself. It never runs
  (no late end happens there), but it no longer matches the contract. It is outside this unit.

## Findings

### new-1. `Mailbox` does not read `ended`

What happened: `Mailbox` reads `Delegates`' rows by the statuses `starting resuming running
finished failed refused` (`@delegates`) and takes `refused` as an end (`ended?/2`). A delegate
written `ended` is in none of them, so `agents[to]` is nil for it.
Why: this unit may touch only `caf_delegates`, `caf_jobs`, `caf_example`, so `caf_mailbox` was
left alone.
What it does: for a stopped delegate, queued messages to it fall into the "main session: no
delivery until `Screen`" branch (marked `:no_delivery`, never `ended`), and the notice for a
message that was in flight when it was stopped is never stored, since `replies/3` needs the
delegate's `parent`.
What the design should change: `Mailbox`'s `@delegates` takes `ended`, and its `ended?/2` is
true for `%{status: "ended"}`. A unit of its own, with a test: a message queued to a stopped
delegate is `ended`.

### new-2. An ended delegate leaves the tree

What happened: the app's `@tree` (and `Tracker.Tree`'s `@held`) list the statuses that hold a
parent's cap; `ended` is not one, so a stopped delegate disappears from `agents()` and the
tree `Grants` reads, together with its row for `fix_state`'s parent check.
What the design should change: say whether `agents()` shows ended delegates (with state
`ended`) or not. If it does, the tree and `Tracker` take `ended` and the cap count does not.

### new-3. `caf_mcp`'s test hand-on returns the end

What happened: `mcp_test.exs` passes `on_late_end: & &1`. See above.
What the design should change: nothing; a one-line change to `fn _ -> :ok end` in the next
unit that touches `caf_mcp`.
