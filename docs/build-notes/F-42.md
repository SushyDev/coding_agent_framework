# F-42: each part's tests in its own app

## What was built

F-37 moved six test files whole to a higher app (F-37 new-1). This unit splits them, so each
part's own cases are in its own app:

- A case of the part alone goes back to its part's app.
- A case that reads a Tracker source becomes a test in `caf_tracker`, named for the source.
- A case that uses two parts together goes to the higher app.

No case changed what it checks. Cases moved between files with their bodies unchanged. Where
two files now need one setup, it moved into a module both use (see "Shared setup").

Six apps now have tests of their own for the first time: `caf_intake`, `caf_accounts`,
`caf_usage`, `caf_sampler`, `caf_sessions` and `caf_recoveries`. Each has the same
`test_helper.exs` as the other apps. `caf_shell` is the one app with no tests of its own: its
tests stay in `caf_test`, and `caf_test`'s `mix.exs` says why. `TestHost` uses `Host`,
`Programs` and `Shell`, so `caf_shell`'s tests may not use `caf_test`. Splitting `TestHost`
into a part with no host and a host part would let them move, and is not worth it.

The notes in `caf_tracker`'s and `caf_cli`'s `mix.exs` that said why they hold other parts'
tests are gone. Each app's test-only deps now name what its tests use. `caf_tracker` dropped
`caf_control`, `caf_holder`, `bandit` and `plug`.

## Shared setup

Six setups are now needed by two files each. Each uses its own part, which sits above
`caf_test`, so none of them can live there: `caf_test` would have to use that part, and the
part's tests use `caf_test`, which is a cycle. Each one moved instead into a module in the
lower app's `test/support/`. That directory compiles only for tests, as `caf_test`'s `lib/`
does (`elixirc_paths(:test)`). An app above uses the module because, in the test env, it
compiles its deps in the test env too. See new-1.

| Module | App | Holds | Used by |
|---|---|---|---|
| `IntakeSetup` | `caf_intake` | the `intake` setup, `secret`, `body`, `post`, `rows` | `intake_test`, `intake_source_test` |
| `AccountsSetup` | `caf_accounts` | the `accounts` setup (the VM's environment and a fake home) | `accounts_test`, `claude_cli_held_test` |
| `UsageSetup` | `caf_usage` | `now`, `week`, `start` | `usage_test`, `usage_source_test` |
| `SamplerSetup` | `caf_sampler` | the `sampler` setup | `tmux_sampler_test`, `tmux_sampler_source_test` |
| `SessionsSetup` | `caf_sessions` | the `sessions` setup, `launch` | `sessions_test`, `sessions_source_test` |
| `RecoveriesSetup` | `caf_recoveries` | the `recoveries` setup, `key`, `rows`, `held`, `agree`, `view`, `hold!` | `recoveries_test`, `recoveries_source_test` |

Each test file names its setup with `setup {Module, :name}`, except that the usage tests call
`UsageSetup.start/1`. Each module's code is the old setup and helpers, made public, with a
`@doc`. The helpers only one file uses stay private in that file.

## What I ran into

`mix compile --warnings-as-errors` runs in the dev env, so it does not compile `test/support`.
I also ran `MIX_ENV=test mix compile --warnings-as-errors`, and it had no warnings: the support
modules use `ExUnit.Callbacks` and `ExUnit.Assertions` with no warning about `:ex_unit`.

A test that names a module through an app it does not declare still compiles (F-37 new-2). So I
checked each app's test deps by hand against the modules its tests and support name.

## Findings

### new-1. Setup shared with a higher app's test cannot live in `caf_test`

What happened: the brief says setup that two files now need is shared through `caf_test`. Each
of the six shared setups starts or calls its own part (`Intake`, `Accounts`, `Usage`,
`TmuxSampler`, `Sessions`, `Recoveries`), and all six sit above `caf_test`.

Why: `caf_test` uses only `caf_shell`, and each of those parts' tests uses `caf_test`. For
`caf_test` to hold their setup it would have to use the parts, and Mix refuses the cycle.
Copying the setup into the second file was the one other way, and the brief rules it out.

What I did: put each setup in a module under its part's own `test/support/`, compiled only for
tests (`elixirc_paths(:test)`). The part's tests use it, and so do tests in apps above. Nothing
is copied.

What the design should change: "The parts" says "Shared test aids live in `caf_test`" and "Each
app has its own tests". It could say: a test of a Tracker source, or of two parts together,
belongs to the higher app (F-37 new-1). Aids that use no part above `caf_shell` live in
`caf_test`. Setup that a part's tests share with a higher app's tests lives in that part's
`test/support/`, compiled only for tests. One cost: in the test env every app above a part can
see its support modules, as it can see the part's code through the apps it declares (F-37
new-2). A gate that compares each app's uses with its declared deps should read the test env's
code too, support included.

### new-2. `hold!` is written twice

What happened: `hold!/2` in `caf_sampler`'s `tmux_sampler_test` and in `RecoveriesSetup` are the
same function. It holds `sh` playing the agent and waits for its pids.

Why: each was written in its own unit. F-37 moved them unchanged, and so did this unit.

What I did: nothing. Sharing it would change a test file beyond moving cases.

What the design should change: nothing in the design. If wanted, a later unit could move
`hold!` into `SamplerSetup`, where `RecoveriesSetup` can use it (`caf_recoveries` uses
`caf_sampler`).
