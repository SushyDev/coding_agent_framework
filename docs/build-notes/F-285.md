# F-285: the offer to set up auto mode is off in every session's settings

## Why

Claude Code 2.1.322 shows "Teach auto mode about your environment?" (Yes / Not now / Don't show
again) at the end of a turn once auto mode has blocked several actions and the settings have no
`autoMode.environment` entries. On a delegate it came back every turn, and the delegate's
messages stayed `queued` behind it. Claude Code's documented way to stop it ("Turn off
/auto-mode-setup") is the settings entry `"skillOverrides": {"auto-mode-setup": "off"}`, which
turns off both the command and the offer.

## What was built

- **`Accounts`** writes `skillOverrides` with `"auto-mode-setup": "off"` into both of an
  account's framework settings files, `parent.settings.json` and `delegate.settings.json`, so
  every session the framework starts carries it: a main through the parent file or its
  overlay, every delegate through the delegate file's overlay. `Accounts.skill_overrides/0`
  names the entries the framework owns.
- **The merge rule.** The framework owns the entry, not the whole key. In `prepare/3`, the
  app's `skillOverrides` entries are kept, and the framework's entry wins over the app's for
  the same skill, as `autoContinueAtUsageLimit` already does. A `skillOverrides` that is not a
  map is refused, `{:bad, {:skillOverrides, value}}`, since no entry of it can be kept. In
  `overlay/5`, an agent's entries merge one by one over the account's, and the framework's
  are put back over the result. So a caller that skips `Options` cannot turn the offer on, and
  an account file written before this unit (with no entry) still gives its overlays one.
- **`ClaudeCLI.Options`** checks an agent's `skillOverrides`: a map of skill name to text, and
  never the framework's entry, refused `{:reserved_skill, "auto-mode-setup"}`. A launch option
  refuses each key the framework writes. This refuses each entry it writes in the same way, so
  an app that asks for it learns at once that it gets something else. `@own_settings` keeps its
  whole-key rule for the keys the framework owns whole. `skillOverrides` is not one of them,
  since an app's own overrides for its own skills are its business.
- **Docs**: `Accounts`' and `Options`' moduledocs, `docs/design.md`'s lines on the settings the
  framework writes, and the README status line.

## Tests

- `accounts_test.exs`: the files `prepare/3` writes carry the entry.
- `accounts_overlay_test.exs`: an app's other entries survive `prepare/3` and an agent's merge
  over them one by one. The app's `"auto-mode-setup": "on"` loses in `prepare/3` and in an
  overlay. An overlay of an account file with no entry gets one. A `skillOverrides` that is
  not a map is refused.
- `options_test.exs`: the framework's entry is refused, and so are a value that is not text and
  a `skillOverrides` that is not a map. An agent's other entries are kept as given.

## What I ran into

- The screen already reads this dialog. F-198's `menu` and `menu-down` fixtures are captures of
  it, and `Screen` reads them as `%{state: :dialog, kind: :menu, title: "Teach auto mode about
  your environment?", …}`. `Sessions` puts a running row's menu on the row, and `Prompts` shows
  it to a person as a `dialog` prompt. So item 2 of the unit (add the title as a known kind)
  was not built. See new-1.
- Messages wait behind the offer because a menu over the box is not an idle box. That is the
  right reading: a typed message would go into the menu, not the box. The cost was that the
  offer came back every turn, and this unit turns that off.

## Findings

### new-1. The offer is already read, by its title, as a menu no rule names

What happened: the unit asked for the dialog's title as a new kind in the screen reader's
list, so a row would name it "instead of a generic screen". The reader already names it. Its
generic menu kind carries the title, and F-198's fixtures are this very dialog.

Why: a new kind would take the offer out of the `:menu` path. `Inlet`'s `{:menu, title,
options}` check, `Sessions.Menu` and `Prompts`' `…:menu` prompt all match `kind: :menu`. With
a kind of its own, the offer would stop reaching a person as a prompt, and nobody could answer
it from the panel.

What I did: nothing in `caf_screen`. The existing test (`"menu" => @teach`) already checks the
title is read.

What the design should change: nothing, unless the operator wants the offer told apart in the
panel. If so, the smallest sound step is a label beside the kind (for example `about:
:auto_mode_setup`, read from the title), not a new kind.

### new-2. How Claude Code merges `skillOverrides` across settings sources is not measured

What happened: the docs say user, project, local and `--settings` files all hold
`skillOverrides`. They do not say whether a higher source's map replaces a lower one's or
merges with it entry by entry.

Why it matters: `--settings` sits above user, project and local files, so the framework's
entry should win either way. But if the map is replaced whole, a project's own
`skillOverrides` for other skills is hidden by the framework's file. That has nothing to do
with this entry: any `skillOverrides` an app puts in an account's settings already hides it.
And only a managed setting sits above `--settings`.

What the design should change: a pinned release's check should measure two things on a real
session. First, the offer no longer shows after several blocked actions. Second, a project's
`skillOverrides` entry for another skill still applies beside the framework's file.
