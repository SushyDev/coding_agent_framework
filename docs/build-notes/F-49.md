# F-49: `Sessions` starts, resumes and stops headless delegates

Built against `model/tla/Start.tla` and `Stream.tla` as they are; no spec changed. Each place
in `Sessions` still names the `Start.tla` action it does.

## What was built

- **`Sessions`**, role `:delegate`. A start writes its row first, as today, now with the session
  id the framework chose (`Stream.uuid/0`). Then `Stream.follow/5` makes
  `<home>/streams/<session id>/` and its FIFO; a follow that fails holds nothing and the row is
  `refused{follow, …}`. Then it holds `ClaudeCLI.headless/2`'s argv inside `ClaudeCLI.wrapper/3`
  (and the `cd` wrapper, as for any session), and opens the viewer: a pane running `tail -F` of
  `events.jsonl`, through `Control`, tagged as it opens.
- **The confirmation** of a delegate: the socket is live; `Stream`'s row holds a `system`/`init`
  naming the session id; the pid the wrapper recorded lives, with its start time from `ps` (the
  form `Registry.Liveness` compares); and the socket is still live after that `ps`. The init
  comes after the wrapper wrote the pid, so the pid read then is this process's. Unconfirmed at
  the deadline, the start answers `{:unknown, :no_first_event}`; an orphan row's reason is
  `no_first_event`. The same confirmation serves `Adopt` and `ReRead`, and `Sessions.cue/2` now
  takes `Stream`'s cue (`stream:<host>`) as well as a `Registry`'s.
- **A resume** names `--resume <id>` and follows the same directory again. `Stream.follow/5` on a
  session it knows keeps its row and offset; it first sees an exit not yet seen (so its messages
  settle), then clears `gone`, `live_seen` and `session_id`, so the new process's own socket and
  init are what count. A session whose socket still lives is refused `{:live, socket}`.
- **A stop** of a delegate writes `end_session` through `Stream` and waits for the exit by pid
  and start time, as before. The caller's reading of the turn is not read for a delegate:
  `Stream.Fold.check/2` now refuses an `end_session` while the turn runs (`:turn_running`), in the
  same call that marks it. Past its deadline the row stays `stopping{no_exit}` for `Recoveries`.
- **`ClaudeCLI.wrapper/3`** writes `printf '%s\n' "$$" > "$d/pid"` before its `exec`s (new-1).
- **`Sessions.Table.starting/2`** keeps `session_id` from the start.
- **`HeadlessStandIn`** writes its init at its start, on its first line read, or never
  (`write!/2`'s mode), and is written whole and renamed into place, as F-39 asks.
- **Tests** (`caf_sessions/test/sessions_headless_test.exs`, real tmux, dtach and `Stream`): a
  start confirmed, its pid the stand-in's own and its viewer showing the log; a start whose
  first event never comes (unknown, then `ReRead` running once the init comes and stopped once
  the socket is dead); a stop refused while a permission request holds the turn, then done; a
  resume that reads on from the saved offset, both inits in one log; and after a restart, a
  starting row adopted, an orphan and a `refused{interrupted}`, and two stopping rows settled,
  one stopped and one running. `SessionsSetup` starts a `Stream`, and its interactive launch
  is a parent now: a delegate is headless.

## What I ran into

- `tail -f` of a log that does not exist yet exits at once, and the viewer can open before the
  wrapper's `>>` has made it: `dtach -n` returns once its master runs. The viewer runs `tail -F`,
  which waits for the file (new-7).
- A stop answers once the pid is gone, and the dtach master ends a moment after its process. A
  resume at once can find the socket still live and be refused; the resume test waits for the
  socket to go (new-4).
- `mix test` run inside `apps/caf_sessions` fails on the umbrella's `:only` options; run it at
  the root with the app's test path.

## Findings

### new-1. A headless session's pid does not come from a session file

What happened: the design says `exec` makes `claude` the held process, "so its pid is the one its
session file names", and `Registry` matches a session file by `name`. No build note shows that
Claude Code 2.1.322 writes `<config>/sessions/<pid>.json` in `-p` mode; the strings of the
pinned binary show the file's writer (`concurrentSessions`, kinds `interactive`, `bg`, `daemon`,
`daemon-worker`) but not whether `-p` reaches it; the headless command has no `--name` (F-34
new-5); and the stand-in writes none.

What I did: the wrapper records its own pid, which `exec` keeps, in `<dir>/pid`, and `Sessions`
reads it only after `Stream` has read the init naming the session id, with its start time from
`ps`, and then checks the socket again. No process is found by its name.

What the design should change: add the pid line to the wrapper in "Headless delegates", say that
a delegate's pid is the one its wrapper records, and name it in the **dtach** rule beside the
session file. Add to the check against each pinned release whether `-p` writes a session file
(its `sessionId` would be the `--session-id`), which could stand in for the pid file.

### new-2. Whether `system`/`init` comes before the first message is not shown

What happened: the start is confirmed by the init, and the stand-in writes it at its start.
F-31 does not say whether Claude Code writes it before it reads its first line.

What I did: `Sessions` does not write the first message; a delegate's brief is a `Stream` write
after the start, for `Delegates`. `prompt:` is not read for a delegate.

What the design should change: add it to the check against each pinned release. If the init
comes only with the first turn, the start writes the brief through `Stream` right after the
hold, before it waits for the init.

### new-3. `Stream.tla` does not model a follow again after an exit

What happened: a resume follows a session whose `Stream` row may be `gone`. The spec's `gone` is
never cleared, and its header leaves the resume to `Delegate.tla` and `Start.tla`, which do not
model the stream.

What I did: a follow again sees an exit not yet seen, then clears `gone`, `live_seen` and the
init's session id and keeps the offset, the messages and the requests. The offset rules are
unchanged, so each event is still read once.

What the design should change: give `Stream.tla` a resume step (the exit seen, then the row
followed again with its offset), and check `NoDoubleRead`, `NoSkippedEvent` and
`ReplayedOrFound` across it. `Fold.check/2` refuses a message whose uuid the row holds
(`:duplicate_uuid`), so an undelivered message resent to the resumed process under its uuid,
as the design asks, is refused today; that spec step should settle how.

### new-4. The exit by pid comes before the socket's end

What happened: `Start.tla` takes a process and its socket as one. In fact `ps` stops listing the
process a moment before dtach's master removes the socket, so a resume right after a stop can
be refused `{:follow, {:live, name}}`, or by the hold.

What the design should change: say whether a delegate's stop also waits for its socket to end,
or whether a refused resume is the caller's to try again.

### new-5. `Recoveries` reopens a delegate's viewer as `dtach -a`

What happened: `Recoveries` reopens every lost viewer with `Holder.viewer_argv/2`; a delegate's
viewer follows its log.

What the design should change: let `Sessions` answer a row's viewer argv, and `Recoveries`
reopen with it.

### new-6. An end refused while a turn runs is now `Stream`'s guard

What happened: "Ending" says `end_session` goes in only after the turn has ended. `Stream`
checked nothing for it, and a check in `Sessions` against `Stream`'s row would read it in
another call than the one that marks it.

What I did: `Fold.check/2` refuses an `end_session` while the row's turn runs, in `Stream`'s own
call. `Stream.tla` does not model the end.

What the design should change: model the end in `Stream.tla` with its guard, beside
`NoResultWait`.

### new-7. A delegate's viewer is `tail -F`, not `tail -f`

What happened: see "What I ran into".

What the design should change: say that the viewer waits for a log that is not there yet.

### new-8. A delegate's directory is named by its session id

What happened: "Headless delegates" names `<home>/streams/<session>/`. Keyed by the name, a new
start of a name that ended would read its old log and fold.

What I did: the directory and `Stream`'s row are keyed by the session id, which a resume keeps
and a new start does not.

What the design should change: write `<home>/streams/<session id>/`.

### Still open: F-34 new-4

A delegate that exits before `Stream` reads it live is never seen gone by `Stream`. `Sessions`
does not yet tell `Stream` that the hold took; its own rows settle by pid either way.
