# F-188: every setting an app passes by hand becomes a config key

An app that moves its tree to `CodingAgentFramework.child_spec/1` (F-169) must find every
setting it passes to a part by hand as a key of `CodingAgentFramework.Config`, checked once by
`Config.new/1`, each refusal naming the key. This unit adds those keys and makes the tree read
them. No test started the real Claude Code.

## What was built

- **`dialogs`**: a startup dialog's kind (`:trust`, `:imports`) to the label of the option to
  press. `Config.dialog/3` is the `dialog:` callback the tree hands `Sessions`: the label when
  the dialog shows it, else `:ask`, so a kind not named, or a label the release does not draw,
  waits on a person as before. None by default. Refused `{:bad, :dialogs}` for another kind, or
  a label empty or with a control character.
- **`secret_file`**: the absolute path of the hooks' secret, which the hooks, the waiter hook
  and `caf-run` post with; `<home>/intake.secret` by default, made by `Intake.secret/1` as
  before. The secret never enters the config. The waiter's port is `ports.intake`, the port
  the hooks already post to, so it gets no key of its own.
- **`restarts`**: the tree's `%{max_restarts, max_seconds}`, OTP's 3 in 5 s by default, handed
  to `Supervisor.init/2`.
- **`extensions` as data**: each `{module, opts}`. The module implements the new
  `CodingAgentFramework.Extension` callback `bundle(opts, part)`, which answers the bundle as
  before (`%{name, scope, tools}`). `part` is a lookup of a part's process by its key, called
  when a tool runs, so a tool reaches the live part after a restart. `Config.new/1` makes the
  bundles with a lookup that answers nil and checks them with `MCP.extensions/3`; the tree makes
  them again with the live lookup when `MCP` starts (`Config.extensions/2`). An option that
  holds a function, pid, port or reference is refused `{:not_data, module}`; a module with no
  `bundle/2` `{:not_an_extension, entry}`; a raise `{:raised, module, message}`. The old form, a
  bundle map with its functions, is now refused.
- **`parts`**: each part's own plain-data options, by its key in the tree, checked against a
  table (`Config.parts/0`) of each option's type: ms, ms under a bound, a count, a path, or a
  value by `Scheduler` class. The tree merges them over its own wiring for every part it starts
  (`Config.options/3`, in `start_part/4`) and for the `Holder`. A part or option the table does
  not hold, or a value out of shape, is refused `{:bad, :parts, {part, option}}`. `Intake`'s
  four deadlines are bounded under their hook's timeout less the margin `Intake.Plug` waits past
  them, since a longer one would let Claude Code's own timeout answer first.
- **`start_part/4`**: a build may answer `{:refused, reason}`, which fails that part's start
  with the refusal (an extension that refuses at the tree's start, not at the config's check).
- **Docs**: an example per new key in `Config`'s module doc (doctests where they need no
  module), the tree's module doc, and a config table in the design's "The app's surface", which
  had none (new-1). "Extensions" says the config names a bundle as data.

Reported, not built:

- `Sessions`' `open_to:` is no setting: it is the tree's own read of its `Mailbox`
  (`Mailbox.open_to/3`), which the tree already wires. Nothing in it is the app's to choose. Who
  may message whom is `Grants`', from the agent tree and the operator's name.
- The viewer's size (`Sessions`' and `Recoveries`' `size:`): plain data, but two parts that
  must agree (a viewer `Recoveries` reopens at another size than `Sessions` opened it). One key
  for both is new-2.
- `Mailbox`'s `frame:`, a function of a row's text and its sender: the app passes one by hand
  today (it names the sender's account). It is a function, so not plain data (new-3).
- `tool_hooks` stay functions, as F-169 decided.
- The test seams (`clock:`, `timer:`) and each call's own `timeout:` are not settings.
- Everything else a part takes is the tree's wiring: a part's process, a table's file, the
  host's programs, or a function over another part.

## What was measured

- `ConfigTest`, 5 new tests: `dialogs`, `secret_file`, `restarts` and `extensions` each
  accepted, defaulted and refused; and one over every option of `Config.parts/0` (33), each a
  value of its type passed over the wiring, absent leaving the wiring alone, and one out of
  shape refused naming the part and option.
- `SurfaceTest`: the extension test now names a module and its options, and the whole tree
  runs with an extension, a secret file outside the home, a restart budget, a dialog answer and
  two parts' options: the tool is served and reaches the live `Mailbox` through its lookup, the
  hooks post with the named file's secret, and the home holds no `intake.secret`.
- Doctests: `Config.parts/0`, `Config.options/3`, `Config.dialog/3`'s and the defaults'.

## What I ran into

- The brief names `Mailbox`'s `open_to:`; the option is `Sessions`', and it reads `Mailbox`.
  See "Reported, not built".
- `Scheduler`'s `queue_bound:` and `max_wait:` by class are read with `Map.fetch!/2`, so a map
  missing a class would crash the `Scheduler` at that class's first request. The config refuses
  a map that does not hold every class of `Scheduler.Queue.classes/0`.

## Findings

### new-1. The design had no config table

What happened: the brief says "the design's config table gains each key"; "The app's surface"
listed the config's contents in one sentence, and `Config`'s module doc was the only list. What
I did: added a table of every key, its meaning and its default, beside the sentence, and kept
the module doc as the place for each key's example. What the design should change: nothing more;
a unit that adds a key adds its row.

### new-2. One viewer size for the parts that open viewers

What happened: `Sessions` opens each viewer at its `size:` and `Recoveries` reopens a lost one at
its own `size:`, both `{200, 50}` by default. Two keys could drift, and a reopened viewer would
then draw at another size. What I did: no key. What the design should change: one config key,
`viewer: {columns, rows}`, the tree hands both.

### new-3. A row's frame is a function the app passes by hand

What happened: `Mailbox`'s `frame:` frames a row's text with its sender; the app's own tree
passes one that names the sender's account. The tree passes none, so `Mailbox.frame/1` frames
every row. What I did: nothing; a function is not a config value. What the design should change:
either the framework's frame names what the app needs (the sender's account is in the agent
row), or a frame is named as data, a module and its options, as an extension is.
