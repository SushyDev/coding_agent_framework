# F-65: `CaptureScreenTest`'s blank capture

## What was built

`bin/capture-screen --dry-run` now takes a capture only when the pane shows what the state is
defined by, not when it first shows the state's name.

- `shows` captures the pane once and checks the stand-in's name and `screen_holds <state>` in
  that one capture, with the running-or-exited check it had.
- `screen_holds` answers what a state's screen holds besides its name. Only `text-typed` has an
  answer: the box with the whole typed text in it, `│ > hello from the capture script `. Every
  other state is defined by its name alone.
- The deadline is the one it had: 10 s, then the script ends with "the stand-in did not reach
  <state> within 10 s". A real run, where the person says when the pane shows the state, is
  untouched.
- `CaptureScreenTest` asserts that `text-typed.txt` and `text-typed.ansi` hold the whole typed
  text. That is the regression test for the cause below; the assertion `escaped =~ "\e["` the
  flake tripped is unchanged.

The cause was in the script, not the test.

## What was measured

The measurements ran the script itself 20 to 40 times in a loop, each run with its own home,
temporary and output directories, and checked each capture: the name in each `.txt`, an escape in
each `.ansi`, and the whole typed text in `text-typed.txt`. "Under load" is 30 busy loops on a
15-core machine.

| Script | Load | Runs | `text-typed.txt` cut short | blank or escape-less capture |
|---|---|---|---|---|
| before | none | 30 | 28 | 0 |
| before | 30 busy loops | 30 | 30 | 0 |
| before | 30 busy loops | 20 | 20 | 1 (`text-typed.ansi`, one non-empty line) |
| after | none | 20 | 0 | 0 |
| after | 30 busy loops | 40 | 0 | 0 |

The one test, `mix test test/capture_screen_test.exs:32 --repeat-until-failure 50` from
`apps/caf_test`, with the same 30 busy loops: before, with the new assertion, it failed on 6 of 6
runs; after, it passed 51 times in a row (the first run and 50 repeats) and exited 0. A run of the
script took about 1.9 s unloaded and 3.7 s under that load, far from the 10 s deadline.

## What was found

The brief and F-51's new-11 guessed that a capture was taken before the pane had drawn. It was
taken before the pane had finished drawing one state, `text-typed`:

- The stand-in redraws the whole screen after every key it gets: `\e[H\e[2J`, then the lines,
  then its name last.
- The script types the 29 characters of "hello from the capture script" with one `send-keys`.
  `shows text-typed` was true as soon as the first key's draw put `[stand-in: text-typed]` on the
  screen, so `step` captured while the stand-in was still drawing the rest.
- That left `text-typed.txt` with a cut-off text in nearly every run (`│ > hello from the capt`),
  which no test looked at. The two captures of a state are separate `tmux capture-pane` calls, so
  `text-typed.ansi` could also land in the window between a draw's clear and its lines. That is
  the blank capture the test read. It needs a loaded machine, which is why it showed once in six
  `gate-test` runs and once in about a hundred runs of the old script here.
- No other state has this: each is reached by one key, or by a line whose last key, Enter, is
  what draws the state, so the stand-in is idle in `read` when the script captures.

A real run is not affected: the person presses Enter when the pane shows the state, and Claude
Code draws its own box.

## What was run into

- The tmux socket path has to be under 100 bytes and the home path must not wrap in the 120-column
  screen, so the loops ran under one short directory below `/tmp`, not the scratchpad.
- `--repeat-until-failure N` runs the test N + 1 times.

- `devenv test`: exit 0, and its log ends with `devenv test: every gate ran: check-versions

- `devenv shell -- gate-test`: six runs. Runs 2 to 5 exited 0 with no `^Failed:` line. Runs 1 and
  6 exited 2, each with two `^Failed:` lines, and none of them is in this unit's files:
  - Run 1: `RegistryTest` property "reads count and name every file, and each cue names only ids

    before its last reply is settled stopped, then resumed" failed on `row_when` timing out, the

  - Run 6: the same property timed out, the same `SessionsHeadlessTest` test failed, and so did

  - `caf_test`, with `CaptureScreenTest`, passed in all six runs.
  - The machine was shared with other sessions: its one-minute load average read 7 to 26 when I
    looked between and after the runs. I did not measure it during runs 1 and 6.

## Findings

### new-1. `RegistryTest`'s generated-files property runs close to its 60 s timeout

What happened: the property "reads count and name every file, and each cue names only ids it
wrote" (`apps/caf_registry/test/registry_test.exs:176`, `max_runs: 15`) timed out after 60000 ms in
two of six `gate-test` runs, on a shared machine. In the four runs that passed, the whole
`caf_registry` app took 35.7 s, 42.3 s, 59.1 s and 49.0 s. I did not time the property apart
from the app, so "nearly all of it" is a reading of `registry_test.exs`, where it is the one test
that runs 15 generated cases with files on disk.

Why: not measured. The times above are of the app, not the property, and every run but the two
that failed was under 60 s only by a margin that load can take.

What I did: nothing, as it is not this unit's file.

What the design should change: if the property is what takes the time, give it fewer runs, a
smaller generator or an explicit `@tag timeout` with a reason. It is the likeliest next
`gate-test` flake after this one.

### new-2. `SessionsTest` "F-61: RunningSettled ..." fails on the same wait as the known race

What happened: in `gate-test` run 6, `apps/caf_sessions/test/sessions_test.exs:180` failed with
`row_when(ctx, "crashed", &(&1.status == "stopped"))` returning `{:timeout, %{...}}`, the way
`SessionsHeadlessTest` "a running delegate killed before its last reply ..." does.

Why: not looked into. Both settle a row whose process was killed, and both wait on `row_when`, so
the cause may be the same one the other unit is fixing.

What I did: nothing. It did not fail in the five other runs.

What the design should change: if the other unit's fix is in the settle and not in the
`SessionsHeadlessTest` test, check that `SessionsTest` at line 180 is covered by it.
