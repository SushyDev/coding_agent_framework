# F-254: answered prompts are read, and a person can set a prompt aside

## Why

An app that embeds the framework kept its own copy of every ask, only to show what was answered
and to let a person set a prompt aside. `Prompts.read/3` answers open prompts only, and there
was no mark for "set aside".

## What was built

- **`Prompts.answered/3`**, a call of its own, not a `:closed` filter on `read/3`. `read/3` is
  one function of the owners' live rows; a closed prompt has no owner's row that still shows
  it, so it has a different source (the ledger), a different shape (choice, by, at, reason) and
  needs a page and a bound, which an open list does not. A filter would have made one call
  with two sources and two shapes.
  - It reads two facts `Acts` already keeps: the `opened` fact (F-202) of each prompt, and the
    `answer` row (F-194) that `answer/5` writes. No new copy; open prompts still keep no row.
  - The `opened` fact's detail now also carries the prompt's parent, project, subagent, text
    and options, so a closed prompt shows what was asked. A fact written by an earlier build
    reads those as nil.
  - The read before an answer (`{:get, id}`) records the open too. Before, only a cue's read
    did, so a prompt answered before any cue had no `opened` fact.
  - Status: `answered` (choice, by, at), `withdrawn` (an ask; reason, by, at), `unknown` (an
    answer's owner did not say whether it took it; its reason), or `closed` (it left with no
    answer through the inbox; no one named).
  - Paged by the `opened` fact's ledger id, newest first: `limit:` 1 to 200 (50 by default) and
    `before:` the last page's `next`. It pages by when a prompt opened, since that is a fact for
    every prompt, while the close time is known only for those answered here. One SQL read takes
    `limit` plus the count open now, so a page is full whatever of it is still open.
- **A hidden mark**: `Prompts.hide/3` and `unhide/3`, by id, with who; the time is the fact's.
  The mark is a fact in `Acts` (act `hide` or `unhide`, actor the person, target the prompt's
  id, no state, so each is a row of its own), in the framework's store (`caf.db`). No new table.
  - `read/3` gives each prompt `hidden: nil | %{by, at}`, the latest of its facts, and takes a
    `hidden:` filter (`false` leaves hidden ones out, `true` keeps only them).
  - On close the mark is **ignored**, not deleted: marks are read only for the prompts open now,
    and the ledger is never pruned.
  - A hide of a hidden prompt is refused `{:hidden, mark}`, an unhide of a shown one
    `:not_hidden`, and either of a prompt not open `:settled` or `:no_prompt`, as `answer/5`.
  - The check and the write run in one step of the `Prompts` process, so two marks of one prompt
    are taken in turn. The read after it cues `prompts` at once: the moved check now compares
    each prompt's status and mark.
- **Facades**: `CodingAgentFramework.answered/2`, `hide/3`, `unhide/3`, and the `hidden:` filter
  on `prompts/2`; the example console's `answered/2`, `hide/2`, `unhide/2`, and `prompts/2`
  shows "hidden by". No MCP tool: the operator's MCP tools are the agents' surface, and a
  hide is a person's console act. `caf_prompts` now declares `caf_store`.
- `docs/design.md`: the app's calls, and "Prompts"' built-so-far.

## Model

No model change. A hide cannot race an answer into a different press: nothing on the answer
path (`answer/5`'s read, `choose`, the owner's guard, the owner's press) reads the mark. A hide
during a press only adds a fact; the prompt then closes as it would, and its mark is ignored.
`Prompt.tla`'s `OneAnswer` and `OnlyRightful` are about the owner's guard, which is unchanged.

## Tests

In `apps/caf_prompts/test/prompts_test.exs`, on the real owners:

- an answered startup dialog, an ask answered by an agent's name and an ask withdrawn read
  closed, newest first, with choice, who, time and reason; bad pages are refused;
- a hidden ask is listed `hidden`, left out by `hidden: false`, refused a second hide, brought
  back by `unhide`, hidden again, then answered by `answer/5` as any prompt, and reads closed
  with its answer; a hide of it then is refused `settled`;
- five asks, four answered: pages of two, newest first, the cursor to the next, the open one on
  no page.

## Findings

### new-1. A prompt closed by the framework's own default reads `closed`, with no one named

What happened: the brief asks who answered, "the framework's own default" among them. Only an
answer through `Prompts.answer/5` is a row keyed by the prompt's id. A default each owner takes
itself (a start's `limit` wait at its deadline, a `usage_credits` stop, a `dialogs:` press from
the config), a press on the pane, and an agent that ended all close a prompt with no such row.
Their owners record them, but under their own acts (`answer_startup`, a start's `waited`, the
limit's `by`) and keys, or on a row that a later state writes over.

Why: the inbox's ledger row is written by `answer/5` alone.

What I did: such a prompt reads `status: "closed"`, `by`, `at` and `choice` nil. I did not join
each owner's own records per kind.

What the design should change: I recommend that each owner that takes a default through
its own path write it through `Prompts.answering/4` with actor `framework` (one row per prompt,
as `answer/5`'s), so `answered/3` names it with no join per kind. The other way is a `closed`
fact the inbox writes when a read finds a prompt gone, which gives the time but not who.

### new-2. Closed prompts page by when they opened, not by when they closed

What happened: "paged by time, newest first". Only the open time is a fact for every prompt.

What I did: pages by the `opened` fact's order. A long-open prompt answered just now appears
below newer ones.

What the design should change: if an app needs close order, new-1's row for every close gives
each one a close time, and the page can then be ordered by it.
