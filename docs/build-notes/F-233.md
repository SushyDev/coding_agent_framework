# F-233: the operator reloads an interactive agent's plugins

Branch `framework/f-233-reload`, from `main` at 638c8f8. An app's panel lets a person reload a
running session's plugins after a plugin changed, by typing `/reload-plugins` into it. On the
framework the app may not type into a pane itself, since the framework owns every write, and no
framework call did it. The MCP `reload` tool only lists the caller's own tools again.

## What was built

- **Screen.** `Screen.result/3` reads a typed command's result line, for a caller that typed
  it: only on an idle screen with an empty box, the line under the last prompt echoed above the
  box (`❯ ` and the command), when the release's pattern matches it. It answers the lines above
  the box too, so a caller tells a result drawn after its Enter from one drawn before. Each
  release's reading names its commands (`commands:`, by the text typed); 2.1.322's names
  `/reload-plugins`, its result modeled, not captured (new-1).
- **Inlet.** `Inlet.reload_plugins/3` types `/reload-plugins` as `type/4` types a text, with
  the same checks in one step of the `Inlet`: the turn by `turn:`, an idle screen with an empty
  box, the text seen in the box, then Enter on its own. The step answers the lines above the
  box read before the text went. Then the caller reads the screen, one capture a call, until
  the result line shows under the echo and the lines above the box changed (`result:` ms,
  10 000 by default). Answers `{:ok, :reloaded}`, refusals as `type/4`'s when nothing was
  typed, and `{:unknown, {:no_result, reading}}` past the bound.
- **Mailbox.** `Mailbox.reload_plugins/3` gives the `Inlet` the turn a typed message's write
  reads in its own step (the agent's row, its session file, its waiter), so a reload goes only
  where a message could be typed. It refuses `:headless` for a headless delegate, `{:no_agent,
  name}` and `:no_inlet`. The `Inlet` works in a task that answers the caller, so `Mailbox`
  waits on no pane. The task's guard against a raise is the hand-on's, now one function.
- **MCP and Operator.** `reload_plugins(agent)` is an operator's tool, refused
  `:operator_only` to an agent and listed to none, as `answer_startup`, `end_main` and
  `withdraw` are. `Operator.reload_plugins/2` calls it. The act is a row in `Acts` with no
  state, written before it acts and settled by the answer (`Acts.answered/4`), as the forced
  `end_main`'s is: a reload moves no state of the agent's and may be made again, so a claim on
  its state would refuse the next reload, and the next interrupt or answer of that state too.
  Answers `%{done: :reloaded, act: id}`.
- **Stand-in.** `ScreenStandIn` draws `❯ /reload-plugins` and a modeled result line above the
  box at an Enter with that text in the box, one pair per reload; written with
  `reloaded: false` it draws the echo alone.
- **Tests.** `Inlet` on a real tmux server and the stand-in: two reloads in a row each answer
  `ok`, the second told from the first by the lines above the box; a turn the session file
  reads as a dialog, a turn running, a menu shown and a person's draft in the box are each
  refused, and nothing is typed; a reload whose result never comes is unknown and typed once.
  `Mailbox` over real `Sessions`, `Registry` and `Inlet`: a main session's reload answers
  `ok`; a headless delegate is refused `headless`. `MCP`: the operator's two reloads are two
  acts, settled `verified`; an agent is refused; a headless delegate's refusal is settled
  `failed` with its reason. `Screen`: a result under another prompt is not read; a running
  screen or a box with text is refused.

## What was measured

- Nothing on the real Claude Code: this machine has no logged-in setup (`CAF_REAL_SETUP` is
  unset), and `bin/capture-screen` needs a person and a logged-in account's directory. So
  `/reload-plugins`' result line and how long it takes on 2.1.322 are not known (new-1).
- On the stand-in, which draws the result as it takes the Enter, the reload's time says
  nothing about the real one. The `Inlet`'s 15 tests, the three new ones among them, ran in
  6.5 s.

## What I ran into

- The brief says `Inlet` already types `/mcp reconnect`. It does not: no code types it, though
  the design's `Inlet` row names it (new-2). The reload follows `type/4` instead, and is the
  first typed command whose result line is read.
- A first version waited for the result line inside the `Inlet`'s step. The `Inlet` is one
  process per host and writes for every session there, so a typed message behind a reload
  would wait up to the result's bound and could time out unknown. The result is now read by
  one capture a call, after the step ends (new-5).
- An operator's reload is the operator's alone here. The brief named it "an operator fix"; a
  parent's reload of its own delegate is not built.
- `mix test` from one app's directory fails on the umbrella's lock; tests run from the root.

## Findings

### new-1. `/reload-plugins`' result line and duration are not captured

What happened: no logged-in setup was at hand, so the real result line was not captured.
2.1.322's reading models it on a captured prompt's result (the usage limit's notice): `  ⎿  `
then a line that starts with `Reloaded`. The bound, 10 s, is a guess.
Why: `bin/capture-screen` needs a person and a logged-in account.
What I did: the reading's comment and the stand-in say it is modeled.
What the design should change: the next real run (`mix test.real`, or `bin/capture-screen`
with a reload state added) captures the screen after `/reload-plugins` on 2.1.322, with a
plugin installed and with none, and times it; the reading's pattern and the bound follow it.

### new-2. No code types `/mcp reconnect`

What happened: the design's `Inlet` row lists `/mcp reconnect` among the typed commands it
types, and F-162's new-2 routes `reload` through it, but no code types it.
Why: it was designed, never built.
What I did: built the reload on `type/4`'s checks and `Screen.result/3`, which `/mcp
reconnect` can use as is, a pattern in the reading and one function in `Inlet`.
What the design should change: the `Inlet` row says `/mcp reconnect` is not built yet, until a
unit builds it on the same path.

### new-3. The slash command menu may change what the box shows

What happened: Claude Code opens a menu of commands under the box once `/` is typed. Whether
2.1.322 still draws the box as one line holding `/reload-plugins` with that menu open, and
whether Enter then sends the text or the menu's highlighted entry, is not captured.
Why: no capture of a slash command being typed.
What I did: nothing; the stand-in draws no menu. If the menu changes the box, the reload
answers `{:unknown, {:not_seen, reading}}` with the text in the box and no Enter.
What the design should change: the capture of new-1 includes the screen with
`/reload-plugins` typed and not sent.

### new-4. A refused reload is a fault in the ledger

What happened: a reload refused for a turn running is settled `failed` by `Acts.answered/4`,
and the fault ledger lists every `failed` row. A busy session refusing a reload is not a fault.
Why: one rule settles every answer, and the ledger reads every `failed` as one.
What I did: kept the one rule, as the forced `end_main` does.
What the design should change: decide whether a refusal that acted on nothing and waits on
no one (a reload, a forced end's refusal) is settled with an outcome the ledger leaves out.

### new-5. A typed message may go in between a reload's Enter and its result

What happened: the result is read after the `Inlet`'s step ends. In between, the screen is
idle with an empty box, so the `Inlet` may type a message the mailbox hands it. The reload's
echo is then not the last prompt, and the reload answers unknown; the message is not harmed.
Why: the alternative held every write on the host for up to the result's bound.
What I did: read the result outside the step, and recorded the unknown.
What the design should change: nothing unless real reloads take long; if they do, `Mailbox`
holds its typed rows to a session while a reload of it is open.

### new-6. The reload's result read has no model

What happened: the reload's write is `Delivery.tla`'s typed write under its existing guard
(the same `Inlet` step, the same turn read), so no spec changed. What is new, the result read
after the step and an act that claims no state, is in no spec.
Why: the brief named no model change, and the claimless act is the forced `end_main`'s,
which `Claim.tla` does not model either.
What I did: nothing in `model/tla/`.
What the design should change: if acts with no state grow (a reload, a forced end), `Claim.tla`
gains a row with no state that never blocks a claim, so `OneActPerState` is checked beside it.

### new-7. Fast model configurations pass 30 s on a loaded host

What happened: in `devenv test`'s `gate-model`, five fast configurations took over 30 s:
`Copy_Forward` 32 s, `Copy_Turns` 39 s, `Delegate_Design` 40 s, `Prompt_Holds` 35 s,
`Team_OperatorMessage` 36 s. This branch changes no spec. Run again one at a time they took
22, 17, 20, 29 and 36 s; `Team_OperatorMessage` has 83,551 states, and the host's load average
was 43 during that run (26 to 30 through the gates).
Why: other work on the machine; TLC uses every core.
What I did: nothing in `model/tla/`.
What the design should change: the 30 s rule is checked on a quiet host, or `bin/check-model`
names its load beside each time, so a slow run on a busy host is not read as a spec grown too
large.
