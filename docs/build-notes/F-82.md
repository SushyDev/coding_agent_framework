# F-82: `Jobs` after a restart: no fetch left behind, no caller left untold

## What was built

- `jobs` gains a `worktree` column, the path the job's fetch writes into. A file made before it
  gains the column on open, as `Sessions.Table` adds its columns. `run` writes it with the row.
- `Copies.sweep_fetch/1` removes the `.caf-fetch-<digits>` folders directly under a worktree and
  nothing else; `fetch/5` and the sweep share the prefix. At its start `Jobs` calls it for the
  worktree of each row whose job had ended (`exited` or `timedout`), the only rows that began a
  fetch. A path not under such a row's worktree is never touched, and no pattern reaches outside it.
- A row a restart left `asked` (nothing reached the host) becomes `interrupted`, owed, and is
  handed to `:on_late_end` once as `{:refused, :interrupted}`, then marked `told`; it is never
  retried or run. A `starting` row the host reads `refused` is still handed on as
  `{:refused, {:start, :not_held}}`. Both are "not an end": the job never ran. The moduledoc says so.

## Measured

Tests: a restart leaves no fetch folder under a row's worktree and leaves a folder outside it, a
non-matching name, and a nested one alone; an `asked` row is handed on once as interrupted across
two restarts and nothing runs; an older file gains the column.

## Ran into

The test plants the folder a cut fetch leaves rather than cutting a real rsync across a
restart: the real cut races the fetch's own removal. The planted folder is what the restart leaves.
