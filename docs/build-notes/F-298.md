# F-298: every session the framework starts may use the Artifact tool

## What was built

- The operator's rule (ask 559, answered "mains and delegates"): every settings file the
  framework writes allows Claude Code's `Artifact` tool. That tool publishes a private page.
- `Accounts.allowed_tools/0` is `["Artifact"]`. `prepare/3` writes it into `parent.settings.json`
  and `delegate.settings.json`, and `overlay/5` writes it into each agent's own file. It goes
  after the caller's `permissions.allow` rules, with no duplicates.
- Like F-285's `skillOverrides` entry, it is put over the merged file. So an account file written
  before F-298, or a caller that skips `Options`, still gets it.
- A `permissions` value that is not an object, or an `allow` that is not a list, is refused as
  `{:bad, {:permissions, value}}`.

## Why

Auto mode's check refused the tool as "Unsanctioned Communication" whenever the request reached a
main session in a message, and not as a prompt the operator typed. The operator then had to type
the request again in the session.

## What was measured

- The settings files on disk, in `accounts_test.exs` and `accounts_overlay_test.exs`.
- Not measured: that 2.1.322's auto mode honors a plain tool-name allow rule for `Artifact`
  before its check. The docs say allow rules are applied first. A logged-in run with `caf_real`
  would show it: start a main, send it a message asking it to publish, and read the screen for a
  permission prompt or a refusal.

## Findings

### new-1. The allow list is the framework's, in code

- **What happened:** the operator asked for one tool. The list lives in a module attribute.
- **Why:** the design has no config key for rules the framework adds.
- **What I did:** nothing more.
- **What the design should change:** if a second tool is added, consider making the list part of
  `prepare/3`'s data with this as its default.
