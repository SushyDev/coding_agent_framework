# F-109: the operator: a person or the app acting through the same checks as a parent

The order of the units, item 10 (F-108): the operator, a parent of every main session and so of
every agent, acting through `Grants` and claims, recorded as the actor, its messages through
`Mailbox`. All four parts of the brief are built.

## What was built

1. **The model** (`Team.tla`). A constant `Operators`, `{}` or `{o}`, outside the agents
   (`ASSUME Operators \cap Agents = {}`: its name is reserved). `Actors` is the agents and the
   operator, and the operator is a caller of `Send`, `ClaimTaken` and `ServiceFixed`, through the
   same steps and guards as an agent: `Edge`, `MayFix` and `MayFixService` hold for it on any
   agent; a claim of it is refused on a state already claimed, by anyone; its fix acts only on
   the state it claimed; its message is typed only into an ended turn, in its order. It owns no
   service: `ServiceStarts` is the agents' only, and `MayHand` never hands to it. `Stoppable`
   refuses a stop of a main session, so a main session still never ends. `MainNeverFixed`
   becomes `MainFixedByOperatorOnly`; `OnlyParentFixes`, `AlongEdges`,
   `ServiceFixedByOwnerOrParent` and `TypeOK` take the operator in. Five Breaks, one per new
   guard: `OperatorTwoClaims`, `OperatorStaleFix`, `OperatorIntoRunningTurn` (the operator's
   path skips a guard a parent's takes), `OperatorStopsMain` and `HandToOperator` (it may do one
   wrong thing more). Every earlier configuration sets `Operators = {}` and keeps its state space;
   four new ones set `{o}`. `READING.md` says how to read it.
2. **`Grants`**: `new/2` takes `operator:`, a name other than `framework`. The operator is known
   to every check: `may_message?/3` and `may_read?/3` to any agent, and no agent to it;
   `may_fix?/3` on any agent, a main session included (no agent's is: the reason is now
   `:main_fixed_by_operator_only`); `may_fix_service?/3` on any service; `may_use?/2` open.
   `may_start_delegate?/3` takes the parent: a main session for itself, the operator for any
   main session. `may_start_service?/2` refuses it (`:operator_owns_nothing`), and `may_hand?/4`
   never hands to it. A tree that names an agent with the operator's name refuses every check
   with `{:reserved, name}`.
3. **The app-level API**: `MCP.operate/3` calls a tool as the operator through `answer/5`, the
   path every agent's call takes: the row in the call log is written under the operator's name
   before it acts, then the same `act/5` with its checks and claims, then the outcome. A
   `start_delegate` or `run_delegate` of the operator names the main session as `parent` (an
   agent's `parent` argument is still never read); a fix of the operator's acts as the target's
   parent would in `Delegates`, with the claim in the operator's name. `issue/2` never makes the
   operator a token. `CodingAgentFramework.Operator` (in `caf_mcp`) names each act as a plain
   function: `start_delegate`, `message`, `interrupt`, `answer`, `resume`, `stop`,
   `service_send`, `service_restart`, `service_stop`. `Mailbox.notify/4` refuses the operator as
   its target, since nothing would deliver to it.
4. **`caf_example`**: the config's `operator` (`"operator"` by default, never `framework` or a
   main session's name) goes to the one `Grants` every part shares.

## Tests

- `Grants`: the properties over generated trees take the operator in (`AlongEdges`,
  `OnlyParentFixes, NoSelfFix, MainFixedByOperatorOnly`, `ServiceFixedByOwnerOrParent`,
  `HandedAlongEdge`); a test of what it owns and of its reserved name; the start check with a
  parent.
- `MCP`: the operator starts a delegate under a main session it names (a delegate as `parent`
  is refused), answers the delegate's request under a claim in its own name, is refused a main
  session's fix as not built, reaches `Services` as itself, and gets no token; each call's row
  names it. An agent's fix of a main session is refused.
- `caf_example`: the operator starts a delegate under `app-main`, messages it and interrupts it;
  the call log, the message's row and the claim name `operator`, and the interrupted turn's reply
  goes to `app-main`.

## What I ran into

- F-108, which writes the operator into "Concepts" and item 10, reached `main` while this was
  built; its `docs/design.md` was read from `framework/f-108-app-gaps`, and the branch is rebased
  onto `main`. This branch does not touch `docs/design.md`.
- TLC splits a disjunction inside an action into branches, so `Live(a) == a \in Operators \/
  proc[a] # "ended"` read `proc` of the operator and failed; it is an `IF`.
- `Break_Team_FixMain` passed once `Stoppable` refused every stop of a main session: with no
  fault, a stop was the only fix its wrong grant could make. It now has one fault, and TLC finds
  the other main session interrupting a stuck one.
- The example test first read the message's row once its request was held, and two of three
  `gate-test` runs found it still `sending`: `Mailbox` marks it from `Stream`'s replay, which may
  be read after the request. It now waits on the row.
- One `devenv test` run failed `caf_sessions`' F-64 test (`{:no_exit, …}` where
  `{:socket_live, …}` was expected), on a loaded workstation; this branch does not touch
  `Sessions`, and the other runs passed it.
- The two slow configurations (`slow/Team_Large`, `slow/Team_FaultsLarge`) had no `SelfTurns`,
  so they could not have run since it was added. Both now set it `FALSE`, with `Operators = {}`.
  They were not run.
- A delegate's row knows its parent, so `Delegates.fix_state/3` and `fix/5` are called with the
  target's parent when the operator fixes; `Delegates` itself is unchanged.
- The model lets the operator interrupt or resume a main session; the code refuses it
  `{:not_built, :main_fix}` until `Mains` and `Screen`, as `look` refuses a main session.

## Findings

### new-1. A reply to the operator's message goes to the main session

What happened: `Mailbox` stores a delegate's reply as a message to the delegate's parent, its
main session, whoever sent the message. A message from the operator gets its reply, or the
framework's notice ("Your message … went in"), at the main session, not at the operator.
Why: the design says a reply goes "from the delegate to its main session" (F-77), when only the
main session could send one; it does not say where the operator's goes.
What I did: kept it; the example test asserts the reply goes to `app-main`, and the model keeps
`ReplyToMain`.
What the design should change: say it. Recommended: a reply to the operator's message is stored
addressed to the operator, never delivered, for the app to read by the message's id (say,
`Mailbox.reply/2`), and the notice too; the main session sees it as any action on its child, in
the log.

### new-2. No agent messages the operator

What happened: the operator is a parent of every main session, so the edge rule ("a delegate to
its parent") would let a main session message it. Nothing delivers to the operator.
Why: the design does not say.
What I did: `Grants.may_message?/3` refuses any message to the operator (`:along_edges`), and
`Mailbox.notify/4` refuses it as a target; the model has no edge into it.
What the design should change: say that no agent messages the operator, and that `ask` is how
an agent reaches a person.

### new-3. The operator's `run_delegate` takes the report from the main session

What happened: `run_delegate` as the operator holds the operator's call for the report and marks
it `answered` when the answer is written, so the main session the delegate is under never gets
that report as a message.
Why: `run_delegate` gives the report to whoever waited; with the operator, that is not the
parent.
What I did: built it as the brief's "the same path as the MCP tools".
What the design should change: decide whether the operator's `run_delegate` also hands the
report to the main session (as a message from the delegate), or whether the operator has only
`start_delegate`.

### new-4. A kept service of a main session goes nowhere

What happened: `Grants.parent/2` still answers `:main_has_no_parent` for a main session, though
the operator is now its parent, so a kept service never goes to the operator.
Why: the operator owns nothing, and a main session never ends, so the case does not arise.
What I did: nothing.
What the design should change: nothing now; say, when `Mains` lets a main session end, that its
kept services end with it or go to a person.
