# F-11: a held process's environment from nothing, and every program from `Programs`

## What was built

- **`Holder.hold/4`** builds the held process's environment from nothing: the host's
  `env -i`, then each `{name, value}` of its `:env` option, then `dtach -n`. It is one command,
  run the same way on this machine and over ssh. `Holder.hold_argv/4` gives that command
  without running it. A name that is not a plain variable name is refused as
  `{:bad_variable, name}`, since a name holding `=` would change what `env` reads.
- **`Shell`** sets no environment any more. Its `:env`, `:unset` and `:unset_prefixes` options
  are gone, and with them `{:refused, {:unset_prefix_over_ssh, …}}` and the remote
  `/usr/bin/env`. A caller that needs variables runs the host's `env`. Over ssh, `Shell` only
  quotes. `Shell.command/3` (it was `/4`; its options held only the environment) is pure.
- **`Host`** carries this machine's `kill`: `Host.local(name, kill)` and
  `Host.ssh(name, ssh, destination, kill)`. `Shell` kills a run past its timeout with it. See
  new-1.
- **`Programs`** names `sh`, `rm`, `kill`, `env` and `ps` as well as tmux, dtach, claude, git and
  gh. `Programs.take/2` gives several paths at once, or one refusal naming each missing one.
  `Programs.find/3` still starts from the host's `/bin/sh`, and its doc says why: it must find
  the rest. It is the only fixed program path left in `lib/`.
- **`Holder.new(programs, dir)`** takes dtach, sh, env and rm from the host's `Programs`; its
  scripts run `rm` by that path. **`Tmux.CLI.new(programs, server)`** takes tmux and rm.
  **`Registry`** takes `programs:` in place of `host:` and `ps:`, and runs sh, env and ps from
  it. **`Registry.Liveness.check/3`** runs `env LC_ALL=C TZ=UTC ps …` with the `env` and `ps` it
  is given. Each constructor refuses with `{:no_program, names}`.
- **Tests**: `TestHost.host/0` gives devenv's kill, and `TestHost.programs/2` builds a host's
  `Programs` from the `CAF_` paths. `HolderEnvTest` holds a stand-in on a real dtach socket with
  `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `TMUX` and `TMUX_PANE` set in the test VM's own
  environment. The stand-in sees `HOME`, `PATH`, `LANG` and `CLAUDE_CONFIG_DIR` with the given
  values, none of the four, and nothing else but what its own sh sets. A test shows the remote
  command through `Shell.command/3`'s pure output: the same words, each quoted.
- **`docs/design.md`**: the parts table's `Programs` row names the new programs. The dtach rule
  already said `env -i` with an allow list.

## What I ran into

- A shell stand-in adds variables of its own under `env -i` (such as `PWD`, `SHLVL` and `_`).
  The test runs the same sh under `env -i` alone and allows exactly those names besides the
  given ones. A program held directly, such as `claude`, gets only the given ones.
- `env` reads every leading argument that holds `=` as an assignment. Names are checked, and the
  next word is dtach's absolute path, which holds no `=` in any path seen here.
- The unit is about 650 changed lines, over the 500 aimed for: about 300 in `lib/` (mostly
  docs and the constructors), 220 in tests, and the note.
- The test that sets the leaking variables changes the whole VM's environment, so it is its
  own module with `async: false` and puts the old values back.

## Findings

### new-1. `kill` is this machine's program, not the host's

What happened: `Shell` kills a run past its timeout by its OS pid. That process is always on
this machine: the program itself, or the ssh that reaches a remote host. So the remote host's
`kill` from its `Programs` would be the wrong path.

Why: a run on a remote host is a local ssh process.

What I did: `Host` carries this machine's `kill` next to this machine's `ssh`, given by the
caller (from this machine's `Programs`). A host app that bootstraps must know `kill` before it
calls `Programs.find/3`, the same way it knows `ssh`.

What the design should change: the `Hosts` row could say a host names the programs of this
machine that reach it: `ssh` to start a run and `kill` to end one.

### new-2. `Registry`'s read script runs `cat` through the host shell's `PATH`

What happened: the script that lists and reads session files calls `cat`, which the host's sh
looks up through its `PATH`. `Holder`'s scripts now run only builtins and paths passed in.

Why: `Programs` does not name `cat`.

What I did: nothing; it is outside this unit's list of programs.

What the design should change: `Programs` could name `cat` too, and `Registry` pass its path to
the script as it passes `rm` to `Holder`'s.
