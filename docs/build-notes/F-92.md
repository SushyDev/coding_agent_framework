# F-92: `MCP`, part 3: `start_delegate` and `run_delegate`

## What was built

- `start_delegate(project, branch, model, brief)`: `Grants.may_start_delegate?/2` (a main
  session only), then `Delegates.start_delegate/7` with the caller as parent. It answers
  `{"ok": {"delegate": name}}` at once, or the start's refusal. The report stays held for a
  message; delivering it waits for `Screen`.
- `run_delegate(project, branch, model, brief, timeout)`: as `start_delegate`, then
  `Delegates.await_report/4`, all within `timeout` (ms, capped by `MCP`'s `:cap`, as `run`'s).
  The start takes at most `min(timeout, 300 000)` of it, so the call never waits longer than
  its timeout. It answers `{"ok": {"delegate", "status", "report"}}`, or at the timeout
  `{"unknown": {"delegate": name, "reason": "timeout"}}`. A start that answers unknown is
  passed on as it is: there is no name to give yet.
- `Delegates.await_report(delegates, parent, id, timeout)`: the caller's deadline is set on the
  node's monotonic clock before the request is sent, so time spent in `Delegates`' queue does
  not move it. A report already held is taken at once. Otherwise the call waits, and `hold/4`
  takes it in the same step that holds it, only while the deadline has not passed. Taking a
  report sets the row's `report` to `answered`, which `held/3` never lists. At the deadline a
  timer answers `{:unknown, :timeout}` and the report is held like any other. It also refuses
  a wrong parent, a report already answered, a second waiter, and a refused start.
- `Grants.may_start_delegate?/2`, with its test.
- `MCP` takes a new required option, `:delegates` (`{module, server}`, as `:jobs`).
- A paragraph in `docs/design.md`, "What `Delegates` holds", says how an answered report is
  kept from being delivered too.

Tests: `apps/caf_mcp/test/mcp_delegates_test.exs` uses an MCP client with tokens over a real
`Delegates`, `Sessions` and `Stream`, with the headless stand-in. It checks that
`start_delegate` is attributed by its token, whatever the arguments say, and answers the name.
It checks the refusals: a delegate caller, an agent off the tree, bad arguments, a bad branch,
and a timeout over the cap. It checks that `run_delegate` answers the report and the report is
not held afterward. It checks that `run_delegate` at its timeout answers unknown with the name
and that the report, once the held turn is allowed, is held for a message.
`apps/caf_delegates/test/delegates_test.exs` covers `await_report/4` itself: a refusal for a
wrong parent, the timeout, the held report after it, a report taken by a waiting call, and the
refusal for one already answered.

## Findings

### new-1. A main session with no delegate cannot start its first one through the tool

What happened: `Grants` knows a main session only as a parent that a delegate's row names
("What `Delegates` holds"). A main session that has no delegate yet is
`{:unknown_agent, name}`, so its first `start_delegate` or `run_delegate` is refused. Why:
`Mains` is not built, and the tree is `Delegates`' rows. What I did: the check is strict. The
test's tree names an earlier delegate, `app-old`, so `main` is known. What the design should
change: before the tools are wired into a running framework, either build `Mains`, or let
`Grants.new` take the main sessions from the embedding app as a second function until `Mains`
exists.

### new-2. A report `run_delegate` took lives only in the tool's answer and the call log

What happened: `Delegates` marks the report `answered` before `MCP` writes the HTTP answer. If
that answer never reaches the agent, the report is not delivered as a message either. This can
happen if the connection drops, the framework restarts between the two steps, or the client
gives up first. Claude Code has its own timeout for an MCP tool call, and a `run_delegate`
longer than that timeout meets it every time. What I did: nothing beyond the deadline check.
The call's row keeps the report as its outcome. What the design should change: say that a
`run_delegate`'s `timeout` must be under the client's tool timeout (and have `ClaudeCLI` set
that timeout at launch). Or mark the report `answered` only after the endpoint has written the
answer, and hold it again when the write fails. A restart between the steps still needs a
settle, as a report's `sending` mark has.

### new-3. The service tools are the next part

What happened: they did not fit (above). What the next part needs: the eight tools through
`Services`' own functions, which already make each `Grants` check (`start/5`, `list/1`,
`logs/4`, `send/5`, `wait/4`, `restart/4`, `stop/4`, `hand/4`). `service_start` needs the
caller's copy, which `MCP`'s `:place` gives `run`. Two things the table promises are not in
`Services` yet: `forward:` (F-89's new-1 and new-2) and a line wait from the current start's
offset (F-89's new-3). That part should either leave them out of the tool's schema or wait for
them.
