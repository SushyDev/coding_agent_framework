# F-77: `Mailbox`, part 1: stored messages along the tree, delivered to delegates

`CodingAgentFramework.Mailbox` in a new app `caf_mailbox`, with its table
`CodingAgentFramework.Mailbox.Table` (`messages`). It builds `Team.tla`'s `Send`,
`DeliveryAsked`, `DeliveryTyped`, `DeliveryRefused`, `DeliveryMarked`, `SendingSettled` and
`EndedFirst` for delegates. A main session's delivery waits for `Screen`.

## What was built

- `message/5` checks the strings, then `Grants.may_message?/3`, then stores the row `queued`
  with a uuid of its own, and answers `{:ok, {:queued, id}}`. A refusal stores nothing. The
  delivery runs after the reply (`handle_continue`), so the row is always stored first.
- `status/3` reads a row: `queued`, `sending`, `delivered` or `ended`, and `attempt`, why the
  last delivery did not go in. This is how the sender learns the outcome for now.
- `cue/2`, wired by the embedding app to `Stream`'s and `Delegates`' cues, reads every open row
  again. At its start it first runs `Stream.read/2`, so a restart settles from each log read to
  its end, as `Delegates` does.
- Delivery to a delegate (the latest `Delegates` row of its name):
  - It goes in only when the row is `finished` and its `Stream` row is idle, not gone and not
    ending (new-2 says why `finished`).
  - It takes the addressee's oldest queued message, and only when none to it is `sending`. So
    one message is in flight per delegate, as `Stream` requires, and each sender's messages go
    in order.
  - The row is marked `sending`, with the session id, before `Stream.write/4` gets
    `{:message, uuid, text}`. If `Stream` refuses, the row is `queued` again, with the reason
    in `attempt`. If the answer is unknown, the row stays `sending`.
  - A `sending` row is settled from `Stream`'s row for that session. A replay makes it
    `delivered`. If the exit found it undelivered, or `Stream` never marked the uuid, it is
    `queued` again under the same uuid, which `Stream` accepts once more for an undelivered
    message. A row whose message is still `writing` is left alone, so nothing is resent blind.
  - A delegate counts as ended when its `Stream` row has `end_session` marked and its process
    is gone, or when its `Delegates` row is `refused`. Then its queued rows become `ended`. A
    `sending` row settles first, as in `EndedFirst`. A dead delegate (gone with no end marked)
    keeps its rows queued.
- Delivery to a main session: a name with no `Delegates` row is a main session (`Grants` has
  already said it is known). Its rows stay `queued` with `attempt` `:no_delivery`, written once.
  **Where it will hook in:** the `deliver/4` clause for a `nil` delegate row. With `Screen`,
  that clause checks that the main session's turn has ended and its input box is empty, marks
  the row `sending`, types through `Control`'s checked write with a mark the transcript shows,
  and settles from the main session's transcript after a restart, as a report's delivery will
  (`Delegates.deliver/2`).
- How the sender should learn the outcome later: when a row settles `delivered` or `ended`,
  `Mailbox` stores a notice to the sender as a message of its own, from the framework, and
  delivers it by the same path. That is this part's job, since `Mailbox` owns the row and its
  settle. Every notice so far goes to a main session (a delegate's only sender is its main
  session; a delegate's own messages go to its main session, which has no `ended`), so it waits
  for `Screen` too. See new-3.

## What was measured

`mix test apps/caf_mailbox/test/mailbox_test.exs`: 4 passed. The tests use real `Delegates`,
`Sessions`, `Stream`, dtach and tmux, with the headless stand-in, and are named for the
`Team.tla` properties:

- only along an edge: an unknown name and a delegate to itself are refused, with no row; a
  message to a main session stays queued with `:no_delivery`;
- stored before delivered, only into an ended turn, once, in order per sender and addressee:
  two messages are queued while the brief's turn waits on a permission. After the answer, they
  go in one at a time, first then second, each once (the stand-in's `taken`);
- ended delegate marked: after `end_session`, a queued message settles `ended` and is never
  written;
- restart settles a marked row: one `sending` row whose replay is in the log settles
  `delivered` and is not resent; one marked with no write settles `queued`, then goes in once
  under its uuid.

The gate results are at the end of this note.

## Findings

### new-1. Nothing marks a delegate "ended" yet; `Mailbox` reads it from `Stream`

What happened: `Delegates`' statuses end at `finished` or `failed`. The stop that ends a
delegate after its report is delivered is not built. Why: delivery of a report waits for
`Screen`. What I did: `Mailbox` treats a delegate as ended when its `Stream` row has
`end_session` marked and its process is gone, or when its `Delegates` row is `refused`.
A `failed` delegate (killed twice) is treated as dead, so its messages wait for a resume
by its parent. What the design should change: give `Delegates`' row an `ended` status, written
once the stop is done, and have `Mailbox` read only that. Today a row `failed` for good has
messages that wait until that status exists.

### new-2. "Only into an ended turn" for a delegate means "after its report is held"

What happened: a delegate's brief's turn ends with its report, and `Delegates.Turn.next/2`
takes the fold's last `result` after the brief as the report. If a message went in between the
brief's `result` and `Delegates`' next cue, the message's turn's result would become the report.
What I did: a delegate takes a message only once its `Delegates` row is `finished`. What the
design should change: say so in "Messages", or have `Delegates` take the result whose
`user_message_uuids` names the brief's uuid, so the order of the two readers does not matter.

### new-3. A delegate's reply to a message reaches no one

What happened: a message to a finished delegate starts a turn, and its `result` is read by no
part. `Delegates` has left `running`, and `Mailbox` only settles the message as `delivered`.
What I did: nothing. What the design should change: decide whether such a reply goes back to
the main session as a message from the delegate, stored by `Mailbox` from the `result` that
names the message's uuid. That would be part 2, with the sender's notice of `delivered` or
`ended`, once `Screen` makes delivery to a main session possible.

### new-4. `Team.tla`'s header says `Mailbox` types through `Control`

What happened: the header says `Mailbox` "types through Control's checked write". For a
delegate it writes through `Stream`, under a uuid, and settles from the replay. What I did:
followed "Headless delegates". What the design should change: the header should name `Stream`
for delegates and `Control` for main sessions. The actions are the same.

### new-5. `Mailbox` and `Delegates` read a `Stream` message's outcome the same way

What happened: both read `fold.messages[uuid].state` (`writing`, `delivered`, `undelivered`,
or absent) to decide whether to write, wait or settle. `Delegates.Turn.next/2` and
`Mailbox`'s `settle_sending` each spell it out. Their test setups repeat each other too.
What I did: followed `Delegates` without sharing code, as the brief asks. What the design should
change: a `Stream.Fold` function that names the outcome of a uuid (`:delivered`, `:writing`,
`:undelivered`, `:none`), used by both, and a `DelegatesSetup` in `caf_delegates/test/support`
for the tests of the apps above it.

### new-6. A delivery holds `Mailbox` for up to one `Stream` write

What happened: `Stream.write/4` runs inside `Mailbox`'s process, with a 5 s deadline (up to
15 s for the call). A `message/5` that arrives meanwhile can answer `{:unknown, {:timeout, _}}`
after its row is stored. What I did: nothing; the answer is truthful and `status/3` reads the
row. What the design should change: if it matters, the write can run in a task, as `Delegates`
runs `Sessions`' calls, with the row `sending` as its claim.
