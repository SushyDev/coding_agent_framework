# F-124: a group signal that meets EPERM from `kill` on a group of zombies

F-123's new-4: once in three `gate-test` runs, `Services.stop` of a kept service answered
`{:unknown, {:end, {:signal, {:ok, %{output: "kill: ‘-24086’: Operation not permitted\n",
status: 1}}}}}`. This unit finds the cause with a test that makes it happen on purpose, and fixes
the reading in `Holder.Process.signal/4`, which every group signal goes through.

## What was built

- **The reading.** `Holder.Process.signal/4`'s shell, after a group's `kill` fails, lists the
  host's processes by group (`ps -A -o pgid=,stat=`) in the same shell. When no member of the
  group is anything but a zombie (`Z` first in its state), or none is left, it answers
  `{:ok, :gone}`. When a member is not a zombie, or the list fails, it answers `{:unknown,
  {:signal, …}}` with `kill`'s own output, as before. A lone pid's failed signal is never read
  this way. A group whose members are all zombies cannot run again: a zombie forks nothing, and
  its pid, the group's id, is not reused until it is reaped. So reading it as gone is final.
- **One place.** `Services`' end (TERM, then KILL) and `end_held/4` with `group: true` both use
  `signal/4`; `Sessions`' stop signals a lone pid. No caller changed: each already treats
  `:sent` and `:gone` alike.
- **Tests** in `holder_process_test.exs`: a held program starts a child in its own group (`set
  -m`), then `exec`s `sleep` and never reaps it; once the child is a zombie, TERM and KILL to
  its group answer `{:ok, :gone}` with the real `kill`. A stand-in `kill` that always answers
  EPERM gives `{:unknown, …}` for a live group and for a lone pid, and `{:ok, :gone}` for the
  zombie group.
- **The design**: "Hosts", a service's end, says how a failed group signal is read.
- **No model change.** The stop's protocol is the same: one signal, its check by pid and start
  time in the same shell. What changed is how one outcome of `kill` is read, so `Start.tla`'s
  `Signal` (a signal to processes that are gone changes nothing) already covers it.

## What was measured

On this Mac (Darwin 27), a child put in its own group and left unreaped:

| target | `kill -TERM` answers |
|---|---|
| the group, its only member a zombie | EPERM (`Operation not permitted`), from `/bin/kill`, `sh`'s builtin and devenv's coreutils `kill` |
| the zombie's own pid | success |
| `kill -0` to the group | EPERM |
| the group, after the zombie is reaped | ESRCH (`No such process`) |

`ps -o pid,pgid,stat,lstart -p <pid>` still lists the zombie with its start time (state `Z` or
`ZN`), so the check by pid and start time passes and the signal is sent to the group. With the
old code, the new test fails with `kill: ‘-21834’: Operation not permitted`, the same message as
F-123's failure; with the fix it passes.

## What I ran into

- F-123's new-4 suggested reading the leader by `kill -0` and its start time. That would not
  tell this case apart: a zombie leader answers `kill -0` and `ps` with its start time, as if it
  ran. The group's members' states are what tell it apart.
- `bash` as `sh` reaps a background job it is still running for, so the zombie needs a parent
  that is no longer a shell: `sleep 0.2 & …; exec sleep 30` leaves the child to a parent that
  never waits.

## Findings

### new-1. The waiter's "secret in no process's arguments" test can match another process

What happened: `IntakeWaiterTest`'s "the hook program the secret is in no process's arguments
while it waits" failed at `refute ps =~ c.secret` in two of this unit's first six `gate-test`
runs, with the secrets `t8258` and `t135`. `devenv test` passed.
Why: the test's secret was `"t" <> Integer.to_string(System.unique_integer([:positive]))`, four
or five characters, and `ps` lists every process on the host, so any process whose arguments
hold that string fails it. The log keeps only the start of `ps`'s output, so which process held
it is not known.
What I did: the gate could not pass three times in a row with it, so I made the secret long.
F-122 met the same failure and landed the same fix first (a 32-character random secret), so
this unit leaves the test as F-122 left it. No code changed in `caf_intake`.
What the design should change: nothing. A test that reads every process on the host for a
string makes the string long enough not to occur by chance.
