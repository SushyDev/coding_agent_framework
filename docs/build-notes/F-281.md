# F-281: a main's turn reads idle soon after its session file does

## What was seen

An embedding app's test starts a main with a brief through the framework's tree, with the
interactive stand-in as Claude Code. It waits until the session file reads `idle`, then until the
tree's row for the main reads `turn == "idle"`. On F-277 the second wait timed out under load (2
of 8 runs passed at a load average of about 25). Before F-277 it passed in every run.

## The cause

The row's turn is `Tracker.Tree`'s, from `Registry`'s rows of the session files. The `Tracker`
re-reads those rows at each `Registry` cue, and `Registry` cues only after a read of its own: at
its `interval`, or when a part calls `Registry.read/2`. The app's test tree runs with an interval
of 60 s, so the turn's end reached the tree only when some part happened to read the files after
the stand-in wrote `idle`.

Before F-277, that part was `Mailbox`. A typed row's evidence (`typed_seen/2`) asked whether the
turn had ended, through `Registry.read/2`, at every settle of the brief's row, until the turn
read ended; that read wrote the `idle` row and cued the `Tracker`. F-277 settles a typed row by
its line alone, so `Mailbox` no longer reads the files after the brief, and nothing else does.
The last read is then the start's own (`Sessions`' confirm), which races the stand-in's turn: it
sees `busy` or `idle` depending on timing. A loaded host makes `busy` more likely, and the row
then reads `working` until the next interval, a minute later.

Measured here, with a trace of every `Registry.read/2` caller: one read after the start, by
`Sessions`, which saw `busy`; then none. `tree_main_test.exs`'s first test with the interval set
to 60 s failed 1 of 4 and 2 of 6 runs at a load average of 6 to 14, its row `working` for the
whole 30 s wait.

## What was built

`Registry` follows a turn in flight. With an `interval:`, a read (a tick or a call) that leaves a
live session file reading `busy`, `shell` or `waiting` arms the next read `follow:` ms after it
(1 s by default, never later than the interval); with every file idle or gone, the next read is
the interval's. One timer, named by a ref in its message, so a tick replaced by a nearer one does
not read twice. A call's read only brings an armed tick nearer.

The bound: a turn's end shows in `Registry`'s table, and so in the `Tracker`'s tree at its cue,
within `follow` and one read's own time (a shell and a `ps`) of the file saying it, whichever part
read last and whatever the interval. Nothing waits on another part's read.

No TLA+ spec: this is one process choosing when to read again, with no step shared with another
process. No spec models `Registry`'s reads.

## Findings

### new-1. The tree's freshness rested on another part's read

What happened: the tree's turn for an interactive session came from whichever part last called
`Registry.read/2`. A change in `Mailbox` that removed a read changed how fresh the tree was.

Why: `Registry` read only at its interval and at calls, and a call is made for a part's own
decision, not for the view.

What I did: `Registry` follows a turn in flight on its own.

What the design should change: nothing more, I recommend. The other readers (`Transcripts`,
`Stream`) read at the interval too; a view that must follow them within a bound would want the
same rule, but none was seen lagging.

### new-2. The brief names a checkout that does not exist

What happened: the brief names the app's test in one checkout; that checkout was gone. Another
checkout held the same test file at the same framework pin, with the assertion at `:365` rather
than `:361`, and it too was removed while this unit ran.

What I did: read and ran the test there, and measured before and after in a copy of it, made
before it was removed, whose framework dependency had only `registry.ex` replaced. The copy's
`.git` pointer named the removed worktree, so it was moved aside and the copy ran as its own
checkout. No checkout was changed.

What the design should change: nothing.
