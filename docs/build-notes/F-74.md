# F-74: `Copies`: a host's copy of a worktree, its turn, its sync and its lock

A new app, `caf_copies`, with `Copies` (one process, with no name, that owns the `copies` table)
and `Copies.Table`. It does what `model/tla/Copy.tla` gives `Copies`. Jobs and services are the
next units.

## What was built

- **The copy's place**: `<host's framework directory>/copies/<project>/<name>`, and its lock
  `<…>/<name>.lock` beside it. The caller gives each copy as `%{programs, dir, project, name}`.
  `programs` are the host's own `Programs` and name the host. `Copies.place/1` refuses a project
  or a name that is empty, `.`, `..`, or holds a `/`.
- **The turn**: the row of `{host, project, name}` in `copies`, a SQLite file in the
  directory the embedding app gives. Its states are `free`, `taken`, `syncing`, `synced`,
  `starting` and `cut`. `take/3` takes it, and a second take is refused as `{:turn_held,
  holder}`. `starting/3` marks that the caller is sending its start. `give_back/3` gives the
  turn back once the caller has settled the start. A cut sync's row is `cut`, with `until` in
  wall-clock ms. A later take frees it once `until` has passed (`TurnBack`). The holder's
  `give_back` before then is refused as `{:cut, until}`.
- **Restart** (`init`): a `syncing` row becomes `cut` and keeps its `until`. A `taken` or
  `synced` row is freed: its run's call ended, and nothing started (`SettleUnasked` with no host
  side left). A `starting` row is kept for its caller to settle by reading the host
  (`SettleStarting`).
- **The sync** (`sync/5`), in the caller's process: it lists the files, records the named
  paths, writes the row `syncing`, runs rsync, and writes the outcome.
  - *The list*: `git -C <worktree> ls-files -z --cached --others --exclude-standard`. This is
    every tracked path plus every untracked path git does not ignore. A tracked file deleted but
    not yet committed is still listed (`--cached`).
  - *Deletes*: the row keeps `sent`, every path an earlier sync may have written. The sync
    sends `current ∪ {p ∈ sent \ current : p is missing from the worktree}` with
    `--files-from --from0 --delete-missing-args`. So rsync deletes in the copy each listed path
    the worktree no longer has. A file no sync ever sent, such as a build output made in the
    copy, is never in the list, so it stays. `sent` becomes `sent ∪ current` before rsync starts,
    and `current` once it completes.
  - *The record*: before anything is sent, each path in `:fetch` is recorded as `%{size, mtime,
    hash}` (sha256, mtime in posix seconds), or as `:absent`. The answer carries it:
    `{:ok, %{record:, files:}}`.
  - *Answers*: `{:refused, {:sync, {:lock, ms}}}` when the host side said it did not get the
    lock. `{:refused, {:sync, {:status, s, tail}}}` for any other non-zero exit, and
    `{:refused, {:sync, {:timeout, ms}}}` for a timeout: both are a cut sync. `{:refused,
    {:turn, holder, state}}` when the run does not hold a taken turn. `{:unknown, {:copies, _}}`
    when a call to the process exits. Every call has a finite timeout.
- **The host's lock**: rsync's `--rsync-path` is `sh -c <script> caf-copies mkdir flock rsync
  <copy> <lock> <secs>`, followed by rsync's own server arguments. The script makes the copy's
  directory and runs `flock -E 75 -w <secs> <lock> rsync <server args>`. On 75 it prints `caf-copies: lock not
  taken` and exits. So the server starts only under the lock and holds it for its whole life:
  the lock fd passes to the server, so the lock lasts as long as the server, even if flock is
  killed first. When the marker is in the output, the host side has exited, so the turn goes
  back at once (`HostGivesUp`). Any other cut keeps the turn until `until`.
- **The workstation**: rsync reaches it through `<dir>/local-rsh`, a two-line stand-in for ssh
  that `Copies` writes. It drops the host name and runs `sh -c "$*"`, as sshd runs a command. So
  the workstation's copy goes through the same host side and lock, by one path of code.
- **Removal** (`remove/3`): it takes the turn as `copies:remove`, runs `rm -rf` on the copy and
  its lock on the host, and deletes the row. It is refused while a run holds the turn. If `rm`
  fails, it gives the turn back and answers `{:unknown, {:rm, _}}`.
- **devenv**: `rsync` 3.5.0, `openssh` 10.6p1 (`ssh`) and `flock` 0.4.0 (the portable flock,
  which has `-w` and `-E`) are added to `packages`, to `CAF_RSYNC`, `CAF_SSH` and `CAF_FLOCK`,
  and to `check-versions`. `Programs` knows `:rsync`, `:ssh` and `:flock`, and so do
  `TestHost.programs/0` and `program!/1`. The `Programs` row of "The parts" names them.

## Tests

`apps/caf_copies/test/copies_test.exs`, 7 tests and a doctest. Each test makes its own git
repository with the person's git config shut out. The ssh host is `Host.ssh("box", <stand-in>,
…)`. The stand-in records its pid, drops ssh's options and destination, and execs `sh -c "$*"`.
When a `cut` file exists, it starts the command in the background (recording its pid) and exits
255, as a dropped connection does while the host side lives on. Another stand-in holds a copy's
lock under `flock` on the host. It records its pid and announces `held`.

- `StartsOnSyncedCopy` (local and ssh): an edit not yet committed, an untracked file, an
  ignored file not sent, the record. Then a build output in the copy stays, and an untracked
  file and a tracked file deleted from the worktree go.
- `NoTurn`: a second take is refused naming the holder, through `syncing`, `synced` and
  `starting`.
- `NoHostLock`: with the lock held, a sync is refused at its 300 ms deadline and the turn is
  back at once. A second sync starts its host side (the ssh stand-in announces it by its pid
  file), waits, and completes once the holder ends.
- `CutBeforeDeadline`: a cut sync whose host side is still waiting for the lock is refused at
  once. Its turn is refused to another run, and its holder's give-back is refused, until its
  deadline. Then the turn is free.
- `TurnInMemory`: a restart, with a sync waiting on the lock, keeps that turn as `cut`, keeps a
  `starting` turn, and frees a `synced` one. The killed caller's rsync and host side end through
  a `Shell.Reaper`.
- Removal: refused while the turn is held, then the copy and its row are gone.

## What was measured

- `caf_copies`' suite: 7 tests in 6.4 s, async. The longest are the deadline waits:
  `CutBeforeDeadline` waits about 2 s for `until` (1 s timeout plus 1 s lock wait).
- Changed lines: about 690 apart from this note. `copies.ex` is 324 lines, about a third of
  them docs. `copies_test.exs` is 211 lines and the table 92. That is over the 500 the brief
  allows (new-1).

## What I ran into

- rsync's local mode (two local paths) ignores `--rsync-path`, so a local sync would take no
  lock. Hence the local stand-in for ssh (new-2).
- `--files-from` turns off recursion, and with it `--delete`. Deletes are therefore driven by
  what earlier syncs sent, with `--delete-missing-args` (new-3).
- `in` with a variable list is not allowed in a guard. `with_turn` uses a `cond`.

## Findings

### new-1. The unit does not fit in 500 lines

What happened: the turn, the sync, the lock, the restart, removal, devenv, and a test per
invariant come to about 690 changed lines. The lock is about 40 of them: the host-side script
and one test. Why: each answer and each restart state needs its own code and test, and the rules
ask for docs on every public function. What I did: I built all of it and did not drop the lock,
since dropping it would not reach 500. What the design should change: nothing in the design. A
brief for a part this size could split it into the turn with its table, then the sync with its
lock.

### new-2. The workstation's sync goes through a local stand-in for ssh

What happened: "Hosts" says a sync runs "locally for the workstation". rsync's local mode skips
`--rsync-path`, so the workstation's copy would have no lock. Why: rsync starts its local
receiver in-process. What I did: `Copies` writes `<dir>/local-rsh`, which drops the host name
and runs `sh -c "$*"`. So the workstation's sync runs the same host side under the same lock.
What the design should change: say in "Hosts" that the workstation's sync also runs through the
host side, by a local stand-in for ssh.

### new-3. Deletes come from what earlier syncs sent, not from git alone

What happened: git lists what is in the worktree. It cannot say which file in the copy is a
build output to keep and which is a worktree file since removed. Why: the copy holds both, and
git's ignore rules do not see the copy. What I did: the row keeps `sent`, every path a sync may
have written, and a sync deletes each of those the worktree no longer has. Two edge cases
follow. A path that became ignored but is still in the worktree is neither sent nor deleted, so
the copy keeps its last version. A copy whose row is lost (the table removed) keeps every file
it had. What the design should change: "Hosts" could say that a sync deletes what earlier syncs
sent and the worktree no longer has.

### new-4. A cut sync keeps its turn for the sync's timeout plus the lock's wait

What happened: the framework cannot tell, without reading the host, whether a cut sync's host
side holds the lock (settled) or still waits for it. Why: `LockSettled` is a fact on the host,
and the spec says the framework knows it "by the time". What I did: the turn stays `cut` until
the sync's start + its timeout + `:lock_wait`. This relies on the spec's one timing assumption:
the host runs a command it got within the command's deadline (here the sync's timeout), or
never. The one early release is the `lock not taken` marker, which the host side prints just
before it exits. What the design should change: name that deadline in "Hosts". If the wait
proves long in use, a read of the host (is a process holding `<copy>.lock`?) could end it
sooner. I did not build that.

### new-5. The record lives only in the answer

What happened: the record of the named paths is answered to the caller and not stored. Why: a
restart ends the call, and "a later `run` fetches nothing for an earlier job", so no fetch after
a restart needs it. What I did: kept it in memory. What the design should change: nothing,
unless `Jobs` is to fetch across a restart.
