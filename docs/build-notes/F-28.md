# F-28: `Transcripts`, a session's transcript tail, its chats and its subagents

## The transcript format

I read the devenv Claude Code 2.1.322 (`$CAF_CLAUDE`, a wrapper around `bin/.claude-wrapped`):
the strings of the binary, which hold its minified code and schemas. No session was started,
and no credential was read. Where the binary left a shape open, I read only the key names and
JSON types of the lines of one transcript under this laptop's own config directory, never a
value; every fixture in this unit is synthetic.

**Where it lives.** The projects directory is `<config>/projects` (`function qm(){return
S(Be(),"projects")}`, where `Be()` is the config directory). A session's transcript is
`<projects>/<key>/<session id>.jsonl`, where the key is the session's `cwd` with every character
other than a letter or digit made `-` (`function k(e){return e.replace(/[^a-zA-Z0-9]/g,"-")}`).
A key over 200 characters is cut to 200 and given a hash (`XPe=200`), which `Transcripts.path/3`
does not compute; it refuses such a `cwd`, and a hook's `transcript_path` names the file.

**Subagents.** A subagent writes its own file, `<projects>/<key>/<session id>/subagents/
[<subdir>/]agent-<agent id>.jsonl` (`function $m(t){...return i(n,`agent-${t}.jsonl`)}`), beside
an `agent-<id>.meta.json`. Its lines carry `isSidechain: true` and `agentId`. An entry is
written with `isSidechain:n, ..., if(It.isSidechain=n,n)It.agentId=r`. Older releases wrote
sidechains into the main file, so the fold skips a sidechain line there by name.

**Lines.** One JSON object per line, with a `type`. The binary's table of types (how a resume
treats each) names `user`, `assistant`, `system`, `attachment` and `progress` as messages, and
`summary`, `queue-operation`, `api-request*`, `file-history-*`, `custom-title`, `ai-title`,
`last-prompt`, `permission-mode`, `session-owner` and about thirty more as metadata. A message
line has `uuid`, `parentUuid`, `isSidechain`, `sessionId`, `cwd`, `version`, `gitBranch`,
`timestamp`, and `message`. A user line has `promptId` ("`promptId:pt.type==="user"?...`").

- **A prompt** is a user line whose `message.content` is a string, or a list of blocks when it
  holds an image (an `image` block beside `text` blocks). A tool's result is a user line whose
  content holds `tool_result` blocks, with the tool's own output in `toolUseResult`. `isMeta`
  marks a line Claude Code wrote itself, not a person.
- **An assistant message** is written as one line per content block (`text`, `thinking`,
  `tool_use`), each with the same `message.id` and the message's `usage` (`input_tokens`,
  `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`). In the one
  transcript whose keys I read, 102 of 146 message ids had two to seven lines. So a message's
  tokens count once.
- **The turn's last reply**: Claude Code itself takes an assistant line with `stop_reason ===
  "end_turn"` and a non-empty `text` block as a turn's end (`Eo.message.stop_reason==="end_turn"
  &&Eo.message.content.some((fs)=>fs.type==="text"&&fs.text.trim().length>0)`).
- **A subagent** starts as a `tool_use` named `Agent` (`Rd="Agent"`; `Task` is the older name,
  `e!=="Agent"&&e!=="Task"`). Its result's `toolUseResult` is `{status: "completed", agentId,
  content, totalTokens, totalToolUseCount, totalDurationMs, usage}`, or `{status:
  "async_launched", agentId, ...}` for one that runs in the background. A background one ends
  with a task notification: a prompt, as a user line or a queued attachment, of the form
  `<task-notification>\n<task-id>ID</task-id>[\n<tool-use-id>…][…]\n<status>S</status>…`, whose
  body holds `<usage><subagent_tokens>N</subagent_tokens>…</usage>` (older:
  `<usage>subagent_tokens: N`). A notification is also sent for tasks that are not subagents,
  such as a background shell.

## What was built

- **`Transcripts.Fold`**: a pure, total fold of a transcript's bytes. It keeps the offset of
  the last whole line, so a partial last line waits, and the last 64 bytes before it (the
  seam). A read starts at the seam; bytes that do not begin with it answer `:rewritten` (the
  file shrank or was replaced). It answers the last reply (text, message id, offset) and
  whether the transcript still ends with it; the prompts (`promptId`, `uuid`, offset, the first
  500 characters, length, images); the subagents by `tool_use` id (`open`, `background` or
  `ended`, status, tokens, agent id); and the session's token usage. A line that is not JSON,
  not an object, has no type, an unknown type, or an odd shape is a problem (the last 20 kept,
  all counted); known metadata types are skipped by name. `contains?/3` answers whether a
  prompt holding a mark and a text is in some bytes.
- **`Transcripts`**: a `GenServer` per `{host, account}`, with no name. `read/3` reads each
  `{session_id, path}` (or every session read before) with one `sh` running the host's `tail -c
  +<byte>` through `Shell`, from the fold's offset, and writes the changed rows in one
  transaction. A shrunk or replaced file is read again from its start, and its row says
  `rewritten` and counts `rewrites`; a missing file says `no_file`. A shell that fails leaves
  the session as it was and names it in `failed`. `session/3`, `rows/2`, and `contains/6`, which
  reads from an offset and changes nothing (settling a report marked sending). `path/3` gives
  the transcript path from a config directory and a `cwd`.
- **`Transcripts.Table`**: `transcripts_sessions` (one row per session, its fold stored as an
  Erlang term, loaded with `:safe` and read again from the start when it is not a fold) and
  `transcripts_reads`. The cue is `%{topic: "transcripts:<host>:<account>", ids: ids}`.
- **`Tracker.TranscriptsSource`**, kind `:transcripts`.
- **`Programs`** names `tail` (devenv's coreutils `tail`, `CAF_TAIL`): neither `sh` nor `cat`
  can start a read at a byte.
- **Tests** (`test/transcripts_test.exs`): properties over generated transcripts of every
  read and skipped type, unknown types and malformed lines: the fold is total and counts each
  bad line; read in pieces at any byte cuts, through a stored and reloaded fold, it equals one
  read; a partial last line waits; a shrunk file is always found, and a replaced one exactly
  when its seam differs. One test writes a file in pieces through a real `Shell`, restarts the
  process over a file whose bytes before the seam were changed (they are not read again), and
  shrinks it; another runs a `tail` that is not there.

## Measured

- `test/transcripts_test.exs`: 12 tests, properties and doctests in about 1.3 s.
- The unit is about 1140 changed lines: 800 of library code with its docs, 330 of tests. It
  could be split: `Transcripts.Fold` with its properties (about 500) first, then the process,
  its table and the `Tracker` source.

## What I ran into

- The binary's strings are one line per chunk, some megabytes long, so a regular expression
  with a long context ran for minutes; a fixed-string search with `awk`'s `index` did not.
- The first write of a session whose file is missing is a row too (`no_file`), so a view shows
  a watched session before its first line.

## Findings

### new-1. A message's tokens count once, by its latest line

What happened: Claude Code writes one line per content block of a message, each with the
message's usage. Summing every line counted a message up to seven times.

What I did: the fold counts a message's usage once, replacing the counts of the message it
read just before when the id is the same. Lines of one message are written one after another; a
message id that came back after another message would be counted twice.

What the design should change: the "Tokens" rules could say that tokens are counted per
message id, never per line.

### new-2. A background subagent's tokens are in its notification, not its result

What happened: a subagent started in the background answers `async_launched` with no tokens,
and its end is a `<task-notification>` prompt whose usage holds `subagent_tokens`. A subagent
whose notification never comes (its session ended first) stays `background` with no count.

What I did: the fold reads both; one with no closing entry stays `open` or `background`, with
its start time, for the caller's bound.

What the design should change: say which part ends an open subagent after the bound the
delegate protocol names, and whether its tokens are then read from its own
`subagents/agent-<id>.jsonl`, which this unit does not read.

### new-3. A replaced file is found only by its seam

What happened: `tail` gives bytes, not the file's identity, so a replaced file is found when the
64 bytes before the offset differ. A replacement with the same bytes there would be read on from
the old offset.

What I did: the seam check, which also finds every shrink; a property shows both.

What the design should change: if a move (copying a transcript to another account) can write
a file that starts with the old one, read the file's size and inode with the bytes, which needs
`stat` or `wc` in `Programs`.

### new-4. One shell per session per read

What happened: a read runs one `sh` per session, each with its own timeout, inside one call.
Many sessions on a slow host could pass the call's 60 s.

What I did: nothing more; the call answers `{:unknown, {:timeout, ms}}` then.

What the design should change: read every session of an account in one shell command, as
`Registry` reads its files, once the number of sessions makes it matter.
