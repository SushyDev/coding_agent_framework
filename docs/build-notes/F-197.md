# F-197: a `PostToolUse` that waits

F-195 left its item 5 unbuilt, since it needed a logged-in Claude Code to measure. The main
session measured it on Claude Code 2.1.322, headless, with a stand-in hook, a `Bash` call of
`echo ORIGINAL-OUTPUT`, and a prompt asking the model to quote the tool result:

| hook | answer | the model read |
|---|---|---|
| command | `hookSpecificOutput.updatedToolOutput` as a string | the original: ignored |
| command | `updatedToolOutput` as an object of the tool's response shape (`{"stdout": …, "stderr": "", "interrupted": false, "isImage": false}`) | the replacement |
| http | the same object, as the response body | the replacement |
| http, `"timeout": 5` | the same object, answered after 12 s | the original; the turn went on at about 5 s |

This unit builds what that shows. No test started the real Claude Code.

## What was built

- **The answer.** `post_tool_use/3` (and `Intake`'s `post_tool_use:` callback) answers `:pass`
  or `{:replace, response}`, `response` a map of the tool's response shape, the event's
  `tool_response`. A `PostToolUse` post is now a hold of its own kind, `post_tool`, through the
  same path as `PreToolUse`'s: its row is written `held` with the hold's deadline, the callback
  is asked in a process of its own, and exactly one response goes out. A replacement goes out
  as `{"hookSpecificOutput": {"hookEventName": "PostToolUse", "updatedToolOutput": response}}`.
  `:pass`, any other value, a crash, an exit and the deadline are an empty body: the model reads
  the tool's own output.
- **The rows.** Each is the hold's, as every kind's (R5), keyed `PostToolUse:<session>:<tool_use_id>`.
  A replacement is `answered`, its actor `app`, its `decision` the response it sent, its
  `written_at` when, and its `data` the tool's name and `tool_use_id`, never the output it
  replaced (`Transcripts` has that, as it has a `PreToolUse`'s input). A pass is `passed`, the
  deadline `expired`, which is the "why" the brief asks for (`pass` or `deadline`) in the
  hold's own words. A replacement that is not a map (a string, which Claude Code ignores) or
  not JSON (a tuple inside) is a pass whose `problem` is `["bad_answer", "replace"]`; the
  encode is rescued, so such an answer never crashes `Intake`. A second post of a replaced
  call answers the replacement again and asks no one, as a `PreToolUse`'s does.
- **The timeout.** `PostToolUse` keeps its 10 s hook `timeout` from `Intake.hooks/4`, the same as
  `PreToolUse`'s, and takes the same `tool_deadline:` (5 s by default; the config bounds it
  under 8.5 s, 10 s less the plug's 1.5 s tool margin). The plug's wait is the deadline plus that
  margin. See new-1 on "set from the config".
- **The `Stop` hold's `PostToolUse` (item 3).** `@tools`' `stop: "PostToolUse"` is not a slip.
  The `Stop` hold resets each session's count of blocks in a row when a tool call runs
  (`Intake.tla`'s `ToolRuns`, F-157, F-171), and the `PostToolUse` post is how `Intake` learns
  one ran. So a `stop` callback must register that hook. Without a `post_tool_use` callback
  the post is answered at once, writes no row, and only resets the count. A new test pins
  this: `hooks/4` with `[:stop]` names `PostToolUse` at 10 s and not `PreToolUse`, and a
  `stop`-only `Intake` answers the post `:not_read` with no row.
- **Docs.** `Intake`'s module doc, `start_link/1`'s, `hooks/4`'s and `post/4`'s (`:handed` is
  gone), `Intake.Event.tool_names/0`'s, the plug's, `ToolHooks`' module doc and the callback's
  type, and `Config`'s `tool_hooks`. Each says what was measured, that a string is ignored, and
  what was not measured. The design's tool-hooks section has "A held `PostToolUse`" with the
  table, the kinds' table a `post_tool` row ("One hold, five kinds", and the two other counts),
  and B3's "Built so far".
- **The model.** No protocol change: the `PostToolUse` hold is `PreToolUse`'s hold with another
  decision, and `Intake.tla` already leaves which decision abstract. Its header now says that
  `HT` models both tool kinds (a call is a tool hook's post, either event), that a pass, the
  deadline or a cut leaves the output as it ran, and that the count's reset is `ToolRuns`, at the
  post, held or not. `Hold.tla`'s header names `PostToolUse` beside `PreToolUse`.

## What I ran into

- The old `PostToolUse` path spawned the callback with no monitor and answered at once. It is
  gone: the hold's path monitors the callback and passes on a crash.
- The test of an answer that is not JSON needed a value `JSON.encode!/1` refuses: a tuple
  inside the map. Elixir's `JSON` raises `Protocol.UndefinedError` there, which is rescued.

## Findings

### new-1. `PreToolUse`'s timeout is not set from the config

What happened: the brief says the `PostToolUse` hook's `timeout` "is set from the config, as
`PreToolUse`'s is". `PreToolUse`'s is a fixed 10 s in `Intake.hooks/4`; the config sets only
`tool_deadline` under it (`Config`'s `{:ms, 8_500}`). Why: F-111 chose one short deadline for
every tool hook. What I did: gave `PostToolUse` the same, the fixed 10 s timeout and the shared
`tool_deadline`. What the design should change: if an app's `post_tool_use` needs longer than
a `PreToolUse` (a summary of a long output, say), the config needs a key that sets both the
hook's `timeout` and its deadline, so they cannot drift apart. Nothing in this unit needs it.

### new-2. A `PreToolUse` correction whose input is not JSON crashes `Intake`

What happened: `tool_response/1` takes `{:allow, updated_input: map}` for any map and calls
`JSON.encode!/1` in `Intake`'s own process. A map that holds a tuple, a pid or a function
raises there, so one app answer ends `Intake` and cuts every hold it keeps (each row then
settles `lost` or `unknown`). Why: the check is `is_map/1`, not "is JSON". What I did: guarded
the new `PostToolUse` encoder (a rescue to `["bad_answer", "replace"]`, with a test) and left
`PreToolUse`'s as it is, outside this brief. What the design should change: an answer that is
not JSON is an answer out of shape, a pass whose row's `problem` names it, for every kind.

### new-3. Every tool call now waits on the app's `post_tool_use`

What happened: before, a `PostToolUse` post was answered at once and the callback ran beside
the turn. Now Claude Code waits for the callback, up to `tool_deadline`, after every tool call.
Why: a replacement must be the response. What I did: nothing more; the `@doc`s say the callback
is asked within the deadline. What the design should change: say that an app that only watches
calls should answer `:pass` at once and do its work in a process of its own, or offer a kind
that does not wait.
