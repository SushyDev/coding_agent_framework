# F-34: `Stream`, a headless delegate's stdin and event log

Built against `model/tla/Stream.tla`; each spec action is named in a comment where the code does
it.

## What was built

- **`ClaudeCLI.headless/2`**: `-p --verbose`, the model and the delegate's settings and MCP
  files, stream-json in and out, `--replay-user-messages`, `--permission-prompts host`, then
  `--session-id <id>` or `--resume <id>` (exactly one). **`ClaudeCLI.wrapper/3`**: the design's
  three lines of `sh`, run by `Programs`' sh, with the directory and the command.
- **`Programs`** names `mkfifo`, and `mkdir` (see new-3); devenv exports both.
- **`Stream.Line`**: the one encoder. A message, an answer (allow, or deny with its message cut
  to fit 512 bytes), an interrupt and an end, each one JSON line; U+2028 and U+2029 are escaped
  too, and text that is not UTF-8 is refused.
- **`Stream.Fold`**: pure. `take/2` folds whole lines from the offset (`Read`); `event/2` is
  `Handle` plus the session id of `system`/`init` and the latest `rate_limit_event`; `check/2`
  and `mark/4` are `Mark`'s and `AnswerAsked`'s guards and writes; `exit_seen/2` is `ExitSeen`.
- **`Stream`**: one per host, no name. `follow/5` makes `<home>/streams/<session>/out` and the
  FIFO. `write/4` checks the row and the delegate's dtach socket (`Holder.state/2`), marks the row,
  spools the line, saves `:spooled`, and runs the claim command under the rest of the deadline;
  a claim that finds no spool (exit 9) is one an earlier claim took. `read/2` checks each
  socket, then reads the log from its offset and saves fold and offset in one transaction; a
  socket gone after one seen live is the exit, which settles a message still writing by its
  uuid in the transcript. Each read claims again a line a restart left marked or spooled, for a
  live delegate only. `interrupt/3` and `end_session/3` are writes.
- **`Stream.Table`** (`stream_delegates`, `stream_reads`), its cue `stream:<host>`, and
  **`Tracker.StreamSource`**.
- `Stream.tla`'s header now names the modules it models.
- Tests: `test/support/headless_stand_in.ex` plays headless Claude Code under real dtach through
  the wrapper; `test/stream_test.exs` has the five contract cases; `test/stream_fold_test.exs`
  has properties of the encoder and the fold (reads at any cut points fold each line once).

## Measured

On the shared laptop, `mix test` of the three files: 25 tests in about 7 s; each contract test
holds one stand-in for 1 to 3 s. A write with no reader is refused after one `Holder.state`
run, well inside its deadline.

## What I ran into

- The design's claim is `exec 3<spool && rm spool && cat`. A second claim of a spool already
  taken would fail its `exec 3<` and end its shell; a `[ -e spool ] || exit 9` first makes "an
  earlier claim took it" a status of its own.
- A partial spool file after a restart: the spool write is not atomic, so `Stream` saves
  `:spooled` only after it, and a line still `:marked` is spooled again whole before its claim.
  No claim starts before `:spooled` is saved, so no claim can have read the partial file.
- At about 1,300 changed lines (the stand-in is 99), the unit is well over 500. It splits
  cleanly: `Stream.Line`, `Stream.Fold` and their properties as one unit; `Stream`,
  `Stream.Table`, `Tracker.StreamSource`, `ClaudeCLI` and `Programs` with the contract tests as
  the next.

## Findings

### new-1. The shape of an answer's replay is not confirmed

What happened: F-31 found that an answer that settled a request is passed on with replays on,
but not its shape. A row moves from answering to answered by that replay.

What I did: the fold reads `{"type":"control_response","isReplay":true,"response":{"request_id":…}}`,
which the stand-in writes.

What the design should change: add the answer's replay to the check against each pinned
release, and record its shape in "Headless delegates".

### new-2. A claim ended at its deadline can cut a long line

What happened: `Shell.run/4` kills the claim command when the write's deadline passes, and
"A claim needs a reader" has `Recoveries` end one still waiting. Opening the FIFO never waits
while the delegate lives (the wrapper holds it read-write), but `cat` does wait when the pipe is
full and the delegate is not reading; killed then, it leaves part of a line in the pipe, and the
next line makes it one that does not parse.

What I did: nothing beyond the design; the contract tests never fill the pipe.

What the design should change: end a claim command only while it has not opened the FIFO, or
keep a message line within the pipe's capacity so its write never blocks; and say which.

### new-3. Making the stream directory needs `mkdir`

What happened: `<home>/streams/<session>/out` must exist on the delegate's host before the FIFO
is made, and the host may be remote, so the framework cannot make it with `File`.

What I did: added `mkdir` to `Programs` beside `mkfifo`.

What the design should change: name `mkdir` with `mkfifo` in "A claim needs a reader".

### new-4. An exit before the first read is never seen

What happened: `Stream` takes a missing socket for the exit only after it has seen the socket
live, since a delegate followed but not yet held has no socket either. A delegate that ends
before `Stream`'s first read of it is never seen gone.

What I did: left it; `Sessions` starts delegates in a later unit.

What the design should change: let the start tell `Stream` the hold succeeded (a confirmed
start), and count a missing socket after that as the exit.

### new-5. Whether a headless start passes `--name`

What happened: "The delegate protocol" confirms every start by the session file's `name`,
which `--name` sets, while its step 4 and "Headless delegates" confirm a headless start by its
first event naming the session id, and that section's command has no `--name`.

What I did: `ClaudeCLI.headless/2` follows "Headless delegates" and passes no `--name`.

What the design should change: say that a headless start is confirmed by its `system`/`init`
event, or add `--name` to its command.
