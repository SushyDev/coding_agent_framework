# F-15: `Accounts` and `ClaudeCLI`

## What was built

- **`Accounts`**: the accounts of one framework instance, from a home and account names the
  host app gives. `config_dir/2` is `<home>/accounts/<account>/claude`. `prepare/3` creates it
  and writes the account's settings, hooks and MCP servers from data, each file whole to a
  temporary name and then renamed. `ready/2` gives an `Accounts.Account` only when those files
  exist, and `login/2` says whether an account looks logged in from which files exist, opening
  none.
- **Which files are Claude Code's**: read from the strings of the devenv Claude Code 2.1.322.
  It keeps `.claude.json` (its global state, written whole from memory, which also holds MCP
  servers added with `claude mcp add`), `.credentials.json`, `settings.json` (its user settings,
  written when a person changes a setting in a session) and its state directories (`projects`,
  `sessions`, `todos`, `logs` and others). The framework writes none of them. It writes only
  `<config>/framework/parent.settings.json`, `delegate.settings.json` and `mcp.json`, which a
  launch names with `--settings` and `--mcp-config`, and which Claude Code only reads.
- **`ClaudeCLI.session/3`**: pure; the argv and environment of a `:parent` or `:delegate`
  session for an `Accounts.Account`. The flags, from `claude --help` of 2.1.322, are in its
  moduledoc. A parent has `--remote-control <name>` and `--name <name>`; a delegate has no Remote
  Control flag, its settings file sets `remoteControlAtStartup` to false, and it needs its brief
  as the first prompt unless it resumes. The prompt goes last, after `--`. The environment is
  `CLAUDE_CONFIG_DIR` plus `HOME`, `PATH`, `TERM` and `LANG`, each given by the caller, with the
  reason for each in the moduledoc. Anything that is not an `Accounts.Account` with an absolute
  directory is refused as `:no_account_dir`; there is no default directory.
- **F-11 new-2 done**: `Programs` names `cat`, and `Registry`'s read script runs it by that path
  (`$2`). `docs/design.md`'s `Programs` row names `cat`.
- **Tests**: `ClaudeCLITest` (pure argv and environment per role, and refusals).
  `AccountsTest` sets `HOME` to a test directory and `CLAUDE_CONFIG_DIR`, `CLAUDECODE` and
  `CLAUDE_CODE_ENTRYPOINT` in the VM, prepares an account, and checks every file written is
  under the instance's home and none of Claude Code's own files was made. A contract test holds
  a stand-in for `claude` through `Holder.hold/4` with `ClaudeCLI`'s argv and environment: it
  sees `CLAUDE_CONFIG_DIR` set to the account's directory, no other `CLAUDE*` variable, and its
  argv intact.

- `devenv test` exit 0.
- The unit is about 680 changed lines, over the 500 aimed for: about 355 in `lib/` (much of it

## What I ran into

- Claude Code 2.1.322 has `--remote-control [name]` but no flag to turn it off, and an account
  can turn it on at startup by a setting or by its organization's default. A delegate is kept
  off by its settings file; see new-1.
- `--remote-control [name]` takes an optional value and `--mcp-config <configs...>` takes
  several, so either could take the first prompt as its value. The prompt goes after `--`.
- `--settings` is a separate source ("flag settings") from the user `settings.json`, so the
  framework's file is never erased by Claude Code's save of its own.

## Findings

### new-1. A delegate's Remote Control off rests on a setting, not a flag

What happened: 2.1.322 has no `--no-remote-control`. The strings show `remoteControlAtStartup`
and an organization default that turns Remote Control on when that setting is not given.

Why: Claude Code offers only a flag to turn it on.

What I did: `delegate.settings.json` sets `remoteControlAtStartup` to false, loaded with
`--settings`. It was not run against the real Claude Code, so whether flag settings win over an
organization default is not shown.

What the design should change: a check, when a delegate starts, that it has no Remote Control,
read from what Claude Code reports, with a refusal when it does.

### new-2. Whether an account is logged in cannot be known without its credential

What happened: on macOS Claude Code keeps the login in the keychain; elsewhere in
`.credentials.json`. `.claude.json` names the signed-in account, but it can also hold an API key,
so it is not opened either.

Why: the only proof of a login is the credential itself.

What I did: `login/2` answers `:logged_out` when Claude Code never ran in the directory,
`:looks_logged_in` when `.credentials.json` exists, and `{:unknown, :login_not_readable}`
otherwise, which is the usual answer on macOS.

What the design should change: say how a person sees an account is logged in: perhaps
`claude auth status` with that account's `CLAUDE_CONFIG_DIR`, run by a person, or a session's
first failure read from its screen.

### new-3. `Accounts` writes on this machine only

What happened: `Accounts` uses the VM's file calls, so it writes a local home only.

Why: a remote host's home is reached only through `Shell`.

What I did: nothing; every host so far is local.

What the design should change: when a remote host has accounts, `Accounts` writes through
`Shell` with `Programs`' paths, the way `Holder` does.
