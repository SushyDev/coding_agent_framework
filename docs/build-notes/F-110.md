# F-110: launch options per agent

Item 11 of the order of units: a settings overlay, extra environment, `--add-dir`,
`--append-system-prompt`, allowed and disallowed tools, each checked and kept on the agent's
row, and passed again on a resume.

## What was built

1. **`ClaudeCLI.Options`** (`caf_cli`, pure). `check/1` takes a map with atom or string keys
   (an MCP call gives strings) and answers `{:ok, options}` with atom keys, or
   `{:refused, {:bad_option, option, why}}` naming the option:
   - `settings`: a map with string keys; `hooks`, `statusLine`, `remoteControlAtStartup`,
     `disableAllHooks` and `env` are refused, since the framework writes them; the
     `permissions` rule lists must be lists of strings; the whole must be JSON;
   - `env`: names `[A-Za-z_][A-Za-z0-9_]*`, never `CLAUDE_CONFIG_DIR`, `HOME`, `PATH`, `TERM`,
     `LANG`, the two MCP timeouts, `DISABLE_AUTOUPDATER`, `CLAUDECODE` or a name starting
     `TMUX`; values UTF-8 strings with no NUL;
   - `add_dirs`: absolute paths that `Path.expand/1` leaves as they are (no `..`, no trailing
     `/`);
   - `append_system_prompt`: UTF-8 text with no NUL, at most 64 KiB;
   - `allowed_tools`, `disallowed_tools`: a name of letters, digits and `_*.:-`, not starting
     with `-`, then an optional `(…)` rule with no parentheses or control characters inside;
   - at most 64 items in each list or map, and all the options as JSON at most 256 KiB.
   `encode/1` and `decode/1` are the row's JSON; `decode/1` checks again. `argv/1` gives the
   flags.
2. **`ClaudeCLI.session/3` and `headless/2`** take `:options` and `:settings` (the agent's own
   settings file). The flags go right after `--settings` and before `--mcp-config`; the extra
   variables go after the MCP timeouts and before `DISABLE_AUTOUPDATER`, sorted by name. A
   settings overlay without `:settings` is refused `{:missing, :settings}`.
3. **`Accounts.overlay/4`** writes `<config>/framework/agents/<name>.settings.json`: the role's
   settings file that `prepare/3` wrote, with the overlay merged over it. The `permissions`
   lists `allow`, `deny`, `ask` and `additionalDirectories` add to the account's (no
   duplicates); every other key replaces the account's. Written whole and renamed into place.
   The launch names this file by `--settings` in place of the account's (new-1).
4. **`Sessions`** takes `options:` in a launch. It checks them before the row, writes the
   overlay file when there is one, and keeps the options on the row (`held_sessions.options`,
   a new column, added to an older file). A resume whose launch names no `options:` takes the
   name's row's.
5. **`Delegates.start_delegate/7`** takes `options:`. It checks them before the row, keeps
   them in `delegates.options` (a new column, added to an older file) and gives them to
   `Sessions` at the start and again at the resume.
6. **MCP** `start_delegate` and `run_delegate` take an optional `options` object and hand it
   to `Delegates`, which checks it.

How each flag of Claude Code 2.1.322 (`claude --help` through devenv) is passed:

| Option | Flag in 2.1.322 | How it is passed |
| --- | --- | --- |
| settings overlay | `--settings <file-or-json>`, one value | the agent's own merged file, in the account's file's place |
| extra environment | none | `env -i NAME=value`, through `Holder.hold/4` |
| add-dirs | `--add-dir <directories...>` | `--add-dir d1 d2 …`, followed by the next flag |
| appended prompt | `--append-system-prompt <prompt>` | one word, `--append-system-prompt=<text>` |
| allowed tools | `--allowedTools <tools...>` | `--allowedTools t1 t2 …`, followed by the next flag |
| disallowed tools | `--disallowedTools <tools...>` | `--disallowedTools t1 t2 …`, followed by the next flag |

The `=` form keeps a prompt that starts with `-` (a Markdown list) from being read as a flag.
The list flags take values up to the next flag, and no value they get can start with `-`.

## Tests

- `ClaudeCLI.Options`: for a parent, a delegate and a headless delegate, each option is its
  flag after the agent's own settings file, and its variables are in the environment; no
  options give the launch as before; a settings overlay with no file is refused; the row's
  JSON reads back the same; each bad value (10 of them) is refused, naming the option.
- `Accounts.overlay/4`: the rule lists add, other keys replace, the role's file is the base
  and is left alone; a bad name and an account not prepared are refused.
- `Sessions` (held stand-in, real dtach): a bad option is refused with no row; a headless
  delegate's argv has the flags and its own settings file, whose content is the merge; the
  row keeps the options; a resume that names none launches with the same flags.
- `Delegates`: a bad option is refused with no row; the row keeps the options; after a kill,
  the resumed process has the same flags.
- MCP: `start_delegate` with a bad `options` is refused naming it; good ones are on the row.

## Findings

### new-1. `--settings` takes one value

What happened: 2.1.322's help gives `--settings <file-or-json>` one value. Whether a second
`--settings` adds to the first or replaces it is not in the help, and no test may run the real
Claude Code to find out.
What I did: the agent's overlay is merged over the account's settings into a file of the
agent's own, and that one file is named. The account's hooks, status line and Remote Control
setting are in it, so they hold whatever the answer is.
What the design should change: "Rules learned" says each launch names the framework's files
by flag; say that an agent's settings are one merged file, and add to the check against each
pinned release (the one for Remote Control) a check of which settings a launch reads.

### new-2. No file form of `--append-system-prompt` is listed

What happened: `--append-system-prompt-file` appears only inside `--bare`'s description, not
as an option of its own, so the brief's "by file, if the flag takes a file" is not settled by
the help.
What I did: the prompt goes as one argument, `--append-system-prompt=<text>`, at most 64 KiB.
What the design should change: the per-release check says whether the file form exists; if
it does, the framework writes the prompt into the agent's own file, as it does the settings.

### new-3. How Claude Code splits a tool pattern

What happened: the help says the tool flags take a "comma or space-separated list", and its
own example `"Bash(git *) Edit"` has a space inside the parentheses. Whether a comma inside
the parentheses is split is not said.
What I did: each pattern is its own argument, and a pattern with parentheses inside its rule
is refused. A comma inside a rule is not refused.
What the design should change: the per-release check covers a pattern with a comma and a
space in its rule.

### new-4. An agent can widen its delegate's launch

What happened: through MCP, a main session's `start_delegate` can give its delegate allow
rules, `allowed_tools`, `add_dirs` and environment that its own launch does not have.
`Grants.may_start_delegate?/2` decides only who may start one.
What I did: nothing beyond the checks above.
What the design should change: say whether an agent may only narrow its delegate's launch
(deny rules, `disallowed_tools`), or also widen it, and make that a `Grants` decision.

### new-5. A resume cannot change the appended prompt

What happened: 2.1.322's `--system-prompt-snapshot` is on by default: the system prompt,
`--append-system-prompt` included, is recorded at a conversation's first request and sent
as it was on every resume, "even when a later launch passes different text".
What I did: a resume passes the row's options again, so it sends the same text anyway.
What the design should change: say that an agent's appended prompt is fixed at its first
start, so the app does not expect to change it by resuming with other options.

### new-6. Other `CLAUDE_CODE_*` names are allowed

What happened: "Rules learned" names an inherited `CLAUDE_CODE_*` among what made an agent act
as if it ran in another session. A name the app gives on purpose is not inherited, and many
such names are Claude Code's own settings.
What I did: only the framework's own names, `CLAUDECODE` and `TMUX…` are refused.
What the design should change: say whether an app's `env` may set `CLAUDE_CODE_*` names, or
list the ones it may not.

### new-7. The operator's start

What happened: the operator (item 10, `framework/f-109-operator`) was not on `main`.
What I did: `Sessions`' start of a main session takes the options; the operator's own start
does not exist yet.
What the design should change: nothing; the operator's start passes `options:` to `Sessions`.
