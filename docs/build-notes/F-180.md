# F-180: the guards an app drops when it runs its agents on the framework (first three)

An app is about to run every main session and builder on the framework, and with that switch
on most of its own recoveries go off. The brief names six guards. This unit builds the first
three as far as `main` allows, and stops before the other three, as the brief says to when the
unit runs well past 1,000 lines (new-6). No test or step of it started the real Claude Code.

## What was built

- **A background command's stdin at end of file** (item 1; `Intake.Background`, new in
  `caf_intake`). Claude Code gives a `Bash` command run with `run_in_background: true` a stdin
  that is an open socket and never closes, so a program that reads stdin waits for ever and a
  delegate's report waits with it. `Intake.Background.pre_tool_use/1` wraps the next callback:
  that callback answers first, on the call as the agent made it (new-3), and when its answer lets
  a background `Bash` call run (`:pass`, `:allow`, or either with options), the input it runs
  with gets `exec </dev/null; ` before its command, and one line of context says why (after the
  app's own context, and left out where both would pass Claude Code's 10,000 characters). A
  command that already starts with `exec </dev/null;` is left as it is. A `<`, a here-doc or a
  pipe still gives its program its own stdin, because each applies after the `exec`; the
  programs after it read end of file. A deny, an ask (new-4), a foreground call, another tool
  and an empty command are left as they are. A callback that raises is a pass, as `Intake` takes
  it.
- **A correction with no decision** (`Intake`): `{:pass, updated_input: map,
  additional_context: text}` goes out as `hookSpecificOutput` with `updatedInput` and no
  `permissionDecision`, so the call runs with the input given and Claude Code's own permission
  rules still decide, as for an empty body (measured, below; new-5). Its row is a decision as any
  other: actor `app`, `answered`, its response kept. A pass that `Background` corrects takes this
  shape, so a background command the app has no opinion on is not let through Claude Code's
  permission prompt.
- **The tree's order** (`caf_surface`): `Mover`'s drain, then `Background`, then the heavy
  commands' rewrite, then the app's callback. A heavy background command so runs as `exec
  </dev/null; '<home>/bin/caf-run' <class> … -- '<command>'`: the wrapper and the command it
  `exec`s both read end of file.
- **A session on a startup dialog reads `dialog`** (item 3). `Sessions.Turn` has a new state
  `:dialog`: `interactive/3` (and so `of/2`) answers it for a row whose status is `dialog`, where
  it answered `:not_running`; no session file exists while a startup dialog is shown, so the row
  is the evidence. The `Tracker`'s tree shows such a row `dialog`, with `waits_on` naming the
  dialog's kind and options, where it showed `unread`. Every caller already treated an unknown
  state as not idle: `Delegates`' and `Mailbox`'s checks ask for `:idle` or `:ended`, and the
  typed transport refuses any other state by name (`{:refused, :dialog}`).
- **The exit dialog's capture** (item 2, the first half). `bin/capture-screen` has two states
  before `exited`: `turn-ended-background` (it asks for `sleep 300` with `run_in_background`,
  and the turn ends with the command running) and `exit-dialog` (it types `/exit`, and the
  person leaves the dialog shown); then the person answers it with the option that exits and
  stops the command, and `exited` is captured as before. The dry run's stand-in draws both with
  words of its own, not Claude Code's. The reading is not built: it waits on a person's capture
  (new-2).
- Docs: `docs/design.md` ("Intercepted, not added"), the README's list, `Config`'s
  `tool_hooks`, `Intake`'s module and `start_link/1` docs.

## What was measured

- **`updatedInput` with no `permissionDecision` is applied by Claude Code 2.1.322.** This
  builder's own session runs 2.1.322, and the app's own `PreToolUse` hook answers a background
  `Bash` call in exactly that shape (`updatedInput` and `additionalContext`, no decision). A
  background `stat -L -f %HT /dev/stdin` printed `Character Device` (`/dev/null`), as a foreground
  one does; the same call without `-L` printed `Symbolic Link`, `/dev/stdin` itself. Not
  measured: that Claude Code still asks its permission prompt for such a call (new-5).
- `IntakeBackgroundTest`: 2 doctests and 5 tests in 0.1 s, one of them through a real `sh -c`
  whose stdin is a pipe from the test VM that never closes, as Claude Code's is: `cat` alone
  ends at once; `cat < file`, a here-doc and a pipe each still feed their program, and a later
  `cat` reads end of file.
- The new `Delegates` test: an interactive delegate on the trust dialog, past twice its idle
  bound, is told nothing; its start answers `{:unknown, {:dialog, :trust}}` and its delegate row
  stays `starting`, so the idle check never takes it up; its turn reads `:dialog`.
- `CaptureScreenTest`'s dry run: 10 states, 4 tests in 6.1 s.
- Gates: see "Gates" below.

## What I ran into

- F-179 (`Prompts`) is not on `main`, and items 2, 3 and 6 lean on it (new-1).
- The capture needs a logged-in account's config directory and a person at a terminal, and an
  agent may touch no Claude config directory but its own test's (new-2).
- The app's hook answers my own shell calls here: it read `sleep` inside a file edit's text as a
  wait and refused the edit, so the capture script's edit went through the Edit tool.

## Findings

### new-1. Items 2, 3 and 6 need F-179, which is not on `main`

What happened: the brief says F-179 already makes a builder waiting on a dialog a prompt whose
parent is told once, and asks for the exit dialog "shown as a `dialog` prompt" and for a second
absence of a main "a prompt". `Prompts` is only on `framework/f-179-inbox`, which another
session was rebasing onto `main` while this unit ran. Why: the brief was written as if F-179
had merged. What I did: this branch is on `main`; item 3's turn state and its test are here, and
its notice to the parent is F-179's own (`Prompts`' `ParentToldOnce`). What the design should
change: nothing; merge F-179 first. Once both are in, `Prompts`' `dialog` kind reads `Sessions`'
rows on a startup dialog (`trust`, `imports`), so the exit dialog's kind is one clause there,
in the unit that builds its reading.

### new-2. The exit dialog's capture needs a person

What happened: `bin/capture-screen` needs a logged-in account's config directory and a person
who presses Enter at each state in a terminal; this repository's rules let a builder touch no
config directory but its own test's. Why: a fixture comes from the pinned release, never from
a stand-in. What I did: the script captures the two new states; its dry run is tested. What the
design should change: nothing; a person runs, since the `2.1.322` directory exists and is never
replaced,

    devenv shell -- bin/capture-screen --out <new dir> <home>/accounts/<account>/claude

then copies `turn-ended-background.*`, `exit-dialog.*` and their manifest entries into
`apps/caf_screen/test/fixtures/2.1.322/` (and checks `exited.*` against the one there). The same
run should note what the session file says while the exit dialog shows: `Sessions` reads a
pane only during a start (F-140), and the exit dialog shows on a running row, so what makes
`Sessions` read that pane (a session file still `shell` after a `/exit` typed through the
`Inlet`, say) is not settled. Recommendation: the reading's unit reads the pane after any
`/exit` the framework types and whenever a person's `/exit` leaves the process live, decided
once the capture shows what the file says.

### new-3. "An app's callback decides after it": which call the app sees

What happened: the brief says the correction is the framework's, always on, "and an app's
callback decides after it". Read as "the app sees the corrected input", the app's patterns and
the heavy commands' (`%{match: "^make", …}`) would no longer match a command that starts with
`exec </dev/null;`, and `Runs`' check that a command is already wrapped reads the command's
start. What I did: the app's callback and the heavy-command rewrite answer on the call as the
agent made it, and the correction applies to whatever input their answer lets run, so the app
decides the call and cannot turn the correction off. What the design should change: confirm this
reading; the design's text now says it.

### new-4. An asked background command keeps Claude Code's stdin

What happened: `Intake` sends `updatedInput` only beside an allow or with no decision, so a
call the app answers `:ask` goes out uncorrected, and if the person approves it, it runs with
the stdin that never closes. Claude Code's hook documentation says `updatedInput` beside `ask`
shows the modified input in the permission prompt, but that is not measured on 2.1.322. What I
did: an ask is left as it is. What the design should change: the next release check measures
`updatedInput` beside `ask`; once confirmed, `Background` corrects an ask too (one clause).

### new-5. A corrected pass is not measured to keep the permission prompt

What happened: a pass with a correction goes out with no `permissionDecision`, so that the
framework's correction never lets a call skip Claude Code's permission prompt. That Claude Code
applies the input is measured (above). That it still asks its prompt for such a call is not:
this builder's session asks none. What I did: nothing more. What the design should change: the
release check runs a held session in the default permission mode, with an app callback that
passes, and checks that a background command not in the allow list is still asked.

### new-6. Items 4, 5 and 6 stand on B7, B8 and `Heal.tla`, none of which is built

What happened: item 4 is a symptom with a remedy (hand the parent the last reply as a
`partial` report, end the hung group by its record, once); item 5 two symptoms, shown; item 6 a
remedy (resume an absent main once per absence) with a prompt past a bound. The `Watch`'s
folds and digest (B7), the healer on an allow-list with its cap and `remedy` prompt (B8),
`Heal.tla` and `Prompts` are not on `main`. `Recoveries` is today's healer: it claims each state
in `Acts` before it acts and verifies after, but its acts are fixed (a lost viewer, an end
owed), with no allow-list, cap or `remedy` prompt; `Boxes.tla`'s healer has one symptom, a
stuck turn, remedied by an interrupt. Why: building each guard now would build B7's and B8's
mechanisms piecemeal, three times, inside one unit well past 1,000 lines. Also, `Mailbox`'s
report carries no `partial` mark, so item 4's report needs one, and its parent's view of it, which
the design does not say. What I did: nothing of items 4 to 6. What the design should change:
one unit for `Heal.tla`, with item 4's and item 6's remedies as its first instances beside
`Boxes.tla`'s stuck turn; then `Watch`'s symptom record with item 5's two
symptoms and `stuck_background`'s detection (CPU time read on Linux, `unknown` on macOS);
then each remedy as a small unit on that shape; and a line in "The delegate protocol" on a
`partial` report: its mark, and that a later report of the same brief is still taken.
