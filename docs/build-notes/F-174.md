# F-174: `subscribe/2` on the app's surface

An app runs on `CodingAgentFramework.child_spec/1` (F-169), and the library owns `Cues`. So the
app's own processes beside the tree (its rows' sync, its inbox bridge, its view refresh) got no
cues. B3 names `subscribe/2` as part of the app's surface; this unit builds it.

## What was built

- **`CodingAgentFramework.subscribe(instance, topics)`**: the calling process gets each later
  cue on those topics as `{:caf_cue, cue}` for as long as it lives. A topic is a pattern of the
  shape `Cues` already routes by (`"sessions"` matches `"sessions:ws"`, `*` is one word, and a
  trailing `:` is the same as none). It answers `{:ok, ref}`, `{:refused, :no_instance}`,
  `{:refused, {:bad, :topics}}`, `{:refused, {:undeclared, topic}}`, or `{:unknown, reason}`
  when the instance's `Cues` did not answer. `unsubscribe(instance, ref)` ends one, and
  `topics(instance)` lists the topics an app may name: the ones the parts declare, from the same
  `reads/0` declarations `Cues` routes by. The moduledoc of `subscribe/2` has the table of each
  topic's cue shape, with an example.
- **`Cues` keeps the subscribers.** `Cues.subscribe/3`, `unsubscribe/2`, `subscriptions/1`, and
  the pure `topics/1` and `check/2`. A cue reaches the parts first, then each matching
  subscriber by a plain `send`. Each subscriber is monitored and removed on its exit. The
  subscriptions are rows in an ETS table the starter may give (`subscriptions:`); the tree's
  supervisor owns it, so a `Cues` a restart replaced re-adopts them: it monitors each again, and
  one that exited meanwhile is removed by its `:DOWN`.
- **The instance's own `Registry`.** A new child, `:names`, after the reaper and before `Cues`:
  an Elixir `Registry` named from the instance's name (`CodingAgentFramework.Instance.<name>`).
  `Cues` registers itself there (`registry: {name, :cues}`). The app's lookup uses only atoms
  that exist, so an unknown name makes no atom and answers `:no_instance`.
- **One instance per name.** `start_link/1` refuses `{:instance_running, name}` when an instance
  of that name already runs in the app, and `Config.new/1` refuses an `instance` that is not 1
  to 100 bytes with no control character (`{:bad, :instance}`).
- Design: the `Cues` row of the parts table, and B3's "Built so far".

## What was measured

- `apps/caf_cues`: 12 tests (3 doctests), 0.07 s. Five new: delivery after the parts and only
  on matching topics, refusals, a crashing subscriber removed with `Cues` alive, `unsubscribe`,
  and a restarted `Cues` re-adopting the table (one subscriber dead meanwhile, removed).
- `apps/caf_surface/test/subscribe_test.exs`: 3 tests, two whole trees in one VM, about 0.6 s;
  run three times in a row, all passed.
- Gates: `devenv test` passed (format, compile, deps, test in 403 s, model), then `devenv
  shell -- gate-test` three times, each with no failure. The first `devenv test` failed 12
  surface tests, all on the list of the tree's part keys, which lacked the new `:names`.

## What I ran into

- An Elixir `Registry` links each process registered in it. Keeping the app's subscribers there
  (its `:duplicate` keys look made for it) would kill the app's processes whenever the
  framework's tree restarts. So the `Registry` only finds the instance (`Cues` is registered in
  it, a process of the tree itself), and the subscriptions live in `Cues`, monitored.
- The tree's existing part `:registry` is Claude Code's session `Registry`, so the new child is
  `:names`, and the surface calls the Elixir one `Elixir.Registry`.
- The `Tracker` declares `:all`. It adds no topic to `topics/1`: otherwise every topic would be
  declared and nothing could be refused.

## Findings

### new-1. Four topics are written but no part declares them, so an app cannot subscribe to them

What happened: the brief limits an app to the topics the parts declare. The parts write cues on
`acts:<host>:<instance>`, `intake:<host>:<account>` (not the waiters), `scheduler:<host>` and
`services`, but no part's `reads/0` names them (only the `Tracker`, by `:all`). So
`subscribe(i, ["acts"])` is refused, though the design calls `acts` the fault ledger's topic
and says `subscribe/2` gives "one stream of `{topic, ids}` for every write". `prompts`, the
inbox's topic, does not exist yet.

Why: what a part reads is declared; what it writes is not. The set an app may name is derived
from the readers.

What I did: followed the brief; the refusal names the topic, and the test asserts `acts` is
refused.

What the design should change: each part declares the topics it writes, as data beside `reads/0`
(a `writes/0`), and `topics/1` is the union of those. `Cues` could then also refuse a cue on an
undeclared topic in tests, which would catch a part that writes a topic it never declared.

### new-2. A subscription ends unannounced when the whole tree restarts

What happened: the subscriptions table is owned by the instance's supervisor, so it survives a
restart of `Cues` (and of the reaper, which `:rest_for_one` takes `Cues` with), but not a
restart of the whole instance under the app's supervisor. The subscriber then gets no more cues
and no message saying so.

Why: the subscriber is not linked to anything in the tree, by design (a framework restart must
not kill the app's view), and nothing tells it the tree it subscribed to is gone.

What I did: nothing beyond documenting that a subscription survives a restart of `Cues`.

What the design should change: either `subscribe/2` answers the instance's supervisor pid with
the ref, for the app to monitor and subscribe again, or `Cues` sends each subscriber
`{:caf_cue, %{topic: "caf:started", ids: []}}` when it starts with an empty table, so a view
re-reads everything. The second fits "a cue is a hint to read rows again".

### new-3. The instance's name is now a process name

What happened: finding the instance by its name needs an atom made from that name, so a name
must be unique in an app and of a bounded size. Two instances of one name were possible before.

What I did: `Config.new/1` checks the name (1 to 100 bytes, no control character), and
`start_link/1` refuses a second instance of a running name.

What the design should change: say in "The app's surface" that the instance name is unique per
app and bounded, as the config checks it.
