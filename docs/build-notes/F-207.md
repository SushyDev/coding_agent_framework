# F-207: an app says which accounts are usable; a home too long for services is refused at the start

Two items of the brief, both in `caf_surface`. No test started the real Claude Code.

## What was built

- **`usable: {module, opts}` in the config**, as `tool_hooks` and `extensions` are (F-188, F-195).
  - **`CodingAgentFramework.Usable`**, a behavior with one callback, `usable?(account, opts,
    part)`, answering `true` or `{false, reason}`. `part` is the live lookup of a part by its key,
    as a hook's and an extension's tool's is, called when the check runs. `Usable.check/3` turns
    the answer into what a `usable:` function answers: `:ok`, `{:refused, {:app, reason}}`, or
    `{:unknown, …}` for a callback that raised, exited or answered neither shape
    (`{:raised, module, message}`, `{:exit, module, reason}`, `{:bad_answer, module, answer}`).
    No account is usable on an `{:unknown, …}`.
  - **`Config.new/1`** checks the key: the module exists and has `usable?/3`, else
    `{:refused, {:bad, :usable, {:not_usable, value}}}`, and a function (or anything that is not
    a `{module, opts}`) is refused the same way, naming the value; `opts` is checked with
    `tool_hooks`' own `not_data/1`, so a function, pid, port or reference is `{:not_data,
    module}` and a struct (this config among them) `{:not_data, module, {:struct, struct}}`.
    Absent is nil: the framework's check alone, as before.
  - **The tree** hands `Delegates`, `Mains` and the `Mover` one `usable:` that reads
    `Logins.usable/3` first and then the app's `usable?`, in `usable/3` of the tree's module. An
    account is usable only if both say so, and the first to refuse is the answer, so the app is
    never asked about an account that is not prepared or not logged in. The three parts take the
    same function they took, so none of them changed. `Usage.pick/4` already answers
    `{:none_usable, reasons}` with each account's own answer, so a refused account reads there:

        {:refused, {:none_usable, %{"work" => {:refused, {:app, "flagged work"}}, …}}}

    The `Mover` reads a named `to:` by the same function, `{:refused, {:account, to, {:app,
    reason}}}`, with nothing begun.
- **A home over 69 bytes is refused for a tree that runs services** (F-205's new-1). A tree runs
  `Services` unless it has `agents: false`, so the bound is 69 there and `{:bad, :home,
  {:longer_than, 69}}` is the answer for any home over it, a home over 93 as well; a tree with
  `agents: false` keeps 93. The 69 is `103 - 34`, the 34 being `/ws/services/<key>.sock` with the
  key's length read from `Services.socket_key/1`, so the two cannot drift.
- **No model change.** `Limit.tla`'s `Pick` takes the usable accounts as given; the app's check
  only narrows that set at a pick, a pure answer with no protocol over time.
- **Docs**: `Config`'s moduledoc (the key, the bound), `Usable`'s, `Services.socket_key/1`'s
  sentence on the home, and the design's config table, the `Services` paragraph, `Logins`' row and
  `pick`'s bullet.

## What I ran into

- The brief names a start "through the `Scheduler` path". The `Scheduler` picks no account: it
  grants a lease for the account the owner picked (`Delegates`, `Mains`), so a start through it
  is a start that takes a lease. The test reads that lease's account.
- **The refusal is tagged `{:app, reason}`**, not the module's bare reason. `Mains`'
  `resume_account` reads a refusal of the form `{:allowance, retry_at}` as a usage limit's reset
  (the resume waits for it, F-196), so an app that answered `{false, {:allowance, 5}}` would have
  been read as one. The tag keeps the app's terms from being read as the framework's. The
  `Mover`'s `{:account, to, reason}` wraps it as it wraps the framework's.
- **A callback that raises is `{:unknown, …}`, not a raise**, since it runs in the process of
  `Delegates`, `Mains` or the `Mover`: a raise there would end the part, and with it every start
  and the tree after its restart budget. The brief did not say; the answer is as explicit as
  `Config.extensions/2`'s `{:raised, module, message}`.
- **A main session's start that is allowed is not run on the whole tree.** The headless stand-in
  gives an interactive session no session file, which `Mains` waits for, so the call outlasted
  the test's 60 s. The tree test shows `Mains`' wiring by its refusal (every account flagged) and
  by the mutation above; the allowed pick is the same function `Delegates` and the `Mover` got.
- The project's `cap` is 2 in `SurfaceTest`, and the cap is checked before the account is
  picked: the new test sets 5 for its project (four starts and a refused one).
- The existing doctest of a 94-byte home answered `93`; it now answers `69`, and the `93` doctest
  has `agents: false`.

## Findings

### new-1. `usable?/3` runs in the picking part's process and has no deadline

What happened: a callback that waits (a call to a part that is busy, a read from the app's
database) holds `Delegates`, `Mains` or the `Mover` for as long as it waits, at each account of
each pick. A callback's exit and raise are caught; a wait is not bounded.
Why: the three parts call `usable:` in their own process, as they did `Logins.usable/3` (which
bounds its own call with `@call`). `ToolHooks`' callbacks run under `Intake`'s tool deadline and
an extension's tool under `MCP`'s, so the app's code there has one; this has none.
What I did: said in `Usable`'s moduledoc that it answers from what the app already holds and does
not wait. No deadline: it would be a new mechanism.
What the design should change: either leave it until an app's check reads outside its own memory,
or run the check under a bounded call (a task with a deadline, `{:unknown, {:timeout, module}}`),
which every part that picks would share through the tree's `usable/3`. I recommend leaving it.

### new-2. A delegate's resume never asks `usable:`; a main session's does

What happened: `Delegates`' resumes (`resume/4`, and `went_on/4`, the word to go on after a
limit) read only `Accounts.ready/2` of the row's own account, no `usable:`, `Logins` included, so
a delegate on an account the app flags goes on resuming there. `Mains` reads `usable:` for a resume's own account (`resume_account`,
F-177) and, when it refuses, copies the conversation to the account `pick` finds; so the same
flag moves a main session's conversation and leaves a delegate's.
Why: a conversation lives only in the account it ran on (`Move.tla`'s ResumeHere); `Delegates` took
that as no choice, `Mains` made one for the refused account (F-181).
What I did: nothing; the brief names the starts.
What the design should change: say which an app's flag governs. If it is the starts only, a
`Mains` resume on a flagged own account should stay (as a delegate's does); if a flagged account
should be left, `Delegates`' resume needs the same step, and a flagged account leaves its running
delegates until a move (the app's, by the `Mover`).

### new-3. `usable` in a tree with `agents: false` is read by no part

What happened: such a tree starts no part that picks an account, so the key is accepted and never
read. `tool_hooks`, `extensions` and `dialogs` are accepted there too and are read by no part.
Why: `Config.new/1` checks each key's shape and not whether the tree reads it.
What I did: nothing.
What the design should change: either refuse, with `agents: false`, a key only an agent's part
reads (`{:bad, :usable}`, and the others), or say it in the table. I recommend the refusal, since
an app that sets `usable` there believes a start is guarded.
