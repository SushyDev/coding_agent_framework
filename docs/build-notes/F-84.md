# F-84: one way to hold a program on a host, shared by `Jobs` and `Services`

A new module, `CodingAgentFramework.Copies.Held`, in `caf_copies`, holds the steps a program
held on a host takes in a copy. `Jobs` and `Services` now use it. Every existing test of both
apps passes unchanged.

## The two apps side by side

Steps both take, in the same order:

| Step | `Jobs` (before) | `Services` (before) |
|---|---|---|
| The context: the host's programs, the copy, `Copies.place`, a `Holder` of `<dir>/<kind>` | `context_of/4`, kind `jobs` | `context_of/3`, kind `services` |
| No such host: `{:refused, {:no_host, name}}` | `host/2` | `host/2`, the same |
| The copy's turn (`Copies.take`), a refusal marks the row | `refuse_on_fail/3` | `refuse_on_fail/3` |
| The sync, with `:sync_timeout`, `:lock_wait`, `:reaper` | `sync/4` and `copy_opts/1` | `sync/4`, the same options inline |
| The directory on the host; a failure gives the turn back and marks the row | `prepare/3`: `mkdir -p` | `prepare/4`: `mkdir -p`, then `rm -f` of the pid file |
| `Copies.starting`, then the row `starting` with `start_until` | yes | yes |
| `Holder.hold` of `sh -c <wrapper> <$0> …args argv…` with the caller's env | yes | yes |
| dtach refused: the row refused, the turn back, `{:refused, {:start, reason}}` | `started/6` | `settle_start/5` |
| dtach's reply cut: wait until `start_until`, then read the host | `started/6` | `launch/3` and `settle_start/5` |
| A read that fails: the row stays `starting`, the turn stays held | `settle_start/4` | `settle_start/5` |
| After a restart, a row `starting`: before `start_until` nothing; after, one read, then as above | `settle_row/4` | `settle_row/3` |

Where they differ, and what stays in each app:

- **The wrapper.** The job's keeps a timeout, ends its group at the command's exit, and writes
  an exit file (`mkdir` picks its one writer). The service's records its pid, then `exec`s the
  program with its output appended to the log.
- **The run's name for the turn.** A job's is its id; a service's is `service:<name>`.
- **What dtach's held reply means.** For a job, the job is live. For a service, the host is
  still read for the pid and its start time (`held`, `gone`, `none`).
- **The read after a cut reply.** A job's reads the socket, then the exit file, in one shell,
  and is tried again until the job's deadline. A service's reads the pid file once.
- **The read of a dead socket.** A job reads it with the exit file, in one shell, so it can never
  read the file before the socket is gone. A service reads `Holder.state/2` every 100 ms. They
  read different things for different reasons, so each stays in its app.
- **The row.** A job's row becomes `running` or `refused`. A service's gets the pid and start
  time, or becomes `ended` (the program already exited) or `refused`, and loses its owner.
- **The sync's `:fetch`.** Only a job records paths to fetch back.

## What was moved, and where

`Copies.Held` (219 lines, about 110 of them docs, comments and blank lines) is pure functions
over a context map, in the caller's process:

- `context/3`: the host, the copy, its path, a `Holder`, `dir` and `base` (`<dir>/<kind>/<name>`
  for the caller's own files), `name` (the socket) and `run` (the turn).
- `ready/4`: take, sync, the directory with the `:clear` files removed in one shell, then
  `starting`. Each refusal of the take, the sync or the directory goes to the caller's
  `refused` function first, which marks its row.
- `copy_opts/1`: the rsync options, also used by `Jobs`' fetch.
- `hold/5`: `Holder.hold` of `sh -c script args… argv…`.
- `settle/5`: from dtach's reply. Held: `read.(:reply)`. Refused: `{:refused, {:start,
  reason}}`. Cut: wait until the start's deadline, then `read.(:cut)`. Then `write.(seen)`, and
  the turn goes back, unless the read or the write answered `{:unknown, _}`.
- `settle_cut/4`: the same after a restart. Before the deadline it answers `{:unknown,
  {:starting_until, until}}`.

**Why `caf_copies`.** Both apps already use it, and the turn and the sync are its own. The
settle exists to know when the turn can go back. `caf_copies` now declares `caf_holder`, which
is in the base layer below it, so the layers still go one way. `caf_jobs` no longer uses
`Holder` directly, so it no longer declares `caf_holder`, which `caf.deps` requires.

## Tests

`apps/caf_copies/test/held_test.exs`, 6 tests and 2 doctests, on real dtach sockets. They use
the workstation and a stand-in ssh host that exits 255 while a `down` file exists.

- `StartsOnSyncedCopy`, on the workstation and on ssh: `ready` holds the turn `starting`; the
  held program prints the synced file into the copy; `settle` reads with `:reply` and writes
  `{:ok, :held}`; the turn is free.
- `NoUntrackedProcess`: a start that landed but whose reply was cut is read with `:cut`, no
  earlier than its deadline, and settled; the turn is free.
- `OneSyncWrites`: with the host down, the read after a cut answers unknown. Nothing is
  written, the turn stays `starting`, and another take is refused. `settle_cut` before the
  deadline does not read; after it, with the host back, it settles and frees the turn.
- `OneProcess`: a second hold of a live name is refused by dtach, settled as `{:refused,
  {:start, {:live, name}}}` with no read, and the turn goes back; one program runs.
- `StartsOnSyncedCopy`, refused sync: the refusal goes to the caller's `refused` function,
  the host's directory is not made, and nothing runs.

## Findings

### new-1. Two edge outcomes of the settle are now the same for both apps

What happened: in edge cases the two apps settled differently. A job gave the turn back even
when its row's write failed, and ignored what `Copies.give_back` answered. A service kept the
turn when the write failed (its settle after a restart gives it back), and answered
`give_back`'s own failure. The shared settle gives the turn back unless the write answers
`{:unknown, _}`, and does not answer `give_back`'s outcome. For a job, a write that fails
answers `{:ok, :running}` as before, so its turn still goes back. For a service, the call now
answers its row even if `give_back` fails. That can only happen when the `Copies` process is
gone, since the run holds the turn in `starting`. Why: one rule fits both apps, and the
difference only shows when a process is down. What I did: chose the rule above; no test
changed. What the design should change: nothing, unless the design wants `give_back`'s failure
in the answer. Then `settle` would answer `{:unknown, {:give_back, _}}` for both apps.

### new-2. The unit grows the code, though both apps shrink

What happened: the brief expects the code to shrink. `jobs.ex` and `services.ex` lose 117
lines between them, but `held.ex` is 219, about half of it docs. Why: each shared step became a
public function with its own `@doc`, as the repository requires. What I did: nothing more. What
the design should change: nothing. The part 2 of `Services` (restart, `hand`, `logs`) now
reuses `ready/4`, `hold/5` and `settle/5` instead of repeating them.
