# F-283: each test that starts a tree takes an instance name of its own

## Why

An instance's name is a lock in its VM: `Home.Lock` registers its holder by the name, and the
tree's `Registry` is named by it too. `tree_main_test.exs` and `console_test.exs` in
`caf_example` are both `async: true`, and both started their trees as instance `"t"`. When the
two ran at once, the later start was refused `{:instance_running, "t"}` (seen at
`tree_main_test.exs:105`).

Apart from that, `delegates_test.exs:410` failed on `main` on the Linux workstation, alone as
well as in the suite.

## What was built

- `TestHost.instance_name/1` in `caf_test`: a label and a unique integer, such as
  `"console-4711"`.
- `tree_main_test.exs`, `console_test.exs` and `surface_test.exs` take their instance from it.
  `surface_test.exs` used `"t"` for every tree it starts and every facade call by name; those now
  read `ctx.i`. Its one `Acts` with `instance: "t"` is left alone: there the instance is only a
  label in a cue's topic, not a lock.
- `delegates_test.exs`'s "queued with wait: false" test waits for the row's mark to clear rather
  than reading it the moment the notice shows.
- `tmux_contract_test.exs`'s "only a capture shows the pane's screen" test, which failed in every
  gate run under load: its wait was a `with` whose unmatched value, a capture taken before the
  script printed, is an `{:ok, …}` too, so `await/2` took it as done. It is a `case` now, and only
  the printed screen ends the wait.

The other tests that start a tree already named their instances per test: `home_test`,
`home_lock_test`, `subscribe_test` and `conversation_test` in `caf_surface`, the second tree in
`tree_main_test`, and `caf_real`'s `RealCase`. The fixed names left under `apps/*/test` (`"a"`,
`"t"`, `"i"` and the like) are `Acts`' `instance:` option, a label in its cue topic, or a
`Config.new/1` that starts nothing (`config_test`).

## The cause of delegates_test:410

A test-only race. `Delegates.tell_starts/1` follows `Delegate.tla`'s `StartTold` then
`StartCleared`: it hands the notice to `Mailbox`, and only once that answers does it write the
row's `tell: nil`. The order is the point: a restart between the two tells nothing twice, since
`Mailbox` keeps the notice's key. The test awaited the notice in the mailbox table, then read the
row at once and asserted `tell: nil`. On this host the test's poll sees the notice before
`Delegates` writes the clear, so the row still read `tell: "main"`. The product does what the
model says; the test now awaits the clear.

## Measured

- `delegates_test.exs:410` alone: failed on `main` every run; passed 5 of 5 after, and the whole
  file passed.
- `tree_main_test.exs` with `console_test.exs`, run together: 13 passed, 5 of 5 runs.
- `surface_test.exs`: 45 passed.
- `gate-test` three times, one after another, on the final tree: each run's one failure in common
  is `mailbox_typed_test.exs:186` (new-3). Run 1 also timed out once in `mains_test.exs:529` (a
  main's title, `start_main` past 60 s, at a load near 28 on 12 cores); it passed in runs 2 and 3.
  `delegates_test` and `tmux_contract_test` passed in all three.
- Before the `tmux_contract_test` fix, a first round of three runs failed it in each. In that
  round's first run `delegates_test.exs:410` failed too, with the assertion this unit replaced in
  its message; the file's content was the new one before and after, and the two later runs passed
  it. I could not find why that run compiled the old text.

## Findings

### new-1. An instance name is a VM-wide lock, and nothing in the test aids said so

What happened: two `async: true` test modules each started a tree as `"t"` and refused each
other. Several other tests had already met this and each wrote its own
`"<label>-#{System.unique_integer([:positive])}"`. Why: the instance name is the one global name
a tree takes, by design, and a test author copying a config reaches for a short fixed name. What I
did: one helper, `TestHost.instance_name/1`, and the three tests that used `"t"` take it. What the
design should change: the test rules in `CLAUDE.md` could say that a test that starts a tree names
its instance with `instance_name/1`, as they already say each test uses its own tmux server and
dtach sockets. The existing per-test helpers in `home_test`, `subscribe_test` and the others could
move to it in a later unit.

### new-2. A test that reads a row right after the notice it awaits races the row's second write

What happened: `delegates_test.exs:410` asserted the mark cleared as soon as the notice showed.
Why: `StartTold` and `StartCleared` are two steps, in that order, by design. What I did: the test
awaits the clear. What the design should change: nothing in the product. A test of a two-step
protocol should await each step's own effect, not infer the second from the first.

### new-3. A multi-line paste can reach a pane whose viewer never saw bracketed paste turned on

What happened: `mailbox_typed_test.exs:186` ("a 300-character and a 5-line message each go
pasted") failed in every gate run and in one of two runs alone. The stand-in recorded only
`From operator (message):` as submitted: the paste's first newline acted as Enter. Why, as far as
I can tell without measuring it: `ScreenStandIn` turns bracketed paste on (`ESC [?2004h`) once, at
its start. dtach keeps no output, so a tmux viewer that attaches after that print never sees the
mode, and `tmux paste-buffer -p` brackets only for a pane whose program asked for it. The text then
goes unbracketed, and each newline submits. The same can happen to Claude Code if it asks for the
mode only once and the viewer attaches, or is replaced, after. What I did: nothing; it is F-279's
delivery, not this unit's. What the design should change: measure in `caf_real` whether Claude Code
turns bracketed paste on again when it redraws on a resize. If it does, the stand-in should do the
same on each resize draw. If it does not, the delivery of a text with a newline should not rely on
the pane's mode: it should refuse it, or send it in a form whose newlines cannot submit, until the
pane is known to bracket.
