# F-270: four gaps an app met on prompts and interrupts

## Why

An app that embeds the framework built on F-254 (answered prompts) and F-258 (the operator
interrupts a main session) and met four gaps: an ask its own check let through was refused
after; a prompt the framework closed read `closed` with no one named; `answered/2` read every
agent's closed prompts at once; and a second interrupt of one main session was refused as
already claimed until a hook event came.

## What was built

1. **An ask's option without a description.** The design asks two to four options, "a label
   and a description each" (`ask`, "Agents working together"), so a description stays required.
   The framework had no check of its own for an app to call: the app's check was its own, and
   it let an option with no description through. `CodingAgentFramework.check_ask/1` is now that
   check, and it is `Mailbox.Ask.questions/1`, the one function `Mailbox.ask/4` refuses an ask
   by, so the two cannot differ. It needs no instance. The design says so ("Prompts"' built so
   far).
2. **A prompt the framework closed names who closed it** (F-254's new-1). The read that finds
   a prompt it listed before gone writes one `closed` fact in `Acts`: actor `prompts:<host>`, act
   `closed`, keyed `closed:<host>:<prompt id>` (once across restarts), target as its `opened`
   fact, and `by` in its detail, read from the owner's row in that same read. `answered/3` reads
   it as `by` and `at`. `by` is never nil: the answer row's actor, a hold's recorded actor
   (`app`, `pause`, `capped`, a name), a startup dialog's press's actor in `Acts`, a `Watch` row's
   `answered_by`, or `{:framework, why}`, `why` one of `:expired`, `:default`, `:ended`,
   `:withdrawn`, `:passed`, `:unknown` and `:logged_in`. `Prompts`' module doc has the table of
   every place a prompt closes and its `by`. A close no read saw (the inbox was down) is named
   by the first `answered/3` page that holds it, marked `late`, with `at` nil. The `opened` fact
   now also keeps the prompt's deadline, so such a close can still be told `expired` or
   `default`.
   - Why not F-254's first recommendation (each owner writes its own close through
     `Prompts.answering/4`): that is a change in seven owners (`Intake`, `Sessions`, `Limits`,
     `Delegates`, `Mains`, `Watch`, `Logins`), each learning the inbox's prompt ids. Every owner
     already keeps how its row ended (`Intake`'s `hold` and `actor`, a dialog answer's `act`,
     `Watch`'s `answered_by`), so the inbox reads it in one place, as it reads every open prompt.
3. **`answered/3` takes `agent:`**: the prompt's `agent`, the same field `read/3`'s `agent:`
   filters on. That is the agent whose wait it is: the asker of an ask, a permission or a
   dialog, the agent a start waits to start as, the agent a remedy is about. I chose it over
   "the agent it was for" since it is the field both reads share and the `opened` fact's target,
   so the filter is a term of the ledger's query (`target = ?`) on its unique `(target, state)`
   index, and the page is bounded as before: `limit` plus the count open now. A key it does not
   take, or a value it does not, is `{:refused, {:bad, key}}` (`kind:` is `{:bad, :kind}`,
   `limit: 0` is `{:bad, :limit}`); a filter that is not a keyword list is still `{:bad,
   :filter}`.
4. **A second interrupt of one main session.** Diagnosis: `MCP`'s fix claims the state
   `Mains.fix_state/3` reads with `fix: :interrupt` (status, session, process, held requests,
   `offset`). Escape writes no hook event, so after the first interrupt settled the state was
   the same, and `Acts.claim/6` refused the next as `{:already_claimed, op}`: after one that
   ended the turn as well as after one that did not.
   - The fix: that state also names `interrupted`, the id of the newest row of the operator's
     interrupt of the session in `Acts` whose act ran and settled. Once the first settled, the
     next is a new state and is claimed. While the first is under way the state is the same,
     and a second is refused `{:claimed, op}`, as one at a time should be. A claim a restart cut
     moves nothing: its key may have gone (`Claim.tla`'s `NoActOnCutOffClaim`). A claim let go
     (its act refused) moves nothing either: its state was freed already.
   - After one that ended the turn, the next is claimed, finds no turn on the screen, and is
     refused `{:screen, reading}` (the design's word, as a delegate's is), its claim let go.
   - After one whose key reached a screen that went on running (`{:unknown, {:still_running,
     reading}}`), the next presses Escape again, with no wait for a hook event.
   - `Mains` reads the rows through `Acts.rows/3` (actor the operator, target the session, act
     `interrupt`, status `settled`), within half its step. One target's interrupts are few.
- **Facades and docs**: `CodingAgentFramework.answered/2` and `check_ask/1`, `Prompts`' and
  `Mains`' docs, the design's "Prompts" and "Main sessions", and the README status line.

Nothing changed in `Mailbox`'s code, `caf_scheduler` or `caf_runs`. `mailbox_ask_test.exs` has
one more assertion (item 1).

## Model

`Team.tla`: the claim rule is unchanged (`Claim.tla` still keeps an acted row's state for good,
and `FreeActed` is still its Break); the state a main session's interrupt claims moves instead.
`FixActs` had one branch for a fix that did not help, which kept the state. Now a main session's
interrupt that did not help (`Retried`) moves `epoch` and leaves the session stuck; a resume, an
answer and a delegate's interrupt keep the state, as their code does. The faults bound counts
the moved state, as it counts a stick, so the states stay few, and at the bound an interrupt
helps. `MaxEpoch` needs no change: each such move uses one of the faults.

- `InterruptRetryOpen`: no ended claim of an interrupt that acted on a main session stands on
  its current state while the session is still stuck.
- `Team_InterruptRetry.cfg`: one project, its main session, the operator, two faults, a
  restart. `Team_OperatorClaims.cfg` checks the new invariant too.
- `Break_Team_RetryBlocked.cfg`: the moved state left out, as the code before this unit. TLC's
  trace: the session is prompted, sticks, the operator claims its interrupt, the interrupt acts
  and does not help, and the claim stands on the state of a session still stuck.
- The header names `Mains`' interrupt state.

## Tests

- `mains_test.exs`, "a main session's second interrupt is claimed once the first settled,
  refused once idle": the screen stand-in started with `--screen running --ignore-escapes 1`
  (new: the turn goes on past its first Escape, each one a line in `<dir>/escapes`), a real
  `Acts`, and the claims taken and settled as `MCP`'s `act/5` does. The first interrupt's state
  has `interrupted: nil`; while its claim is open the state is the same and a second claim is
  refused `{:claimed, "op"}`; it answers `{:unknown, {:still_running, _}}` and the stand-in
  took one Escape. Settled, its old state is `{:already_claimed, "op"}` (the gap), the state
  read now has `interrupted` its row and the same `offset`, the old state presses nothing
  (`{:moved, now}`), and the new one is claimed and answers `{:ok, :sent}`. The third is
  claimed, refused `{:screen, %{state: :idle}}` with no Escape sent, and its let-go claim
  leaves the state the same and free.

- `prompts_test.exs`, "a dialog whose start was stopped reads closed by the agent's end": a

## Findings

### new-1. The framework had no check of an ask for an app to call

What happened: the brief names "the facade's own check of an ask (the one an app calls first)".
The facade had none: the only check was `Mailbox.Ask.questions/1`, behind `Mailbox.ask/4`.
The app's check was its own, and it took an option with no description.

Why: F-138 built the check inside `Mailbox` only, for the `ask` tool.

What I did: `CodingAgentFramework.check_ask/1` is that function. The `ask` tool's JSON schema
also says `description` is required, but a schema says nothing of a blank one, which the check
refuses.

What the design should change: nothing more, unless the app's own check should go: say in the
app's guide that `check_ask/1` is the check.

### new-2. An interactive delegate's second interrupt has the same gap

What happened: `Delegates.fix_state/3` puts `offset` in an interactive delegate's state, as
`Mains` did, and nothing else moves after an Escape that reached a screen that went on running.
Its parent's second interrupt is refused as claimed until a hook event comes.

Why: the same as item 4. `Team.tla`'s `Retried` keeps a delegate's state, as its code does.

What I did: nothing in `Delegates`; the model says which agents move.

What the design should change: give `Delegates`' interrupt state the same `interrupted` term
(the newest settled interrupt by the parent), and drop `r.t \in Mains` from `Retried` and
`InterruptRetryOpen`.

### new-3. A late close is named from the owner's row as it is then

What happened: a close the inbox did not see is named when a page first holds it. An owner's
row may have moved on since (a dialog's answers written over by a later start, an agent row
ended later), so its `by` may be `{:framework, :withdrawn}` or `:ended` where the press was the
app's.

Why: the inbox keeps no row of its own, and the owner keeps only its newest state.

What I did: such a close is marked `late` and read with `at: nil`, so a reader knows it was
not seen when it happened.

What the design should change: if an app needs an exact closer for closes made while the inbox
was down, F-254's first way (each owner writes its close with its actor) gives it; the inbox's
reads would then prefer that row.

### new-4. The interrupt's need of a running turn is checked at the act, not before the claim

What happened: `Team.tla`'s `Needed` takes an interrupt's claim only on a stuck agent. The code
cannot read the screen from the state alone (`Mains.fix_check/2` reads `status`), so after an
interrupt that ended the turn the next is claimed and then refused by the `Inlet`'s screen
read, its claim let go. The ledger holds one more row, `not_verified` with no act, per such
call.

Why: the screen is read by the `Inlet`, in the press.

What I did: left it; the let-go claim blocks nothing, and the answer is the design's
`{:screen, reading}`.

What the design should change: if a refusal before any row is wanted, put the screen's turn
(`running` or not, one pane read) in the interrupt's state, so `fix_check/2` refuses
`:idle` before the claim and a successful interrupt's settle reads the state moved (verified).
