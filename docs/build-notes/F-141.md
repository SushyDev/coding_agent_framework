# F-141: `Mains`: a project's main sessions, its checkout, the pull, `start_main`

Item 13's last part (`docs/design.md`, "Main sessions", item 6): each project's main sessions
as agent rows of kind `main`, the project's checkout under the framework home, made once, the
pull after a landing only while the checkout is clean, and `start_main`, through the
`Scheduler` and F-140's startup dialogs. A main session's end is not built: the design does not
say what ends one (new-1).

## What was built

- **The model first: `Checkout.tla`**, a spec of its own (about 260 lines). The remote's trunk
  as a count that landings raise; the checkout's path and the clone's temporary path; the
  checkout's trunk, `origin/<trunk>` as the last fetch left it, an edit and a local commit a
  person makes or takes back at any step; the owed pull, in memory; the pull's fetch, clean
  check and merge as three steps; restarts that lose what is in memory and keep what is on disk.
  Invariants `NoLostEdit`, `WholeCheckout`, `Forward`; liveness `Made` and `CaughtUp` (once the
  remote stops moving and the checkout stays clean, it holds the remote's trunk). One
  configuration, `Checkout_Design`, and one break per guard: `CloneInPlace` (the clone writes
  the checkout's own path), `ResetHard` (the pull resets trunk), `ClearAfter` (the owed pull is
  cleared after the merge: a landing during a pull is lost), `NoPullAtStart`, `ClearOnDirty`
  (a pull held back for an edit is dropped).
- **`caf_mains`, a new app**, after `caf_sessions`, `caf_mailbox` and `caf_scheduler`:
  - `Mains`, one process per host. The app hands it its projects, each naming its `origin`,
    and the main sessions it declares (name to project), which it declares in `Sessions`
    before its start answers. Each checkout is cloned on trunk at
    `<home>/checkouts/.<project>.clone` and renamed into `<home>/checkouts/<project>`; a start
    removes a clone a restart cut. A pull is owed after `landed/2` and at each start, cleared
    as its task starts; the task reads first, fetches only from a clean checkout on trunk that
    is not ahead, reads again, and runs `git merge --ff-only`. A reading that holds the pull
    back leaves it owed, and the read on the next interval pulls once the person cleaned it; a
    clone or a fetch that failed waits for the next `landed/2` or start. git runs under `env -i`
    with the project's environment and the host's reaper, one task per project at a time.
  - `start_main/5` (the design's `start_main(project, name, brief)`, with `from:`): the name
    checked (any agent row holds it but a declared main session of that project, a start of it
    under way, `framework` or the operator's name: `{:running, name}`), the project and its
    checkout, the brief's length; the account with the most allowance left; the agent row
    declared; its own row `starting`; a lease, class `:main`, module the project, holder
    `{"main", key}`; then the brief stored from the caller, marked by `launch`, and
    `Sessions.start/5` interactively in the checkout with the app's MCP config. A trust dialog
    on the new checkout answers `{:unknown, {:dialog, :trust}}` and the row waits; it runs once
    the agent row does, at a `sessions:` cue. A row a restart left `starting` is settled by the
    agent row of its call, or refused `interrupted` at its deadline. A start queued for its
    lease when the `Scheduler` ends is refused.
  - `Mains.Checkout`, the pure part: paths, git's arguments, a reading from git's output, and
    whether a pull may go. `Mains.Table` (`checkouts`, a `Tracker` source: topic `mains`),
    `Mains.Starts` (`main_starts`), and `Mains.Work`, the lease's holder for the `Scheduler`
    (live while the start is under way and while its agent row may hold a process or a move
    is under way).
- **`Sessions`**: `declare/4` in place of the `mains:` option ("until `Mains`"), refusing a
  name that cannot be a session's and a delegate's; `Sessions.Agents.declared?/1`.
- **`Grants.may_start_main?/2`**: a main session or the operator, never a delegate.
- **`MCP`**: the tool `start_main(project, name, brief)`, through a `mains:` handle;
  `Operator.start_main/4`.
- **`Scheduler`**: reads the `mains` topic, so a start refused after its grant releases its
  lease at once.
- **The example app**: each project names its `origin`; `Config.new/1` fills its `repo`, the
  checkout (`Mains.project/3`), so `Sessions` and `Delegates` make worktrees from the
  framework's own clone; `mains` is now name to project; `main_model` is the model a main
  session runs. It starts `Mains` after `Mover` and before `MCP`, gives the `Scheduler` the
  `main` holder and the `Tracker` the `checkouts` source.
- **Tests**: `MainsTest` on real git, tmux and dtach with the screen stand-in: a cut clone
  removed and the checkout made whole (`WholeCheckout`); a landing pulled; an edit holding the
  next pull back, owed, never lost, and the read after the person cleans it pulling
  (`NoLostEdit`, `CaughtUp`); a commit on trunk read `ahead`; a start of `Mains` pulling what
  landed while it was down (`NoPullAtStart`'s guard); `start_main` refusing the reserved names,
  an unknown project and a name whose start is under way or runs, its lease's class and holder,
  the trust dialog waiting on a person, the row running once answered, and the brief its
  prompt, from its sender, by `launch`. `ExampleTest`: the checkout cloned at the start (every
  delegate's worktree now comes from it), `start_main` through `MCP` and the operator, and the
  cue routing with `mains:<host>`. `MCPTest` and `AgentsTest` follow the new tool and
  `declare/4`.
- **Docs**: `docs/design.md` ("How `Mains` does it" under "Main sessions", the parts table,
  the cue table, the example's paragraph, the model, the unit order), `README.md`'s Status and
  "The apps" chart.

## What I ran into

- An app's tests cannot run from its own directory in this umbrella (an `only: :test` dep that
  another app uses at run time is refused there); `MIX_ENV=test mix do --app caf_mains test`
  from the root runs one app's tests.
- A test of the clean check raced the interval read: an edit written while a pull was between
  its check and its merge was carried by git, as the model allows, and the pull went. The test
  now waits for a reading that shows the edit before the landing.
- Claude Code's command line needs a model; the design's `start_main` names none, so the app's
  launch does (`main_model` in the example, new-8).

## Findings

### new-1. Nothing in the design ends a main session

What happened: the brief asks that a main session's kept services end with it or go to a
person (F-109's new-4) and that its delegates be told "as their parent's end says". The design
says a main session is never archived, `Team.tla` keeps `\A m \in Mains : proc[m] # "ended"`,
`Sessions.ended/3` refuses a main session, and no section says what ends one or what its
delegates are told then. Why: a main session's end was never a step of the design; only its
process ends (a move, a crash), and its delegates and services outlive that. What I did:
built no end. A main session's process that exits is `stopped`, as before, and is resumed as
before. What the design should change: decide the end as an act of the operator alone,
`end_main(name)`, modeled in `Team.tla` first: refused while any of its delegates has not
ended (`{:refused, {:delegates, names}}`), so no delegate is left with no parent; the session
stopped by SIGTERM once idle, as a move's stop is; its agent row `ended`, so
`Sessions.Agents.ended?/1` holds for it and the app's `Ends` ends its services; a kept service
ends too, since the operator owns nothing and `Grants.parent/2` answers `:main_has_no_parent`.

### new-2. `Mains` owns two tables, where the parts table said none

What happened: the parts table had `Mains` own nothing. A view must show each checkout's
reading, and a start's lease needs a holder row written `starting` before the lease is asked
for (F-134's new-1); the agent row cannot be it, since a declared row is free and the
`Scheduler` would release the lease before `Sessions` writes `starting`. Why: neither was
foreseen when the table was written. What I did: `checkouts` (a `Tracker` source) and
`main_starts`, both written by `Mains` alone, and the parts table now says so. What the design
should change: confirm it, or name another owner for the checkout's reading.

### new-3. What tells `Mains` that something landed

What happened: `Stacks` is not built, and a landing's job (class `landing`) passing its gates is
not a merge. Why: the merge is `gh stack`'s, a later unit's. What I did: `Mains.landed/2`, which
the app calls; a pull is also owed at each start of `Mains`. What the design should change:
say that `Stacks` calls `landed/2` once it has seen a stack's layer merged into trunk.

### new-4. A refused start leaves its name declared and its brief queued

What happened: a start refused after its agent row was declared (by its lease, or by
`Sessions`) leaves the row `declared`, so the name shows in the tree and may be started again;
its brief stays `queued` in `Mailbox` and goes in, first, with the next start of that name,
before that start's own brief. Why: `Mailbox.ended/3` ends every queued row to an addressee,
which is right for a delegate whose start was refused but would drop messages another main
session sent a declared one. What I did: nothing more. What the design should change: a
`Mailbox` settle of one row by its uuid (`ended`), which `Mains` calls for the brief of a
refused start.

### new-5. A main session's resume after its process ended runs with no lease

What happened: `Mains.Work` answers `:ended` once the agent row is free with no move under
way, so the `Scheduler` releases the lease when a main session's process exits; a person who
resumes it later (or a recovery) starts it with no lease. A move keeps it live. Why: a lease
lasts as long as its work, and a stopped main session does no work; the design does not say
whether its resume is new work. What I did: what the lease rule says. What the design should
change: say whether a resume of a main session asks the `Scheduler` for a lease of its own
(class main session), as a start does.

### new-6. A failed fetch, or a merge a restart cut, waits for a person

What happened: a clone or a fetch that fails (the network, the remote's credentials) is a
state the view shows, `failed` with its reason, and is not tried again until the next
`landed/2` or start of `Mains`: no hidden retry. A merge a restart cut may leave git's
`index.lock` in the checkout, and every git command there then fails, reads included. Why: the
framework never removes a file in the checkout it did not write. What I did: nothing more.
What the design should change: say whether a person's act clears a checkout's stale lock, as
`Recoveries`' clear works for its states, or whether the view only shows it.

### new-7. The unit is over 500 changed lines

What happened: the library grew by about 1 230 lines, `Mains` itself by 700. Why: the clone,
the read and pull loop, the start with its lease, its brief and its settle after a restart are
each small, and the brief asked for all of them with the model and the example's rewiring.
What I did: kept git's arguments and readings in the pure `Mains.Checkout` and the holder in
`Mains.Work`. What the design should change: nothing; a later unit of this kind could split
the checkout from the start.

### new-8. `start_main` names no model

What happened: Claude Code's command line needs `--model`, and `start_main(project, name,
brief)` names none. Why: a main session's model is the app's choice. What I did: the app's
launch for `Mains` names it (`main_model`, `"opus"` by default in the example); a move's resume
takes the agent row's. What the design should change: say that the app names a main session's
model, or add it to `start_main`.

### new-9. A cut fetch in `JobsTest` can outlive the test VM

What happened: the first of the extra `gate-test` runs failed only on its check of what the
test VM left running: the host side of a fetch (`rsync --server --sender` under `flock`, of
`big.bin`) from `JobsTest`'s "AnswerIsReal: a fetch cut by a drop". Every test passed; the next
three runs left nothing. Why: not read further; this unit touches neither `Jobs` nor `Copies`.
What I did: ran `gate-test` again. What the design should change: nothing; a unit on `Jobs`
should find what keeps a cut fetch's host side alive past its drop.
