# F-243: the real suite runs steps 12 and 13, and records each press

## What was built

`docs/e2e.md` steps 12 and 13 had been run by hand only, and F-242's new-1 found that the real
suite kept no screen around a press, so a `still_shown` answer could not tell a late marker from
a misread press. This unit adds two real tests and records every dialog or menu press the
suite makes. It is built on F-239's `RealCase` (its branch, not yet on `main`).

### Every press is recorded (`RealCase.press/4`, `press!/4`)

`press(ctx, agent, id, label)` answers prompt `id` from the inbox with `label`, as `answer/3`
does, and writes a folder in the records folder, `<project>-press-<n>-<label>/`:

- `before.txt` / `.ansi`: the pane before the call, so before the keys;
- `frames/<i>-<ms>ms.txt` / `.ansi`: every distinct pane read while the call ran, read about
  every 50 ms by a process beside it, `ms` from the call;
- `marker.txt` / `.ansi`: the last frame that showed Claude Code's marker (`❯`) on the label;
- `enter.txt` / `.ansi`: the first frame after it that did not, the nearest read to the Enter;
- `after.txt` / `.ansi`: the pane after the answer;
- `press.txt`: agent, prompt, label, the answer whole, the UTC time of the call, its ms, and
  which frames `marker` and `enter` are (or `none read`).

`press!/4` asserts `{:ok, _}` and its failure names the folder. Every press the suite makes goes
through them: `answer_trust/2` (every trust press of a main), the interactive delegate's trust
press in `interactive_delegate_test.exs`, the menu press in `question_menu_test.exs`, and the
exit press `end_run/1` makes for a main left on its dialog. A press made inside the library
(an interactive delegate's stop, F-231's exit press) is not one of them (new-2).

### Step 12, `background_command_test.exs`

A main session, then a headless delegate (`unit/bg`) told to run `sleep 30; echo bg $((6*7))`
in the background, not wait, report `started in background`, and reply with the output when it
ends. The output, `bg 42`, is not in the command's text, so a reply that names it read it. The
test:

- follows the delegate's event log (`streams/<session>/events.jsonl`) from a process of its own
  (`RealCase.follow/1`), stamping each line with the monotonic ms it was first read, since the
  log has no times of its own;
- allows the `Bash` request from the inbox, checks the main session was told of it once (a
  `prompt` delivery naming the request's id), and records the request, the answer, its time
  and that delivery as `<project>-permission.txt`;
- waits for the delegate's `report` delivery in the main session's transcript, and checks the
  log had no `task_notification` yet: the report went while the command ran;
- waits for the notice of its own turn, `From framework (notice): Delegate <name>, in a turn of
  its own after its report:`, naming `bg 42`, then the delegate idle;
- checks the log: two `system`/`init`, two `result`, the `exec </dev/null; ` correction (F-180),
  and the wake gap, the command's `task_notification` to the next `init`, under `Stream`'s
  `wake:` (30 s, the design's bound, F-204); and one report and one such notice, each once.

Deliveries are read by `RealCase.deliveries/2`: each `From <sender>[ on <account>] (<kind>):
<text> [delivery <id>]` in the transcript, once per delivery id, since the JSONL holds each two
or three times (the hook's feedback and the turn's message), with its escaped newlines read
back.
- records the log's events with their times and the gap as `<project>-background.txt`;
- stops the delegate and ends the main session.

It does not check that `agents` reads the delegate working while its own turn runs (a read in
a window of seconds), nor `usage`'s reading; those stay in `docs/e2e.md`.

### Step 13, `absent_main_test.exs`

A main session idle; its row's pid is checked as Claude Code's by `ps` and ended by that pid
alone (`kill`); the row reads `stopped`, reason `exited`. Then the operator's `resume`, a trust
dialog if one comes, idle, the same session id and a new pid. One message (`Reply with only the
sum of 17 and 25.`) is answered `42` on the screen, and the transcript still holds the first
turn. `Acts` holds the one resume as two rows, as the design's "An act" says (a resume by
`Sessions` is an act of its own): the operator's claim, `verified`, and `Sessions`' own
(`sessions:<host>`) under the same `start_id`; none is the healer's (`absent_mains:<host>`).
The first real run read exactly that (ids 116 and 117). The rows, the `ps`
line, the answer, the acts, the symptoms and the prompts go to `<project>-absent-main.txt`. Then
the main session ends.

The healer resumes an absent main by itself at once, so the test's tree takes `absent_main` off
the allow-list (`start_tree!/2`'s new `adjust` function, on the parsed config): the absence is
only asked, and the one resume is the operator's, as the brief asks (new-3).

### Each test's own

Each test starts its own tree (`real12`, `real13`), project and main, states a bound per wait,
and ends what it started; `end_run/1` ends what a failed run left. `caf_real` now declares
`caf_acts` and `caf_stream`, which the tests use.

## What I ran into

- The worktree had no `deps`: `mix deps.get` first.
- A test cannot see into a press: the `Inlet` reads the marker and sends Enter inside one
  call (new-1).

## Findings

### new-1. A press's own reads are not visible outside the `Inlet`

What happened: the brief asks for the screen after the marker's read and after the Enter. Both
happen inside one call of the tree's `Inlet`, and only an unknown answer carries a reading.
Why: `Inlet.choose/5` is one step by design, and nothing it reads is kept. What I did: the
suite reads the pane beside the press, about every 50 ms, and names the nearest frames
`marker` and `enter`; under load those reads come late as any other (F-216's new-1), so a frame
can miss a redraw that the `Inlet` saw. What the design should change: if a press's record must
be exact, have the `Inlet` answer the readings it made (the marker's and the leave's) with every
answer, or keep them on the press's act row.

### new-2. Presses made inside the library are not recorded

What happened: an interactive delegate's stop and a main's end press the exit dialog in the
library (F-231), not through the inbox, so `press/4` does not see them. Why: they are part of
`Operator.stop/2` and `end_main/3`. What I did: nothing; only the inbox presses and `end_run/1`'s
are recorded. What the design should change: the same as new-1 would cover them.

### new-3. Step 13 by the operator needs the healer off, and the config file cannot say so

What happened: `docs/e2e.md`'s step 13 is passed by the healer's own resume; the brief asks for
the operator's. With `absent_main` on the default allow-list, the healer resumes at the
absence's first check, before an operator could. Why: `AbsentMains` acts at once on a listed
kind. The example's config file has no `remedies` key. What I did: the test takes the kind off
the parsed `Config`'s `remedies`, so the absence is asked and the operator resumes; the healer's
path, its bound and the remedy prompt stay in `docs/e2e.md`. Not yet seen on the real program:
whether the asked absence leaves a `remedy` prompt open after the operator's resume settles it
(the record keeps the prompts). What the design should change: decide which resume the real
suite covers; if both, a second test with the default list, and a `remedies` key in the config
file.

### new-4. The event log has no times, and the correction may not be in it

What happened: the wake gap is read from when the follower first read each line, about every
100 ms, so it is good to about 100 ms plus the host's late wakes. And step 12's "the request's
command, as its event log shows it, begins `exec </dev/null; `" may not hold: the correction is
the `PreToolUse` hook's `updatedInput`, and the log's `tool_use` may show the model's own input.
Why: Claude Code's `stream-json` lines carry no time, and I did not see a real log. What I did:
the test asserts the correction anywhere in the log and records whether it was there; if the
first real run fails only there, the assertion is the thing to change, to the inbox request's
text or the hook's row. What the design should change: if the wake gap is to be checked
closely, have `Stream` stamp each line as it reads it, or answer the fold's `waking` stamp.

### new-5. A delegate's own turn is told as from `framework`, not from the delegate

What happened: `docs/e2e.md`'s step 12 expected `From demo-unit-bg on <account> (notice):
Delegate demo-unit-bg, in a turn of its own after its report:`. The real main session got
`From framework (notice):` and then that text. Why: `Delegates`' `tell_turn/4` sends it by
`Mailbox.notify/4`, which names no sender, so the framework's own header goes on it; the
delegate's name is only in the text. The report and the prompt name the delegate and its
account. What I did: the test matches what is sent, and `docs/e2e.md`'s line now says so. What
the design should change: decide whether a delegate's own turn should name the delegate and
its account as its sender, as its report does; a main session that reads senders now sees it as
the framework's.

### new-6. A delivery is in the transcript two or three times

What happened: each delivery (`[delivery <id>]`) is two or three times in the main session's
JSONL: the Stop hook's feedback and the turn's message, one of them escaped twice. A test that
counts a text's matches counts lines, not deliveries. Why: most likely Claude Code writes the hook's feedback once as
it comes and again in the message it begins; I did not narrow which line is which. What I did: `deliveries/2`
counts each delivery id once. What the design should change: nothing; a reader of a transcript
that counts deliveries should count their ids.
