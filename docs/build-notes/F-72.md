# F-72: `Copy.tla`, part 2: the fetch's check, the host's lock, the group's end

A model unit: `model/tla/Copy.tla`, its configurations, its part of `model/tla/READING.md`, and
`docs/design.md`. No code changes. Two builders: the first wrote most of it and stopped on a case
the design did not settle (new-1); the person settled it in "Hosts", and the second modeled the
rule and finished the unit.

## What was built

F-70's new-2, new-4 and new-7, which "Hosts" now settles, are in the spec:

- **The fetch's check.** `SyncBegins` takes the record of the job's named paths before rsync
  sends (`stale[j]` empty). `Edit` is the agent, or a subagent, editing a path at any time, which
  makes it stale for every job's record. `FetchPath` writes a path only if it is not stale, and
  otherwise adds it to `skipped`; `FetchDone` answers `fetch: conflict` when any were skipped. A
  path one job's fetch writes is stale for every other job. Property: `NoEditLost`, F-70's, over
  `since[j]` (paths edited after `j`'s sync began) and `clobbered` (the ones a fetch wrote over).
- **The host's lock.** A sync's host side (`hs`) is a writer of its own: `HostLocks` takes the
  copy's lock (`lock`) and begins writing, `HostGivesUp` is the lock's deadline passing while
  another host side holds it, `HostSideEnds` a host side that notices its local side ended and
  exits, and `SyncCompletes` frees the lock. Property: `OneSyncWrites`, counting host sides whose
  local side a drop or a restart ended.
- **The cut sync's turn** (new-1, settled by the person). `SyncCut` and `SettleUnasked` refuse the
  run at once, and give the turn back only once the sync's host side can no longer take the lock
  (`LockSettled`: it is not `"waiting"`: it holds the lock, has exited, or gave up at the lock's
  deadline). Until then the refused row keeps the turn, and `TurnBack` gives it back. The
  framework knows the deadline by the time; the spec reads `hs` for it.
- **The group's end.** `grp[j]` says the job's process group has a process left. `JobExits`
  ends it before the wrapper reaps the command, `HostTimesOut` at the timeout, and `WrapperLost`
  takes it with the wrapper (assumed, new-4). Property: `JobGoneAtEnd`, and `FetchOnlyAfterEnd`
  now counts the group too.
- `run`'s answers are "Hosts"' list: the fetch is `done`, `conflict`, `unknown` or none.
- F-70's `NoChangeUnderRun` is gone: the design allows a later sync under a running job or
  service (F-70's new-1), and the spec says so in its header.

Five new Breaks, each failing on the property it guards:

| Break | Removes | Fails |
|---|---|---|
| `FetchBlind` | the fetch's check of the record | `NoEditLost` |
| `RecordAfterSync` | the record taken before the sync sends (taken once it completes) | `NoEditLost` |
| `NoHostLock` | the host side's lock | `OneSyncWrites` |
| `NoGroupEnd` | the wrapper's end of the group at the command's exit | `JobGoneAtEnd` |
| `CutBeforeDeadline` | the cut sync's wait for its host side: the turn goes back at the cut | `StartsOnSyncedCopy` |

`Break_Copy_CutBeforeDeadline` uses `Copy_Turns`' constants. Its trace, 13 states: both runs ask;
the first's sync begins and a drop cuts it while its host side waits; `SyncCut` gives the turn
back; the second's sync takes the turn, its host side the lock, and completes; the first's host
side then takes the lock and writes; the second's start lands on a copy not whole.

No F-70 Break is obsolete: all 16 still fail on their property under the new guards, so none
was removed or rewritten.

## What I ran into

- The first builder's `Copy_Turns` failed `StartsOnSyncedCopy` in 13 steps: a sync cut while its
  host side still waited for the lock gave the turn back; the next run's sync took the turn and
  completed; the cut sync's host side then took the lock and wrote, and the next start landed on
  a copy not whole. The design did not say when a cut sync's turn goes back. That is new-1.
- `SettleUnasked` refuses a row in `"syncing"` after a restart, and it is a cut sync too: the
  rule applies there as in `SyncCut`.

## Findings

### new-1. A cut sync's host side may still be waiting for the lock

What happened: a drop or a restart cuts a sync whose host side has not yet taken the copy's
lock. The turn went back at the cut, as F-70's spec had it. The host side, still waiting, takes
the lock later, after the next sync's completes, and writes under the next run's start
(`StartsOnSyncedCopy`, 13 steps in `Copy_Turns`).

Why: the lock keeps two host sides apart, but not a host side from a start: the next run's
start does not take the lock.

What I did: the first builder stopped and reported it. The person settled it in "Hosts": a cut
sync gives the turn back only once its host side can no longer take the lock (it holds it, has
exited, or its lock deadline has passed); the refusal is answered at once, and only the turn
waits. The second builder modeled it (`LockSettled`, `TurnBack`) with
`Break_Copy_CutBeforeDeadline`.

What the design should change: nothing more; it says this now.

### new-2. rsync's server can delete before any file's data arrives

What happened: with `--delete`, rsync's receiving side may remove paths the file list leaves
out as soon as it has the list, before the data of any file arrives. The spec takes the lock and
begins writing in one step (`HostLocks`), which holds only if the lock is taken before rsync's
server starts.

What I did: kept the spec's one step, and say so in its header.

What the design should change: say in "Hosts" that the host side takes the lock before rsync's
server starts (the server runs under it, as its `--rsync-path`), not at its first write: "a sync
holds a lock of its copy for its whole life" reads that way, but `Copies` should not have to
infer it.

### new-3. What the spec assumes of the host

What happened: three things the guards rely on are not modeled.

- A host does not restart. A restart would end every held job without an exit file, and a sync's
  host side and its lock with it.
- A wrapper killed before it writes the exit file takes the job's group with it
  (`WrapperLost`). If the group outlives it, nothing ends the group and `JobGoneAtEnd` fails.
- The fetch's compare of one path and its write of that path are one step. An edit between the
  two is lost.

What I did: each is stated in the spec's header, "Assumed, not modeled".

What the design should change: for the second, say how the wrapper's group ends when the
wrapper itself is killed (for example, the job's group is the wrapper's own, so a kill of the
group takes both, or a later read ends a group whose wrapper is gone). For the third, say the
fetch compares and renames into place under one check (rsync's own compare-then-rename, or the
fetch compares after it writes to a temporary name and before the rename); an edit between the
compare and the rename is the one window left. The first needs no mechanism unless a person
wants one: a restarted host ends the run as `lost`.
