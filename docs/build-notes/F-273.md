# F-273: a measured default for memory pressure's `full` on Linux

## What was built

- `Scheduler.Pressure`'s default `full:` is 1% of the span, not 0. Memory `full` over 1% asks
  for `severe`. The `some` thresholds stay: cpu 25%, memory 10%, io 20% ask for `high`. An app's
  own thresholds still go over the defaults (`pressure: [full: 0.05]`).
- **The way down from `severe`.** `judge/4` timed a return to a lower state from the last
  change of the asked level. Samples that flip between `ok` and `high` restarted that timer at
  each flip, so neither held a whole window and the level stayed `severe` for good. Now a lower
  state is taken once no sample of a whole window asked for the current one or above, and it is
  the highest any of them asked. Going up to `high` still needs each sample of a window to ask.
- **A clock set back.** A sample at or before the last one was dropped, and the last sample
  kept. When the wall clock went back, every sample was dropped until the clock passed the old
  time, and then the whole growth since then was divided by a span of a few ms. Such a sample
  now starts the next span. A span of 0 does the same.
- **The reading.** `Pressure`'s state keeps `reading`, what set the level: `%{file, line,
  share, threshold, at}` (for a `{:level, read}` source, `file: :level, line: :level` and the
  level as `share`). A pressure refusal is `{:refused, {{:pressure, level, reading}, retry_at}}`,
  and the lease row's `reason` is that refusal as JSON, `["pressure","severe",{"at":…,"file":
  "memory","line":"full","share":…,"threshold":0.01}]`. `Scheduler.pressure/2` answers
  `reading` too. Telemetry's `reason` stays `:pressure`.
- Callers: `Runs.Plug` named the reason by interpolation, which raised on a tuple; it now names
  it with `word/1` (`refused pressure <time>`). `Jobs` matched `is_atom(reason)`; it now matches
  an integer `retry_at` and writes `pressure` in the job's row. `Delegates` and `Mains` pass the
  refusal through as `{:lease, why}` and store it as JSON, unchanged.

## What was measured

On the Linux workstation (NixOS, k3s running, other agents' sessions running beside it), a shell
loop read each `total` in `/proc/pressure/{cpu,memory,io}` every 2 s: 300 spans at rest (no
test suite), then 300 spans while `devenv test` ran. Each span's share is its growth in µs over
its length in µs.

| line | at rest: median, p95, max growth | under the suite: median, p95, max growth |
| --- | --- | --- |
| memory `full` | 0, 0.00005%, 4 µs (45 spans grew) | 0, 0.00005%, 3 µs |
| memory `some` | 0, 0.00005%, 4 µs | 0, 0.00005%, 4 µs |
| cpu `some` | 7%, 78%, 1.84 s | 28%, 76%, 1.76 s |
| io `some` | 7.7%, 9.0%, 218 ms | 7.1%, 8.2%, 184 ms |
| io `full` | 4.9%, 7.5%, 203 ms | 2.3%, 5.8%, 148 ms |

Memory `full` grew 58 µs in the 10 minutes at rest and 40 µs under the suite. So:

- `full: 0.01` (1% of the span) is 5 000 times the largest growth seen (4 µs). A span reads
  `severe` only when memory is short for 20 ms of 2 s, a real stall.
- Memory `some` at 10% and io `some` at 20% read `ok` in every span (io's largest is 10.7%).
- cpu `some` over 25% in 113 of 300 spans at rest and 164 of 300 under the suite. See new-1.
- io `full` sits at 2 to 10% of every span. The `Pressure` module does not judge it, so it
  reads nothing; an app that judged it with `full: 0.05` would read `severe` in most spans.

## Item 6: how many Schedulers answer a lease

One. The tree (`CodingAgentFramework`, the `:scheduler` child) starts one `Scheduler` per
instance, and `Delegates`, `Mains`, `Jobs` and the heavy commands' wrapper are each handed that
one. Its `pressure:` is the config's `pressure` as given; only a nil config reads
`[source: :psi]` with the defaults. A new test in `surface_test.exs` starts an agentless tree
with `pressure: [source: :psi, dir: …, full: 0.05]` and checks that the tree has one
`Scheduler` and that its state holds `full: 0.05`. Nothing in the framework starts a second
one. An app that runs a second instance (an agentless tree for jobs, say) with no `pressure` in
its config gets the defaults there: before this unit that was `full: 0.0`.

## Item 7 and the live clue

What could read `severe` from these counters:

- `full: 0.0`: any growth of memory `full`. On this host memory `full` grew in 1 span of 8
  even at rest (see above), so a tree on the old default reads `severe` within seconds.
- With the old hysteresis, one `severe` sample was enough for good: cpu `some` here moves
  around 25% under load (it read from 0% to 85% of a span), so the asked level flipped
  between `ok` and `high` and the timer never ran a whole window. The test "samples that flip
  between ok and high take severe down to high after a quiet window" fails on the old code.
- A clock set back: see above; "a first sample, a span of 0, a counter that went back and a
  clock set back read nothing" fails on the old code.
- Two samples closer than `interval:`: not possible. `init/1` sends the one `:pressure`
  message, its handler sends the next with `send_after` and nothing else sends it; the tree's
  `interval:` tick runs only the holders' checks, and no call samples. A blocked `Scheduler`
  makes a span longer, not shorter.
- A first sample only stores its totals; a counter that goes back reads 0; `psi/1` and
  `parse/1` map each file to its own name.
- The clock: the app passes no `clock:`; the default is `System.os_time(:millisecond)`, and the
  share divides µs by span ms × 1000, as the unit tests check.

With the app's `full: 0.05` and memory `full` growing at most 4 µs in a 2 s span, none of
these reads `severe` from memory `full` unless the span is under 0.1 ms. So the `severe` the
panel read at 16:42 did not come from a `Scheduler` holding `full: 0.05` through these paths,
unless its clock was set back. The cause, found in the embedding app: its config had dropped
`pressure:`, so its tree ran on the old default, `full: 0.0`, and any growth of memory `full`
read `severe`. With this unit a missing option gives the measured defaults, and a refusal names
the file, the line, the share and the threshold it was held to. The reproduction the brief
describes was not run: its cause was the same dropped option.

## Findings

### new-1. cpu `some` at 25% reads `high` on a shared host at rest

What happened: on the workstation, with other agents' sessions running, cpu `some` passed 25% in
113 of 300 spans at rest and 164 of 300 under the test suite; its p95 was 78%. Why: cpu `some`
counts any runnable task that waits, and a host that runs several agents always has some. With
the new way down, a `high` asked in each sample of a window is rare, so heavy runs are barred
only some of the time, but the threshold is not measured. What I did: kept 25%; it is a
placeholder, as the module's doc says. What the design should change: measure cpu `some` on a
host that runs the intended number of builders, and either raise the default or judge cpu by its
`full` line on kernels that have one.

### new-2. A tree that omits `pressure` reads the defaults without saying so

What happened: the live refusals came from an app's config that dropped its `pressure:`; the
tree took `[source: :psi]` with the defaults, and nothing showed that the app's own thresholds
were gone. Why: a nil `pressure` means the defaults by design. What I did: the defaults are now
measured, and a refusal names the threshold it was held to, so a missing option shows in the
first refusal. What the design should change: `Scheduler.pressure/2` (and the facade's `holds`)
could answer the thresholds in force beside the level, so an app can see them before a refusal.
