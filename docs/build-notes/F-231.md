# F-231: an end reaches an agent that is mid-start, and a refusal frees its act

Branch `framework/f-231-end-start` (the brief named `framework/f-231-end-mid-start`; the person
who started this unit chose the shorter name). From F-223's real runs on 2026-11-23: new-3 (a
main session on its trust dialog could not be ended) and new-6 (a stop refused before it acted
used up the delegate's state in `Acts`).

## What was built

- **The model first.** `Dialog.tla` has an end asked while the row waits on a dialog (constant
  `Ends`; `AskEnd`, `EndPress`, `EndAfterPress`, `EndTerm`, `EndOutlived`, `EndDone`). The end
  answers the trust dialog with its exit option, as a person's answer, through the prompt's
  checked press; a dialog with no exit option, an answer already marked, or a process still
  live after the press gets SIGTERM. Once the process is gone the row is `ended`. A restart
  cuts the end. New invariant `NoTurnAfterEnd` (a row asked to end is never confirmed running)
  and liveness `EndEnds` (an asked end ends, or answers unknown). `Dialog_Ends` checks them
  with restarts; `Break_Dialog_EndRefused` (the end refused, as `{:starting, name}` was) fails
  `EndEnds`. The other Dialog configurations set `Ends = FALSE` and check what they checked.
- `Claim.tla` has `Free`: a claim let go with no act frees its state, and the next claim of it
  is taken. A row that acted, or that a restart cut, keeps it. `OneActPerState` now also says a
  refused act repeats no effect; `Break_Claim_FreeActed` (a row that acted freed too) fails it.
- **Sessions.** `stop/3` and `end_main/3` of a row on a dialog press the trust dialog's exit
  option (`Dialog.exit_option/1`, `No, exit`) through the same checked press a person's answer
  takes, an act in `Acts` by `operator` (an end) or `person` (a stop). Sent, the end waits for
  the process to go; anything else gets SIGTERM, as a stop of a row on a dialog did before. The
  row is then `stopped`, or `ended` for an end. `end_main` no longer refuses a row on a dialog
  `{:not_free, "dialog"}`.
- **Mains.** `end_main` refuses `{:starting, name}` only while the start's call is under way, or
  its agent row is not on a dialog. Otherwise it asks `Sessions`, and the start then settles
  refused, reason `ended`, and its lease goes.
- **Acts.** `settle/5` takes `free: true`: a row settled `failed` or `not_verified` with no act's
  time then moves its state into its detail (`state`) and leaves the state free. The MCP's fix
  path passes it for a fix refused when it acts, which is new-6's stop.
- Tests: an end of a main session at its trust dialog ends it (`Sessions` and `Mains`, stand-in);
  an end at the imports dialog sends SIGTERM; a stop refused before it acted is claimed again on
  the same state, while one that acted, or a refusal not freed, keeps its state.
  `MCPDelegatesTest`'s "a stop only once the report is delivered" had pinned new-6 itself (a
  second stop refused `already_claimed`); it now meets the stop's own refusal again,
  `["report", "queued"]`, and finds both refused rows with their state freed.

## What was measured

- `Dialog_Ends`: 1,406,403 states generated, 389,288 distinct, depth 27, about 60 s on this
  host, the slowest of the Dialog configurations (`Dialog_Menus` takes about 24 s).
- `Break_Dialog_EndRefused` fails `EndEnds` in about 5 s; `Break_Claim_FreeActed` fails
  `OneActPerState` at depth 6.
- `Claim_Design`: 61,257 states, 15,376 distinct.

## What I ran into

- The brief's rule for Acts, "a claim settled `failed` or `not_verified` with no `acted` mark
  leaves its state free", made two Acts tests fail. A read of the callers showed why: most rows
  settled `failed` with no act's time are refusals that wait on a person. `Recoveries`'
  `repeating` and its refused viewer, for example, ask a person, and their claim is what stops
  the next sample from acting and asking again. Freed, each sample would claim, fail and ask
  once more. So the free is the caller's word (`free: true`), and only the MCP's fix path gives
  it (new-1).
- `Claim.tla`'s `ClaimsEnd` (`<>[]` every claim done) fails once states are freed: an actor
  claims a freed state again at any step. The alone spec now checks `EachClaimEnds` (each claim
  ends), with fairness for each claim on its own. A single fairness over all claims let one
  starve while others cycled. The specs that instance `Claim.tla` never free, so they keep
  `ClaimsEnd` unchanged.
- `Dialog.tla`'s new end first broke `GoesOn`: a person who asked the end again after each TERM
  the process outlived kept `Confirm` from ever being taken. The model now lets a person ask
  again only after a restart cut the end (new-3).
- TLC refuses `WF_vars(A)` for an `A` that leaves a variable of `vars` unprimed. The steps from
  before F-231 are wrapped `K(A) == A /\ UNCHANGED endVars` in the fairness, rather than editing
  each one's `UNCHANGED` list.

## Findings

### new-1. A refusal frees its state only when its caller says so

What happened: the brief asked for every `failed` or `not_verified` row with no act's time to
free its state. Most of those rows, in `Recoveries`, `Limits`, `AbsentMains` and
`StuckBackgrounds`, are refusals a person must answer, and their claim keeps the next sample
from acting and asking again. Why: "no act's time" says the act did not run, not that nothing
waits on its row. What I did: `Acts.settle/5`'s `free: true`, given only by the MCP's fix path
(new-6's case). What the design should change: decide which other callers free. One likely
case is `Sessions`' startup press refused because the pane moved on: it takes its mark back,
and its next answer claims the same state and is refused `{:acts, {:already_claimed, …}}`.
`Acts.answered/4`'s refusals could take `free: true` there, case by case.

### new-2. A dialog with no exit option is ended by SIGTERM

What happened: the brief says an end "presses the dialog's exit option". Only the trust dialog
has one (`No, exit`). The imports dialog's "No" goes on with imports off, and a start's menu
names none. What I did: those, and a trust dialog whose answer is already marked, get SIGTERM to
the held program's record, as `stop/3` of a row on a dialog did before F-231. The model says so
(`EndPress`, `EndTerm`). What the design should change: confirm SIGTERM as the end for a dialog
with no exit option, or name what else to press.

### new-3. An end answered unknown may be asked again in the code, not in the model

What happened: `Dialog.tla` lets a person ask the end again only after a restart cut it. A
person who asks again after each TERM the process outlives would starve `GoesOn` in the model.
The code does not refuse a second `end_main` or `stop` after an unknown answer: it TERMs again.
Why: in the model, asking is a person's step with no bound, and an endless one breaks liveness.
The code leaves asking to the person. What I did: kept the code, and wrote the model's bound
and its reason in the spec. What the design should change: decide whether a second end of a
dialog row whose TERM went unanswered should be refused (`{:no_exit, sent}`, as `Recoveries`
owns a stop's `no_exit` for a running row), or whether the model should bound the asks with a
counter instead.
