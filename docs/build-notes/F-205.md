# F-205: a service's socket path always fits; a login prompt's id names its refusal

Three follow-ups to F-196 and F-202's new-2 and new-5, in `Services`, `Prompts` and `MainsTest`.

## What was built

- **A service's socket is named by a key, not its name** (F-202's new-5). `Services.socket_key/1`
  is the first 16 hex digits of the SHA-256 of the name. The service's and its forward's
  sockets and records are `<dir>/services/<key>.sock` and `<key>.pid`: 31 bytes after the
  host's directory, whatever the name. The name stays where a person reads it: the row, and
  the log (`<dir>/services/<name>.log`, and its `.from` file). `Held.context/3` names both
  the socket and its record by its `name`, and `Jobs` shares it, so `Services` hands it the
  key as `name` and sets `log` and `from` itself.
  - **How long a home may be**, in `socket_key/1`'s `@doc` and the design: `Holder` allows a
    socket path of 103 bytes, so a host's directory may be 72 bytes, and the workstation's is
    `<home>/ws`, so a home may be 69. A longer directory is refused at the first start,
    `{:refused, {:start, {:socket_path_too_long, path}}}`, the row `refused`. That is now the
    only way a name's socket is too long.
  - **The name's room is gone for services.** F-172's `name_room:` check refused a service
    name past `103 - home - 18` bytes. With a key that rule refuses a name the socket no longer
    depends on, and in any home over 21 bytes it refused the 64-letter name the brief says must
    fit. So `Services` lost its `:name_room` option and `fits/2`, the tree no longer hands it
    one, and `Config.name_room/1` answers `%{agent: n}` only. Agents' names (`Delegates`,
    `Mains`) keep their room, unchanged.
  - **Tests.** The key's shape and the name staying in the row and the log (a 2-byte and a
    64-byte name). The longest allowed name starts under a host directory of 72 bytes, so its
    socket is exactly 103 bytes and dtach binds it; the same name under 73 bytes is refused
    with a 104-byte path and its row `refused`. Under that 72-byte directory the name's own
    socket would have been 151 bytes, so the test fails without the key. The existing
    "a name is a file name on the host" has no path that grows with the test VM any more. The
    other `Services` tests read `db.sock` and `db.pid` through `held/4`, which names the key's
    files. `SurfaceTest`'s delegate-end test, which started a name past the room and saw it
    refused, now starts a 64-letter service through the tree's own home, and sees it end with
    its owner.
- **A login prompt's id names its refusal** (F-202's new-2). `login:<account>:<refused_at>`,
  `refused_at` the time of the check that refused it (`Logins`' own, which stays while the
  refusal is kept and is cleared by a login). `answer/4` takes that id; an id whose account is
  in `Logins`' table but is not an open prompt answers `{:refused, :settled}`, as before; the
  old shape `login:<account>` is `{:refused, :no_prompt}`. A test follows one account through
  refusal, a kept refusal (same id), a login, and a second refusal (a new id, a later time),
  with the first id `:settled` while the account is refused again.
- **`MainsTest`'s race** (F-196). "a main's start refused at a usage limit waits as its row,
  and starts at its reset" asserted `Scheduler.leases/1` as soon as the start's row read
  `starting`. `Mains` writes `starting` before the start asks for its lease, so the lease can
  come later than the row. The test awaits the lease (`leases/2`, which cues the `Scheduler`
  as the app's cue does), then asserts there is one. The rest of the test reads the agent row,
  the mailbox and the row's `tell` only after an await or a call that has settled them: the
  notice is written before `tell` is cleared. `MainsTest`'s other direct read of the leases,
  after `start_main` answered `{:unknown, {:dialog, :trust}}`, comes after the call that took
  it.

The second refusal's `opened` row (F-202) is not built here: F-202 has not landed on `main`.
Its record is keyed by the prompt's id, so with this id a second refusal is a second row. Its
test, when it lands, can be one more line in the login test.

## What I ran into

- `Held.context/3` names the socket, the record and the `base` of a caller's own files by the
  one `name`. A caller whose socket needs a different name from its files has to build the
  files' paths itself, as `Services` now does; `Jobs` names the socket by its job's name, which
  is short.
- A key of 16 hex digits is 64 bits, so two names may share it with a chance of about 2^-64 for
  a pair. They would share a socket: the second start would be refused `{:live, key}` while the
  first runs. I did not add a check; the row's `service_exists` already keeps one name at a
  time.

## Findings

### new-1. `Config` accepts a home a service cannot start in

What happened: `Config.new/1` refuses a home over 93 bytes, the room `tmux.sock` needs. A
service's socket is `<home>/ws/services/<key>.sock`, 34 bytes after the home, so a home of 70 to
93 bytes is accepted and every service start in it is refused `socket_path_too_long`. Before this
unit such a home still started a service with a name short enough for its room.
Why: the brief's key is 16 hex digits and the services' directory is two levels deep; neither
the 93 nor the key's length was changed.
What I did: said it in `Services.socket_key/1`'s `@doc`, in `Config`'s moduledoc and in the
design, and left the refusal at the start.
What the design should change: either `Config.new/1` refuses a home over 69 bytes when its tree
runs services (`{:bad, :home, {:longer_than, 69}}`, as it refuses over 93), or the key is 8 hex
digits (a home may be 77; two names then share it with a chance near 2^-32 per pair). I
recommend the first: a person's home is about 40 bytes, and a refused config says it at the
start, not at a service's.

### new-2. An agent's socket is still named by its name

What happened: `Delegates` and `Mains` name `d/<agent>.sock` by the agent's name and keep
F-172's `name_room`. The same fixed key would drop that rule and its refusals.
Why: the brief names a service only.
What I did: nothing.
What the design should change: if agents' long names matter, the same key for their sockets,
and `Config.name_room/1` goes.

### new-3. A service started before this unit is read dead after it

What happened: a service held under the old name (`<dir>/services/<name>.sock`, `<name>.pid`) is
looked for under its key after this unit. Its row says `running`; the key's socket is absent, so
a settle reads it dead and ends the row while the program still runs under its old socket.
Why: the socket's name is part of where its row finds it; the row does not keep it.
What I did: nothing. A framework with no running service across the upgrade is not affected.
What the design should change: either say that services end before an upgrade, or the row keeps
the socket's name it was started with (a column written at the start) and an old row reads its
old name.
