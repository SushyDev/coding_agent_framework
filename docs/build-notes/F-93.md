# F-93: `Services`, part 4: the forwarded port, and a wait from the current start

`Services` gains the forward (`start/5`'s `:forward`), the reopen (`reopen/4`, for
`Recoveries`), and a line wait that looks from the current start's log offset. `Programs` and
devenv gain `wc` and `lsof`.

This unit was built in two runs. The first builder wrote most of the code: `wc` and `lsof` in
`Programs`, `TestHost` and devenv; the new columns of `Services.Table` (`log_from`, `port`,
`local`, `fwd`, `opens`); the wrapper's log offset; the forward, held by dtach after the row
says `running` with `fwd: "starting"`; the forward's read, end and settle after a restart; and
`reopen/4`. It stopped when the machine's disk filled, before any gate ran, and committed its
work as "work in progress". The second run found that work compiling once a half-written
`_build` was removed, and added: the new columns on an existing file, an optional
`:workstation`, a stale claim checked before the forward's socket, a call timeout that covers
the forward's hold, the tests and this note.

## What was built

- **The forward.** For a service on a host reached over ssh, `forward: port` (or `{port,
  local}`) holds `ssh -N -o BatchMode=yes -o ExitOnForwardFailure=yes -L
  127.0.0.1:<local>:127.0.0.1:<port> -- <destination>` under dtach in the workstation's
  services directory, on a socket named for the service. A wrapper writes the ssh's pid to
  `<name>.fwd.pid` and execs it, so the pid is the listener's. The forward is held only after
  the start is settled and the row says `running` with `fwd: "starting"` (`ForwardEarly`). It is
  open only when `lsof` reads that pid itself listening on `127.0.0.1:<local>` (`OpenByPort`);
  another program on the port reads the same as none. The start answers once it is open; a
  forward that exits, or is not open by `:forward_timeout` (10 s), ends the service, and the
  start answers `{:refused, {:forward, reason}}` (`FailKeepsService`). An end ends the forward
  first, by its pid and start time, and is done once both sockets read dead
  (`ServiceEndFirst`). The row reports `port` and `local`. A host reached without ssh needs no
  forward: there `forward:` must name the same port twice, and nothing is held.
- **The reopen.** `reopen(services, name, %{pid:, started:, opens:})` acts only while the row
  is `running` with `fwd: "open"` and that start and open count; then it reads the forward's
  socket dead, writes `fwd: "reopening"`, and holds the forward again, all in `Services`' own
  process. Open counts up `opens`, so the same claim never reopens twice; a reopen that fails
  leaves `fwd: "failed"` until the service's next start, which clears it. A reopen a restart of
  the framework cut is read once its deadline passes, at the start or a cue: open, or failed
  (`Copy.tla`'s `FwdSettles`).
- **Where it hooks into `Recoveries`** (not wired in this unit): `Recoveries` would read a
  forward lost when the workstation's `Holder` reads `<name>.sock` in the services directory
  dead while `Services.list/1` says `running` with `fwd: "open"`, and call `reopen/4` with that
  row's `pid`, `started` and `opens`. The claim, the row's `reopening`, is `Services`' own
  write, made in the same call that checks it, so `Recoveries` keeps no row for it.
- **The wait's offset.** The wrapper writes the log's size (by `wc -c`) beside the pid before
  the program writes; the row keeps it as `log_from`. `{:line, pattern}` looks from it; `{:line,
  pattern, from}` from the caller's offset (F-89's new-3).
- **An existing `services.db`** gains the five columns on open by `ALTER TABLE … ADD COLUMN`, as
  `Sessions.Table` and `Mailbox`'s table do; `opens` takes `DEFAULT 0`.

## The tests

The stand-in ssh cannot forward. Given `-L`, it records its pid, writes whether `db`'s pid
file was there (`ForwardEarly`), and execs `nc -k -l 127.0.0.1 <local>` under a name in the
test's directory: the forward's pid is then the listener, and nothing is relayed. That is what
`OpenByPort` needs. With a `no-forward` file it runs and holds no port. A sleep it starts ends
it after the stand-ins' idle time.

- `ForwardEarly, OpenByPort`: the start answers `fwd: "open"`, `opens: 1`, with `port` and
  `local`; the forward began after the service's pid file; the local port listens, and no
  longer after the stop. A forward on a local host with two ports is refused.
- `OpenByPort, FailKeepsService`: with the test holding the local port and the stand-in holding
  none, the start answers `{:forward, :not_open}` and the row is `ended`, `fwd: "failed"`;
  without the file, the stand-in's nc cannot bind and exits, and the start answers `{:forward,
  :exited}`, the service gone.
- `ServiceEndFirst`: a service that, at TERM, writes whether the local port still listens
  writes `dead`.
- `ForwardReopened once per Key`: a live forward is no loss; a lost one reopens once (`opens:
  2`), and the same claim again is `changed`; a reopen that fails (the stand-in's `down` file)
  leaves `fwd: "failed"` with the service running; a restart opens it again with `opens: 1`,
  and the old claim is `changed`.
- `Wait`: after a restart, a line wait finds the new start's line, not the old one, unless the
  caller names offset 0.
- `Table`: a file with the old schema opens, its row with the new columns empty and `opens` 0.

- The diff is about 680 changed lines apart from this note, over the 500 the brief names. The

## What I ran into

- The first builder's `_build/dev/lib/caf_shell` was left half-written by the full disk:
  compiling warned that every `caf_shell` module was redefined. Removing that directory fixed
  it.
- `:workstation` was a required option; only a forward needs it, so it is now optional.
- The forward's hold runs three reads in `Services`' own process (a reopen's socket read, the
  pid file's clear, dtach), each up to the holder's timeout. They are 2 s each, and the call
  that waits for them is 7 s, so the caller never answers unknown while the hold goes on.

## Findings

### new-1. A forward's hold blocks `Services`' process for up to three reads

What happened: the hold is made in `Services`' process, so that an end written there comes
wholly before or after it (the end never misses a forward held after its read). Each read is
bounded (2 s), but while the workstation is slow every other call to `Services` waits behind
it. Why: the atomicity the design asks for is had here by the process, not by the row. What I
did: bounded the reads and gave the call a timeout that covers them. What the design should
change: say whether that blocking is acceptable for a part with many services, or whether the
hold should claim the row (`fwd: "holding"`) and run outside the process, with an end that
reads that claim.
