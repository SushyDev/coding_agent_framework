# F-272: the gates pass on a Linux host

## What was built

The gates now pass on a NixOS host. On `main` (6da64bf) four groups of tests failed there every
time. Each had its own cause. None was in the library, so the fixes are in the tests and in the
screen stand-in, which now plays one more thing Claude Code does.

1. **`programs_builtin_test.exs`: kill and sleep not found.** The test set `PATH` to
   `/bin:/usr/bin`. NixOS has no `/bin/kill` or `/usr/bin/sleep`; they live in the system or
   devenv profile. `Programs.find/2` searches the `PATH` it is given, which is right. The test
   now builds its `PATH` from the directories that hold `kill` and `sleep` as files, so it
   still checks that a shell builtin is found as a file. On macOS those are `/bin` (or the
   devenv profile), so the test holds there.
2. **`holder_process_test.exs`: a group of zombies.** macOS answers EPERM to `kill -TERM -pgid`
   when every member of the group is a zombie not yet reaped, and `Holder.Process.signal/4`
   reads that failure as `{:ok, :gone}`. Linux sends the signal to the zombies and `kill`
   succeeds, so the answer is `{:ok, :sent}`, which is true: a signal went, to nothing that
   runs. Every caller treats both answers as done, and an end then waits for the program to
   read dead, which is the same on both systems. The test now expects `:gone` on macOS and
   `:sent` on Linux, and never `:unknown`. The design and the function's doc say so.
3. **`mains_test.exs` (five tests) and `sessions_dialog_test.exs:217`: a blank trust dialog.**
   See "Why the mains tests waited". The stand-in now redraws when its size changes.
4. **`home_test.exs:186`: "malformed" in place of a refusal.** See "Why home_test read
   malformed". The test now writes its broken file in a home no tree has run on.

## Why the mains tests waited

All five mains tests, and one sessions test the brief did not list, hung in one call:
`Sessions.start` (or a start or resume through `Mains`) waiting for the trust dialog. The pane
was blank. The held stand-in was alive in its key loop, so it had drawn its screen, and that
screen was lost.

A start holds the program under `dtach -n`, then opens the viewer pane with `dtach -a`. dtach
keeps no output, so what a program draws before the viewer attaches is gone. The viewer opens
one row short and is then grown, because Claude Code draws again when its size changes
(`Sessions`' moduledoc). The stand-in never drew again: it ignored SIGWINCH.

On macOS the stand-in starts more slowly than the viewer attaches, so it always drew to an
attached viewer. On Linux it starts faster. The tests that passed all start with a prompt,
which the hold reads from its file before the program runs, and that delay was enough. The
five that failed start with no prompt (`start_main(…, nil)`, a resume, or `Sessions.start`
with no `prompt:`).

The stand-in now traps WINCH and draws again when `stty size` changed, as Claude Code does. Two
facts of bash 5.3 shaped it, both checked on this host:

- a WINCH trap runs while `read -t` waits, and the read then goes on to its timeout (a trap at
  1 s in a 3 s read: the trap ran at 1 s and the read returned 142 at 3 s). So the trap itself
  draws: a flag would wait for the next key.
- a trap also runs between a draw's commands. A resize during a draw sets a flag, and the draw
  draws again at its end, so two draws never interleave.

On macOS this adds at most one draw of the same screen when the viewer grows, which no test
counts.

## Why home_test read malformed

The test started a tree on a home, stopped it, removed the WAL files, and wrote a non-database
over `caf.db`. `start_link` then answered `{:unknown, {:home_mark, "… database disk image is
malformed"}}`: the open succeeded and a later statement raised.

A table process closes its SQLite connection only when the VM frees it (`Store`'s moduledoc).
That can come after the process's DOWN, so after `stop_supervised!` returns. The last
connection's close checkpoints its WAL into the file, through the file descriptors it still
holds, and that writes a database header over the test's bytes. The next open finds a database
with broken pages.

Measured on this host:

- of 60 processes that each opened a store, wrote a row and exited, 11 still had the file open
  when their DOWN arrived (no other load in the VM);
- a connection left open while its file is rewritten: an open then refuses `file is not a
  database`; after the old connection closes, the file starts with `SQLite format 3` and an
  open succeeds.

It failed only in the whole gate, never in `caf_surface` alone, even with 14 busy loops beside
it. The fresh file in a home no tree ran on does not depend on that timing, on either system.
The library is not changed here: closing on collection is the design's choice (new-1).

## Findings

### new-1. A stopped tree's SQLite connections close after the stop returns

What happened: `home_test` rewrote a stopped tree's database and read "malformed", because a
connection of that tree closed after the stop and checkpointed into the new file. Why: a table
process's connection is closed when the VM frees the process, which can come after its DOWN.
What I did: the test uses a fresh file. What the design should change: decide whether a stop
of the tree means every connection is closed. If it does, each table process would close its
connection in `terminate/2`, which needs `trap_exit`. If it does not, `Store`'s moduledoc
should say that a stopped tree may still write its file for a moment.

### new-2. A hung start runs into the test's timeout before its own bound

What happened: each hung start failed as an ExUnit timeout at 60 s, not as an answer. Why:
`Sessions.start`'s call waits its timeout (30 s) plus 30 s of slack, which is ExUnit's default
test timeout, so the call's own `{:unknown, {:timeout, _}}` never arrives. What I did: nothing;
the cause was found from the pane. What the design should change: the call's bound under the
test timeout, so a hung start reports where it waited.

### new-3. A program that does not draw again on a resize shows a blank viewer

What happened: the stand-in's first screen was lost, and the start waited on a blank pane. Why:
a start relies on the program drawing again after the viewer's grow. Claude Code does. What I
did: the stand-in now does too. What the design should change: the viewer's part could say
that what a program draws before the viewer attaches is lost, and that the grow is what shows
it, so a later stand-in or program does not meet this again.
