# F-305: a message's key is scoped to its sender and recipient

## What was built

- **The key is per (sender, recipient, key).** `Mailbox.handle_call({:message, …})` stored a
  message's key as `reply_to: "key:" <> key`. `reply_to` has one unique index over the whole
  table, so one key took one row whatever the sender or recipient. The MCP prefixed the
  sender (`msg:<from>:<key>`, F-250), so two senders were apart, but one sender's key to three
  agents stored one row: the second and third sends answered the first id and were dropped.
  The key is now stored as `msg:<n>:<from><m>:<to><key>`, `n` and `m` being the byte lengths
  of `from` and `to` (`Mailbox.message_key/3`, private). A send again from the same sender to
  the same recipient under the same key still stores no row and answers the first id.
- **Why the form cannot collide.**
  - Two triples never spell one string: reading the string from the left, the digits up to
    the first `:` give `from`'s length, so `from` is the next `n` bytes; the same gives `to`;
    the rest is the key. The string gives back exactly one triple.
  - It never meets a notice's key: `notify/4` stores `key:<key>`, and a message's form starts
    `msg:`.
  - It never meets a uuid in `reply_to` (an answer, a reply or a report names its row's
    uuid): a uuid is hex and dashes, with no `:`.
  It stays within the column's existing unique index; no schema change.
- **The MCP passes the key as the agent gave it.** Its `msg:<caller>:` prefix did half of the
  scope in the wrong place. Now `Mailbox` owns the scope, so a caller of `Mailbox.message/5`
  other than the MCP gets the same rule.
- **Docs**: the `message` tool's description, `Mailbox.message/5`'s and `status/3`'s `@doc`,
  the design's two lines for the key (the agents' verbs table and the `message` tool's row),
  and the README's status line.

## Rows stored with the old form

No migration. A message row stored before F-305 keeps `reply_to: "key:msg:<from>:<key>"`. It
stays readable: `status/3` shows `reply_to` as stored, and no code reads a message's
`reply_to` back as a key (`sender_of/2` only reads a reply's or notice's `reply_to` as a
uuid). A send again across the upgrade under the same key looks for the new form, finds none,
and stores a second row: at most one repeat per key, and only for a send again that straddles
the upgrade. The old row still holds its `key:` value, which a notice could meet only if a
notice were keyed `msg:<from>:<key>`. No caller keys a notice so.

## The model

No spec in `model/tla/` models a message's key. `Delivery.tla`'s `re` is the key of an
answer (one reply or notice per answered row), not the sender's send-again key, and
`Boxes.tla`'s keys are a press's keys in flight. The scope is a uniqueness rule on one table
write, not an order over time, so no spec changes.

## Tests

- `mailbox_test.exs`: the same key to two recipients stores two rows and delivers both
  (two delegates started, each row `delivered`), and a send again to the second answers its
  own first id; the same key to the same recipient twice stores one row and answers the first
  id; the same key from two senders to one recipient stores two rows; a message keyed `job:x`
  and a notice keyed `job:x` each store a row. The test tree gains `d2`.
- `mcp_test.exs`: the key is passed on as the agent gave it.

## What was measured

- `mix test` on `mailbox_test.exs` and `mcp_test.exs`: 21 and 26 pass. The gates' results
  are in the report.

## Findings

### new-1. A scope split over two layers hid the missing part

What happened: F-250 scoped the key to the sender in the MCP, and the design said "scoped to
the sender". The recipient was never part of it, and the doc's "sent again with the same key"
read as one message's retry. Why: the scope lived in the caller, so `Mailbox`'s own rule
(one row per key, table-wide) was never stated against what a sender means by a key. What I
did: the scope is now `Mailbox`'s alone, and the MCP passes the key through. What the design
should change: state a key's scope where the unique write is, in `Mailbox`'s line, and name
every part of it.

### new-2. A notice's key is still table-wide

What happened: `notify/4`'s keys (`job:<id>`, `seat:<host>:<id>:<n>`, `turn:…`) are still one
row per key across every recipient. Why: each such key names one event to one addressee, so
it is the dedup the caller wants. What I did: nothing; it is out of this unit's scope. What
the design should change: say in `Mailbox`'s line that a notice's key is the caller's whole
name for one event, so a caller that tells two agents of one event keys each apart.
