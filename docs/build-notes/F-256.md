# F-256: a prompt notice whose prompt closed before delivery is not typed

## What was built

On the live tree a delegate's trust dialog was answered within seconds, but its `prompt` notice
reached the parent 3.7 minutes later, at the parent's turn end, as if the prompt were open.
Nothing checked at delivery that the prompt was still open.

1. **The model first.** `Delivery.tla` has a constant `Notices`: rows that are a prompt's notice.
   `PromptCloses` closes the prompt while its row is due or marked and not yet handed on.
   `PromptWithdraws` settles such a marked row `withdrawn` and writes nothing. `Handed`,
   `Launch`, `Unknown` and `Refused` each need `Checked(i)`, so a closed notice is never handed
   on and never refused. `ClosedNotHandedOn` and `WithdrawnWhy` are invariants, `Arrives` allows
   `withdrawn` for a closed notice, and `UnknownStays` keeps it final. `Delivery_Notices` has a
   notice and a message behind it, a restart and a person's prompt. `Break_Delivery_ClosedTyped`
   removes the check and fails `ClosedNotHandedOn`. The four specs that instance `Delivery`
   pass `Notices <- {}`; every `Delivery` configuration has `Notices = {}`.
2. **`Mailbox`.** The option `prompt_open:` is a function of a prompt's id that answers
   `{:ok, :open}`, `{:ok, :closed}` or `{:unknown, reason}`. `hand_on/5` runs it in the
   hand-on's task, as the last act before the transport's call, for a row of kind `prompt` keyed
   `prompt:<id>`. Closed: the task answers `{:withdrawn, :prompt_closed}`, and `handed/3` writes
   status `withdrawn`, attempt `prompt_closed`. The settle that follows hands the next row on.
   Unknown: a refusal `{:prompt, reason}`, so the mark is undone and the row waits for its next
   cue. Without the option nothing is checked. The stream, waiter and typed write all go through
   `hand_on/5`. The wake line passes `false`: it is a fixed line, not the row's text, and the
   waiter that carries the row is checked.
3. **The app's wiring.** `CodingAgentFramework`'s tree gives `Mailbox` a `prompt_open:` that
   reads `Prompts` by its registered name (`{:via, Registry, …}`): the inbox starts after
   `Mailbox`. Open means the inbox lists the id.
4. Docs: `design.md` (the Prompts paragraph and a new "A prompt's notice" paragraph under
   Delivery), `Mailbox`'s module doc, `Table`'s status list, the README's status, `Prompt.tla`'s
   header.

### Why the check runs in the task

`Prompts.list` calls `Mailbox.open_asks`, and `Prompts.tell` calls `Mailbox.notify` from inside
`Prompts`. A `Prompts.read` made from `Mailbox`'s own process would wait on `Prompts`, which waits
on `Mailbox`: both time out. The hand-on's task is another process, so it is safe. The main agent
approved this design after the first report.

### What remains

A prompt that closes after the check and before the transport's write is delivered. The window is
one transport call: a waiter's answer, or the Inlet's keys, which cannot be called back once
typed. This is acceptable because the notice then says what was true when it went, and the
framework cannot be quicker than its own transport; the model puts check and write in one step,
so it shows no violation there. A notice already typed, and a person's answer after it, is the
same case as any prompt answered just after its notice was written.

**A launch's first row is not checked.** `Mailbox.launch/4` runs in `Mailbox`'s own process and
cannot read `Prompts` without the deadlock above. The main agent's direction was to check it in
the caller (`Delegates`, `Mains`) through a new `Mailbox` call that settles the row withdrawn.
That adds an option and a call to two more apps, tests included; with the model and the hand-on
path it was past the size the direction named, so it is a unit of its own.

## What was measured

On macOS, 15 cores, under a load of 60 to 90 from other work.

- `Delivery_Notices`: 2831 distinct states, depth 25, ok. The first run found a loop that the
  weak fairness did not cut: `Mark` and `Refused` alternating on a closed notice. `Refused` now
  needs `Checked(i)`, as the code's check comes before any transport answer.
- `Break_Delivery_ClosedTyped`: `ClosedNotHandedOn` fails in 137 states.
- `mailbox_typed_test.exs` 13 of 13 and `mailbox_waiter_test.exs` 11 of 11. The typed file
  failed `a row too long to type, with no home, waits` once, under load, in a run with my new
  tests; it passed alone, and the same run's other failure was my test's own fault.

## What I ran into

- The worktree had no `deps`: `mix deps.get` first.
- `devenv shell -- mix test` needs `MIX_ENV=test` and the umbrella root: `mix do --app caf_mailbox test …`.
- A typed line over a length bound is typed as a pointer to a file, so my test's notice text had
  to be short.

## Findings

### new-1. `Mailbox` and `Prompts` read each other

What happened: `Prompts` calls `Mailbox` (`open_asks`, `notify`) and the delivery check needs
`Prompts`' answer. Why: the inbox is built from its owners' rows, and `Mailbox` is one owner. What
I did: the check runs in the hand-on's task. What the design should change: say that no part
calls `Prompts` from its own process; a part that needs a prompt's state reads it in a task, or
takes it from a cue.

### new-2. A launch's first row needs its caller's check

What happened: see "What remains". What I did: nothing built. What the design should change: a
unit that adds `prompt_open:` to `Delegates` and `Mains` and a `Mailbox` call that settles a
launch row `withdrawn`, then starts with the next row or none.

### new-3. `Prompts.read/3` lists every open prompt for one id

What happened: the check reads the whole inbox to look for one id. Why: `read/3` filters by agent,
subtree and kind, not by id. What I did: nothing; the read is once per prompt notice. What the
design should change: an `id:` filter, if prompt notices become many.
