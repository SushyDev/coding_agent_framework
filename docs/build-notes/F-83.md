# F-83: `Services`, part 1: a kept program on a host, owned, logged, stopped

A new app, `caf_services`, with `Services` (one process, with no name, that owns the `services`
table) and `Services.Table`, and two small checks in `Grants`. The whole unit did not fit in
500 lines, so, as the brief says, this unit stops after the start, the stop and the owner's
end. The restart, `hand` and `logs` were built and tested, then taken out; they are the next
unit (new-1).

## What was built

- **The row**: one per service in `services`, keyed by its name: host, project and copy (the
  copy it runs in), the worktree it syncs from, `argv` and `env` (so a restart can start it
  again), `owner`, `keep`, the held process (`pid`, and `started`, its start time as `LC_ALL=C
  TZ=UTC ps -o lstart=` gives it), `restarts` (0 until the restart is built), `state` and
  `start_until`. States: `asked`, `starting`, `running`, `ending`, `ended`, `refused`. A name is
  free again once its row is `ended` or `refused`; otherwise a start is refused as
  `{:service_exists, name}`.
- **`start(services, owner, name, argv, opts)`**: `Grants.may_start_service?/2` (any agent the
  tree holds, a main session or a delegate), the row `asked`, the copy's turn (`Copies.take`,
  run id `service:<name>`), the sync, `mkdir -p <dir>/services` and removal of an old pid file
  on the host, the turn `starting`, the row `starting` with `start_until`, then `Holder.hold`
  of the wrapper. The options name the copy: `:host`, `:project`, `:copy`, `:worktree`; the
  MCP layer resolves the caller's own worktree (a main session's is its checkout).
- **The wrapper**, a `sh -c` argument as in `Jobs` (F-76 new-1): it writes `$$` to
  `<name>.pid`, then `cd`s into the copy and `exec`s `argv` with its output appended to
  `<name>.log`. Its input stays dtach's terminal, for `service_send`. `exec` keeps the pid, and
  dtach's child leads its own session and group, so the program's pid is its group's id.
- **The start's settle**: dtach's reply `{:ok, _}`, or a cut reply once `start_until` has
  passed, is followed by one read on the host that waits up to the read's timeout for the pid
  file, then prints the pid and its start time (`held`), `gone` (the program already exited),
  or `none` (the wrapper never ran). The row becomes `running` with its pid, `ended`, or
  `refused`, and the turn goes back. A read that fails leaves the row `starting` and the turn
  held, for the settle below.
- **`stop(services, caller, name, opts)`**: `Grants.may_fix_service?/3` (the owner or its
  parent), on a row `running` or `ending`. The row is written `ending` (only if its state has
  not changed since it was read) before the end is sent. The end is one shell on the host: it
  reads the pid's start time and sends TERM to the group only if it matches the row's, so a
  reused pid is never signaled. The call then reads the socket with `Holder.state/2` every
  100 ms until it is `absent` or `stale`, and only then writes `ended` (no pid, no owner). At
  `:timeout` (10 s by default) with the socket live, or with the host unread, it answers
  `{:unknown, _}` and the row stays `ending`.
- **`owner_ended(services, owner, opts)`**: the embedding app calls it when an agent ends. Each
  `running` service the agent owns with `keep` goes to `Grants.parent/2` (new in `Grants`);
  each other one, and each still `ending`, ends as `stop` ends it. It answers each service's
  outcome by name. A main session has no parent (`{:refused, :main_has_no_parent}`), but never
  ends either (`Team.tla`).
- **`list(services)`**: every row.
- **After a restart of `Services`**: at its start, a row `asked` is `refused` (nothing was
  sent to the host). At its start and at each `cue/2`, in `Services`' own process with 2 s
  reads: a row `starting` past `start_until` is read once and settled as above, and its turn
  given back; a row `ending` is sent its end again and is `ended` once one read finds the
  socket dead. A row unread waits for the next cue.
- **`Grants`**: `may_start_service?/2` and `parent/2`, each through the same tree read as the
  other checks, with a test.

Where part 2 hooks in:

- *The restart* (`restart/4`): `stop`'s check on a `running` row, then `end_service` with
  `%{state: "restarting", restarts: n + 1}` written before the end, then, on a dead socket, the
  row back to `asked` and the same `launch/3` as a start, with its own sync. The settle would
  end a `restarting` row a restart cut and not start it again, as a cut claim is closed and
  never retried. The scratchpad copy named in the report has it, with its test.
- *`hand/4`*: `Grants.may_hand?/4`, then a write of the owner guarded by the owner and state
  read, as `put/4` already allows.
- *`logs/4`*: `tail -c +<offset+1>` of `<dir>/services/<name>.log`, as `Jobs.log/4`.
- *`service_send`*: the program's stdin is dtach's terminal; a write goes through `Control`'s
  checked write to the socket `Holder` names (`<dir>/services/<name>.sock`).
- *`service_wait`*: a line in the log (from an offset, as `logs`), the socket read dead (as
  `dead/3`), or a port that listens, read on the host.
- *The forwarded port*: a field on the row, opened over the host's ssh connection once the
  start is `running`, and closed in `end_service` after the socket reads dead.
- *The claim*: `Grants.Claims` takes `{:service, owner}` with the state `{pid, started,
  restarts}`, all three on the row. The MCP layer takes it before `stop` or `restart`.

## Tests

`apps/caf_services/test/services_test.exs`, 7 tests and a doctest, each named for the
`Copy.tla` or `Team.tla` property it checks. The ssh host is a stand-in as in F-76 (drops
ssh's options, runs `sh -c`, exits 255 while a `down` file exists). The service is a bash
stand-in that records its pid, prints `up in <a.txt>`, and waits for input (bounded by
`stand_in_idle/0`). The tree is `web-main` with delegates `web-a` and `web-b`, and `web-a1`
under `web-a`.

- `StartsOnSyncedCopy` (workstation and ssh): the row is `running` with a pid and a start time,
  the log says `up in one` (the synced file), the copy's turn is free, a second start of the
  name is refused.
- `OneOwner`: an agent the tree does not hold is refused; a main session may start one, and
  owns it until its end, when the owner is cleared.
- `ServiceFixedByOwnerOrParent`, `EndedIsEnded`: a sibling and a child of the owner are refused;
  the owner's parent stops it; the socket file is gone and the pid is gone; a second stop is
  refused as `{:state, "ended"}`.
- `EndedIsEnded`, cut: with the connection down the stop answers `{:unknown, {:end, _}}`, the
  row stays `ending` and the program lives; a new `Services` on the same table, cued, sends the
  end and makes the row `ended`, and the pid is gone.
- `ServiceEndsWithOwner`: the owner's end ends a service and hands a kept one to the parent; a
  service of another agent is left running.
- `ServiceEndsWithOwner`, keep: a kept service of `web-a1` goes to `web-a` at its end, then to
  `web-main` at `web-a`'s, the same process all along.

The restart's test (a second sync's file in the log, the count, the old pid gone, a sibling
refused) and `hand`'s (`HandedAlongEdge`: a parent and a sibling refused, `keep` kept) passed
before they were taken out with their code.

## Findings

### new-1. Even the brief's fallback does not fit in 500 lines

What happened: the brief allows 500 changed lines, and says to stop after the start, the stop
and the owner's end if the whole will not fit. The whole came to about 860; the fallback is
still about 770. Why: the start alone needs the turn, the sync, the hold, the start's settle
and a read of the pid on the host, as `Jobs` does, and a new app brings its table, `mix.exs`
and test setup (the stand-in ssh is about 30 lines of the test). What I did: followed the
brief, took the restart, `hand` and `logs` out (about 90 lines with their tests), and kept a
copy of the fuller version for part 2. What the design should change: nothing in the design; a
brief for a new app with a host protocol could allow about 800 lines, or split the start (with
its settle) from the end.

### new-2. The end's signal is TERM, and nothing sends KILL

What happened: the design says the end is "the service's process, by its pid and start time",
but not which signal, nor what happens when the program does not exit. Why: a dev server or a
database should be let to shut down cleanly, so TERM fits; one that ignores TERM keeps its
socket live. What I did: TERM to the program's group; at the call's deadline the answer is
`{:unknown, {:not_dead, _}}` and the row stays `ending`; a later stop or cue sends TERM again.
What the design should change: say whether the end goes to KILL after a grace (say the call's
timeout), and whether that is the end's own step or a fix that goes to a person.

### new-3. A start under way when its owner ends is not taken

What happened: `Copy.tla`'s `OwnerSeen` takes a service whose start is under way once it
settles. `owner_ended/3` acts on rows `running` and `ending` only, so a start that settles
after the owner's end leaves a `running` service whose owner has ended. Why: the start runs in
the owner's own call, and the owner's end does not wait for it. What I did: documented it on
`owner_ended/3`. What the design should change: name what takes such a service. A small fix is
for the start's settle to check the owner's end (the embedding app's tree) before it writes
`running`, and end the service if the owner has gone.

### new-4. `Grants` gains `may_start_service?/2` and `parent/2`

What happened: the brief says the start checks that the owner may start one, and the owner's
end hands a kept service to the owner's parent; `Grants` had no check for the first nor a way
to read the second. Why: `Grants` is the only reader of the tree; `Services` reading the
tree function itself would be a second one. What I did: added both, each through `Grants`' one
tree read per check. What the design should change: add `may_start_service?/2` to the checks'
table in "Agents working together" (any agent the tree holds).

### new-5. The program's group is its own; a child that leaves it outlives the end

What happened: the end sends TERM to the group the program leads. A program that starts a
daemon in a new session (a database that forks itself away, say) leaves a process the end
does not reach, and the socket reads dead while that process runs. Why: dtach's socket follows
the program it holds, not its descendants. What I did: nothing beyond the group. What the
design should change: say that a service must stay in the foreground (most dev servers can),
or have the end also read a port or a pid file the service names.
