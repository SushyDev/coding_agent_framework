# F-85: `Services`, part 2: restart, hand, logs, and a start after its owner's end

`Services` (F-83) gains its restart, its hand and its log, KILL after a grace, and the owner
check at a start's settle. It starts from the fuller F-83 version kept aside, rebuilt on F-84's
`Copies.Held` (`ready/4`, `hold/5`, `settle/5`, `settle_cut/4`): none of those steps is
repeated here.

## What was built

- **`restart/4`**: for the owner or the owner's parent, on a `running` service. The end writes
  `restarting` with the count one up; once the socket reads dead the row is `asked`, and the
  start runs as `start/5`'s does, with its own turn and sync. A restart that a framework restart
  cut is ended at the next settle, not started again (as F-83's fuller version did).
- **`hand/4`**: the owner only, to its parent or a child (`Grants.may_hand?/4`), on a `running`
  service. The write expects the owner and the state it read, so a hand racing an end or a
  second hand is refused with `{:changed, _}`. `keep` is not touched, so it stays with the
  service.
- **`logs/4`**: `tail -c +<offset+1>` of the log on the host; answers the text and the next
  offset.
- **KILL after a grace**: the end writes `end_until` (now plus the call's `:timeout`, 10 s by
  default) with `ending` or `restarting`, sends TERM to the group while the pid has its recorded
  start time, and waits for the socket to read dead until `end_until`. Still live, it sends KILL
  the same way (one script, the signal as an argument), then waits up to 2 s. It is `ended`
  only once the socket reads dead; otherwise `{:unknown, {:not_dead, _}}` and the row stays as
  written. The settle after a framework restart sends TERM before `end_until` and KILL after
  it, so a program that ignores TERM is still ended across a restart. The table gains the
  `end_until` column for that.
- **A start that settles after its owner's end** (F-83's new-3): `Services` takes a new
  required option, `:ended`, a function of an agent's name that answers true once that agent
  has ended (the embedding app reads its own durable row, as `Grants` reads the tree). The start's
  settle writes the row in one call to `Services`' process (`{:started, name, seen}`), which,
  when the row is now `running`, reads the owner's end in the same call. Ended without `keep`,
  the row becomes `ending` with no owner (`Copy.tla`'s `OwnerSeen`), and the start's own call
  ends it and answers `{:refused, {:start, :owner_ended}}`. With `keep`, it goes to the owner's
  parent and the start answers that row. The settle after a framework restart uses the same
  write, and ends such a row in its second pass over `ending` rows.

The write and the read are in one call so the race closes: the embedding app makes the owner's
end durable before it calls `owner_ended/3`, and `owner_ended/3` lists rows through the same
process. Either the settle's write comes first and the list sees `running`, or it comes after
and the read sees the end.

## The model

No spec changed. `Copy.tla` models the end as one step that lands once nothing is held
(`EndSent`, `Lands`, `EndedIsEnded`); TERM, then KILL, is how that step lands, and the row is
still `ended` only on a dead socket. `OwnerSeen` already takes a service whose start settled
after its owner's end; this unit builds that.

## Tests

`apps/caf_services/test/services_test.exs`, five new, named for the property each checks:

- `StartsOnSyncedCopy, OneProcess`: a restart ends the old process, syncs the edited worktree
  again (the log reads `up in one`, then `up in three`), and counts 1, then 2. Every turn is
  free after.
- `HandedAlongEdge, OneOwner`: the parent and a sibling are refused, a child takes it with
  `keep` and the same pid, and the child hands it back up.
- `Logs` (no property of its own: the model's log reads are a job's): from offset 0, 3 and the
  end, and an unknown name refused.
- `EndedIsEnded`: a program that traps TERM is ended by KILL after a 500 ms grace; the stop
  takes at least the grace and the pid is gone.
- `ServiceEndsWithOwner`: a start whose owner has already ended is ended and answers
  `{:refused, {:start, :owner_ended}}`, its pid gone; one with `keep` runs, owned by the
  parent.

## Findings

### new-1. A sync skips an edit of the same size made in the same second

What happened: the restart test first wrote `two\n` over `one\n` and the restarted service
still read `one`. Why: `Copies.sync/5` runs rsync with `-lpt` and rsync's quick check, which
compares size and modification time to the whole second (rsync 3.5.0 from devenv; checked by
hand: a copy with `-lpt` keeps `one` after such an edit). A worktree edit that keeps a file's
size, made in the same second as the copy's last sync of that file, does not reach the copy, so
a job or service can start on a copy that is not the worktree (`StartsOnSyncedCopy`). What I
did: the test writes `three\n`, another size, with a comment; `Copies` is not this unit's. What
the design should change: say the sync compares content, not only size and second; the plain
fix is rsync's `--checksum` (it reads each file on both sides at each sync), or a sync that
sends each path whose mtime in nanoseconds or size changed since the last record.

### new-2. `Services` reads an agent's end through a new `:ended` option

What happened: the design says a start's settle "reads the owner's end", but not from where.
`Grants` cannot tell: it reads only names and parents, and an ended owner must stay in the
tree, since `owner_ended/3` asks `Grants.parent/2` for it. Why: the owner's end is the
embedding app's durable row (`Copy.tla`'s `OwnerEnds`). What I did: a required option,
`:ended`, a function of an agent's name, as `Grants` takes its tree. What the design should
change: name `:ended` in "Services", and say the embedding app makes an agent's end durable
before it calls `owner_ended/3`. The race closes only in that order.

### new-3. After KILL, the end waits a fixed 2 s

What happened: the design says KILL comes after the call's timeout, but not how long the end
then waits for the socket. Why: KILL cannot be ignored, but dtach still has to see the
program go and remove its socket. What I did: a 2 s module constant; past it the call answers
`{:unknown, {:not_dead, _}}` and a later stop or cue sends KILL again. So a stop can take up to
its timeout plus 2 s. What the design should change: nothing, unless a caller needs the whole
call bounded by `:timeout`; then the grace would be the timeout less the wait.
