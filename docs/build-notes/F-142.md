## What was built

- **The drain waits for background commands** (item 1, F-133's new-1). The main session
  measured on 2.1.322 that the session file's `status` is `shell` while a background command
  runs after the turn ended, and `idle` once it ends. `Sessions.stop/3` already sends the
  SIGTERM only on `idle`, so `shell` refuses the stop as `{:not_idle, "shell"}`, and the
  `Mover` asks again on the next `registry:` cue. So that read is the wait. `Sessions.Turn.file_state/1`
  now knows `shell` as `:running`, where it read `:unread` before, so no reader takes it for
  an ended turn. The `ClaudeStandIn` writes `shell` on that line.
- **`Move.tla`** reads that evidence. `IdleRead` needs `bg = {}`, since the file says `idle`
  only then. `Cleared` no longer reads `bg`: it is the drain read clear. New
  `Break_Move_ShellIsIdle` takes `shell` for `idle` and fails `NothingLost`. A crash of the old
  process no longer counts toward `lost`: once `Cleared` stopped guaranteeing `bg = {}`, TLC found
  a crash during `stopping` ending a background command. That is a crash, not the move.
- **The copy takes `session-env/<session id>`** (item 2, F-133's new-4), beside the transcript
  and its directory. It is copied as a directory or as a file, each under a temporary name and
  renamed. A session with none has nothing to copy.
- **A move's resume carries the first due row by `launch`** (item 3, the move's half).
  `Mover`'s resume of an interactive session first calls `Mailbox.launch/4`. It passes the text
  as the resume's `prompt:` and tells `Mailbox.launched/3` the answer, as `Delegates`'
  resume does. `{:ok, :none}` and `:no_transcripts` resume with no prompt.
  `{:refused, {:sending, ids}}` waits for the next cue. A headless session's rows still go by
  its stream.
- **`Move.tla`'s instance of `Delivery`** now sets `turned` and `Long` from the spec's own state. `turned` is a
  new variable: true at first, false at the resume, and true at a turn's end of the current
  process. `Long` is every row, since any row may be a report. `stopping` is the row's
  `stopping` only while its process runs: once the process is gone, the row is free.
  `LaunchMarked` and `ResumedWith(i)` are the launch. `ResumedBare` resumes with no prompt only
  when no row is due or in flight. New `Break_Move_NoResumeLaunch` resumes bare whatever is due,
  and fails `RowsArrive`: the message waits for a waiter the new process never gets.
- `design.md`: "Moving it" step 2, `copying` and `resuming`, the session file's statuses and the
  per-release check, and the launch paragraph in "Delivery". `READING.md`: `Move.tla`'s steps.

## Findings

### new-1. A row stored after a resume that carried none, or after a restart cut the waiter, still waits for a person's prompt

What happened: the brief's item 3 says a resume carries the first due row by `launch`. That
covers a move's resume and a restart that cut a main session's waiter, "so a long report never
waits for a person's prompt". Two cases are left that a launch at the resume does not reach:

1. A move's resume when nothing is due. The new process has no waiter until a turn of it ends,
   and the `Inlet` types no long row. So a report stored after the resume waits for a person's
   prompt. `Move.tla` now says so: `Waits(i)`, the escape in `RowsArrive`, is exactly this
   case.
2. A framework restart cuts a running main session's waiter, and the same follows after its
   waiter's 7,200 s deadline. No part resumes a main session then: only `Mover` calls
   `Sessions.resume` for one. A resume would first need a SIGTERM of an idle session a person
   may be typing into, and then the case above if nothing was due yet.

Why: the launch carries a row only at a start, and only a row due at that moment.

What I did: built the move's half, where a row is due at the resume. I modeled the rest
honestly in `Move.tla` (`Waits`). I left `Team.tla` and `Delegate.tla`'s parent instance with
`turned` always true and `Long = {}`. Taking those from their own state now would only turn
the stuck report into an accepted `Held`, and there is no mechanism yet for a Break to fail
against.

What the design should change: one way for a long row to reach an interactive session whose
turn has ended and that has no waiter. That covers after a bare resume, a restart, or a
waiter's deadline. A recommendation: the typed transport carries a long row by a pointer. Write
the row's text to a file of the framework's, and type one short line that names the file, with
the row's uuid at its end (the `Inlet`'s checked write, as today). The transcript's user line
settles it, as a typed row's does. Its turn's end brings the next waiter. This needs no SIGTERM
and no new transport: `Delivery.tla`'s `typed` loses the `Long` guard, and `Held` goes away.
The other way is a resume that always carries a prompt, a short word to go on when nothing is
due. It costs a turn at every move and still leaves the restart and the waiter's deadline.
Once one is decided, `Team.tla` and `Delegate.tla`'s parent instance take `turned` and `Long`
from their own state, with a `Break` that fails where the old assumption hid the report.

### new-2. Nothing stops a background command from starting during the drain

What happened: "Moving it" step 1 says the drain starts no new background commands, and
`Move.tla` refuses `BgStarted` while draining. In the code, nothing stops Claude Code from
starting one: a person's prompt or a row taken before the stop can run a command in the
background.
Why: the drain is `Mailbox`'s and `Delegates`'; a background command is the session's own.
What I did: nothing. The idle read now waits for any background command, wherever it came
from, so none is cut. One started between the idle read and the SIGTERM is cut, as a person's
turn is (step 3).
What the design should change: say that the drain stops what the framework starts, and that
the idle read covers the rest up to the SIGTERM; or name a hook (PreToolUse on `Bash` with
`run_in_background`) that refuses one while the row has a move phase.
