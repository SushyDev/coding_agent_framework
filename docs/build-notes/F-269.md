# F-269: a delegate whose report was missed, a hand-on that never settles, and a lease ask that times out

The unit began with a diagnosis (below, from the first builder), which stopped for a design
decision. The decisions: new-1 and new-2 accepted, new-3 split out as F-276 (the lease ask's
caller deadline). This unit then built new-1 and new-2, with their tests.

## What was built

- **The model first** (`Delegate.tla`): a variable `shell`, the interactive delegates whose
  session file reads `shell` because a background command of an ended turn still runs.
  `DelegateFinishes` may leave one running; `BackgroundEnds` ends it, with no fairness, since
  a hung command never ends; a kill or the delegate's end ends it too. `ReportTurnEnded` guards
  `StopHandled` and `TranscriptRead`: in the design it always holds, since the turn-end line
  comes with the turn's end. `Break_Delegate_BackgroundHolds` reads the session file instead,
  and TLC finds `ReportArrives` violated (188 states).
- **new-1** (`Transcripts.Fold.reply_to/2`, `Delegates.settle_interactive/3`): `reply_to/2`
  answers `ended` too, true when a `system` line with subtype `turn_duration` follows the turn's
  last assistant line and the turn has a reply. `settle_interactive/3` takes the report when
  the turn is closed by a later turn or ended by that line, and only then reads the session
  file. A report is no longer held behind a running background command. A message due to the
  delegate still goes by its transports' own rules: `Mailbox` is unchanged.
- **new-2** (`MCP`'s fix flow): a state read that answers `{:unknown, reason}` records an act of
  its own in `Acts` (`Acts.record/7`), the tool's name, outcome `unknown`, the reason whole, and
  detail `{"step":"state"}`, and the caller gets the unknown unchanged. The claim still comes
  after the state read, as the design decides.
- **The per-release check**: `caf_real`'s interactive delegate test now checks that the pinned
  release writes `turn_duration` after the report's reply. It runs with `mix test.real` only;
  it was not run in this unit (no logged-in setup).
- `docs/design.md`: the interactive report's turn-end rule ("Interactive delegates") and the
  unknown state read ("fixes", beside the claim's rules).

Nothing changed in `Mailbox`, `caf_scheduler` or `caf_runs`.

- `MCPTest`, "a stop whose state read times out is an unknown act in the ledger": a stand-in

- `Fold.reply_to/2`'s doctest: `ended` false with no turn-end line and on a turn a later prompt
  closed, true after `turn_duration`.
- Not built: a restart with a hand-on attempt running (item 2 needed no code: the row was
  `queued`, not in flight, and the restart rules hold), and a lease ask whose caller times out
  (item 4, F-276).

## What was measured

- **A `SubagentStop` follows every `Stop` by about 3 s**, whatever the `Stop` input's
  `background_tasks` holds (0 or 1 tasks). On this host, 53 `SubagentStop` rows, each about 3 s
  after a `Stop` of the same session. So the `SubagentStop` at 11:56:11 is routine, and not the
  cause.
- **`attempt = running` on a `queued` row is not a hand-on in flight.** It is the typed
  transport's refusal `{:refused, :running}` (`Transport.Typed.turn/2`), written as the row's
  attempt by `Mailbox`'s `type/3`. It means: no waiter was held, and `Sessions.Turn.interactive/3`
  read the session's turn as `:running`. This host's store shows the same shape twice now: a
  row to a main session and a row to this delegate, each `queued` with `attempt` `running`
  while its target's turn ran. A row whose hand-on is in flight is `sending`, never `queued`.
- **The `Stop` input lists background tasks.** Rows here carry `background_tasks` entries of
  type `shell`, status `running` (as "An agent's background commands in the tree" says).

## Diagnosis

### Item 1: the missed report

An interactive delegate's report is taken when its turn has ended: a later user entry closed
the turn, or its session file reads idle (`settle_interactive/3`, `turn_ended?/2`, which asks
`Sessions.Turn.interactive(agent, files, false) in [:idle, :ended]`). The session file reads
`shell` while a background command of the turn still runs after it ended, and `busy` while a
turn runs. `file_state/1` reads both as `:running`. So while a background command runs, the
report waits. A command that never ends (a server, a watcher, a hung test) holds the report for
ever. No cue changes that: the transcript has no later line, and the idle `Notification` moves
nothing in `Delegates`.

The queued rows' `attempt = running` confirms that the delegate's file read `busy` or `shell`
from 12:17 on. The idle `Notification` at 11:57:08 shows Claude Code's prompt was idle by then.
Of those two, only `shell` fits: the turn had ended, and a background command still ran. This
is inferred: the observed `Stop` row's `background_tasks` is not in this store. Its row on the
earlier host would settle it.

Of the brief's candidates: the `SubagentStop` is ruled out (measured above). A report read
before its last line was written is ruled out as the cause of a lasting stall: each later cue
reads the transcript again. The waiter is not part of the report's path (`turn_ended?/2` passes
`false` for it). The cause is a fourth one: the turn-end rule for an interactive report reads
the session file, which a background command keeps at `shell`.

This contradicts the design's own rule for headless delegates (F-184, "A background command
outlives its report"): "a delegate's report is never owed behind a hung command".
`stuck_background` covers only headless delegates, so nothing ends the hung command either.

### Item 2: the queue behind a row

No hand-on was left `running` across the restart. The row was `queued`, and each settle refused
it again for the same `:running` turn. Rows to one addressee go oldest first, so the two rows
behind it were never tried. `updated_at` at 22:57 fits the restart writing another attempt
(such as `no_waiter` while nothing was read yet) and then `running` again. The design's restart
rules for a `sending` row already hold, and the code follows them. Item 2 has the same cause as
item 1: an interactive session whose file reads `shell` is never typed into.

One question is left open: why no waiter was held at 12:17, 21 minutes after the `Stop`. Each
turn's end starts one, and it holds for 7,080 s. With a waiter held, `Mailbox` would have handed
the row by the waiter whatever the file said. This store cannot answer it. `Intake`'s waiter
holds for that session on the earlier host would.

### Item 3: the stop that timed out

`{:unknown, {:timeout, 15000}}` is `Delegates.fix_state/3`'s bound (`3 * @step`). The MCP fix
flow reads the state first and claims the act in `Acts` only with that state
(`MCP`'s `by.state.()`, then `Acts.claim/6`). So a state read that times out claims no act. The
`Delegates` process did not answer within 15 s: it was busy, most likely in settles on the
loaded host (F-261 found settles slow there). Had it answered, the stop would have been refused
at once: `act/7` refuses a stop whose report is not delivered (`{:refused, {:report, status}}`).
"Record the act before it waits" conflicts with the design's claim, which holds the state the
fix was decided on (F-144, F-149).

### Item 4: the lease ask

`Delegates.lease/4` calls `Scheduler.request/3` with the default 5 s bound. Under load the
request waited about 6 s in the `Scheduler`'s mailbox. The `Scheduler` then took it, granted it
in the same step (`receive_request/3`, then `serve/1`), and replied to a call that had already
given up. The late reply reaches `Delegates.handle_info({ref, answer}, s)`, finds no pending
call, and is dropped. The row is refused `{:lease, {:unknown, {:timeout, 5000}}}` (the reason is
kept whole here; `lease_refusal/1`). The grant is released later by the monitor, once
`Delegates.Work.state/2` answers `:ended` for the refused row. So a late grant does settle
today, but late, and nothing records why it was made.

## What is left

- Item 4, the lease ask's caller deadline, is F-276 (new-3).
- Why no waiter was held for the delegate at 12:17 (item 2's open question) is not answered:
  see new-4.

## Findings

### new-1. An interactive delegate's report waits behind a background command

What happened: an interactive delegate ended its turn with its report while a background
command of that turn still ran. Its session file read `shell`, which `Sessions.Turn` reads as
`:running`. So `Delegates` never took the report, and `Mailbox` never typed a row into it, for
11 hours.

Why: the interactive turn-end rule reads only the session file or a later user entry. The
headless rule takes the report at the turn's `result`, whatever runs in the background (F-184).

What I did: diagnosed it. Accepted; built after the decision (`## What was built`).

What the design should change (recommendation): end an interactive report's turn by the
transcript, as the headless one is ended by its `result`. The turn has ended once the
transcript shows, after the reply with `stop_reason` `end_turn`, Claude Code's own turn-end
`system` line (`turn_duration`, written after `stop_hook_summary`). Check that line per pinned
release, as the screen fixtures are. Keep `shell` as `:running` for `Mailbox`'s typed writes and
for moves: a typed write into a session whose background command runs is a separate question.
The cost is one more line kind in `Transcripts.Fold.reply_to/2`'s `closed`, and a release
check. The other way, reading the `Stop` row in `Intake`, loses the event while the framework is
down, which the transcript does not.

### new-2. A fix's state read that times out claims no act

What happened: the parent's `stop` answered `{:unknown, {:timeout, 15000}}` and no act was
recorded.

Why: the claim in `Acts` holds the state the fix was decided on, so it is written only after
`fix_state/3` answers. The `Delegates` process did not answer within 15 s.

What I did: accepted; built after the decision (`## What was built`).

What the design should change (recommendation): keep the claim after the state read, as the
design decides. Record the failed read as an act of its own, the tool's name with outcome
`unknown` and the reason, so the record shows the call was made. Separately, measure how long a
`Delegates` settle takes under load before changing its bounds.

### new-3. A lease granted after its caller gave up

What happened: two starts answered `{:refused, {:lease, {:unknown, {:timeout, 5000}}}}`. The
`Scheduler` granted each lease about 6 s after the ask, then released it.

Why: the caller's bound and the `Scheduler`'s step are not one clock. A request that waits in
the mailbox past the caller's bound is still granted.

What I did: nothing. Split out as F-276.

What the design should change (recommendation): withdraw the ask, as `Sessions` does a call
past its caller's deadline (F-166). `Scheduler.request/3` carries `caller_deadline:` (wall-clock
ms, the call's timeout less a slack). A request taken past it is answered `{:refused,
:caller_gone}` and writes no grant. A grant made in the slack and still answered late is
released at once by the reclaimer, as today, with `by` `caller_gone`. Model it in
`Schedule.tla` with `Break_Schedule_GrantAfterCaller`.

### new-4. Rows to an interactive session wait while its background command runs

What happened: with new-1 built, the report goes. By the code (not run here), a parent's
message to the same delegate still waits while its session file reads `shell` and no waiter is held: the typed write
refuses `:running`, and the row stays `queued`, attempt `running`, with every row behind it.
Under a hung command that is for ever, as the 12:17 row was.

Why: the transports' own rules, kept by new-1's decision. A waiter would carry the row, and
each turn's end should start one, but on the observed host none was held 21 minutes after
the `Stop`. This unit could not find out why: that host's `Intake` holds are not in the store
read here.

What I did: nothing; the decision keeps `Mailbox` as it is.

What the design should change (recommendation): measure on the pinned release whether the
Stop hook's waiter is held after a turn that leaves a background command running, and whether
Claude Code takes a waiter's text then. If it is held, find why it was not on that host. If
not, decide whether a typed write may go into a session whose file reads `shell` when its
screen shows an idle box (the screen already tells a turn running from an idle prompt).

### new-5. The screen stand-in has no `shell` state

What happened: the interactive test needs a session file that reads `shell`. The screen
stand-in writes only `busy`, `idle` and `waiting`, so the test rewrites the file itself once
the first turn reads idle.

Why: `ScreenStandIn` never modeled a background command.

What I did: the test's own `shell!/2` helper, renamed into place as Claude Code writes it.

What the design should change (recommendation): none needed now. If more tests need it, give
the stand-in a key or flag that starts a background command and writes `shell` until it ends,
as `ClaudeStandIn` does for headless sessions.
