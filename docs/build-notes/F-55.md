# F-55: worktrees, the later part of `Sessions` (model and design)

## What was built

The model and the design. The code was written and its tests pass, but it came to 549 changed
lines apart from tests, past the 500 the unit allows, so it is not on this branch (new-11).

- **`Start.tla`** now models a start's worktree. Its header names the new parts (`Sessions`'
  worktree steps, `Sessions.Worktree`, git, `Shell.Reaper`) and what each word means in git
  (new-1 to new-6). Between the row and the hold there are three steps. `Checked` is the list
  and the status: a free path is added, a clean tree on the branch is reused, and anything else
  is refused. `Added` is `git worktree add`, with `-b` when the branch does not exist; at a path
  taken since the check it fails and leaves its branch behind. `SetupStarts` and `SetupEnds` run
  the setup, which can finish or fail. `RowWritten` first checks that no other row holds the
  path. `Adopt`'s refused branch removes a clean tree no other row holds. A later start of a
  name may be a resume. People and other programs can take a free path or change files in a
  tree (`MaxOutside`).
- Five new invariants: `BusyTreeUntouched`, `RemovedWasClean`, `ReusedWasClean`, `OnlyInTrees`
  ("a branch a failed add left behind is not taken for a worktree") and `StartsInReadyTree`,
  plus `TypeOK`'s new fields. There are eight new `Break` values, each with a configuration TLC
  must fail: `NoHeldCheck`, `ReuseDirty`, `ReuseOther`, `ReuseSkipsSetup`, `BranchAsWorktree`,
  `RemoveDirty`, `RemoveOrphan` and `SetupOutlives`. Defense in depth, named in the header: the
  removal's own check for a row that holds the path (behind `RowWritten`'s), and git's refusal
  to remove a dirty tree (behind the clean check).
- **`Worktrees`, a constant**, turns the new steps off. Every existing configuration sets it
  FALSE and finds exactly the states it found before (new-10). Two new configurations set it
  TRUE: `Start_Worktrees` (one name started twice, two restarts, `Before` any path state, one
  outside event) and `Start_SharedTree` (two names on one path, one restart).
- **`docs/design.md`**: "The worktree" under the delegate protocol holds every pick below. The
  parts table no longer calls worktrees a later part of `Sessions`, and the model section lists
  the new invariants. `model/tla/READING.md` covers the new steps.

## What I ran into

Every point below was tried on git 2.56.0 (devenv's) in a scratch repository, never the
repository this unit is built in.

- `git worktree add -b <b> <taken path> main` exits 128 ("already exists") and leaves `<b>`
  behind, as the rule says. An existing empty directory is accepted as the path.
- `git worktree list --porcelain` prints the path with symlinks resolved. A worktree added at
  `…/wl/a`, where `wl` links to `w`, is listed as `…/w/a`, and the test directories sit under
  `/tmp`, which links to `/private/tmp`. So the path has to be physical to be found (new-1).
- A `post-checkout` hook that exits 1 makes `git worktree add` exit 1 with the worktree in
  place and listed (new-7).
- `git worktree remove` without `--force` refuses a tree with an untracked file ("contains
  modified or untracked files"), and removes one that holds only ignored files, ignored files
  and all (new-3).
- `git worktree add <path> <branch>` of a branch another worktree has checked out fails
  ("already used by worktree").

## Findings

### new-1. Where worktrees live

What happened: the design does not say where a delegate's worktree lives.

What I did: `<home>/worktrees/<project>/<name>`, named by the session's name, under the physical
path of the framework home, since git lists worktree paths with symlinks resolved. The home
already holds "everything the framework keeps on a host", and the name is already a socket name
and unique on the host. A path named by the branch would need escaping (`a/b` against `a`).

What the design should change: nothing more; "The worktree" says it.

### new-2. The project's data that `Sessions` reads

What happened: the design says a project is data ("its repository, trunk, branch pattern, setup
commands and the checks its stacks must pass") but gives no shape.

What I did: `%{name, repo, trunk, setup, setup_timeout, env}`. Each setup command is an argv
whose program is an absolute path, so no command is looked up through a `PATH`. One deadline
covers the whole setup. `env` is the setup's environment, built from nothing with `env -i`. git
runs with an empty environment: nothing of the framework's own environment, such as a `GIT_DIR`
set by a hook the framework runs under, reaches the repository. And the removal after a restart
needs only the row's `repo`. The branch pattern and the cap stay with `Delegates`.

What the design should change: when `Delegates` is built, say where the projects' data lives
(the host app's configuration, handed in, or a table) and that `start_delegate` hands
`Sessions` the project as above.

### new-3. "Clean" in git's terms

What happened: the design says a worktree is reused or removed "only when clean".

What I did: `git status --porcelain --untracked-files=all` lists nothing: no change to a tracked
file and no untracked file that is not ignored. Ignored files do not count, since the setup
makes them (dependencies, build output), and `git worktree remove` deletes them. Commits not yet
pushed do not count either: they stay on the branch, which no removal deletes.

What the design should change: nothing more.

### new-4. A setup that fails or passes its deadline

What happened: the design says what the setup is for, not what a failed one leaves.

What I did: the start answers `refused{setup, …}`, and the worktree and its branch stay as they
are. Every start runs the setup again, a reused tree's too, so a tree whose last setup failed
is never started as if ready (`Break_Start_ReuseSkipsSetup` shows the bug that skipping it
would be). A project's setup must therefore be safe to run again. The setup runs under the
host's reaper, so a restart of the framework ends it (`Break_Start_SetupOutlives`: otherwise
the removal after the restart takes a tree a setup still writes in).

What the design should change: nothing more. A view could show a row's `worktree` and reason, so
a person sees a tree left by a failed setup.

### new-5. A resume's worktree

What happened: the design's step 1 checks are for `start_delegate`; a resume (step 6) of a
killed delegate meets its own uncommitted work in the tree.

What I did: a resume takes its name's tree as it is, dirty or not, refuses one that is not there,
and runs the setup. It is still refused when another row holds the path.

What the design should change: nothing more; "The worktree" says it.

### new-6. "Held by a live agent"

What happened: the design does not say how the framework knows an agent holds a worktree.

What I did: a row that has not ended (any status but `stopped` and `refused`, the same rule as
a name that is not free) whose `cwd` is the path. The check is made in the same call that
writes the row, so no two starts take one path. A row holds its path from its write until it
ends, so the removal's own check is defense in depth. Services, when they are built, will hold
a path in the same way.

What the design should change: when `Services` is built, its rows count as holders.

### new-7. What an add did is read from the list, never from its exit status

What happened: a failing `post-checkout` hook makes `git worktree add` exit 1 with the tree in
place. And a `-b` add at a taken path fails and leaves the branch.

What I did: after an add, whatever its answer, the start reads `git worktree list` again, and
only the path listed on the branch counts as added. The branch's existence is never read for
that (`Break_Start_BranchAsWorktree`). A path that holds a directory git does not list is found
only by the add's failure, so such a start leaves a branch behind. That branch is harmless: the
next start of the name checks it out without `-b`.

What the design should change: add to the **Delegates** rules: "A repository's hook can make
`git worktree add` exit non-zero with the worktree added; read the worktree list for what an
add did." (Added by the reviewer.)

### new-8. A long setup runs outside the `Sessions` process

What happened: a start today runs its hold inside `Sessions`' call, which is short. A setup can
take minutes, and every other call of the host would wait behind it.

What I did (in the code left off this branch): the checks, the add and the setup run in a task
linked to `Sessions`. When `Sessions` dies, the task dies with it, and the reaper ends the
task's commands. The row's deadline covers the setup's (`setup_timeout` plus the git
commands' bounds), and so does the call's timeout.

What the design should change: nothing, unless "one process with one job" is read to forbid a
linked task under a call; then say that a call may run its slow commands in one.

### new-9. A worktree start needs the reaper

What happened: `Sessions` had no `Shell.Reaper`.

What I did: `Sessions` takes the host's reaper (`reaper:`), and a worktree start without one is
refused (`:no_reaper`).

What the design should change: nothing more.

### new-10. `Start.tla` was extended, not split into a new spec

What happened: the brief allowed a new spec if it read better.

What I did: extended `Start.tla`. The removal is part of `Adopt`, and the worktree steps sit
between `RowWritten` and `Held`, so a new spec would repeat the start and its adoption. The
`Worktrees` constant keeps the old configurations exactly as they were.

What the design should change: nothing.

### new-11. The unit is past 500 lines: the split I would make

What happened: the code came to 549 changed lines apart from tests: 179 for `Sessions.Worktree`,
49 for the table and 321 for `Sessions`.

What I did: stopped. This branch holds the model, the design and this note. The code and its
tests, with all 35 of `caf_sessions`' tests passing, are on the local branch
`framework/f-55-worktrees-code`, one commit on top of this branch (not pushed).

What the design should change: nothing. The split I would make:

1. **`Sessions.Worktree`**, the pure module: the project's and the branch's checks, the git
   argv, `listed/2` (the porcelain list), `decide/4` (`Checked`) and `removal/4` (`Remove`), with
   its doctests and unit tests. About 180 lines and 30 of tests.
2. **`Sessions`' worktree start and removal**: the table's `repo`, `branch` and `worktree`
   columns and `holding/4`, the path check before the row, the task that checks, adds, reads the
   list again and runs the setup under the reaper, the resume, the removal in `Adopt`, and the
   tests on real git repositories (a new branch's tree set up at each start, a dirty tree
   refused and taken by a resume, an add at a taken path that leaves its branch, a tree on
   another branch, a failed and a timed-out setup, a held path, and a restart that ends the
   setup and then removes a clean tree and keeps a dirty one). About 370 lines and 190 of
   tests.
