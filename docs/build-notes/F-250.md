# F-250: an agent's `message` can be sent again safely

## What was built

On a loaded host, two `message` calls answered `{:unknown, {:timeout, 5000}}` although their
rows were stored and delivered. An agent that sends again after `unknown` queued a second copy.

- `message` takes an optional `key`: a string of 1 to 128 bytes, scoped to the sender. The MCP
  passes `"msg:<from>:<key>"` to `Mailbox.message/5`. Any other key is refused `{:refused, :bad_key}`
  before anything is stored.
- A second send under the same key stores no row and answers `{:ok, {:queued, id}}` with the
  first row's id. With no key nothing changes.
- An `unknown` answer for a keyed send is `{:unknown, %{reason: …, key: key}}`, so the agent
  sees that sending again with that key is safe. Without a key it is as before.
- The tool's description tells the agent to set a key whenever it might send again after
  `unknown`.
- The step bound is the MCP instance's `:step` option, 5 000 ms by default, held in the
  instance's context. It covers one call a tool makes into another part: for `message`, one
  table write behind the `Mailbox` process's queue. The library does not scale it by load; the
  embedding app may give a larger value. The bound on a call into the MCP process itself
  (`ask/2`, used by `call/4` for the call log) is still the fixed 5 000 ms: it has no instance
  to read the option from (new-2).

## What was measured

Nothing new: the failure was seen on the live tree at a load of about 60, not reproduced here.
`mix test` for `caf_mcp` and `caf_mailbox` pass (3 new MCP tests, 1 new Mailbox test).

## What I ran into

The brief says `Mailbox.message/5` already takes `:key`. It did not: only `notify/4` did.
`message/5` now takes it and stores it in `reply_to` as `notify/4` does. A repeat answers
`{:ok, {:queued, first_id}}`, found with `Table.answer/2`; `notify/4` still answers
`{:ok, :stored_before}`.

## Findings

### new-1. `message/5` had no `:key`

What happened: the brief named `:key` as existing. Why: only `notify/4` had it. What I did: gave
`message/5` the same key, in the same unique column. What the design should change: nothing; its
doc now says both share one key space.

### new-2. The MCP's own call bound is still a constant

What happened: `:step` reaches every call a tool makes, but `ask/2` (the `GenServer.call` into
the MCP process) is a module function with only the pid, so it keeps `@step`. Why: no instance
state is at hand. What I did: left it. What the design should change: decide whether the MCP
process should hand out its `:step` (one extra call) or keep one constant for its own table.

### new-3. A key could clash with a framework key (built)

What happened: `"<from>:<key>"` shared the column with `notify/4`'s keys such as `job:<id>`, so
an agent named `job` sending key `x` would have clashed with a notice keyed `job:x`. What I did:
the MCP stores an agent's key as `"msg:<from>:<key>"`; a test stores a notice keyed `job:x` and
a message keyed `msg:job:x`, each its own row. The test is at the mailbox, whose tree has no
agent named `job`; the MCP test checks the key's form. What the design should change: nothing.
