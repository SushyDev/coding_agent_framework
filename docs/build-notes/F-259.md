# F-259: an interactive session's background commands, in the tree

## What was built

- `Tracker.Background` (new, pure): an agent's background commands as
  `%{count, since, source, groups}`, or `{:unknown, reason}`.
  - A headless delegate's come from its `Stream` fold's `tasks` (`source` `stream`).
  - An interactive session's come from its newest `Stop` row and its session file:
    `session_file` when the file's status was written after that `Stop`, else `stop`.
  - An agent with no process has none (`process`).
- `Tracker.Tree` gives each agent `background`, and `Tree.records/1` names each running agent's
  process. `Tracker.agents/2` takes `groups:`, a map of host to a groups reader
  (`&StuckBackgrounds.Groups.read(procs, &1)`). It reads each running agent once, in the
  caller's process, and shows the count or `{:unknown, :no_proc}` as `groups`.
- `Stream.Fold.stamp/2` stamps each background command with the read that saw it start, which
  gives `since`.
- `Tracker.Fold` keeps a session file's `status_updated_at`.
- The interactive stand-in writes `statusUpdatedAt`, as Claude Code does at each status write.
- `model/tla/Background.tla` models one interactive session: commands that start in turns, a
  `Stop` that lists every running command and maybe ended ones, a session file, and a view that
  reads each source on its own. It has `NoNoneWhileRunning` and `EmptiesAtEnd`, with
  `Break_Background_StaleFile` and `Break_Background_UnknownAsNone`.
- Tests (`apps/caf_tracker/test/background_test.exs`) run on the stand-ins with real `Sessions`,
  `Registry`, `Stream` and `Intake` tables. Both kinds cover a command that runs after its turn
  and a command that ends between turns. The interactive test covers a stale `Stop` followed by
  the file's end. The headless test covers the groups read, which is `{:unknown, :no_proc}` on
  macOS and a count on Linux.

## What was measured

There was no logged-in setup here (`CAF_REAL_SETUP` unset), so I read the pinned release's
bundle (`claude-code-2.1.322/bin/.claude-wrapped`) and ran no live session.

- **The `Stop` input** of an interactive session (the same code builds `SubagentStop`'s) carries
  `background_tasks`. The bundle describes it as "in-flight background work (running/pending +
  backgrounded) registered in this session … Empty array when nothing is in flight."
  - An entry is `{id, type, status, description}`, plus `command` for a shell. Its `type` is a
    friendly label: `local_bash` becomes `shell`.
  - The filter keeps a task whose status is `running` or `pending` and that is not
    `isBackgrounded: false`. So the list holds only tasks still running at that turn's end.
    Tasks that ended before the turn ended are not in it.
  - It also carries `session_crons`.
- **Anything else between turns**: no hook fires when a background shell ends. `TaskCompleted`
  (`task_id`, `task_subject`) belongs to the task list, not to shells. The session file does
  tell: its status is `shell` exactly when the session is idle and some `local_bash` task is not
  in a final state. Every write that carries a status sets `statusUpdatedAt` to `Date.now()`.
  So `shell` turns to `idle` when the last command ends, and that write's time follows the
  turn's `Stop`. A command's end also wakes the session in a turn of its own, which ends with a
  new `Stop` (F-184 measured that headless; for interactive it is not run here).
- **Process groups on Linux**: not run; macOS answers `{:unknown, :no_proc}`. The main session can
  run this on the Linux host:

  ```
  devenv shell -- mix test apps/caf_tracker/test/background_test.exs
  ```

  Its headless test asserts that the groups read is a count there. To see whether the groups
  agree with a real interactive session, run this from the logged-in setup:

  ```
  export CLAUDE_CONFIG_DIR="$CAF_REAL_SETUP/one"   # the account bin/caf-login set up
  mkdir -p /tmp/f259 && cd /tmp/f259
  printf '%s\n' '{"hooks":{"Stop":[{"hooks":[{"type":"command","command":"cat >> /tmp/f259/stop.jsonl"}]}]}}' > settings.json
  tmux new -d -s f259 "claude --settings /tmp/f259/settings.json"
  tmux send-keys -t f259 'Use Bash with run_in_background true to run exactly: sleep 90; echo bg. Then reply: started.' Enter
  # Once it replies, while the command runs and again after it ends:
  cat /tmp/f259/stop.jsonl
  cat "$CLAUDE_CONFIG_DIR"/sessions/*.json
  pid=$(pgrep -f 'claude --settings /tmp/f259'); ps -o pid,ppid,pgid,stat,command -g "$(ps -o sid= -p $pid)"
  tmux kill-session -t f259
  ```

  Record: the `background_tasks` of each `Stop`; the file's `status` and `statusUpdatedAt`
  while the command runs and after; and which groups the claude process leads. Check whether a
  stdio MCP server also leads one.
- **The model**: `Background_TwoCommands`: 258,273 distinct states, depth 12, 5 s at load 44 on
  15 cores. Both Break configs fail with `NoNoneWhileRunning` violated: `StaleFile` with a file
  read older than the newest `Stop`, and `UnknownAsNone` at the initial state.

## What I ran into

- The model's first run found a real hole in my first rule. A view that read a newer `busy` file
  but an older `Stop` showed none while a command from the unread turn ran. A `busy` file says
  nothing about commands from before its turn, so it is not evidence about them. The rule
  stands; the model's horizon now counts only `Stop` reads and `idle`/`shell` file reads.
- The brief asks for `:unknown`; the tree answers `{:unknown, reason}` (`:no_stop`,
  `:no_stream`, `:starting`, `:dialog`), as the repository's rule for outcomes asks. A person
  sees why.
- The `Tracker`'s fold kept only some session-file columns, so `status_updated_at` was dropped
  until I added it.
- The stand-in wrote no `statusUpdatedAt`; it now writes the time of each status write.
- `count` from a `shell` file is at least 1 and otherwise the newest `Stop`'s count. When one of
  two commands ends between turns, the tree still shows 2 until the file says `idle` or a new
  `Stop` comes: the sources do not say which one ended.
- No test timed out under load.

## Findings

### new-1. The process groups cannot yet check the count

What happened: on Linux a groups read names every group the agent's process started. That
includes a stdio MCP server if Claude Code spawns it detached, so a count of groups is not a
count of commands. Why: no run on Linux has recorded the groups' shape (the design already says
so for `stuck_background`). What I did: the tree shows `groups` beside the count and decides
nothing by it. What the design should change: after the Linux run above, decide whether a
group that is not an MCP server can be told apart (by its leader's command line, `bash -c …`).
If it can, the tree could say "listed but no group" for a stale `Stop`.

### new-2. A second `Stop` with the same body is kept as the first one's row

What happened: with no `stop:` callback, `Intake` keys a `Stop` by its body's hash. A later
`Stop` whose body is the same as an earlier one (same message, same tasks) is `seen` and keeps
the earlier row's `written_at`. The newest row can then be an older `Stop`, and the tree reads
that one. Why: `Intake.Event` keys an event with no id of its own by its hash. With the `Stop`
hold on, each `Stop` has a key of its own. What I did: nothing. The session file corrects it
whenever it is newer. What the design should change: key every `Stop` row as the hold does
(with its time), with or without the callback.

### new-3. `since` of an interactive command is when the tree first saw it listed

What happened: neither the `Stop` input nor the session file says when a command started. Why:
the release does not write it. What I did: `since` is the oldest kept `Stop` that lists one of
the newest `Stop`'s commands, or the `shell` file's time when no `Stop` lists one. What the
design should change: nothing unless an app needs the start; a transcript's `tool_use` of the
command (its `run_in_background` call) has it.
