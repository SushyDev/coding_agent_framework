# F-79: `Mailbox`, part 2: a delegate's reply goes to its main session

`Mailbox` stores a delegate's reply to a delivered message as a message from the delegate to its
main session ("Messages": "A message into a delegate starts a turn of its own after its report";
F-77's new-3). The reading of a `Stream` message's outcome moved into `Stream.Fold.outcome/2`,
which `Delegates.Turn` and `Mailbox` both use (F-77's new-5).

## What was built

- `Stream.Fold.outcome(fold, uuid)` names what became of a message written under `uuid`:
  `:none`, `:writing`, `:undelivered`, `:delivered`, or `{:result, text}` once it is delivered
  and the fold's last `result` names it in `user_message_uuids`. It was spelled out three times:
  `Delegates.Turn.next/2` read the state and `last_result`, F-77's `settle_sending` read the
  state, and the reply needs the state and the result. Now all three call it.
- `Delegates.Turn.next/2` reads its brief's (or resume's) outcome through it. One thing changed
  with it: a result counts as the brief's only when it names the brief's uuid, where before any
  result after the brief's replay, with the turn idle, did. See new-4.
- `Mailbox.Table` has a `reply_to` column, the uuid of the message a reply answers, with a unique
  index. `Table.reply/6` inserts with `ON CONFLICT (reply_to) DO NOTHING` and answers the new id
  or nil, so a restart or a second cue never stores a second reply. A file made by F-77's table
  gains the column when it is opened (`ALTER TABLE … ADD COLUMN`, as `Sessions.Table` does).
- Each settle, after the `sending` rows settle and before any delivery, `Mailbox` reads, for each
  `Stream` row whose last result names uuids, the `delivered` rows of that session under those
  uuids. For each whose outcome is `{:result, text}`, it stores `text` as a `queued` message from
  the delegate to its `Delegates` row's `parent`, `reply_to` the answered uuid, under a new uuid
  of its own. The reply is then a row to a main session like any other: it stays `queued` with
  `attempt` `:no_delivery` until `Screen`.
- `status/3` answers `reply_to` too.
- A turn that ends with no result stores no reply. The row of the message stays `delivered`.

## What I ran into

- F-77's table is on `main`, so a `CREATE TABLE IF NOT EXISTS` with the new column would not add
  it to an existing file, and the unique index would then fail to open. The column is added on
  open, and the index made after it.
- `Team.tla` has no action for a reply (new-1). The code follows the design's paragraph.

## Findings

### new-1. `Team.tla` does not model a reply

What happened: the model has `Send` and the delivery actions, but nothing stores a delegate's
reply. Why: the design added the reply after F-69's model. What I did: built it from "Messages"
as the brief says; storing it is one guarded insert, keyed by the answered uuid. What the design
should change: add a `ReplyStored` action to `Team.tla` (a delivered message whose turn's
result was read gains one message from the addressee to its main session, at most once) and an
invariant that each delivered message has at most one reply, so the model checks "once" across
a restart as it does for delivery.

### new-2. A turn that ends with no result: the main session learns nothing

What happened: when the delegate's process ends during a message's turn (killed, crashed), the
message is `delivered` and no reply comes. The delegate's `Delegates` row is `finished`, so
nothing resumes it, and nothing writes the message again: it was delivered. Why: no part reads
"delivered, gone, no result". What I did: nothing; no reply is stored. What the main session
should learn: that its message went in and the delegate's process ended before it answered, so it
can resume the delegate and ask again. Whose part: `Mailbox`'s, since it owns the message's row
and reads both its outcome and its session's exit. It belongs with the sender's notices of
`delivered` and `ended` (F-77's new-3): when the session is gone and the delivered message's
outcome has no result, store one notice to the sender, "no reply: the delegate exited during
its turn", once per message, as a reply is. It too waits for `Screen` to be delivered.

### new-3. The fold keeps only the last result, so a reply can be lost

What happened: `Stream.Fold` keeps one `last_result`. A delegate can start a turn by itself
(F-31's new-2). If that turn's result comes after the message's, and both are folded before
`Mailbox` reads the row, the message's result is replaced and its reply is never stored; the row
just stays `delivered`. The same holds for a brief's report in `Delegates`. Why: the fold was
built when only one reader read one result. What I did: nothing; `outcome/2`'s doc says a reader
must read the result before the next message, which holds for messages the framework writes but
not for a turn the delegate starts. What the design should change: have the fold keep each
result's text on the messages it names (`messages[uuid].result`), so `outcome/2` reads it from
there and no later result replaces it.

### new-4. Sharing the reading made `Delegates` take its report by uuid

What happened: `Delegates.Turn.next/2` used to take any result after the brief's replay as the
report. With `outcome/2`, a result counts only when it names the brief's (or the resume's) uuid.
This is what F-77's new-2 suggested, and it follows from one shared reading: the reply needs the
uuid, and two readings of one outcome would be the duplication the brief asks to remove. What I
did: kept `Mailbox`'s rule that a delegate takes a message only once its row is `finished`, so
behavior with the framework's own messages is unchanged. What the design should change: "Messages"
can say the report is the result that names the brief, and drop F-77's ordering concern, or keep
the `finished` rule as the reason. Your call; nothing in this unit depends on it.

### new-5. An error result becomes a reply with no mark of the error

What happened: a turn that ends `error_during_execution` (after an interrupt) or with
`is_error` still has a `result` that names the message, and its text is stored as the reply.
What I did: stored it as any reply. What the design should change: decide whether a reply row
carries the result's `subtype`, so the main session can tell "the delegate answered" from "the
turn failed", or say that the text alone is enough.
