# F-81: results per message, a reply's subtype, and the notice of a turn with no result

It builds what `model/tla/Team.tla` modeled in F-80: the fold keeps each result on the messages
it names, a message whose turn the process's end cut is `exited`, a reply carries its result's
subtype, and `Mailbox` stores the framework's notice in place of a reply under the same key. It
closes F-79's new-2, new-3 and new-5 and F-80's new-1 and new-3.

## What was built

- **Results per message** (`Stream.Fold`). A message's row has `result` (nil until a `result`
  names it) and `exited`. A `result` event puts itself on each message it names in
  `user_message_uuids` that has none yet, so a later result, a self-started turn's or one that
  names the message again, never replaces it. `last_result` stays, as before, for what reads
  the last turn. `outcome/2` reads the result from the message and answers
  `{:result, %{text, subtype, is_error}}`; `Delegates.Turn.next/2` takes the text from it.
- **`:exited`**. `exit_seen/2` marks each delivered message no result named `exited`, after the
  writing ones are settled from the transcript (a message the transcript holds went in, and its
  turn was cut too). It is kept across `again/1` and a second settle. `outcome/2` answers
  `:exited` for it (`Team.tla`'s `fold[i] = "exited"`).
- **An older fold** (F-63). `Stream.Table`'s load runs `Fold.upgrade/1` after it fills missing
  fields: a message stored without `result` or `exited` gets them, its result from
  `last_result` when that names it, which is what the earlier `outcome/2` read.
- **The reply's subtype.** `messages` gains `subtype` (TEXT) and `is_error` (INTEGER), each added
  to an older file as `reply_to` was. `Table.reply/7` takes the result; `Mailbox.status/2`
  answers both.
- **The notice.** `Mailbox`'s `replies` now walks each fold's messages whose outcome is a result
  or `:exited`, and the rows delivered under those uuids with no reply or notice yet
  (`Table.unanswered/3`, which replaces `delivered/3`). A result stores the reply; `:exited`
  stores a message from `"framework"` to the delegate's main session, `reply_to` the message's
  uuid, saying the message went in and the process ended before it answered. Both go through
  the one `ON CONFLICT (reply_to) DO NOTHING` insert, so the unique index lets in one of them,
  never both. The notice waits like any message to a main session (`:no_delivery`).
- **The stand-in.** A message whose text starts with `self` ends its turn, then at once runs a
  turn of its own whose `result` names no message.

## Tests

Each names the `Team.tla` property it checks.

- `Mailbox`: the reply test (`ReplyOnce`, `ReplyToMain`, `ReplyNamesMessage`) now also checks
  `subtype: "success"`. "the notice" (`ReplyOrNotice`, `ReplyOrNoticeComes`, `ReplyOnce`):
  the stand-in is killed while its turn waits on a permission; one notice comes, and a restart
  and repeated cues store nothing more. "a self-started turn's result is never taken as a reply
  or a report" (`ReplyNamesMessage`): the test waits until `Stream`'s fold holds the
  self-started result as the last one before any cue reads a reply; the reply is still the
  message's, and the held report the brief's. "a reply's subtype is kept": an interrupt ends
  the turn, and the reply says `error_during_execution`.
- `Mailbox.Table`: a notice then a reply, and a reply then a notice, to one message: the second
  stores nothing (`ReplyOrNotice`).
- `Stream.Fold`: a later result, self-started or naming the message again, never replaces one;
  a delivered message no result named is `exited` at the exit, stays so after a resume, and a
  message the result named is not.
- `Stream.Table`: a message an earlier build stored loads with its result taken from
  `last_result` when it names it.

## What I ran into

- The interrupt in a test is `Stream.interrupt/2`, not a `{:interrupt, id}` line: `Stream.write`
  refuses that as `:bad_line`.
- The self-started test needed care to mean anything: if `Mailbox` read the reply between the
  two results, the old fold would pass it too. The test cues `Mailbox` only while the message
  is not yet written, and reads replies only once the fold's last result is the self-started
  one.
- `Delegates.Turn`'s tests built folds by hand in the earlier shape (results on
  `last_result` only). They now go through `Fold.upgrade/1`, as a stored fold would.

## Findings

### new-1. The notice's sender is the name `"framework"`

What happened: the design says the notice is "from the framework to the main session", and
`messages.from_agent` is `NOT NULL`. Why: no part names the framework as a sender. What I did:
`Mailbox` stores the notice from `"framework"`, a name no agent holds, since an agent's name
holds its project's (`app-…`) and `Grants` refuses a name it does not hold. What the design
should change: name the sender of the framework's own messages, or give a notice a `kind`
column as `Team.tla`'s `answers` has, so a reader does not tell it apart by a sender's name.

### new-2. A reply carries `is_error` as well as `subtype`

What happened: Claude Code's `result` has both, and a turn can end `subtype: "success"` with
`is_error: true`. Why: the brief names the subtype and says "so the main session can tell a
failed turn (`error_during_execution`, `is_error`)". What I did: stored both, `is_error` as 1, 0
or NULL. What the design should change: say "its result's subtype and `is_error`" in
"Messages", if that is what it means.

### new-3. A message an earlier build delivered may get a notice although it was answered

What happened: an earlier build's fold kept only the last result. A message whose result was
replaced there before `Mailbox` read it (F-79's new-3) loads with no result, and at its
process's next exit it is marked `exited`, so it gets a notice. Why: the earlier fold lost the
result; nothing can tell the two cases apart now. What I did: nothing more; the notice is then
the only word the main session gets about a reply that was lost, which is better than none.
What the design should change: nothing, unless such a notice must say it may be wrong.

### new-4. `docs/design.md` does not yet say the notice shares the reply's key

What happened: F-80's new-1 asked the design to say the notice is stored with `reply_to` set to
the message's uuid under the same unique index. "Messages" says "in place of the reply" only.
What I did: built it that way and left `docs/design.md` alone, as the brief names only this
note. What the design should change: add that sentence.
