# F-296: a heavy command may run on another host

## What was asked

F-280, F-291 and F-292 let another host take jobs and give it heavy slots of its own, but
`caf-run` still ran an agent's command on the workstation (F-292's new-1), so an agent's
`mix test` never used the second machine. This unit lets the app's list of heavy commands place
a match on another host, where it runs under that host's slot with its output streamed back and
its exit code the wrapper's.

## The shape

- **How the host is named.** By the app's entry, `%{match: ~r/\bmix test\b/, class: :heavy,
  host: "mac"}`, a host of the config's `hosts` or the workstation (`{:bad, :heavy, {:no_host,
  name}}` otherwise). The rewrite adds `--host 'mac'` to the wrapper's line; the wrapper sends
  its command and its directory with it. The plug runs the command there only when its own match
  of the command names that host, and refuses it `bad_host` otherwise, so a wrapper never names a
  host the app did not (as F-292 chose for the workstation's slot). An entry naming the
  workstation is the same as one naming none.
- **How the tree gets there.** Through `Jobs.run/6`, as any job's: the copy is the agent's own on
  that host (its project, the agent's name as the copy's name, as `Sessions.Agents.place/2`
  gives for services), synced from the agent's worktree before each run. The command runs as
  `sh -c <command>` at the wrapper's directory relative to the worktree (refused `outside` when
  the wrapper is not inside it), with the host's environment, not the agent's shell's. Nothing
  is fetched back.
- **The stream and the status.** The plug (`Runs.Remote`) runs the job in a process of its own
  and, once the job's row reads it running, sends `started on <host> (job run-<id>)`, then reads
  the job's log from an offset every second and sends each line as `o <line>` (text with no
  newline as `p <text>`, at the end or past 16 KiB). The wrapper prints the first on its errors
  and the rest on its output. The end goes only after the log's last line: `ended exit <code>`
  (the wrapper exits with it), `ended timeout` (124: the host ended the job at its timeout, an
  hour, `Runs.remote_timeout/0`), `ended unknown <reason>` (69), or a refusal (75, nothing ran).
  The job's output and its errors are one log, so both reach the wrapper's output.
- **The host away mid-run.** A failed log read is not an end: the reads go on, and once they
  have failed 30 s in a row the run ends `ended unknown host_away` and the wrapper exits 69 at
  once. The plug ends the run's process, which leaves the job's row owed (`Jobs`' rule for a
  caller gone). The job may still run there (away is a lost connection or a host asleep, not a
  host that ended its jobs), so its slot is freed once `Jobs` reads its end from the host, never
  before. A host away takes no new work meanwhile (`AwayRefusedAtOnce`), so the hold costs
  nothing until it answers again; `RemoteRun.tla`'s `Break_RemoteRun_FreeOnAway` shows a second
  job on the host's one slot when it is freed at the give-up. I read the brief's "its slot is
  freed" as this (see new-1).
- **The agent's Ctrl-C** (or Claude Code's own timeout) ends the wrapper. The plug's next write
  fails (a newline goes every 5 s with nothing else to send) and it ends the run's process: a job
  not started never starts, its request leaves the queue; one started runs on to its own end or
  its timeout, holding its slot, and its end is its row's. `Jobs` has no stop (new-2).
- **A cut stream.** A wrapper that got its `started` line and loses the stream exits 69 and
  never runs the command itself. Before that line, a wrapper with no answer behaves as before:
  it asks again for 30 s, then runs the command here without a lease.
- **No host**: nothing changes. The wrapper sends no command, and the plug's path is F-292's.

## What was built

- **The model first**: `model/tla/RemoteRun.tla`, a spec of its own as `HostSlots.tla` was:
  that spec's five requests would each grow by a log, a job and a row for no new check of its
  own. One other host with one slot, two runs; the job writes its log and exits whether or not
  the host answers; the plug streams, gives up while the host is away, is cut, or sees the agent's
  interrupt; `Jobs` settles an owed row. `RemoteRun_Design` checks `HostCapacity`,
  `NoRunUnleased`, `TrueCode` (a code only when the job exited with it), `WholeStream` (only
  after every line), and the liveness `WrapperEnds` and `SlotFreed`. Four breaks each fail:
  `FreeOnAway` (the give-up frees the slot while the job may run), `KeepSlot` (a run whose host
  went away keeps its slot: the give-up leaves the row to nobody), `ReportSuccess` (the give-up
  exits 0) and `CodeBeforeLog` (the end before the log's last lines). `HostSlots.tla`'s header
  names it.
- **`Runs`**: an entry may name `host:` (`heavy/1` answers `{regex, class, host}`); `place/2`
  answers the class and the host; the rewrite adds `--host`; the wrapper takes `--host`, sends
  `host`, `cmd` and `cwd`, prints the stream, and exits by the end line. One ask's bound with a
  host is its wait, the job's timeout and 300 s (`prepare/5`'s `:remote_timeout`). `ask/1` reads
  the three fields.
- **`Runs.Plug`** sends a wrapper with a host to `Runs.Remote`, with the options `policy:`,
  `jobs:`, `where:`, `remote_timeout:`, `away:` and `poll:`. Its body bound is 512 KiB, since a
  command now comes in it.
- **`Runs.Remote`**, the stream above. **`Jobs.row/2`** reads one row, so the stream knows when
  the job started without reading every row.
- **The tree** hands the plug its `Runs`, the `Jobs` server (looked up at each request) and
  `Sessions.Agents.place/2`. **`Config`** checks each entry's host.

| `Break_RemoteRun_CodeBeforeLog` | 141 | 6 | 1 s |

Code and docs apart from the model and the tests come to about 550 changed lines, 512 of them in
`apps/*/lib` with their docs, and `Runs.Remote` alone 250. I did not split anything out: the
host-away give-up and the interrupt are some 30 lines of the stream's own loop, and a remote run
without them waits up to an hour on a host away.

## Tests

`caf_surface/test/remote_host_test.exs`, on the stand-in ssh, with the wrapper written by
`Runs.prepare/5`, the rewrite of `Runs.pre_tool_use/2`, and `Runs.Plug` on a real port over the
tree's `Jobs`, `Hosts` and `Scheduler`:

- a command from a subdirectory of the agent's worktree runs in its copy on the other host: its
  output and its errors come back on the wrapper's output, in order,
  its code 3 is the wrapper's, its `started` line is on the errors, and its lease was that host's
  slot, held by the job's row and released at its end;
- a failing command exits 1 after its last line, one with no newline;
- the host going away mid-run ends the wrapper 69 within the plug's 1 s bound, with what had
  come; its slot is still held, and once the host is back and the job ends, `Jobs` settles the
  row `exited` and the slot is freed;
- a command with no host is rewritten with no `--host` and runs on the workstation as before,
  under the workstation's slot, with no job.

`config_test.exs`: an entry's host is the workstation or a declared host.

## What I ran into

- The stand-in host's `PATH` holds only the programs `Hosts` needs, so the tests' commands name
  `cat` by its path, and match `mix test` while the host has no `mix` (its complaint is part of
  the command's own output).
- This host's shell hook refuses some compound commands; edits went through the editor and
  script files.

## Findings

### new-1. The brief's "its slot is freed" meets the lease rule

What happened: the brief asks that a run whose host goes away end `unknown` and free its slot,
and that a Break config keep it. The design's lease rule is that a job's lease lasts until its
row holds the job's end (`Schedule.tla`'s `NoRunUnleased`), and a host away from the workstation
may still run the job.

What I did: the wrapper ends 69 at once, and the slot is freed once the job's end is read from
the host, never before. A host away takes no new work, so nothing waits on that slot until the
host answers, and then `Jobs`' next settle frees it. `Break_RemoteRun_FreeOnAway` shows what the
literal reading costs (two jobs on one slot once the host is back), and `Break_RemoteRun_KeepSlot`
is the break the brief asks for: a slot never freed.

What the design should change: nothing, I recommend. If the operator wants the slot freed at the
give-up, the job must be ended on the host by then, which needs new-2 and a host that answers.

### new-2. A started remote run cannot be stopped

What happened: the agent's Ctrl-C ends the wrapper, but `Jobs` has no stop, so a started suite
runs on to its end or its hour, holding the other host's slot.

What I did: the run's process is ended and the job runs on; its end is its row's.

What the design should change: I recommend `Jobs.stop/3`, which ends a held job's group on its
host (the wrapper's own pid, as its timeout does), for the plug to call when the wrapper is gone.

### new-3. An absolute path into the worktree does not reach the copy

What happened: agents often write `cd /abs/worktree/apps/web && mix test`. The command's text
runs unchanged in the copy, so such a `cd` fails on the other host.

What I did: nothing; the command runs at the wrapper's directory relative to the worktree, so
`cd apps/web && mix test`, or a call from that directory, works.

What the design should change: if it matters, the job could run with the worktree's path bound
to the copy's (a symlink on the host at the same path, or the text's prefix rewritten). Each is
a mechanism of its own to decide.

### new-4. A remote run prints no queued line

What happened: `Jobs.run/6` waits for its lease inside the call, so the plug cannot say the
run's place in the queue as the workstation's path does.

What I did: the wrapper prints `started on <host>` once the job runs, and nothing before.

What the design should change: if agents need it, `Jobs.run/6` could take a function it calls
with the `Scheduler`'s queued answer.

### new-5. Each read of the stream is one ssh connection

What happened: `Jobs.log/4` runs one ssh command per read, and ssh here opens a connection per
command (F-280's new-1). A remote run reads its log once a second, so a ten-minute suite costs
some 600 connections, beside `Jobs`' own wait on the host.

What I did: read once a second, not every 500 ms as first built.

What the design should change: if it is measured to matter on the Mac, a shared ssh connection
per host (`ControlMaster`), or a log read held open on the host (`tail -f` under one ssh), the
first being F-280's open choice.
