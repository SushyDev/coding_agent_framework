# F-229: a project never takes another project's checkout

## What was built

- **One owner per directory, across configs.** `Mains` opens `Mains.Table` before it checks its
  projects, and refuses its start `{:checkout_taken, path, other_project}` (as `start_link/1`'s
  `{:error, …}`, beside F-156's `{:same_dir, …}`) when a checkout row of this host names a
  project's path under another project. A project's own row, from an earlier start, is its own.
  The lookup is `Checkout.owner/3`, a pure function of the rows.
- **Check before adopting.** Each read of a checkout first runs `git config --get
  remote.origin.url` in it (`Checkout.git({:origin, path})`; the URL as written, not as
  `insteadOf` rewrites it) and compares it with the project's `origin` (`Checkout.same_origin?/2`:
  only the output's newline and a trailing `/` are trimmed, since git records a local origin as
  the absolute path given). Another origin, or none, ends the read before its `git worktree
  repair`, fetch or merge: the row reads `failed`, reason `{:origin_mismatch, path, found}`. A
  start or resume in it is refused `{:origin_mismatch, path, found}`, read at the start itself,
  so one sent right after `Mains` starts never runs in another origin's clone before the first
  read. Nothing clones over it or changes it; a person decides.
- **The design**: the Checkout entry says a directory has one owner on a home, and that `dir:`
  gives two origins of one name a directory each. The README status line names F-229.
- **The model**: `Checkout.tla` has `Taken` (an earlier config may hold the path), the variables
  `owner` (another project's row holds the path), `origin` (what is at the path is a clone of
  the project's origin or another's) and the ghost `foreign`, the guards `Owned` and `OriginOK`
  (in `Ready`, `CloneStart`, `RenameOld` and `Repair`), and the invariant `OwnCheckout`. New
  configurations: `Checkout_Taken` (the design with `Taken` and `Old`), and
  `Break_Checkout_NoOwner` (a second project adopts the path the first's row holds) and
  `Break_Checkout_NoOriginCheck`, each failing `OwnCheckout`. Every other Checkout
  configuration sets `Taken = FALSE`. `Made` and `CaughtUp` hold for a path that is the
  project's own (`<>[]Mine`), since a refused one is never made.
- **Tests** (`mains_test.exs`): two projects whose origins share a name are refused in one
  config, and `dir:` gives each its own; a later config on the same home naming a new project
  whose origin has the earlier project's name is refused by `Mains`, the earlier clone untouched,
  and `dir:` gives it its own while the earlier project still starts on its own; a directory at
  the path cloned from another repository reads `failed` with `origin_mismatch`, refuses a
  start, and a landing neither pulls nor changes it. The test helper `ready/2` now answers
  `{:not_ready, row}` for a row not `ready`: it passed `{:ok, row}` of any state, so `await`
  stopped at `cloning`. The new test found it; the one older use (the import test's wait for
  project `web`) may have gone on with a row still `cloning`, and now waits for `ready`.

## Findings

### new-1. A clone's temporary name is by the project's name, its removal by the directory's

What happened: `Mains.clone/2` clones into `Checkout.clone_path(home, p.name)`, while the start's
Recover removes `Checkout.clone_path(home, dir)` and the `Checkout` moduledoc says
`.<dir>.clone`. For a project whose `dir` differs from its name, a clone a restart cut stays as
`.<name>.clone` until that project's next clone removes it first. Why: F-156 moved the checkout
to its directory and the clone's temporary path kept the name. What I did: nothing; the clone
removes its own temporary path before cloning, so nothing is used half made. The design should
change: one name for the temporary path, the directory's, in both places.

### new-2. A rename of an old checkout does not read its origin first

What happened: F-156's rename moves `checkouts/<project>` to `checkouts/<dir>` when the project
has no checkout at its directory. A later config whose project has the same name as an earlier
one's but another origin would have the earlier clone renamed to its own directory; the read
after the rename then reads `failed`, `origin_mismatch`, so nothing uses it, but the directory
has moved. Why: the brief's check is before a checkout reads `ready`, and the rename comes
before that read. What I did: nothing beyond the brief. The design should change: the rename
reads the old checkout's origin first, and holds it `old` with that reason on another.

### new-3. A stale row holds its path for good

What happened: a project dropped from the config keeps its checkout row, so a later project
whose directory is the same is refused `checkout_taken` even when the directory is gone. Why: the
row is the record of the owner, and nothing releases it. What I did: nothing; the brief makes
the row the owner. The design should change: a person's act (an operator tool or a `bin/`
command) releases a project's row, recorded in `Acts`, so the refusal names what to run.

### new-4. A relative origin never matches

What happened: git records a clone's local origin as an absolute path, and `same_origin?/2`
compares the config's `origin` as written. A project whose `origin` is a relative path would
read `failed`, `origin_mismatch`, on its own clone. Why: the config's origin is not made
absolute anywhere. What I did: nothing; every config seen names an absolute path or a URL. The
design should change: the config refuses a relative local `origin`, or makes it absolute
against the config file.

### new-5. An intake test's 50 ms deadline can pass before it reads the row held

What happened: the first `devenv test` failed once in `caf_intake`, which this branch does not
touch: "at the deadline the response is empty, and a later decision is dropped" read the row
`expired` where it asserts `held` (`intake_tools_test.exs:223`), with the full gate's load on
the host. Why: the test starts the Intake with `tool_deadline: 50` and reads the row after its
`{:asked, …}` message, so a scheduler pause of 50 ms between the two lets the deadline settle
it first. What I did: ran the gates again; they passed, as did the three `gate-test` runs. The
design should change: nothing; the test should read the held row with a deadline that a pause
cannot reach (a long one, ended by the test's own clock), as F-224 gave the store's bounds a
slack.
