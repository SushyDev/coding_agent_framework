# F-97: `Delegate.tla` models the report a call takes; `Delegates` watches the waiting caller

## What was built

- `Delegate.tla` now models a `run_delegate` call that takes a report. The new constants are
  `Awaited` (the delegates a call waits on, once each) and `ClientLeaves` (the client may give
  up before the call's deadline). The report states gain `answering` and `answered`. The new
  steps:
  - `CallWaits`: the call starts.
  - `Taken`: before the call's `Deadline`, it marks the report `answering` and starts the
    watch.
  - `Written`: the write, with three outcomes. The agent gets it (`heard`); it fails; or it
    succeeds to a client that had gone (`lost`).
  - `Told`: `answered/2` or `release/2`. `TellLost`: the word that cannot reach `Delegates`.
  - `CallerEnds`, at any step, and `CallerSeen`: `Delegates` sees the end.
  - The start (`FrameworkStarts`) holds every `answering` report again.
- New properties:
  - `AnsweredNotSent` and `AnsweredStays`: a report is never both answered and sent as a
    message, and `answered` is final.
  - `AnsweredWasWritten`: answered only after a write that succeeded.
  - `TwiceOnlyIfUnsure`: the agent has a report both ways only after an `answering` report was
    held again by the caller's end or a restart.
  - `ReportArrives` now reads: answered (`heard`) or delivered, at least once, except `lost`.
  - `ReportArrivesUnderCap` has no exception. It is checked with `ClientLeaves` false and no
    parent stop.
  - `EndsAfterDelivery` and `DeliveredDelegateEnds` accept `answered`.
- New configurations:
  - `Delegate_Answers.cfg`: one delegate, a call, a client that may leave, a restart, a
    parent stop.
  - `Delegate_Cap.cfg`: the cap, two restarts, no parent stop.
  - Six Breaks, each failing as meant: `TakeLeavesHeld` (`TwiceOnlyIfUnsure`),
    `TakeAfterDeadline` (`ReportArrives`), `AnsweredOnFailure` (`AnsweredWasWritten`),
    `AnsweredFromAny` (`AnsweredNotSent`), `NoCallerWatch` (`ReportArrives`), `NoRestartHold`
    (`ReportArrives`).
  - The existing configurations set `Awaited = {}` and `ClientLeaves = FALSE`, so they check
    what they checked before.
- `READING.md` describes the new steps and the exception.
- `Delegates` monitors the process that waited in `await_report/4`. The monitor starts at the
  take, in both places a take happens: a report already held, and a waiter answered when the
  report is held. `answered/2` and `release/2` drop the monitor. On `:DOWN`, an `answering`
  report is held again, with its mark, as `release/2` does. A caller that ended before the take
  is seen at once, since a monitor of a dead process answers `:noproc`. The docs of the module
  and of `await_report/4` say the caller must settle from the process that waited. `MCP.answer/5`
  already does: `act` and `settle` run in the plug's process.

## What I ran into

- The take is its own step in the model. In the code, `Delegates` takes a report in the same
  step that holds it. The model's order is one of the orders the code allows, and more. The
  header says so.
- Two existing tests took the report in a `Task` that ended at once, then called `answered/2`
  or `release/2` from the test process. With the watch, the `Task`'s end holds the report again
  first. The tests now use a caller like `MCP`'s: one process waits, then settles, then ends.
- To kill a caller while it waits, the test must know its wait has reached `Delegates`. A wait
  of 0 ms answers `:awaited` once another call waits, and never waits itself, so the test polls
  with that.
- The hold and the take are one step of `Delegates`, but they are two writes to the table. A
  test that polls the table can see `held` between them. The new test reads `held/2`, the
  process's own answer, instead.

## Findings

### new-1. A parent whose process ends during a `run_delegate` call loses the answer, even under the cap
What happened: `Delegate_Cap` with one parent stop fails `ReportArrivesUnderCap`. The trace:
the report is taken, the parent's process ends, the write succeeds, and the report is
`answered`. No one reads it, and it is never sent as a message. Why: a process that ends closes
its sockets. When it ends normally, the kernel sends FIN, and F-95 measured that a write then
succeeds. The cap only keeps the client from giving up by its own limit. A move or an exit of
the parent is a second way for the client to go. What I did: the model shows it as `lost`,
the one exception of `ReportArrives`. I built nothing more. What the design should change: the
design says the cap is what keeps the client from going first. It should also name the
parent's process ending during a call. Then decide whether that loss is accepted (the report
stays in its row and in the call log, where the read tools find it), or guarded. Two possible
guards: a move that waits for no `answering` report of its parent, or `answered` only after
`Parents` says the same process still runs.
