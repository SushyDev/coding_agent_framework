# F-24: how hook events reach the framework, and `Intake.tla`

Research and the model only; no Elixir code.

## The source

I read the devenv Claude Code 2.1.322 (`$CAF_CLAUDE`, a wrapper around
`bin/.claude-wrapped`, 324 MB): its `--help`, and the strings of the binary. The strings hold
the built-in hook documentation, the `/hooks` event table, the settings schema (zod, with its
descriptions) and the minified code. No session was started, and no credential or person's
config directory was read. Quotes below are from the strings unless marked `--help`.

**Hook kinds.** The event list is PreToolUse, PostToolUse, PostToolUseFailure, PostToolBatch,
Notification, UserPromptSubmit, UserPromptExpansion, SessionStart, SessionEnd, Stop,
StopFailure, SubagentStart, SubagentStop, PreCompact, PostCompact, PreModelSwitch,
PostModelSwitch, PermissionRequest, PermissionDenied, Setup, TeammateIdle, TaskCreated,
TaskCompleted, Elicitation, ElicitationResult, ConfigChange, WorktreeCreate, WorktreeRemove,
InstructionsLoaded, CwdChanged, FileChanged, DirectoryAdded and MessageDisplay. From the
`/hooks` table:

- Every input has `session_id`, `transcript_path`, `cwd`, `prompt_id` ("Absent until the first
  user input"), `permission_mode`, `agent_id`, `agent_type` and `hook_event_name`.
- SessionStart: "session start source", matcher `startup`, `resume`, `clear`, `compact`,
  `fork`. SessionEnd: "session end reason", `clear`, `resume`, `logout`, `prompt_input_exit`,
  `other`.
- Stop: "Right before Claude concludes its response". StopFailure: "Fires instead of Stop when
  an API error (rate limit, auth failure, etc.) ended the turn. Fire-and-forget".
- SubagentStart: `agent_id`, `agent_type`. SubagentStop: also `agent_transcript_path`.
- Notification: "notification message and type", types including `permission_prompt`,
  `idle_prompt`, `agent_needs_input`, `agent_completed` and `elicitation_dialog`.
- UserPromptSubmit: the prompt text. PreToolUse and PostToolUse: the tool's input, and its
  response after.
- PermissionRequest: "When a permission dialog is displayed. Input to command is JSON with
  tool_name, tool_input, and tool_use_id", with `permission_suggestions`. PermissionDenied:
  "After auto mode denies a tool call".

**How a hook reaches its handler.** Hook types are `command`, `prompt`, `agent`, `http` and
`mcp_tool`. A command gets the input JSON on stdin, runs through bash (or by argv with `args`),
and answers by exit code and stdout. An `http` hook is "URL to POST the hook input JSON to", with
`headers` that may name environment variables listed in `allowedEnvVars`. Its response body is
the hook's JSON output. A managed `allowedHttpHookUrls` can block a URL; nothing sets it here.
"agent-type hooks are not supported for PermissionRequest events ... Use a command- or http-type
hook instead."

**Timeouts.** Each hook may set `timeout` in seconds. With no `timeout`, a command or http hook
gets 600000 ms (`var Cu=600000`, used as `e.timeout?e.timeout*1000:Cu`). At its timeout the hook
is aborted and counts as canceled, which gives no decision. SessionEnd hooks share a budget
of `SESSION_END_HOOK_TIMEOUT_MS_DEFAULT` = 1500 ms. A hook's own `timeout` raises it, up to
60000 ms, and `CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS` can set it.

**What a failure does.** `onFailure`: "it could not start (a missing script or plugin
directory), timed out, exited with a code other than 0 or 2, or printed JSON that is invalid
... 'continue' (default): the failure is reported and the action goes ahead. 'block': the
failure counts as exit code 2". An HTTP error is logged as "Hooks: HTTP hook error" and counts as
a non-blocking failure. Claude Code does not retry a hook; no retry path appears in the hook
runner. Hooks are skipped until the workspace is trusted (`shouldSkipHookDueToTrust`), and by
`--bare` (`--help`: "skip hooks").

**How a PermissionRequest answers.** Output: `hookSpecificOutput: {hookEventName:
"PermissionRequest", decision: {behavior: "allow", updatedInput?, updatedPermissions?} |
{behavior: "deny", message?, interrupt?}}`. The error text says: "PermissionRequest decision
must be {"behavior": "allow"} or {"behavior": "deny", "message": "..."}". "Exit code 0 - use
hook decision if provided". A deny with `interrupt` aborts the turn. "Don't ask again" is an
allow with `updatedPermissions`. A plain deny is "No"; the message goes to the model.

**How long it waits, and the race.** In the interactive permission path the dialog is
shown, and in the same call these all start, each racing for one claim (`if(!q||!I())return`):
the Remote Control bridge, channel relays and the PermissionRequest hooks (`r.runHooks(...)`).
The first answer closes the dialog. A later one finds the claim taken and is dropped. The hooks
run under the turn's abort signal (`n.abortController.signal`), not the dialog's, so a person's
answer does not end a waiting hook. A hook that fails, times out or gives no decision returns
null, and the dialog stays for a person.

**When the handler is gone.** A refused POST or a command that cannot reach the framework is a
non-blocking failure under `onFailure: "continue"`: the event is lost, and for a
PermissionRequest the dialog stays on the screen.

## What was built

- **`docs/design.md`**: a section "Intake", and a line for `Intake.tla` in "The model". The
  recommendation is one `http` hook per event read, to `127.0.0.1` on the framework's node. No
  helper program is needed on the host, and a held hook is one open request. The command and
  file transports each need a program `Programs` does not have (a client for a socket, or `mv`
  for whole files), and a file cannot carry an answer back.
- **`model/tla/Intake.tla`**: events posted (twice, or while the framework is down), stored,
  then acknowledged. Numbered dialogs open one at a time, each with its hook held, answered,
  expired by the framework's own deadline, or cut by a restart. A person may answer first.
  Invariants: `AckedIsStored`, `StoredOnce`, `SentAtMostOnce` (defense in depth),
  `OnlyNamedDialog`, `AnsweredWasHeard`, `NeverTyped`. Liveness: `RequestsEnd`, `HoldSettles`.
- Seven `Break` values, each with a configuration TLC fails: `AckBeforeStore`, `NoDedupe`,
  `ByAgent`, `NoOwnDeadline`, `NoExpiry` (liveness), `TrustAnswering`, `TypeWhenNoHold`.
- `Intake_Events.cfg` and `Intake_Holds.cfg` in the gate, `slow/Intake_Large.cfg` by hand.
  `model/tla/READING.md` has a section on the spec.

## Measured

With `TLC_WORKERS=2` on a busy laptop:

- `Intake_Events`: 20,844 distinct states, depth 23, 8 s.
- `Intake_Holds` (three dialogs, one restart): 39,074 distinct states, depth 24, 15 s. With two
  restarts it was 82,440 states in 25 s, too close to the 30 s bound for the gate.
- Each `Break_Intake_*`: under 70 states, 2-3 s.
- `slow/Intake_Large` (one event posted twice, three dialogs, two restarts): 230,750 distinct
  states, depth 29, 123 s. A
  first try with two events and three restarts passed 1 million distinct states in 10 minutes
  and was stopped: the two halves of the spec multiply.

## What I ran into

- The binary's strings mix documentation and minified code, so a default is read from code
  (`Cu=600000`), not from a sentence. A later release may change it, so the hook sets its own
  `timeout` and does not lean on the default.
- In the design, `HookTimesOut` never fires, since its guard puts the framework's deadline
  first. That ordering is an assumption about the clock, and `NoOwnDeadline` shows what breaks
  without it.

## Findings

### new-1. A hold that a restart lost leaves the dialog to a person

What happened: Claude Code posts a PermissionRequest once. When the node restarts, the request
ends, and Claude Code never posts it again for that dialog.

Why: the hook runs once per dialog, and its failure leaves the dialog on the screen.

What I did: the design marks the row "lost" and lets a person answer. It does not type keys.

What the design should change: say whether an agent may answer a lost hold by typed keys
through `Control`'s checked write, confirmed by the dialog's label (the rule for typed
answers). I recommend no: refuse with `{:refused, :hold_lost}` and ask a person.

### new-2. An answer cannot tell whether a person answered first

What happened: a person's answer closes the dialog but leaves the hook waiting, and the hook's
later answer is dropped with no sign the framework can read.

What I did: `answer` returns `{:ok, :sent}` in the design.

What the design should change: name the reader that confirms a sent answer: a PostToolUse with
the dialog's `tool_use_id` for an allow, or the transcript for a deny. That means reading
PostToolUse, or reading the transcript after each answer.

### new-3. HTTP to 127.0.0.1 reaches only the node's own host

What happened: a session on a remote host posts to its own 127.0.0.1.

What the design should change: for a remote host, an ssh reverse forward of the port, held as
part of that host's connection; or a remote host's sessions run with no held hooks and say so.

### new-4. A row's key for events with no id of their own

What happened: Stop, Notification and SessionEnd carry no event id. Two identical posts of one
of them cannot be told from two events.

What I did: the design keys rows by Claude Code's ids where they exist, and leaves the rest to
the readers, which move their rows forward once.

What the design should change: confirm that no part counts Stop or Notification rows, so a
duplicate is harmless.
