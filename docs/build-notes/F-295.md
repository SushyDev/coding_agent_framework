# F-295: a prompt's answer is cued after its row settles, and its closer is never guessed

## Why

An embedding app reads the inbox on each `prompts` cue. Since F-289 the `Mailbox` answers a
call and cues at once, and `Prompts.answer/5` settles the answer's row in `Acts` only after the
owner's call returns. So the inbox read the `Mailbox`'s cue, found the ask gone, and cued; the
app read on that cue, found the prompt gone and no settled answer, and showed it closed. No later
cue came. The app's builder also read F-270's code and thought the `closed` fact, written once,
could be written with a guessed closer in that same window.

## Confirmed first, on main (8d8dfd9)

Two stand-in tests in `apps/caf_prompts/test/prompts_test.exs`. `SlowSettle`, a process in
front of the test's `Acts`, holds the caller's settle (`Acts.answered/4`) until the test lets it
go, and passes every other call straight on. So the inbox reads the `Mailbox`'s cue before the
row settles, as on a loaded host. Each test answers one ask and withdraws another.

- "a reader on each prompts cue finds an ask answering, then answered: never only gone". On
  main, the read on the `Mailbox`'s cue gave `read/3` `{:ok, []}`, and `answered/3` gave the ask
  `status: "closed", by: {:framework, :ended}` (`d1` has no agent row; an app with one gets
  `{:framework, :passed}`). After the settle no `prompts` cue came: the test failed at "no
  prompts cue". **Confirmed.**
- "the closed fact of an ask answered names its answerer, whenever its row settles". On main
  the facts were `%{"ask:1" => ["framework", "ended"], "ask:3" => ["framework", "ended"]}` for
  an answer and a withdrawal that `sam` made. The fact is keyed once, so the record stayed wrong
  for good. **Confirmed:** the builder's reading was right. The inbox's read on the owner's cue
  found the prompt gone with its answer row still `claimed`. `taken/1` saw no taken row, so
  `closer/2` fell back to the owner's row, and an ask's owner row names no one.

Both cases are one cause: the inbox treated "gone from its owner" as "closed" while the answer
that made it go was still open in the ledger. It is not only the `Mailbox`: an `Intake` hold or a
dialog's press also leaves its owner before `answer/5` settles the row.

## The model

`model/tla/Inbox.tla` (new): one ask. The caller of `answer/5` claims the row, hands the answer
(the owner lets the prompt go and cues), settles the row, then cues. The inbox reads on a cue,
the reader reads on a `prompts` cue, a page of closed prompts runs, and the inbox may restart
(losing what its last read listed and its pending reads). Properties: `NeverOnlyGone` (the
reader's card is never gone, nor closed by anyone else), `FactNamesAnswerer` (the fact, once
written, names the person), and `ReaderSeesAnswered` (liveness).

| configuration | result |
| --- | --- |
| `Inbox_Answer` (2 restarts) | ok, 249 distinct states, 2 s |
| `Break_Inbox_CueBeforeSettle` (main's listing) | NeverOnlyGone violated |
| `Break_Inbox_FactBeforeSettle` (a page writes while the row is open, past a restart) | FactNamesAnswerer violated |
| `Break_Inbox_NoCueAfterSettle` (no cue after the settle, the ledger's cue not wired) | ReaderSeesAnswered violated |

`Prompt.tla`'s header now points to it for the inbox's reads. No other spec changes.

## What was built

In `apps/caf_prompts/lib/coding_agent_framework/prompts.ex` only:

- **`answering` until the row settles.** `list/1` also lists each prompt that the last read
  listed (`seen`) and that has left its owner while its answer's row is `claimed` or `acted`,
  with no taken row, as `answering`. A read on the owner's cue cues it moved `open` to
  `answering`. `answer/5` refuses it `{:refused, :settled}`, as it refuses any `answering`
  prompt.
- **No fact while the row is open.** `closer/2` answers `:settling` when the prompt's answer
  rows hold an open one and none taken. `close/3` then writes nothing and the prompt stays in
  `seen`. This covers the live read and `answered/3`'s late path.
- **The cue once the row settled.** After `Acts.answered/4`, `answer/5` casts `{:settled, id}`
  to the inbox. That read lets the prompt go and writes its fact with the answer's actor. Then
  `answer/5` calls `notify` with `%{topic: "prompts", ids: [id]}` from the caller's process, so
  a restart of the inbox cannot lose the cue. The `{:settled, id}` read leaves `id` out of its
  own cue, so the settle gives one cue, not two. A refused answer cues nothing.
- **Past a restart of the inbox,** a prompt whose row is still open is not listed (its `seen`
  is gone). `answered/3` shows it `status: "answering"`, with the row's `by`, `at` and `choice`,
  and writes no fact.

The module doc, `answered/3`'s statuses, `list/1`'s doc, `docs/design.md`'s prompts paragraph
and the README's status list say so.

The app's own cue after the call, its stopgap, is no longer needed. It does no harm.

## Findings

### new-1. An interrupted answer row still leaves the closer to a guess

What happened: if the caller of `answer/5` ends between the hand and the settle, its row stays
`claimed` and the prompt reads `answering`. At the next start, `Acts` closes the row
`interrupted`. Then the prompt is gone with no taken row and no open one, and `closer/2` falls
back to the owner's row. For an ask, that is `{:framework, :passed}`, though the answer was
most likely this row's.

Why: `taken/1` counts only `verified` and `unknown` outcomes. An interrupted row has no
outcome.

What I did: nothing. It needs a caller to die in a window of one call, and the brief kept the
fix to rows that settle.

What the design should change: an interrupted `answer` row of a prompt that left its owner
should read as `unknown` by its actor, as a row settled `unknown` does, not as no answer.

### new-2. What the inbox listed is in its memory

What happened: `answering` depends on `seen`, the inbox's last read, which a restart of the
inbox loses. Past a restart, `read/3` does not list a prompt whose row is still open.
`answered/3` shows it `answering` and writes nothing.

What I did: modeled it (`Inbox.tla`'s Restart). The caller's own cue is what keeps
`ReaderSeesAnswered` true across a restart. The fact of such a prompt, once its row settles,
is not written by a read, because no read listed it. Its answer row names the closer, so
`answered/3` reads it right without a fact.

What the design should change: nothing for the reader. If every closed prompt must have a
`closed` fact, the inbox's first read after a start could seed `seen` from the open `answer`
rows. That is one query over `Acts` per start.

### new-3. `notify` is now called from `answer/5`'s caller

What happened: the cue after the settle is called in the caller's process, not the inbox's, so
that a restart of the inbox cannot lose it.

What the design should change: say that a part's `notify` may be called from any process. The
`Cues` function the tree passes already allows it.
