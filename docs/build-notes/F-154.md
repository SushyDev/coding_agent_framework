# F-154: app tools on the agents' MCP endpoint, and app metadata on an agent

What an app needs to run its own main session on the framework: a few tools of its own for its
agents (G1), and its own facts kept on an agent (G2). G1 is the start of the extension
mechanism (B12, "Extensions"), so it is built in that shape.

## What was built

**App tools (G1).**

- `CodingAgentFramework.Extension` (in `caf_grants`, a pure module): the app's bundles, each
  `%{name, scope, tools}`, checked whole by `check/3`. A bundle's name is 1 to 16 lowercase
  letters and digits, never a framework tool's name nor a prefix of one (`service` would take
  `service_stop`). A tool is `%{name, description, schema, call, scope, timeout}`: its name is
  the bundle's, `_`, and more, so it never clashes with a framework tool or another bundle's;
  its schema is an object's; `call` is a function of the caller's name and the arguments; its
  `timeout` is at most the endpoint's deadline. A key the check does not know is refused by
  name (`{:unknown_key, :skill}`), so B12 adds `skill`, `context`, `events` and `guards` here
  and nowhere in `MCP`.
- `Extension.run/4` calls a tool's function in a process linked to the caller and answers its
  own outcome, or `{:unknown, {:crashed, text}}`, `{:unknown, {:bad_answer, text}}`, or
  `{:unknown, {:timeout, ms}}`, when it is killed so nothing of the call runs on.
- **Scope**, by role (`:main`, `:delegate`) and project, on the bundle and narrowed on a tool:
  `Grants.may_call?/3`, answering `:ok` or `{:refused, :out_of_scope}`; the operator may call
  every tool. `Grants`' tree now keeps each agent's project.
- `MCP`'s `extensions:` option, checked at start (it stops on the first refusal); `MCP.tools/2`,
  the list one agent sees (the framework's, then the app's its scope holds), which the
  endpoint's `tools/list` now answers per caller, and `reload` names too. A call of an app's
  tool goes through `MCP.answer/5` as any other: written `called`, the scope checked, the
  function run within its deadline (its `timeout`, else `:tool_timeout` less `:margin`, the
  bound every tool call already keeps under the client's), and written `answered` with its
  outcome.

**App metadata (G2).**

- `agents.meta`, a column added to an earlier file (`Sessions.Table`): a map of the app's own
  keys as canonical JSON (`Table.meta_text/1`, at most 64 KiB, else `{:refused, {:bad,
  :meta}}`).
- `Sessions.start/5`'s `meta:`; a start that names none keeps the row's, so a resume, a move's
  resume and a declared main session's start keep what the app set. `Sessions.put_meta/4` sets
  it later, in place of what it had; no tool reaches it, so no agent sets it.
- `Delegates.start_delegate/7` and `Mains.start_main/5` take `meta:` and hand it to the start.
  Through the endpoint, `start_delegate`, `run_delegate` and `start_main` take `meta` from the
  operator only; an agent's call that names it is refused `{:operator_only, :meta}`.
- `Sessions.Agents.meta/1` reads it back as JSON gives it (string keys), `%{}` for none. The
  `Tracker`'s source of `agents` carries the column, as it carries every column of the table's
  metadata. The tree's entries (what `agents()` shows the agents) do not carry it.

**Tests.** `apps/caf_mcp/test/mcp_extensions_test.exs`: a tool scoped to main sessions is
listed and callable by the main session and absent and refused for its delegate; a tool of
another project is neither; the caller is the token's agent, whatever the arguments say; a
refusal, a crash, an answer that is no outcome and a deadline passed are each an explicit
outcome, each a row, and the late call's process is gone; a clashing, misnamed, unknown-keyed
or too slow bundle stops `MCP` at start with its reason; a start's `meta` is the operator's
only. `apps/caf_tracker/test/agents_source_test.exs`: meta given at a start is read back through
`Agents` and the `Tracker`'s source, a bad one is refused, `put_meta` replaces it, and a later
start that names none keeps it. Doctests for `Extension`, `Grants.may_call?/3`,
`Table.meta_text/1` and `Agents.meta/1`.

**The model.** No spec changes. An app tool's call is a tool call as the others are: one row
written before it acts and settled after, no claim (it fixes no agent's state), and the same
bound under the client's tool timeout. No spec models `mcp_calls`. The metadata is a column its
one writer sets; nothing reads it to decide anything.

## What I ran into

- `MCP.tools/0` was the one list every agent saw. A list per caller needs `MCP`'s context,
  so `tools/2` asks the process for it and filters in the caller's process, since
  `Grants.may_call?/3` reads the tree, and `MCP`'s process should not wait on a read.
- A tool's crash reason is often an exception struct, which `MCP.json/1` cannot turn into JSON
  (a struct is not enumerable). `Extension.run/4` answers the exception's message as text.
- `Extension.run/4` links the call's process to the caller, so a request cut by its client
  ends the call too; at the deadline it unlinks first, then kills, so the caller lives on.

## Findings

### new-1. The design says one verb per extension; the app needs several tools in one

What happened: the brief asks for a list of tools under the app's extension name, each named
under it. "Extensions" says an extension brings "one verb at most, its acts as an option".
Why: today the agents see 25 tools, not seven verbs (B5 is not built), and the app's next unit
needs a few tools at once.
What I did: a bundle holds a list of tools, each named `<bundle>_<act>`, and wrote the
departure into "Extensions".
What the design should change: at B5, fold a bundle's tools into its one verb, each tool an
act (`board(act: :cards, …)`), its schema that act's options and its function that act's
function. The app's config then changes only in shape, not in its functions. Or the design
allows several tools per bundle, and B5's count is "7 verbs and the extensions' tools".

### new-2. A tool's schema is handed to the client, not checked

What happened: the framework has no JSON Schema validator, so an app tool's arguments reach
its function unchecked; Claude Code checks some of the schema on its side, not all.
Why: no package for it is among the dependencies, and the framework's own tools check their
arguments by hand.
What I did: the module doc says `call` checks what it is given.
What the design should change: B12 decides whether `Team.operate/4` checks an extension's
arguments against its schema (a validator package, the refusal `{:bad, :args}` as for the
framework's tools) or leaves it to the extension.

### new-3. A tool past its deadline is killed with its work unknown

What happened: at its deadline a tool's process is killed and the call answered `{:unknown,
{:timeout, ms}}`. What the function did before the kill is not known to the framework.
Why: a function of the app's can do anything; the framework cannot settle it by evidence.
What I did: nothing beyond the explicit outcome and its row.
What the design should change: B12 says whether an extension's act that changes state outside
(a card moved, a comment posted) takes a claim in `Acts` and is settled by the extension's own
evidence, as a fix is, or whether an extension's act must be idempotent by its key.

### new-4. The metadata is shown in the source, not in the tree

What happened: the brief asks for meta "shown by the `Tracker`'s source". The source carries
every column, so it carries `meta` as JSON text; the tree the `Tracker` folds, which `agents()`
answers to agents, does not.
Why: the metadata is the app's; an agent need not see it, and the framework never reads it.
What I did: left the tree as it is; an app's view reads `Agents.meta/1` of the source's row.
What the design should change: item 16's "app metadata" says whether an agent may see the
app's metadata on its tree (`look`), or only the app.

### new-5. F-165's end-time test raced its own `Sessions`

What happened: the first `devenv test` failed one test, `AgentsTest`'s "a row's end time is
its first done status's" (F-165): its row, written `starting` straight into the table, read
`refused` with reason `interrupted`. It passed eight runs out of eight alone.
Why: the test's own `Sessions` runs while it writes. Its rows had no deadline, so a settle on
any cue (the sampler's, the registry's) took a starting row as past its deadline with no
process and gave it up, as `Start.tla` says it should.
What I did: the test's rows (that one and the migration test's) take a deadline ten minutes off,
so only the test writes them. No code changed.
What the design should change: nothing. A test that writes a writer's table behind its back
should keep the rows out of the writer's settle, as these now do.
