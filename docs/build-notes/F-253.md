# F-253: a tool call's own duration

## What was built

- `Intake.Event` knows `PostToolUseFailure` and posts both post-tool events always. `Intake.hooks/4`
  now writes `PostToolUse` and `PostToolUseFailure` for every account, not only with a callback.
- A post-tool row keeps `data` as `tool_name`, `tool_use_id` and `duration_ms`. With the
  `post_tool_use:` callback the row is held as before; without one it is kept, not held, and the
  post is answered at once (before: no row).
- `Tracker.Tree.tool_calls/3` reads those rows from the view's `:events` by `tool_use_id` and gives
  each call `duration_ms`, or nil with no row. `ms` is unchanged. A subagent's calls match the same
  way, since a `tool_use_id` is unique.
- `docs/design.md`, the README status line and the tests are updated.

- The rows are bounded. `Intake`'s `tool_rows_keep:` (ms, 7 days by default, per instance) is how
  long a `PostToolUse` or `PostToolUseFailure` row stays. The intake has no timer for it, so the
  sweep runs at a post, at most once a minute (the first post sweeps), and deletes the older
  rows of those two events only. No new process, no global state. 7 days because the tree reads
  durations for recent calls: an older call keeps `ms` from its transcript, and its `duration_ms`
  becomes nil.

## What was measured

Read only from the 2.1.322 binary (no live body was run). `PostToolUse` carries `session_id`,
`cwd`, `transcript_path`, `hook_event_name`, `tool_name`, `tool_input`, `tool_response`,
`tool_use_id` and `duration_ms`. `PostToolUseFailure` carries the same without `tool_response`, and
with `error` and `is_interrupt`. Both name the call by `tool_use_id`, the id the transcript's
`tool_use` block has.

## What I ran into

- The brief says the intake already receives these hooks. It did not: `PostToolUse` was posted only
  with a callback (or `stop:`) and, with no callback, dropped without a row; `PostToolUseFailure`
  was an unknown event.
- The tracker tests build the view and the fold by hand, as the file's other tests do, not on the
  stand-in; the intake tests post real bodies through the plug.

## Findings

### new-1. Every tool call writes an `intake_events` row

What happened: with the hooks always on, each call adds one row, and the table had no bound. Why:
the row is the only place the call's own time is kept. What I did: `tool_rows_keep:` and a sweep
(see above). What the design should change: nothing more for these rows; other events' rows are
still unbounded.

### new-2. A row with the hook's body lost has no `duration_ms`

What happened: a hook post that fails (framework down) leaves the call with `duration_ms: nil`. Why:
`onFailure` continues by design. What I did: nil, never `ms`. What the design should change:
nothing; the app shows "unknown".
