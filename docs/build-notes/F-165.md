# F-165: a brief queued after its agent ended is settled `ended` too early

## What was built

- **The agent row keeps its end's own time** (`ended_at` on `agents`, wall-clock ms). The write
  that first gives a row a done status (`refused` or `ended`, `Sessions.Table.done/0`) stamps
  it. A later write keeps it, whether it is done again or carries no status. Any other status
  clears it, and so does a new start (`Table.starting/2`). The column is added to a file an
  earlier build made, and `Table.open/1` gives each done row there its `updated_at`, the best
  time such a file kept. Only `Table.update/3` stamps it, so every path that ends a row
  (`Sessions.ended/3`, `end_main/3`, the settle, the migration's hand-over) gets it.
- **`Mailbox` reads "since the end" from that time**, never from `updated_at`, which every
  write to the row moves. A queued brief stored before the end's own millisecond is the ended
  start's, and is settled `ended`. A brief stored in that millisecond or after is a later
  start's, and waits. Before this unit the check was `created_at <= updated_at`. A message to
  an ended agent is settled `ended` as before. An end with no time yet ends no brief: that is
  a file an earlier build wrote, read before `Sessions` opened it.
- **Tests.** `mailbox_test.exs`, "a brief stored since the end waits, whatever writes the agent
  row after it", ends a delegate through `Sessions`. It then stores a later start's brief and
  gives it the end's own millisecond. It writes the agent row again (`parent` and `project`, as
  the migration's hand-over writes them to a row that ended). It sends a message, and waits
  until the message is `ended`. The brief is still `queued`. A brief stored a millisecond
  before the end is settled `ended`. `agents_test.exs`, "a row's end time is its first done
  status's, kept by later writes", covers the stamp, the keep, the open of an earlier file and
  the clear.

## What was measured

Which reading was right, found on purpose. I instrumented the failing test,
`mailbox_test.exs:71`, to print the brief's `created_at` minus the agent row's `updated_at`
for the brief "Again.". I ran it alone 11 times. The gap was 1, 3, 4, 4, 3, 3, 2, 1, 1, 1 and
2 ms. Nothing writes the row after its end in that test: `Sessions` settles no `ended` row, and
`Sessions.ended/3` answers an `ended` row without writing it. So the failure is the first
reading at its narrowest: a brief stored in the same millisecond as the end reads as stored
before it, because the check was `<=`. A 0 ms gap is one step from what a run alone shows.
The same check also ends a later start's brief whenever anything writes the row after its end.
In use that means the migration's hand-over (`adopt_tree`, which writes `parent` and `project`
to a free row, `ended` ones too).

The new Mailbox test, run against the old `Mailbox` with the new `Sessions.Table`, fails at
its `queued` assertion. With the fix it passes. The instrumentation was not kept.

## What I ran into

- **`Delivery.tla` does not say it either way.** In it an addressee's end (`over`) lasts for
  good, and `EndedFirst` ends every due row to it. No later start of an ended name exists in
  the spec, so the rule "a brief stored since the end waits" is code with no spec behind it.
  It came in with F-129. This unit changes only which time the code reads, not the protocol,
  so I left the spec as it is and report the gap (new-1).
- **Two millisecond clocks cannot order events in the same millisecond.** The tie goes to the
  later start (`<`). A later start's brief can follow the end within a millisecond: the test
  above does it in 1 ms. The other case would be a start's own brief left unsent and its start
  ended in the same millisecond, and that cannot happen. A start spawns processes first, and
  a refused start's brief is settled by `Mailbox.ended/3`, by name, when Delegates sees the
  refusal.

## Findings

### new-1. No spec has a later start of an ended agent, and the code orders it by a clock

What happened: a later start's brief, stored after its agent ended, was settled `ended` when
it was stored in the end's own millisecond. It would also be settled `ended` after any write to
the agent row past the end.
Why: `Mailbox` tells a later start's brief from the ended start's by comparing two wall-clock
times. `Delivery.tla` has no later start of an ended addressee (`over` is final), so nothing
checks the rule.
What I did: the code now compares against the end's own time (`ended_at`), breaks the tie
toward the later start, and has tests for both cases. I did not change the spec.
What the design should change: model it in `Delivery.tla`. An addressee may start again after
its end (`over` cleared by a new life). Each row keeps the addressee's end count when it is
stored. `EndedFirst` ends only a row stored before the latest end. Add a property that a row
stored since the latest end is never `ended` by it, and a `Break` that ends one. Then the code
could follow the spec by order, not by clock. `Mailbox` stores the brief, so it could record
on the row, at store time, whether the agent row was done. That read sees the end whenever the
end was written before the brief was stored, as it is when one part asks for both in turn. I
did not check that Delegates and Mains always do.
