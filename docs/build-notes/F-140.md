# F-140: startup dialogs: read, shown to a person, answered by them

Any session the framework starts interactively can stop before its first turn on Claude Code's
folder trust dialog, or on "Allow external CLAUDE.md file imports?" when the project's
`CLAUDE.md` imports a file outside its folder. Neither sends a hook event, and on 2.1.322 no
session file exists while either is shown (measured by the main session), so `Registry` saw
nothing, and two sessions sat on the imports dialog for 17 and 42 hours, holding their slots.
F-137 answered the trust dialog by itself in a worktree start; this unit makes every startup
dialog a person's to answer, unless the app chooses otherwise.

## What was built

- **The model first: `Dialog.tla`**, a small spec of its own (about 300 lines; `Start.tla` is
  already 930). One start's program shows the dialogs in order (`TrustThenImports`, 2.1.322's
  order), a person at the viewer may answer at any step, `Sessions` reads the pane while the
  row has no session file, the app's callback answers the kinds in `Auto`, a person's answer is
  taken, marked `pressing`, then pressed by the `Inlet` in one checked step (sent, or unknown
  and landed or not), the start's deadline reads the pane in the same step, `Recoveries` ends an
  orphan, a restart loses the call and the presses not yet made, and the `Scheduler` releases
  the lease once the row is free. Invariants `OnlyAsked`, `OnNamed`, `AtMostOnce`,
  `NotEndedOnDialog`, `LeaseWhileLive`; liveness `DialogShown` and `GoesOn`. Configurations
  `Dialog_Ask` (nothing answers on its own) and `Dialog_Auto` (the app answers trust), and one
  break per property: `Break_Dialog_AutoAnswer` (F-137's own answer), `Unchecked`,
  `RetryUnknown`, `DeadlineEnds`, `DialogFree` and `NoRead` (the pane read only while the
  start's call waits).
- **`Screen` reads the imports dialog** (kind `:imports`), from the new fixture
  `imports-dialog.{txt,ansi}` (paths scrubbed to `/work/…` as `bin/capture-screen` scrubs them,
  in the manifest): its options by label, the selected one, and `paths:`, the external paths it
  lists, one a line under "External imports:", more indented than the heading, at least one. A
  dialog's reading now names its options' `indent` (the trust dialog's are one column in, the
  imports dialog's two), and the two kinds, which share a footer, differ by their title.
- **`Inlet`**: `look/4` reads a session's pane for `Sessions` (no write); `choose/5`, after its
  Enter, reads the pane until the dialog of that kind has left (`{:ok, :sent}`), else
  `{:unknown, {:still_shown, reading}}`.
- **`Sessions`**: a new status `dialog` (not free, not done) and two columns, `dialog` (the
  dialog shown, as JSON) and `answers` (each kind's label and mark), added to an older file on
  open and cleared by a new start. An interactive start with `inlet:` reads its pane at each
  check while it has no session file; a startup dialog makes the row `dialog`, with a cue. The
  app's `dialog:` callback (`fn kind, options -> {:answer, label} | :ask end`, default
  `Sessions.Dialog.ask/2`) is asked once per kind; an answer is pressed, `:ask` answers the
  start `{:unknown, {:dialog, kind}}` at once. A row on a dialog is read again every `look:` ms
  (5 000 by default) and at each cue: running once its session file names its process, stopped
  once its socket is dead, else its pane read and the next dialog taken. The start's deadline
  reads the pane before it makes anything unknown, and a `starting` row past its deadline after
  a restart is read before it is made an orphan. `answer_dialog/5` checks the row (that
  dialog, that label, no mark yet), marks it `pressing`, has the `Inlet` press it, and marks it
  `sent` or `unknown`, or takes the mark away on a refusal. A restart turns `pressing` into
  `unknown`. `Sessions.Dialog` is the pure part; `Sessions.Agents.dialog/1` is what a view
  reads. F-137's own trust answer and its `unknown`, reason `trust_dialog`, are gone.
- **`MCP`**: the operator's tool `answer_startup(agent, kind, label)`, through a `sessions:`
  handle; any other caller is refused `:operator_only`. `Operator.answer_startup/4`.
- **The example app** passes `dialog: &Sessions.Dialog.ask/2` (it asks) and hands `MCP` its
  `Sessions`.
- **The stand-in**: `ScreenStandIn.write!(…, dialogs: [:trust, :imports])` draws each dialog
  in turn from the fixtures, moved by Down and Up, answered by Enter (`<dir>/trusted`,
  `<dir>/imports`), and writes its session file only once they are answered, as 2.1.322 does.
- **Tests**: `ScreenTest` (the imports fixture both ways, its paths, a heading with none, a
  path not indented, another dialog's indent, its option keys); `SessionsDialogTest` on real
  tmux and dtach: each dialog shown and answered by a person, an answer for another dialog or
  label refused, the start going on and its prompt run (`OnlyAsked`, `DialogShown`, `GoesOn`);
  the deadline passing with the row still waiting and not free (`NotEndedOnDialog`,
  `LeaseWhileLive`); a restart with a press marked `pressing`, which becomes `unknown` and is
  refused (`AtMostOnce`); the app's callback answering trust and asking for imports; "No,
  exit" stopping the row. `DelegatesInteractiveTest` now gives its `Sessions` a callback that
  answers trust, the app's choice. `MCPTest` lists the new tool.
- **Docs**: `docs/design.md` ("Startup dialogs" under "Main sessions", the parts table, the
  model, interactive delegates, the trust rule), `README.md`'s status and its flow chart.

## What I ran into

- TLC's configuration file takes no tuple, so the configurations name the spec's own
  `TrustThenImports` (`Dialogs <- TrustThenImports`); and a record compared with a string is an
  error, so a person's answer in flight is a set of at most one.
- The reading's box mark is `❯` and a no-break space; a rewrite of the reading by hand typed a
  plain space and every idle screen read as unrecognized. The reading now writes it as
  `"❯ "`.
- F-137's stand-in wrote its session file before the trust dialog; 2.1.322 writes none while a
  dialog is shown. The stand-in now writes it after the last dialog, which F-137's new-2 asked
  to measure: the main session measured it for this unit.
- The start's call cannot wait for a person (hours, and no `:infinity`), so it answers
  `{:unknown, {:dialog, kind}}`, which every caller already reads as "the row decides later":
  `Delegates` leaves its row starting until the agent row runs or is free, `Mover` waits while
  the row is neither, and `Mailbox`'s launch row is settled by the transcript's user line once
  the brief runs.

## Findings

### new-1. The unit is over 500 changed lines

What happened: the library grew by about 580 lines and the tests by about 300. Why: the read
loop of a waiting row, the marks, the operator's tool and the stand-in's dialogs are each small,
but they are many, and the brief asked for all of them in one unit. What I did: kept the pure
part in `Sessions.Dialog` and the spec separate from `Start.tla`. What the design should change:
nothing; a later unit of this kind could split the screen reading from the answer.

### new-2. `Sessions` waits on the `Inlet`'s press in its own process

What happened: `answer_dialog/5`, and a callback's answer inside a start's check or a waiting
row's read, call `Inlet.choose/5` from `Sessions`' one process: two screen reads of up to 2 s
each and the keys, 20 s at most. Meanwhile a call to `Sessions` with a 5 s timeout (a read, a
stop) can answer unknown. Why: the mark, the press and the mark after must stay in order with
every other write to the row, as `Mailbox`'s did before F-136. What I did: bounded the press
(20 s) and the call (25 s). What the design should change: say whether `Sessions` hands a press
to a task whose answer comes back as a message, as F-136 did for `Mailbox`'s hand-on, with the
row `pressing` meanwhile.

### new-3. A press a restart cut can only be answered at the viewer

What happened: an answer marked `pressing` when `Sessions` restarts is `unknown` and never
pressed again (`AtMostOnce`), even when the restart came before its keys went, and so does an
answer the `Inlet` called unknown. The row keeps waiting; only a person at the viewer can answer
that dialog then. Why: whether the keys went is not known, and a second press could land on the
next dialog. What I did: what the model says. What the design should change: a person's clear
of an unknown mark, as `Recoveries`' clear works, once they have seen the pane still shows the
same dialog with its first option selected.

### new-4. Nothing ends a start that waits on a dialog but the dialog itself

What happened: a row on a dialog is not `running`, so `Sessions.stop/3` refuses it, and it is
not an orphan, so `Recoveries` does not end it. The trust dialog's "No, exit" ends it; the
imports dialog has no option that does. Why: a stop is SIGTERM once the session file reads
idle, and there is no file. What I did: nothing more. What the design should change: a stop of a
row on a dialog, by SIGTERM to its held program's record (`Holder.Process`), which the hold
wrote before the program ran, so an operator can give up a start without answering.

### new-5. A long external path may wrap, and the dialog then reads as unrecognized

What happened: the fixture lists one short path. A path wider than the pane wraps; `Screen`
takes the lines under "External imports:" that are more indented than it, so a wrapped line at
the margin makes the dialog unrecognized, and the row never says `dialog`: the start answers
`{:unknown, :no_session_file}` and the row waits `unknown` with its process live, unseen as
before. Why: no capture shows a wrapped path. What I did: refused a path line that is not
indented, so a guess is never a path. What the design should change: the capture script records
the imports dialog with a path longer than the pane and with several paths.

### new-6. A person's answer is not an act in `Acts`

What happened: the operator's `answer_startup` is a row in `MCP`'s call log, and `Sessions`'
marks keep the answer to one press per dialog, but no `Acts` row records it, unlike a fix or a
move. Why: the marks are the once-per-state guard here, and the state (a dialog with no session
file) has no record `Acts` could claim. What I did: nothing more. What the design should
change: say whether answering a startup dialog is an act, actor the operator, so the fault
ledger shows who answered what.
