# F-96: `MCP`, part 4: the service tools

## What was built

The eight service tools of the design's table, in `CodingAgentFramework.MCP`. Each goes through
`Services`' own function, which makes its own `Grants` check. `MCP` adds the argument checks
and the call log, as it does for `run`:

- `service_start(name, argv, opts)`: `Services.start/5` with the caller as owner, in the copy
  `:place` names for the caller (its project, its name as the copy, its worktree). `opts` may
  name `host` (the new `:workstation` option unless named), `forward` (a port, 1..65535) and
  `keep` (a boolean).
- `services()`: `Grants.may_use?/2`, then `Services.list/1`, each row cut to the fields the
  table names: name, host, owner, state, restarts, `port` and `local`.
- `service_logs(name, from)`: `Grants.may_use?/2`, then `Services.logs/4`.
- `service_send(name, input)`: `Services.send/5`.
- `service_wait(name, until, timeout)`: `Grants.may_use?/2`, then `Services.wait/4`. `until`
  is `{"line": pattern}`, `{"port": n}` or `"exit"`. A line is looked for from the current
  start's offset only; the tool takes no other offset. `timeout` is capped by `:cap`, as
  `run`'s.
- `service_restart(name)`, `service_stop(name)`, `service_hand(name, to)`: `restart/4`,
  `stop/4`, `hand/4`.

A service's name must be 1 to 64 letters, digits, `-` or `_`, since it names the socket and the
log on the host; `Services` itself does not check it. Every bad argument answers `{"refused":
["bad", "args"]}` before `Services` is called. Each tool's schema states its arguments and
their bounds.

`MCP` takes two new required options, `:services` (`{module, server}`, as `:jobs`) and
`:workstation`. `caf_mcp` uses `caf_services` in its tests only.

Tests: `apps/caf_mcp/test/mcp_services_test.exs`, an MCP client with a token per agent over a
real `Services` and `Copies` whose one host is this workstation, with a stand-in service that
records its pid, says `up` and echoes each line it reads. They check that a service is the
caller's, whatever the arguments say, in the caller's copy, and that any agent lists, reads and
waits on it; that the refusals follow the tools table (a stray start, a sibling's send and stop,
a grandchild's restart, a parent's hand, a hand to a sibling) and the allowed hand, restart and
stop go through; that twelve bad argument sets are refused with no row written; and that an
`ok`, a `refused` and an `unknown` answer of `Services` pass through unchanged.

## What I ran into

Nothing that stopped the work. `services()` cuts each row because `Services`' row also holds
the program's environment, argv and the worktree's path, which the table does not list.

## Findings

### new-1. A forward through the tool always uses the same local port as the remote one

What happened: `Services.start/5` takes `forward: {port, local}`, but the tool takes only a
port, forwarded to the workstation's same port. Two agents that each start a service on port
5432 on different hosts get the second forward refused or failed, since the workstation's port
is taken. Why: the design's table says "a port forwarded to the workstation", and choosing a
free local port is a policy the design does not state. What I did: integer only. What the
design should change: say whether `forward:` may name a local port, or whether `Services`
chooses a free one and `services()` shows it.

### new-2. A `service_start`'s whole time is bounded only by `Services`' defaults

What happened: the call's time is the copy's turn, the sync, dtach's reply and the forward's
open, each with `Services`' default timeout. The caller cannot set them, and their sum is not
capped against the client's tool timeout as `run`'s is. `service_restart` and `service_stop`
use the default 10 s grace. What I did: nothing beyond the defaults. What the design should
change: say whether a service tool takes a `timeout` that `MCP` splits across those steps, as
`run_delegate` splits its own.
