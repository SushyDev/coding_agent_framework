# F-297: a prompt's closer is right when its answerer died, and after an inbox restart

## Why

F-295 made a prompt read `answering` while its answer row in `Acts` is open, and wrote its
`closed` fact only once that row settles. Its build note left two gaps:

- **new-1.** If `answer/5`'s caller ends between the hand and the settle, its row stays
  claimed. The next start closes it `interrupted`, which has no outcome, so `closer/2` fell
  back to the owner's row: `{:framework, :passed}` for an ask. The fact is written once, so the
  record stayed wrong.
- **new-2.** What the inbox knows (`seen`) is in its memory. After a restart, `read/3` no
  longer listed an answering prompt, and no read wrote its fact.

## Confirmed first

The two new tests in `apps/caf_prompts/test/prompts_test.exs`, run against main's
`prompts.ex` (ffb44f3):

- "a caller ended between the hand and the settle…": after the caller is killed and `Acts` and
  the inbox start again, no `prompts` cue came and no read wrote a fact (the test failed at
  its first `assert_receive`). Only a page of `answered/3` would have written one, with the
  owner's guess. **Confirmed.**
- "an inbox restarted while an answer's row is open…": the restarted inbox's `read/3` gave
  `{:ok, []}` for a prompt whose row was still claimed. **Confirmed.**

## The model

`model/tla/Inbox.tla` now has:

- `Die`: the caller ends between the hand and the settle. `Start`: the next start of the
  framework closes the claimed row `interrupted` (as `Acts` does at its start) and starts the
  inbox again. `Start` is weakly fair: the liveness assumes the next start comes.
- `Rebuilt`: an inbox start (`Restart`, `Start`) knows each prompt whose answer row is open, or
  settled or interrupted with no `closed` fact. It takes an open or interrupted one as listed
  `answering`, so the read that lets it go cues it.
- `CueSettled` names the prompt, so one answered between two reads is the inbox's too.
- `starting`: the start's first read runs before any call the inbox takes (its
  `handle_continue`), so a page cannot come between a start and that read.
- `Closer` of an interrupted row is `unknown`, the person as actor.

Properties: `FactNamesAnswerer` is now "the fact names the answerer, or says `unknown` with the
answerer as actor, and only for an interrupted row; never a guess". `ClosedHasFact` (new,
liveness): a prompt gone from its owner whose answer row is settled or interrupted gets its fact
from the inbox's own reads (the page is the reader's and need not come). `ReaderSeesAnswered`
now ends at `unknown` for a dead caller.

## What was built

In `apps/caf_prompts/lib/coding_agent_framework/prompts.ex` only:

- **An interrupted row names its actor.** `cut/1` is the last answer row when it is
  `interrupted`. `closer/2` takes it after a taken row and an open one: `{:unknown, actor}`.
  The `closed` fact's detail then has `by: actor, outcome: "unknown"`. `answered/3` shows such a
  prompt `status: "unknown"`, `by` the actor, `reason: "interrupted"`, `choice` as the row has
  it. Only the last row counts: `answer/5` claims only for an open prompt, so an answer claimed
  after an interrupted one shows that one did not close it.
- **The first read after a start rebuilds what the inbox knows** (`rebuild/1`, from
  `handle_continue`). One query on `Acts`: each `answer` row joined to its prompt's `opened`
  fact of this host by that fact's key (`acts_state`), where the row is open, or interrupted or
  settled `verified` or `unknown` with no `closed` fact of this host. Each prompt found goes
  into `seen`. One whose row is open or interrupted also goes into `shown` as `answering`, so
  the read that lets it go cues it. One whose rows are all closed closed while the inbox was
  down, so its fact is written `late`.
- **The settle's read names the prompt.** `answer/5` casts `{:settled, prompt}`. The inbox
  puts the prompt into `seen` if it is not there, so a prompt answered between two reads (no
  read listed it) gets its fact from that read.

The module doc ("A dead caller, and a restart"), the close table, `answered/3`'s statuses,
`list/1`'s doc, `docs/design.md`'s prompts paragraph and the README's status list say so.

## Tests

On the stand-ins, with F-295's `SlowSettle` holding the settle:

- "a caller ended between the hand and the settle closes its ask unknown, by its answerer":
  the caller (unlinked) is killed while its settle is held; `Acts` starts again with a new
  `start_id`, so its row is `interrupted`; the inbox starts again. Its first read cues the ask,
  `read/3` no longer lists it, the fact is `by: "sam", outcome: "unknown", late: true`, and
  `answered/3` shows it `unknown` by `sam`, `reason: "interrupted"`.
- "an inbox restarted while an answer's row is open lists it answering, and writes its fact":
  the inbox starts again while the row is claimed and lists the ask `answering`; `answered/3`
  leaves it out. After the settle, the caller's cast went to the old inbox, and the ledger's
  cue has the new one read: it cues the ask, lets it go, and writes its fact `by: "sam"` (not
  `late`, as this read saw it close). `answered/3` shows it answered by `sam`.

## Findings

### new-1. The rebuild takes more than the open rows

What happened: the brief said to rebuild the `answering` set from the open answer rows. The
model found three paths where that leaves a closed prompt with no fact from any read:

- The next start interrupts the row before the inbox's first read. A new `start_id` is a new
  framework start, `Acts` starts before the inbox, and so at the rebuild no row is open.
- The inbox restarts between the caller's settle and its `{:settled, _}` cast being read: the
  pending read is lost, and the row is no longer open.
- A prompt answered between two reads was never in `seen`, so the read after its settle did not
  close it. This one was there since F-295.

What I did: the rebuild also takes rows that are interrupted, or settled and taken, whose
prompt has no `closed` fact. It is still one query per start. The settle's cast names the
prompt. With these, `ClosedHasFact` holds.

What the design should change: say that the inbox's first read rebuilds from the answer rows
whose prompt has no `closed` fact yet, not only the open ones.

### new-2. The first start writes the facts the ledger lacks

What happened: every prompt whose answer was taken before F-270, or that closed past an inbox
restart since, has no `closed` fact. The first start after this unit writes one for each,
`late`, naming the answer's actor. They are not cued: a settled one is not put into `shown`. Each
later start finds only the prompts still waiting. The query reads every `answer` row of the
ledger at each start: no index has `act` first, and the ledger is never pruned.

What I did: nothing more. The one-time writes complete the record, and the facts are right.

What the design should change: if the start's read grows slow on a large ledger, an index on
`acts (act, status)` would serve it.

### new-3. A caller that ended before the hand

What happened: if the caller ends after its claim and before the owner takes the answer, the
prompt stays open with its owner and the next start interrupts the row. If the prompt then
closes otherwise (a hold expires) with no later answer, its last answer row is still the
interrupted one, so it reads `unknown` by that actor, not the hold's `expired`.

What I did: nothing. The answer row does not say whether the hand happened. The model leaves it
abstract, and the header says so.

What the design should change: let the owner's row come first when it records the close itself
(a hold's `expired`, its `actor`, a dialog's press), and the interrupted row only where the owner
names no one (an ask). Or mark the row before the hand so a start can tell the two cases apart.
