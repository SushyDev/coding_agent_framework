# F-59: `Delegates`, up to a held report

## What was built

This branch holds the model and the design. The code passed 500 lines apart from its tests
(new-9), so it waits on the local branch `framework/f-59-delegates-code`, as F-55's did, with
the split new-9 proposes.

- `Delegate.tla` models what the code needs that the spec did not have: the row written first
  as `"starting"`, the call of `Sessions` (`Called`, `SessionsDecides`, `CallAnswered`) and its
  settling after a restart (`Settled`), a start under way counted against the cap, a resume
  counted in the row (`"resuming"`) before it is asked, and the turn's message (`InputWritten`,
  `InputTaken`), one per process, under the uuid the row holds. New invariants:
  `RefusedHoldsNothing`, `OneMessagePerProcess`, and `resumed` in `ResumedAtMostOnce`; a new
  property, `CallSettles`. New breaks, each failed by TLC: `CapSkipsStarting` (`CapHeld`),
  `SettleEarly` (`RefusedHoldsNothing`), `ResumeBeforeRow` (`ResumedAtMostOnce`, across a
  restart) and `NewUuid` (`OneMessagePerProcess`). The header names `Sessions` and `Stream`
  beside `Delegates`, `Parents` and `Control`.
- `docs/design.md` says what the design was silent on (new-1 to new-4, new-6, new-7), and the
  model section what the spec settles. `READING.md` reads the new steps.
- On the code branch: a new app `caf_delegates` with `Delegates` (the process),
  `Delegates.Table` (`delegates`, its one writer) and `Delegates.Turn` (the pure checks and
  what a `Stream` row says); `Stream.Fold` keeps the `result` event's text in `last_result`;
  the headless stand-in writes a `result` text and holds every turn while a file `hold` is
  in its directory. Tests: the checks, the brief written once and its result held as the
  report across a restart, the cap, `deliver/2` refused as `:no_delivery`, a kill after the
  last reply finished from the transcript, a starting row settled after a restart by
  `Sessions`' row of its call (and refused as interrupted with none), and a kill before the
  last reply asking one resume, which `Sessions` refuses today (new-5).

## Findings

### new-1. Where the projects' data lives

What happened: F-55 new-2 asked where the projects' data lives and how `start_delegate` gets it.

What I did: the host app hands `Delegates` its projects at start (`projects:`), each as
`Sessions.Worktree.project/1` reads it plus `branches` (a `Regex`) and `cap`. No table: nothing
in the framework writes a project, and a table can come when something does. `start_delegate`
hands `Sessions` the project as it is; `Sessions` takes the keys it reads.

What the design should change: nothing more; it now says so under "What `Delegates` holds".

### new-2. The cap's number and where it is set

What happened: the design names a cap of delegates but no number or place.

What I did: `cap` is a field of each project's data, with no default, since "the framework holds
no project's policy". It counts the parent's rows from their start until they end (starting,
running, resuming, finished, failed): a finished delegate still holds its worktree and its
report. `Delegate.tla`'s `Active` already counted finished and failed ones; a start under way
now counts too (`CapSkipsStarting`).

What the design should change: nothing more.

### new-3. A parent before `Parents`

What I did: the caller names the parent (a string), and the row keeps it. `held/3` answers a
parent's held reports by that name.

What the design should change: when `Parents` is built, a start checks the name against its
rows, and the project against the parent's.

### new-4. A delegate's session name

What happened: `start_delegate(project, branch, model, brief)` takes no name, but the worktree
lives by the session's name, and a reused worktree must be found again.

What I did: `<project>-<branch>`, each character of the branch other than a letter, a digit,
`_` or `-` as `-`. Two branches that differ only there share a name; the second's start finds
the first's tree on another branch and is refused. A name over 64 characters is refused by
`Sessions`.

What the design should change: nothing more; it now says so.

### new-5. Nothing ends a running `Sessions` row whose process was killed

What happened: a delegate killed before its last reply is to be resumed with
`Sessions.resume/6`. `Sessions` starts a name only when its row has ended (`stopped` or
`refused`), and nothing moves a `running` row when its process exits by itself: `Sessions`
settles `starting`, `unknown` and `stopping` rows, not `running` ones. `Start.tla` has no such
step either (`ProcExits` leaves the row as it is). So the resume answers
`{:refused, {:exists, "running"}}`.

Why: the specs so far only stop a process through `Sessions.stop`; a kill was `Recoveries`'
concern for orphans and late stops.

What I did: nothing in `Sessions`. `Delegates` asks the resume once, counted first, and holds
the refusal as the `failed` report, never retried; a test shows it. The second-kill report and
a resume that runs are checked only in the model and in `Delegates.Turn`'s tests.

What the design should change: `Start.tla` gains a step that settles a `running` row with no
call under way as `stopped` once its process is gone by pid and start time and its socket is
dead (with a `Break` whose bug settles it by the socket alone, so a reused pid or a socket that
dtach has not yet removed is caught), and `Sessions` takes it at each settle that a cue starts,
as it does for `stopping`. Then the delegate's resume works as `Delegate.tla` has it.

### new-6. The resumed process's message

What happened: the design says a killed delegate is resumed once, and that a resumed headless
process starts no turn of its own. It does not say what makes the resumed process go on.

What I did: when the brief had not gone in (`Stream` found it undelivered at the exit, or it was
never written), the brief goes again under its own uuid, as `Stream` requires; otherwise a fixed
message (`Delegates.Turn.resumed/0`) under a uuid of its own, which the row holds before the
resume is asked. The finish is then that message's turn's `result`.

What the design should change: nothing more; it now says so.

### new-7. A headless delegate's Stop

What happened: the protocol speaks of a Stop event, which a restart can lose. A headless
delegate's hooks are not read; its turn ends with a `result` in its log, whose offset persists,
so a restart loses nothing. Only a kill between the last reply and the `result` line loses it.

What I did: finished is the turn's message delivered and a `result` read after it; its
`result` text is the report. Otherwise, at an exit, the transcript's last reply is a finish.
`Delegate.tla` keeps its abstract Stop, which allows more than the code does.

What the design should change: nothing more; it now says so.

### new-8. One host per `Delegates`

What happened: the design does not say which host a delegate starts on.

What I did: `Delegates` is started per host, with that host's `Sessions` and `Stream`.

What the design should change: when a second host runs delegates, say how a start picks its
host.

### new-9. The code passes 500 lines: the split

What happened: the code is about 590 changed lines apart from its tests: `delegates.ex` 337,
`table.ex` 124, `turn.ex` 91, `mix.exs` 27, `Stream.Fold` 5, the stand-in 7.

What I would split, after this branch's model and design:
1. `Delegates.Table`, `Delegates.Turn` and `Delegates` with the start, the brief, the finish by
   the `result`, the held reports, `deliver/2` refused, and the settling after a restart, with
   the `Stream.Fold` and stand-in changes (about 430 lines).
2. new-5 in `Start.tla` and `Sessions`, a unit of its own.
3. The kill path in `Delegates`: the transcript's last reply, the resume counted first and its
   message, the second kill (about 160 lines), with the resume's tests end to end.

### new-10. `Stream.Table` loads a fold with a new field as a new fold

What happened: "State that never lags or lies" rule 4 says a load fills a field a newer build
added with its default. `Stream.Table.load/1` answers a stored fold whose keys differ from
`Fold.new/0`'s as a new fold, which reads its log again from the start.

What I did: the result's text goes inside `last_result`, whose keys `load/1` does not compare,
so no stored fold is dropped.

What the design should change: nothing; `Stream.Table.load/1` should fill new fields with their
defaults, in a unit of its own.

`docs/`.

What I did: ran `gate-test` three more times; all three passed.

What the design should change: nothing; a second sighting makes the test's wait worth a unit of
its own.
