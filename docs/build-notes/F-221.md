# F-221: a headless delegate's permission requests reach the inbox

## What was built

- Every headless launch and resume (`ClaudeCLI.headless/2`) passes `--permission-prompt-tool
  stdio` after `--permission-prompts host`.
- `HeadlessStandIn` behaves as the real Claude Code does. Without `--permission-prompt-tool
  stdio` in its argv, an `ask` turn emits `{"type":"system","subtype":"permission_denied", …}`,
  sends no `can_use_tool`, and ends its turn. With the flag it asks as before.
- A stream test launches without the flag and checks that the request is denied and none is
  held. A launch that loses the flag now fails there.
- The design's launch line, the README status and the stand-in's doc say so.

## What was measured

The end-to-end rerun on macOS (2026-11-23, step 3) found it. A headless delegate asked for Bash
(a compound `printf`, `git add` and `git commit`) and then Write. Claude Code 2.1.322 refused both
itself: `{"type":"system","subtype":"permission_denied","tool_name":"Write",…,"message":"Claude
requested permissions to write to …/hello.txt, but you haven't granted it yet."}`. No
`can_use_tool` was sent, so no prompt was listed and the parent got no notice. The launch had
`--permission-prompts host`, whose help reads "the SDK host or --permission-prompt-tool": with
no prompt tool named, it denies.

Then one headless run with `--permission-prompt-tool stdio`, the same message asking for a
Write, and stdin closed after the message. Claude Code sent the Write's permission to the stdio
prompt tool, and it failed "AbortError: Stream closed" instead of `permission_denied`. Answering
a live request was not measured here. A driver that answers another session's permission
requests was refused by this session's auto mode. The end-to-end step 3 rerun measures it with a
person answering from the inbox.

The answer's shape was read from the pinned binary's schema: `{"behavior":"allow",
"updatedInput": … optional}` or `{"behavior":"deny","message": … optional}`. `Stream.Line`'s
`allow` (no `updatedInput`) and `deny` (with `message`) match it.

Then the real path, in the end-to-end run, with this branch's launch: a headless delegate
(demo-unit-hello2) asked for Bash. Its `can_use_tool` was held and listed in the inbox as
`permission:stream:<session>:<id>`, and the parent got one `(prompt)` notice. `allow` read
`ok`, a second `allow` read `refused: :settled`, the command ran, and the commit and the report
came. But the prompt stayed `answering` after the delegate was idle. Claude Code 2.1.322 echoes
the answer on its stdout as written, with no `isReplay`, and the fold settled only on
`"isReplay": true`, a shape the release check never confirmed. So the fold now settles on any
`control_response` from the program, and the stand-in echoes the answer without `isReplay`, as
the real one does.

## What I ran into

Every earlier test passed because `HeadlessStandIn` sent `can_use_tool` whatever its argv. A
stand-in that is kinder than the real program hides a missing flag. The `permission_denied` event
was never folded, so nothing showed it.

## Findings

### new-1. A denial by Claude Code's own rules reaches no one

What happened: a `permission_denied` event goes into the delegate's log, and nothing else reads
it. The parent and the person learn of it only from the delegate's report, if it writes one.
Why: the fold reads only `can_use_tool`. What I did: nothing beyond the flag, which makes the
prompt path the normal one. What the design should change: the fold could turn
`permission_denied` into a parent notice, `From <name> on <account> (prompt): denied: <tool>:
<message>`, in the shape of the `prompt` notices.
