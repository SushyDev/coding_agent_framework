# F-86: `MCP`, part 1: an agent's tools, who calls, and `message`

This part was cut to the brief's fallback: who calls, the transport, the call log and
`message`. `run` and `reload` were built and tested, then taken out because the unit was too
big (new-1).

## The design question: who calls

"Each agent's MCP server starts with that agent's identity, and the agent cannot choose it."
There were two ways to do it:

- **A stdio bridge.** Each agent's config starts a small program with a token in its
  arguments. The program carries each message to the framework's endpoint. That is one program
  per agent. It must read stdin as binary and reconnect by itself (the bridge rule in "Rules
  learned"), and it adds a protocol hop.
- **An `http` server entry.** Claude Code speaks MCP over HTTP itself. The entry names
  `http://127.0.0.1:<port>/mcp` and a header with the agent's token. No program runs, and so
  nothing reads stdin. The endpoint keeps no MCP session (no `Mcp-Session-Id`), so each request
  stands alone, and after a restart of the framework there is nothing to reconnect.

Both keep the rule the same way: the token is in a file the framework writes, the endpoint maps
the token to the agent, and no argument names the caller. The `http` entry is simpler and
avoids the bridge's two failure modes, so it is the choice. "Agents working together" now says
so in a paragraph, **Who calls**. The pinned Claude Code 2.1.322 has the strings of the HTTP
transport (`mcp-session-id`, `text/event-stream`, `headersHelper`). I did not check against a
real session that it sends the header (new-3).

## What was built

- **`caf_mcp`**, a new app. It uses `caf_grants`, `exqlite` and `plug`. Its tests also use
  `bandit` and `caf_test`.
- **`MCP`**: one process with no name, the one writer of its table.
  - `issue/2` makes an agent a 32-byte random token, in place of any earlier one. It writes
    `<dir>/agents/<agent>.json` (mode 600, written to a temporary name, then renamed) with one
    server, `caf`, of type `http`, and the token in `x-caf-token`. Only then does it keep the
    token's SHA-256 in the table. An agent name that cannot be a file name is refused.
  - `who/2` maps a token to its agent.
  - `call/4` writes the call's row `called` (caller, tool, arguments as JSON), acts in the
    caller's process, then writes `answered` with the outcome as JSON. A refusal is written
    too. If the second write fails, the outcome still stands, and the row stays `called`.
  - `message(to, text)`: `Grants.may_message?/3`, then `message/5` of the `mailbox:` the
    embedding app gives as `{module, server}`, with a 5 s timeout. `Mailbox` checks the edge
    again itself. An unknown tool is refused as `{:unknown_tool, name}`, and bad arguments as
    `{:bad, :args}`.
- **`MCP.Table`**: `mcp_tokens` (agent, token hash) and `mcp_calls`. A row still `called` when
  the table opens is marked `cut`: a restart ended its call.
- **`MCP.Plug`**: `POST /mcp` from 127.0.0.1 only. The token is checked before the method and
  the body, so a missing or unknown token gets 403 and writes no row. It answers `initialize`,
  `ping`, `tools/list` and `tools/call`, gives 202 to a notification, and -32601 to any other
  method. A tool's outcome is the result's text, as JSON (`{"ok": …}`, `{"refused": …}`,
  `{"unknown": …}`), with `isError` unless it is `ok`. The status is 403 and not 401, because
  a 401 can start a client's OAuth flow.
- **`ClaudeCLI`**: a new option, `mcp:` (an absolute path). The agent's file goes after the
  account's, in the same `--mcp-config` list, before `--strict-mcp-config`. This works for
  `session/3` and `headless/2`. Without the option, the argv is the same as before.

## Tests

`apps/caf_mcp/test/mcp_test.exs`. The test is the MCP client. It speaks JSON-RPC with a token,
as the `http` entry would. The mailbox is a stand-in module.

- Served by Bandit on 127.0.0.1 and read with `:httpc`: `initialize` and `tools/list`.
- A call is attributed only by its token: an argument `"from"` naming another agent changes
  nothing.
- A missing, made-up or replaced token gets 403, writes no row, and reaches no mailbox.
- A call is `called`, with its arguments, while it acts (the stand-in waits for the test's go),
  then `answered` with its outcome.
- `message` off an edge (delegate to delegate) is refused `along_edges` and logged. Bad
  arguments and an unknown tool are refused.
- A row a restart left `called` reads `cut`.
- `ClaudeCLI`: the agent's file follows the account's, for both kinds of launch, and a relative
  path is refused.

No bridge was built, so the bridge's binary stdin rule has no test.

## What was measured

- `mix test` in `caf_mcp`: 8 pass (2 doctests, 6 tests) in about 2.5 s.
- Size: 643 lines added and 6 removed, the build note apart. The library is about 400 of them,
  and about half of that is `@moduledoc` and `@doc`.

## What I ran into

- The first version, with `run` and `reload`, was 740 lines. The patch is kept outside the
  repository (see new-1).
- `Mailbox` and `Jobs` need `Stream`, `Delegates`' table, `Copies` and hosts to start. So
  `MCP` takes each part as `{module, server}`, and the tests use a stand-in module. As a result
  `caf_mcp` does not declare `caf_mailbox`: the gate would count it as unused, since only a
  value names the module.

- The first `devenv test` failed one test in `caf_sessions`, which this unit does not change.
  It was `SessionsWorktreeTest`'s "Remove: a restart ends the setup …": `setup_pid/2` waited
  10 s for a setup script's pid file, and the machine's load was around 60. The next
  `devenv test` and three `gate-test` runs passed.

## Findings

### new-1. Even the brief's fallback does not fit in 500 lines

What happened: identity, transport, call log and `message` come to about 640 lines. `run` and
`reload` add about 100 more. Why: a new app with its table, its endpoint, its docs and tests
costs that much before the second tool. What I did: I cut to the fallback, as the brief says,
and kept the full version (with `run`, `reload` and `Grants.may_use?/2`, tested) as a patch.
What the design should change: plan the next part, `run` and `reload`, as its own unit of
about 120 lines. The rest of the tools follow, as below.

The tools still to build, and what each needs:

| Tool | Needs |
|---|---|
| `run(host, argv, timeout, opts)` | a `Grants` check that any agent the tree holds may run a job; a function from the embedding app that gives the caller's project, name and worktree (its copy); `Jobs.run/6` with the job id `mcp-<call id>`; a cap on `timeout`. Built in the patch |
| `reload()` | what "reloads the caller's own tools" means (new-2) |
| `agents()` | `Tracker`'s view of the tree, with each agent's state and what it waits on |
| `look(agent)`, `transcript(agent, from)` | `Grants.may_read?/3`; `Screen` for a main session, `Stream`'s rendered log for a delegate, `Transcripts` |
| `interrupt`, `answer`, `resume`, `stop` | `Grants.may_fix?/3` and a claim (`Grants`' claims); `Stream`, `Intake`'s held hook, `Sessions`/`Delegates` |
| `start_delegate(…)`, `run_delegate(…, timeout)` | `Delegates`' start; for `run_delegate`, a wait on the report up to the timeout |
| `start_main(project, brief)` | `Mains`, which is not built |
| `service_start`, `services`, `service_logs`, `service_send`, `service_wait`, `service_restart`, `service_stop`, `service_hand` | `Services` (part 1 is built), with `may_fix_service?/3` and `may_hand?/4` |
| `ask(question)` | somewhere a person reads and answers; not in the design yet |

### new-2. What `reload()` does is not settled

What happened: the tools table says `reload()` "reloads the caller's own tools", and nothing
says how. Why: the tools come from the framework's node, so the server side is never stale.
What a client may hold is its cached tool list. What I did: in the patch, `reload` answers the
tool names as an event stream, with `notifications/tools/list_changed` before the result. The
pinned Claude Code has that string, but I did not check that a session lists the tools again on
it. What the design should change: say what `reload` is for. If it is "the agent sees new
tools after the framework is upgraded", the notification is enough, once a check against a
real session shows that Claude Code acts on it.

### new-3. Nothing checks the `http` entry against the pinned Claude Code

What happened: the tests play the client, so nothing shows that Claude Code 2.1.322 loads the
`http` entry from a file given by `--mcp-config`, sends its header, and keeps calling after a
request failed while the framework was down. What the design should change: add a check against
each pinned release, like the Remote Control check in "Rules learned". It starts a real session
by hand, with a stand-in endpoint.

### new-4. A token is as private as the workstation's user

What happened: the token is in a file every process of the user can read, so one agent's Bash
tool could read another agent's file and call as that agent. A stdio bridge with the token in
its arguments has the same exposure (`ps`). What I did: the file is mode 600, and the table
keeps only the hash. What the design should change: decide whether this matters. If it does,
one way is to remove the file once the session's tools are connected. Then a `reload` or a
resume needs a new token.

### new-5. Nothing wires `issue/2` into a launch yet

What happened: `ClaudeCLI` takes `mcp:`, but `Sessions` does not pass it yet. Its headless
launch takes only `claude`, `model` and `env` from the launch options. And `Delegates` does not
call `MCP.issue/2` before a start. What the design should change: nothing. The next part that
starts agents through the framework with tools (or `Mains`) passes the path.
