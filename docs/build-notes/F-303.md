# F-303: work placed on a remote host finds that host's programs

## What was built

- No change to the library. The tree does not read programs from a `hosts:` entry, so there was
  nothing to fix. This unit lands the tests that show it, and states the entry's shape in the
  design.
- `remote_host_test.exs` gains a setup tagged `:app_shape`. It declares the host the way an
  embedding app does: `%{host: host, dir: dir, env: [{"PATH", bin}], programs: empty}`. The
  programs are only on the entry's `env` PATH. The PATH that the stand-in's ssh gives has none
  of them. Under that setup, a job and a heavy run (`caf-run --host`, on the tree's `Jobs` and
  `Scheduler`) both start on the host and report their end. A third test shows where a
  two-element `{:no_program, names}` does come from: an entry of empty programs read as it is,
  the way a part started outside the tree reads one.
- `docs/design.md` ("Hosts") and the README's status list say what the app passes in `hosts:`.

## What was measured

- `remote_host_test.exs` passed before the change (8 tests) and passes after it (11 tests).
  The new tree-level tests do not fail on `main`, because `main` has no such fault.

## What I ran into

- The tree (`apps/caf_surface/lib/coding_agent_framework.ex:1138-1140`) gives `Jobs` and
  `Services` each remote host as `%{hosts: <the Hosts pid>}`. It ignores the declared entry. Only
  `Hosts` gets `c.hosts` (line 1554). `Copies.Held.host/4`
  (`apps/caf_copies/lib/coding_agent_framework/copies/held.ex:99-104`) sends that entry to
  `Hosts.reach/4`: `:place` for new work, `:reach` for work already placed. Every remote use goes
  through it:
  - a job's placement, and the reads of its log and its end;
  - a heavy run, which `Runs.Remote` sends through `Jobs.run/6`;
  - a service's placement and its reads;
  - a forward's other end, through `Held.host(_, _, :reach, _)`;
  - a copy's sync and fetch. These run the workstation's rsync with the host's programs from
    the context.

  No part reads the decl's programs.
- `Held.host/4` takes an entry that has no `hosts:` key as it is. A part started outside the tree
  with `hosts: %{"mac" => %{programs: <empty>, dir: d}}` is refused by `Holder.new/3`
  (`apps/caf_holder/lib/coding_agent_framework/holder.ex:105`) as `{:no_program, [:dtach, :sh,
  :env, :rm]}`. That is the two-element shape in the report.
- Services and forwards on a remote host were checked by reading the code, not tested through
  the tree. A service needs a live owner agent, and only an agentful tree runs `Services`. They
  use the same `hosts.(pid)` map as `Jobs`.

## Findings

### new-1. The refusal seen in the app does not come from the tree's `hosts:`

- **What happened:** the reported reading was that the tree builds its remote hosts once, with
  no programs, and that the parts use them. The code does not do that. Built the way the app
  builds it, the tree places a job and a heavy run on the host and finds every program.
- **Why:** the tree replaces each entry with `%{hosts: pid}`. Programs are found only at a
  placement.
- **What I did:** landed the tree-level tests in the app's shape. I changed no code.
- **What the design should change:** the app should look for the place where it hands a
  `Jobs`, `Services` or `Copies.Held` an entry of its own `%{programs: <empty>, dir: d}`, for
  example a part it starts itself or a direct `Held.context/4` call. The two-element refusal
  comes from there. The app should pass `hosts:` to the tree only as
  `%{host: Host.ssh(name, ssh, destination, kill, options), dir: abs_dir}`, plus `env` (with its
  `PATH`) and `ssh_env`. It should drop the `programs` key.

### new-2. A host entry's unknown keys are accepted in silence

- **What happened:** `Config.new/1` accepts a `hosts:` entry that carries `programs:`, and the
  tree ignores that key. The app could believe the key counts.
- **What the design should change:** `Config` could refuse an entry key other than `host`,
  `dir`, `env` and `ssh_env` as `{:bad, :hosts, {:key, name, key}}`. Also, `Held.host/4` could
  refuse an entry whose programs lack `Hosts.needs/1` with the three-element
  `{:no_program, host, names}`, so that both paths name the host. Neither is built here.
