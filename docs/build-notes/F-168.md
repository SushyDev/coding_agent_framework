# F-168: small follow-ups: gh's token in the home, devenv's mktemp, a test race

Four items from F-155's findings (new-1, new-11, new-15, new-13), each its own small change.

## What was built

- **gh's token is a file in the home** (F-155 new-1). `bin/caf-login --gh <home>` runs `gh auth
  login --insecure-storage` with the home's `GH_CONFIG_DIR`, so the token is in
  `<home>/gh/hosts.yml`, never in macOS's Keychain (gh's default). After the login it reads
  `hosts.yml` for an `oauth_token:` and ends with status 1 and a message when there is none.
  `bin/caf-login --check --gh <home>` runs `gh auth status` as before, then says where the
  token is: `the token is in the home: a file, <path>`, or `the token is not in the home` when
  the file holds none. If gh's own status passed on such a token (the keyring, or `GH_TOKEN`),
  the check ends with status 1, so a login in the Keychain does not pass as one in the home.
  The test for the file is bash's own (`$(<file)`), so it needs no program. `docs/design.md`
  (the framework home) and `docs/e2e.md` (step 4) say it.
- **`bin/caf-login`'s onboarding step takes `mktemp` and `rm` from devenv** (F-155 new-11):
  `"$CAF_MKTEMP"` and `"$CAF_RM"`. `devenv.nix` has `CAF_MKTEMP` now (coreutils' `mktemp`, by its
  store path, beside `CAF_MKDIR`); `CAF_RM` was there. The script names every `CAF_*` it runs in
  its header. An unset `CAF_MKTEMP` stops the script (`unbound variable`); there is no fallback
  to PATH.
- **`AgentsTest` "a row's end time is its first done status's" no longer races its `Sessions`'
  adopt** (F-155 new-15). The test writes its rows under the host `"other"`, which its `Sessions`
  (host `"test"`) does not own. `Sessions` reads and settles only its own host's rows
  (`Table.with_status(db, state.host.name, …)`), at its adopt and at every later cue, so no
  timing decides whether it sees them.
- **`caf_tool_home` is named in the design's base** (F-155 new-13): "The boxes" lists `caf_shell`,
  then `caf_tool_home` (`ToolHome`: where every tool the framework runs keeps its state, in the
  home; pure, using only `caf_shell`), then `caf_holder`, `caf_store` and the `Ledger`. The
  layering paragraph in "Parts" already named it.

## What was measured

- **The mode gh gives its files.** devenv's gh (`CAF_GH`, 2.103.3; the one on my `PATH`, 2.96.0,
  gave the same) writes `config.yml` and `hosts.yml` `-rw-------` under umask 022. I made
  `hosts.yml` with `gh config set -h <host> git_protocol ssh`, which writes the same file a
  login does. So the token's file is mode 600 by gh's own write; the check does not test the
  mode, and does not add a program (`stat`) to do it.
- **The new `--gh` flows, with a stand-in gh** that writes `hosts.yml` (a token only when given
  `--insecure-storage`) and passes or fails `auth status` as told. Exit codes: check, nothing
  there, gh fails: 1 (`no token in the home`); check, gh passes, no token in the file: 1 (`the
  token is not in the home`); login, the file gets no token: 1; login: 0, the stand-in was
  called with `auth login --insecure-storage`; check after it: 0; check with a token and gh
  failing: 1. `bash -n bin/caf-login` passes.
- **The onboarding step, with a `PATH` that has no `mktemp` and no `rm`** and a stand-in
  Claude Code that passes the onboarding: the script called `CAF_MKTEMP -d
  <TMPDIR>/caf-login.XXXXXX` and `CAF_RM -rf -- <that folder>` and ended 0. With `CAF_MKTEMP`
  unset it stopped at `CAF_MKTEMP: unbound variable`, status 1.
- **gh and a token in the environment.** With `GH_TOKEN` set, `gh auth login --insecure-storage`
  refuses (`The value of the GH_TOKEN environment variable is being used for authentication`,
  status 1; both ghs), and `gh auth status` reads that token (the `PATH`'s gh). Hence the check's wording: the token is not
  in the home, so gh reads it from the keyring or the environment.
- **The test file, 30 runs alone**, each `12 passed`. Before the change the failure showed in two
  of six `gate-test` runs under load (F-155), never alone, so these 30 do not show the cure; the
  cure is that the rows are on a host the adopt does not read.
- **Not measured**: a real `gh auth login --insecure-storage`. It needs a GitHub account and a
  browser or a token. What gh does with a keyring entry that an earlier login left, when the
  same user logs in again with `--insecure-storage` (see new-3).

## What I ran into

- F-155 names two ways to cure the test's race: wait for the adopt (`:sys.get_state`), or write
  the rows under a host the `Sessions` does not own. I took the second. A `get_state` waits for
  the first adopt only; any later `settle(:all, …)` on a cue (`registry:`, `stream:`, `tmux:`
  for the `Sessions`' host) would still settle a `starting` row with no deadline as `interrupted`.
  Nothing in this test sends one, but the host makes it so by construction, not by what the
  test happens not to send.

## Findings

### new-1. `bin/caf-login` still takes `grep` and `dirname` from PATH, and `gate-test` takes `mktemp`

What happened: item 2 moved the script's `mktemp` and `rm` to `CAF_*`. `onboarded()` still runs
`grep`, and the script's first lines run `dirname`, both found on PATH. `devenv.nix`'s
`gate-test` script runs `vm_file=$(mktemp)` the same way.
Why: the brief names `mktemp` and `rm` only, and I touched only those. `dirname` runs before
the script has re-run itself through `devenv shell`, so no `CAF_*` exists there yet.
What I did: nothing.
What the design should change: say whether a script under `bin/` or in `devenv.nix` may call a
program by name from the devenv shell's `PATH`. If not, add `CAF_GREP`, use `${0%/*}` for the
directory before the re-run (bash, no program), and use `"$CAF_MKTEMP"` in `gate-test`.

### new-2. The next test in `AgentsTest` has the same race

What happened: "the migration's hand-over gives a delegate with no parent its parent and its
end" writes a `starting` row on host `"test"` into the table of the `Sessions` its setup
started, then updates it to `stopped` at once. A settle between the two writes would refuse the
row as `interrupted`, as in new-15. I did not see it fail.
Why: the same shape as the test this unit fixed; the window is two writes wide, so it is rarer.
What I did: nothing; the brief names one test.
What the design should change: nothing. The host cure does not fit this test: `adopt_tree/2`
reads only the `Sessions`' own host's rows, so the row must be on host `"test"`. Its cure is to
wait for the adopt first (`:sys.get_state(ctx.sessions)`, which runs after `handle_continue`), or
to write the row already `stopped`; the first leaves a later cue's settle a possibility.

### new-3. A token an earlier `--gh` login left in the keyring stays there

What happened: F-155's `--gh` kept gh's default, so a home logged in before this unit may hold
its token in the Keychain. `--check --gh` now ends 1 on it (`the token is not in the home`),
and `--gh` again runs `gh auth login --insecure-storage`, which writes the file. I did not
measure whether gh then removes the old keyring entry.
Why: that needs a real login.
What I did: nothing; the message tells the person to log in again.
What the design should change: say whether `bin/caf-login --gh` first runs `gh auth logout`
(which removes the keyring entry), so that no token is left outside the home. I did not build
it: it ends a login the person may want.

### new-4. A `GH_TOKEN` in the person's shell stops `--gh`

What happened: gh refuses to log in while `GH_TOKEN` is set (measured above), and its status
passes on that token. `--gh` ends 1 on gh's own message; `--check --gh` ends 1 on `the token is
not in the home`, whether or not the token is valid.
Why: gh reads those variables before the config directory.
What I did: nothing. The script unsets `CLAUDECODE` and `CLAUDE_CODE_*`, but not these.
What the design should change: say whether `bin/caf-login` unsets `GH_TOKEN`, `GITHUB_TOKEN`,
`GH_ENTERPRISE_TOKEN` and `GITHUB_ENTERPRISE_TOKEN` for gh, as it does Claude Code's variables,
and whether a launch, job or service sets them for an agent (`ToolHome.env/2` does not).

### new-5. `SessionsDialogTest` hangs in `Sessions.start/4` under load, again

What happened: in one of six `gate-test` runs (the third, after two passes), "the app's callback
answers the kinds it chooses, and asks for the rest" (`sessions_dialog_test.exs:233`) was killed
by ExUnit's 60 s timeout inside `Sessions.start(sessions, "alpha", …)`, which answers
`{:unknown, {:dialog, :imports}}` in 0.4 to 0.6 s when run alone (six of six). The load was
15 to 16 (the five-minute average), from my own runs and other builders'.
Why: not found. It is the test F-155's new-12 saw run past 60 s twice. This unit changes no
code the test runs: only a test of another file, the script `bin/caf-login`, `devenv.nix` and
docs.
What I did: nothing to it; I ran a second series of three, which passed.
What the design should change: a start that waits on a dialog has a deadline of its own, so a
60 s hang means something waited past it, or the stand-in's startup dialogs never showed. Find
which, with the test run in a loop under load and its `Sessions` state read when it hangs; I did
not, since the brief names a small set of items.
