# F-302: caf-run fails closed when the framework does not answer

## What was built

- The wrapper treats an `unknown` answer as no answer. Examples are `no_scheduler` while the
  app's tree restarts, and `no_answer` when the `Scheduler` did not answer the plug in time.
- It asks again under the same id, once a second, until its no-answer bound has passed by the
  clock. The bound is `:unanswered` (30 s), or the wrapper's own wait when that is longer.
- Then it prints `caf-run: not run: no lease (<reason>); try again` and exits 75, and nothing ran.
  Before this change it ran the command without a lease.
- `CAF_RUN_UNLEASED=1` in the wrapper's environment keeps the old behavior, for a caller that
  chooses it.
- A run on another host (F-296) that got no lease before its start now also exits 75. Before
  this change it fell back to running the command on the workstation.

## Why

On a loaded host the `Scheduler` timed out, and the app restarted its tree eight times in a day
on landings. Each time, every waiting wrapper on the host ran its heavy command at once, without
a lease (`caf-run: no lease (timeout); the command runs without one`). That raised the load that
made the `Scheduler` slow: a spiral. F-217 had chosen to fail open, as a hook does. The operator
chose to fail closed instead (ask 773).

## What was measured

- `runs_test.exs`, on a plug with no `Scheduler`: the wrapper asks more than once, exits 75, and
  never runs the command. With `CAF_RUN_UNLEASED=1`, it runs the command and says so.
- A listener that hangs up gives exit 75 within the bound. So does an ask the intake never
  answers.

No spec models the wrapper's no-answer path. `Schedule.tla` models leases once a request is in.
The change only removes a path that ran without a lease, so the specs' `NoRunUnleased` and
capacity invariants hold more tightly, and none of them changes.

## Findings

### new-1. A caller must handle exit 75 from a slow framework

- **What happened:** exit 75 used to mean only a lease refusal (`try again after <time>`). Now it
  also means no answer.
- **What I did:** the line says `try again`, with no time, since none is known.
- **What the design should change:** an app's `bin/run`-style wrapper should retry on 75 with a
  backoff, or pass a `--wait` long enough to ride out a restart.
