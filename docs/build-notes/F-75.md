# F-75: `Grants`' claims table

`CodingAgentFramework.Grants.Claims` in `caf_grants`: the table of claims a fix takes on its
target's state before it acts (`Team.tla`: `claims`, `ClaimTaken`, `ClaimSettled`,
`OneClaimPerState`).

## What was built

- One process owns the SQLite file (`start_link/1`, with `path`, `grants`, `start_id`), after
  `Delegates.Table`'s open, schema and WAL. The embedding app's supervision tree starts it.
- `claim/6` runs `Grants.may_fix?/3` (or `may_fix_service?/3` for a `{:service, owner}` target),
  then looks for an open claim on the same target and state, then writes the row `claimed`.
  Answers: `{:ok, claim_id}`, the check's `{:refused, reason}`, or `{:refused, {:claimed, by}}`.
- `settle/4` ends a `claimed` row as `verified` or `not_verified`; any other row is
  `{:refused, {:not_open, status}}`, so a settled row is never reopened.
- On open, rows still `claimed` whose `start_id` differs from the opening start's become
  `interrupted` (settles F-73 new-2 by the recommendation there). Rows of the current start are
  kept, so a second open in one start closes nothing live.
- `state` and `target` are stored as Erlang terms and compared decoded, by equality.
- `get/3` and `rows/2` read rows, for tests and for a later view.
- Calls take a finite timeout (5 s default). A dead writer is `{:refused, :no_claims}`; a timeout
  or exit is `{:unknown, reason}`, as `Delegates` does.

## What was measured

`mix test apps/caf_grants/test`: 18 passed. Tests are named for the `Team.tla` invariants
(`OneClaimPerState`, `MayFix`, `ClaimSettled`, `ClaimTaken`).

## What I ran into

The brief's `{:refused, reason}`-only answers do not cover a timeout, where the claim may or may
not have been written. I used `{:unknown, …}` for it, as the rules ask (see new-2).

## Findings

### new-1. `Team.tla` refuses a claim on any earlier claim of the state; the brief says open ones

What happened: `ClaimTaken` requires that no claim in `claims` has the same target and epoch,
and `claims` never loses a row, so a settled claim also blocks a new one on that state. The
brief, and this table, refuse only on an open claim. Why: the model's `n <= 2` per caller and
target counts calls across epochs, and the guard may be meant to cover settled claims too (a
fix on a state acts once). What I did: followed the brief; a settled claim frees its state, and
a test states it. What the design should change: say which holds. If a state is fixed once,
`claim` should refuse on a settled row of the same state with `{:refused, {:already_claimed, by}}`.

At landing, the main session took new-1 the model's way: `claim` refuses a state any claim has
held, open or closed (`{:already_claimed, by}` for a closed one), and the two tests that said a
settled or interrupted claim frees its state now say it does not; a new state is free.

### new-2. Timeout answers

What happened: a `claim` that times out is `{:unknown, {:timeout, ms}}`, and the row may exist.
What I did: nothing more; no retry. What the design should change: the fix's caller should read
`rows` or `get` before it decides, or `claim` should be idempotent on a caller-given key.
