# F-240: a message to an interactive delegate after the tree restarts

## What was built

- **The reproduction** (`apps/caf_mailbox/test/mailbox_restart_test.exs`), on the stand-in: an
  interactive delegate `d1` (`ScreenStandIn`, its pane 200 columns wide as the live one was),
  idle; the `Mailbox` and the `Inlet` stopped and started again while the session runs on; no
  `Intake`, so no waiter, as after a restart cut it; a framework home 100 characters longer
  than the test's directory, as a live home under an application-support directory is. Then an
  860-character message from `main`, then a short one. On `main` at 6d4f4b9 both stay `queued`
  for ever: the first with `attempt` `["too_long",196]`, exactly the live row 39, and the
  second behind it with no attempt, exactly row 48. Nothing is typed.
- **The model** (`Delivery.tla`): a constant `Wide`, the `Long` rows whose pointer line is
  still wider than the box. The typed write never reaches them. A new step, `WaitBound`: a
  `Wide` row, first to its interactive addressee, whose process runs idle with no waiter, is
  answered `unknown` (time is abstract, so at any such step). `Arrives` now allows `unknown` for
  a `Wide` row, and `UnknownWhy` says an `unknown` row is a forced end's or the bound's.
  `Delivery_Wide.cfg` (one sender, row 1 wide, row 2 behind it, a restart, a prompt that may
  or may not come) checks every property; `Break_Delivery_WaitForever.cfg` drops the bound, and
  TLC finds the row, and row 2 behind it, waiting for ever. The four specs that instance
  `Delivery` bind `Wide <- {}`; every `Delivery` configuration sets `Wide = {}`.
- **The fix** (`Mailbox`): `wait_bound:` (600 000 ms by default). A row whose text the `Inlet`
  refused (`Transport.Typed.text_refused?/1`: too long, a control character, or too long with
  no home) still waits for a waiter, and a waiter that comes takes it as before. Its bound runs
  from the refusal, its last write (`updated_at`), so a restart reads the same time; a timer is
  set at the refusal and, at a start, for each such row. Past the bound, with the turn read idle
  in that step (`turn_now/3`) and no waiter held, the row is written `unknown`, `attempt`
  `["wait_bound", refusal]`, and the next row to the session is tried at once, not at the next
  cue, which may never come. `open_to/3` no longer counts it, so a parent's stop is not refused
  by it.
- The design's "A session with no waiter", `Mailbox`'s and `Transport.Typed`'s docs, and the
  README status line say so.

## What was measured

- On the stand-in, on `main`: the long row's pointer line, ``From main (message): a message for
  you is in `<home>/due/d1/1.md`; read it. [delivery <uuid>]``, is wider than the 196 columns
  the `Inlet` allows a 200-column pane (`width - 4`), and is refused `{:too_long, 196}` before a
  key goes. With the fix and a 1.5 s bound, the row is `unknown` about 1.5 s after the refusal
  and the short row behind it is typed and delivered.
- TLC: `Delivery_Wide` 617 distinct states, 4 s; `Break_Delivery_WaitForever` fails `Arrives`
  in 330 distinct states.

## What I ran into

- **Which of the two causes held.** Only the second. The `too_long` at 196 *was* the pointer:
  an 860-character text goes as the pointer line, and that line, which names the whole path of
  the due file, is what the `Inlet` refused. With a long home it is wider than the box, so the
  row is never typed and "waits for a waiter" (`Transport.Typed.text_refused?/1`, and the
  design's "A pointer line the box still cannot hold is refused, and its row waits for a
  waiter"). An idle session has no waiter after a restart cut it, and starts none until a turn
  of it ends, so the row waited for ever, and row 48 behind it, from the same sender, with it.
  Other long messages to the same parent went in because the parent is a main session with a
  waiter, which takes a text of any length.
- **`not_followed` is not a cause.** `Stream` follows headless delegates only: `Sessions` calls
  `Stream.follow/5` for a headless start alone, and nothing follows an interactive delegate,
  before a restart or after it. `look`'s `events` is `Stream.log/4`, so for an interactive
  delegate it always answers `{:refused, :not_followed}` (the test shows it before and after
  the restart). No interactive delivery reads `Stream`: the typed and waiter transports read the
  agent row, the session file (`Registry`), `Intake`'s waiter and the transcript. `Stream`'s own
  table (`Table.delegates/2`) keeps the headless delegates it follows across a restart. So item
  3's first fix, following every interactive delegate again at boot, has nothing to follow, and
  was not built.
- **What the design wants for the rows behind** (item 4): in order per sender and addressee
  (`Delivery.tla`'s `InOrder`), one row in flight per addressee. `Mailbox` keeps one queue per
  addressee (`Table.open_rows/1`, a row due again first, then by id), stricter than the model's
  `First`, which lets another sender's row pass. Rows 39 and 48 share a sender, so 48 could not
  pass 39 either way. The bound is what frees it: a row behind a refused one waits at most the
  bound, and no longer.
- **The short row in the reproduction.** "short one" is 78 characters with its frame and mark,
  over `Transport.Typed.short/0` (76), so it too went as a pointer and was refused. The test
  sends "hi". See new-1.
- The first try's bound wrote the row `unknown` and stopped: the row behind it waited for the
  next cue, which an idle session with no waiter never sends. The fix tries the next row at
  once.
- `erl_child_setup: failed with error 32` printed once in a mailbox run that passed; it comes
  from a port closed early and failed nothing.

## Findings

### new-1. Under a long home, an idle interactive session with no waiter takes almost nothing

What happened: the typed transport sends a row as itself only within 76 characters with its
frame and its 48-character mark, so a framed text of about 28 characters at most. Anything
longer goes as the pointer line, which names the due file's whole path, and under a home like
the live one that line is wider than the 196 columns a 200-column box holds. So after a restart,
or past a waiter's deadline, an idle interactive delegate takes only a few words; every longer
row waits for the bound and is answered `unknown`, never read.

Why: the `Inlet` refuses a box of more than one line, since no fixture shows how a release
draws a wrapped box (F-113's new-1), and the pointer line's width grows with the home's path.

What I did: bounded the wait and answered it, as the brief allows when the design has a reason
to wait. I built nothing that makes the line fit.

What the design should change: make the pointer line fit, not only the wait end. Recommended:
capture 2.1.322's screen of a box wrapped over two lines (a fixture at 200 columns), teach
`Screen` to read it, and let the `Inlet` type a pointer line up to two rows; at 200 columns that covers
every home under about 270 characters. A smaller step, with no fixture: when the framed pointer line
is too wide, type the unframed one the brief and the word to go on already use (``A message for
you is in `<path>`; read it.``), since the file holds the framed text; it saves the frame's
width, not the path's.

### new-2. `unknown` for a row that was never typed

What happened: the brief names `unknown` for the answer at the bound, and it is what the code
writes. But the `Inlet` refused the line before any key went, so the outcome is known: it never
went in. `unknown` elsewhere means the text may have gone in (`ForceSettled`).

Why: the row's statuses have no word for "never went in, and never will" but `ended`, which
says the session ended.

What I did: wrote `unknown` with `attempt` `["wait_bound", refusal]`, so a reader can tell it
from a forced end's, and added `UnknownWhy` to the model.

What the design should change: decide whether a row answered at the wait bound is `unknown`, or
a status of its own (`undelivered`, say) that the sender's views and `Metrics` read as "not
delivered". Either way the sender is told nothing today: recommend a notice to the sender, as
a process's end gives one (`NoticeStored`), so a parent learns to send it again shorter.

### new-3. `look` shows `events: {refused: :not_followed}` for every interactive agent

What happened: the live report read it as a sign that nothing followed the delegate after the
restart. It is the answer for any interactive agent at any time: `events` is the headless
event log.

What I did: nothing in the code; the test shows the answer before and after a restart.

What the design should change: `look` leaves `events` out for an interactive agent, or names
it `:interactive`, so a reader does not take it for a fault.
