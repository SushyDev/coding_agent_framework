# F-116: the remodel F-115 proposed, folded into the design

A design unit. It changes `docs/design.md`, `README.md` and this note; no code and no spec. The
operator took F-115's whole proposal: the target parts, the model (`Claim`, `Hold`, `Delivery`;
`Intake`, `Delegate`, `Team`, `Stream` and `Move` reshaped), and the path R1 to R12, before the
rest of unit-order item 13 and item 14.

## What changed in the design

- **"Concepts"**: a claim is any actor's hold on a target's state, a row in `Acts`. Two new
  words: a **delivery** (one row in `Mailbox`, with its **transport**) and a **hold**.
- **"The parts"**: the rule that each part writes only its own table, reads another's only
  through that part's functions, and keeps a status list once. A short "Remodel" paragraph says
  the code reaches the target through R1 to R12. The table has an "Owns" column and the target
  parts: `Store`, `Reader`, `Cues`, `Holder.Process`, `Registry` and `Transcripts` one per host
  over every account, `Inlet` in place of `Control`, `Stream` as transport only, `Intake` with
  one hold of four kinds, `Sessions` as the agent row and the tree, `Delegates` as the protocol
  only, `Mailbox` as every delivery, `Acts`, `Recoveries` with no table of its own, `Grants`
  over `Sessions`' tree. The layers name `caf_store`, `caf_cues` and `caf_inlet`. The
  embedding app's paragraph loses its cue routing, its ticker and its reads of other parts'
  tables. A list of how the flows go (a session's life, a delivery, a hook, an act) follows the
  table.
- **"The delegate protocol"**: the report is handed to `Mailbox` as the reply to the brief, and
  its sending mark is `Mailbox`'s row; `Delegates` keeps whether it was taken. A delegate's life
  is its agent row's status. A main session is an agent row of kind `main`. `run_delegate` is
  the `call` transport, with F-92 to F-97's rule kept as it was, once.
- **"Headless delegates"**: a message's sending mark is `Mailbox`'s row, settled by the replay
  `Stream`'s fold reads; `Stream` keeps the line's claim and no message state; the end checks
  `Mailbox` for the report delivered and nothing to the delegate sending or due.
- **"Delivery into a main session"**: the waiter is a hold of kind `waiter`, decided by
  `Mailbox`; with no waiter, the `Inlet`'s checked write is one more transport of the same row.
- **"Delivery"**, a new section: one row in flight per addressee, the mark and settle once, and
  a table of the four transports with each one's evidence and restart policy.
- **"Agents working together"**: a key goes through the `Inlet`; a fix's claim is a row in
  `Acts`, with a unique index; a message is a delivery like a report and a reply.
- **"Intake"**: one hold, four kinds, with each kind's decider, deadline and row.
- **"State that never lags or lies"**: one `Inlet` per host writes panes; every other part reads
  a table through its owner.
- **"The model"**: the gate parses the slow configurations (F-115's new-1); the fast set is
  timed on an idle machine by the next unit that changes a spec (new-13); a mechanism is written
  once and a cross-spec property is checked in the spec that owns it. F-115's table of what
  becomes of each spec, and a table naming the spec that will own each property F-115 found
  unchecked.
- **"Rules learned"**: a new **Parts** group (build a mechanism once; never open another part's
  table; the order of cues is the library's), and under **Tests** that a fake is a test aid
  (`Tmux.Fake`, new-12) and that a fast configuration is timed on an idle machine (new-13).
- **"Order of the first units"**: R1 to R12 with their sizes, before item 13; item 13 rewritten
  to what is left (interactive delegates, then what R9 leaves of `Mains`); item 14 rewritten on
  the new shape, with the fault ledger moved to R10. Items 4, 5 and 6 point to R5, R7 and R8,
  to R12, and to R9.
- **`README.md`**: the overview chart shows the target shape, with a line that says so; the
  bullets under it and the "Next" part of Status name the remodel. "The apps" chart is kept as
  built, with one sentence that the remodel changes it.

## Rules F-115 replaces

Every other rule of F-114 and the units before it is kept.

- "One `Control` per host writes panes" (state rule 2): one `Inlet` per host, which is
  `Control` with `Screen`'s box check.
- A fix's claim as "a row in `Grants`' table" (F-75): a row in `Acts`, shared with `Recoveries`.
- The report's own `sending` mark in `Delegates`' row (F-14, and F-114's step 5) and its
  `answering` mark for `run_delegate` (F-92 to F-97): one mark, `Mailbox`'s row; the rules of
  each are kept as the `waiter` and `call` transports.
- `Stream`'s message state as the sending mark of a message to a delegate: `Mailbox`'s row is
  the mark, and `Stream`'s replay is its evidence.
- `Stream` refusing an end while a message is under way or found undelivered: `Sessions` reads
  that from `Mailbox` before it asks for the end; `Stream` still refuses an end while the turn
  runs.
- "One `Registry` reader per account": one `Registry` and one `Transcripts` per host over every
  account (this also settles item 13's "found through `Registry` across every account").
- The embedding app wiring each part's cue, a ticker driving `Jobs` and `Services`, and the app
  reading `Delegates`' and `Sessions`' tables for the tree, `place` and `agent_of` (F-102): `Cues`
  routes what each part declares, and the tree and the lookups are `Sessions`' functions.
- Until `Mains`, a main session known to `Grants` only as a parent a delegate's row names
  (F-73's new-3, new-4): a main session is an agent row of kind `main`.
- "Delegates' delivery of a report through the waiting Stop hook" as item 4's own work, and the
  fault ledger as item 14's: R7 and R10.

## Choices F-115 left open

- **`Cues` is its own app, `caf_cues`, in the base layer.** It is a process (one per instance)
  with one job, routing; `caf_store` is a pure module and starts no process, so putting the
  router there would give one app two kinds of part. `caf_cues` uses no other app: each part
  declares its topics as data, and the embedding app hands them to `Cues` at start, so no part
  needs to depend on `caf_cues` either.
- **A delivery's restart policy lives with its transport**, as one module per transport inside
  `Mailbox`, beside the one mark and settle, and `Delivery.tla` models each transport's policy as
  its own choice. The four policies differ only in the evidence and in what "due again" means
  (`stream`: undelivered is final, due again first under the same uuid; `waiter` and `typed`:
  from the transcript once the turn ended; `call`: due again for the waiter). Putting the policy
  in the transport keeps `Mailbox`'s core free of a case per kind, and a fifth transport adds a
  module, not a branch.
- **`caf_control` becomes `caf_inlet`; `caf_screen` stays** as the pure reading `Inlet` uses.
  F-115 says "Control and Screen merged" in its table but keeps "Screen as a pure reading per
  release" and removes only `caf_control`; this takes the second reading, which keeps Screen's
  fixtures and tests where they are.
- **`Sessions`' stop by SIGTERM goes in R3**, with `Holder.Process`, not in R9: R3 already
  moves `Sessions`' held record to the module that ends a process by pid and start time, and
  R8 removes `Control`, whose `/exit` is the stop's only use today.
- **`Grants` stays a pure module** handed the tree's function, now `Sessions`' (R9), so
  `caf_grants` still uses no other app.
- **The `waiter` hold has no row of its own**: the delivery's row in `Mailbox` is its record,
  so a restart that cuts a waiter settles the row from the transcript, not a hold row.

## Findings

### new-1. `Stream`'s `can_use_tool` requests are a hold, and F-115's model table does not say so

What happened: F-115's section 3 says "Intake, Stream and the new Delivery would instance
`Hold`", and its section 1b names `Stream`'s requests as a hold; its table of specs says
`Stream.tla` keeps its requests as they are.
Why: the table lists what moves out of `Stream.tla`, and requests stay in it.
What I did: the design names `Hold.tla` as the module for every held request and lists
`Stream.tla` as kept with its requests; it does not say whether R4 instances `Hold` in
`Stream.tla`.
What the design should change: R4 instances `Hold` for `Stream`'s requests too (decider a
person or an agent's `answer`, no deadline, settled by a cancel or the exit), so the shape is
written once. If its state counts grow too much, it stays as it is and the header says why.
