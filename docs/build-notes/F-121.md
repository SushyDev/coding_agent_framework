# F-121: R5, `Intake`'s one hold (part 1); the waiter not built

The brief has two parts: one hold structure in `Intake` for `PermissionRequest` and
`PreToolUse`, then the `waiter` kind. This unit lands part 1 alone. The waiter needs answers the
design does not give yet (new-1 to new-3), and the two parts together would be well over the
unit's 500 lines.

## What was built

- **One hold structure.** `Intake` keeps one map of holds, keyed by row id, in place of `holds`
  and `tools`. It has one drop, one `:DOWN` lookup, one deadline message (`{:expire, id}`), one
  `decide` (the row moves `held` to `deciding` before the response goes to the plug), one
  `release` (an empty response and the row's end) and one `settle` (`held` becomes `lost`,
  `deciding` becomes `unknown`). A kind is `:permission` or `:tool`. Kinds differ only in their
  decider (`answer/4`, or the callback's process), their deadline (`deadline:`,
  `tool_deadline:`), their plug margin (5 s, 1.5 s) and their response encoder.
- **The tool hold takes the permission hold's shape**, as `Intake.tla` says since F-119
  (new-3). A `PreToolUse` gets its row `held` when it is held. A decision moves it `deciding`,
  with the actor `app`, and then `answered` once the plug writes it. A pass, a crash or exit of
  the callback, or a non-decision leaves it `passed`. The deadline leaves it `expired`. A
  request that closes while held is `lost`, and a restart settles the row like a permission's.
  A second post of the key answers the row's decision, or an empty body, and asks no one.
- **The plug** gets `{:held, id, ref, wait}` for every kind, with the margin already in `wait`.
  It calls `written/3` after every decision.
- **The row word `answering` is now `deciding`**, Hold's word, for both kinds. `Table.start`
  also settles a row an older build left `answering`.
- `Table.decide/6` and `Table.decision/4` are gone. `Table.insert/5` returns the seen row's
  decision, and `Table.move/7` takes an optional actor.
- **The design's Intake section** now says that a tool call's row is written when the call is
  held, and it uses `deciding` for a permission. No model change: `Intake.tla` already says this.

Every behavior that Claude Code sees from both hooks is as before: the same responses, the same
deadlines, and a late decision dropped. The tests that said a pass, a deadline, a crash or a
restart writes no row now check the row the hold leaves. New tests cover a second post of a
call that passed, the row `deciding` before the decision is handed out, and a request that
closes while held, with the decision that comes later dropped.

## What was measured

- 500 allowed `PreToolUse` calls through the plug, against a stand-in callback that answers at
  once, each round trip timed: median 2.6 ms, p95 25 ms. 500 `Stop` posts (one row write each):
  median 0.7 ms, p95 4.6 ms. A held tool call now writes its row three times (`held`,
  `deciding`, `answered`) where it wrote once for a decision and never for a pass. The cost is
  well under the 5 s deadline. The machine was loaded, so the p95 values are rough.
- **Whether a held request learns that its client went away**, on Bandit 1.14.1, with a raw TCP
  client that posts and then closes:
  - a handler blocked in `receive`: still alive 3 s after the close;
  - a handler that writes a chunk every 100 ms: two writes succeeded after the close, the third
    returned `{:error, :closed}`, and the handler went down (`{:shutdown, :peer_closed}`)
    42 ms after the close.

## What I ran into

- With a row from the start, the old `wmon` race goes away. The callback's normal exit after its
  answer reaches `Intake` while the hold is `deciding`, and the answer comes first, because
  Erlang keeps the order of signals from one process. `decide` stops watching the callback when
  it takes the answer.

## Findings

### new-1. `Intake` does not know when a waiter's connection is gone

What happened: the design says a session with no waiter is known to `Intake`, "since it holds
each waiter's connection". Measured on Bandit: a handler that waits in `receive` is not told when
its client closes. It stays alive until it writes, and in a waiter that could be hours. Chunked
writes find the close by the second or third write after it.
Why: Bandit (ThousandIsland) reads the socket only when the handler asks for it, so no close
reaches a handler while it waits.
What I did: nothing built. The waiter is not built here.
What the design should change: the waiter's hold sends a heartbeat, a chunk of whitespace every
few seconds. The program ignores whitespace, and a failed write ends the hold (Hold's `Cut`).
The response is then chunked from the start: status 200 at once, and the due text as the last
chunk. Model the waiter's connection as able to die unseen until the next heartbeat. Its rule
that "a second connection replaces the first only when the first is gone" then reads "gone" as
a failed heartbeat, so a second connection, on its arrival, triggers a heartbeat to the first.
Without that, a session whose waiter died unseen refuses its live waiter, and no waiter is
left.

### new-2. The waiter's program is not settled: which program, and where its secret goes

What happened: the other hooks are `http` hooks, and their secret is in a header in the settings
file. `asyncRewake` needs a `command` hook, and the command must post, wait, and turn the answer
into stderr and exit 2. The natural program is `curl` inside `sh`, but `Programs` does not list
`curl`. A secret on curl's command line is visible in `ps` for the hours the waiter runs.
What I did: nothing built.
What the design should change: the waiter hook is `sh -c` around `curl`, with the secret
passed as a curl config on file descriptor 3 by a here-document (`-K /dev/fd/3`), so it never
appears in argv. The posted body is the Stop hook's input. If the response, stripped of
whitespace, is not empty, the script writes it to stderr and exits 2, and otherwise exits 0.
Add `curl` to `Programs` and to devenv, so a contract test can run the real script against
`Intake` with a stand-in hook input. Name the waiter's path, for example
`/hooks/<account>/waiter`, so its body is not stored as a `Stop` event.

### new-3. Which settings carry the waiter hook

What happened: the hooks are written per account (`Accounts.prepare/3`), so every session of an
account shares them, delegates included. The design says each *main* session's settings name
the waiter. A headless delegate does not take the waiter's wake, since its transport is
`stream`.
What I did: nothing built.
What the design should change: the waiter hook goes into the main session's launch overlay
(item 11's settings overlay, written by `ClaudeCLI` for the main role), not into the account's
settings. `Intake` offers the hook's fragment as a function, as `hooks/4` does for the account's
hooks. Wiring it in belongs to R7 or item 13, which start main sessions.

### new-4. A tool call's row is now written for every call

What happened: the design said that a pass writes no row, since every tool call posts
`PreToolUse`. With the tool hold in the permission hold's shape (F-119's new-3, this brief),
every held call writes a row with its tool input.
Why: one hold has one row from `held` on. The model's `DecidedHasRow` and the settle after a
restart need it.
What I did: built it so, and changed the design's sentence. The cost is above: 2.6 ms median per
call.
What the design should change: if the tool inputs in `intake_events` are unwanted (Transcripts
already holds them), a tool row can keep `data` empty until a decision. That is a change of one
column's content, not of the hold.
