# F-227: each role's permission mode is pinned, not the account's default

## What was built

- `ClaudeCLI` takes `:permission_mode`, one of `permission_modes/0` (what `claude --help` lists
  on 2.1.322: `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan`), and
  launches with `--permission-mode <mode>` after the effort, for an interactive session and for
  a headless one alike. An unlisted mode is refused `{:bad, :permission_mode}`, and none is no flag.
- `Sessions` takes `permission_modes:` (`%{main:, interactive:, headless:}`) over its default
  `auto`, `auto`, `manual`, and gives each launch its role's mode: a main session, an
  interactive delegate (its kind is delegate, its role parent), or a headless delegate.
- The config's `permission_modes` key, checked: only those roles, only listed modes. An
  agentless tree refuses it, as it refuses the other agent-only keys.
- The design's config table has the key. Its Remote Control line says an interactive delegate
  has Remote Control as a main session does, decided by the person running the framework and kept as it was.

## What was measured

On 2.1.322, a headless `-p` session with no flag, and one with `--permission-mode manual`, both
init with `"permissionMode":"default"`. `--permission-mode auto` inits with `"auto"`. So
`manual` is the mode whose init says "default", and the defaults reproduce what the end-to-end
run saw on 2026-11-23: interactive sessions in auto (the accounts' default), headless ones in
default.

Why pin at all: the run found every interactive agent in auto because of the accounts' own
default, with no permission prompts and no trust dialog. So the inbox's paths for interactive
agents were never exercised, and nothing in the framework said so. The person running it decided: a
mode per role in the config, defaulting to today's behavior.
