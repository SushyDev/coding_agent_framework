# F-232: the interactive stand-in writes its session file, as the real one does

## What was built

- `ScreenStandIn` makes `<CLAUDE_CONFIG_DIR>/sessions/` itself and writes `<pid>.json` in
  2.1.322's shape: `pid`, `sessionId`, `cwd`, `startedAt` and `updatedAt` (epoch ms),
  `procStart`, `version`, `kind` (`interactive`), `name`, `status`, and `waitingFor`
  (`dialog open`) while a dialog is drawn. The shape is the end-to-end run's
  `exit-dialog-session-*.json` records, in the fields `Registry.SessionFile` reads, plus
  `version`. It removes the file when it exits, as before.
- Its status follows its screen: `idle` at the empty box, `busy` in a turn (`--screen
  running` said `idle` before), `waiting` while its running menu is drawn (it said `idle`), and
  `idle` again once the menu is answered.
- It answers `auth status` with a logged-in login, as `HeadlessStandIn` does.
- `session_file: false` writes no file.
- `apps/caf_example/test/tree_main_test.exs`: the example app's whole tree, with the stand-in
  as its Claude Code, starts a main session through `Mains.start_main/5`, sees the stand-in's
  file, the start prompt, and `app-epic: main of app, on one, idle` in the tree, then ends it
  through `Mains.end_main/3` and sees the file go.
- `inlet_test.exs` has a test of the file itself: its fields at the menu, `idle` after it is
  answered, gone at exit, and none with `session_file: false`.
- One line in the design's test rules.

## What was measured

The brief's premise was not quite the cause. The stand-in already wrote a session file when
`CLAUDE_CONFIG_DIR` was set. Run on a whole tree, it failed in two other places, one after the
other:

1. `start_main` was refused `{:none_usable, %{"one" => {:unknown, {:login_check, "{:timeout,
   30000}"}}}}`: the tree checks each account's login with `claude auth status`, and the
   interactive stand-in took that as a start and waited for keys until its idle timeout.
2. With that answered, `start_main` answered `{:unknown, :no_session_file}`. The stand-in had run
   its start prompt, but `<config>/sessions/` did not exist. Every test that used it made the
   directory in its setup (`SessionsSetup`, `MoverSetup`), and the stand-in's write failed
   silently without it. A whole tree makes no such directory; Claude Code makes its own.

With both fixed, the main session reached running and idle on the tree.

## What I ran into

- `end_main` was refused `{:sending, [1]}` until the stand-in was written with `transcript:
  true`: the brief sent at the start stays `sending` until the transcript shows it. The tree
  test uses `transcript: true`. See new-2.
- No test passed only because no file was written. No test checks a missing file with this
  stand-in (the `:no_session_file` tests use `ClaudeStandIn`'s `:never`), so nothing uses
  `session_file: false` but its own test. The inlet tests run it with no config directory, so
  the `busy` and `waiting` changes do not reach them; the sessions, prompts, mains and delegates
  tests with it all pass.

## Findings

### new-1. A stand-in leaned on its tests' setup for what the real program does itself

What happened: `ScreenStandIn` wrote its session file into a directory only test setups made,
and took `auth status` as a start. Every test passed, and no whole tree with it could reach
running. Why: each test built the parts around it, so the parts' own setup was never exercised.
What I did: the stand-in makes its directory and answers `auth status`; a test starts the whole
example tree with it. What the design should change: the line added under the test rules. It
could also say that each stand-in is run at least once on a whole tree.

### new-2. The interactive stand-in writes no transcript by default

What happened: on a whole tree, a main session's brief stays `sending`, and `end_main` refuses
`{:sending, [id]}`, unless the stand-in writes the start's prompt to its transcript, which it
does only with `transcript: true`. Claude Code always writes one. Why: the option was added for
the tests that needed it (F-153), and the rest never deliver through the transcript. What I
did: the tree test passes `transcript: true`. What the design should change: whether the
stand-in writes its transcript by default, as the real program does, with an option to turn it
off for a test that checks a missing one. Changing the default touches every test that uses it,
so it is not done here.

### new-3. `waiting` for the running menu is inferred, not measured

What happened: the stand-in now says `waiting` with `waitingFor: "dialog open"` while its menu
(F-198) is drawn. The record is 2.1.322's exit dialog; what the real file says at that menu was
never captured. What the design should change: capture the session file at a running menu in
the next end-to-end run, and keep the stand-in to it.

## After review (main session)

The whole-tree test failed once under the gates' load: `end_main` was refused `{:not_idle, "busy"}`.
The stand-in wrote the brief's prompt file before it said `busy`, so the test, having seen the
prompt and the tree's `idle`, could read the `idle` from before the turn. The stand-in now says
`busy` before it writes the prompt file, and the test waits for the session file's next `idle`, the
turn's end, before it ends the session. Rebased onto F-230 and F-233: the stand-in's own question
screen (F-230) now says `waiting` while drawn, as its menu does.
