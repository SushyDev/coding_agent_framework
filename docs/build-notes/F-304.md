# F-304: a heavy run with no agent may go to another host, and an away host falls back

## What was asked

An embedding app found two things with F-296 in use:

1. A heavy run the app starts itself (its lander or a script, not a framework agent) asks under
   a name such as `run-<worktree>`. Marked for another host, it was refused `no_worktree`: the
   run's place came from `Sessions.Agents.place/2`, which knows only agents' rows.
2. An entry names one host. With that host away (asleep), the run was refused `host_away` and
   `caf-run` exited 75, though the workstation could have run it.

## The model first

`model/tla/RemotePlace.tla` is new. It models one run whose entry names two other hosts and then
the workstation (`r1`, `r2`, `ws`): the plug's choice from what `Hosts` keeps, the placement's
find, the one fallback, the lease, the start settled by its reply or by the fence, the host away
mid-run, and other work finding a host and keeping the answer at any time (and a kept away
coming due). Its header names `Runs.Plug`, `Runs.Remote`, `Hosts` and `Jobs`.

- Invariants: `OneHost` (a run has a find, a slot or a job at one host at a time),
  `NeverTwice` (the command starts at most once), `OneSlot`, `NeverMoved` (a job that was sent
  stays its host's); liveness `RunEnds` and `SlotFreed`.
- Breaks, each failing its invariant: `AskNextEarly` (the plug gives a slow find up and asks the
  next host while the find runs on: `OneHost`), `LeaseFirst` (the slot asked before the
  placement and kept when it falls back: `OneSlot`), `CutAsAway` (a start whose reply was cut
  taken as never sent: `NeverTwice`), `MoveOnAway` (a job whose host went away mid-run started
  on the next host: `NeverMoved`).

What the model settled for the code: fall back only on a placement refused `host_away` before
anything was sent, which `Jobs.run/6` gives before the job's row and its lease (the find is its
first step). So the code falls back only when `Jobs` has no row for the job, and never once the
start may have been sent.

TLC first took 5 minutes on the design's liveness with one fairness condition per action and
host (32 of them). Grouping them into one weakly fair `Moves` and one strongly fair `Settles`
brought it to 4 s, the same 2 988 distinct states.

## What was built

- **The place of a run no agent asks for.** `Runs.Plug`'s `where:` is now a function of the
  wrapper's agent and its directory. The tree's (`run_place/4` in the surface) answers an agent's
  place as before when the name is an agent's row, and otherwise `Runs.folder/2`: the wrapper's
  directory at or under a configured project's checkout (`Mains.project/3`'s `repo`) is that
  checkout, copy `+checkout` (a name no agent can have, so it never shares an agent's copy); at
  or under `<home>/worktrees/<project>/<name>`, a directory there of a configured project, it is
  that worktree, whose copy is the one an agent working there has. Anything else is
  `{:refused, :no_worktree}`, as before. These are the folders F-286's trust rule names.
- **How the folder reaches the plug, and why it cannot name another.** The wrapper sends its
  `$PWD` as the form field `cwd` (F-296 already did, for the directory in the copy). The plug
  cannot check that field: any process that reads `<home>/runs.curl` (mode 0600) may ask. But
  the folder only selects one of the known roots: the plug syncs the known checkout or worktree
  root, never the path given, `Path.expand/1` takes `..` out before the match, and the run's
  directory in the copy is checked to be inside that root (`Runs.Remote`'s `inside/2`). The
  command must still match the app's own entry for that host. So the worst a false `cwd` does is
  run an app-listed command on a tree the framework already copies for its agents.
- **Hosts in order.** `Runs.heavy/1` takes `host: "mac"` or `host: ["mac", "ws"]` (non-empty,
  each named once); the config checks each name as before. `Runs.place/2` answers the first
  (nil for the workstation's name), which the rewrite writes as `--host`; `Runs.hosts/2` answers
  the whole list. The plug takes the hosts from the wrapper's on and chooses the first that
  `Hosts.held/2` (new: what `Hosts` keeps, no ssh; a held host whose `retry` is due reads not
  held) does not refuse; the workstation (the plug's `host:`) is never held. When every host is
  held it places the first, as before F-304, so a host that came back joins at once. If that
  placement is refused `host_away` and `Jobs` has no row for the job, it goes to the next host
  of the rest once (`Runs.Remote.run/5`'s `fallback`). Each move sends `note mac away; running
  on ws` before the run's own lines, which the wrapper prints as `caf-run: mac away; running on
  ws` on its errors. On the workstation the run is then the ordinary local one: `granted` under
  that host's slot, and the wrapper `exec`s the command in its own directory.

- **Results back** (added to the unit while it was built). `caf-run --fetch <path>`, repeated,
  names paths relative to the worktree; the wrapper sends them one a line in the form field
  `fetch` beside its host, and `Runs.ask/1` refuses an absolute one, or one with a `.` or `..`
  part (`Jobs.run/6`'s own rule), as `bad_fetch`: 75 before anything runs. `Runs.Remote` passes
  them to `Jobs.run/6` as `fetch:`, and its end line carries what came back: `ended exit 0
  fetch done`, `fetch none`, or `fetch not_fetched conflict | unknown`. The wrapper prints
  `caf-run: fetch <that>` on its errors when it named paths, and `caf-run: fetch not_fetched`
  for an end unknown or a cut. A run on the workstation, a fallback's included, sends no
  `fetch` and ignores it: the file is already there.

The config an app writes:

```elixir
workstation: "ws",
hosts: %{"mac" => %{host: mac, dir: "/Users/me/caf"}},
heavy: [%{match: ~r/\bmix test\b/, class: :heavy, host: ["mac", "ws"]}]
```

and its lander, with no agent, from the project's checkout or a worktree under the home:

```sh
'<home>/bin/caf-run' --host 'mac' --fetch out/events.json heavy "$id" 'run-app' -- 'mix test'
```

The Scheduler is unchanged: the choice is made before the plug asks for a slot.

## Tests

In `apps/caf_surface/test/remote_host_test.exs`, on the stand-in remote host, a new describe
with the plug placed by folder and `held:` the tree's `Hosts`:

- from the project's checkout, a run no agent asks for runs on `mac`: exit 6, its output, one
  `started on mac` line, one job row `exited` 6, no workstation lease;
- from a worktree under the home, it runs in that worktree's copy: its file comes back;
- from an unknown folder, and from a folder under the worktrees root that is no worktree:
  exit 75 with `no_worktree`, no job row, no lease;
- an entry `["mac", "ws"]` with `mac` held away: exit 4 on the workstation, the one line, no job
  row, one lease (the workstation's), and `Hosts`' kept `at` for `mac` unchanged, so no find;
- `mac` unknown and found away at its placement: the same on the workstation, once, and `mac`
  now kept away;
- an entry of `mac` alone, found away: refused 75 `host_away`, no row, no lease;
- `--fetch out/events.json` on a run that writes it in its copy: exit 0, `caf-run: fetch
  done`, and the file in the worktree after the end;
- `--fetch ../x` and `--fetch /etc/passwd`: 75 `bad_fetch`, no job row.

`config_test.exs` checks a list's hosts are declared and each named once; `Runs.heavy/1`,
`place/2`, `hosts/2` and `folder/2` have doctests.

## Findings

### new-1. A request that takes whichever host's slot frees first

What happened: the brief left it out. With `["mac", "ws"]` both busy, the run queues on the one
the choice took, though the other may free first.

Why: a request names one `where`. An any-of request needs the Scheduler to hold one request
against several hosts' slots, grant it on the first that frees and drop the rest in the same
step (its one process makes that atomic), and answer which host won. But today a remote run's
placement (the find) comes before its lease, and `RemotePlace.tla`'s `LeaseFirst` Break shows
what a lease taken first does when it is kept on a fallback. So `Jobs.run/6` would have to take
its host from the grant and find that host after it, giving the slot back at once when the find
answers away, and the plug would need the grant's host before it knows whether to run locally.

What the design should change: if wanted, a unit that adds `where: %{hosts: [..]}` to the
Scheduler's request (one grant, the others dropped in the same step), a `Jobs.run/6` that finds
its host after the grant and releases on a find away, and a spec, a variant of `RemotePlace.tla`
with two runs, for `OneSlot` under that race.

### new-2. Every host held: the first is placed

What happened: the brief says the run goes to the first host `Hosts` does not hold away or
lacking. For an entry of one host (every F-296 entry) or of other hosts only, that can be none.

What I did: then the first is placed as before F-304, so its find runs and a host that came
back joins at once; refusing at once would hold a single-host entry refused for `retry` (30 s)
after one failure, which F-296's "the next placement finds the host again" rules out. The model
has the workstation last, so it never meets this case.

What the design should change: say so in "Hosts", as the design lines here now do.

### new-3. A home reached through a symlink

What happened: `Sessions` makes worktrees under the physical path of `<home>/worktrees` (`pwd
-P`), while the tree's folder check compares the wrapper's `$PWD` with `<home>/worktrees` and the
checkout paths as written. On a home through a symlink (macOS `/tmp`), a wrapper whose `$PWD` is
the physical path would be refused `no_worktree`.

Why: no part hands the surface the physical root, and `Runs.folder/2` follows no symlink, on
purpose, so a link inside a known folder cannot take it elsewhere.

What the design should change: I recommend `Sessions` expose the worktrees root it resolved and
the surface pass both the written and the physical forms of each root to `Runs.folder/2`.

### new-4. A placement that finds the host lacking does not fall back

What happened: the fallback is on `host_away` alone, as asked. A host whose find answers
`no_program` or `old_rsync` at the placement refuses the run (75), though the next host could
run it. At the choice, a host held lacking is skipped, as asked.

What the design should change: decide whether a placement refused lacking falls back too. The
model's rule is the same for it (nothing was sent), so it would be one more case in
`Runs.Remote`'s `away/2`.

### new-5. A fetch of a path the job never wrote answers `done`

What happened: while I built the fetch test, a first version of its command failed before it
wrote `out/events.json` (the stand-in host has no `mkdir` on its PATH), and `Jobs.run/6` still
answered `fetch: :done`, so the wrapper printed `caf-run: fetch done` with nothing come back.

Why: `Copies.fetch/5` takes a path missing in the copy as nothing to bring, not as a miss.

What I did: nothing in `Jobs` or `Copies`; the line says what `Jobs` answers.

What the design should change: I recommend `fetch` answer the paths missing in the copy, for
example `{:missing, paths}`, so a caller can tell a result that came back from one never made.
The wrapper's line would then say `not_fetched missing <paths>`.
