# F-238: the gates hold on a loaded machine

## What was built

The host runs several builders and their gates on 15 cores, at load 25 to 60. Each test the
brief names failed on time, not on behavior. For each, this unit found what the test waited on
with a bound that load breaks, and fixed that.

### One factor, read once: `TestHost.read_load!/0` and `scaled/1`

Where the bound is the length of work that load stretches (a cold VM's boot, a stand-in's
redraw), the bound is scaled, the same way for every such test, from one place.
`TestHost.read_load!/0` reads the host's 1, 5 and 15 minute load averages once, as the suite
starts (`/proc/loadavg` on Linux, devenv's `sysctl -n vm.loadavg` on macOS). It keeps the
factor `max(1, ceil(largest average / cores))`: on 15 cores, load 8 gives 1, load 25 gives 2,
load 45 gives 3. `scaled(ms)` is `ms` times that factor. It raises when the suite never read
the load, so no bound is left unscaled by accident. The two helpers whose tests call it,
`caf_sessions`' and `caf_surface`'s, call `read_load!/0` and print the reading:

    test VM: load 47.9 on 15 cores, load-sized bounds x4

A wait on an announced event still ends on the event. The factor only sizes the bound past
which it gives up. It lives in a `:persistent_term` key, set once per test VM: the host's load
is the VM's, whatever instance a test starts. It is a test aid, so the library's rule of no
global state does not reach it.

### `SessionsDialogTest`: the Inlet's 2 s read back

The cause, reproduced. A press of a dialog's option (`Inlet.choose/5`) sends the keys and then
reads the screen until the option shows selected, and after Enter until the dialog leaves. Each
read waits at most `see:`, 2 s. On a loaded host the stand-in redraws late. Past 2 s the press
is unknown: `{:not_selected, _}`, and no Enter goes. The trust answer is then marked `unknown`,
and is never pressed again. The start sees its pane on the trust dialog with an answer marked,
so it waits for its deadline. The test's clock is an `Agent` frozen at setup, so that deadline
never comes, and the start waits for its call's whole bound: 30 s plus 30 s of slack, 60 s.
That is exactly ExUnit's timeout, which fired first, with the start "still in its trust and
imports dialogs", as F-230's gate saw.

A throwaway probe showed it. The probe's dialog callback stopped the stand-in (`SIGSTOP`) for
3 s while the trust press ran. With the 2 s `see:`, `Sessions.start` answered
`{:unknown, {:timeout, 60000}}` after 60.0 s, the trust answer marked `unknown`. With the
scaled `see:` (x4 at load 48), it answered `{:unknown, {:dialog, :imports}}` in 3.5 s, trust
`sent`. The probe was removed.

The fix: `Inlet.start_link/1` takes `see:`, the instance's bound for a `type/4` or `choose/5`
call that names none. The default stays 2 s, so the app's tree runs as before. The test starts
its `Inlet` with `see: scaled(2_000)`. `Sessions`' press bound (`@press`, 20 s) still holds two
such reads up to a factor of 4, which is load 60 on 15 cores. Past that, a press comes back
unknown in its bound, never hung.

### `HomeLockTest`: a cold VM's first eval

F-223's rerun and F-232's gate failed "a home held by another VM refuses a start, and is taken
once that VM dies": the announce file was not there (`enoent`). The test spawned
`Code.eval_string` in a fresh `:peer` VM and polled for the file the eval wrote, with
`read_when/2`'s 5 s bound. A cold VM's first eval loads Elixir's evaluator, and on a loaded
host that takes more than 5 s. Now the peer call itself evaluates: it spawns the holder, which
takes the home and sends back its answer, then lives on. The call answers once the holder
holds the home, so the test waits on that answer, not on a file it polls. Its bound, the
peer's boot (45 s, F-215's own sizing for a cold VM) and the test's ExUnit timeout (90 s) are
`scaled/1`'s. The other five tests in the file each took under 1.4 s at load 50, and wait on
messages or on the start's answer.

### The model test is dropped from `mix test`

`caf_test`'s "every fast TLC configuration passes" ran `bin/check-model all` under a 300 s
ExUnit bound. F-234 saw it time out even alone, while `bin/check-model` passed on its own.
`gate-test` already left it out (`--exclude model`), and `gate-model` runs the same script with
no bound but TLC's own. So the test only ran under a bare `mix test`. There it repeated the
gate's half-hour TLC work next to every async test, under a bound no one can size for a host
whose load is unknown. It is removed. `gate-test`'s `--exclude model` goes with it, and so does
`:tlc` in `TestHost`'s programs, which only that test ran. TLC runs in one place, `gate-model`,
and `bin/check-model` checks `CAF_TLC` itself.

### `bin/check-model`: the load beside each time, and the 30 s rule

Each configuration's line now ends with the host's 1-minute load average, read as that
configuration starts, and the core count (coreutils' `nproc`):

    == HomeLock_Design (HomeLock.tla)
       172 states generated, 57 distinct states found; depth 11; 4 s at load 50.55 on 15 cores

No check of the 30 s rule existed: the design leaves it to a unit that changes a spec, timing
the fast set on an idle host. The script now judges each fast configuration that takes over
30 s. Under a load below the core count, it fails ("move it to slow/ or shrink it"). At or over
the core count, the time says nothing about the configuration, and it prints "not judged".
When the load cannot be read, it fails, since nothing shows the time was load's. The slow
configurations are never judged.

The average also holds this run's own earlier TLC work, which uses every core. So it reads high
rather than low. A loaded host never fails a configuration that is fast. A slow one on an idle
host can go unjudged after a long stretch of TLC, and the design's idle timing still catches it
(new-4).

## Findings

### new-1. The Inlet's 2 s read back is the app's bound too

What happened: on a loaded host a stand-in's redraw took longer than the Inlet's 2 s `see:`.
The press came back unknown, and the start stayed on its trust dialog for a person. Why: the
real Claude Code redraws on the same loaded cores, so the app's own dialog presses, and typed
writes (`type/4`'s `see:`), meet the same bound. What I did: made `see:` an `Inlet` option per
instance, default unchanged, and sized only the test's. What the design should change: decide
what an app's tree starts its `Inlet` with. That could be a `Config` field, or a bound taken
from the host's load as the tests take theirs. `Sessions`' `@press` (20 s) would then have to
cover two such reads.

### new-2. A press whose pane closes waits out its whole read back

What happened: "No, exit" ends the stand-in, and its pane with it. `Inlet`'s check that the
dialog left reads a failed capture as "says nothing", so it waits the whole `see:` and answers
`{:unknown, {:still_shown, _}}`. Why: a capture that fails is not taken as the dialog gone.
What I did: nothing; with the scaled `see:` such a test takes 6 to 10 s, inside its bound. What
the design should change: a pane that `Tmux` reports gone after Enter could read as the dialog
left, `sent`, once the model says a pane gone is that.

### new-3. A frozen test clock turns a start's undecided wait into ExUnit's timeout

What happened: with the test's clock frozen, a start that never decides waits for its call's
bound, 60 s, which equals ExUnit's timeout. The failure showed as an ExUnit timeout with no
answer to read. Why: the start's deadline is on the test's clock, and its call's bound is on the
VM's. What I did: removed the cause of the undecided start (the late read back). What the design
should change: nothing in the library. A test aid could give `SessionsSetup`'s starts a call
bound under ExUnit's, so a late start fails with its answer.

### new-4. The 30 s rule's load reading holds TLC's own work

What happened: the 1-minute average at a configuration's start includes the run's earlier
TLC, which uses every core. Why: a load average cannot tell this run's work from the other
builders'. What I did: judged by it anyway, which errs toward "not judged", never toward a
false failure, and said so in the script. What the design should change: if the rule should be
checked on a loaded host too, judge TLC's CPU time, or run the timing with `TLC_WORKERS` fixed
and the load read before the first configuration.

### new-5. Other fixed bounds on load-stretched work remain

What happened: other tests start an `Inlet` with the 2 s `see:` (`prompts_test.exs`, the
`Mailbox` typed and launch tests, `inlet_test.exs`), and others size bounds by hand for a
loaded host (`shell_group_test.exs`' 90 s, `registry_test.exs`' 300 s). Why: only the tests
the brief names were in scope. What I did: left them. What the design should change: a unit
that sees one of them fail on time moves its bound to `scaled/1`. A sweep could do all at once.

### new-6. Why the model test timed out alone was not found

What happened: F-234 saw the model test run past its 300 s bound alone, while
`bin/check-model` passed alone.
Why: not found. Dropping the test made it moot, so it was not chased. What I did: removed the
test. What the design should change: nothing, unless TLC is run from a test again.
