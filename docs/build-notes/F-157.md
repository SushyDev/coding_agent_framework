# F-157: the Stop hold and a pause (part A)

The brief had three parts: A, the `Stop` hold with Claude Code's cap and a pause; B, heavy
commands rewritten into a wrapper under a lease; C, a small backlog. Part A alone, with its
model, tests and docs, came to about 1,250 changed lines, so as the brief says I land part A
now and report. Of part C only `Store.transaction/2`'s rollback is in this branch (it is a few
lines and a test). Part B and the rest of part C are left (below).

## What was built

- **The model first.** `Intake.tla` gains the `Stop` hold as `Hold.tla`'s fourth instance
  (`HS`), with Claude Code's count of blocks in a row (`ccBlocks`) and its override past `Cap`
  as the environment's act (`StopRead`), `Intake`'s own durable count (`fBlocks`), reset only
  by a tool call's `PostToolUse` post (`ToolRuns`), a new turn after which Claude Code may or
  may not reset its count (`NewTurn`), the `stop_cap` hold a person answers (`CapAnswered`),
  and a pause set and lifted (`PauseSet`, `PauseLifted`). New properties: `NeverOverridden`,
  `CountKept` (Intake never counts fewer than Claude Code), `NotWhilePaused`,
  `StopOneResponse`, `StopLateDropped` and the liveness `StopRequestsEnd`; Breaks `NoCap`,
  `CountInMemory` and `IgnorePause`, each failed by TLC. Configurations `Intake_Stop` and
  `Intake_StopPause`. Every other Intake configuration sets the new constants to nothing.
- **The waiter, which one is kept.** `Intake.tla`'s new `Superseded`: the newest waiter is the
  session's, and each older one still held is answered empty at once. A waiter whose text is
  in flight is kept, and a newer one waits behind it. `EmptyOnlyAtDeadline` now allows an empty
  answer to a superseded waiter; `Break_Intake_RefuseSecond` (a newer one turned away) still
  fails it. `WaiterTaken` counts `passed` among the ends.
- **`Prompt.tla`**: at the cap's last block the app's callback may pass, as below it; only its
  block becomes the `stop_cap` prompt. `NoCap` still fails.
- **`Intake`**: the `stop:` callback makes each `Stop` a hold of kind `stop` (deadline
  `stop_deadline:`, 570 s, under the hook's 600 s, which `hooks/4` writes with `:stop`, beside a
  `PostToolUse` hook). The agent and project lookups and the callback run in processes of their
  own. The count is a row per session in `intake_stops`; a block below the cap's last writes it
  before the response goes out; the cap's last (`stop_cap:` 8, less one) moves the row's new
  `prompt` column to `stop_cap` and waits for `answer/4` with `:go_on` or `:end`; past it the
  hold passes with actor `capped`. `pause/5` and `lift/3` keep `intake_pauses`: `:hold`, or the
  pause's word `:pass` or `{:block, reason}` (actor `pause`), an agent's before its project's.
  A callback's answer that comes while its `Stop` is paused waits for the lift.
- **Waiters** in `Intake`: as modeled; the heartbeat sent to the first at a second's arrival
  is gone, since the first is answered empty.
- **`caf_example`**: `tool_hooks` takes `stop:`; `Intake` gets the project lookup from the
  agent row.
- **`Store.transaction/2`** rolls back and re-raises when its function raises, throws or exits
  (part C).
- **Design**: "Intake" has the held `Stop` and the `stop` row of the kinds' table; "Delivery
  into a main session" says which waiter is kept; item 14's `Stop` paragraph takes F-167's
  new-1.

## What I ran into

- **Two `Stop`s with the same body would be one row.** A `Stop` has no id, so its key was a
  hash of its body, and two blocks with the same last message would read as a second post of
  one event and pass. Claude Code never posts one event twice, so a held `Stop`'s key adds the
  time and a unique number.
- **What resets the count.** The measurement says "no tool call between". `Intake` sees a
  tool call only by a hook, so the `Stop` hold's settings add `PostToolUse`. Whether a person's
  prompt or a wake resets Claude Code's count is not measured, so `Intake` does not reset on
  them; it may count high, which opens the person's prompt early, never late (new-1).
- **No `Prompts` box yet.** B6 is not built, so the `stop_cap` prompt is the `Stop` row with
  `prompt` `stop_cap`, cued on Intake's topic and answered by `Intake.answer/4`, as a held
  permission request is today.
- **The pause's "hold" is bounded by the hook's timeout.** A `Stop` held by a pause passes at
  570 s, so a pause longer than that lets each turn end after about ten minutes (new-2).

## Findings

### new-1. What resets Claude Code's count of `Stop` blocks is half measured

What happened: the reading says 8 blocks in a row "with no tool call between". Whether a
person's prompt, a wake by the waiter, or a turn that ended resets the count is not known.
Why: only the tool call was varied.
What I did: `Intake` resets only on a `PostToolUse` post, so it counts at least as many as
Claude Code; `Intake.tla`'s `NewTurn` lets Claude Code reset or not, and `CountKept` holds
either way.
What the design should change: measure on the pinned release whether a person's prompt and a
wake reset the count; if they do, `Intake` resets on `UserPromptSubmit` and on a delivery's
take, and fewer `stop_cap` prompts reach a person.

### new-2. A pause that holds lasts at most the `Stop` hook's timeout

What happened: a `Stop` held by a pause passes at its deadline (570 s of 600 s), and the turn
ends.
Why: Claude Code reads no hook past its `timeout`; a longer `timeout` keeps a turn open as
long, with its session's process held.
What I did: the deadline passes, as every other hold's does; the pause's word (`:pass` or
`{:block, reason}`) is there for a pause meant to last.
What the design should change: decide what a long pause is for. If it is "finish this turn
and take no more work", it is `:pass` plus `Mailbox` holding the agent's due rows while the
pause is on, which is a `Delivery.tla` change, not `Intake`'s.

### new-3. Part B and the rest of part C are not built

What happened: part A ran past the brief's 1,000 lines.
What is left: part B (the `caf-run` wrapper and the `PreToolUse` rewrite of a heavy command,
under a lease; then `run` leaves the agents' list) and part C's `Jobs.Table.meta/0` and
`Copies.Table.meta/0`, the `Scheduler`'s pressure cue and macOS source, and a headless
delegate's turn reading its own background command as running.
What the design should change: nothing; the next units take them.
