# F-98: `service_start`: names checked by `Services`, a local port, and one deadline

## What was built

- **Names.** `Services.start/5` checks the name (1 to 64 letters, digits, `-` or `_`) before
  anything else and refuses others with `{:refused, {:name, name}}`. `MCP` no longer has the
  pattern: it only checks that a name is a string, and passes `Services`' answer through. A
  name with a bad form is now `{"refused": ["name", name]}`, not `["bad", "args"]`.
- **The local port.** `service_start`'s `opts` takes `local:` (1..65535, only with `forward:`),
  passed as `forward: {port, local}`; without it the local port is the service's port. In the
  same step that writes the new row, `Services` refuses a local port another live row holds
  (any state but `ended` or `refused`) with `{:refused, {:local_taken, holder}}`, naming that
  service, before anything starts.
- **One deadline.** `service_start` takes an optional `timeout` (ms, at most `:cap`, as `run`'s).
  `Services.start/5` takes it as `:timeout`, turns it into a deadline, and cuts each step's
  timeout (the copy's wait for its lock, the sync, dtach's reply, the forward's open) to what is
  left. Without it each step keeps its own default, as before. `:timeout` is not passed on to
  the end a failed start makes, whose grace is its own.
- The design's `service_start` row names `local:` and `timeout`.

Tests: `apps/caf_services/test/services_test.exs` (six bad names and the 64-character edge, with
no row written; a local port held, refused by name and free again after the stop; a start
bounded by a 4 s deadline with a 60 s forward wait ends at the forward's deadline) and
`apps/caf_mcp/test/mcp_services_test.exs` (a name and a local port answered by `Services`,
`local` without `forward` and a bad `timeout` refused as bad arguments).

## Findings

### new-1. A deadline that is gone before a step still lets that step run once

What happened: a step given what is left gets 0 ms when the deadline has passed, but the start
does not stop there: dtach is still asked, and the forward's first read still happens. Why: a
start that has begun must be settled from the pid file, or a program could run unrecorded.
What I did: nothing. What the design should change: say that a deadline bounds the start's
waits, not its last reads, or name a refusal for a start whose deadline passed before the hold.

### new-2. A local port is checked against services only

What happened: `local_taken` looks at the service rows. Another program on the workstation
holding the port still fails the forward at its open (`{:forward, :not_open}` or `:exited`), as
before. What I did: nothing. What the design should change: say that is enough, or that
`Services` probes the port before the sync.
