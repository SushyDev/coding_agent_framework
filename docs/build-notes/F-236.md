# F-236: the app's tool hooks take a session's start (stopped at the measure)

An embedding app gives each session a short text of its own rules at the session's start, from
a plugin hook of its own. It wants to drop that hook and use `ToolHooks` (F-195) instead, which
has `pre_tool_use`, `post_tool_use` and `stop`, and nothing at a session's start. The brief's
first item was to measure whether a `SessionStart` hook's `hookSpecificOutput.additionalContext`
reaches the model from an `http` hook as the framework's is. If it cannot, the unit stops there
with a finding and builds no command-hook path.

It cannot: Claude Code 2.1.322 never runs an `http` hook on `SessionStart`. This unit built
nothing. It adds this note only.

## What was measured

- **The bundle.** Claude Code 2.1.322's hook matcher removes every `http` hook from the matched
  hooks when the event is `SessionStart` or `Setup`, and logs "Skipping HTTP hook <url> — HTTP
  hooks are not supported for SessionStart". The check keys on the event's name alone, not on
  its `source` or on the session's mode, so it covers `startup`, `resume`, `clear` and
  `compact`, interactive and headless alike. The output parser would read
  `additionalContext` (and `initialUserMessage`) from a `SessionStart` hook's
  `hookSpecificOutput`, but an `http` hook's response never gets that far.
- **A headless run** (`-p`), in a scratch config directory of this unit's own: a `SessionStart`
  with a `command` hook and an `http` hook to a listener on 127.0.0.1. The command hook ran,
  and the debug log shows its output parsed ("Parsed initial response: {…"additionalContext":
  "CMD-CTX-…"}"). The `http` hook was skipped with the line above, and the listener got no
  post. The scratch config is not logged in (F-195's new-1), so the run ends at "Not logged
  in" after the start's hooks. Whether the model reads the command hook's context was not
  measured, since it does not decide this unit.
- **An interactive run**, on a tmux server of this unit's own socket, stops at the login
  screen before any hook runs, so no interactive start was measured. The matcher's check above
  is the same code path for both.
- Not measured, for want of a logged-in setup: `resume`, `clear` and `compact` starts. The
  bundle's check does not read the `source`.

## What I ran into

- A tmux socket under the scratch directory is past the 104-byte limit of a Unix socket
  path; the interactive probe's socket went in a short temporary directory instead.
- A builder's scratch config directory is not logged in (F-195's new-1), so no measure here
  reached the model.

## Findings

### new-1. An `http` hook cannot take a session's start, so `ToolHooks` cannot give one

What happened: Claude Code 2.1.322 skips every `http` hook on `SessionStart` (and `Setup`)
before it runs, for every `source`, and logs that HTTP hooks are not supported there. The
framework's hooks are all `http` hooks but one, so a `session_start/3` callback would never be
called. Why: Claude Code's own rule, read in its bundle and seen in a headless run's debug log.
What I did: stopped at the measure, as the brief says, and built neither the callback nor a
command-hook path. What the design should change: decide whether a session's start is the
framework's to give. If it is, the smallest path is a `command` hook in the accounts' settings
of the waiter's shape (`Intake.waiter_hook/5`: `sh -c` around `curl`, the secret on fd 3),
which posts the start to `Intake` and prints its answer as the hook's JSON. That path needs its
own measure on a logged-in setup, for each `source` and in both modes, before it is built. If it
is not, the app keeps its own plugin hook, and `ToolHooks`' doc says why there is no
`session_start/3`.

### new-2. The framework's own `SessionStart` hook never posts

What happened: `Intake.hooks/4` writes an `http` hook for each name in `Event.names/0`,
`SessionStart` among them, and the design's Intake section ("Transport") lists `SessionStart`
among the events each account's settings post. Claude Code 2.1.322 skips that hook (new-1), so
`Intake` never gets a `SessionStart` row, and each session's start writes a "Skipping HTTP hook"
line in its debug log. Why: the hook list was written before this rule was known. No part reads
a `SessionStart` row: the design's "Lost events" already names the session file as its stand-in,
and only `IntakeSource`'s test posts one by hand. What I did: nothing; it is outside this unit.
What the design should change: drop `SessionStart` from the `http` hooks and from "Transport",
and say that the session file is how a start is known; or move it to the command path, if
new-1's decision builds one.

## Gates
