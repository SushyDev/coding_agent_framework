# F-236: the app's tool hooks take a session's start

An embedding app gives each session a short text of its own rules at the session's start, from
a plugin hook of its own. It wants to drop that hook and use `ToolHooks` (F-195) instead, which
had `pre_tool_use`, `post_tool_use` and `stop`, and nothing at a session's start.

The brief's first item was to measure whether a `SessionStart` hook's
`hookSpecificOutput.additionalContext` reaches the model from an `http` hook as the framework's
is, and to stop with a finding if it cannot. It cannot: Claude Code 2.1.322 never runs an `http`
hook on `SessionStart`. The builder stopped there (new-1, new-2). The main session then measured
a `command` hook on a logged-in setup and decided to build the start on one, shaped like the
waiter's; this note records both rounds.

## What was built

- **`ToolHooks.session_start/3`**, optional as the others. The event has `agent`, `account`,
  `session_id`, `cwd` and `source` (`Intake.start_event`). It answers `:pass` or `{:context,
  text}`, within `Intake`'s `tool_deadline`, else a pass. `ToolHooks.implemented/1` and
  `Config.hooks/1` name it, and the tree hands it to `Intake` as `session_start:`.
- **The start's hold in `Intake`.** With the callback, a `SessionStart` post is a hold of a new
  kind, `start`, asked in a process of its own as a tool call is, under the same deadline and
  the plug's same 1.5 s margin. `{:context, text}` answers
  `{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": text}}`,
  checked as the other contexts are (UTF-8, at most 10,000 characters, else a pass whose row's
  `problem` says `context_too_long` or `bad_answer`). A pass, any other value, a crash and the
  deadline are an empty body. Each start gets a key of its own, as a `Stop` does: a session
  starts again at each resume, clear and compact under one session id, often with one source
  twice, and the event's key (`session_id` and `source`) would answer the second start from the
  first one's row. Without the callback a `SessionStart` post is stored as before.
- **The start's command hook, `Intake.start_hook/4`.** `sh -c` around `curl`, as
  `waiter_hook/5` is, the secret on file descriptor 3 by a here-document, so it is in no
  process's arguments; the two now share `curl_command/6`. It posts the hook's input to
  `/hooks/<account>`, prints the response on stdout and exits 0. `curl -f` makes a refusal's
  status a failed post, which prints nothing, so a framework that is down or a wrong secret
  never keeps a session from starting. Its `timeout` is 10 s, over the deadline and the margin.
- **Written only for the callback.** `Accounts.prepare/3` adds the start's hook when `tools`
  has `:session_start`, from `:programs`' sh and curl (`{:refused, {:no_program, [:sh,
  :curl]}}` without them). A module without the callback gets no `SessionStart` hook at all.
- **The framework's own `http` `SessionStart` hook is gone** (new-2). `SessionStart` moved from
  `Event.names/0`, the events every account posts, to `Event.tool_names/0`, the ones posted
  only for an app's callback. Nothing read its rows; the session file stays the one reader of a
  start.
- **Docs.** `Intake`'s and `ToolHooks`' `@doc`s, `start_hook/4`'s with a doctest, the plug's,
  and the design: the Transport bullet, "Lost events", the kinds (six now, with the `start`
  row), "A held `SessionStart`" with the main session's measurement, the config table, and the
  build history. README's status has a line.
- **The model.** No protocol change: the start's hold is the tool hold, a post whose callback's
  answer or a pass is the one response, which `Intake.tla`'s `HT` already models. Its comment
  says so; no action or invariant changed.
- **Tests.** `IntakeStartTest`: a context is the response's `additionalContext` and the event is
  what the callback gets; three starts of one session, two of one source, are three answered
  rows; a pass, a crash and a context of 10,001 characters answer an empty body, the last with
  its problem; an answer after the deadline is dropped and the row says `expired`; without the
  callback a start is a stored row. On the stand-in path, the hook's own command run by `sh` with
  the input on stdin against `Intake.Plug` under Bandit: a context is printed as the hook's
  JSON; a pass, a late answer and a wrong secret print nothing and exit 0. `AccountsHooksTest`:
  no `SessionStart` hook for tools without `:session_start`, the command hook in both roles'
  settings with it, and the refusal without programs. `SurfaceTest`: the app module without the
  callback has no `SessionStart` hook, and a module with it answers the account's command on the
  running tree's port, its `part` lookup live.

## What was measured

- **By this builder: the `http` hook.** Claude Code 2.1.322's hook matcher removes every `http`
  hook from the matched hooks when the event is `SessionStart` or `Setup`, and logs "Skipping
  HTTP hook <url> — HTTP hooks are not supported for SessionStart". The check reads the event's
  name only, not its `source` or the session's mode. A headless run in a scratch config of the
  builder's own, with a `command` and an `http` `SessionStart` hook: the command hook ran and
  its output was parsed; the `http` hook was skipped with that line and its listener got no
  post. The scratch config is not logged in (F-195's new-1), so that run reached no model, and
  an interactive start stopped at the login screen before any hook.
- **Measured by the main session: the `command` hook**, on 2.1.322 with Haiku and the real
  suite's account, a hook printing a context that named a code word:

  | session | the model answered |
  |---|---|
  | headless `-p`, `--settings <file>` | the code word |
  | interactive, in a folder already trusted | the code word |
  | interactive, a first start that showed the trust dialog | none: the context was lost |

  On 2.1.322 the trust dialog's cursor starts on "No, exit".
- Not measured: `resume`, `clear` and `compact` starts with a model, and the wait a held start
  adds to a session's start (at most the 5 s deadline).

## What I ran into

- A tmux socket under the scratch directory is past the 104-byte limit of a Unix socket path;
  the interactive probe's socket went in a short temporary directory.
- `mix test` in an app's own directory does not resolve the umbrella's deps here; the tests run
  from the root with the files' paths.
- A held start can't keep the event's key: a second start of one session and source would read
  as a repeated post (`{:seen, …}`) and get no context. It takes a unique key as a `Stop` does.

## Findings

### new-1. An `http` hook cannot take a session's start

What happened: Claude Code 2.1.322 skips every `http` hook on `SessionStart` (and `Setup`)
before it runs, for every `source`, and logs that HTTP hooks are not supported there. Why:
Claude Code's own rule, read in its bundle and seen in a headless run's debug log. What I did:
stopped at the measure, as the brief said. The main session measured a `command` hook and
decided to build the start on one, which this unit then built (`Intake.start_hook/4`). What the
design should change: done here; any later hook on `SessionStart` or `Setup` is a `command`.

### new-2. The framework's own `SessionStart` hook never posted

What happened: `Intake.hooks/4` wrote an `http` hook for `SessionStart`, and the design's
Transport listed it, but Claude Code 2.1.322 skipped it at every start, so `Intake` never had a
`SessionStart` row. Nothing read one: "Lost events" already named the session file as its
stand-in. What I did: by the main session's decision, dropped it from `Intake.hooks/4` (moved
`SessionStart` to the events posted only for a callback) and from the Transport bullet. What the
design should change: done here.

### new-3. A session whose start waited on the trust dialog starts without the app's context

What happened: the main session's measure shows the model reads the start's context headless
and in an interactive start in a trusted folder, but not when the start first showed the trust
dialog. Why: not read; whether Claude Code 2.1.322 runs the hook before trust and drops its
output, or runs none, was not measured. What I did: said so in `Intake`'s and
`ToolHooks`' docs and in the design's "A held `SessionStart`"; built nothing more. What the
design should change: decide whether the framework re-sends the app's text after a start's
trust dialog is answered, for instance as the first message `Mailbox` delivers to that session,
or as a `UserPromptSubmit` context on its first prompt; the `start` row's `answered` decision
holds the text to send.

### new-4. A held start adds its callback's time to every start

What happened: the start's hook waits on the app's callback, up to `tool_deadline` (5 s by
default), before the session goes on, at every startup, resume, clear and compact. Why: Claude
Code waits on a `SessionStart` command hook. What I did: kept the tool deadline, as the brief
said. What the design should change: if an app's callback is slow, a deadline of the start's
own (shorter than a tool call's) may be wanted; not measured here.
