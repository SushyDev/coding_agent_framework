# F-152: a headless delegate's brief goes in at the hold, before the init

The end-to-end run of 18 November, on the real Claude Code 2.1.322, found that a headless
delegate never starts. `claude -p --input-format stream-json --output-format stream-json`
writes `system`/`init` only after it reads its first line, and the start waited for that init
before the delegate's row was `running`, while `Mailbox` hands a row by `stream` only to a
running row: each waited on the other. The design already said what to do (the per-release
check in "Headless delegates"); the remodel had lost it. The tests ran the stand-in in
`:at_start`, which writes the init at once, so no test saw it. A delegate stuck `starting` could
not be stopped either. No test or step of this unit started the real Claude Code.

## What was built

- **The model first.** `Delivery.tla`: a headless session in `Launched` starts only with its
  first row, marked `sending` by `stream` while no process runs (`ForStart`) and written into
  the new process's FIFO in the start's own step, as `launch` carries an interactive start's
  prompt; a later `stream` row is marked only once the process is `Ready` (it took a row, so
  its init came). `GoOn` may store the word to go on while no process runs, since the resume
  needs it first. `Break_Delivery_BriefAfterInit` starts the session bare and waits for the
  init: `Arrives` fails. New configurations `Delivery_HeadlessStart` (a crash and its resume, a
  restart, the replies) and `Delivery_HeadlessReady` (a second row after the init).
  `Delegate.tla`: a headless start is held (`sess = "held"`) with its message, marked before the
  call, in its pipe; `Confirmed` makes it running once the delegate took it, or refused if its
  process is gone first. `Break_Delegate_BriefAfterInit` writes the message only once the row
  runs: `CallSettles` fails. `RefusedHoldsNothing` now reads "no process runs" (`none` or
  `dead`), since a start whose process died before its init is refused.
- **`Mailbox.launch/4`, `via: :stream`.** Marks the first row due `sending` by `stream`, its
  text as it is, `sent_at` the start's deadline, held in `launching` until `launched/3`. From
  the start's answer the session's fold settles it as any `stream` row (a start refused after
  its hold may have written the line). `Transport.Stream.settle/3` keeps a start's row whose
  fold has no line of it until the start's deadline; after a restart, a row with no session id
  is read against the agent row's session, and a wake is set at its deadline.
- **`Delegates`.** `launch_first/3` marks the first row for every start and resume: by
  `launch` for an interactive delegate, by `stream` for a headless one, whose launch carries it
  to `Sessions` as `first: %{uuid, text}`. A headless start or resume with no row due is not
  made (a start is refused `{:launch, {:ok, :none}}`; a resume waits for the next cue).
- **`Sessions`.** A delegate's way carries `first:`; `hold_and_view/3` writes it through
  `Stream.write/4` right after the hold, before the check waits for the init. Written once.
- **The stop of a start never confirmed.** `fix_state/3` of a row still `starting` answers its
  row's state (`offset` nil) instead of `{:not_started, "starting"}`, and `fix/5` takes `:stop`
  only: `Sessions.stop/3` of a delegate row `starting` or `unknown` sends SIGTERM to the held
  program's record (as F-144 does for a row on a dialog). With the start's call under way, the
  start answers `{:refused, :stopped}` once its process is gone and its socket dead, and the
  stop `{:ok, :stopped}`; with none (a restart, an unknown answer), the stop waits and writes
  the row refused. `Delegates`' row then settles refused, reason `stopped`. A start still in its
  worktree or setup is refused `{:not_held, :tree}`.
- **Tests in the real release's shape.** `HeadlessStandIn` defaults to `:on_message`;
  `SessionsSetup.headless(ctx, :on_message)` carries a `first:` line; every test of a headless
  start that used `:at_start` uses `:on_message`. `MoverSetup.headless/1` keeps `:at_start` and
  says why (new-1). The Mailbox tests start delegates as `Delegates` now does (mark, `first:`,
  `launched/3`). Two Stream tests no longer wait for an init before the first line. New tests:
  a Sessions start with no first line stopped by its record; a Delegates start whose stand-in
  never writes its init, stopped by its parent, settles refused, its brief delivered by its
  replay.
- **Docs.** `docs/design.md`: the protocol's step 4, "The first line" and the stop of a start
  never confirmed, the per-release check's init order (2.1.322 writes it only after a line),
  and the `stream` row of the transport table. The moduledocs of `Delegates`, `Sessions`,
  `Mailbox` and the stand-in.

## What I ran into

- `Delivery_HeadlessReady` with four row ids and `AnswerComes` took 69 s, 55 s without
  `AnswerComes`; the fast gate allows 30 s. With three ids it checks the second row's mark
  after the init in 5 s, and `Delivery_HeadlessStart` checks `AnswerComes` across a resume.
- `Delegate_Restarts` and `Delegate_Cap` failed at first: the delegate took its brief,
  finished and was killed before `Sessions` confirmed the start, so the start was refused and
  the reply lost. `Sessions` reads the init every 200 ms while it waits and a turn lasts longer,
  so `DelegateFinishes` now waits for the start to leave `held`, and the spec says so (new-2).
- The claim command returns once the line is in the pipe, not once it is read: a stop right
  after the hold can end the stand-in before it reads the line. The Delegates test waits for
  the stand-in to take the line before it stops.
- `mix test` run alone includes the model test, whose 300 s timeout a run under load passed;
  `gate-test` excludes it and `gate-model` runs the model on its own.
- Rebased onto F-150, `Delegate_Idle` failed twice. F-150's `StartAgain` marked a new row's
  brief only for an interactive delegate, as before this unit; it now marks it by
  `MarkedFirst`, as `StartAsked` does, so a headless new start's brief goes in at the hold.
  F-150's `TurnEndsBare` could end a turn while the start was `held`, leaving it stuck; it now
  waits for the start to leave `held`, as `DelegateFinishes` does (new-2).
  `Break_Delegate_BriefAfterInit.cfg` sets F-150's `Stalls` and `MaxAgain`.

## Findings

### new-1. A move's resume of a headless delegate carries no first line

What happened: `Mover.resume/2` resumes a moved delegate through `Sessions.resume/6` with no
first line (`launch_first/2` answers nil for a headless row). On 2.1.322 the resumed process
writes no init until it reads a line, so `Sessions` never confirms the resume, and `Mailbox`
hands no row to a row that is not running. Why: F-142 gave the move's resume a first row only
for an interactive session; this unit's mechanism covers `Delegates`' own start and resume.
What I did: nothing in `Mover`; `MoverSetup.headless/1` keeps its stand-in `:at_start` and says
why. What the design should change: a move's resume of a headless delegate takes the first
row due by `stream`, as `Delegates`' resume does (`Mailbox.launch/4`, `via: :stream`, then
`first:`). A moved delegate's drain leaves its turn ended, so often no row is due; the design
should say what its resumed process is given then (a fixed word from `framework`, as after a
kill, or no resume until a row is due).

### new-2. A turn that ends and a process that exits within one read of the init

What happened: `Delegate.tla` found that a headless delegate that takes its brief, finishes
and is killed before `Sessions`' next read of the init has its start refused and its reply
unread. Why: `Sessions` confirms only a live process with the init read, and a refused start's
row takes no report. The model now assumes the init is read before the turn it began ends
(200 ms against a model turn). What I did: stated the assumption in `DelegateFinishes`.
What the design should change: decide whether a start refused with its brief's turn ended
(its fold holds the brief's result) is reported as a finish; it may stay a known gap.

### new-3. A start whose first-line write is refused waits for its deadline

What happened: `Sessions` writes the first line once; a write refused (the socket not yet
live after a hold that answered unknown) leaves the start to its deadline, then `unknown`,
and `Delegates`' row waits on an agent row that is neither running nor free. The new stop
ends it. Why: the design forbids a hidden retry. What should change: decide whether the
start's check, which already reads at a fixed interval, writes the line again while the fold
shows none of it marked (nothing went in, so it is safe), or whether the stop is the answer.
