# F-113: `Screen`, a main session's screen read from the real fixtures

Item 13 of the order of units, its first part (item 4's `Screen`): a pure reading of one
captured pane of Claude Code's terminal interface, for a named release, checked against the
2.1.322 fixtures F-105 captured.

## What was built

1. **A new app, `caf_screen`**, with no dependencies. It starts no process, runs no tmux and
   reads no file.
2. **`Screen.read(capture, release)`** takes what `tmux capture-pane -p` prints, with or
   without `-e`; it drops the escapes (CSI and OSC), the trailing spaces of each line and the
   blank lines at the bottom, then places the screen by what is drawn last:
   - `exited`: the last two lines are `Resume this session with:` and `claude --resume …`;
   - otherwise the last rule of `─` splits the screen. If the lines between it and the rule
     above it start with the box's mark (`❯` and a no-break space, or `❯` alone), it is the
     box: `running` when a line under it holds `esc to interrupt`, else `idle` with the box
     `:empty` (nothing, or the placeholder `Try "…"`) or `{:text, text}`. A box of more than
     one line while no turn runs is unrecognized;
   - otherwise the lines under the last rule are a dialog when the last starts with a known
     kind's footer, the kind's title is a line above the options, and the options are the
     lines just above the footer, each ` ❯ label` or `   label`, exactly one selected, every
     label once, the line above them blank or the title. A permission dialog's options must be
     numbered `1.` to `n.` in order; the number is not part of the label.
   - anything else is `{:unknown, {:unrecognized, release}}`.
   An earlier prompt in the conversation shows `❯` and a plain space, so it never reads as the
   box.
3. **One reading per release**: `Screen.Reading` is the behavior, and `Reading.V2_1_322` its
   data (the marks, the placeholder, the running words, the exit line, each dialog's kind,
   title and footer). `Screen` finds the module by the release's name, so a new release adds
   one module and changes nothing else. Only a string of three dot-separated numbers reaches
   `Module.concat/2`; any other is refused `{:unknown_release, release}` with no atom made.
4. **`Screen.option_keys(screen, label)`**: a list of `"Down"` or `"Up"` keys from the
   selected option to the one labeled, or `{:refused, {:no_option, label}}`, or
   `{:refused, :no_dialog}`. It goes by labels only.
5. **Tests** (`ScreenTest`, no tmux): each fixture the manifest shows reads as its state from
   both files, and a state the manifest names without an expected reading fails. One-change
   screens: an unknown question, an unknown footer, no option selected, options out of order,
   a line that may be a wrapped option, text that starts like the placeholder, `❯` alone, a typed
   `❯`, a box of two lines, a done line above a running footer, a spinner with no running footer, and a
   resume line with more under it. Unknown and malformed releases are refused. `option_keys`
   for every option of both dialogs, upward too.

`Control` is unchanged.

## What was measured

- `Screen.read/2` on a 120 by 40 capture: 28 µs (`turn-running.txt`), 46 µs
  (`idle-empty.ansi`), 130 µs (`permission-dialog.ansi`), as the mean of 1000 reads after a
  first. The app's 36 tests run in 0.06 s.
- 479 changed lines apart from this note and the fixtures.

## What I ran into

- One of four `gate-test` runs failed one test outside this unit: `SessionsTest`'s "F-64: a
  stop is done only when its socket has ended too" answered `{:unknown, {:no_exit, …}}` where
  it expects `{:socket_live, …}`. The machine's load average was 70 to 95 then, from other
  work. The other three runs, and the run inside `devenv test`, passed. Under that load the
  stand-in likely did not exit within the stop's deadline. `caf_screen` is used by no other
  app, so this unit cannot reach that test.

## What the next unit needs from `Screen`

The checked write (type the text, see it in the box, then Enter as a key of its own, then see
the box empty or the turn start; F-105's new-3) needs:

- before typing, `{:ok, %{state: :idle, box: :empty}}`; anything else refuses the write;
- after typing, `{:ok, %{state: :idle, box: {:text, text}}}` with `text` the typed text less its
  trailing spaces (tmux and `Screen` both drop them); this works today only for a text that
  fits on one line (new-1);
- after Enter, `:running`, or `idle` with an empty box, as the send's confirmation;
- the release of the session it writes to, named by the caller (new-4);
- at a main session's start, the trust dialog read by its label: `option_keys(screen, "Yes, I
  trust this folder")` gives `["Down"]` from the default `No, exit`, then Enter; and the input
  box shown first, with no dialog, is a start that goes on (F-105's new-1).

## Findings

### new-1. No fixture shows a box of more than one line, so a long write cannot be checked

What happened: the 2.1.322 fixtures show only a one-line box. A text longer than the box's
width wraps, a text with newlines takes several lines, and a burst Claude Code reads as a paste
may show as a marker in place of the text (F-105's new-3 suggests it reads bursts as pastes).
Why: the capture script types one short line. What I did: a box of more than one line reads as
unrecognized unless a turn runs, rather than guessing how the release draws wraps and newlines.
What the design should change: before the checked write is modeled, the capture script records a
wrapped text, a text with a newline and a long pasted text, and the write's check compares what
each shows. A report delivered into a main session is long, so the write needs this.

### new-2. A capture can be taken mid-draw

What happened: in `idle-empty`, the rule under the box is 66 of 120 columns and the footer is
missing, while every other capture's rule is whole. Why: likely the capture ran while Claude Code
was still drawing. What I did: a rule of any length is a rule. What the design should change: the
checked write's model treats one read as possibly torn: a running turn whose footer is not yet
drawn reads as idle. The write's check should not let a single read be the only sign that a turn
has ended.

### new-3. Typed text that looks like the placeholder reads as an empty box

What happened: the placeholder and typed text differ on the screen only by the dim attribute,
which a capture without `-e` does not carry. What I did: a box whose text is exactly `Try "…"`
reads as empty, and any other text, `Try the build` say, reads as text. What the design should
change: nothing now; a write of such a text would not be confirmed and would end refused, not
sent twice. If it matters, the reading could take the dim mark from a capture with `-e`.

### new-4. `Screen` needs the session's release, and nothing records it

What happened: `read/2` takes the release by name, and a main session's row does not say which
Claude Code release runs it. Why: devenv pins one release, and nothing has needed the version.
What the design should change: the launch records the release it started (`claude --version`
from the program it runs, checked at start with `Programs`, item 14), and the checked write
reads with that release; a release with no reading refuses the write.

### new-5. A permission dialog's labels carry a path and a hint

What happened: option 2 of the permission dialog names the project's folder (`…access to
/work/repo from this project`), and option 3 ends with a hint after ` · `. What I did: a label is
the whole text after its number. What the design should change: nothing for main sessions,
whose permissions are answered through the held `PermissionRequest` hook (`Intake`); `Screen`
reads this dialog so a write never types into it. An answer by label to this dialog would have to
build the label with the folder.
