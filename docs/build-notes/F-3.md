# F-3: `Control`, the one writer per host

## What was built

- **`docs/design.md`** takes three of F-2's findings: the example command in "Writes to panes"
  compares `#{pane_id}` with the target as well as the tag, and says why (new-1); the tmux rule
  says a backslash goes before an argument's trailing `;` (new-2); a dtach rule keeps each
  host's dtach directory short and bounds a session id used as a socket name (new-5). new-3 and
  new-4 are left for the main agent. `Agent.tla`'s header says `Control` is built, and that its
  stop and respawn are writes there; the spec's actions are unchanged.
- **`Control`**: a `GenServer` the caller's tree starts, one per host, with no name. It is the
  only caller of `Tmux.write/4` for its server. `open/4` opens a session's tagged pane and keeps
  its id; `send/4` (text and then Enter), `interrupt/3` (one `C-c`), `stop/3` and `respawn/4`
  name a session and act only on its kept pane through the one-command tag check. A session with
  no kept pane is `{:refused, :no_kept_pane}`. Calls are served one at a time. Each has a finite
  timeout (15 s by default); past it the caller gets `{:unknown, {:timeout, ms}}`, and a request
  still queued when its deadline passes is dropped unsent. Nothing is retried. "Answer" and
  "type only when the turn has ended" are left out; the moduledoc says they come later.
- **`Tmux`** gains `kill_pane/3` and `respawn_pane/4` (`respawn-pane -k`), both run under the
  same `if-shell` check as a write, and the input `{:line, text}`: text and then Enter in one
  tmux command, so a send cannot end with the text typed and the Enter lost. `Tmux.CLI` shares
  one private `guarded/5` for the three; `Tmux.Fake` does the same in one step.
- **Tests**: `test/control_test.exs` runs on a real tmux server on a socket the test owns and on
  the fake, through a probe `Tmux` that reports each write's process, how many writes were under
  way at once, and its input. `test/tmux_contract_test.exs` covers `kill_pane` and
  `respawn_pane` on both.

What the tests show:

- After the server is killed and beta's pane takes alpha's kept `%0`, `send`, `interrupt` and
  `stop` for alpha are `{:refused, {:tagged_for, "beta"}}`, and beta's file then holds only
  beta's own next line.
- Thirty callers sending at once: every write is made by the `Control` process, with exactly
  one under way each time, and all thirty lines arrive whole.
- A write the probe answers `{:unknown, :lost}` is answered so, and no second write follows.
- A call that times out while another holds `Control` is `{:unknown, {:timeout, 50}}`, and its
  text never reaches the pane, then or later.
- A session with no kept pane is refused for every call, with no write made.
- A respawned pane keeps its id and its tag and runs the new program; a stopped pane is gone and
  its id forgotten.

- The 40 tests and 12 doctests take 49 s for `mix test`, most of it `bin/check-model all`; the
  `Control` and contract tests alone take 3 s. The load average was 46 to 81 during the gates.

## What I ran into

- tmux ends a server when its last session's pane is killed, so a test that stops the only
  session then finds `{:refused, :no_server}`. The test keeps a second session open.
- `Shell` crashed under load: a program that exited before `Port.info(port, :os_pid)` left the
  port closed, the match on `{:os_pid, _}` failed, and the rescue read `.original` from a
  `MatchError`. `Shell` now takes a closed port's missing pid as `nil`, still collects the exit
  status from the mailbox, and kills by pid only when it has one. See new-2.
- A probe of `respawn-pane` and `kill-pane` inside `if-shell`, on a socket named for its own pid
  under a short directory (the scratch directory's path was over the socket limit), showed the
  tag survives `respawn-pane -k` and that `display-message -p` still prints after the last pane
  is killed. The socket file and its directory were removed by exact path.
- The unit is about 520 changed lines apart from this note: 130 for `Control`, 200 for its test,
  about 100 in `Tmux` and its two implementations, 20 in the contract test, and the rest in
  `Shell` and the docs. The probe module (about 35 lines) could move to `test/support/` if a
  later unit reuses it.

## Findings

### new-1. Stop and respawn by pane id need the write's check too

What happened: the design gives the one-command tag check to writes. `Control` also stops and
respawns a session's pane, and both act on a pane id kept from when the pane opened.

Why: after a server restart the kept id can name another session's pane, and `kill-pane` or
`respawn-pane -k` on it would end another agent's viewer, or replace what it runs.

What I did: `Tmux.kill_pane/3` and `Tmux.respawn_pane/4` run under the same `if-shell` check as
a write, with the same refusals, and `Control` uses them. `Agent.tla` counts them as writes.

What the design should change: "Writes to panes" could say that every tmux command that acts on
a kept pane id (a key, a kill, a respawn) goes through the same one-command check.

### new-2. A program can exit before its port reports its pid

What happened: under a load near 80, `Programs.find/3` crashed a test's setup: the program had
already exited, `Port.info/2` answered `nil`, and the match failed.

Why: a port with `:exit_status` closes as soon as its program exits; its output and status stay
in the mailbox.

What I did: `Shell` reads a missing pid as `nil` and goes on collecting; only a timeout needs
the pid, and a program that has exited cannot time out.

What the design should change: nothing; the "Tests" rules already say a check must hold under
load. This one is noted so later units that open ports do the same.

### new-3. Text and Enter as one command

What happened: `send` is text and then Enter. As two writes, the Enter could be refused or
unknown after the text went out, leaving text in the input box that a later send would join.

What I did: the input `{:line, text}` sends both in the one checked tmux command.

What the design should change: "Writes to panes" could say a send's text and its Enter go out in
one tmux command. Whether Claude Code reads an Enter that arrives right after pasted text as a
submit is a question for `Screen`'s fixtures, since no test here runs the real Claude Code.
