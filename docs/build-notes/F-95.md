# F-95: a report `run_delegate` answered is never lost

## What was built

- `Delegates`: `await_report/4` now marks the report it takes `answering`, in the same step
  that held it. `answered/2` moves an `answering` report to `answered`; `release/2` moves it
  back to `held`, with the mark it had. Both refuse a report that is not `answering`
  (`{:not_answering, report}`) and an unknown id. A wait on an `answering` report is refused
  as `:answering`. When `Delegates` starts, every `answering` row of its host is `held` again,
  before any call is handled. A second start finds it `held` and leaves it, mark and all.
- `MCP`: `answer/5` calls a tool, then writes its outcome with a function the caller gives,
  then tells `Delegates`: `answered/2` when the write answered `{:ok, _}`, `release/2`
  otherwise. `call/4` is `answer/5` with a write that always succeeds, since its caller has the
  outcome in hand. The plug writes through `answer/5`. Its write rescues what the adapter's
  `send_resp` raises, so `MCP` hears of the failure, and then raises it again, so the server
  sees what it saw before.
- `MCP` takes two required options, `:tool_timeout` and `:margin` (ms, `0 < margin <
  tool_timeout`). `run_delegate` refuses a `timeout` at or over `tool_timeout - margin` as
  `{:timeout, {:under, limit}}`. The cap of a day still applies first.
- `ClaudeCLI`: a required `:tool_timeout` (ms, 1 000 to 2 147 483 647) that `session/3` and
  `headless/2` put in the environment as `MCP_TOOL_TIMEOUT` and
  `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`, before `DISABLE_AUTOUPDATER`. `Sessions` passes it on
  from the launch. The test setups give it.

### The setting Claude Code reads

Found in the strings of the pinned binary, Claude Code 2.1.322 (`.claude-wrapped` in its store
path). Its environment schema reads `MCP_TOOL_TIMEOUT` as an integer of at least 1. Three
limits apply to an MCP tool call on an `http` server:

- **Wall-clock limit**: the server entry's own `timeout`, if it is at least 1 000, else
  `MCP_TOOL_TIMEOUT`, else a default of 100 000 000 ms. It is clamped to 1 000 ms and up, at
  most 2^31 - 1. Its error is "MCP tool timeout".
- **Idle limit**: `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`, else 300 000 ms for a remote server
  (1 800 000 for stdio). It is raised to the server entry's `timeout` and lowered to the
  wall-clock limit. Only a response or a progress notification resets it, checked every 30 s.
  Its error is "MCP tool idle timeout".
- **HTTP request limit**: the server's `timeout`, else `MCP_TOOL_TIMEOUT`, raised to at least
  60 000 ms, else 60 000 ms. That value is then raised to a second one, which I did not trace.

Our endpoint sends nothing until the answer. Without these settings, a `run_delegate` call
that waits more than 5 minutes is aborted by the idle limit. The HTTP request limit may cut
it sooner. So `ClaudeCLI` sets both variables to the same value. The idle limit then
equals the wall-clock limit, and the HTTP request limit is at least as long.

### How the plug knows the write reached the socket

Bandit's `send_resp` writes the headers and body in one `ThousandIsland.Socket.send/2`, which
is `:gen_tcp.send/2`. It returns once the kernel has taken every byte into the socket's send
buffer. On an error it raises `Bandit.TransportError`. So a return means the kernel accepted
the answer. It does not mean the client read it. Bytes the kernel took can still be lost when
the client is gone, and nothing on this side tells.

## What was measured

A scratch script ran Bandit with a plug that waits 300 ms and then writes, while a client
connected and closed in several ways before the write:

| client before the write | write of 100 B | write of 4 MB |
|---|---|---|
| `close` (FIN) | returned `:ok` | returned `:ok` |
| `shutdown(:write)` | returned `:ok` | — |
| close with linger 0 (RST) | raised `TransportError` "closed" | — |

A client that closes normally gets an answer that "succeeds". See new-1.

Tests: `caf_cli` 13, `caf_stream` 36, `caf_sessions` 41, `caf_delegates` 15, `caf_mailbox`
12, `caf_mcp` 19 (with the new ones), all passing. Gate results are at the end.

## What I ran into

- `Delegates` already has a private `answered/3`, so the new public functions take no
  options (`answered/2`, `release/2`), as the brief names them.
- The MCP endpoint test cannot make Bandit's write fail on demand (see the table), so the
  tests swap the `Plug.Test` adapter for one whose `send_resp` raises (`BrokenSocket`). One
  test does this over a stand-in `Delegates`, and one over the real one.
- `ClaudeCLI` now refuses a launch without `:tool_timeout`. Every caller that builds a launch
  had to give it: `Sessions` passes it on, and the test setups set it.

## Findings

### new-1. A client that closed its socket normally still gets a write that succeeds
What happened: a client that closes its socket with FIN before the answer does not make the
write fail. `:gen_tcp.send/2` returns `:ok`, even for 4 MB on loopback. Only a reset (RST)
connection makes it raise. Why: TCP takes the bytes into the send buffer, and the peer's RST
arrives only after it. What I did: built the release as the brief asks. It covers a reset
connection and any error raised before the bytes are taken. The test makes the write raise
on purpose. How Claude Code ends an aborted call's connection (FIN or RST) was not measured,
since no test runs the real Claude Code. What the design should change: say that the write's
success means "the kernel took it", not "the agent got it". The cap under the tool timeout is
then the guard that counts, and the release is a second line for resets. To cover a normal
close too, the plug would need to see end-of-file on the socket before it writes. Plug does
not expose that, so it would need the server's own socket, with Bandit's internals. Or the
report could stay `answering` until something from the agent confirms it. Either is a design
decision.

### new-2. Claude Code's idle limit gives up on a silent call after 5 minutes
What happened: the pinned Claude Code aborts a remote MCP call after 300 s with no response
or progress notification. It does this whatever `MCP_TOOL_TIMEOUT` says, unless
`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` or the server entry's `timeout` raises the limit. Its HTTP
request limit follows `MCP_TOOL_TIMEOUT`, and is 60 s or another default without it. The design names only "the tool timeout".
What I did: `ClaudeCLI` sets both variables to the launch's `:tool_timeout`. What the design
should change: name all three limits in "What `Delegates` holds". Also decide whether the
per-server `timeout` in the agent's MCP config (`MCP.issue/2`) should set them instead. That
would scope them to the framework's server, since the environment variables also apply to the
account's own MCP servers.

### new-3. `Delegate.tla` does not model the report a call takes
What happened: the model's report states are `none`, `held`, `sending` and `delivered`.
Neither F-92's take (`answered`) nor this unit's `answering` is in it, and nothing models the
restart that holds an `answering` report again. What I did: built the code from the design's
prose, as the brief asks, and did not change the model. What the design should change: add
the take, `answering`, the write's outcome and the restart's hold to `Delegate.tla`, with a
property that a report is answered or delivered at least once.

### new-4. A report stays `answering` until a restart when the caller's process dies
What happened: when the process that runs the call dies after the take and before it says
`answered` or `release`, the report stays `answering`. The same happens when `Delegates`
cannot be reached at that moment. Only the next start of `Delegates` holds it again. What I
did: nothing beyond the design's restart rule. What the design should change: decide whether
`Delegates` should monitor the waiting caller and hold the report again when the caller goes
down. It already has the caller's pid from `await_report`.
