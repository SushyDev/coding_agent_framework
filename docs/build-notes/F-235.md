# F-235: the tree shows each agent's tool calls, and the one it runs now

Branch `framework/f-235-tools`, from `main` at 638c8f8. An app's panel shows, for a working
agent, the tool it runs now, how long each call took and when the agent last did anything. It
learned this from its own `PreToolUse` and `PostToolUse` hooks; it can now read the framework.

## The source: the transcript

The brief offered two sources: the transcript (a `tool_use` block starts a call, the
`tool_result` that names its id ends it) or the tool hooks posted on every call. I chose the
transcript. The framework already reads it (`Transcripts`), it costs no post per call, and the
measurement below shows it is in time.

**Measured on Claude Code 2.1.322**, on this builder's own session, read only:

- *Is the `tool_use` line written before the tool runs?* Yes. A Bash call searched the session's
  transcript for text that only its own `tool_use` block held, and found it while it ran.
- *How late does the line land after the call starts?* A watcher polled the file every 20 ms
  for three calls. Each line appeared 0.10, 0.11 and 0.20 s after the command printed its start
  time, which is within the watcher's own resolution (a sleep plus a grep of a large file). The
  line lands at the tool's start, not after it.
- *What its timestamp says.* The `tool_use` line's `timestamp` was 1.6 to 1.8 s before the
  command started in those three calls, and 5.8 s before in a call a hook and the permission
  check held longer. The timestamp is when the assistant message was taken, before the
  `PreToolUse` hooks and the permission check run.
- *The end.* The `tool_result` line's timestamp was 39 to 60 ms after the command ended.

So `started_at` is a second or two early and `ms` counts the hooks' and permission's time with
the tool's own (new-2). Both are well within the brief's "a second or two".

## What was built

- **`Transcripts.Fold`** keeps three more fields. `tools`: the session's own calls, newest
  first, each `%{id, name, started_at, ended_at, ms}` (ms; `ended_at` and `ms` nil while it
  runs), at most 200. `agent_tools`: a sidechain entry's calls under its `agentId`, never the
  session's, at most 200 per subagent and 50 subagents (the stalest dropped). `last_event_at`:
  the time of the session's last entry; a subagent's entries do not move it. A result whose
  call the bound dropped ends nothing; a `tool_use` id seen twice starts one call.
- **`Tracker.Tree`**: each agent row carries `tool`, the newest call of its transcript that has
  not ended while the agent is `working` (`%{name, id, started_at}`), else nil; and
  `last_event_at`, the newer of its transcript's last entry and its newest `Intake` row
  (`written_at`, by account and session). Both are added in one `Map.merge` after the row's
  existing fields, so F-234's row changes (`transcript`, the subagents' `agent_id`) merge apart.
- **`Tree.tool_calls/3`** and **`Tracker.tool_calls/3`**: an agent's recent calls, newest first,
  at most `limit:` (default 50). The agent is a tree agent's name, or a subagent's `agent_id`;
  `host:` chooses between two agents of one name. `{:refused, :unknown_agent}` or
  `{:refused, :ambiguous}` otherwise. Bounded by the fold's 200 per agent.
- `caf_tracker` declares `caf_transcripts` for its tests (`only: :test`).
- Tests (`apps/caf_tracker/test/tools_test.exs`) on lines of the shape recorded above: a call
  that starts and ends, with its ms; one still running is the agent's `tool`, and none is when
  the agent is idle or the call ended; a newer hook event is the last event; a subagent's calls
  are under its agent id and not the parent's; the bound holds (250 calls keep 200, 60
  subagents keep 50, `limit:` answers fewer); and `Tracker.tool_calls/3` end to end over a
  `Tracker` with stand-in sources. Doctests on `Fold` and `Tree.tool_calls/3`.

No model: the fold is a pure read of lines already written, not a protocol over time.

## What I ran into

- The brief's item 4 says a subagent's calls come from "the sidechain's entries". On 2.1.322
  those entries are in the subagent's own file, which `Transcripts` does not read (new-1).
- Changing the fold's keys makes `Transcripts.Table.load_fold/1` read each stored fold as
  stale, so each transcript is folded again from its start once, at its next read (new-5).

## Findings

### new-1. A subagent's calls on 2.1.322 are in a file `Transcripts` does not read

What happened: F-28 found that 2.1.322 writes a subagent's entries to
`<projects>/<key>/<session id>/subagents/agent-<id>.jsonl`, each with `isSidechain: true` and
`agentId`; only older releases wrote them into the main file. `Transcripts` reads the main
file alone.

Why: the fold reads what it is given; no reader hands it a subagent's file.

What I did: the fold keeps any sidechain entry's calls under its agent id, never the parent's,
so a subagent's file folded by the same `Fold` gives the right answer. Today, on 2.1.322,
`tool_calls(tracker, agent_id)` answers `{:refused, :unknown_agent}` and a parent shows only
its own `Agent` call.

What the design should change: `Transcripts` reads each subagent's file of a session it reads,
and folds its calls into that session's row. A foreground subagent's `agentId` arrives only
with its result, so the files are found by listing the session's `subagents/` directory, not
from the fold. This touches the same rows as F-234; one unit should do it after both merge.

### new-2. A call's time includes the hooks and the permission check

What happened: the `tool_use` line's timestamp is 1.6 to 1.8 s before the tool starts, and
5.8 s once in this measurement.

Why: Claude Code stamps the assistant message when it takes it; `PreToolUse` hooks and the
permission check run after that.

What I did: `started_at` is the line's timestamp and `ms` runs from it to the result's.

What the design should change: say so where a view shows a call's time. The tool's own run time
is not in the transcript; only a hook would give it.

### new-3. The view is as late as `Transcripts`' read interval

What happened: the line lands when the tool starts, but the tree sees it at `Transcripts`' next
read, every `interval:` ms, or when something calls `read/3`.

What I did: nothing; the interval is the app's choice.

What the design should change: name the interval a "now running" view needs (a second or two),
or have `Intake`'s posts that already arrive (a `PreToolUse` with an app callback) cue a read.

### new-4. A call whose result never comes stays open

What happened: a session killed in a tool call writes no `tool_result`, so the call keeps
`ended_at: nil` in `tool_calls/3` for good.

What I did: the tree's `tool` shows a call only while the agent is `working`, so a dead or idle
agent runs none. `tool_calls/3` still shows the call open.

What the design should change: decide whether a turn's end, an interrupt line or a new prompt
closes the calls still open before it, and with what time.

### new-5. A new fold field reads every transcript again once

What happened: `load_fold/1` treats a stored fold with other keys as stale, so after this
change each transcript is folded again from its first byte, once.

What I did: nothing; the rule is the existing one, and a read is bounded by the file.

What the design should change: nothing now. If transcripts grow large, a fold's version could
add fields with defaults instead of reading again.
