# F-286: the framework trusts the folders it starts sessions in

## What was built

The operator decided that delegates and main sessions never stop at Claude Code's folder trust
dialog in the folders the framework starts them in. Until now a trust dialog that showed waited
on a person, or on the app's `dialog:` callback, in every folder; F-255's mark kept it from
showing in a worktree the framework made, but a mark refused (the lock held) left the dialog to
a person, and a main session's checkout was never marked.

### The rule (`docs/design.md`, "Startup dialogs")

Two kinds of folder, and nothing else:

- a worktree the framework made for the start (a `worktree:` launch): `Sessions` knows it, since
  it made it;
- a main session's checkout the app configured: `Mains` starts every main session in its
  project's checkout and names it with `trusted: :checkout` in the launch. `Sessions` refuses
  `trusted:` with any other value, on a delegate, or on a worktree's start, `{:bad, :trusted}`,
  before any row.

The agent row keeps which, in a new column `trust` (`worktree`, `checkout`, or NULL). A start or
resume that names no `trusted:` keeps the row's `checkout`, but only in the row's own folder, so
a move's resume, which goes through `Sessions.resume/6` with the row's launch, keeps it. Any
other folder's trust dialog waits on the app's callback or a person, as before.

### The mechanism: (a), the press

`Sessions` already reads an interactive start's pane while it has no session file. When the
pane shows the trust dialog and the row's `trust` names a rule, with no answer marked for that
kind, `Sessions` presses "Yes, I trust this folder" itself (`ruled?/2`, `decide_by_rule/3`),
before the app's callback is asked:

- the act is a row in `Acts`, act `answer_startup`, actor `framework`, its state the one every
  answer of that dialog claims (the start, the dialog, the mark), so a person's later answer to
  the same dialog is refused as already claimed; its detail is `%{why: "operator_rule", rule:,
  folder:}`;
- the answer is marked `pressing` in the same write that makes the row `dialog`, so no reader
  of the row sees the dialog wait on a person: `Prompts` opens no prompt for it and tells no
  parent (it tells a parent only of an `open` prompt);
- the press is the `Inlet`'s checked press, as any (F-246's settle, the marker read before
  Enter, the dialog's leaving after it), and its answer settles the act;
- the start then goes on to its confirm, as after a person's answer. A press refused before its
  mark leaves the dialog to the callback or a person; one unknown or cut is a person's, never
  pressed again by the rule (a kind with any mark is never pressed again, F-144).

Why (a): it has no lost-update race. It writes nothing Claude Code rewrites, and it is the path
every answer of a startup dialog already takes, with its claim, its check and its record. (b), a
write of `.claude.json`, is what F-255 does for a worktree, under Claude Code's own lock, modeled
in `Trust.tla`; it stays, since a dialog that never shows needs no press, and the rule's press
is the fallback F-255's note named. (b) is not extended to a checkout: the brief prefers (a), and
the press covers both folders.

### The model: `Dialog.tla`

A constant `Trusted` (the rule names the start's folder) and a step `Rule`: at a trust dialog
the row shows, its prompt open and not cleared, the framework answers "yes", claimed and marked
first as the app's callback is. In `Prompt.tla`'s terms the rule answers as the app does, for
the one kind it names (`AppKinds <- Auto \cup RuleKinds`), so `OnlyRightful` and `OnlyAsked`
hold only when the folder is in the rule. A liveness property `RulePasses`: in such a folder the
trust dialog leaves the pane, or the process ends, or its press is unknown or cut, or a person
cleared a cut press, which is theirs then. Every existing configuration sets `Trusted = FALSE`.

- `Dialog_Trusted.cfg` (both dialogs, a restart, no end): passes.
- `slow/Dialog_TrustedEnds.cfg` (the same with an end asked): passes, 561 064 distinct states,
  333 s on 2 workers at load 35; too slow for a fast configuration.
- `Break_Dialog_TrustAny.cfg` (the rule presses a folder it does not name): `OnlyAsked` is
  violated, as it must be.

The first run of `Dialog_Trusted` found `RulePasses` false: a restart cut the rule's press, a
person cleared it, and nothing answered it again. The code does the same (a cleared mark is a
person's to answer), so the property now counts a cleared press as handed to a person.

## What was measured

### The screen on the stand-in

`caf_screen`'s fixtures hold 2.1.322's trust dialog, captured 2026-11-16
(`trust-dialog.txt` and `.ansi`, 120 by 40): "Accessing workspace:", the folder's path on its
own line, the safety text, then `❯ No, exit` and `  Yes, I trust this folder`, and "Enter to
confirm · Esc to cancel". The stand-in draws that fixture with each option selected; `Screen`
reads it as kind `:trust` with those two options, "No, exit" selected. The rule's press on it
took Down then Enter (`dialog_keys`), and the stand-in went on.

### The worktree lead

The lead that trust in a git worktree is keyed on the main checkout's root was measured on the
real program in F-255 ("Which mark the program honors"): 2.1.322 reads the mark at the git root
(for a worktree, the main repository) and then at the cwd and its parents up to the cwd's own
git root, and a trust dialog answered "Yes" in a worktree writes the mark under the **main
repository's** real path. So the rule's press in a worktree trusts the project's checkout and
every worktree of it, which the rule names too. No new run was needed; to check it again on a
pinned release, F-255's "What the main session runs on the real program" applies: after a
`caf_real` run that starts an interactive delegate with its mark refused (hold
`<config>/.claude.json.lock` as a directory before the start), `jq '.projects | keys'` of the
account's `.claude.json` shows the checkout's real path, not the worktree's, and the
`<home>/records/` hold no person's press of kind trust for that delegate, only the framework's
act.

## Findings

### new-1. The design already trusted a worktree before this unit

What happened: the brief says the design left the trust dialog to the operator; F-255 had
already made the framework write a worktree's trust mark into `.claude.json` before the start,
which is the brief's mechanism (b), with the lock and `Trust.tla`. Why: the brief was written
from Claude Code's docs, not from the design. What I did: kept F-255's mark, and built (a) as
the press for every folder in the rule, which is the fallback F-255's mark already left to a
press. What the design should change: nothing; it now says the mark comes first in a worktree
and the rule's press after it.

### new-2. The rule reads the folder from the row, not from the dialog

What happened: the trust dialog draws the folder it asks about (the fixture's line under
"Accessing workspace:"), but `Screen` does not read it, and the rule presses by the row's
`trust` and `cwd`. Why: no capture shows which path 2.1.322 draws in a worktree, the worktree's
or the main repository's, and a check against the wrong one would never press. What I did:
pressed by the row only; the act's detail names the row's folder. What the design should
change: capture the trust dialog in a worktree (`caf_test`'s capture script, or a `caf_real`
start with the mark refused), let `Screen` read its path, and have the rule press only when
that path is the row's folder or its git root.

### new-3. `caf_real`'s trust steps still expect a person may answer

What happened: `caf_real`'s steps answer any trust prompt from the inbox and accept none; with
the rule no trust prompt should open in a worktree or a configured checkout. Why: the real
suite does not run in the gates, and its steps were written when a person answered. What I did:
left them as they are; they still pass when no prompt comes. What the design should change:
once run on a logged-in setup, those steps could assert that no trust prompt opened and that
the framework's act is in `Acts`.

### new-4. A press marked with the dialog in one write

What happened: the first version wrote the row `dialog` and then marked the rule's answer, two
writes. Why: `Prompts` opens a prompt for a dialog with no answer and tells a delegate's parent
of an open prompt, so a read between the two would have told the parent of a dialog nothing
waited on. What I did: the rule's mark goes in the same write as the dialog. The model keeps
them as two steps; nothing it checks reads the row between them. What the design should change:
nothing.

### new-5. Interactive starts time out under the whole suite

What happened: across six full gate-test runs, five tests each failed once and passed the next
run; two were in `delegates_interactive_test.exs` (a reply's wait, and a start past ExUnit's 60
s). Why: not found; the file passes alone every time, and the failures moved between apps. What
I did: reran until three runs in a row passed. What the design should change: nothing yet; if
these recur on `main`, time an interactive start's steps (the settle, the press, the confirm)
under the full suite.
