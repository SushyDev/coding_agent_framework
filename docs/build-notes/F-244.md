# F-244: a transcript's first read is bounded

Branch `framework/f-244-bound`, from F-237's branch `framework/f-237-subagents` at ca2315e
(F-237 is not on `main` yet; `main` has F-238 and F-239 past F-237's base). F-237's new-2: a
session's main transcript read for the first time was still folded whole. A tree that starts,
or restarts, beside long-running sessions folded each of them from its first byte.

## Measured

Read only, on this account's own transcripts: every main file
`<config>/projects/<project>/<session id>.jsonl` of both accounts on this host (subagent files
left out), on Claude Code 2.1.322. The fold is `Fold.take/2` on the whole file in memory,
timed with `:timer.tc` on this laptop, under the gates' build; the read is `tail -c +1` (and
`tail -c 1048577` for the bound) through a port, as `Shell` runs it locally.

- **Sizes.** 52 main files, 321 MB in all. Median 1.7 MB, 90th percentile 3.8 MB, largest
  three 54.9 MB, 92.0 MB and 111.0 MB. 34 of 52 are over 1 MB, 3 over 10 MB.
- **A whole first fold of the largest four:**

  | file | entries | whole fold | last 1 MB | whole read | last 1 MB read |
  |---|---|---|---|---|---|
  | 4.1 MB | 1,836 | 86 ms | 10 ms | 10 ms | 5 ms |
  | 52.4 MB | 20,498 | 442 ms | 5 ms | 49 ms | 5 ms |
  | 87.7 MB | 46,752 | 831 ms | 9 ms | 72 ms | 4 ms |
  | 105.9 MB | 56,850 | 905 ms | 8 ms | 77 ms | 5 ms |

  So one restart beside these sessions folded about 320 MB, some 3 s of fold alone, in one
  `Transcripts` process that answers nothing else meanwhile, before the tree showed anything.
  A host over ssh adds the bytes' transfer, each file in one shell run under a 10 s timeout.
  With the bound each first read is about 10 ms, whatever the file's size.

## What was built

- **`Transcripts`**: a session whose fold has read nothing (offset 0) is read with one more
  shell script, `@last`: the file's size from the host's `wc -c`, then `tail -c +N` from one
  byte before its last `first_read:` bytes (the same option, default 1 MB), printing the byte
  it started at first. A file not larger than the bound is read whole, as before. A fold with an
  offset, stored or in memory, is read on from it as before (`main/3`). The same holds after a
  file is rewritten or gone and back: its fold is new, so it is read bounded too (new-2).
- **`Transcripts.Fold`** has `partial` (false for a new fold) and `take_from/2`: the bytes of a
  first read that starts at byte `at`. The first line, cut by the bound, is skipped; the fold
  starts at the next whole line with `partial: true`, and its seam is the cut line's last
  bytes, so the next read checks them as `take/2` does. At 0 it is `take/2` on a new fold.
- **A subagent started before the cut.** `file_meta/3` reads the meta's `toolUseId`; when the
  fold holds no such call, it now adds the row rather than dropping the id: `tool_use_id`,
  `agent_id`, `type` and `description` from the meta's `agentType` and `description` (new-1,
  after review), `state` `:ended` when the meta says `finished` and `:open` when not, and
  `started_at`, `status` and `tokens` nil. A later task notification or result
  closes it as it would any row (they find it by agent id or call id).
- **`Tracker.Tree`**: each agent row carries `partial`, its transcript's. Its `tool`,
  `last_event_at` and `tool_calls/3` come from the partial fold as from any other.
- **`Transcripts.Table`**: the row holds `partial`, from the fold.
- Tests. In `transcripts_test.exs`, through a real shell: a main file longer than the bound is
  read from its last part, `partial`, its last call (`b9`) its one tool and its first prompt
  absent; the subagent whose `Agent` call is before the cut keeps its row, its agent id, type
  and description from its meta, its own calls read; a short file in the same read is
  whole, not partial, with the call's description; the partial fold goes on from its offset.
  In `tools_test.exs`: in the tree, a partial fold's agent row says `partial: true` and shows
  its running call as `tool`, and the subagent started before the cut has its row with its own
  `tool`; a whole fold says `partial: false`. Doctest on `take_from/2`.

No model: as F-235's and F-237's folds, this reads files already written; it is not a protocol
over time.

## What a partial fold cannot know

Everything before the cut: the session's first entries and prompts (`prompts` holds only those
after it), its token `usage` before it (the counts are from the cut on), the calls in `tools`
started before it (a call that ends after the cut ends nothing and is absent), the `Agent`
calls started before it (their rows come only from a subagent file's meta, with no start
time), `interrupts` before it (and an interrupt's `turn_at` when its turn opened
before), and a usage `limit` line before it. Its `entries` counts lines from the cut.

The tree shows it as `partial: true` on the agent's row; a subagent row known only from its
meta has no `started_at` and sorts first. A subagent that ended before the cut and has no
file is not shown at all. A partial fold's `usage` counts from the cut and is never the
session's total (`Fold`'s doc says so).

## What I ran into

- `wc -c < file` on macOS pads its number with spaces. The script reads it unquoted inside
  `$(( ))`, where the spaces do not matter; the test ran on macOS.
- The meta already holds `agentType` and `description` (new-1).
- Adding `partial` changes the fold's keys, so each stored fold is folded again once, as
  F-235's new-5 describes; with this unit that read is bounded (new-3).

## Findings

### new-1. The meta names the subagent's type and description

What happened: every meta read here, as in F-237's measurement, has `agentType` and
`description` beside `toolUseId`. The brief asked for the row with its description and type
unknown.

Why: the brief kept the row's fields to what the fold knows from the main file.

What I did: first kept them nil, as the brief says. framework-main read the finding and asked
for them in this unit: the row now takes `type` and `description` from the meta's `agentType`
and `description`; `started_at` stays nil.

Decision: built. Nothing more for the design.

### new-2. A rewritten main file, or one gone and back, is read bounded too

What happened: the bound is on a fold that has read nothing. A file that shrank or was replaced
(`rewritten`), or one that was gone and came back, starts again from a new fold, so it is also
read from its last 1 MB and marked `partial`.

Why: one rule, offset 0, covers "no stored fold" and the reads that start over. F-237's
subagent files do the same on `rewritten`.

What I did: kept the one rule. The existing test of a shrunk file reads a short one, which is
read whole.

Decision (framework-main): yes, a rewritten or returned main file is read bounded and marked
partial.

### new-3. The first restart after this unit drops every stored fold, and reads each partially

What happened: the fold's keys changed (`partial`), so `Table.load_fold/1` starts each stored
fold over. Each session over 1 MB then becomes `partial`, and loses what its old whole fold
held: its first prompts, its usage before the cut, and its ended subagents with no file.

Why: F-235's new-5, a stored fold of an earlier build is folded again from its start; that
start is now bounded.

What I did: nothing more. It is one restart, and it is the cost this unit removes from every
later one.

Decision (framework-main): accepted, a one-time refold after landing. The README's line says
so.

### new-4. `usage` and `limit` of a partial fold count from the cut

What happened: nothing in the tree reads `usage`, but `Limits` and `Delegates` read `limit`.
A usage limit line before the cut is not in a partial fold.

Why: the bound reads the last 1 MB only.

What I did: nothing. A limit line that has more than 1 MB of entries after it was followed by
a turn long before, so its `followed` would be true and nothing acts on it. A session that
stopped at its limit has that line last, inside the bound.

Decision (framework-main): `Fold`'s doc says that a partial fold's `usage` counts from the cut
and is never the session's total. Done.
