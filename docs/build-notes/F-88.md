# F-88: a sync never skips an edit

## What was built

- `Copies.sync/5` passes `--modify-window=-1` to rsync, so a file is compared by size and
  modification time to the nanosecond, not to the whole second.
- A test per reach (workstation, and the stand-in ssh): sync, overwrite `a.txt` with content of
  the same size, set its time to the whole second of the copy's file, sync again under another
  run's turn, and read the new content in the copy. It failed before the fix on both reaches
  (the copy kept `one`) and passes after.
- `docs/design.md`, "Hosts": the sentence on the copy says how the sync compares a file, and why.

## What was measured

- The devenv rsync is 3.5.0. The workstation's file system (APFS) keeps nanosecond times
  (`stat -f %Fm` shows nine digits). The test's copy lives on the same file system, so a
  separate host's file system is the only end not checked here; there is no real remote machine
  to check it on. `--checksum` was not needed, so its cost was not measured.

## What I ran into

- A second sync of the same run is refused (`{:turn, "r1", "synced"}`), so the test gives the
  turn back and takes it as another run.
- `fetch/5` keeps `-lpt` without the window: it already compares content against the record.

## Findings

### new-1. A host whose file system keeps only whole-second times re-sends everything

What happened: nothing observed here. Why: with `--modify-window=-1`, a copy on a file system
that stores times to the second never equals the worktree's nanosecond time, so each sync would
send every file. What I did: nothing; no such host is in use. What the design should change: if
a host like that appears, a sync should fall back to `--checksum` for that host, chosen by the
host's own record, not by a hidden retry.
