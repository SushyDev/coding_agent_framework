# F-143: a main session's end, and F-141's follow-ups

The brief asked for a main session's end (F-141's new-1), F-141's other follow-ups (new-2 to
new-6, new-8) and F-140's (new-2 to new-6), with leave to land the end and F-141's items first
if the unit ran well past 1 000 lines. With the model, the tests and the docs it is near 1 000,
so this unit lands the end and F-141's items; F-140's are the next unit (new-2).

## What was built

- **The model first: `Team.tla`.** `MainEnds(c, m)`: the operator's act alone (`MayEnd`),
  refused while any delegate of the main session has not ended (`LiveDelegates`), taken while
  it is idle (SIGTERM, as any stop) or its process is gone (`dead`); its `proc` is then `ended`.
  `Kept(s)`: a kept service goes to a delegate's main session; one a main session owned ends
  with it, kept or not. New invariants `MainEndedByOperator`, `MainEndedIdle`,
  `NoDelegateWithoutParent`; `MainFixedByOperatorOnly` now says no fix stops a main session
  (it said no main session ever ends); `EndedMarked` covers every agent, not only delegates;
  `ServiceEndsWithOwner` covers a kept service of an ended main session. Two configurations,
  `Team_MainEnds` (a message to each agent) and `Team_MainEndsServices` (a service, kept or
  not), and one break per guard: `EndWithDelegates`, `EndBusy`, `EndByAgent`, `MainKeeps`.
- **`Sessions.end_main/3`**: in one step of `Sessions`, the row checked (a main session, no
  move, no call under way, every delegate ended: else `{:delegates, names}`) and moved: a row
  with no process is `ended` at once; a running one is stopped as `stop/3` stops it, and its
  row is `ended` in place of `stopped`. An ended main session never starts again (`{:ended,
  name}`), and a delegate's start under one is refused `{:parent_ended, name}`, checked in the
  step that writes its row. `Sessions.Agents.ended?/1` holds for an ended main session (not for
  a refused start of one, whose name may start again).
- **`Mains`**:
  - `end_main/3`: refused `{:starting, name}` while a start of the name is under way here, else
    `Sessions.end_main/3` in a task, so `Mains` answers other calls meanwhile.
  - `resume_main/3` (new-5): a stopped main session with a session id, resumed in its checkout
    under a start's row and a lease of its own, class main session, as a start is; the model
    its row keeps unless the call names one; no brief, so what is queued to it goes in by its
    waiter once it runs.
  - `start_main/5` takes `model:` (new-8), over the app's launch's.
  - A start refused after its brief was stored, by its answer or by its settle after a
    restart, settles that one row `ended` (new-4) through the new `Mailbox.settle_row/3` (by
    uuid; a row in flight is refused `{:not_queued, "sending"}`).
  - The checkout (new-6): a reading with git's `index.lock` present is `locked`, and so is a
    failure whose output names it (`Mains.Checkout.failed_state/1`); a pull a lock held back
    stays owed, and the read after the person removes the lock pulls. Nothing removes it.
- **`Services.owner_ended/3`**: a kept service of an owner with no parent (a main session) ends,
  as `Team.tla`'s `Kept` says; its settle after an owner's end did so already.
- **`MCP`**: the operator's tool `end_main(name)` (any other caller `:operator_only`) and
  `start_main`'s optional `model`; `Operator.end_main/2`, `Operator.start_main/5`.
- **Tests**: `MainsTest` on real git, tmux and dtach with the screen stand-in: the end refused
  while a delegate waits on its dialog, then, once the delegate ended, the idle session stopped
  and its row ended, a delegate's start under it, its start, its resume and a `Sessions`
  resume refused, a declared main session ended at once, a delegate's name refused
  (`NoDelegateWithoutParent`, `MainEndedIdle`), and the model a start names on its row; a
  resume under a lease of its own once the first start's lease was released; a refused start's
  brief settled `ended`; a stale lock shown `locked`, owed, kept, and the pull going once it is
  removed. `ServicesTest`: a main session's kept service ends with it. `MCPTest`: `end_main` is
  refused to a delegate and to a main session. `ExampleTest`: the operator ends a declared main
  session through `MCP`, and its name does not start again.
- **Docs**: `docs/design.md` (the concept, "Main sessions": the end, the resume, the refused
  brief, the model, the lock, `Stacks`' call of `landed/2`; services' `keep`; the parts table;
  `Team.tla`'s properties; the unit order), `README.md`'s Status.

F-141's new-2 (`Mains` owns `checkouts` and `main_starts`) is what the parts table already said;
nothing changed for it. Its new-3 is a sentence in the design for the unit that builds `Stacks`.

## Findings

### new-1. Nothing calls `resume_main` yet

What happened: the operator's `resume` tool is a fix under a claim in `Acts`, and for a main
session it still answers `{:not_built, :main_fix}`; `Mains.resume_main/3` is built and tested,
but only the app can call it. Why: a fix of a main session goes through `Grants`' claim and
`Acts`, and the brief asked only that a resume ask for its own lease. What I did: built the
resume in `Mains` and no tool. What the design should change: route the operator's `resume` of
a main session, under its claim on the `dead` state, to `Mains.resume_main/3`.

### new-2. F-140's follow-ups are not built

What happened: the dialog's press in a task (new-2), a person's clear of an unknown mark
(new-3), the stop of a row on a dialog (new-4), the shortened imports path and its fixture
(new-5), and the answer as an `Acts` row (new-6) are not in this unit. Why: with them the unit
would be about 1 600 lines, and the brief allowed landing the end and F-141's items first. What
I did: named them as the next unit in the design's order. What the design should change:
nothing; the next brief takes them as decided.

### new-3. `Team_Operator` doubled, near the fast bound

What happened: with the operator's `MainEnds` in every configuration that has an operator,
`Team_Operator` checks about 1.07 million distinct states in 22 s (F-122's note lists about
0.54 million); the fast configurations are to finish under 30 s. Why: the end adds a branch
from every state where a main session is idle or dead. What I did: nothing more; it passes. What
the design should change: if it passes 30 s on a loaded machine, move `Team_Operator` to
`slow/`, since `Team_MainEnds` checks the end on its own.

### new-4. An end whose stop is unknown needs a second call

What happened: when the SIGTERM went but the process outlived the stop's deadline, the end
answers the stop's unknown and leaves the row `stopping`, which settles to `stopped`, not
`ended`. Why: the end's intent is held only by its call, as a stop's is. What I did: documented
it; a second `end_main` ends the row once it is free. What the design should change: say
whether the row should keep an end asked (a mark as `move` keeps a move's phase) so the settle
ends it.

### new-5. `main_starts` does not say whether a row was a start or a resume

What happened: a resume writes a start's row like any start; the view cannot tell them apart.
Why: the table has no column for it, and adding one needs a migration of older files. What I
did: nothing. What the design should change: a `resume` column (the session id resumed) the
next time the table changes.
