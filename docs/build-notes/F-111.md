# F-111: PreToolUse and PostToolUse hooks, answered by the app

The first half of item 12 of the order of units. `Intake` holds a PreToolUse hook while the
app's callback is asked, with a short deadline, and hands a PostToolUse to a second callback.
The permission policy, asked before a `PermissionRequest` is held for a person, is the next
unit.

## What was built

1. **The model.** `Intake.tla` gains numbered tool calls, each with its PreToolUse hook:
   `ToolPosted` (failed while the framework is down), `ToolHeld` (an entry in `Intake`, and the
   callback asked), `CallbackAnswers` (a decision or a pass, at any time or never, even after a
   deadline or a restart), `DecisionHanded` (the row, then the decision handed to the plug, in
   one step), `PassHanded`, `ToolDeadline` and `ToolAnswered` (the plug writes the first thing it
   was handed). A restart cuts every open request, and Claude Code goes on with no decision.
   Invariants: `OneResponse`, `LateDropped`, `DecidedHasRow` (defense in depth). Property:
   `ToolRequestsEnd`. New configuration `Intake_Tools` (two calls, one restart). Two Breaks,
   each found by TLC: `TwoResponses` (the deadline fires after the decision went out) and
   `LateSent` (a decision after the deadline is still handed out). The other configurations
   set `MaxCalls = 0`, so they check what they checked before.
2. **`Intake`** takes, per instance, `pre_tool_use:` (`fun(event) -> :allow | {:deny, reason} |
   :ask | :pass`), `post_tool_use:` (`fun(event)`), `tool_deadline:` (5 s by default) and
   `agent:` (`fun(account, session_id) -> name | nil`). The event is `%{agent, account,
   session_id, tool_name, tool_input, tool_use_id}`, and a PostToolUse adds `tool_response`.
   The callback runs in an unlinked process of its own, which also builds the event, so a slow
   `agent` lookup or a slow callback never blocks `Intake`. Its answer comes back as a message.
   The deadline is a timer in `Intake`. Its crash or exit arrives as `:DOWN`. Whichever comes
   first removes the entry, so whatever comes after it finds no entry and is dropped. `:pass`,
   a crash, an exit, a value that is not a decision, and the deadline all answer an empty body.
   A request the plug closed first removes the entry and writes nothing.
3. **The response** is `hookSpecificOutput: {hookEventName: "PreToolUse", permissionDecision,
   permissionDecisionReason}`, with the reason only beside a deny: 2.1.322 keeps it only beside
   deny or ask.
4. **A row per decision.** `Table.decide/6` writes the row, keyed `PreToolUse:<session>:
   <tool_use_id>`, with the response as its `decision` and `actor` `app`, before the response
   goes out. If a row with its key is there, it answers that row's decision instead. A post
   whose key has a row is answered from it at once, with no callback asked. `intake_events`
   gains an `actor` column. A file made before it gains it at open, as `Delegates.Table` does
   for `options`.
5. **PostToolUse** is answered 200 at once and handed to `post_tool_use:` in a process of its
   own, with no row.
6. **The settings.** `Intake.hooks/4` takes the tool callbacks given, and writes a PreToolUse
   or PostToolUse `http` hook only for each one named, with a 10 s timeout. `onFailure` stays
   at its default, continue, as for the other events. `Accounts.prepare/3` passes
   `intake: %{tools: …}` on. With no callback, no hook is written, and a tool post that comes
   anyway is answered empty and stored nowhere.
7. **`caf_example`.** `Config` gains `tool_hooks: %{pre_tool_use: fun, post_tool_use: fun}`.
   `Example` gives them to `Intake` and names them to `Accounts`. Its `agent:` lookup finds the
   tool call's session among `Sessions`' rows of that account.
8. **`docs/design.md`**: "Intake" says when the tool hooks are written, and has a bullet on a
   held PreToolUse. "The model" says what `Intake.tla` now checks. The parts table says
   `Intake` holds PreToolUse hooks too.

## Tests

- `IntakeToolsTest`: each answer (`:allow`, `{:deny, reason}`, `:ask`, `:pass`) and its
  response body; the event the callback gets, with its agent; a row per decision with actor
  `app`, and none for a pass. A duplicate post is answered from the row, and no callback is
  asked. The deadline gives an empty body, and a decision after it writes no row. A crash and an
  exit each give an empty body. A slow callback blocks neither another call nor another event.
  A restart ends an open request with an empty body and no row. A PostToolUse is answered at
  once and handed on, with no row. With no callback, both tool events are answered empty with
  no row.
- `IntakeTest`: the parser's properties include the tool events.
- `AccountsHooksTest`: the settings with no tool callback, with each one, and with both.
- `ExampleTest`: the tree started with both callbacks. The account's settings name both hooks.
  A PreToolUse for `WebFetch`, posted over HTTP to the URL and with the headers the settings
  name, is denied with the app's reason. One for `Read` passes, and a PostToolUse reaches the
  app's callback.
- `Intake.hooks/4`'s doctest: no PreToolUse hook without its callback, and a 10 s one with it.

## What I measured

- The PreToolUse output shape, from the strings of the devenv Claude Code 2.1.322 binary, as
  F-24 read them: the zod schema `hookEventName: "PreToolUse", permissionDecision:
  allow|deny|ask|defer (optional), permissionDecisionReason (optional), updatedInput,
  additionalContext`. The reason is kept only when the decision is deny or ask (`y=h==="deny"||
  h==="ask"`). `defer` is "print-mode only" and ignored interactively. `Intake` never sends it.
- TLC, on this machine under load: `Intake_Tools` has 1 026 distinct states, depth 13, 4 s.
  `Break_Intake_TwoResponses` has 14 states, and `Break_Intake_LateSent` 17. `Intake_Events`
  (12 s) and `Intake_Holds` (14 s) are unchanged by the tool calls, since they set none.
- The diff is 756 changed lines apart from this note and the model's configurations (51): 370
  in the libraries, 216 in tests, 143 in `Intake.tla` and 20 in the design. See new-5.

## What I ran into

- `mix test` inside one app's directory fails the umbrella's dependency check, so the tests
  ran from the root by path, as in F-110.
- An `init` that returns `{:stop, …}` under `start_link` takes its linked caller down. That is
  one reason the first version's check of the deadline's bound (refused at start when not
  under 8 s) came out again. The other reason was size. The bound is now stated in the docs,
  and the plug's own wait is the deadline plus 1.5 s.
- `send/2 && value` in a test callback is a type warning under this Elixir, since `send`
  never returns a falsy value. The tests use a small helper instead.

## What the permission policy will need from this unit

- The same way of asking: a callback in an unlinked process, a deadline timer in `Intake`, and
  one entry whose removal drops whatever comes later (`hand/4`, `drop_tool/3`). A
  `PermissionRequest` already holds an open request, so the policy is asked while the row is
  `held`. Its decision would go through `answer/4`'s path (`answering`, then `answered`), so
  the existing restart rules (`lost`, `unknown`) still hold.
- The `actor` column, for "its decision recorded as a person's is": the policy's rows say
  `app`, and an answer through `answer/4` would need its actor too (none is recorded today).
- The event shape. A PermissionRequest carries `tool_name`, `tool_input`, `tool_use_id` and
  `permission_suggestions`, so the same `tool_event` and `agent:` lookup serve it.
- `Intake.tla`: the policy's ask is a step between `HoldStored` and either `AnswerAsked` or
  "wait for a person". It needs a Break of its own, such as "the policy's late answer is sent
  after the hold was handed to a person".

## Findings

### new-1. The design said PreToolUse and PostToolUse are not read

What happened: "Intake", Transport, said "PreToolUse and PostToolUse are not read: they carry
every tool input, and `Transcripts` reads those". Item 12 of the order of units reads them.
Why: item 12 was added later (F-108), and the Transport bullet was not changed with it.
What I did: I followed item 12. The bullet now says the tool hooks are written only when the
app gives a callback, and are not stored as they come. A new bullet describes the held
PreToolUse.
What the design should change: confirm the new wording.

### new-2. A decision's row does not show that Claude Code read it

What happened: the row is written before the response, as the brief asks. A restart, or a
request Claude Code closed, between the write and the response leaves a `deny` row while
Claude Code read an error and ran the tool, under `onFailure` continue.
Why: the model's `DecidedHasRow` goes one way only. A decided call has a row, but a row does
not mean a decided call. `PermissionRequest` solves this with `answering`, then `answered`.
What I did: nothing beyond the order the brief gives. The row records what the app decided.
What the design should change: say that a PreToolUse row is the app's decision, not the tool
call's outcome. Name the reader that confirms it (a PostToolUse for that `tool_use_id`, or the
transcript), or give the row `answering` and `answered` as `PermissionRequest` has, before the
policy unit records decisions "as a person's is".

### new-3. Claude Code may ignore a hook's allow

What happened: the 2.1.322 strings hold "permissionDecision=allow ignored: it matched this
tool only through another of its names, which can deny or ask but not allow", and "while auto
mode is on (also behind plan mode) a hook cannot approve".
Why: Claude Code ranks hook decisions (allow < ask < deny) and lets some modes refuse an allow.
What I did: nothing. `:allow` is sent as it is.
What the design should change: say that a hook's deny and ask always hold, and its allow is
advisory: the permission policy must not count an allow as the tool having run.

### new-4. `Intake` does not know which agent a session is

What happened: the brief's event "names the agent". A hook post carries a `session_id` and
the account (by its URL), not the agent.
What I did: `Intake` takes an `agent:` lookup per instance. `caf_example` finds the session
among `Sessions`' rows of the account. An interactive session's `session_id` is nil there
until its session file names it, so its first tool calls may name no agent.
What the design should change: name the one place where a session id becomes an agent's name
(the `Tracker`, `Registry` or `Sessions`), so `Intake`, `Transcripts` and the policy all use the
same lookup.

### new-5. The unit is over its size

What happened: the diff is 756 changed lines apart from this note and the configurations,
against 500. The model is 143 of them, and the tests 216.
Why: the brief asks for the model, two hooks, the rows, the settings, the example and seven
kinds of tests in one unit.
What I did: I removed a check of the deadline's bound and two tests that other tests cover,
and kept every requirement of the brief.
What the design should change: give such a unit two branches: the model and PreToolUse in
one, and PostToolUse with `caf_example` in the next. Or say that the 500-line bound excludes
the spec.

### new-6. A callback that never returns keeps its process

What happened: at the deadline `Intake` answers and forgets the call, but the callback's
process runs on. The model lets it, since its late answer is dropped. A callback that hangs
leaves one process per tool call. Each PostToolUse also starts a process, with no bound.
What I did: nothing. A callback's process is not killed, so a callback in the middle of a
side effect is never cut short.
What the design should change: decide whether `Intake` kills a PreToolUse callback at its
deadline (as `Task.shutdown/2` would), and whether the app's callbacks run under a task
supervisor the embedding app starts, with a bound.
