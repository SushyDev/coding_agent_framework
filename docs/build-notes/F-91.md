# F-91: `Copy.tla` models a service's forwarded port

Model only, no code. F-89 designed a service's forward (an `ssh -N -L` with
`ExitOnForwardFailure`, held by dtach on the workstation) and left it unbuilt until its life
beside the service's is modeled (F-89, new-1). This unit models it in `Copy.tla`.

## What was built

- `Copy.tla` gains the forward, for the services in a new constant `Fwds`. It is in `Copy.tla`,
  not a spec of its own, because its start, end and reopen interleave with the service's own
  steps there (`StartReplies`, `SettleStarting`, `EndSent`, `EndConfirmed`, `AskRestart`,
  `OwnerSeen`, `FrameworkDies`); a separate spec would have to copy them. Every other
  configuration sets `Fwds = {}`, the new variables never move, and their state counts did not
  change, so the fast configurations stay as fast.
- Steps: `FwdStartSent` (once the start is settled), `FwdLands` (dtach -n's answer), `SshBinds`,
  `SshFails` (port taken, or no connection), `FwdDrops`, `OtherTakes` (another program takes the
  local port), `FwdSettles` (open, or dead: a start's forward ends the service, a reopen's waits
  for a person), `FwdLossClaimed`, `FwdReopens`, `FwdReopenMoot`, `FwdEnd`. A forwarded
  service's start answers `started` once its forward is open, not at dtach's answer.
- Properties: `ForwardOnlyToCurrent` (a held forward was started for the row's current start,
  whose process is held), `ForwardEndsWithService` (an ended or refused row has no forward),
  `PortIsTheForwards` (a row says open only while its own ssh holds the local port),
  `OneReopenPerState`, and the liveness `ForwardReopened` (a lost forward is held again, or
  waits for a person, unless the service stops first). The existing `RunAnswered`,
  `ServiceEndsWithOwner` and every service invariant are checked with the forward too.
- `Copy_Forward.cfg`, and eight Breaks, each failing on its property:

  | Break | guard removed | fails |
  |---|---|---|
  | `ForwardEarly` | the forward starts after the service's start is settled | `ForwardOnlyToCurrent` |
  | `ServiceEndFirst` | the service's end waits for its forward's socket to read dead | `ForwardOnlyToCurrent` |
  | `OpenByPort` | open is the forward's own ssh on the port, not any listener | `PortIsTheForwards` |
  | `FailKeepsService` | a forward failed at the start ends the service before the refusal | `NoUntrackedProcess` |
  | `ActWithoutCheck` | the reopen acts only while the claimed state is the row's | `ForwardOnlyToCurrent` |
  | `RetryFailed` | a failed reopen waits for a person | `OneReopenPerState` |
  | `ReopenInMemory` | the row says reopening, durable, before the act | `OneReopenPerState` |
  | `NoReopen` | Recoveries reopens a lost forward | `ForwardReopened` |

- `READING.md` explains the new steps and variables.
- `docs/design.md` is not changed: on `main` it does not yet have F-89's forward text, which
  lands with F-89's pull request. What it should say is in the findings.

## The design's sketch, checked

It holds, with the changes in the findings. The brief's example, a forward that must start
before the service listens, does not arise: ssh binds the local port of `-L` once it has
connected, whether or not anything listens on the host's port, and connects to that port only
when a connection arrives. So the forward starts after the service's start is settled, and the
model checks that order (`ForwardEarly`).

## What I ran into

- The first `Copy_Forward` run failed `RunAnswered`: Recoveries claimed a loss, the owner
  restarted the service, and the act, which checked only that the row runs, opened a forward
  for the new start before the new start's own forward, which then never started. The claim now
  holds the state it claims (the start and the open count), and the act checks it (new-1).
- TLC refuses to compare the string `"none"` with a number or a tuple, so the forward's command
  and claim use `NoCmd == 0` and `NoClaim == <<0, 0>>` (a service's first start is 1).
- `devenv test`'s hooks reported files modified when I edited the spec while it ran; run again
  without edits, it passed.

## Findings

### new-1. A forward's reopen acts on the state it claimed, not on "the service runs"

What happened: TLC found a claim made before a service's restart acted on after the new start
was running (above). Why: "once per state" keys the claim, but an act that checks only that the
service runs reads any later start as the same one. What I did: the claim holds its state, and
the act reads it still the row's (`ClaimCurrent`); `ActWithoutCheck` fails without it. What the
design should change: "Hosts" should say a forward's loss is claimed with its state (the
service's pid and start time, and the forward's open count), and the reopen runs only while
that is still the row's; otherwise it does nothing.

### new-2. A forward is open when its own ssh holds the local port

What happened: dtach's answer says the ssh is held, not that it listens: ssh binds the local
port after it connects, and with a taken port it exits a moment later. A read that the port
listens can see another program's listener (`OpenByPort`). Why: the design's sketch did not say
how the start reads the forward open. What I did: the model reads open only when the forward's
own ssh holds the port. What the design should change: the forward is open when the listener on
`127.0.0.1:<local>` is the forward's pid (for example `lsof -nP -iTCP:<local> -sTCP:LISTEN -t`),
read until it is, or the socket reads dead, or a deadline. The builder should weigh the
program this needs on the workstation.

### new-3. A forward that fails at its start ends its service, with or without a waiting call

What happened: the design says a taken local port "ends the service's start as refused", but
by then the service is held on its host. Why: the forward starts after the service's start is
settled. What I did: the service's start answers only once its forward is open; a forward that
fails there makes the row `ending`, and the call answers refused once the service is ended
(`FailKeepsService` fails without it). The same holds after a restart of the framework, with no
call: a forward the row says is starting and whose socket reads dead ends the service. A forward
that cannot connect (the connection down) fails the start the same way. What the design should
change: say the start's answer waits for the forward, and that a forward failed at the start
ends the service before the refusal, whether or not a call waits.

### new-4. A cut-off or failed reopen waits for a person until the service's next start

What happened: a reopen that fails, and a claim a restart of the framework cut off before its
act, leave the row's forward `failed`; nothing reopens it until the service's next start. Why:
once per state, and no hidden retry. What I did: modeled both as `failed`; no clear by a person
is modeled. What the design should change: name how a person acts on it (a `service_restart`,
which is a new state, may be enough), and note that a reopen tried while the connection is down
fails and goes to a person, where waiting for the connection would not.
