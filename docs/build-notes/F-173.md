# F-173: USER in every launch on macOS

On macOS, Claude Code finds the login's Keychain item by `USER` and by nothing else. The item's
account is the OS user. With the same binary, the same `CLAUDE_CONFIG_DIR` and `env -i HOME PATH
TERM LANG`, `claude auth status` answered `loggedIn: false` without `USER`, `true` with
`USER=<the OS user>`, and `false` with only `LOGNAME` (Claude Code 2.1.322).

## What was built

- `ClaudeCLI`: the launch env takes `:user`, passed as `USER` after `LANG`. It is optional in the
  library (a Linux host has no Keychain) and checked when given: a non-empty name with no control
  character, else `{:refused, {:bad, :user}}`. `USER` joined the names the launch sets itself, so
  the tools' state may not set it.
- `Config` (`caf_surface`) takes `user:`, adds it to `env` as `:user`, and refuses
  `{:bad, :user}` when it is missing on macOS or malformed anywhere.
- `caf_example`'s config file takes `launch.user`, by default `USER` of the environment the caller
  hands in.
- `ClaudeCLI`'s moduledoc and `docs/design.md` said `USER` is not needed; both are corrected.
- Tests: the launch env has `USER` after `LANG`; a bad one is refused; the tools may not set it;
  a config on macOS without `user:` is refused; the config file's default and override.

## What I ran into

The Config doctests and `surface_test` built configs without `user:`; they now give one, since
on macOS those would be refused.

## Findings

### new-1. The wrong claim came from reading the moduledoc, not from a measurement
What happened: F-146's new-3 said the OS user name stands in for `USER`; it was never run with
`env -i`. Why: the held launch was only tried from a shell that had `USER` set. What I did:
nothing beyond the fix. What the design should change: a claim about what Claude Code reads from
its environment is measured with `env -i` before it is written down.

### new-2. `bin/caf-login` gets `USER` from the shell it runs in
It does not set `USER` itself, so it names the same item as the held launch only while the
shell's `USER` is the OS user's. A `sudo` or a stripped shell would differ. Recommendation: set
`USER` in the script from `id -un`; not built here, as the brief did not name it.
