# F-155: Linux's argument cap, one memory per checkout, a turn after the report, cloudflared

What a move to a Linux workstation needs first: a launch's prompt cap per operating system, one
agent memory per checkout, a delegate's turn after its report told to its parent, every tool's
state in the home with a commit author of the app's own, and cloudflared in devenv. No test or
step of this unit started the real Claude Code.

## What was built

- **The launch's prompt cap per OS** (G4). `Programs` names the host's operating system
  (`os/1`): `find/3` reads `uname -s` beside the lookup, and `new/3` takes `os:`, a local
  host's being the VM's own (`local_os/0`). `ClaudeCLI.prompt_max/1` answers the cap per OS:
  macOS 512 KiB as before, Linux 126 976 bytes (`MAX_ARG_STRLEN`, 131 072 with its NUL, less
  4 KiB), and `{:refused, {:os, os}}` for one never measured. `Sessions` checks an interactive
  start's prompt against its host's cap. `Mailbox.launch/4` (option `os:`, the VM's own by
  default) writes a first row longer than the cap to `<home>/due/<agent>/<row id>.md`, as a
  typed row's pointer is written (F-142), and the prompt is one line naming it with the row's
  uuid (`Transport.Launch.pointer/2`); with no home it is refused, nothing marked. So
  `Delegates` and `Mains` no longer refuse a long brief, and `caf_mains` no longer uses
  `caf_cli`.
- **One memory per checkout** (G6). `Sessions.Memory.link/3`, before every start or resume
  with a home: the account's `<config>/projects/<encoded cwd>/memory` is a symlink to
  `<home>/memory/<encoded cwd>/`. A real folder there is moved in entry by entry (`rename`,
  never over anything) when the home's holds nothing, and the start is refused `{:memory,
  {:both, account_dir, home_dir}}` when both hold files; a file or a link elsewhere is refused
  and left. `Transcripts.project_dir/2` is the one encoding of a cwd, which `path/3` now uses.
- **A delegate's turn after its report** (G3), modeled first in `Delegate.tla` on F-150's
  `keys`: `OwnWakes` (a background command of its own wakes it while its row is running or
  finished), `OwnTurnEnds` and `TurnTold` (once its report is stored, the notice under the
  turn's key, which Mailbox takes once), with `TurnToldOnce`, `TurnNotReport` and
  `TurnNoticed`; `Break_Delegate_TurnInMemory` keeps the mark in memory and fails
  `TurnToldOnce` after a restart. `MaxWakes = 0` in every earlier configuration keeps its state
  space as it was; `Delegate_Wakes` (headless, a kill and a restart) and
  `Delegate_WakesInteractive` (a person's turn too) check it, and `slow/Delegate_Large` runs
  two wakes. In code: `Stream.Fold` keeps each result that names none of the framework's
  messages in `own`, with its uuid (one with none is a problem); `Transcripts.Fold.own_turns/2`
  finds an interactive delegate's turns begun by a `<task-notification>` with no delivery mark
  (`Waiter.marked?/1`) after the report's turn, each by its reply line's uuid; `Delegates`
  tells each ended one, once the report is taken, by `Mailbox.notify/4` with the new `kind:
  :notice` under `turn:<host>:<uuid>`. The stand-in's results carry a uuid now, as a real
  release's do.
- **Every tool's state lives in the home**, a new pure module `ToolHome` in a new app
  `caf_tool_home` (base layer, uses `caf_shell`):
  - `env/2`: `GH_CONFIG_DIR` (`<home>/gh`), `GIT_CONFIG_GLOBAL` (`<home>/git/config`),
    `GIT_CONFIG_NOSYSTEM=1`, `GIT_SSH_COMMAND` (devenv's ssh with the home's options), and
    `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME` under
    `<home>/xdg/`;
  - `ssh_options/1`: `-F <home>/ssh/config -o UserKnownHostsFile=<home>/ssh/known_hosts`,
    which `Host.ssh/5` takes as `options:` and `Shell`, the copies' rsync and a service's
    forward put before the destination;
  - `prepare/2`, at the app's start: the directories; `ssh/config` and `ssh/known_hosts` made
    empty when missing and never written again; `git/config` whole, renamed into place, with
    the author (`user.name`, `user.email`), SSH signing (`gpg.format ssh`, `user.signingkey`
    the key file, `gpg.ssh.program` devenv's ssh-keygen, `commit.gpgsign` and `tag.gpgsign`,
    `gpg.ssh.allowedSignersFile` `<home>/git/allowed_signers`), the home's `gh auth
    git-credential` as the credential helper of `https://github.com` (an empty helper first),
    and a project's override in `git/projects/<project>.config`, included by `includeIf
    "gitdir:<checkout>/"` with the checkout's physical path, which also holds each of its
    worktrees' git directories. With no author, `user.useConfigOnly`, so git refuses a commit
    rather than guess an author from the machine. A missing key is refused before any git file
    is written (`{:no_signing_key, path}`), and so is a home with whitespace in its path, since
    ssh splits `UserKnownHostsFile` on it.
  - `ClaudeCLI` takes the variables as the launch env's `:tools` (pairs in order, none a name
    the launch sets itself), after the CA bundle. `Copies.Held` (so `Jobs` and `Services`) runs
    every held program on a host in that host's `env` and then the run's own.
  - The example app: the config file's `git` (`name`, `email`, `signing_key` a file name in
    `<home>/git/`, `signing_key` by default) and a project's `git` override; at its start it
    runs `ToolHome.prepare/2` and adds the variables to every launch, every project's `env`
    (git and the setup) and the workstation's jobs and services, with the launch's `PATH`.
    The default `PATH` of a launch and of a project is devenv's programs' directories first,
    then the system's (`/usr/bin:/bin`, and `/usr/sbin:/sbin` for a launch), so a session's
    own Bash tool runs devenv's git. `Programs` names `ssh_keygen`.
  - `bin/caf-login --gh <home>` runs `gh auth login` with the home's `GH_CONFIG_DIR` (and the
    git and XDG variables), `--check --gh` runs `gh auth status`; `--git <home> [--key <name>]
    [--title <title>]` makes `<home>/git/<name>` once with devenv's ssh-keygen (ed25519, no
    passphrase, never over an existing key), prints the public key and offers `gh ssh-key add
    --type signing --title <title>` with the home's gh. `docs/e2e.md` step 0 says so.
- **cloudflared in devenv**, beside tmux and dtach: `CAF_CLOUDFLARED`, `devenv.nix`'s packages
  and `check-versions` (2026.10.7). `CAF_SSH_KEYGEN` too. The framework runs neither
  cloudflared nor a tunnel.
- **Tests** for item 3: `delegates_test.exs` (a headless delegate's own turn told once, its
  report still the brief's, across a later cue and a restart) and
  `delegates_interactive_test.exs` (an interactive one's: the own turn told, a waiter's row and
  a person's turn not); the `own_turns/2` and `marked?/1` doctests.
- **Tests**: `mailbox_launch_test.exs` (a first row past Linux's cap goes as a pointer and is
  settled by its line; no home, refused unmarked), `delegates_interactive_test.exs` (a long
  brief with no home for its file starts nothing), `shell_test.exs` (the OS read beside the
  paths; the home's ssh options before the destination), `tool_home_test.exs` (devenv's real
  git: a commit carries the home's author and a signature git verifies; a project's override
  reaches the checkout and its worktree, and another repository keeps the home's author; no
  author refuses a commit; a missing key, a bad email and a home with a space are refused),
  `claude_cli_test.exs` (the tools' variables in the launch, in order; bad ones refused),
  `memory_test.exs` (one folder across accounts; a folder moved in once; both holding files
  refused; a file or a link elsewhere refused), `mover_test.exs` (a move keeps the memory: the
  file written on the first account reads the same on the second, both links naming the
  home's folder), `console_test.exs` (the config's `git`, its refusals, the `PATH` default,
  and `bin/caf-login --git` making the key once and keeping it).
- **Docs**: `docs/design.md` ("Concepts", "The parts", "How `Mover` does it", "Interactive
  delegates", "Delivery", "Claude Code"), `README.md` (devenv's tools, the apps' chart,
  Status), `docs/e2e.md` step 0, and the moduledocs of each module above.

## What was measured

- **What a tool writes outside the home.** A script ran devenv's git (init, commit, clone,
  worktree add, a commit in the worktree, fetch), gh (`auth status`, `config get`, `repo view`),
  tmux (a server on a socket in the home, then `kill-server`), dtach (`-n` on a socket in the
  home), ssh (to `127.0.0.1`, refused) and rsync, with the real `HOME` and a fresh home, once
  bare and once with `ToolHome`'s variables, and listed what changed in `$HOME` (with the
  folders of unrelated programs left out, and `~/Library` searched for these tools' names) and
  in `/tmp`:
  - bare: ssh read the person's own `~/.ssh/config`, and the ssh agent that file names (a
    password manager's) rewrote four of its files under `~/.ssh/`;
  - with the home's variables: nothing these tools wrote outside the home. gh wrote nothing
    without a login; with one, its `hosts.yml` goes to `GH_CONFIG_DIR` and its state to
    `XDG_STATE_HOME`, but see new-1 for the token.
  - Not measured: Claude Code (no step starts it), gh with a login and the network, and ssh to
    a real host (its known host goes to the home's file by the option itself). See new-2.
- The test suite before the gates: every app's tests passed; the `bin/caf-example` test timed
  out once with the load average at 86 and passed alone.

## What I ran into

- git's `includeIf "gitdir:"` matched nothing in the tests: the test directory is behind a
  symlink (`/var` is `/private/var` on macOS), and git matches the git directory it found,
  whose path is physical. `prepare/2` writes the checkout's path with its symlinks resolved,
  as far as it exists.
- Jobs and services ran with an empty environment before this unit (`env -i` and nothing): no
  `PATH`, no `HOME`. A host's `env` now carries the home's variables and the `PATH`; `HOME` is
  still not set for a job (see new-5).
- rsync's `-e` takes one string it splits on spaces and quotes, so the host's ssh options go
  in quoted word by word.

## Findings

### new-1. gh keeps its token in the OS keyring, outside the home

What happened: `gh auth login` stores the token in the system keyring when there is one
(macOS's Keychain), and `hosts.yml` in `GH_CONFIG_DIR` names only the user. Why: that is gh's
default; `--insecure-storage` keeps the token in `hosts.yml`. What I did: `bin/caf-login --gh`
keeps gh's default, as Claude Code's own login on macOS is in the Keychain too. A Linux
workstation with no keyring service gets the file. What the design should change: say whether
a login's secret may live in the OS keyring or must be in the home (`--insecure-storage`, a
file readable only by its user, as the hooks' secret and the MCP tokens are).

### new-2. What Claude Code writes outside its config directory is not measured

What happened: the measurement ran every tool but Claude Code. Why: no step of a unit starts
the real Claude Code. What I did: nothing beyond the variables, which also reach Claude Code's
own XDG reads. What the design should change: each pinned release's check runs one start, one
turn and one end with a fresh home and lists what changed outside it.

### new-3. The memory's key is the cwd as Claude Code names it

What happened: the brief names `<home>/memory/<project or worktree key>/`. What I did: the key
is the cwd encoded as Claude Code encodes it in `projects/` (`Transcripts.project_dir/2`), one
per checkout or worktree, so it is total for any cwd, needs no second naming rule, and reads as
the same name in both places. What the design should change: confirm it, or name a key of its
own (the path under the home, say).

### new-4. A start whose memory cannot be linked is refused

What happened: the brief says the link is "refused and reported if both hold files". What I
did: the start is refused, `{:memory, {:both, account_dir, home_dir}}`, so a session never
runs on a memory that has split; a person merges the two folders. What the design should
change: confirm, or say the start goes on unlinked with the refusal shown.

### new-5. A remote host's environment, and a job's `HOME`

What happened: the workstation's jobs and services carry the home's variables and the launch's
`PATH`; a remote host's `env` and ssh options are the app's to give, and the example app has no
remote host. A job still has no `HOME`. What I did: `Held` takes a host's `env`, and
`Host.ssh/5` its options. What the design should change: say what a remote host's `env` is (its
own framework directory for the XDG directories, say, and its own `PATH`), and whether a job
gets a `HOME`.

### new-6. ssh's identities still come from `~/.ssh`

What happened: with `-F <home>/ssh/config`, ssh no longer reads the person's config, but it
still offers the default identity files `~/.ssh/id_*`. Why: ssh's own default. What I did:
nothing; it reads, never writes, there. What the design should change: say whether a host's
key must be named in the home's `ssh/config` (with `IdentitiesOnly yes`).

### new-7. `GIT_CONFIG_NOSYSTEM`, and the system's directories on `PATH`

What happened: the brief names `GIT_CONFIG_GLOBAL` only. What I did: every launch, job and
service also sets `GIT_CONFIG_NOSYSTEM=1`, so a system git config never adds an author or a
credential helper. The launch's `PATH` keeps `/usr/bin:/bin:/usr/sbin:/sbin` after devenv's
directories, for macOS's `security`; a session's Bash tool can still find a system program
devenv does not bring. What the design should change: confirm both, and say whether Linux's
launch drops the system's directories.

### new-8. The shape of a turn of a delegate's own is not measured

What happened: a headless own turn is read as a `result` that names no message the framework
wrote, keyed by the result's `uuid`; an interactive one as a turn begun by a user line that
starts with `<task-notification>` and carries no delivery mark, keyed by its last reply's line
uuid. Why: no step runs the real Claude Code, and no fixture holds a background command's wake.
What I did: built on the shapes `docs/build-notes/F-28.md` and `F-31.md` record, and the
stand-in plays them. A wake written as a `queued_command` attachment would not begin a turn here.
What the design should change: the release check records one background command's wake in each
mode, and the fixtures hold it.

### new-9. A headless fold's `own` grows with each turn of its own

What happened: `Stream.Fold` keeps every own turn's result, text and all, for the delegate's
life, and the fold is saved whole at each read. Why: the fold is `Stream`'s alone; `Delegates`
may not trim it, and `Mailbox`'s key is what makes the notice once. What I did: kept them all.
What the design should change: say whether `Stream` drops an own turn once its notice is
stored (`Delegates` telling it so), or keeps only the uuids past a bound.

### new-10. F-150's idle notice is a `msg`, which a delegate's turn answers

What happened: `notify/4` stored kind `msg` only. A `msg` delivered into a delegate makes its
next result a reply (`Mailbox.Table.unanswered/3`), so an idle notice to a parent that is itself a
delegate would be answered by that parent's next turn, as a reply to `framework`. What I did:
the own turn's notice is `kind: :notice`; F-150's stays as it was. What the design should
change: say whether the idle notice is a `notice` too.

### new-11. `bin/caf-login`'s first run calls `mktemp` and `rm` from the system's PATH

What happened: F-153's onboarding step makes and removes its scratch folder with `mktemp` and
`rm` found on PATH, where every other program the script runs is devenv's `CAF_*`. What I did:
kept it as F-153 wrote it, since it is that unit's; devenv has `CAF_RM` but no `CAF_MKTEMP`.
What the design should change: add `mktemp` to devenv's programs and use both by their paths.

### new-12. Two tests fail only under load

What happened: in `gate-test` at load 15 to 30, `SessionsOptionsTest` once got
`{:refused, :turn_running}` from `Sessions.stop/2` called right after a headless start, and
`SessionsDialogTest` twice ran past 60 s; each passed alone, five and three times. Why: the
first stops the session without waiting on an announced event that its turn reads ended (F-152
last changed it); the second is slow under load. Neither runs code this unit changed (no home,
so no memory link). What I did: nothing to the tests. What the design should change: nothing;
the options test waits for the session's turn to read ended before its stop.

### new-13. `caf_tool_home` is in no box of F-162's

What happened: F-162 landed while this unit was under way, and its table of the seven boxes
names the base every box stands on as `caf_shell`, `caf_holder`, `caf_store` and the `Ledger`.
This unit adds `caf_tool_home`, a pure module that uses only `caf_shell` and that the embedding
app calls at its start and `ClaudeCLI`, `Copies.Held` and `Host` take the output of. What I
did: kept it as its own app in the base layer, as `docs/design.md`'s parts table says. What
the design should change: name it in the base beside `caf_shell` (or fold `ToolHome` into
`caf_shell`), so the boundary gate (B2) knows it.
