# F-149: every fix's precondition is checked before its claim

F-148's new-1: a fix refused when it acts keeps its state claimed, so any other fix of that state
waits too. F-148 moved the answer's id before the claim; this unit moves what every other fix
needs of the state it claims, as the brief decided. A fix refused that way takes no claim and
spends nothing, so the next fix of that state is taken. A fix refused by what it meets only when
it acts still settles its claim and keeps the state, as before. It is built on
`framework/f-148-answer-check` (fast-forwarded to its commit), which is not on `main` yet. No test
or step of it started the real Claude Code.

## What was built

- **`Delegates.fix_check/2`**, a pure function of a fix and `fix_state/3`'s state: a `:resume`
  is refused `:resumed_once`, `:live` (its process not gone), `{:status, status}` (its row not
  `running`) and `:session_running` (its agent row not free), in the order `fix/5` refused them;
  a `:stop` `{:report, report}` while the row's report is not `taken` (handed to `Mailbox`); an
  `:interrupt` `:gone` once its process is gone. `fix/5` calls it on the state it reads again, so
  a direct caller meets the same checks, and the resume's own `cond` is gone from its act.
- **`Mains.fix_check/2`**: a `:resume` is refused `{:not_stopped, status}` unless the row is
  `stopped` with a session id. `resume_main/3`'s own check (`resumable/2`) now calls it, after
  its check for a start under way and for a move, which the state does not hold.
- **`MCP`**: the fixer carries `check:` (the module's `fix_check/2`), and `act/5` calls it after
  `held/2` and before `Acts.claim/6`.
- **The model.** `Team.tla`'s `ClaimTaken(c, t, k)` now takes the fix `k` the caller names, not
  the one the state needs (`Kind(t)` is gone), and `Needed(t, k)` is its guard before `Claim`'s
  `Take`: the process the fix needs (stuck, dead, idle) and, for a resume, a row whose end is not
  asked (the code's `stopping`, refused `{:not_stopped, status}`). `CanAct` still checks the
  same at the act, behind it. `Break_Team_ClaimBeforeCheck` takes any fix's claim on any state,
  and fails `ClaimedStateNeedsFix` (no claim of an interrupt or a resume stands on a current
  state that does not need it). `FixClaimsChecked` is the ghost of the same (`"claim before
  check"`). Both are added to the 20 Team design configurations that check `FixOnClaimedState`.
  `ResumeEnding` now also skips the pre-claim ending check, so it still fails as before.
  A stop is left out of `ClaimedStateNeedsFix`: its idle can pass with no move of the state, as a
  stop's report can be delivered with none in the code, so a stop refused when it acts is not a
  claim before its check.
- **Tests.** `mcp_delegates_test.exs`: a `resume` refused `live` and a `stop` refused `["report",
  "none"]` now leave `Acts.rows` empty, and the next fix of the same state (the answer of its
  held request) is taken and verified; the second `stop` of a delegate whose report is handed but
  not delivered (refused `["report", "queued"]` when it acts) is refused `already_claimed`, which
  shows the act-time refusal still keeps the state; a second resume refused `resumed_once` takes
  no claim. `example_test.exs`: the operator's resume of a declared main session is refused
  `{:not_stopped, "declared"}` twice, with no row in `Acts` for it.
- **Docs.** `docs/design.md`: the claim rule names each check and what is still met only when
  the fix acts; the main session's resume says its `not_stopped` is checked before the claim.
  `docs/e2e.md` had no workaround left for this: F-148 removed the only one (the wrong id).

## What I ran into

- The brief names "an `interrupt` with no turn running" as a precondition read from the claimed
  state. It is not one. A headless delegate's interrupt has no such refusal at all (`Stream`'s
  `Fold.check/2` answers `:ok` for an interrupt line), and an interactive delegate's is refused
  `{:screen, reading}` by `Inlet`, from its screen, which the state does not hold. What the state
  does hold for an interrupt is `gone`, so that is what is checked (`:gone`, which `Stream` gave
  for a headless one already). The screen's refusal stays an act-time one (new-1).
- The brief names "a `stop` refused for its report state (`{:report, status}`)". The state holds
  the row's `report` (`none`, `held`, `taken`), not `Mailbox`'s status of it, which the stop
  reads when it acts. So `none` and `held` are refused before the claim; `taken` but not yet
  `delivered` is refused after it, and keeps the state (new-2).
- `Agents.ended?/1` (the stop's `{:status, "ended"}`) and `Mailbox.open_to/2` (`{:open, ids}`)
  are not in the state either; they stay act-time refusals.
- A resume refused for both a start under way and a status not `stopped` was refused `{:running,
  name}` by `Mains`; through `MCP` it is now `{:not_stopped, status}`, since that is checked
  first. `resume_main/3` called directly still answers `{:running, name}` first.

## Findings

### new-1. An interactive delegate's interrupt with no turn on its screen still spends its state

What happened: the brief decided that an interrupt with no turn running is checked before the
claim. Whether a turn runs is read from the screen by `Inlet.interrupt/3` when it acts, not from
the state `fix_state/3` reads (the newest hook event's id, the requests held, whether its agent
row runs). So such an interrupt still claims, is refused `{:screen, reading}`, and keeps the
state until the delegate's state moves (its next hook event). Why: the state an interactive
delegate's fix claims does not say whether a turn runs. What I did: checked `gone` only, which
the state holds. What the design should change: decide whether the state names whether a turn
runs (from `Intake`'s hook events: a prompt submitted with no stop after it), so the interrupt is
checked before its claim, or whether this refusal stays an act-time one. I recommend the first:
the hook events are already what moves that state.

### new-2. A stop before its report is delivered keeps a state that delivery does not move

What happened: a stop of a delegate whose report is handed to `Mailbox` but not delivered is
refused `{:report, "queued"}` (or `due`, `sending`) when it acts, and its claim keeps the state.
The delivery of the report moves nothing `fix_state/3` reads, and a finished delegate's state
then moves no more by itself, so every later stop of it is refused `{:already_claimed, by}` until
something else moves it (a message to it, its process's exit); meanwhile `end_main` of its main
session is refused while it lives.
The test of `mcp_delegates_test.exs` now shows the second stop refused that way. Why: the report's
delivery is `Mailbox`'s, read by the act, not part of the claimed state. What I did: nothing past
the row's own `report`. What the design should change: name the report's `Mailbox` status in the
delegate's fix state (`fix_state/3` reads `Mailbox.answer_to/2` when the row's report is
`taken`), so the stop's whole report check comes before the claim and the delivery moves the
state. `{:open, ids}` (a row to it still open) is the same case, and would need its rows' states
named too.
