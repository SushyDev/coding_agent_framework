# F-138: the `ask` tool: an agent asks a person, without blocking

An agent asks a person through its `ask` tool and goes on at once. The app reads the open asks,
shows each as a dialog, and answers through one function. The answer reaches the agent as a
row of `Mailbox`, as any message does.

## What was built

- **The model first.** `Team.tla` owns the ask, since it holds the operator and who may reach
  whom. `Ask(a)`: any live agent stores a row to the operator, which Delivery's `StoreRow`
  keeps (`kept`), since the operator is no session; the step leaves the agent's turn as it was.
  `Answers(o, i, t)`: the operator stores one row to the agent that asked, under the ask's key,
  due as any row, settled `ended` by `EndedFirst` when the asker ended first. New constant
  `MaxAsks` (0 in every earlier configuration). Three new invariants, each with its `Break_*`:
  - `OperatorRowsKept`: every row to the operator is kept, an ask or a reply or notice to its
    own message; no message goes to it. `Break_Team_MessageToOperator` lets an agent's message
    go to the operator.
  - `AnswerOnce`: an ask has at most one answer. `Break_Team_AnswerTwice` drops the check.
  - `AnswerToAsker`: an answer is the operator's, to the agent that asked.
    `Break_Team_AnswerToOther` lets it go to any agent.

  `Team_Asks.cfg` checks them with the existing invariants and `MessageDelivered`,
  `EndedMarked` and `ClaimEnds` over a restart. `Delivery.tla`'s `TypeOK` takes the kinds `ask`
  and `answer`.
- **`Mailbox.Ask`**, a pure module: the questions' shape (one to four; each a header, the
  question, two to four options with distinct labels and a description, a multi-select flag;
  string or atom keys, stored as JSON), the answers' check (one per question; labels among the
  question's, at most one unless multi-select; labels or the person's own text, not neither),
  and the text the agent gets, one line per question: `Ask 7, Base: Rebase; the person wrote:
  then push`.
- **`Mailbox`**: `ask/4` stores the row (kind `ask`, from the agent to `Grants`' operator) and
  answers `{:ok, {:asked, id}}` at once; refused with no row for bad questions, an agent the
  tree does not hold, no operator, or the operator itself. `open_asks/2` and `asked/3` are the
  app's reads (each ask with its questions and, once answered, the answer's id, text and
  status). `answer/4` stores the answer (kind `answer`, `reply_to` the ask's uuid); the
  table's unique `reply_to` keeps the first and refuses a second (`:answered`). The private
  writer of a delegate's reply was renamed `reply_row` to free the name.
- **`MCP`**: the `ask` tool with its input schema; it answers `%{ask: id}`.
- **The example app**: its doc says how an app shows and answers asks, and a test runs the
  whole path: a delegate's `ask` call, the open ask read, the answer, a second answer refused,
  the answer delivered by the stream and taken by the stand-in.
- **Design**: the tools table's row, a paragraph on an ask under "The operator", and
  `Team.tla`'s invariants in "The model".

## What was measured

| configuration | distinct states | time |
|---|---|---|
| `Team_Asks`, one ask, a restart, no fault | 4,792 | 10 s |
| the same with one fault (first draft) | 190,440 | 476 s |

The fault was dropped from `Team_Asks`: an answer is delivered by the same steps a message is,
and the fault configurations check those. Each `Break_Team_*` of this unit fails in 3 to 4 s.

## What I ran into

- `Mailbox.answer/4` with a default argument clashed with the private `answer/4` that stores a
  delegate's reply; renamed the private one.
- The example test first read the stand-in's log of what it took once the row read
  `delivered`; the replay can settle the row before the stand-in writes its log, so the test
  now waits for the line.

## Findings

### new-1. Rows to the operator are `queued` forever, not `kept`

What happened: `Delivery.tla` stores a row to no session as `kept`. In the code a row to the
operator, a reply to its message before this unit and now an ask, is stored `queued`, and the
next settle marks it `attempt: no_delivery`. It stays in `Table.open_rows/1`, so every settle
reads every ask and every reply to the operator again, for good. `Mailbox.reply/2`, which the
design names for the operator's replies, is not built; `answer_to/3` serves.
Why: rows to the operator went through the one store and the one target function, which finds
no transport for a name that is no agent.
What I did: kept asks the same way as the operator's replies, as the brief says.
What the design should change: store a row to the operator as `kept`, a status of its own out
of `open_rows`, at the store, for replies, notices and asks alike; and either build
`Mailbox.reply/2` or name `answer_to/3` in its place.

### new-2. An answer of several questions to a main session with no waiter waits for a waiter

What happened: the answer is one line per question. The typed transport sends one line only,
so the `Inlet` refuses a text of several lines, and the row waits for the session's waiter.
Why: Enter in the input box sends the line; that is the typed transport's rule for any text.
What I did: nothing; a session's turn end starts a waiter, which takes it.
What the design should change: say in "Delivery" that a text of several lines goes to an
interactive session by its waiter only, or decide how such a text is typed.

### new-3. The answer's labels are kept only as the agent's text

What happened: `asked/3` shows the answer's text and status, not the labels the app passed.
Why: the table has no column for them, and the text holds them, one line per question.
What I did: nothing more.
What the design should change: if an app needs the labels back, a column for the answer's
JSON beside its text.
