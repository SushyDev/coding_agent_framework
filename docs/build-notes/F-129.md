# F-129: R9 part 1, the agent row and the tree

R9 (`docs/design.md`, "The parts", "A session's life", "What `Delegates` holds", R9), with
F-115's section 2, new-7 and new-11, F-117's new-2, F-120's new-2, F-126's new-1, new-2 and
new-4, and F-127's new-2 read for it. R9 now goes before R8, since R8's typed write needs R9's
turn function for an interactive session (F-127's new-2); "Order of the first units" says so.
The unit ran past its size, so it stops at the clean point the brief names: the row and the
tree are built, and the turn state, the `Acts` rows, `Store`'s one rule and the last two writer
sources are its second part (new-1).

## What was built

- **The agent row.** `Sessions`' table is `agents` (it was `held_sessions`): one row per agent,
  main session or delegate, with `kind` (`main`, `delegate`), `parent` and `project` beside
  what it held. A launch names `kind:` (by default from its role), `parent:` (a delegate must
  name one: `{:refused, {:missing, :parent}}`; a main session none: `{:refused, {:bad,
  :parent}}`) and `project:` (a worktree's by default); a resume keeps the row's. Two statuses
  are new: `declared`, a main session the embedding app names (`Sessions`' `mains:` option,
  until `Mains`), written when it has no row, and `ended`, a delegate done for good, which
  `Sessions` writes when `Delegates` asks (`Sessions.ended/3`) and only once no process of it
  may live. The cue is `sessions:<host>`: a row is the host's, not an account's, so a move
  will not change its topic.
- **`Sessions.Agents`**, the read side every other part uses: `open/2` (a reader's own
  connection to `Sessions`' file, which never writes, so no reader waits on `Sessions`'
  process, which itself waits on `Mailbox` in a stop), `get/2`, `rows/1`, `by_session/3`,
  `place/2`, `children/3`, `ended_names/2`, and the tree: `tree/1`, a total function of rows
  (every row of kind `main`, every delegate's row with its parent), and `read_tree/1`. Each
  status's meaning is a predicate there: `holds?/1` (an agent of the tree), `ended?/1` (no
  process of it will run again), `active?/1` (holds its parent's cap), `free?/1` (no process
  may live, so the name may start again), `running?/1`, `starting?/1`, `headless?/1`,
  `since?/2`. No part outside `caf_sessions` names a status of
  the agent row.
- **The statuses, once.** `Sessions.Table` lists every status once (`statuses/0`) and derives
  `free/0` and `done/0` from it; each derived list is checked against the full one when the
  module compiles. `Delegates.Table` does the same for its own statuses. The check, run by
  hand on this branch (then undone): renaming `stopped` to `exited` in `@statuses` alone,

  ```
  == Compilation error in file lib/coding_agent_framework/sessions/table.ex ==
  ** (CompileError) free names stopped, not a status of agents
  ```

  It fails in the one part that owns the statuses: `Mailbox`, `Delegates`, the `Tracker`,
  `Grants` and the app read `Agents.free?/1` and the others, which change with it. Inside
  `Sessions`, its own writes and settles still name statuses as text, as before; the check
  covers the lists other parts read through, not those clauses.
- **`Delegates`' table** keeps only the protocol's facts: `name`, `branch`, `model`,
  `brief_uuid`, `resume_uuid`, `status` (`starting`, `resuming`, `running`, `finished`,
  `failed`, `refused`), `reason`, `resumes`, `report` and its `text`, and its calls' times. Its
  parent, project, account, session id and launch options are the agent row's; `ended` moved
  there. The cap counts the parent's delegates the tree holds (`Agents.children/3`) and its
  starts under way in memory (a start a restart cut before it reached `Sessions` never will).
  A report goes to the agent row's parent. A resume names no options: `Sessions` takes the
  row's. Only each name's latest row moves; an older one is history.
- **The end of a delegate**, one rule: a failed one (killed twice, or its resume refused) ends
  once no process of it may live, at once, since it is never resumed again; a finished one once
  its report was delivered, since only then is it stopped. Its services then end, by the agent
  row's cue. It keeps its place and its edge in the tree (`agents()` shows it `ended`), so its
  kept services go to its parent (`Grants.parent/2`) and a message to it is settled `ended` by
  `Mailbox`; it no longer holds its parent's cap.
- **The readers.** `Grants` is handed `Sessions.Agents.read_tree/1`; a main session is an entry
  with no parent, and only that (the fallback "a parent no entry names" is gone).
  `Tracker.Tree` folds the view's agent rows by `Sessions.Agents.tree/1`, the same rule, so the
  two no longer disagree (F-99's new-3; only their freshness differs, as before). `Mailbox`
  reads the addressee through `Sessions.Agents`, and settles a row to an agent that ended
  `ended`, except a brief stored since the end: that is a later start's, stored before
  `Sessions` writes the start, and waits for it. The app's `tree`, `place`, `agent_of`, `ended`
  and the ends' ids are `Sessions.Agents`' functions; it opens no table; it hands `Sessions`
  its declared mains; `sessions` cues now reach the ends, `delegates` cues no longer do.
- **The sources** (F-120's new-2, in part): `Sessions.Table.meta/0` and `Delegates.Table.meta/0`
  make their `Tracker` sources from `Tracker.TableSource` (`ReaderSource` renamed), each per
  host (`Reader.describe/2` takes `name: nil`); `SessionsSource` and `DelegatesSource` are gone.
  `caf_tracker` no longer uses `caf_delegates`.
- **The design and README.** "The parts" (the layers' sources), "A session's life" (`declared`,
  `ended`, the tree), "What `Delegates` holds" (the agent's life and the cap, and what
  `Delegates`' row keeps), R9's two parts, and R9 before R8. README's status and its chart.

## Migration

- `Sessions.Table.open/1`: a file with `held_sessions` has its rows taken into `agents`, ids
  kept (the `Tracker`'s keys stay), each of kind `delegate` when it ran headless and `main`
  otherwise, with no parent yet; then `held_sessions` is dropped, in one transaction, so a
  second open takes nothing. A reader (`Sessions.Agents.open/2`) never migrates.
- `Delegates`, at its start: an earlier build's `delegates` holds each delegate's parent and
  project. It hands them over first, from each name's latest row
  (`Sessions.adopt_tree/3`: a delegate row with no parent takes them, and one the old table had
  `ended` is `ended` when no process of it may live), then rebuilds its table with its own
  columns, an `ended` row as `finished`. A hand-over that fails stops `Delegates`' start, so
  nothing is dropped before `Sessions` has it. The hand-over goes through `Sessions`, not by
  one part's migration opening the other's table, and works when the two tables are in two
  files.

`AgentsTest` writes `held_sessions` as the earlier build made it and checks the rows taken, and
the hand-over (`adopt_tree/3`) once.

## What I ran into

- A reader that called `Sessions`' process would deadlock with a stop: `Sessions`' stop reads
  `Mailbox` (`open_to:`) inside its call, and `Mailbox` reads its addressee's row at each
  settle. So the read side is a pure module over a reader's own connection, as the `Tracker`'s
  sources already are, not a call.
- The first rule for a delegate's end (its report delivered, for both outcomes) never ended a
  delegate killed twice whose main session is declared with no process, as the example app's
  test has it: the notice is never taken, so its services never ended. A failed delegate's
  process never runs again, so it ends at once; its report stays the parent's row.
- A first rule took an ended delegate out of the tree. `Services` then could not hand its kept
  services on: it asks `Grants.parent/2` for an owner that has ended, and the tree no longer
  held it (the build before had the same gap for a delegate stopped after its report, and none
  for one killed twice, which stayed in the tree for ever). So an ended agent keeps its edge,
  and the cap and the ends read `ended?/1`.
- Several tests' trees named only delegates, and relied on `Grants`' fallback that took an
  unnamed parent for a main session. They now name each main session, as `Sessions`' tree does.
- `Recoveries`' tests write agent rows themselves; `Table.starting/2` takes the kind from the
  role when none is given, as the migration does.

## Findings

### new-1. R9 is two units

What happened: the row, the tree, the read side, `Delegates`' table and its migration, and the
readers and their tests came to +1,357 −675 (library +972 −537), where R9 was estimated at
+300 −350 in all.
Why: every part that read `Sessions`' or `Delegates`' table changes, and so do their tests,
which wrote and read the old columns.
What I did: stopped at the clean point the brief names. Part 2 is the turn state per kind of
session (a headless session's from `Stream`'s fold; an interactive one's from the session
file's `status` through `Registry` and `Intake`'s waiter, never one read alone when it decides
a write), the `Acts` rows (a start, `Delegates`' resume, a service's restart and stop, a
raised error), `Store.update/4`'s one rule with the stored values converted, and `Stream`'s and
`Intake`'s sources as `TableSource`. The design's R9 entry says so.
What the design should change: R9's size, and its second part before R8.

### new-2. A delegate's life is not all the agent row's status

What happened: the design said a delegate's life (running, finished, failed, ended) is its
agent row's status. Only `ended` is: whether a delegate finished with a reply or failed with a
notice is the protocol's outcome, which `Delegates` decides and keeps, and the agent row's
status is its process's life (starting, running, stopped, …), which `Sessions` reads.
Why: putting `finished` and `failed` on the agent row would have `Sessions` write a higher
part's outcome, and a stopped row would then mean two things.
What I did: `ended` is the agent row's (written by `Sessions` when `Delegates` asks); the
outcome stays in `Delegates`' row. "What `Delegates` holds" says so.
What the design should change: confirm that split, or name the field of the agent row that
should hold the outcome (as `Mover`'s phase will be one).

### new-3. A failed delegate held its parent's cap for ever

What happened: before this unit, a delegate killed twice stayed `failed` and held its parent's
cap for ever, while the app took it as ended and ended its services: two rules for one end.
What I did: one rule. It ends once no process of it may live, which is at once; its notice
stays its parent's `Mailbox` row.
What the design should change: nothing more; "What `Delegates` holds" says it.

### new-5. An ended delegate stays in `agents()`

What happened: an ended delegate keeps its row and its edge, so `agents()` lists every
delegate name a host ever started, `ended`, and a message to one is stored and settled
`ended` (before, `Grants` refused it as `unknown_agent`, unlike "Messages" in the design).
Why: its kept services go to its parent, which `Grants.parent/2` reads from the tree.
What I did: nothing more; a name's later start takes the same row.
What the design should change: decide whether `agents()` shows ended delegates, or a view
filters them; and whether an ended row is ever dropped (a retention rule), as F-126's new-5
asks of `Acts`.

### new-4. A start under way counts in its parent's cap from memory

What happened: between `Delegates`' row and the agent row `Sessions` writes, the parent of a
start under way is known only to the `Delegates` process (for the cap). After a restart, a
start that had reached `Sessions` is counted by its agent row; one that had not never runs.
What I did: nothing more.
What the design should change: nothing, unless a start must be counted while its call sits in
`Sessions`' queue across a restart of `Delegates`; then `Delegates`' row keeps the parent as its
call's argument.
