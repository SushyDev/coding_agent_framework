# F-63: `Stream.Table` loads a stored fold of an earlier build without dropping it

## What was built

`Stream.Table`'s private `load/1` now follows "State that never lags or lies", rule 4 (Total
folds), for a stored fold, and answers what it found:

- A stored map missing some of `Fold.new/0`'s keys loads as `Map.merge(Fold.new(), stored)`: the
  missing fields get their defaults, and the offset, messages and requests stay. Nothing is
  reported; this is the normal case of an older build's row.
- A stored map with keys `Fold.new/0` does not have loads with the known keys only, and the
  problem `{:unknown_fields, keys}` (the keys sorted).
- Bytes that `binary_to_term(…, [:safe])` refuses, or that are not bytes, load as `Fold.new()` with
  the problem `:unreadable`; a term that is not a map loads as `Fold.new()` with `:not_a_map`.

`load/1` returns `{fold, problems}`. `Stream.rows/2` (that is, `Table.rows/2`) and
`Table.rows_by_id/3` had no problems list, so each row now carries one, `load_problems`: `[]`
when the stored fold was whole, otherwise the problems above. It is a list on the row, the shape
`Registry.SessionFile` gives its own `problems`, and it adds 10 lines net to the code, so the
`Logger.warning/1` fallback is not used. It is not a field of the fold: `Fold.new/0` is
unchanged, and the fold's `problems` count (log lines that were not JSON objects) is a different
thing. `Table.delegates/2`, the writer's own view, takes the fold and drops the problems (new-2).

Tests, `apps/caf_stream/test/stream_table_test.exs` (a SQLite file under the test's own
`TestHost.test_dir/0`, the fold's bytes rewritten with an `UPDATE`):

- a fold as written loads whole, with no problem;
- a fold lacking `:ending` loads with its offset and `ending: false`, for a reader and for the
  writer;
- a fold with an extra field loads with its offset, without the field, and names it;
- a fold lacking one field and holding another is both;
- bytes that are not a term, and a term that is not a map, load as `Fold.new()` with a problem;
- `rows_by_id/3` answers the same problem as `rows/2`.

## Findings

### new-1. A field a newer build added is unreadable to this build, so its row loads as a new fold

What happened: `:erlang.binary_to_term(bytes, [:safe])` refuses a term holding an atom this VM
has never seen. A field a newer build added is a new atom, so a fold written by that build is
`:unreadable`, not `{:unknown_fields, …}`, and loads as `Fold.new()` with offset 0: the case the
rule names ("a field it does not know") only reaches the `unknown_fields` problem when the atom
happens to exist, as it does in the test, where the module that rewrites the row has it as a
literal. Checked by hand: a map whose key is an unseen atom raises `ArgumentError` under `:safe`,
and a map of known atoms decodes.

Why: the fold is stored as an Erlang term with atom keys, and `:safe` is what keeps a stored row
from making atoms.

What I did: nothing more; the brief says bytes `:safe` refuses load as a new fold, and a
mechanism that decodes them would be a new one.

What the design should change: decide how a stored fold carries a field this build does not
know. Two ways: store the fold with string keys (JSON, as the log is), so a later build's field
decodes to a string, is dropped and named without making an atom; or keep the term and decode it
with `[:safe]` after the known atoms are loaded and the unknown ones are mapped by name. The first
also lets the rule hold in both directions. Until then rule 4 holds for a missing field and for
an extra field whose atom this build has, not for the usual later-build case.

### new-2. The problem is seen only until the writer's next write of the row

What happened: `load_problems` is computed when a row is read. The writer (`Stream`) loads a row
at its start with `Table.delegates/2`, which drops the problem, and its next `Table.write/4` of
that row stores the loaded fold, whole, with no unknown field. After that write the row is clean
and the problem is gone, though the data was dropped; and no consumer of `Stream.rows/2`
(`Delegates`, the tracker) reads `load_problems`, so no part shows it.

Why: the problem belongs to the stored bytes, and the write replaces them.

What I did: nothing; a part showing the problem, or a writer that keeps it, is a mechanism.

What the design should change: say where a load problem is kept until someone sees it. The
fold's own `problems` count (log lines) is not the place, because it counts a different thing;
a persisted list on the row, or a `problems` column of `stream_delegates` the writer sets at its
load and clears when read, would be.
