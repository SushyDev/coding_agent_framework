# F-78: `Jobs`, part 2: the fetch, and a job's late end

The rest of `model/tla/Copy.tla`'s `Jobs`: `run`'s `fetch: [paths]` (`FetchBegins`,
`FetchPath`, `FetchDone`, `FetchCut`), and the late end of a job whose call answered unknown
(`JobSettles`, with the end handed to the embedding app).

## What was built

- **The record**: `run/6` passes `fetch:` to `Copies.sync/5`, which records each named path
  (size, time, hash, or `:absent`) before it sends (F-74), and keeps the record. Each named path
  must be relative, with no `.` or `..` part; otherwise the run is refused as
  `{:refused, {:fetch_paths, bad}}` before anything happens.
- **The fetch** (`Copies.fetch/5`, beside the sync, since it uses the same rsync, ssh reach and
  host-side lock): after the end is read and written to the row, for an `exited` or `timedout`
  job, one rsync brings every named path from the copy into a temporary directory in the
  worktree (`.caf-fetch-<n>`), under the host's lock of the copy (the sync's host side, so it
  never reads a later sync's half-written files). Then, path by path: a path the copy lacks is
  left alone; a path whose worktree file no longer matches the record is a conflict; any other
  is renamed into place. The temporary directory is removed whether the rsync completed or not.
- **Answers**: `{:ok, %{exit: code, log: tail, fetch: f}}` and, for a timeout,
  `{:unknown, {:timeout, %{fetch: f}}}` (new-1), where `f` is `:done`, `:none`,
  `{:conflict, paths}` or `{:unknown, reason}`. A `lost` job fetches nothing (`AnswerJob`).
- **The late end**: the row has a `late` column: `owed` or `told`. A call that answers
  `{:unknown, :dropped}` marks its row `owed`; so does `Jobs`' start, for every row `starting`
  or `running` (its call ended with the restart). `Jobs` settles every owed row from the host
  when it starts (`handle_continue`) and at each `cue/2`, in its own process. Every write of a
  row goes through one function: an owed row that has ended (`exited`, `timedout`, `lost`, or a
  cut start read `refused`) is handed to `:on_late_end` as
  `%{job: id, end: {:exit, code} | {:unknown, :timeout} | {:unknown, :no_exit} |
  {:refused, {:start, :not_held}}, fetch: :not_fetched}`, then marked `told`. So a row that
  `settle/2`, a cue and the call's own write all reach is handed on once. `Jobs` sends no
  message: the moduledoc says the embedding app routes the end.

## Tests

`apps/caf_jobs/test/jobs_test.exs`, 12 tests and a doctest, each named for its `Copy.tla`
property:

- `FetchOnlyNamed` (workstation and ssh): the job writes `a.txt`, `d/b.txt` (a new directory)
  and `c.txt` in the copy; with `fetch: ["a.txt", "d/b.txt"]` the first two come back, `c.txt`
  does not, and nothing temporary is left.
- `NoEditLost`: an edit of `a.txt` in the worktree while the job runs gives
  `{:conflict, ["a.txt"]}`; the worktree keeps the edit, the copy keeps the job's version. A
  named path the copy lacks (`n.txt`) is no conflict.
- `AnswerIsReal`, a cut fetch: the connection drops once part of a 4 MB file has come in; the
  answer is `{:ok, %{exit: 0, fetch: {:unknown, _}}}`, the file is not in the worktree, and no
  temporary file is left.
- `JobEndsAtTimeout` with the connection down: after the drop and the connection's return, a
  cue hands `%{job: "jd", end: {:unknown, :timeout}, fetch: :not_fetched}` on once; the row is
  `told`, and a second cue hands nothing.
- `JobSettles`: after a restart, the new `Jobs` settles the running row and hands
  `{:exit, 4}` on once.
- `AnswerIsReal` (exit 0 and 3) now checks `fetch: :none`.

## What was measured

- `caf_jobs`' suite: 12 tests and a doctest in 17 to 19 s, async. With the stand-in's final drop, 26

- Changed lines: about 440 apart from this note; `jobs.ex` grew by about 160, `copies.ex` by

## What I ran into

- A fetch per path into a temporary file beside it failed when the path's directory was new in
  the copy: rsync's sender changes into the file's directory and exits 23. One rsync with
  `--files-from` into a temporary directory has no such case, and takes one ssh command per
  fetch instead of one per path.
- The ssh stand-in's drop killed only its `sh -c`; rsync's server under it kept the stream
  open, so the client waited out its timeout. A real drop closes the connection under every
  process of the command. The stand-in now ends the command's whole tree on a drop, walked by
  parent pid from `ps` (never by a pattern), each process stopped before its children are
  read. A process dtach holds has left the tree, so a job still outlives a drop.
- My first try at that ran the command in its own process group (`set -m`) and killed the
  group. Under `set -m`, bash at times wrote `child setpgid (…): Operation not permitted` into
  the command's output; in `Holder`'s state read that made the start's reply unknown, and the
  start was then read `not_held`. It failed one run in a few, in different tests, and I first
  took it for load and raised the tests' timeouts; a debug print of the cut reply showed the
  note. The timeouts are back as they were.
- Cutting the fetch partway: filtering rsync's stream through a pipe (`| head -c`, even
  `| cat`) breaks its protocol. Under a `cut-fetch` file the stand-in instead adds
  `--bwlimit=1000` to the sender and drops the connection once the file under the temporary
  directory is not empty.

## Findings

### new-1. The design gives a timeout's answer no place for the fetch's outcome

What happened: "Hosts" says `run` answers `{:unknown, :timeout}` "with the fetch's outcome",
and `Copy.tla` fetches for a `timedout` job, but the answer `{:unknown, :timeout}` has nowhere
to put it. Why: F-76 built the timeout as a bare atom before the fetch existed. What I did:
`{:unknown, {:timeout, %{fetch: f}}}`. What the design should change: write that shape in
"Hosts".

### new-2. The late end is handed on at least once, not exactly once

What happened: the row is marked `told` after `:on_late_end` returns. A crash between the two
hands the end on again at the next start. Why: marking first would lose the end if the function
raised. What I did: at least once; the job id lets the receiver drop a repeat. What the design
should change: say that `Mailbox` takes a late end keyed by its job id, so a repeat is one
message.

### new-3. The settle reads the host in `Jobs`' own process

What happened: the start's and each cue's settle read every owed row's host in `Jobs`, with a
2 s read per row, as `Delegates` settles in its own process. While it reads, a run's write to
the row waits, and could reach its own 5 s call timeout with several hosts down. Why: the one
writer of a row must also be the one that hands its end on, or a row could be handed twice.
What I did: so, with the short read. What the design should change: when the one ssh connection
per host is built, a cue could settle only that host's rows, from that host's reader.

### new-4. A cut fetch under a restart can leave a temporary directory

What happened: the fetch removes its temporary directory after the rsync, whether it completed
or not; a restart during the rsync ends the call before that. Why: the row does not keep the
worktree's path, so nothing at the next start knows where to look. What I did: nothing; the
brief asks only that a drop leave nothing. What the design should change: keep the worktree's
path in the row and remove `.caf-fetch-*` there at the next start, or have the fetch's
temporary directory under the framework's home on the same file system.

### new-5. A `starting` or `asked` row a restart left is not owed the same way

What happened: an `asked` row (nothing sent) stays `asked` after a restart, and its caller is
never told. A `starting` row read `refused` is handed on as `{:refused, {:start, :not_held}}`,
which is not an end. Why: `JobSettles` covers `starting` and `running` only. What I did: handed
a refused start on, since its caller had no answer; left `asked` alone. What the design should
change: say whether a restart's `asked` row becomes `refused` and is handed on too.
