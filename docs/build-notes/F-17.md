# F-17: `Sessions`, one host's session lifecycle, without worktrees

## What was built

- **`Sessions`**: a `GenServer` the caller's tree starts, one per host, with no name. It takes
  the host's `Programs`, its dtach directory, its `Control`, a `Registry` per account and a
  SQLite path.
  - `start/5` writes the row first, as `starting`, with the session's name, which is also its
    socket name and its tmux session's name. It holds `ClaudeCLI.session/3`'s argv and
    environment through `Holder.hold/4`, in the given directory (`sh -c 'cd -- "$0" && exec
    "$@"'`, since `Holder` and `Shell` set no directory). It opens a viewer pane (`dtach -a`)
    through `Control`, tagged as it opens, one row short and then grown. It confirms the start
    when the account's `Registry` reads a session file with the session's name and a live pid
    while the socket is live, and keeps that pid and its `procStart` in the row. Answers:
    `{:ok, %{name, pid, session_id}}`, `{:refused, reason}` or `{:unknown, reason}`; an
    unconfirmed start is `{:unknown, :no_session_file}` after its timeout, and its row says so.
    A viewer that fails does not fail the start; the row's `viewer` says why.
  - `resume/6`: the same, with `--resume <id>`.
  - `stop/4` takes the caller's reading of the turn (`:ended` or anything else, which is
    refused), marks the row `stopping`, types `/exit` through `Control.send/4`, and waits until
    `Registry.Liveness` judges the row's `{pid, procStart}` gone or replaced. A refused write
    puts the row back to `running`; an unknown one is waited on and never typed again.
  - After a restart, each row still `starting` is adopted when its socket is live and its
    session file names a live pid, and otherwise ends as `refused` with `interrupted`.
  - The waits read the `Registry` (or `ps`) every `poll` ms until the call's deadline. The
    process serves other calls while one waits.
- **`Sessions.Table`**: `held_sessions`, one row per `{host, name}`; a new start of an ended
  name reuses its row. **`Tracker.SessionsSource`**: the table as a `Tracker` source of kind
  `:held`, topic `sessions:<host>:<account>`, which is what `Sessions` cues on.
- **`Tmux` and `Control`**: `new_session/4` takes `size: {columns, rows}`, and a new
  `resize_pane/4` (`Control.resize/4`) runs `resize-window` and then unsets `window-size`, under
  the same one-command tag check as a write. The CLI and the fake both have it.
- **The stand-in** (`test/support/claude_stand_in.ex`): a bash script started with
  `ClaudeCLI`'s argv and environment. It writes `<CLAUDE_CONFIG_DIR>/sessions/<pid>.json`
  (synthetic `sessionId`, the `--name`, `cwd` and `procStart` as `ps` prints it) at start, on
  the line `go`, or never; echoes its input; exits on `/exit`; and records its pid so the test
  ends it by pid.
- **Tests** (`test/sessions_test.exs`, real tmux and dtach): a confirmed start, its cue and its
  `Tracker` row, a second start of a running name refused, a stop refused without an ended turn
  and then done; a resume; a start whose file never comes answers unknown with a row that says
  so; a `Sessions` killed mid-start, restarted, adopts the live start and ends the dead one as
  `interrupted`. A contract test shows a window opened one row short, grown, with no fixed
  `window-size` left.

## What I ran into

- The first restart test killed nothing: the viewer's row was written before the stand-in had
  recorded its pid, so the test now waits on the pid file. Two dtach masters with their
  stand-ins were left by those two runs, from this test's own VMs; I ended them by pid.
- `with` in the confirmation let `{:ok, :absent}` from `Holder.state/2` fall through as if it
  were a session file, and the restarted `Sessions` crashed at adoption. Its `else` names it now.
- `Holder` and `Shell` have no working directory, so the session's directory is entered by a
  `sh` wrapper inside the held command.

## Findings

### new-1. A start is matched to its session file by `name`, not shown against the real Claude Code

What happened: dtach does not report the held pid, so the confirmation looks for a session file
whose `name` is the session's name (`--name`) and whose pid lives.

Why: nothing else in the file ties it to this start; the `sessionId` is new on a start.

What I did: matched by `name` and a live pid, with the socket live. The stand-in writes `name`;
whether Claude Code 2.1.322 writes `--name` into its session file is not shown.

What the design should change: name the key a start is confirmed by, and check it against each
pinned Claude Code release, as the Remote Control check does (F-15 new-1).

### new-2. A held process with no session file after a restart is left running without a row

What happened: after a restart, a `starting` row whose socket is live but whose file has not
come yet ends as `refused{interrupted}`, as the design says. Its process runs on, and no row
follows it.

Why: the process may only be slow to write its file, and with no file there is no pid to end it.

What I did: what the design says; nothing ends the process.

What the design should change: let the adoption wait for the start's own deadline before it
decides, or end such a process through its socket, and say which.

### new-3. Only `starting` rows are settled after a restart

What happened: a restart in the middle of a stop leaves the row `stopping`, and an `unknown`
row stays `unknown`, even when its process has since exited or written its file.

Why: the design names only a start's adoption.

What I did: nothing changes them, as the brief asks.

What the design should change: settle a `stopping` row by its `{pid, procStart}` after a
restart (stopped when gone, running otherwise), and say whether an `unknown` row is ever read
again.

### new-4. The start and its adoption are a protocol with no spec

What happened: `CLAUDE.md` asks for a spec before the code of a protocol; `Delegate.tla` leaves
the start abstract and the design says it is modeled with `Delegates`.

What I did: built `Sessions` from the design's words, with tests of each path.

What the design should change: model the start (row first, hold, file, restart) in its own
small spec, or in `Delegate.tla`, before `Delegates` builds on it.

### new-5. `Sessions` waits by reading the `Registry` on a timer

What happened: a start and a stop read again every `poll` ms until their deadline.

Why: `Registry`'s cue is a function the host app wires, and `Sessions` cannot be handed it
without a name.

What I did: a bounded wait, read by `Registry.read/2` and `ps`.

What the design should change: say whether a part that waits on a reader polls it or is
handed its cue.
