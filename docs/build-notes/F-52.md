# F-52: `Recoveries` reopens a delegate's viewer with its own command

Closes F-49's finding new-5. No spec changed: the model says that a lost viewer is reopened,
not with which command.

## What was built

- **`Sessions.viewer_argv/3`** answers a row's viewer command from the host's table: `dtach -a`
  of its socket (`Holder.viewer_argv/2`, as before) for an interactive session, and `tail -F`
  of `<home>/streams/<session id>/events.jsonl` for a delegate. A name with no row is
  `{:refused, :no_session}`, as `stop/4` answers it. It is a read: nothing is opened, and it
  waits at most `:timeout` (5 s by default).
- **`Sessions` uses it itself.** A start no longer builds the delegate's `tail -F` inside its
  hold; it asks the same private `viewer_command/2` the public call asks, once the row's map
  exists and before the row is written. So the viewer a start opens and the one a reopen opens
  are one function's answer. `hold/4` and `prepare/3` no longer carry a viewer.
- **`Recoveries`** asks `Sessions.viewer_argv/3` where it asked `Holder.viewer_argv/2`, and takes
  a new required option, `sessions:`. A refusal ends the state `failed` with that reason and the
  agent runs on; an answer that did not come in time (`{:unknown, _}`) ends it
  `failed{no_viewer_command, …}`, since asking opens nothing.
- **Tests.** `caf_sessions/test/sessions_viewer_test.exs`: the answer for an interactive row,
  for a delegate row, for a name with no row and for a `Sessions` that is gone; for the first
  two, the pane `start` opened was started with exactly that command. `caf_recoveries`: a lost
  viewer of an interactive row is reopened with `dtach -a`; one of a delegate row is reopened
  with `tail -F` of its log, and shows the log; one of a socket with no row, and one with the
  host's `Sessions` gone, end `failed` and the agent runs on. `RecoveriesSetup` starts a
  `Sessions` on the test's directory and table, and `hold!/3` leaves the row a start would
  (`"parent"` by default, `"delegate"`, or none).

## What I ran into

- `pane_info.start` in the `Tmux` contract is `pid@start_time`, not the pane's command, so the
  tests ask the test's own tmux server for `#{pane_start_command}` directly, as F-49's test
  already reads a viewer with `capture-pane`.
- `SessionsSetup` ends stand-ins on exit with `HeadlessStandIn.kill_all/1`, which lists
  `<dir>/pids` and fails when no stand-in ever started there. A test that starts none (the
  refusal test) makes the directory first.
- A start now checks the socket name after the directory and role, since the delegate's command
  needs the session id the framework chooses. A name that is bad and also has no directory
  answers the directory's refusal first. No test depended on the order.
- `mix test` inside an app still fails on the umbrella's `:only` options; run it at the root
  with the app's test path.

## Findings

### new-1. A lost viewer is reopened with its owner's command, and `Recoveries` asks only `Sessions`

What happened: a held socket with no `Sessions` row used to be reopened with `dtach -a`; it is
now `failed{no_session}`. That is right for a socket nobody started, but a service (a dev server
held by dtach, owned by one agent) will be held without a session row, and its viewer is its own.

Why: the viewer's command belongs to the part that holds the program. `Recoveries` cannot know
which part that is from a socket name.

What I did: asked `Sessions` alone, and ended the state `failed` when it has no row, rather than
fall back to `dtach -a`, which would reopen a delegate's lost viewer as the wrong program again
whenever its row is missing.

What the design should change: say that each part that holds programs answers its viewer
command, and that `Recoveries` is given the part to ask for each socket (the sampler's held row
could name its owner). Decide it when services are built.

### new-2. `Recoveries`' `holder:` now serves only the host check

What happened: `Recoveries` took `holder:` to open viewers' argv and to check the host. The argv
now comes from `Sessions`, so `holder:` is read once, in `init`, to compare its host with the
server's.

What I did: left the option. A builder does not drop a part's option on its own.

What the design should change: either name the host check as the option's job, or let
`Sessions` answer its host and drop `holder:` from `Recoveries`.

### new-3. `HeadlessStandIn.kill_all/1` fails when nothing started

What happened: see "What I ran into". It lists `<dir>/pids` with `File.ls!/1`, and `SessionsSetup`
runs it on exit for every test.

What the design should change: nothing in the design; `caf_test` should list with `File.ls/1`
and treat a missing directory as empty. I did not touch `caf_test`.

### new-4. A viewer's command waits behind a start in `Sessions`' mailbox

What happened: a start's hold and viewer steps run inside its call, so `viewer_argv/3` for
another session waits for them. Past its 5 s it answers `{:unknown, {:timeout, 5000}}`, and
`Recoveries` ends that state `failed{no_viewer_command, …}` with nothing opened. No test drives
that branch: it would cost the 5 s wait.

What the design should change: if a lost viewer must not wait for a start, `Sessions` could
answer the command from a read of its table (anyone may read it) with its own programs, outside
the process. Decide it if a start's steps prove slow in a real host.

### new-5. The `Tmux` contract does not say what a pane runs

What happened: see "What I ran into". A test of what a viewer ran cannot ask the contract, so it
reads tmux itself.

What the design should change: add the pane's start command to `pane_info`, or say that tests
of viewers read it from their own server.
