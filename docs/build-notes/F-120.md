# F-120: R2, `Reader` on `caf_store`, one `Registry` and one `Transcripts` per host

The remodel's second unit (`docs/design.md`, "Order of the first units", R2; F-115's 1e and
"Repeated code"). No behavior changes apart from the per-host start: the readers' tables and
cues are as they were.

## What was built

1. **`CodingAgentFramework.Reader`**, a pure module in `caf_store` beside `Store`. It starts no
   process and owns no table.
   - The loop: `call/4` (a call whose `noproc`, timeout or exit is refused or unknown, with the
     reader's own word for a missing process), `loop/1` (the `notify` and `interval` options,
     and the first tick), `tick/2`, `diff/2` (the puts and deletes from what was written to what
     was read) and `cue/4` (a cue after a change, a scope's first read, or when asked).
   - The table, from the reader's `meta/0`: `open/2`, `read_row/3`, `last_read/3`, `rows/3`,
     `select/3`, `rows_by_id/4`, and `write/3`, which writes the changes and reads rows of one or
     more scopes in one transaction and answers each scope's ids and whether it was its first
     read.
   - A `Tracker` source from the same metadata: `describe/2` and `source_read/4` (rows by id or
     all, within the source's scope, through an optional view; a reads row with a newer
     `failed_at` is unknown).
2. **The four readers on it.** `Registry.Table`, `Usage.Table`, `Transcripts.Table` and
   `TmuxSampler.Table` each keep their schema and give `meta/0`; their `open`, `rows`,
   `last_read`, `rows_by_id` and `write` are one-line calls of `Reader`, and their own `query`,
   `open`, upsert and reads-row code is gone. `Registry`, `Usage`, `Transcripts` and
   `TmuxSampler` use `Reader`'s call, loop, tick, diff and cue. The four apps declare
   `caf_store` in place of `exqlite`.
3. **One `Registry` per host**, over every account (`accounts:`, each name to its config
   directory). One shell command reads every account's `sessions/` (a marker per account, then
   the listing and the files as before), one `ps` checks every pid, and one transaction writes
   every account's rows and reads row. A failed shell writes nothing and is unknown, as before.
   It cues per account, `registry:<host>:<account>`, as before. `rows/3` takes the account.
4. **One `Transcripts` per host**, over every account (`accounts:`). Its folds are keyed by
   `{account, session_id}`, so a session id a move copied into a second account is a second
   row. `read/3` takes `{account, session_id, path}`; `rows/3`, `session/4`, `contains/7` and
   `text/5` take the account. It cues per account as before. It takes `interval:`, the
   `Reader`'s, so it reads every known session on its own timer, as the design says ("Stream
   and Transcripts are read on an interval, as Registry is"); the example's ticker no longer
   reads it. A read records a read of each account it names, and of every account on `:known`.
5. **`Tracker.ReaderSource`** replaces `RegistrySource`, `TranscriptsSource`, `UsageSource` and
   `TmuxSamplerSource`: `{Tracker.ReaderSource, table: Registry.Table, db:, host:, account:}`.
   `caf_tracker` uses `caf_store` and no longer uses `caf_registry`, `caf_transcripts`,
   `caf_usage` or `caf_sampler` (three stay `only: :test`).
6. **Callers**: `Sessions` takes `registry:` (one, optional) in place of `registries:`;
   `Delegates` takes the host's `Transcripts`; `MCP` takes `transcripts: {Transcripts, pid}` or
   nil. The example starts `:registry` and `:transcripts` once and builds its sources from
   `ReaderSource`.
7. **Tests**: `ReaderTest` (two scopes in one write; a source's scope, view and failure; the
   cue rule; a missing reader) and `Reader`'s two doctests; a `Registry` over two accounts that
   finds a session moved from one to the other; a `Transcripts` over three accounts with one
   session id in two of them, and its interval. Existing tests changed only where the options
   or calls take an account.
8. The README's status and its apps chart, which now matches every app's `mix.exs` (checked by
   script: no edge only in the chart, none only in a `mix.exs`). After the rebase onto F-118
   the script found two edges F-118 added to `mix.exs` and not to the chart (`caf_registry`
   and `caf_jobs` use `caf_holder`); the chart has them now.

Rebased onto F-118 (R3): `Registry` checks liveness with `Holder.Process.liveness/3` in place
of `Registry.Liveness`, and F-118's new read of the session file at a session's end
(`Sessions.end_reading/2`) takes the one `Registry` and the row's account, as `confirm/3` does.

## What I ran into

- `mix test` inside one app's directory refuses to run (an `exqlite` lock and a `stream_data`
  `only:` mismatch with `caf_test`); `MIX_ENV=test mix do --app caf_store test` at the root
  runs one app.
- The `devenv test` run printed `erl_child_setup: failed with error 32 on line 284` during
  `gate-test` (error 32 is a broken pipe, likely a port whose reader had already exited). No
  test failed. Each of the three `gate-test` runs after it printed it once too, and each passed;
  I did not find which test's port it is.
- The four tables are not one shape: `Usage` keeps one reads row per instance (`one = 1`) and
  keys its rows by account alone, the sampler's reads row records a failure and may have no
  `read_at`, and `Transcripts` stores a term in a blob. `meta/0` carries each difference as data
  (`filter:`, `failed:`, `dump:`, `load:`), so `Reader` names none of them. See new-3.

## Findings

### new-1. R2 is past the 500-line aim, as R1 was

What happened: the unit is about 2,000 changed lines, four times the aim and twice F-115's
estimate.
Why: the move alone (four tables, four loops, four sources) is close to the estimate, but one
`Registry` and one `Transcripts` per host change their call shapes (an account on each call),
and so `Sessions`, `Delegates`, `MCP`, the example and their tests.
What I did: kept it one unit and kept the move mechanical. Splitting the per-host start into a
second unit would have changed the same functions twice.
What the design should change: as F-117's new-1 said, an R-unit that moves several parts could
state up front that it runs past 500, or count a mechanical move's deletions apart.

### new-2. The writers' `Tracker` sources are still five modules

What happened: `SessionsSource`, `IntakeSource`, `RecoveriesSource`, `DelegatesSource` and
`StreamSource` repeat the same open, describe and filter-by-scope as the readers' sources did;
only the readers' four are made from metadata.
Why: the design names "a `Tracker` source made from the reader's table metadata"; the writers'
tables have no reads row (their `read_at` is the time of the read) and each loads its rows its
own way.
What I did: nothing; the writers' sources are unchanged.
What the design should change: when R9 and R10 rewrite those tables, give each writer's table a
`meta/0` with a "read now" reads rule, so `ReaderSource` (renamed `TableSource`) covers them too.

### new-3. `Usage`'s table is keyed by account alone

What happened: `Registry` and `Transcripts` key rows by host and account; `Usage` keys them by
account only, with one reads row per instance, so its metadata needs `filter:` beside `scope:`.
Why: `Usage` was built one per instance, reading files in the framework home.
What I did: kept its table, as the brief asks.
What the design should change: if `Usage` reads per host (an account's status line on another
host), key its rows by host and account like the others, and `filter:` goes.

### new-4. A failed transcript read names a session id without its account

What happened: `Transcripts.read/3` answers `failed: [{session_id, reason}]`. With one
`Transcripts` over every account, a session id a move copied is in two accounts, so a failure
does not say which.
Why: the shape was kept so `Delegates` and the tests read it unchanged.
What I did: nothing.
What the design should change: name the failure `{account, session_id, reason}` when a unit
next changes `Transcripts`' callers (R7 or R12).
