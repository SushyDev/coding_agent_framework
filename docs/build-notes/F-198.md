# F-198: any numbered menu on a main session's screen is a prompt; a dim suggestion is never input

A main session sat for hours on a Claude Code menu no rule knew ("Teach auto mode about your
environment?"), and no person saw it. Its input line held a prompt suggestion drawn dim, which
the screen read as typed text. This unit reads any numbered menu as a dialog of kind `menu`,
shows it in the one inbox as a `dialog` prompt with its options and `esc`, with no default and
no deadline, presses a person's answer with the marker read back before Enter, and reads a dim
run on the input line as no text. No test or step of it started the real Claude Code.

## What was built

- **The model first** (`model/tla/Menu.tla`, new). A menu drawn on a running screen, the pane
  read into the row's menu, a person's answer by a label or `esc` marked `pressing` before its
  press in a task; the press checked (the pane shows that menu, or nothing goes), the keys that
  move the marker, which land or not, the read-back (Enter only with the marker on the label),
  Escape for `esc`, Enter or Escape that lands or not; a person at the viewer who moves the
  marker or answers first; a restart that makes a press under way `unknown`. A menu is one menu
  by its content, as the code reads it. Invariants `OnlyAsked` (no default: every key that
  answers a menu comes from a person's answer), `OnNamed` (a press lands only on the menu it
  names, and Enter confirms only the label answered), `AtMostOnce` (each draw pressed at most
  once); liveness `LeavesWhenGone` (the row's menu goes once the pane shows none) and
  `MenuShown`. Five breaks, each failing its property: `Default` (`OnlyAsked`), `Unchecked` and
  `NoReadBack` (`OnNamed`), `RetryUnknown` (`AtMostOnce`), `KeepGone` (`LeavesWhenGone`).
- **The reading** (`Screen`, item 1). After the dialogs a rule names (which keep their rules)
  and before the box, a menu no rule names: the last line that starts with the release's menu
  footer (`Reading`'s new `menu: %{footer: "Enter to confirm · Esc to cancel"}`), with only
  blank lines under it before the box's own upper rule (the rule or named rule above the last
  rule) or the screen's end, so a capture of a menu printed in the agent's output, with its
  rules, is not one (as an agent that reads this brief would print), and the region under
  the rule above it: its first line the `title`, the lines under it `detail`, then two or more
  numbered options in a row, numbered from 1, at one indent, one marked. Read as `%{state:
  :dialog, kind: :menu, title, detail, options, selected}`. With the footer and anything else in
  that place (one option, a gap, an option out of order, two marks, a line under the options)
  the screen is unrecognized, never read past to the box. `option_keys/2` works on it as on any
  dialog. The usage limit's menu under a rule of `─` (no longer its own rule) now reads as a
  `menu`, not unrecognized; its test says so.
- **The dim suggestion** (item 3). `Screen` keeps each line's escapes beside its plain text;
  the box's line drops every run drawn dim (SGR 2 up to SGR 0, an empty SGR or 22; a color's
  own parameters, `38;2;…` among them, are not read as dim) before it is read. A box holding
  only a suggestion is `:empty`; `ye` typed before a dim `s, run …` is `{:text, "ye"}`. Dim
  runs elsewhere are kept: the exit's two lines are drawn dim. `Tmux.capture/3` now runs
  `capture-pane -p -e`, so the `Inlet`'s reads carry the colors. The `@doc` says only the screen
  sees a suggestion, and that typed input comes from `UserPromptSubmit` (F-194).
- **The fixtures**: `menu` (the marker on 1) and `menu-down` (on 2), each `.txt` and `.ansi`;
  `suggestion.ansi` (an empty box) and `suggestion.txt`, state `suggestion-plain` (without
  colors the same line reads as text). All four built from the brief's capture (new-1).
- **The row** (`Sessions`, `Sessions.Menu`, new). A `menu` column on the agent row. With
  `inlet:`, each `running` interactive row's pane is read every `look:` ms (5 s by default), in
  a task, one read per name at a time, none while a call or a press is under way for it. A menu
  read becomes the row's field (`start`, `at` the read's wall-clock ms and the prompt's key,
  `title`, `detail`, `options`, `selected`); the marker moved is the same menu; another menu, or
  one read after the last was sent, is a new one; a screen with no menu takes it away. Every
  change is written with the row's cue. `Agents.menu/1` reads it for a `running` row of the same
  start.
- **The answer** (`Sessions.answer_menu/5`). Checked against the row (that read's menu,
  unmarked, a choice it offers), an act in `Acts` (`answer_menu`, actor the person, state the
  start and `at`), marked `pressing`, then the `Inlet`'s press in a task: `Inlet.choose/5` now
  takes `{:menu, title, options}` (the pane must show that menu) and `:esc` (Escape, checked
  shown, then left). Sent or unknown stays marked; a refusal takes the mark back; the pane is
  read again at once. A restart makes a `pressing` press `unknown` and settles its act unknown.
- **The prompt** (`Prompts`, item 2). A row's menu is a prompt of kind `dialog`, id
  `dialog:<agent>:<at>:menu`, text its title and detail, options its labels and `esc`, no
  deadline; `open`, `answering` while pressing, `unknown`, and gone once sent or once the field
  goes. `answer/4` hands it to `Sessions.answer_menu/5`; a menu answered, gone or another is
  `{:refused, :settled}`.
- **The stand-in**: `ScreenStandIn` draws the menu (`--screen menu`, or `menu: true`), moves its
  marker on Down and Up, and writes the option answered or `esc` (`menu_answer/1`).
- Docs: the design's Screen paragraph of "Headless delegates" (the main session's screen), the
  parts' table, "Prompts" (the kinds' table and "Built so far") and "The model"; the README's
  list; `Screen`, `Reading`, `Tmux`, `Inlet`, `Sessions`, `Agents`, `Prompts`.

## What I ran into

- **A racy test, tilted by this unit.** `SessionsTest`'s "F-64: a stop is done only when its
  socket has ended too" failed every time here and passed on `main`. Its `linger` wrapper also
  wraps the start's `claude --version`, so that run writes `exited` and holds the release read
  until its 5 s bound; the test's wait for `exited` then returns before any stop, and its clock
  advance races the stop's call to `Sessions`. With the stop taken first the deadline passes;
  with the advance first it never does. The three queries a confirmed start now runs
  (`look_later/1`) were enough to lose the race. Fixed in the test: `--version` goes straight to
  the stand-in, so `exited` is the stop's, and the start no longer waits 5 s.
- `caf.deps` found the inbox's test naming `Tmux` (a key at the viewer): `caf_tmux` is now
  `only: :test` there.

## Findings

### new-1. The fixtures are rebuilt from the brief's capture, not captured

What happened: the brief quotes a `capture-pane -p` with blank lines dropped and the input line
from `capture-pane -e`; no capture-screen run made them. Why: the menu shows when Claude Code
decides, so the capture script cannot reach it on demand. What I did: built `menu`, `menu-down`
and the `suggestion` pair from the quoted text, the session's name scrubbed to `capture-main`,
the rules 80 columns; the `.ansi` files carry only the input line's escapes; the manifest says
so. The reading is by shape, with blank lines allowed around each part, so the real blank lines
read the same (a test adds them). What the design should change: the next person who sees such
a menu saves `capture-pane -p` and `-e` of it whole, and it replaces these.

### new-2. Who reads a running main session's screen, and how often

What happened: the brief says a menu is a prompt and leaves the inbox when the screen no longer
shows it, but not who reads a running session's pane; nothing did (`Sessions` reads only a
start's, `Limits` only a limited row's). What I did: `Sessions`, the row's writer, reads each
running interactive row's pane every `look:` ms (5 s), one tmux capture per session, in a task.
What the design should change: confirm the interval, or cue the read from `Intake`'s events of
that session (a `Stop`, a `Notification`) beside a slower interval. A capture costs one tmux
command; ten main sessions are two a second.

### new-3. "Its title (the first line above the options)"

What happened: in the capture the line just above the options is the description, and the
menu's first line is the question. What I did: the title is the menu's first line under its
rule; the lines between it and the options are `detail`, and the prompt's text is both.

### new-4. A menu during a start is not yet a startup dialog

What happened: a menu no rule names that a start meets before its session file (an onboarding
menu on a new account, say) reads as `menu`, and `Sessions`' start reads only `trust` and
`imports`, so the row waits `starting`, then `unknown`, as before. What I did: nothing; the
brief names a running main session. What the design should change: the start's read takes
`menu` as a startup dialog (`Dialog.kinds/0` and one clause of `shown/3`), its prompt the same
`dialog` kind, if a start's menus should reach a person too.

### new-5. An unknown press of a menu has no clear

What happened: a press whose outcome is unknown, or cut by a restart, stays `unknown` in the
inbox until the screen no longer shows the menu; only a person at the viewer answers it. A
startup dialog's cut press has a person's clear (`clear_dialog/4`, F-144). What I did: no clear
for a menu. What the design should change: a clear like F-144's, read on the pane with the
marker unmoved, if unknown menus are common.

### new-6. Delivery into a main session while a menu shows

What happened: the typed transport refuses a menu (the box check reads `dialog`), but the
waiter's delivery at a turn's end does not read the screen. What Claude Code does with a turn
the waiter starts while a menu is drawn is not measured. What I did: nothing. What the design
should change: the next release check measures it; until then a main session's waiter may
deliver under a menu.

### new-7. This unit is over 500 changed lines

What happened: about 1,300 changed lines apart from the fixtures: the spec and its
configurations (340), `Screen` and its tests (250), `Sessions` with its new module and test
(390), `Inlet`, `Prompts`, the stand-in, the docs. Why: the brief's four items cross the model,
the reading, the row's writer, the press and the inbox. What I did: kept each part apart in the
diff.
