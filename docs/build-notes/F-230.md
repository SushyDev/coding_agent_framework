# F-230: Claude Code's own question reaches a person until B10 intercepts it

## What was built

The 2.1.322 reading takes Claude Code's own question dialog (`AskUserQuestion`) as a menu
(F-198, `Menu.tla`):
- **Footer:** "Enter to select · ↑/↓ to navigate · Esc to cancel" joins the release's menu
  footers. Drawn in the box's place, with the box's named rule under it, as F-228 allowed.
- **Shape** (`menu: %{ask: %{header, free_text}}` in the reading): under the dialog's rule, one
  header line, `☐ <header>`; the question; numbered options, each with any description lines
  indented past its number; a rule inside the dialog; the options after that rule. Once the
  header is there, any other shape is unrecognized. It never falls back to the generic menu,
  which would have read only the option under the inner rule.
- **Reading:** `title` is the question, `options` the labels, `detail` one line per described
  option (`"Yes: Continue the session."`), and `numbers` each option's number as drawn.
  The header is left out: the question already says it.
- **Not read:** a header line with more than one `☐`, a `✔` or arrows (a form of several
  questions, one tab at a time), or labels that start with `[` (a question that takes more than
  one answer, drawn with a box before each label). Pressing an option there moves to the next
  tab or toggles a box. It does not close the dialog, so no single press answers it.
- **Keys:** `Screen.option_keys/2` counts by `numbers` when a reading has them, so a press
  counts the rows the marker crosses, including the one left out.

The inbox shows it as any menu: the question and the labels, plus `esc`. The press goes through
`Inlet.choose/5` as F-198 built it: the marker moves, is read back on the option, then Enter.

### "Type something." and "Chat about this"

- **"Type something." is left out.** Enter on it does not close the dialog: it opens a text
  field in the same dialog. A press would leave the dialog shown, and `Inlet` would report the
  press `{:unknown, {:still_shown, _}}`, never a clean answer. Typing into that field is a
  typed write, which a menu answer is not. A person who wants their own words picks "Chat about
  this" or `esc`, then sends a message. Its number is still kept, since the marker crosses it,
  and a marker on it reads as `selected: "Type something."`. Pressing it is refused as
  `{:no_option, "Type something."}`.
- **"Chat about this" is an option a person may pick.** Enter on it closes the dialog and gives
  the turn back to the box, so a press answers it. That is the person's way to say "neither,
  let's talk".

### Fixture and tests

`ask-question.{txt,ansi}` is a **stand-in drawn from the screen F-223's suite printed** when it
failed (2.1.322, 200 columns). It is not a capture. `bin/capture-screen` needs a person at a
logged-in account to bring each state to the screen, and none was at hand. The rules are 200
columns, and the name is scrubbed to `capture-main`. The screen it was drawn from showed no
escapes, so the `.ansi` holds none. A real capture should replace it the next time
`bin/capture-screen` runs. Of all this unit's fixtures, this one is the one most worth
recapturing (new-1).

- `ScreenTest`: the fixture reads as its menu at its own width and at 80 and 400 columns. A
  marker on "Type something." still reads. Each shape it must not take is unrecognized (a form
  of several questions, a multi-answer question, numbers out of order, a description not
  indented, no question, nothing after the inner rule). The keys count the option left out.
- `ScreenStandIn` gains `--screen ask`: the fixture with the marker on each of its four
  options, its rules redrawn at the stand-in's width. An `InletTest` presses "Chat about this"
  across "Type something." (three Downs, then Enter; the stand-in records `4`) and is refused
  "Type something." with no key sent.

No model changed. `Menu.tla` already models a menu's prompt and its press. This is a screen's
reading, and its options are a subset of what is drawn.

## What was measured

Nothing live. The screen is the one the brief quotes from F-223's failure. Two things were not
measured on a real 2.1.322 dialog: whether the marker visits "Type something." on Down, as
assumed here, and whether Enter on "Chat about this" closes the dialog. If either is wrong,
the press comes back unknown, `{:not_selected, _}` or `{:still_shown, _}`, never as a wrong
answer, because `Inlet` reads the marker back before Enter and checks that the dialog left.

## What I ran into

The first `InletTest` run read the stand-in's pane as unrecognized. The fixture's rules are
200 columns, wider than the stand-in's pane, so they wrapped. The stand-in now redraws them at
its own width, as `Screen` reads any width.

The first of the three `gate-test` runs failed `SessionsDialogTest`'s "a press runs in a task,
and each answer is an act in Acts". ExUnit's 60 s timeout fired while `Sessions.start` was still
in its trust and imports dialogs. That start's own call may wait longer than 60 s. In that run
`caf_sessions` took 71 s, against about 28 s in the others, so the VM was loaded. That path
never meets a question dialog or the stand-in's `ask` screen. The file passed 8 of 8 alone, and
the next five `gate-test` runs passed with no failures.

## Findings

### new-1. The question's two unmeasured keys want a capture

What happened: the reading assumes Down crosses "Type something." and Enter on "Chat about
this" closes the dialog. Neither was seen on a real session. Why: the only screen was a test's
failure output. What I did: built the press so that a wrong assumption comes back as an unknown
press, and drew the fixture as a stand-in. What the design should change: `bin/capture-screen`
could gain an `ask-question` state (a prompt that makes the session call `AskUserQuestion`),
with the marker moved by one Down to "Type something." and by two. A person running it would
then settle both assumptions.

### new-2. A form of several questions still waits unseen

What happened: `AskUserQuestion` with more than one question, or a question that takes more
than one answer, draws a tabbed form, which this reading leaves unrecognized. Why: one press
does not answer it, so it does not fit `Menu.tla`. What I did: left it unread, tested as such.
What the design should change: B10 intercepts the call before any dialog is drawn. Until then,
the design could say that such a form is unrecognized and leaves the agent idle, or a model
could cover a form answered field by field.
