# F-103: what the embedding app needs from the parts

F-102's findings new-1, new-2, new-4 and new-5, built: the parts offer what `caf_example` could
not wire, and the app wires it.

## What was built

1. **Main sessions as roots.** `Example.Config` takes `mains`, each project's main session
   (project to name). The app's `Grants` tree is those entries, `parent: nil`, then `Delegates`'
   rows. `Grants` reads an entry with no parent as a main session (a root), as it reads a parent
   no entry names; `parent/2` of a root is `{:refused, :main_has_no_parent}`.
2. **A delegate's own MCP config.** `Delegates` takes `mcp:`, a function of the delegate's name
   that answers `{:ok, path}`. Each start and each resume calls it in the task that calls
   `Sessions`, just before the launch, and adds `mcp: path`; a refusal refuses the start (or
   fails the resume, as a refused resume does). With no `mcp:` nothing changes. `Sessions` now
   passes `mcp:` on to `ClaudeCLI` (it took only the other launch keys). The app gives
   `MCP.issue/2` on the current `MCP` process.
3. **A job's late end to its caller.**
   - `Mailbox.notify(mailbox, to, text, opts)`: stores a message from `framework` to `to`, an
     agent the tree holds (`Grants.may_use?/2`), delivered as any message. With `key:`, a
     second message under the same key is not stored (`{:ok, :stored_before}`), so the repeat
     of a late end after a crash is dropped. The key goes in `reply_to` as `key:<key>`, whose
     unique index already takes one row per value.
   - `MCP.caller(dir, instance, job)`: the agent whose `run` call made job
     `mcp-<instance>-<id>`, read from the call log file opened read-only.
   - The app's `on_late_end`: the caller, then `notify` with the end and "Nothing was fetched.",
     key `job:<id>`. A refusal (no such call, an unknown agent) is logged; anything else raises,
     so `Jobs` hands the end again at its next start.
4. **An owner's end.** `Example.Ends`, a process of the app's own, after the ticker. The
   `delegates:` cue reaches it with the row ids; it calls `Services.owner_ended/3` for each named
   delegate whose latest row is `refused` or `failed` (the rule `Services`' `ended` already
   uses). At its start it does so for every such delegate, since a cue sent while it was down is
   lost; `owner_ended/3` on an owner with no running service does nothing.

The stand-in for headless Claude Code now writes its arguments to `<dir>/argv/<session id>`
(`HeadlessStandIn.argv/2`), so a test reads what a delegate was launched with.

**Tests** (`example_test.exs`, each under its own home, server and ports):

- the main session, with no delegate, starts both delegates through `MCP`'s `start_delegate`;
  both show in `agents()`; each launch names the account's MCP config and then
  `<home>/parts/mcp/agents/<name>.json`, and that file's token is the delegate's (`MCP.who/2`);
  the restart part of F-102's test is kept;
- a stand-in job: `MCP`'s log holds a `run` call by `app-main` answered `{:unknown, %{job:
  "mcp-t-1", reason: :dropped}}`, and `Jobs`' table owes that job's end (exit 3). The app's start
  hands it on: one message from `framework` to `app-main` names the job and the end, the row is
  `told`, and a repeat under the same key is not stored;
- a delegate whose brief's turn waits on a permission starts two services through `MCP`, one
  with `keep`; it is killed, resumed, and killed again, so it is `failed`; then the plain
  service is `ended` and the kept one runs on, owned by `app-main`.

## What I ran into

- `Jobs` hands the late ends it owes in its `handle_continue` at start, and `MCP` starts after
  it (`MCP` is given `Jobs`). A caller asked of the `MCP` process would be missing then, so
  `MCP.caller/3` reads the call log from the file. It opens the file read-only: `MCP.Table.open`
  would mark every live call `cut`. The test's stand-in job is handed on at that start, so it
  covers this order.
- `Mailbox` comes before `Jobs`, so `notify` has a process to call at that moment.
- Ending a delegate takes two kills in a test: the only ends a delegate has today are a refused
  start and `failed`.

## Findings

### new-1. A late end that cannot be stored restarts `Jobs` and every part after it

What happened: `Jobs` keeps a late end owed only when `on_late_end` raises, and then hands it
again only at its next start. The app raises when `Mailbox` does not answer, which crashes
`Jobs`, and the `:rest_for_one` tree restarts `Jobs`, `Services`, `MCP`, its endpoint, the ticker
and `Ends` with it. Why: the function's return is not read. What I did: the app raises on an
unknown answer and logs a refusal. What the design should change: let `on_late_end` answer
`:ok` or `{:unknown, reason}`, and keep the row `owed` on the second, for the next cue to hand
again; no crash is needed to keep an end.

### new-2. A delegate stopped after its report never ends its services

What happened: `stop` ends a delegate's process once its report is answered, through
`Sessions`; `Delegates`' row stays `finished` and is not written, so no `delegates:` cue shows
the end and `Services.owner_ended/3` is not called. The same holds for a finished delegate whose
process exits on its own. Why: a delegate's end after its report is not built. What I did:
`Ends` and `Services`' `ended` read `refused` and `failed` only. What the design should change:
when that end is built, `Delegates` writes it to its row (an `ended` status, say), so the cue
shows it and both rules read it.

### new-3. `reply_to` holds two kinds of value

What happened: `notify`'s key is stored in `reply_to` as `key:<key>`, beside the uuids of
answered messages, to reuse its unique index. A uuid never starts with `key:`, so they do not
meet, but a reader of `status/3` sees a `reply_to` that is not a message. What the design should
change: if a second kind of keyed message comes, give the key a column of its own.

### new-4. A framework message into a delegate gets the delegate's reply

What happened: `notify` to a delegate is delivered as any message, so its turn's `result` is
stored as the delegate's reply to its main session, as for a message from that main session.
What I did: nothing; today a late end goes to a delegate only for a job it ran itself, and the
reply reaching its parent does no harm. What the design should change: say whether a reply to a
`framework` message goes to the parent, or nowhere.
