# F-201: what an app's first run on the tree found

An app pinned the tree with `agents: false`, `agent_rows/1`, `tool_hooks: {module, opts}` and
F-197's replacement (which answered in 8 to 9 ms), and found five things. Each was decided in
the brief; this unit builds them.

## What was built

- **The tool event's `cwd`** (item 1). `Intake`'s `tool_event` (what `pre_tool_use/3` and
  `post_tool_use/3` get) and `stop_event` (what `stop/3` gets) carry `cwd`, the directory
  Claude Code posted with the hook, so an app's rewrite of a command that depends on where it
  runs can apply. It is taken as posted and never guessed: a post without one, or with one
  that is not text, carries `nil`. Both typedocs and `ToolHooks`' doc say so. A test per hook.
- **An agentless config needs only what it reads** (item 2). With `agents: false`,
  `Config.new/1` requires only `home`, `instance`, `programs` and `env`, whose `path` `Jobs`
  reads (`{:bad, :env}` without it). `accounts`, `ports`, `claude` and `user` are optional
  there, on macOS too, and named in `Config`'s doc and the design's config table; `accounts`
  defaults to `[]`, `ports` and `claude` to `nil`. A `user` given is still checked. Where agents
  run, each of the three stays required, now by `new/1`'s own check rather than
  `@enforce_keys`. The tree skips the tool home for such a config: no `ToolHome.prepare`, so no
  `gh`, `ssh` or `ssh-keygen` is needed, and its jobs run with `env`'s `path` alone. The
  surface test's agentless tree now starts from that minimal config with those three programs
  removed, and checks that no `gh/`, `git/` or `ssh/` was made in the home.
- **`agent_rows` by the instance's name** (item 3). The tree's `:names` child, the instance's
  `Registry`, keeps the config the tree started with in its meta beside `tree`, and
  `agent_rows(name)` reads it there and answers as `agent_rows(config)` does, or `{:refused,
  :no_instance}` when no tree of that name runs. The data check of `tool_hooks` and
  `extensions` options now refuses a struct, naming it: `{:not_data, module, {:struct,
  struct}}` (the config among them; it was a `Protocol.UndefinedError` raised from
  `Enum.all?` over the struct). A function, pid, port or reference stays `{:not_data,
  module}`. `ToolHooks`' doc says why: the hook names the instance instead.
- **A non-JSON answer is out of shape** (item 4, F-197's new-2). Each key of an answer is
  checked before it is encoded: `updated_input` must encode as JSON (`["bad_answer",
  "updated_input"]`), a context must be UTF-8 (`["bad_answer", "additional_context"]`, or
  `"context"` for `PostToolUse`'s), a deny's reason too (`["bad_answer", "reason"]`), and a
  `Stop` block's reason (`["bad_answer", "block"]`). Each is a pass whose row's `problem` names
  it. A pause whose block reason is not UTF-8 is refused `{:bad_pause, how}`, as any pause out
  of shape is. Behind the checks, `tool_answer/2` rescues whatever raises while an answer is
  made (`["bad_answer", "not_json"]`), so the `Intake`, which every hold shares, never crashes
  on an app's answer. A `PermissionRequest`'s answer already answered its caller `{:refused,
  {:bad_decision, …}}`; it is unchanged.
- **`post_tool_use/3` may answer `{:context, text}`** (item 5), sent as `PostToolUse`'s
  `hookSpecificOutput.additionalContext` under `PreToolUse`'s bound of 10,000 characters, and
  `{:replace, response, context: text}` sends both. A context too long, not text, or a key
  other than `context:` is a pass whose row names it, as `PreToolUse`'s are. The `@doc`s
  (`Intake`, `ToolHooks`) and the design's "A held `PostToolUse`" carry the main session's
  measurement.

No protocol changed: `cwd` is a field of the event, and a context is one more decision body of
the `post_tool` kind, which `Intake.tla`'s `HT` already models as a decision or a pass. No spec
was touched.

## What was measured

The main session measured item 5 on Claude Code 2.1.322, headless, a `Bash` call and the model
asked to quote any note with the result: `hookSpecificOutput.additionalContext` on
`PostToolUse` is read by the model on that call, from a command hook and from an `http` hook
alike, shown as "PostToolUse:Bash hook additional context: <text>"; the tool result itself is
unchanged. Nothing else here needed a measurement: Elixir 1.20.5's `JSON.encode!` raises
`ErlangError` on bytes that are not UTF-8, `Protocol.UndefinedError` on a tuple, a pid or a
struct, and `FunctionClauseError` on an improper list, which is why the last guard rescues any
exception rather than a list of them.

## What I ran into

- `@enforce_keys` made `struct!/2` raise for a config without `ports` or `claude`, so the agent
  keys moved to a check of their own in `new/1`, which answers `{:bad, key}` as before.
- The surface test's agentless tree used the agent tree's whole config; it now uses the
  minimal one, which covers F-195's case as well.

## Findings

### new-1. An agentless tree's jobs get no tool state, and an app cannot give them any

What happened: skipping `ToolHome.prepare` (item 2) also drops `env`'s `:tools` from an
agentless tree's workstation jobs, which F-195's tree passed (`GH_CONFIG_DIR`, `GIT_SSH_COMMAND`
and the rest, pointing into the home). The tree builds a workstation job's environment from
`env.tools` and `env.path` alone, so an app has no way to give its jobs any other variable.
Why: the tool home is the agents' state; an agentless app's jobs (its gates, its landings) run
with whatever state the app itself keeps. What I did: the jobs of an agentless tree run with
`PATH` only, as the brief's "skip `ToolHome.prepare`" implies, and `Config`'s doc says so. What
the design should change: decide where an app's own job environment comes from, for instance a
`job_env` the config names (or `hosts`' `env` for the workstation too), so a landing on an
agentless tree can reach its credentials without a tool home.

### new-2. A tree that runs agents still crashes at its start on an `env` without `path`

What happened: `Config.new/1` checks `env.path` only for `agents: false` (item 2). A tree that
runs agents reads `c.env.path` in its supervisor's `init`, so a config whose `env` has no
`path` passes `new/1` and the start fails with a `KeyError`, not an explicit refusal. Why: the
brief scoped the check to the agentless config, and every doctest of `Config` builds an agent
config with `env: %{}`. What I did: nothing beyond the agentless check. What the design should
change: `new/1` refuses `{:bad, :env}` without a `path` for every tree, and the doctests give
one.
