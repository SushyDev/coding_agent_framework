# F-200: a delegate's effort, and a delegate without Claude Code's git instructions

An app that runs builders as delegates decided two things: a delegate's start names how hard
its model thinks, as `claude --effort` takes it, and a delegate starts without Claude Code's
built-in git instructions, which a main session keeps. This unit builds both.

## What was built

- **`effort` on a delegate's start.** Optional, one of `low`, `medium`, `high`, `xhigh`, `max`
  (`ClaudeCLI.efforts/0` is the one list). `Delegates.start_delegate/7` takes `effort:`, the MCP
  tools `start_delegate` and `run_delegate` take `effort` (the input schema has it, not
  required), and `Operator.start_delegate/7` and the example console take `effort:`. Any other
  value, a number or a list included, is refused `{:refused, {:effort, value}}` in
  `Delegates`' `with`, right after the options check and before any row, so a refusal writes no
  row, no brief, no agent and no process. A JSON `null` is no effort.
- **The row keeps it.** `delegates` has a new column `effort TEXT` (`Delegates.Table`'s
  `@added`, so a file made before it gains it when it opens; `@create` and `@columns` have it).
  `Delegates.launch/4` adds `effort: <row's>` when the row has one, at every launch: the start's,
  a resume after a kill, `go_on`'s and `Delegates.launch/2`, which `Mover` resumes a moved
  delegate with. With none there is no flag.
- **The launch line.** `ClaudeCLI.session/3` and `headless/2` take `:effort` (nil is none, any
  value outside the list is `{:bad, :effort}`) and put `--effort <level>` right after the
  model (and the name). `Sessions` passes `:effort` to both, for a headless and an interactive
  delegate.
- **`includeGitInstructions: false` in every delegate's settings.** `Accounts.overlay/5` takes
  `defaults` (a map, none by default) that sit under the account's role file and under the
  agent's own settings. `Sessions.own/7` always writes a delegate's overlay (the agent's own
  settings, or none, and the hook of an interactive one) with
  `%{"includeGitInstructions" => false}` as the defaults, and none for a main session. An app
  that wants the git instructions back sets `"includeGitInstructions" => true` in the delegate's
  `options` settings (the launch options an app passes today), which wins. `Options` does not
  reserve the key.
- **The design** says both: "What `Delegates` holds", item 11 of "Order of the first units", and
  the `delegate` row of the agent's surface.
- **The stand-in** `ScreenStandIn` records its arguments in `<dir>/argv/<pid>` (`argvs/1`), as
  `HeadlessStandIn` does, so a test reads an interactive delegate's launch line.

## What was measured

- `claude --help` on the pinned 2.1.322: `--effort <level>  Effort level for the current
  session (low, medium, high, xhigh, max)`. The list is that.
- The pinned binary's settings schema (read from the release's own strings, not by running it):
  `includeGitInstructions: boolean().optional()`, described as "Include built-in commit and PR
  workflow instructions in Claude's system prompt (default: true)". So an absent key means the
  instructions stay, which is why a main session's settings say nothing of it, and a delegate's
  must say false.
- Not measured: a real 2.1.322 session started with the setting false, to see its system prompt
  lack the instructions. No test starts the real Claude Code, and the unit's tests read the
  line and the file a delegate gets. A check against the pinned release should read a delegate's
  first request (new-3).

## What I ran into

- An interactive delegate does not run in the delegate role. `Delegates.launch/4` gives it role
  `:parent` (the terminal interface, with `--remote-control` and `parent.settings.json`) and
  kind `:delegate`. The account's `delegate.settings.json`, the one place that reads like "a
  delegate's settings", would have covered a headless delegate only. See new-1.
- A delegate with no options had no overlay file before: it ran with the account's
  `delegate.settings.json` itself. It now has `agents/<name>.settings.json` too.
  `SessionsOptionsTest`'s existing delegate asserts only the permission rules, and passed
  unchanged.
- `Accounts.overlay/4` became `overlay/5` with a default argument, which needs a function head
  once the fallback clause is kept; callers of `overlay/4` are unchanged.
- The stand-in records `argv` without the program's path, so its first element is `-p` for a
  headless delegate and `--model` for an interactive one.

## Findings

### new-1. The delegate's default lives in the per-delegate overlay, since an interactive delegate runs in the main role

**What happened.** The brief's "the part that writes a delegate's settings file" reads as
`Accounts.prepare/3`'s `delegate.settings.json`. An interactive delegate is launched as role
`:parent`, so it reads `parent.settings.json`, with `remoteControlAtStartup` true, and gets
`--remote-control` too.

**Why.** `Delegates` runs an interactive delegate as a main session does, on purpose
("Delegates": the terminal interface), and `ClaudeCLI` takes its settings file by role.

**What I did.** Put the default where the kind is known, in `Sessions.own/7`'s overlay for a
launch of kind `delegate`, whatever its role. Both kinds of delegate get it; a main session's
launch is as it was. One mechanism, and a test for each of the two.

**What the design should change.** Nothing now: "What `Delegates` holds" says it. A later
decision may want an interactive delegate to have its own role (a `delegate.settings.json` with
`remoteControlAtStartup` true, say), which would let the account's file carry such defaults.

### new-2. A default under the account's file means an account-level `includeGitInstructions` wins over the framework's

**What happened.** `Accounts.overlay/5`'s `defaults` sit under the account's file, so a
`includeGitInstructions: true` an app writes into its account settings (`Accounts.prepare/3`'s
`settings`, which every role of that account reads) reaches every delegate of that account,
and the delegate's own `options` settings still win over it.

**Why.** A default is what nobody said; the account's file is somebody saying it. The brief
asks that the delegate's own settings win, and says nothing of the account's.

**What I did.** Kept that layering and wrote it in `overlay/5`'s doc. The other order (the
default over the account's) would make the account-level value silently useless.

**What the design should change.** Nothing, unless the operator wants the default to beat the
account's file, which is one line in `Sessions.own/7`.

### new-3. No check yet that a real session started with the setting leaves the git instructions out

**What happened.** The unit's tests read the settings file and the launch line a delegate gets,
and the pinned binary's schema has the key. Nothing starts the real Claude Code with it.

**Why.** No test starts the real Claude Code, by rule, and "Rules learned" asks a check against
each pinned release for what the framework relies on (a delegate's Remote Control off is one).

**What I did.** Nothing: a builder builds no mechanism a finding suggests.

**What the design should change.** Add `includeGitInstructions: false` and `--effort` to the
checks run against each pinned release: a headless delegate started with both, its first
request's system prompt read for the commit and PR workflow text, and the session's init event
read for the effort.

### new-4. The MCP schema names the levels in its description, not as an `enum`

**What happened.** `start_delegate`'s and `run_delegate`'s `effort` is `type: "string"` with the
five levels in its description.

**Why.** `caf_mcp` does not depend on `caf_cli`, where the list lives, and the tools reach
`Delegates` through the `{module, server}` the embedding app gives it. A copy of the list in
`caf_mcp` would drift; a new dependency just for it loosens a boundary. `Delegates` checks the
value, and the refusal names it.

**What I did.** The description, and a test that it names all five.

**What the design should change.** If clients should see the levels as an `enum`, `Delegates`
or the app can hand the tool its list (`efforts:` to `MCP.start_link/1`), which is a small
change in its own unit.

### new-5. A main session cannot name an effort

**What happened.** `start_main` takes `model` only, and `Mains`' row keeps no effort. The
`:effort` launch key works for a main session at `ClaudeCLI`'s level (the pure function takes it
for both roles), but nothing above gives it one.

**Why.** The brief names delegates only.

**What I did.** Nothing. `Sessions` keeps no effort on the agent row either, since `Delegates`
names it at each of a delegate's launches; any other part that resumes a delegate must take its
launch from `Delegates.launch/2`, as `Mover` does.

**What the design should change.** If a main session is to have an effort, `Mains`' row keeps it
as `Delegates`' does, and its resumes name it again.
