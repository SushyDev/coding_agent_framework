# F-287: a paste brackets its own text, so a newline never submits early

## Why

Since F-279, `mailbox_typed_test.exs:186` failed in every gate run and in some runs alone: a
5-line message's stand-in recorded only its first line as submitted. F-283's new-3 named a
likely cause. `tmux paste-buffer -p` adds bracketed paste's markers only when the pane has seen
its program turn the mode on (`ESC [?2004h`). The program runs under dtach, which keeps no
output, so a pane that attaches after the program printed that never sees it. The paste then
goes in unbracketed, and each newline submits.

## The cause, confirmed

The new `inlet_test.exs` test "a 5-line text arrives as one submit, whether or not the pane saw
bracketed paste on" starts the stand-in under `dtach -n`, as `Holder` starts a session, waits
for it to run, and only then opens a tmux pane that runs `dtach -a`. On `main`'s paste
(`paste-buffer -p -r -d`), with the stand-in as it was (the mode asked for once, at its start),
the paste was submitted as five lines, `"line 1"` to `"line 5"`. A pane that ran the stand-in
itself took the same text as one submit.

Why the mailbox test failed only some of the time: `Holder` starts dtach with `-n`, and the
session's pane attaches right after. Whether the stand-in prints `ESC [?2004h` before or after
that attach is a race, which a loaded host loses more often. Run alone on an idle host, the
mailbox test passed 3 of 3 on `main`'s paste even with the stand-in asking only once.

What a real Claude Code does: in production, on Claude Code 2.1.322 sessions that had outlived
restarts of the tree in dtach, three multi-line pastes (6, 12 and 23 newlines) each arrived
whole, as one user line with every newline. So a real Claude Code's pane does see the mode
turned on, which most likely means Claude Code asks for it again when it draws again (on the
resize an attach makes, F-272). Only the stand-in, which asked once at its start, split. This
was reported from production, not measured here; the `:real` test below is the measurement.

## What was built

- `Tmux.bracketed/1`: the text inside `ESC [200~` and `ESC [201~`. `Tmux.CLI`'s paste loads
  that into the write's own buffer, from stdin as before, and pastes it with
  `paste-buffer -S -r -d`: no `-p`, so tmux adds no second pair whatever the pane saw. `-S`
  is needed: by default tmux 3.8 writes a buffer's control characters out with vis(3), and the
  pane got the markers as the text `^[[200~` (seen in the contract test when tried without it).
  `paste_text/1`'s check is unchanged, so no text can hold an escape and end the bracket early.
- `Tmux.paste_max/0` is `Shell.input_max/0` less the 12 bytes of markers, 16 372, since the
  whole bracketed text goes to the load's stdin. The mailbox's own bound (8 000) is unchanged.
- `ScreenStandIn` asks for bracketed paste at its start and again at each draw a resize makes,
  as the real program appears to. Written with `paste_mode: :once`, it asks only at its start,
  the old behavior, so a test can have a pane that never saw the mode. It reads a paste by its
  markers either way; it never depended on the mode to read them.
- Tests: the contract test's paste now expects one pair of markers around the text on the real
  server, and the fake renders a paste the same way. The new inlet test pastes a 5-line text to
  three panes: one that ran the stand-in, one that attached under dtach later and saw the mode
  at the resize, and one that attached later to a `paste_mode: :once` stand-in and never saw
  it. Each takes one submit and shows an empty, idle box after. `mailbox_typed_test.exs:186`
  (now line 188) runs on a `paste_mode: :once` stand-in, so its 5-line row settles by its line
  through a pane that never saw the mode.
- `caf_real`'s `own_brackets_test.exs` (`:real`): pastes a 3-line text through `Tmux.CLI` into
  an idle real main session's pane, then Enter, and expects one user line in the transcript
  that holds the whole text and no escape. It is not run by the gates. Run it with
  `CAF_REAL_SETUP=<home> mix test.real apps/caf_real/test/own_brackets_test.exs` (as
  `docs/e2e.md` says for the others). It was not run in this unit.

The model: `Agent.tla` keeps a write's text abstract (a write's text is its number) and names
the load, the paste and the Enter. Bracketing changes the bytes of the text, not the steps or
who may load between them, so no spec changes.

## Measured

- With the fix, `mailbox_typed_test.exs` "a 300-character and a 5-line message…", on a
  `paste_mode: :once` stand-in, passed 10 of 10 alone. On the faithful stand-in it also passed
  10 of 10 alone.
- The new inlet test failed on `main`'s paste in its "never saw the mode" pane (five submits)
  and passed its other two; with the fix it passes all three.

- Gates, after `mix compile --force` in both environments: the first `devenv test` failed one
  test, `mains_test.exs:431` (end_main, timed out at 60 s at a load near 24 on 12 cores, other
  units' gates running beside it); it passed alone, and a second `devenv test` passed whole.
  `gate-test` passed three of three with no failure. `bin/check-model` passed. The names check
  finds nothing.

## Findings

### new-1. tmux writes a buffer's escapes out as text unless `-S`

What happened: with the markers in the buffer and `paste-buffer -r -d` as the brief named it,
the pane received `^[[200~…^[[201~`, and the stand-in took it as typed text. Why: tmux 3.8
sanitizes control characters in a paste with vis(3) by default; `-S` turns that off. What I
did: the paste is `paste-buffer -S -r -d`. The text's check keeps every control character but
newline and tab out of the text, so only the framework's two markers are passed raw. What the
design should change: nothing more; the design's paste line now names `-S`. The tmux version
the devenv pins matters here: a tmux without `-S` would need another way.

### new-2. The paste's bound lost the markers' 12 bytes

What happened: the bracketed text goes to the load's stdin whole, and stdin is bounded by
`Shell.input_max/0`. Why: the markers are 12 bytes. What I did: `paste_max/0` is 16 372. What
the design should change: nothing; the mailbox pastes at most 8 000 bytes.

### new-3. The stand-in asked for bracketed paste once, the real program apparently on each draw

What happened: the gates' only multi-line split came from the stand-in, not from a real
session. Why: it printed `ESC [?2004h` once at its start, and under dtach a pane attached after
that never saw it. What I did: it asks again at each resize draw, and `paste_mode: :once` keeps
the old behavior for the test that needs a pane that never saw the mode. What the design
should change: run `own_brackets_test.exs`, and capture whether 2.1.322 prints `ESC [?2004h`
on a resize draw, so the stand-in's behavior is measured rather than inferred.
