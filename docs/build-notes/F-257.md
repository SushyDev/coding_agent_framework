# F-257: a delegate's reply to a message delivered by the waiter is never lost

## What was built

On the live tree (Claude Code 2.1.322, interactive delegates, messages delivered by the Stop-hook
waiter), three of five replies to a parent's message were not stored as replies. Two were lost,
and one came to the parent as a "turn of its own" notice.

### The cause

Two readings were missing or wrong. Neither is an order of reads.

1. **No reader of an interactive delegate's reply existed.** `Mailbox` stores a reply from a
   headless delegate's `Stream` fold (`replies/2`), where each message's turn ends with a
   `result` that names it. An interactive delegate's turn writes no `result`, and no part read
   its reply from the transcript: `Delegates` read only the report (`Fold.reply_to/2`) and the
   turns of its own (`Fold.own_turns/2`). The model held the same gap: `Delivery.tla`'s
   `Answerable` takes only a headless addressee. So every message handed to an interactive
   delegate in an idle session was answered by nothing (messages 236 and 256).
2. **A message queued into a turn of its own made that turn read as its own.** A wake begins a
   turn while the last turn's waiter is still held. A message handed to that waiter joins the
   running turn as a `queued_command` attachment, which opens no turn. `own_turns/2` judged a
   turn by its opener alone, an unmarked `<task-notification>`, so the turn's reply, the answer
   to the message, was told as a turn of its own (message 231, and 285 on 2026-11-25).

Rows 232 and 249, the two replies that did arrive, could not come from either reading. They were
most likely messages the delegate sent itself; this was not checked against those rows.

### The fix

1. `Transcripts.Fold.turns/2` replaces `own_turns/2`. It returns every turn from the report's
   turn on, each with `marks` (the delivery uuids in its user lines and its queued texts),
   `own` (an unmarked `<task-notification>` opener and no mark in the turn), its last reply's
   `uuid` and `text`, and `closed`.
2. `Mailbox.answered/4` stores an interactive delegate's answer to a delivered message under the
   message's uuid: the turn's reply, or with its process gone in that turn and no reply, the
   notice. It builds the same rows `replies/2` builds (`answer_row/3`). It refuses a row that
   no turn answers (a brief, a word to go on, a notice, an answer), a row not yet settled
   delivered, and an unknown uuid.
3. `Delegates` reads the turns of an interactive delegate, running or finished
   (`interactive_turns/3`), behind F-261's cache: `s.own` keeps every turn `Fold.turns/2` read,
   and the transcript is read again only once `Transcripts.offset/4` has moved (`turns_read/4`).
   The session file is read (`turn_ended?/2`) only while the last turn is open and still holds a
   message to answer or a turn of its own to tell. Each ended turn answers each message whose
   mark is in it (`answer_turns/4`), the brief's and the word's marks aside. A turn of its own
   is told only when no mark is in it. The messages Mailbox settled are kept in memory (`answered`) only to
   spare Mailbox a repeat; the key in Mailbox keeps one answer per message across restarts.
4. `Transport.Waiter.marks/1` replaces `marked?/1`.
5. `Reply.tla` models a delegate's turns after its report: wakes, a message taken into an idle
   session or queued into a running turn, the turn's end, the process's end, and the framework's
   read at any moment. `Reply_Turns` checks OneAnswer, ReplyIsItsTurns, NotToldAsOwn,
   ReplyArrives and OwnTold. `Break_Reply_NoReply` (no reply read, as before) fails
   ReplyArrives, and `Break_Reply_OpenerOnly` (the opener alone, as before) fails NotToldAsOwn.

### Also looked at

- **`Interventions` and a person's typing.** It read every `UserPromptSubmit` prompt with no
  handed mark as `typed` by a person. A wake's turn has no mark, and the waiter's turn may carry
  none in its prompt, so both were recorded as a person's typing. This is the same reading as
  Fold's: a prompt that begins with `<task-notification>` is Claude Code's own turn. Fixed here,
  with two prompts added to its test. Which of the two 2.1.322 sends to the hook for a waiter's
  text was not measured.
- **`stop` on an idle delegate whose answer was lost.** By the code, `stop` does not wait on a
  reply. It needs the report delivered, no row open to the delegate (`Mailbox.open_to/3`), and
  then `Sessions.stop/3`'s idle session file with no row `sending`. A lost reply leaves no row
  open to the delegate: the message is `delivered`, and the reply would be a row to the parent.
  A 15 s timeout with no act means the call ended before its claim was written. The claim comes
  after `Delegates.fix_state/3`'s read of the state, a call into the `Delegates` process. That
  read waits behind whatever a cue is doing in that process. F-261 drains queued cues into one
  settle, which shortens that wait; that it caused the timeout was not shown.

## Findings

### new-1. A message queued into the report's turn gets the report's text as its reply

What happened: a message whose mark is in the report's turn (queued while the brief's turn ran)
is answered by that turn's reply, so the parent gets the report's text twice: once as the
report, once as the reply. A turn two messages went into answers both with its one reply. Why:
an interactive turn has one last reply, whatever went into it. A headless turn writes a result
per message. What I did: each message gets the turn's reply, so none is dropped (`Reply.tla`'s
ReplyArrives). The waiter holds only after a turn ends, so a message in the brief's turn needs a
typed write or a person's turn first. What the design should change: say whether a message that
joined the report's turn should get the report as its reply, or a notice that names the report.

### new-2. A running interactive delegate's report turn is still read at each cue

What happened: before the rebase, `interactive_turns/3` read an interactive delegate's
transcript and session file again at every cue. After the rebase onto F-261 these reads sit
behind its offset cache (see "The fix", 3), and F-261's test of 50 cues with zero
`Transcripts.text/5` reads passes unchanged. What remains is `settle_interactive/3`'s own read of
a running delegate's report turn (`turn_of/3`) at each cue, as on `main`. Why: that read is
F-261's and the report's, not this unit's. What I did: nothing. What the design should change:
put `settle_interactive/3`'s read behind the same offset, if cue time with several running
interactive delegates shows it matters.

### new-3. Messages to an interactive delegate before a resume are read from the word's mark

What happened: the turns are read from the report's turn, the word to go on's after a resume.
A message whose turn the first process's end cut, before the resume, is never read, so it gets
no notice. Why: `report_turn/3` reads from the mark that begins the report's turn. What I did:
nothing. The waiter holds only after a turn ends, so this needs a message after a brief's turn
with no report and then a kill. What the design should change: read the answers from the brief's
mark, and the turns of its own from the report's turn.

### new-4. `Interventions` keeps its own copy of `marks/1`

What happened: `Interventions.marks/1` and `Transport.Waiter.marks/1` are the same regular
expression. Why: they were written apart (F-194, here). What I did: nothing. What the design
should change: `Interventions` uses `Transport.Waiter.marks/1`, and its copy goes.
