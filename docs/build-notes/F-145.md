# F-145: two test races the gates found

The brief named two races: `MainsTest`'s commit into the checkout that found git's
`index.lock` held (F-142's new-5), and `JobsTest`'s cut fetch whose host side outlived the test
VM (F-141's new-9). Each was to be reproduced on purpose, its cause found, and fixed in the
test, or in the code it names if the framework does the same in real use.

## What was built

- **`Mains` reads the checkout with no lock.** `Mains.Checkout.git({:status, path})` now runs
  `git --no-optional-locks -C path status …`. A plain `git status` refreshes the index's cached
  file times and writes them back under `.git/index.lock`, an optional lock. So each of
  `Mains`' reads (every `interval:` ms, 5 s by default) held the lock for a moment, and a git
  command that writes the index in the checkout in that moment failed: `fatal: Unable to create
  '…/.git/index.lock': File exists.` In the test that is its own `git commit`. In real use it is
  a person's `git commit`, `git add` or `git switch` in the checkout, so the fix is in `Mains`,
  not only in the test. A read with `--no-optional-locks` writes nothing and prints the same
  porcelain. The function's doc says so, with a doctest.
- **`MainsTest`** still commits into the checkout while `Mains` reads it every 100 ms, as a
  person's commit would come, and its comment says why that is safe now: a read takes no lock,
  and the row the test waited on (`ready`, owing nothing) was written once the pull's task had
  ended. That task's merge is the one git command of `Mains` that takes the lock, and none
  starts before the next landing. The row is the announced event the test waits on; no wait
  was added.
- **`JobsTest`: no change.** The cut fetch's host side does not outlive a run of this test that
  passes (below), and the failure F-141 saw has another cause, in the gate's check (new-2).

## What was measured

- **The lock, on purpose.** A test (not kept) started `Mains` with `interval: 5` and made 300
  commits into the checkout, with 20 busy loops running on the 15-core machine. Before the fix,
  15 of the 300 found `index.lock` held. With it, 0 of 300, in each of four runs.
- **Git with the lock held** (git 2.56.0, a lock file put in place by hand): `status` with and
  without `--no-optional-locks` exits 0; `commit` exits 128 (`Unable to create …index.lock`);
  a fast-forward `merge` fails.
- **The cut fetch, under load.** None of these left a process:
  - the test alone, 20 runs with 20 busy loops;
  - JobsTest and CopiesTest together, 4 runs with 14 busy loops;
  - JobsTest, 23 runs with 8 busy loops, with a trace (not kept) in the ssh stand-in;
  - the fetch alone outside ExUnit, 150 runs with 25 busy loops: real rsync 3.5.0 and flock
    0.4.0, the test's stand-in, and `Copies`' host side.

  Each of the 23 traced drops walked sh, flock and rsync's server, each stopped (`T`) and in
  the process group of the workstation's rsync, and killed them.
- **Why a passing run cannot leave the host side.** Every process of the host side and the
  stand-in holds the workstation rsync's stderr, which is the port's pipe (`lsof` on a slow
  fetch). An Erlang port sends `exit_status` only once every holder of its pipe has closed it,
  even a stopped one. A port whose shell exited at once, while a child it stopped held the
  pipe, gave no status for 3 s, and gave it at once after the child was killed. So while any of
  them lives, `Shell.run` cannot answer `{:ok, %{status: _}}`, which the test asserts. At its
  timeout `Shell` sends TERM, then KILL, to the group, which holds them all, and answers
  `{:unknown, {:timeout, _}}`, which fails the test.
- **What the gate saw, on purpose.** The machine still runs processes from test VMs that
  ended 2½ days ago (Sun 15 Nov, about 16:00 to 20:00): 18 VM directories are named by running
  processes. Three of them, VMs 19309, 68119 and 93726, are whole fetch trees: the
  workstation's rsync (orphaned, parent 1), the ssh stand-in, `head -c 1500000`, sh, flock and
  `rsync --server --sender`, deadlocked on their pipes. That `head -c` cut is in no commit: it
  is a stand-in from while F-78 was built. The other 15 are a dtach master and its bash each,
  from Sessions tests. The gate's own listing loop, run by hand with `vm=19309`, prints
  `gate-test: the test VM 19309 left these processes running:` and the five processes of that
  tree whose command lines name the directory. That is the failure F-141 reported, "the host
  side of a fetch (`rsync --server --sender` under `flock`)", with no test failing, from a run
  of nothing. Pids wrap often here (99 099, then 2 566, within this unit's runs).

## What I ran into

- The odds of the collision are small per run: 18 stale names among about 100 000 pids, 3 of
  them fetch trees. So this explains F-141's one failure without proving it: its VM's pid is
  not recorded. What it does settle is that the test itself, in its current form, cannot leave
  what was listed while it passes, and that the gate can list processes no part of its run
  made.
- The stale trees show what does leave a host side running: a test VM that ends while its
  fetch is under way. `Shell` with no reaper leaves a program running when its caller or the
  VM dies (`Shell`'s doc), and `JobsTest` gives `Jobs` no reaper. A gate run's VM ends only
  after every test has ended, so this takes a VM cut short, as one stopped by hand.
- `erl_child_setup: failed with error 32 on line 284` is printed by some `MainsTest` runs that
  pass, before and after this unit's change.

## Findings

### new-1. A `locked` checkout may be a person's git at work, not only a stale lock

What happened: the brief asked whether `Mains` meets the lock of a person's git in the checkout.
It does, and handles it: while a person's git holds `index.lock`, a read still passes and is
`locked` (the lock file exists), and a pull's merge fails and stays owed. The read after the
lock is gone pulls. `Mains`' own merge holds the lock for its moment too, so a person's commit
then fails as it would beside any other git.
Why: git allows one writer of the index at a time, and `Mains` writes only in its merge.
What I did: nothing more than the read's fix.
What the design should change: "Main sessions" calls the lock stale ("a git command a restart
cut"). It should say that `locked` is also shown for one read while a person's git command
runs, and that the next read clears it.

### new-2. The gate's left-process check matches a stale process of an earlier VM by pid

What happened: see "What was measured". The gate lists a process as its run's when its command
line names `/caf-<VM pid>/`. Processes left by VMs that ended days ago still name their
directories, and a later VM can get the same pid.
Why: `TestHost.vm_dir/0` and the gate name the VM's directory by its pid alone, and the machine
keeps what earlier runs left (here an uncommitted stand-in's deadlocked fetches, and dtach
masters).
What I did: nothing in the gate or in `TestHost` (outside this unit); no process was ended
(none is this unit's).
What the design should change: two things.
- The VM's directory should be unique to its run, and the gate should know it: for example the
  gate makes it and passes it to the VM in an environment variable that `TestHost` reads, or the
  name joins the pid and the run's start time.
- A person should end the stale trees, from the 18 VMs listed by
  `ps -axww -o pid=,etime=,command= | grep /caf-`.

### new-3. `Sessions.Worktree` reads a worktree's status with git's optional lock

What happened: `Sessions.Worktree.git(_, {:status, path})` runs a plain `git status` when a
start, a resume or a removal decides on a worktree, so an agent's git in that worktree at that
moment may find `index.lock` held, as in new-1's cause.
Why: the same optional lock.
What I did: nothing at first; the main session then added `--no-optional-locks` there in this unit.
What the design should change: nothing; a unit on `Sessions` should add `--no-optional-locks`
to that read as this one did to `Mains`'.
