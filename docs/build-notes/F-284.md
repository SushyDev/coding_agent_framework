# F-284: a launch whose start timed out before anything started settles, and frees its name

## What was seen

An embedding app on Linux (main 8b4f023, load about 17) started an interactive delegate with a
brief. The start answered `{:refused, {:launch, {:unknown, {:timeout, 5000}}}}`. No worktree,
branch or tmux session was made. The brief's row stayed `sending` by `launch`, and every later
start of that branch was refused `{:launch, {:refused, {:sending, [id]}}}`. A later retry was
refused `{:brief, {:unknown, {:timeout, 5000}}}`: the `Mailbox` was slow for every call then.

About twelve minutes after the first start, the row read `queued`, `again` 1, `via` empty,
`attempt` `no_delivery`. The retries' briefs read `ended`. The app then started the same work
under another branch name, which went fine.

## Diagnosis

**Whose 5 s.** `Delegates.launch_first/3` calls `Mailbox.launch/4` in the `Delegates` process,
inside `begin/4`, with `Mailbox`'s default call bound (`@step`, 5 000 ms). By then the start had
written its `starting` row, got its lease and stored the brief (`queued`). Nothing else: the
worktree is made by `Sessions`, which is called only after the mark.

**Why nothing settled it.** `Delegates` read the `{:unknown, _}` as "nothing marked": it
answered the start refused and called `Mailbox.ended/3`, which settles `queued` rows only. But
the `launch` request was still in the `Mailbox`'s message queue. Handled after its caller gave
up, it marked the brief `sending` by `launch`, put its id in `launching` (memory) and answered
into nothing. The `ended` request came after it in the same queue, so it found the row `sending`
and left it. No one would call `launched/3`, and `settle/2` skips every id in `launching`, with
no bound: the row was read by no evidence for as long as that `Mailbox` process lived. Each later
start's `Mailbox.launch/4` found it `sending` and was refused.

**What moved it to `queued`.** Only `Transport.settle`'s `:again` writes `again` 1 with `via`
nil, and `settle/2` reaches a launch row only once its id is out of `launching`, which only a
new `Mailbox` process forgets. So the `Mailbox` restarted (its first settle wrote other rows in
the same seconds). There `launch_seen/2` read no agent row, so `gone`, so due again; then
`deliver/3` found no agent row (`target` `:none`) and wrote `attempt` `no_delivery`.

**Does that `queued` row block a start of the name?** Not by a refusal: `Mailbox.launch/4`
refuses only while a row is `sending`. It does worse. A new start of the name (`Turn.again/3`
answers `:new` after a refused row) stores its own brief, then marks the first row due, and a
row made due again goes first: the old brief becomes the new start's prompt, and the new brief
waits behind it. The test below shows it: with the fix taken out, the new start's prompt was
`Stale.`, not its own brief.

## What was built

The model first. `Delivery.tla` has a row field `unheard` and the step `MarkLost`: the caller of
a start's mark gave up on its answer, so `Launch` never comes for it. The design's caller undoes
the mark, which is `Refused`; `Break_Delivery_LostMark` tells nothing, and TLC finds the row in
`hand`, `sending` for good (`SendingSettles`, four states). `NoStart` ends a brief marked for a
start that made no process and that no start will make now (out of `hand`).

The code:

- `Mailbox.launch_lost/4`: the caller of `launch/4` for `to` by `deadline` got `{:unknown, _}`
  and makes no start. The row that call marked, if any, is undone as a refused start's: due
  again, `attempt` `launch_lost`. `Mailbox` takes one process's calls in the order sent, so this
  call always finds the late mark made or never to be made. `Delegates` (start and resume),
  `Mains` and `Mover` call it on an unknown answer of `launch/4`. For `Mover` this matters as
  much: its retry of a resume read `{:sending, _}` as unknown and asked again, for good.
- A mark is read by no evidence until the start's answer, and no longer than the start's
  deadline (`sent_at`), past which `Sessions` takes no call of it (`caller_deadline`). A timer
  reads the row at that deadline, set at the mark and again at a restart.
- A mark whose start made no process (`at` nil) while no agent row is there waits for the
  start's deadline, since the start may still write the row; it was due again at once, so a
  start still under way could carry a row that was then sent again. Past the deadline, a brief
  is `ended`, `attempt` `no_start` (a later start stores its own), and any other row is due
  again, for the addressee's next start (F-143).
- A delegate's new start (`Turn.again/3` `:new`) calls `Mailbox.ended/3` for its name before it
  stores its brief: any row still queued to the name is an earlier start's that never ran.

**The bound.** With a live caller, the late mark is undone the moment `Mailbox` handles it, and
the refused start's `ended` follows at once: before any later call of that caller is handled, so
the next start of the branch is never refused by it. With no caller left (it died, or `Mailbox`
restarted), by the start's deadline: for a delegate `@call + setup_timeout + @slack` after the
start (30 s + the project's setup bound + 120 s; 750 s in the app above).

`unknown` or `failed`: the brief named either. The design's word for a row that never went in is
`ended` (`EndedNotDelivered`), which is what a refused start's rows already read; nothing of a
lost mark went in, so it is `ended` too (new-1).

## Findings

### new-1. The brief asks for `unknown` or `failed`; a lost mark reads `ended`

What happened: the brief asked that a launch row with no session behind it settle `unknown`, or
`failed` when it is known nothing started. Why: a message row has no `failed`, and `unknown` is
the forced end's alone (`UnknownWhy`: a row whose text may have gone in). A lost mark is known
not to have gone in, which is `ended`, as a refused start's rows already read. What I did: `ended`,
with `attempt` `launch_lost` (then the refused start's `ended`) or `no_start`. The design should
change: say in the launch's restart cell that `ended` is the end of a start's rows that never
went in, so no later unit adds a `failed`.

### new-2. A leftover from before this build ends only at the name's next start

What happened: the app's row 235 is `queued` to a name no process of which runs. Why: no
`Mailbox` rule can tell a queued brief whose start is under way (stored, not yet marked) from a
leftover: a queued row has no deadline. What I did: a delegate's new start of the name ends it,
the one moment it could do harm. A name never started again keeps it `queued`, counted in the
open rows. The design should change: a brief could carry its start's deadline from its store, so
`Mailbox` ends a brief queued past it with no agent row, as `NoStart` does for a sending one.

### new-3. Every `Mailbox` call waited past 5 s on a loaded host

What happened: two calls of one start (`launch`, then a retry's `brief`) timed out at 5 s within
two minutes. Why: `Mailbox` is one process, and its settle pass reads `Stream`'s rows and each
open row's transcript, each read up to 5 s, so one pass can hold every call for longer than a
caller's bound. Not measured here. What I did: nothing beyond making a lost answer safe. The
design should change: measure a settle pass's length under load, and either bound the pass or
read the transcripts outside the `Mailbox`'s own process, so its calls answer within `@step`.

### new-4. A mark whose deadline already passed is accepted

What happened: a test marked a launch with a deadline a minute past, and its start then ran.
Why: `launch/4` never checks its deadline, and a mark past it is now read as lost at once. What I
did: the test marks with a deadline ahead. The design should change: `launch/4` could refuse a
deadline already past (`{:refused, :past_deadline}`), since `Sessions` would refuse that start's
call anyway.
