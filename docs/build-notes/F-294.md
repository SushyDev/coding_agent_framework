# F-294: an interactive delegate's second interrupt, as a main's

## Why

F-270 found that Escape writes no hook event, so a main session's claimed interrupt state never
moved and every later interrupt was refused `{:already_claimed, op}`. It fixed main sessions,
and its new-2 said an interactive delegate's interrupt has the same gap: `Delegates.fix_state`
relies on `offset` the same way.

## What was built

- **The model first.** `Team.tla`'s `Retried` and `InterruptRetryOpen` drop `r.t \in Mains`, so
  a delegate's interrupt that did not help moves its state too, as a main session's does. The
  header names `Delegates.fix_state/4` among what the spec models. `Break_Team_RetryBlocked`
  has one main session and no delegate, so it covers main sessions only; the new
  `Break_Team_DelegateRetryBlocked` (one main session, its delegate, no operator, so only the
  parent interrupts, and only the delegate) keeps the state and fails `InterruptRetryOpen`. The
  new `Team_DelegateInterruptRetry` is the design's case: a main session, its delegate and the
  operator, two faults and a restart.
- **The code.** `Delegates.fix_state/4` takes `fix: :interrupt`, and then names `interrupted`,
  the id of the newest row in `Acts` of an interrupt of the delegate whose act ran and settled.
  Unlike `Mains`, it reads every actor's: a delegate's interrupt may be its parent's or the
  operator's acting as its parent, and `Acts` keys a claim by target and state, so the two are
  one claim. `Delegates.fix/5` reads the state the same way for an `:interrupt`, so a state read
  without it is `{:refused, {:moved, now}}`. `MCP`'s delegate fixer reads `fix: :interrupt` for
  the `interrupt` tool. A read of `Acts` that did not answer is `{:unknown, {:acts, reason}}`.
- **Shared.** The reading is `Acts.newest_acted/3` (a `rows/3` filter, settled, `acted_at`
  set, the largest id), and `Mains`' `interrupted/2` now calls it.
- **Tests.** `delegates_interactive_test.exs` gains one test on the screen stand-in, as F-270's
  main-session test: a stubborn turn that goes on past its first Escape. The first interrupt
  answers `{:unknown, {:still_running, _}}`; while its claim is open the state is the same and a
  second claim is refused as claimed; once it settled the state names it and the retry, the
  operator's claim this time, sends; the next is claimed on a new state and is refused
  `{:screen, %{state: :idle}}`, its claim let go, and the state is free again.

## What was measured

- `Break_Team_RetryBlocked` still fails `InterruptRetryOpen`, and
  `Break_Team_DelegateRetryBlocked` fails it too. `Team_InterruptRetry`: 358 distinct states, 1 s.
  `Team_DelegateInterruptRetry`: 48 238 distinct states, depth 20, 4 s on 12 cores.
- The new test runs in about 8 s.

## What I ran into

- Without `acts:` a delegate has no claim to name, so its interrupt state leaves the key out,
  where `Mains` puts nil. An existing test in `delegates_interactive_test.exs` reads a state
  with `fix_state/3` and interrupts with it on a `Delegates` with no `acts:`; with nil there it
  would have been refused as moved. Another unit changes that file at the same time, so this
  one adds its test and changes none of the others. See new-1.

## Findings

### new-1. A delegate's interrupt state leaves `interrupted` out with no `Acts`

What happened: `Mains.fix_state/3` with `fix: :interrupt` always names `interrupted`, nil with
no `acts:`. `Delegates.fix_state/4` names it only with `acts:`.

Why: an existing test reads a state with `fix_state/3` and interrupts with it, on a `Delegates`
with no `acts:`. The key left out keeps that state equal to the interrupt's, and the test file
was not this unit's to change beyond its own test.

What I did: left the key out with no `acts:`, and said so in the `@doc`.

What the design should change: once the other unit's change to that file is in, name
`interrupted` always (nil with no `acts:`), as `Mains` does, and read the state there with
`fix: :interrupt`, so a delegate's and a main session's interrupt states have one shape.
