# F-204: no message into the moment between a background command's end and its own turn

F-196's new-6: one `gate-test` run failed `DelegatesTest`'s "a turn a background command's end
begins is never a second report or a reply", the parent's message `delivered` where it must
wait through the turn the command's end begins. The cause was as the brief read it.
`task_notification` emptied the fold's `tasks` while `idle` still held from the brief's result,
so `Sessions.Turn` read the delegate `:ended`. A read that fell between that event and the
next turn's `system`/`init` let `Mailbox` mark the message, and Claude Code's own turn took it.
No test or step of this unit started the real Claude Code.

## What was built

- **The model first** (`Remedies.tla`). The command's end and its turn's init are now two
  steps. `CommandEnds` takes an idle delegate to `waking` (a turn is coming) or `silent` (a
  release that starts none), `OwnInit` takes `waking` to `own`, and `OwnResult` ends it. New
  variables: `fidle` (what `Stream.Fold` reads, as `Mailbox` reads it), `msg` (a parent's
  message, `Send`, then `Deliver` only on an idle read with no command running) and `joined`
  (it went in between the end and its turn's end). `ReplyResult` ends a turn the message
  began. `Unwake` is `Stream`'s bound: `silent` reads idle again. New properties:
  `NoMessageIntoOwnTurn` and `ReadBusy` (invariants) and `ReadsIdleAgain` (liveness). Two new
  breaks: `Break_Remedies_IdleAtEnd` (the fold reads the turn ended at the command's end) fails
  `NoMessageIntoOwnTurn`, and `Break_Remedies_NoBound` fails `ReadsIdleAgain`. The header names
  `Stream.Fold`'s `waking`, `Stream`'s `wake:` and `Mailbox`.
- **`Stream.Fold`**. A `task_notification` read while the turn reads ended, after an init, with
  the process not gone, clears `idle` and sets `waking: %{at: nil}`. `stamp/2` gives it the
  read's time once. The next init or `result` clears it; so do an exit and a follow again. An
  end during a running turn changes nothing. `unwake/3` (pure): a fold waking since `bound` ms
  or more reads the turn ended again and counts it in `unwoken`. That is how it records why.
  `upgrade/1` fills both fields for a stored fold.
- **`Stream`**. A new option, `wake:` (ms, 30 s by default). Each read applies
  `Fold.unwake/3` after the stamp, so the bound ends on the first read past it, and that read
  cues `stream:<host>` like any changed row. `Config.parts` takes `stream` `wake`.
- **The stand-in's `bg`** now waits for a second line on `bg.fifo` between the command's end
  (`task_updated`, `task_notification`, the empty list) and the init. A third line ends the
  turn. So a test reads the moment between the two events every time.
- **Tests.** `DelegatesTest`'s case writes the end and waits for the read that saw it. It cues
  `Mailbox` and checks that the message is still `queued` and the fold `waking`. It then writes
  the init, waits for the turn of its own to begin (`waking` nil, not idle), and checks that the
  message is still `queued`. Only after the result does the message go. Every wait is on a
  stream read, never a sleep. `StreamFoldTest` covers the order, the stamp, an end inside a
  running turn, an end before any init, the bound, the exit and the follow again. `StreamTest`
  runs a real stand-in under a `Stream` with `wake: 0`: the read that sees the end passes the
  bound, the row reads idle with `unwoken: 1`, and a message is taken.
- **Docs.** `docs/design.md`: "When a delegate reads idle after a background command" under
  "A background command outlives its report", and a pointer from "Turns are events".

## Findings

### new-1. The bound's length rests on a gap nobody measured

What happened: `Remedies.tla` takes `wake:` as longer than the gap between a command's end and
the init of the turn it begins, so the bound passes only where no init comes. If an init came
later than the bound, the delegate would read idle in the gap again, and a message could go in.
Why: F-184 measured the order of the events, not the time between them. What I did: I set
30 s by default, a guess well past anything one read interval (2 s in the app) could show, and
let the config change it. What the design should change: the release check, which already
records the background command, records the time from `task_notification` to the next
`system`/`init` on the pinned release, and the default is set from it.

### new-2. Every task's end is taken to begin a turn; only a background `Bash` command's was measured

What happened: the fold makes any `task_notification` read while the turn reads ended
`waking`, whatever the task's type. F-184 measured only `local_bash`. Why: the event looks the
same for every task type, and the only case the fold can tell apart is a turn running or not.
What I did: nothing more. If some task's end begins no turn on a release, the delegate reads
busy until the bound, so a message to it waits up to 30 s, and `unwoken` counts each such end.
What the design should change: the release check records, for each task type the pinned
release shows (a background command, and any other its `task_started` names), whether its end
begins a turn. A view could also show `unwoken` above 0, since it means a release
behaved in a way not measured.
