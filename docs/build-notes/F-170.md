# F-170: delegate ergonomics

Four small changes to how an app and an agent use delegates: the operator's start takes the
tool's options, a queued start answers at once, every delivery names its sender, and the
operator can end a session that a delivery can't settle.

## What was built

- **Options on the operator's start.** `Operator.start_delegate/7` takes `interactive:`,
  `meta:`, `options:` and `wait:`, each mapped to the tool's own argument, so an app never names
  the tool. Any other option is refused `{:bad, {:option, key}}` with no call made.
- **A queued start answers at once** (`Delegate.tla` first). `start_delegate` takes `wait`:
  an agent's call defaults to `false`, and the operator's to `true`. With `wait: false`, a start
  whose lease the `Scheduler` answers `queued` writes `tell` (the parent's name) on the
  delegate's row, then answers `{:ok, %{delegate: name, queued: position}}`. Once the lease
  is answered (granted and the start run, or refused), `Delegates` stores one notice to the
  parent in `Mailbox` under the key `start:<host>:<id>:<created_at>`, then clears `tell`. A
  refusal names its reason and the time to ask again. The notice is sent from every place the
  start can reach an outcome: the lease's message, the start task's answer, and the settle
  after a restart.
- **The sender on every delivery.** `Mailbox.frame/1` puts `From <name> (<kind>):` before the
  text of every row but a brief and a word to go on. It is applied at the hand-on, in each
  transport (stream, waiter, typed, launch, and the launch's file), before the uuid mark, so
  the settle is unchanged. An app may pass `frame:`. A frame that answers no text is refused
  `{:bad, :frame}`, and the row stays due with that `attempt`.
- **A forced end.** `Operator.end_main/3` and `Operator.stop/3` take `force: true`, operator
  only. `Sessions.stop/3` and `end_main/3` then skip their check for open or sending rows to the
  session, and stop it as usual (SIGTERM once idle). After that, MCP calls
  `Mailbox.ended_while_sending/3`, which settles each row still `sending` to the session
  `unknown` with attempt `ended_while_sending`, but only once the session is free. The end is
  a claimed act in `Acts` (no state, act `end_main`), and each row's settle is a `settle` row
  with outcome `unknown`. A forced stop of a delegate still needs its report delivered.

- **Tests.** `delegates_test.exs`: a queued start with `wait: false` answers its place at
  once, then its refusal (reason and retry time) is told once, and a restart that left the
  mark stores no second notice; with `wait: true` the caller waits, as before.
  `mcp_test.exs`: an agent's start does not wait by default and the operator's does; the
  operator's options reach `Delegates`, and an unknown one is refused; a forced end is the
  operator's only, its act and each row's settle are rows in a real `Acts`, and an agent's
  forced stop is refused. `mailbox_waiter_test.exs`: an app's frame, and one that answers no
  text; a row in flight at a forced end settles `unknown` once the session is free, and its
  hand-on's late answer changes nothing. The tests that compare a delivered text now expect
  the sender line.

## What I ran into

- `Delegate_Queued` with two delegates and the liveness properties ran past ten minutes, so I
  split it: one delegate with liveness, and two with invariants only.
- A first `Delivery_Forced` on `Delivery_Launch` failed `Arrives` for a reason that has nothing
  to do with the forced end (new-3).
- The first full model run failed `Delivery_Turns`: alone, `ForcedEnd` is enabled in every
  Delivery config once a stop is asked, and a row it settles `unknown` never reaches
  `delivered` or `ended`, so `Arrives` failed. `Arrives` now also accepts `unknown`, but only
  for a row to an addressee in `forced`. Without a forced end, the property is unchanged.
- The sender line broke the tests that compare a delivered text exactly, and the headless
  stand-in, which reads its cue (`ask`, `self`, `quiet`, `half`) from the start of the text.
  The stand-in now also takes the cue after a `From <name> (<kind>): ` line.
- A guard on `MainEnds` that only allowed an end the unforced rules allowed meant
  `Break_Team_ForceByAgent` could never be reached. The guard now has its own case for the
  forced end (`MayForce`).

## Findings

### new-1. "At once if it never ran a turn" is not built

The brief asks the forced end to stop a session at once if it never ran a turn. `Sessions`
has nothing that tells "never began a turn" apart from "not idle yet". It has no config dir for
the transcript, and no one has measured what the session file of a session that is not logged
in says. So the forced stop waits for idle, as every stop does. In the model, `idle` covers a
session that never began a turn. The design should say which evidence means "never ran a
turn" (perhaps the transcript has no user line and the session file reads idle) once that is
measured on a session that is not logged in.

### new-2. A forced stop of a delegate still needs its report

A forced stop of a delegate with no delivered report would break `EndsAfterDelivery` in
`Delegate.tla`. So the forced stop skips only the wait for rows in flight to the delegate, not
the report rule. If the design wants the operator to end a delegate with no report (one that
never logged in, say), that is a new act with a property of its own, such as the brief settled
`ended` and the parent told.

### new-3. In `Delivery.tla` alone, a launched session asked to stop never starts again

On `Delivery_Launch`, `Arrives` fails after a launched session has a stop asked (or a crash):
alone, nothing starts its process again, so a row to it never arrives. This was already in the
alone model; it appears only when a config checks liveness with a stop. `Team.tla` and
`Delegate.tla` start sessions again. The forced-end config checks on `Delivery_Interactive`
instead. The design could add a restart to the alone model, or say that `Arrives` holds there
only for sessions that are never stopped.

### new-4. The liveness of a forced end is checked only in part

A `SendingSettles` liveness property on `Delivery_Forced` was too slow to finish, so the config
checks the invariants and `UnknownStays`. That each sending row to a forced session settles is
checked by the code's tests, not by TLC.

### new-5. Settling unknown is a second call after the end

The forced end and the `unknown` settle are two calls (`Mains` or `Delegates`, then `Mailbox`).
If the framework restarts between them, rows stay `sending` to an ended session. Calling the
forced end again on the ended session settles them, since `ended_while_sending/3` needs only
the session to be free. Nothing does that by itself. The design could have `Mailbox` settle,
at its own settle, every row `sending` to an `ended` agent row whose end was forced, if the
`Acts` row of the end is enough evidence.

### new-6. The sender line leaves little room on a typed line

The `typed` transport types a row as itself only when its line, with ` [delivery <uuid>]`
(48 characters) at the end, fits in 76 characters (`Transport.Typed.short/0`). `From d1
(message): ` takes 19 more, so a typed row from a two-letter sender now fits only if its text
is 9 characters or shorter: "report one" from `d1` now goes as a pointer to its file. That is
still correct delivery, but almost every typed row is now a pointer, and the agent has to read
a file for a one-word message. The design could raise the short limit (if the `Inlet`'s line
allows it), or put the sender in the pointer line instead of only in the file.
