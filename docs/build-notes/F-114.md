# F-114: delivery into a main session by a waiting Stop hook; a session ended by SIGTERM

A design unit, from two checks run on the real Claude Code 2.1.322 on the capture account, in
a scratch folder of their own with a settings file of their own (named by `--settings`). No
code changes.

## What was measured

Each check started an interactive session in tmux, sent one prompt, and let the turn end. The
settings named two hooks:

- a Stop hook with `asyncRewake: true`: a script that waits for a file and, once the file is
  there, writes its text to stderr and exits 2;
- a SessionEnd hook that records its input.

| Check | First run (hook `timeout` 600 s, idle 20 s) | Second run (`timeout` 7200 s, idle 12 min) |
| --- | --- | --- |
| A wake while idle | answered in 3 s | answered in 4 s |
| A wake with a draft typed in the box, not sent | answered in 2 s; the draft stayed in the box, not sent | the same |
| The session file's `status` once idle | `idle` | `idle` |
| SIGTERM to the session file's pid | exit 143; the resume hint shown; SessionEnd with `reason: "other"` | the same |

- Each turn's end starts a new waiter. The waiter of one turn is the hook of that turn's Stop,
  so exactly one waits at a time.
- The transcript holds each wake as a user line whose text is
  `Stop hook blocking error from command "Stop": <text>`, inside a `task-notification` and a
  `system-reminder`, after a `queue-operation` enqueue and dequeue.
- The screen shows `⏺ Stop hook feedback` above the reply.
- After the SIGTERM the transcript ends with its `last-prompt` and `cost-state` lines, as after
  `/exit`.

The research behind it (Claude Code's docs and the binary's strings) found the other ways, and
why they are not used:
- `asyncRewake`: "If true, hook runs in background and wakes the model on exit code 2
  (blocking error). Implies async."
- Channels (`notifications/claude/channel`) need a development flag that shows a warning at
  every start, and are a research preview.
- Cross-session messaging is behind a feature flag that is off.
- Remote Control is not an API.
- SIGINT, SIGTERM and SIGHUP all run the same shutdown, with codes 0, 143 and 129, and fire
  SessionEnd with reason `other`. `/exit` gives `prompt_input_exit`.

## What the design changes

- **Delivery into a main session** (a report, a reply, a message) goes through a waiting Stop
  hook, not typed keys. Each main session's settings name a Stop hook with `asyncRewake: true`
  and a long `timeout`. Its program connects to the framework, says which session it is, and
  waits. When something is due, the framework answers that waiter with the text, and the
  program writes it to stderr and exits 2, which starts a turn. Delivery is confirmed by the
  transcript's line, as a typed write was. Nothing is typed, so a draft a person left in the
  box is not touched and the box need not be empty.
- **A session with no waiter** gets nothing that way. That happens before its first turn ends,
  after a waiter's timeout, or after the framework restarts while the waiter's connection is
  cut. The framework knows it, since it holds each waiter's connection. Due text is held until
  a waiter connects. A view shows a session idle with no waiter and something due; the checked
  write through `Screen` stays as the way to reach it.
- **Ending a session** is SIGTERM to the pid from its session file, sent once that file says
  `idle`, by the row's pid and start time. It replaces typing `/exit`. The move's end and
  `Recoveries` read SessionEnd's `reason: "other"` as this end.
- **`Screen`** keeps:
  - the trust dialog;
  - typed commands with their result lines (`/mcp reconnect <server>`, `/reload-plugins`,
    `/reload-skills`);
  - the interrupt key;
  - the box check before any typed write.
- **The session file's `status`** (`busy`, `idle`, `waiting` with `waitingFor`) is undocumented.
  It is read as a hint, and checked against each pinned release like the screen fixtures.

## Findings

### new-1. The longest a hook's `timeout` may be is not known

What happened: 7200 s held for a 12-minute idle. Whether Claude Code caps a hook's timeout
lower than the value given, or kills an async hook for another reason (a compaction, a
`/clear`), was not measured.
What the design should change: the per-release check measures a long idle (hours) and a
compaction with a waiter running. Until then, a session with no waiter is a state a view shows,
and the checked write reaches it.

### new-2. `Move.tla` ends by `/exit`

What happened: the move's step 3 types `/exit` in the same step as the box check. A SIGTERM
after an `idle` read leaves a window in which a prompt through Remote Control starts a turn and
is cut off. Copying the transcript after the exit keeps what that turn wrote.
What the design should change: `Move.tla` models the end by SIGTERM after an `idle` read, before
`Mover` is built, and shows that the cut-off turn is kept by the copy.
