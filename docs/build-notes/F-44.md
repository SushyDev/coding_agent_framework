# F-44: `devenv test` shows the gates it runs, and fails when none ran

## What was wrong

Under a coding agent, `devenv test` printed only devenv's own tasks and exited 0. Its log ended
with `✓ Running devenv:enterTest in 1.08µs (no command)`. It looked as if the gates did not run.

They did run. A run on the clean tree before the fix wrote `_build/dev`, `_build/test` and
`_build/tlc` while it ran, and took 8 min 10 s. The same tree with agent detection turned off
(`DEVENV_NO_AI_AGENT=1 devenv test --no-tui`) printed 426 lines: `ok tmux: tmux 3.8`, every
app's test result, every TLC configuration, `✓ Running tests in 221s` and `Tests passed :)`.
What was missing was the output, not the gates.

## The cause, from devenv 2.4.0's source

- `devenv test` has two parts that share a name. `Devenv::test` in `devenv/src/devenv/mod.rs`
  first runs the task graph rooted at the task `devenv:enterTest` (phase 2), which includes
  `devenv:git-hooks:run`. Then it builds `config.test`, the `enterTest` option wrapped in
  `set -euo pipefail`, and runs it as the operation "Running tests" (phase 5). The task
  `devenv:enterTest` has no command of its own (`src/modules/tasks.nix`), so it always logs
  `(no command)`. The `enterTest` in `devenv.nix` is phase 5.
- `run_in_shell` sends phase 5's stdout to the log at Info level and its stderr at Error level.
- `is_ai_agent()` sees `CLAUDECODE=1` (also `AI_AGENT` and others) and sets the verbosity to
  Quiet. In `devenv/src/console.rs`, Quiet shows only the Error level. It hides "Running tests",
  every line the gates print to stdout, and `Tests passed :)`. It keeps the hidden lines and
  prints them only when the operation fails.
- Since 2.3.0, Quiet prints each task's running and succeeded lines (#3115). So the log shows
  the phase 2 tasks and ends at `devenv:enterTest (no command)`, the last line printed.

When it changed: `devenv.lock` pins the devenv modules at `6c954cc` and has not changed since
F-1, so no commit here changed it. The change is in the devenv program, which comes from the
system, not from the lock. The changelog dates it. 2.1.0 (2026-05-05) added the agent
auto-quiet, which has hidden passing gates ever since (F-8 already noted "`devenv test` hides
the gates' output when they pass"). 2.3.0 (2026-09-07) added the task lines that end on
`enterTest`. The machine keeps only two system generations, both with devenv 2.4.0, so the
day this checkout first ran 2.3 or later cannot be read back.

## What was built

`devenv.nix` only.

- The five steps (`check-versions`, `gate-format`, `gate-compile`, `gate-test`, `gate-model`)
  are now tasks `caf:<name>`, generated from one list, in phase 2. Each has `showOutput = true`.
  Since 2.3.0 that is devenv's one way to print a passing task's output under Quiet (#3038).
  Each comes after the one before it, so a failing gate stops the rest (`dependency failed`) and
  `devenv test` fails with `enterTest tasks failed`. The first waits for `devenv:enterShell` and
  `devenv:git-hooks:run`: the hook's `mix format` would otherwise run beside `gate-compile` on
  the same `_build`. Each has `before = [ "devenv:enterTest" ]` and
  `wantedBy = [ "devenv:enterTest" ]`. `wantedBy` keeps them out of `devenv shell` (checked:
  `devenv shell -- true` runs none of them). Each runs in the root. The scripts keep their names,
  so `devenv shell -- gate-test` still works.
- Each gate task that passes exports `CAF_PASSED_<NAME>=1` (task `exports`). Phase 5, the
  `enterTest` script, now only checks these. If any is missing it prints `devenv test: these
  gates did not run: …` and fails. Otherwise it prints `devenv test: every gate ran: …`. It
  writes to stderr, which Quiet still prints.

Why exports and not mark files: the first try wrote a file per gate under `$DEVENV_STATE`. In
the hollow-run demo below it reported only three gates missing, because a failed run before it
had left marks for `check-versions` and `gate-format`. A file can outlive its run. devenv gives
phase 5 the exports from its own run's phase 2, so nothing goes stale. (A caller that has set
`CAF_PASSED_*` in its own environment would pass them on; nothing here sets them.) A
summary line that something outside devenv must look for was the other choice, but it needs a
check outside `devenv test`. This check is inside it.

## What was measured

- `devenv test`, clean tree: 4 min 56 s with the fix (`gate-model` 250 s). Earlier runs took
  7 min 29 s and 8 min 10 s, with the first compile in a fresh worktree and `gate-model` at
  287 s. F-8 measured 48 to 62 s for everything; see new-3.
- `devenv shell -- gate-test`, three runs: 213 s, 185 s and 56 s. Each ran 173 tests, all
  passed, with no compiling. The load average was 52 to 69 from other work on the machine, so
  the spread is load.

## What I ran into

- `devenv test` runs with `DEVENV_STATE` at `.devenv/test-state`, not `.devenv/state`. So
  `MIX_HOME`, `HEX_HOME` and the rebar3 cache differ from `devenv shell`'s, while `_build` is
  shared. It did not cause a recompile here.
- The brief named `enterTest` and the task `devenv:enterTest` as one thing. They are two, and
  that is why the log line misled.

## Findings

### new-1. A passing check was invisible to the agent that ran it

What happened: from devenv 2.1.0, `devenv test` under a coding agent hid everything a passing
gate printed. The one sign it ran was its time. The F-8 note saw this and took it as how
devenv works. Later units read the short log as "only the hooks ran".

Why: devenv cuts its output for agents to save tokens. A pass then looks like a run that did
nothing.

What I did: the gates print through `showOutput`, and the run fails unless every gate reports
that it passed.

What the design should change: add to the gates rule that a gate run must show, in the log its
runner reads, each gate's name and its result, and that it must fail when a gate did not run. A
quiet pass is not a pass.

### new-2. The devenv program is not pinned

What happened: `devenv.lock` pins the modules, but the `devenv` command comes from the system
(`/run/current-system/sw/bin/devenv`, now 2.4.0). Its updates changed what `devenv test` prints,
and nothing in this repository noticed.

Why: devenv is how the shell is built, so the lock cannot hold it.

What the design should change: `check-versions` could compare `config.devenv.cli.version` (the
version devenv reports at evaluation) with a version written in `devenv.nix`. Then an update of
the program is seen and checked the way a tool update is. Not built here.

### new-3. The fast model configurations now take most of `devenv test`

What happened: `gate-model` runs `bin/check-model all`, which is only the fast configurations.
It took 250 to 287 s here, about 80% of the run. F-8's whole `devenv test` took under a minute.

Why: "fast" is a limit for each configuration (under 30 s), not for all of them together. Each
new spec adds to the total.

What the design should change: give the test gate's model step a budget for the whole set, or
say that there is none. Then a slow `devenv test` is either a finding or expected.
