# F-87: `MCP`, part 2: `run` and `reload`

F-86 built `run`, `reload` and `Grants.may_use?/2`, then took them out for size. This unit puts
them back on what landed. F-86's patch was a side-by-side display, not a patch `git apply`
takes, so the code was carried over by hand and checked line by line against it.

## What was built

- **`Grants.may_use?/2`**: any agent the tree holds, for a tool open to every agent.
  `may_start_service?/2` is now that same check.
- **`run(host, argv, timeout, opts)`** in `MCP`:
  - The arguments are checked first. `argv` must be a non-empty list of strings. `timeout` must
    be an integer in ms, above 0 and at most a day (the cap). `opts.fetch`, if given, must be a
    list of strings. Anything else is `{:refused, {:bad, :args}}`.
  - Then `Grants.may_use?/2`, so an agent off the tree is `{:unknown_agent, name}`.
  - Then `place`, a function the embedding app gives `MCP`. It maps the caller to `%{project,
    name, worktree}`, which is the copy `Jobs` runs in.
  - Then `Jobs.run/6` with job id `mcp-<call id>`, `timeout:` as the job's and the call's, and
    `fetch:` passed through. The answer is `Jobs`' own, as JSON.
  - `MCP` now takes `jobs: {module, server}` and `place:`, both required.
- **`reload()`**: `Grants.may_use?/2`, then the tools' names. The endpoint answers it as an
  event stream: `notifications/tools/list_changed` first, then the result. `initialize` now
  declares `capabilities.tools.listChanged: true`. Without that, the pinned Claude Code ignores
  the notification (below).

## Tests

`apps/caf_mcp/test/mcp_test.exs`. The test is the MCP client, with a token. `run` reaches a
real `Jobs` and `Copies`, whose one host, `ws`, is this workstation. The job is a stand-in
`bash -c` that writes a file, prints a line and exits 3. So `caf_mcp` declares `caf_jobs` and
`caf_copies` as `only: :test`.

- `run` is the caller's, by its token. An argument `"from"` changes nothing. The job's row is
  `mcp-<call id>`, in the caller's copy. The named file comes back into the worktree. The answer
  equals `MCP.json/1` of a direct `Jobs.run/6` of the same job.
- `run` from a token whose agent the tree does not hold is refused `unknown_agent`, and no job
  starts. Timeouts of a day plus 1 ms, 0, a string, and none are refused as bad arguments, and
  so is a `fetch` that is not a list. Each refusal is logged.
- `reload` sends the notification, then the result with the tool names. Off the tree it is a
  plain JSON refusal, with no notification.
- `tools/list` names `message`, `run` and `reload`.

## Checked against the pinned Claude Code (2.1.322), without running it

I read the strings of the pinned binary (`.claude-wrapped` in the devenv store path):

- It registers a `tools/list_changed` handler only when the server's `initialize` result has
  `capabilities.tools.listChanged`. On the notification it fetches `tools/list` again ("Received
  tools/list_changed notification, refreshing tools"). Its SDK client treats a POST answered as
  `text/event-stream` as a stream, and sends each message in it to its handlers.
- It opens a GET listen stream. On a 405, which our endpoint gives, it returns without an
  error.

Still to check by hand, against a real session and a stand-in endpoint (F-86's new-3):

1. Claude Code loads the `http` entry from the agent's `--mcp-config` file and sends
   `x-caf-token`.
2. After `reload`, the session's tool list is fetched again and the model sees the new list.
3. A 405 on the listen stream does not cause a refetch loop. The strings name a "synthesized
   tools refetch after listen-stream reopen (no notification received)", and the 405 path calls
   `onRequestStreamEnd`. The strings cannot show whether these two connect.
4. A `run` held for minutes is not cut by Claude Code's own MCP tool timeout. Our endpoint
   holds the POST open for the job's whole timeout, up to a day.

## Findings

### new-1. An unknown `run` answer does not name its job

What happened: "Hosts" says "An unknown answer names the job", and its late end comes later as
a message. `Jobs.run/6` answers `{:unknown, :dropped}`, `{:unknown, :no_exit}` and `{:unknown,
{:timeout, …}}` without the id. The brief says to answer as `Jobs` does, so `run` passes these
through. An agent then gets a late end for `mcp-<n>` and has nothing to match it to. Why: the
`Jobs` caller picked the id, so `Jobs` had no reason to repeat it. `MCP` picks it here, and the
agent never sees it. What the design should change: say whether `run`'s unknown answers carry
`job: "mcp-<n>"`. The simplest version: `MCP` adds the job id to every `run` answer, as
`%{job: id, …}`. Then the answer's shape is no longer exactly `Jobs`'.

### new-2. `run`'s cap is a constant

What happened: the cap on `timeout` is a day, set in `MCP`. Nothing in the design names a
value. What the design should change: name the cap, or make it an option of `MCP` per
instance. A day is the bound of "a job the caller forgot still ends".

### new-3. Job ids are unique only within one `MCP`

What happened: the job id is `mcp-<call id>`, and the call id comes from that `MCP`'s own
table. Two `MCP` instances sharing one `Jobs` would make the same ids. Why: the brief names the
id's form. What the design should change: nothing, if each `MCP` has its own `Jobs`. If they
may share one, the id needs a part per instance.
