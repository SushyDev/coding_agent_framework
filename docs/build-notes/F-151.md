# F-151: what the first end-to-end run fixed on the spot

The first end-to-end run (`docs/e2e.md`, 18 Nov 2026, on the real Claude Code 2.1.322 with two
accounts and a person watching) met three faults that stopped it; each was fixed during the run,
so the run could go on, and is landed here with a test.

## What was built

- **The launch passes a CA bundle.** Every interactive start exited at once: Claude Code could
  not reach the API (`UNABLE_TO_GET_ISSUER_CERT_LOCALLY`). Node reads its own CA bundle, and a
  machine whose certificates come from devenv or Nix has them in none of the places it looks.
  `ClaudeCLI` now takes `:ca` in the launch env (a map of variable name to absolute path, checked)
  and passes it on, sorted, after the four variables a session needs. The library reads nothing
  from its own environment; the example app gives what devenv sets (`NODE_EXTRA_CA_CERTS`,
  `NIX_SSL_CERT_FILE`, `SSL_CERT_FILE`).
- **A name whose start never ran can start again.** `Mains.free/3` took only a declared row; a
  main session's row left `stopped` or `refused` with no session id (nothing to resume) now
  counts as free for its own project.
- **An unknown main session's screen is read again.** A start that met a screen `Screen` does
  not read (Claude Code's first run on a new account) went `unknown`, and the trust dialog after
  it was never seen. `Sessions` now reads an unknown main session's pane at a settle and in its
  look loop, so a startup dialog that comes later becomes the row's.

## What was measured

The run passed step 1 (the clone) and step 2 (a main session; the person answered its trust
dialog from the console), and step 4 in part (an interactive delegate's brief as its first turn,
its report into the main session through the waiter, after a person's prompt). It stopped there:
three faults break delivery itself, and the run is to be done again once they are fixed.

## Findings

### new-1. A headless delegate never starts

The real release writes `system`/`init` only after it reads its first line, and the start waits
for the init before the brief goes in. F-152 takes it.

### new-2. A `launch` delivery is never settled, so every interactive start gets its brief twice

Both briefs of the run went in by `launch` as the first turn and again by the waiter after it,
with the same uuid; `Mailbox` recorded them as delivered `via waiter`. A `launch` row is not
settled from the transcript's first user line.

### new-3. `Screen` cannot read a real main session's screen

The typed write to a main session with no waiter answered `screen unrecognized`: the viewer's pane
is far wider than the 120x40 fixtures, with a Remote Control footer and notices no fixture has.

### new-4. Claude Code's first run on a new account is a screen nothing reads

Its onboarding (a theme picker and more) came before the trust dialog on each new account.

### new-5. Smaller findings of the run

The console's `attach` prints `-t =name` unquoted (zsh expands it); IEx's interrupt runs the
console's start again and stops the VM; a delegate stuck `starting` cannot be stopped (F-152);
`agents` reads `unread` for running interactive sessions; a main session whose delegate's start
failed can never end (`end_main` refused while that delegate is `stopped`, and nothing ends it).
The fault ledger listed every failed start with its reason.
