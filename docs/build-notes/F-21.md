# F-21: a session's start and its adoption after a restart, in the model

## What was built

- **`model/tla/Start.tla`**, a spec of its own rather than more of `Delegate.tla`. The start is
  `Sessions`' protocol: every session runs it, parent or delegate, and a resume too. It shares
  nothing with a report's path but the fact that a delegate exists. Inside `Delegate.tla` its
  variables would multiply that spec's states with every report's, and the start's invariants
  would read next to ones they do not touch. `Delegate.tla`'s one `StartAsked` step now stands
  for this spec, and its header still says so.
- Steps: `RowWritten` (the row first, as starting), `Held` (dtach: held, refused, or unknown
  with nothing held), `ViewerOpened`, `FileWritten` (at any time, perhaps late), `Tick` (the
  start's wall-clock deadline passes), `StartDecided` (running, or unknown past the deadline),
  `Adopt` after a restart (running; past the deadline, orphan for a live socket and refused for
  a dead one), `ReRead` of an unknown row, and a stop: `StopAsked`, `StopSettled`,
  `StopTimedOut`, `Kill`. `FrameworkDies` may come between any two steps and clears the calls
  under way; `ForeignStarts` is another program taking a freed pid.
- Invariants: `NoHeldWithoutRow`, `RowEndsOnce`, `KillsOwnOnly`, `NotGivenUpEarly` (a process
  that wrote its file before the deadline is never made an orphan or refused); the step
  property `RunningOnlyIfLive`. Liveness: `StartingSettles`, `UnknownSettles`.
- Six `Break` values, each with a configuration TLC fails: `DecideEarly`, `DropOrphan`,
  `SettleByPid`, `KillByPid`, `HoldFirst` (the process held before its row), `NoReRead`.
- Fast configurations `Start_Restarts` and `Start_TwoSessions`; `slow/Start_Large.cfg`.
  `bin/check-model` needed no change. `READING.md` gains a section on `Start.tla`.

## What I ran into

- Two names with a foreign pid and one restart took 123 s, past the gate's 30 s. The fast
  two-name configuration has no foreign pid; pid reuse is checked with one name, and with two
  in the slow configuration.
- "No row says running without a live process its file names" cannot be a state invariant: a
  process may exit at any moment before anything reads it. It is checked on the step that
  writes `running`.
- A first run of several configurations in one `devenv shell -- bash -c` printed nothing for
  ten minutes; I ended it by its pid and ran each configuration in its own `devenv shell`.

## Findings

Each of new-1 to new-7 is a place where `lib/coding_agent_framework/sessions.ex` does not do
what `Start.tla` checks. The code was not changed.

### new-1. The adoption decides at once, before the start's deadline

What happened: `handle_continue(:adopt, …)` reads each starting row once and, unless it is
confirmed, writes `refused{interrupted}`. `Break_Start_DecideEarly` is this: a slow process
that then writes its file in time is given up.

Why: the row keeps `started_at` but not the start's timeout, and the call's deadline is
monotonic time, which a restarted VM cannot compare. So a restarted `Sessions` cannot know
the deadline.

What the design should change: the row keeps its deadline in wall-clock time, and the
adoption reads a starting row again until that deadline before it decides, without blocking
the process's other calls.

### new-2. A live socket with no file becomes `refused`, not an orphan row

What happened: the adoption ends every unconfirmed starting row as refused, live socket or
not. Its process runs on with no row that has not ended. `Break_Start_DropOrphan` fails
`NoHeldWithoutRow` this way.

What the design should change: nothing; the code lacks the `orphan` status the design names.

### new-3. A failed read is taken as a dead socket

What happened: `confirm/2` returns `{:not_yet, other}` for every miss: a socket the `Holder`
could not read, a `Registry` that failed or is unread, an account with no registry. The
adoption then refuses the row as if its socket were dead.

What the design should change: say that an adoption whose reads fail leaves the row starting
(or unknown) for the next read, and decides refused only on a socket read as dead.

### new-4. A stopping row is not settled after a restart

What happened: only starting rows are read at boot. A restart in the middle of a stop leaves
`stopping` forever. `StopSettled` with no stop under way settles it by pid and start time.
The in-call check already uses `{pid, proc_start}` (`Liveness`, `:gone` or `:replaced`), as
the spec does.

What the design should change: nothing; it is not built.

### new-5. An unknown row is never read again

What happened: a start or stop that answered unknown stays unknown, even after its process
wrote its file or exited. `Break_Start_NoReRead` fails `UnknownSettles` this way.

What the design should change: nothing; it is not built. The code should read unknown rows
at each `Registry` read, which needs `Sessions` to be given the `Registry`'s cue (F-17 new-5).

### new-6. A new start may take the name of an unknown row whose process lives

What happened: `free/1` counts `unknown` as ended, and `Table.starting/2` writes the new row
over the old one, clearing its pid. The old process, perhaps alive, then has no row; the new
hold meets its live socket. The spec lets a start begin only over `none`, `stopped` or
`refused`.

What the design should change: say that a name whose row is unknown or orphan is not free
until a read settles it.

### new-7. A hold that answers unknown ends the start at once

What happened: when `Holder.hold/4` answers unknown, the code writes the row unknown and
answers, though a process may have started. The spec waits for the file until the deadline
either way, so a process that did start is confirmed by the same call.

What the design should change: say that a start whose hold answered unknown waits for its file
like any other start. With new-5 built, the row would at least reach running later.

### new-8. The design says `Delegate.tla` gains the start

What happened: the design's delegate protocol says "`Delegate.tla` leaves the start abstract;
it gains the start and its adoption before `Delegates` is built". The start is now its own
spec, `Start.tla`, for the reasons under "What was built".

What the design should change: name `Start.tla` there, and add it to the list of specs in
"The model", between `Agent.tla` and `Move.tla` or beside `Delegate.tla`.

### new-9. Nothing in the code kills a session's process

What happened: `KillsOwnOnly` checks a kill by pid and start time, but `Sessions` never kills:
a stop types `/exit` and waits. The invariant holds in the code because nothing kills.

What the design should change: say who ends a process that does not exit on `/exit`, or an
orphan's (`Recoveries`), and that it kills by the row's pid and start time; the spec already
checks that rule.
