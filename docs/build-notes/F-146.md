# F-146: run the example app for real: a config, an operator console, an end-to-end script

The design's readiness step is one run of the example app against the real Claude Code, with a
person watching. Nothing ran `caf_example` outside its tests. This unit makes that run possible
and repeatable; it does not make the run itself, and no test or step of it started the real
Claude Code.

## What was built

- **The config file** (`Example.ConfigFile`): one JSON object, read and checked whole into
  `Example.Config` before anything starts: the home, the accounts, the ports, the projects
  (`origin`, `trunk`, `branches`, `cap`, and optionally `mains`, `setup`, `setup_timeout`,
  `env`), the `Scheduler`'s `resources`, `lease` and `job_lease`, the launch (`claude`,
  `model`, `home`, `path`, `term`, `lang`), `instance`, `operator` and `interval`. A key it does
  not know is refused, so a misspelled key never falls back to a default. Each refusal names
  its key as a dotted path (`{"projects.demo.cap", :missing}`), or the file, the JSON, or the
  `CAF_*` variables unset. The main session names are checked across projects (once each, never
  `framework` or the operator's), each setup program must be absolute, every unit a lease asks
  for must name a declared resource, and `land:<project>` is the app's. Programs are devenv's,
  from the environment the caller hands in, never `Application.get_env`.
- **The console** (`Example.Console`), one module of short functions over the operator's
  tools: `agents`, `dialogs`, `answer_dialog`, `start_main`, `end_main`, `start_delegate`,
  `run_delegate` (it waits in a process of its own and prints the report when it comes),
  `message`, `status` (a message's status, transport, pointer file and reply), `look`,
  `answer_request` (a delegate's held permission), `stop_delegate`, `asks`, `answer_ask`,
  `move`, `leases`, `faults`, `checkout` and `attach` (the command that opens a viewer). Each
  acts through `Operator` or `MCP.operate/3`, or reads through a part's own functions
  (`Sessions.Agents`, `Mailbox`, `Scheduler`, `Acts`, `Mains`), and prints a short plain
  reading. It holds no global state: `start/2` answers the running app, which every function
  takes first.
- **`Example.Run`**: the unlinked process that starts the tree and keeps it for the console, so
  an error typed in the shell never takes the tree down; it traps the tree's exit.
- **`bin/caf-example <config>`**: runs itself through `devenv shell` outside devenv, then `iex
  --dot-iex apps/caf_example/console.iex.exs -S mix run`, which starts the app as `caf` with the
  console imported, or ends with status 2 on a refused config.
- **`bin/caf-login [--check] <home> <account>`**: Claude Code's own `claude auth login` (or
  `auth status --text`) with `CLAUDE_CONFIG_DIR` set to `<home>/accounts/<account>/claude`,
  the updater off, and nothing of a Claude Code session it was typed in (`CLAUDECODE`,
  `CLAUDE_CODE_*`, `TMUX`) passed on. It refuses a relative home, a name that is no account's,
  and the default `~/.claude`.
- **`docs/e2e.md`**: the run in eleven steps (preparing, then ten), each with what to type,
  what to watch and what counts as passed, for the brief's list: the clone, a main session
  whose trust dialog the console answers, a headless delegate's report into the idle main
  session by the waiter, an interactive delegate, an ask, a job under a lease, a move to the
  second account and back, a restart in the middle of a delegate's run, a message by its
  pointer (right after the restart, which cut the waiter), and `end_main`.
- **Tests** (`ConsoleTest`, with the headless stand-in): a config file read whole; nineteen
  refusals, each naming its key, a missing file and an unset program; the console in the test
  VM starting a delegate, messaging it, the operator's `run_delegate` printing its report,
  leases and faults; `bin/caf-example` started on a config, through every reading to `end_main`
  and an exit with status 0; a refused config ending it with status 2; `bin/caf-login`'s
  refusals.
- **Docs**: `README.md` ("Running the example app", Status), `docs/design.md` (the example
  app's config file and console; item 15's login).

## What I ran into

- The console first opened its reader of the agent rows before the tree had made the home, and
  SQLite could not open `caf.db`; it now opens it after the tree.
- IEx reads a pipe as its input when the shell is not a terminal: the script test writes
  commands to the port and waits on each reading, with the prompts between them.
- To see what the console prints from the process `run_delegate` waits in, the in-VM test sets
  its own group leader to a `StringIO`, which a spawned process inherits.
- `ExampleTest` (not changed here) sometimes prints `erl_child_setup: failed with error 32 on
  line 284` and passes: a port's program that went first, the VM's helper then writing to its
  closed pipe. `ConsoleTest` run three times alone never printed it. Not new in this unit.
- The first `devenv test` failed in `MainsTest` ("the checkout is made once, whole, and pulled
  after a landing only while clean", `mains_test.exs:153`): the test's own `git commit` in the
  checkout met `index.lock`, taken by `Mains`' read of the checkout on its interval. Not this
  unit's code (`caf_mains` is unchanged here); the test should wait for a read to end, or
  commit in a clone, before it commits. Reported, not fixed.
- Other worktrees ran their gates on the same machine during this unit's, so its times were
  taken under load.
- Claude Code 2.1.322's own login is `claude auth login` (`--claudeai`, `--console`, `--sso`,
  `--email`), and `claude auth status --text` reads it back; both read `CLAUDE_CONFIG_DIR`.
  Read from `claude --help` with a scratch config directory, as `check-versions` runs
  `--version`; no session was started.

## Findings

### new-1. A new home can start no session

What happened: `start_main` and `start_delegate` pick the account with the most allowance left
(`Usage.pick/4`), which refuses `:none_known` while no account has a reading, and an account has
no reading until a session on it draws its status line. On a new home nothing has run, so every
start is refused, and the framework can never start the session that would give the first
reading. The example's tests write a reading by hand before they start. Why: "Allowance" says
`pick` never guesses past the known readings, while "A lease" says an account with no reading
has room; the two rules were written for an account that ran before. What I did: `docs/e2e.md`'s
step 0.4 writes each account a reading whose week has reset (0 %, marked assumed), which the
first status line replaces. What the design should change: an account with no reading counts
for `pick` as assumed at 0 %, as a reset week does, after any account at the same share with a
current reading; so a new home starts on its first account, and the reading follows.

### new-2. A restart leaves the held sessions with the old hook secret

What happened: the example app makes the hooks' secret once per start and writes it into each
account's settings; `Intake.Plug` refuses any other with 401. A session held across a restart
was started with the settings of the earlier start, and its merged settings file (`--settings`)
is written only at its start or resume. Unless Claude Code reads that file again when it
changes, which nothing here has measured, every hook it posts after the restart is refused: its
`Stop` and `SessionEnd` events, its permission requests (shown on the screen only), and its
waiter, so every delivery to it after a restart is typed. Why: a held session outlives the
framework's start, and the secret does not. What I did: nothing in the code; `docs/e2e.md`'s
step 9 asks the run to record whether a waiter came back after the restart. What the design
should change: keep the secret per home (written once under the home, readable only by its
user) rather than per start, or say that a session held across a restart has no hooks until its
next resume.

### new-3. A held session's Keychain read needs `security` on its PATH, not `USER`

What happened: item 15 names `USER` and `security` for Keychain reads in held processes. The
pinned release's bundle (2.1.322, read as text, not run) names the Keychain account by `USER`,
else the OS user name, and runs `security` through `PATH`. `env -i` keeps no `USER`, so the OS
user name stands in. Why: `ClaudeCLI` keeps only `HOME`, `PATH`, `TERM` and `LANG`. What I did:
the config file's default launch `path` is `/usr/bin:/bin:/usr/sbin:/sbin`, which holds macOS's
`security`. What the design should change: item 15 keeps `security` on the launch's `PATH` and
drops `USER`; each pinned release's check confirms both from a held session's login.

### new-4. The app cannot read the text of a reply to the operator

What happened: "Agents working together" says the app reads the reply to the operator's
message by its id (`Mailbox.reply/2`), but `reply/2` and `status/3` answer the row's status,
kind and transport, not its text. The console's `status/2` shows that a reply came and where
it is, not what it says; `look/2` shows it in the agent's transcript. Why: both answer through
the one view of a row that `status/3` gives. What I did: nothing. What the design should change:
`reply/2` answers the reply's text too.

### new-5. The operator cannot answer a main session's permission request

What happened: the operator's `answer` is a fix through its target's parent, and a main session
has none, so `answer` on a main session answers `{:not_built, :main_fix}`, as `resume` does
(F-143's new-1). In the run, a main session's request to use a `caf` tool or `Bash` is answered
by the person on its screen. Why: the main session's fixes wait for `Mains`. What I did: the
console's `answer_request` says it is for a delegate, and `docs/e2e.md` sends the person to the
main session's screen. What the design should change: route the operator's `answer` of a main
session's held `PermissionRequest` to `Intake.answer/4` under its claim, as an interactive
delegate's is.
