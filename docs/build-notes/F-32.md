# F-32: MuonTrap for `Shell`, evaluated; it does not fit, so `Shell` is unchanged

The unit asked `Shell` to run every command under MuonTrap, so that nothing it starts outlives
a timeout or the VM, while a held agent still outlives the framework. The evaluation shows
MuonTrap does not do the first on macOS. Per the brief, nothing was built past the tests that
show it.

## Evaluation

MuonTrap 2.0.1, the newest stable release on Hex (2026-10-06). Sources are its package as
fetched into `deps/muontrap`, by file and line.

**How it runs a command.** `MuonTrap.cmd/3` opens a port on its own port program,
`priv/muontrap`, with the command after `--` (`lib/muontrap/port.ex:29`, `:80`). The port
program forks and execs the command as its only child (`c_src/muontrap.c:172`, `fork_exec`).
It never calls `setpgid`, `setsid` or `killpg`: the command stays in the VM's process group,
and there is no group of MuonTrap's own to kill.

**On a timeout, and when its owner dies.** On a timeout, `MuonTrap.cmd/3` closes the port and
returns `{output, :timeout}` at once (`port.ex:58`). When the owner dies, the VM closes the
port. Either way the port program sees its stdin close (`muontrap.c:865`) and signals its one
child: SIGTERM, then SIGKILL after `:delay_to_sigkill` (500 ms by default) (`muontrap.c:628`,
`kill_child_nicely`, called at `:1164`).

**cgroups, Linux only.** With `:cgroup_base` or `:cgroup_path`, the child is moved into a new
cgroup before exec (`muontrap.c:184`), and after the child ends, every process still in that
cgroup is killed (`muontrap.c:589`, `cleanup_all_children`, called at `:1168`). This is the only
way MuonTrap reaches a child's own children. The README says so: it "kills OS processes if the
Elixir process running them crashes and if you're running on Linux, it can use cgroups".

**On macOS** there are no cgroups, so MuonTrap ends only the program it started.

Measured on this laptop (aarch64-darwin), with three tests on MuonTrap 2.0.1 (not kept; see
"What was built"):

| Run | The program (`sh`) | Its child (`sleep 60 &`, then `wait`) |
|---|---|---|
| MuonTrap, past its timeout | ended | **still running** |
| MuonTrap, owner killed | ended | **still running** |
| Plain port, owner killed (`exec sleep`) | **still running** | none |
| MuonTrap, owner killed (`exec sleep`) | ended | none |

`Shell` today kills the program by its pid on a timeout, which ends `sh` and leaves its child
too. So MuonTrap gains one thing: the program ends when its owner or the VM dies. It does not
gain what the unit was for: a child the program starts outlives a timeout and the VM under
both.

**dtach escapes.** `dtach -n`, run through MuonTrap with `Holder.hold_argv/4`'s command, returns
0 and its held stand-in keeps running after the run and its owner have ended. dtach's master
forks, has parent pid 1 and is its own process group leader (seen with `ps -o pid,ppid,pgid`),
so it is not MuonTrap's child, and MuonTrap would not have signaled it. On Linux with a
cgroup, it would not escape: the master stays in the cgroup, and MuonTrap kills the cgroup as
soon as `dtach -n` returns (see new-2).

**Build.** MuonTrap ships no precompiled port program. Its package holds `c_src/muontrap.c`
and a `Makefile`, and builds them with `elixir_make` at `mix compile` (`mix.exs:22`, `:76`).
There is no checksum file because nothing is downloaded. `mix.lock` pins the Hex tarball,
C source included (outer checksum `4504655c…`). In `devenv shell`, the build uses the stdenv's
clang 21.1.8 and GNU make 4.4.1, which `devenv.lock` already pins, so `devenv.nix` needed no
compiler. The result is a 54 KB arm64 Mach-O that links only `libSystem`. Any architecture
builds the same way. A host app that builds outside such a shell needs a C compiler and `make`.
See new-1.

**Over ssh.** MuonTrap would wrap this machine's `ssh` and end only that `ssh`. With
`BatchMode` and no terminal, the remote shell gets no SIGHUP. The remote command keeps running
until it writes to its closed output. Ending a remote run needs the remote host's own kill,
whichever wrapper runs here.

## What was built

- This evaluation. The builder's three tests (MuonTrap ends its program when its owner dies and
  a plain port does not; a program's child outlives MuonTrap's timeout and its owner's death; a
  hold through MuonTrap outlives the run) were written with `{:muontrap, "~> 2.0", only:
  :test}`. The main agent took them and the dependency out when landing: a test-only C build in
  every checkout, to show what MuonTrap does not do, is not worth keeping. They are in the
  branch's first commit, `1bdf238`, if a later unit adopts MuonTrap.
- `Shell`, `Holder`, `devenv.nix` and `docs/design.md` are unchanged.

## What I ran into

- One `gate-test` run failed while MuonTrap's timeout was 300 ms. Under load, the timeout passed
  before `sh` wrote its pids. The test now gives 2 s, and the stand-ins sleep 60 s, so a
  child left by a failed run ends on its own.
- `MuonTrap.cmd/3` raises `ErlangError` `:enoent` for a missing program. It checks the path
  before opening the port. A `Shell` on MuonTrap would map that to `{:refused, {:cannot_start,
  …}}` as it does now.
- `erl_child_setup: failed with error 32` printed once in six `gate-test` runs, and the run
  passed (F-25 new-5).

## Findings

### new-1. MuonTrap ships no precompiled port program

What happened: the brief expected a precompiled port program fetched per architecture with a
pinned checksum. MuonTrap 2.0.1 compiles `c_src/muontrap.c` with `elixir_make` on every build.

Why: its package lists only C sources and a `Makefile`, and it does not use `cc_precompiler`.

What I did: built it with the clang and make that `devenv.lock` already pins, adding nothing
to `devenv.nix`, and only for tests.

What the design should change: if MuonTrap is adopted, the constraints should say a host app
needs a C compiler and `make` to build the framework. Tests and gates already have them in
`devenv shell`.

### new-2. A cgroup would kill a held agent

What happened: with cgroups, MuonTrap kills every process left in its cgroup when its program
exits. `dtach -n` exits as soon as its master has forked, and the master stays in the cgroup.

Why: `setsid` leaves a process group, not a cgroup.

What I did: nothing; no cgroup options are passed anywhere.

What the design should change: the dtach rules could say a hold never runs under a cgroup (or
any wrapper that kills what its program leaves behind), since a held agent must outlive the
framework.

### new-3. Ending a program's children needs a process group, which neither a port nor MuonTrap gives

What happened: the program's own child outlived `Shell`'s timeout and MuonTrap's timeout and
owner death alike. On macOS, ending a whole tree needs the program to start in a new process
group and the kill to signal that group. OTP's `open_port/2` cannot set one, and MuonTrap does
not.

Why: MuonTrap leaves descendants to cgroups, which only Linux has.

What I did: kept `Shell` on its plain port and its kill by pid.

What the design should change (recommendation): keep `Shell` as it is for now. Then choose one:
(a) ask MuonTrap upstream to `setpgid(0, 0)` in its child and `killpg` the group on cleanup
when no cgroup is set (dtach still escapes, since its master calls `setsid`), and adopt it when
released; or (b) adopt MuonTrap 2.0.1 now for the one gain it gives: a program ends with its
owner and the VM. Its moduledoc would then say that a program's own children are not ended on
macOS. Option (a) gives what this unit asked for. Option (b) is a smaller step that is safe
for holds.
