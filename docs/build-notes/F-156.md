# F-156: `bin/caf-import`, imported conversations as stopped main rows; a checkout's directory name

An app moves its existing Claude Code conversations onto the framework at once, on a new host.
Its agents' `CLAUDE.md` files import sibling repositories' files by relative path, so each
checkout is now named by its repository; and its start-or-resume must resume an imported
conversation, so each named one becomes a stopped main session's row. No test or step of this
unit started the real Claude Code.

## What was built

- **A checkout's directory name.** `Mains.project/3` fills in `dir`, the project's own `dir:`
  or by default its repository's name (`Checkout.dir_name/1`: the origin's last path part,
  without `.git`), and `repo` is `<home>/checkouts/<dir>`; its clone is made at
  `.<dir>.clone`. A `dir` that is not one plain path component is refused `{:bad, :dir}`. Two
  projects naming one directory are refused at config, `{:bad, :projects, {:same_dir, dir,
  names}}` (`Config.new/1`), and by `Mains` at its start, `{:same_dir, dir, names}`
  (`Checkout.same_dir/1`). The example app's config file takes `dir`.
- **A checkout under the project's name**, which an earlier build made, is renamed once
  (`Mains.Rename`, modeled first in `Checkout.tla`). While the project's checkout is not at its
  new path and one is at `<home>/checkouts/<project>` (no other project's directory), each read
  first asks whether any agent row of the project, or any whose cwd is the old checkout, may
  hold a process (`Agents.free?/1`). If one may, the checkout's state is `old` with the names
  as its reason, the rename waits for the next read, nothing clones beside it, and a start in
  it is refused `{:checkout, "old"}`. Otherwise, in a task: each account's `projects/<encoded
  old cwd>/` and the home's `memory/<encoded old cwd>/` go to the new path's, entry by entry
  with `rename` and never over one (`{:both, path}` refuses the whole rename before anything
  moves), the account's memory link dropped for `Sessions.Memory.link/3` to make again; then
  the checkout itself, last; then `git worktree repair` of every worktree whose `.git` names a
  git directory that is gone. Every read also runs that repair while one is stale, so a restart
  between the rename and the repair still repairs. The rename is an act in `Acts` (`rename`,
  target `checkout:<project>`): `verified` with its paths, or `failed` once for each new reason
  it waited for. `Mains` takes `acts:`; the surface's tree hands it the instance's.
- **`bin/caf-import`** (`Mains.Import`, run by `mix run --no-start` in devenv): parses the
  decided arguments, then, with nothing copied on any refusal:
  - reads each mapped project's checkout path from `Mains`' `checkouts` rows in
    `<home>/caf.db`, never writing it, so the app must have started once on the host
    (`{:no_app_start, path}`, `{:no_checkout, project}`); the rows' one host is the one whose
    agent rows it reads;
  - is refused `{:running, names}` while any agent row of the account may hold a process;
  - plans every copy: each `projects/<encoded old cwd>/<id>.jsonl` with the `<id>/` directory
    beside it and `session-env/<id>` (what `Mover` copies), into the account's `projects/<encoded
    checkout>/`; each file of that cwd's `memory/` into `Sessions.Memory.dir(home, checkout)`;
    `settings.json`, `CLAUDE.md`, `agents/`, `commands/` and `skills/` where the account has
    none. `.credentials.json` and `.claude.json` are never copied. A conversation file there
    already and different, or a memory file that differs (also between two old cwds mapped to
    one project), refuses `{:conflicts, paths}`; a `--name` for a session not found, a name
    given twice or taken by another session's earlier import, and a `--meta` with no `--name`
    are refused by name;
  - copies each item whole under a temporary name and renames it, then writes the session's
    manifest, `<home>/imports/<account>/<id>.json` (its id, account, project, old and new cwd,
    name and meta), last. A second run copies nothing for a session with a manifest and says
    `imported already`. Exit status 0, 2 (usage), 3 (refused), 1 (a copy failed part way).
- **Imported conversations as rows.** I picked the step at the app's start from the manifest:
  `Mains`, before it declares the config's main sessions (so a declared name an import took
  is `stopped`, not `declared`), reads `Import.manifest/1` and calls the new
  `Sessions.import_main/4` for each named one, which writes the row of kind `main`, `stopped`,
  reason `imported`, role `parent`, with its project, account, session id, checkout and `meta`
  (`Sessions.Table.imported/4`), over no row or a declared one of that project, `{:ok,
  :already}` for a row that holds that session, else `{:refused, {:exists, status}}`. An import
  that wrote a row is an act `import` verified; one refused is an act `failed`, at each start
  until a person sees to it. Why this and not a call through the app's node: the embedding app
  runs no distributed node and the framework names no process, so a script could reach neither
  without new machinery in every app; an import on a new host is made before the app's
  sessions ever run, which the start step serves at once; and `Sessions` stays the rows' one
  writer, written only in its own process.
- **Its first resume.** `start_main` of an imported name is refused `{:running, name}`, as for
  any stopped main session with a session to resume, and `resume_main/3` takes it up through
  the `Scheduler` and the startup dialogs as any resume. Such a row keeps no model, and a
  resume dropped the launch's model to take the row's: `Mains` now keeps the app's model when
  the row has none (a resume of a row with a model is as before).
- **The model.** `Checkout.tla`: constant `Old`; variables `old`, `inOld` (a session's process
  may live in it), `links`, and the ghosts `moved` and `two`; steps `OldEnds`, `RenameOld`
  (only while no session may run there, before any clone) and `Repair` (each read while a link
  is stale); `CloneStart` waits while the old checkout is there; `Use` needs the links whole.
  New properties `OneCheckout` and `NoSessionMoved`; `Made` and `CaughtUp` hold once no session
  holds the old checkout. `Checkout_Old` checks it; `Break_Checkout_RenameWhileRunning` fails
  `NoSessionMoved`, `Break_Checkout_CloneBesideOld` fails `OneCheckout`,
  `Break_Checkout_NoRepair` fails `WholeCheckout`. Every earlier configuration sets `Old =
  FALSE`, so its state space is as before. The imported row's first resume is not a new
  protocol: the row is written before `Mains` answers its start, and its resume is the
  modeled one.
- **Tests** (`mains_test.exs`): an import of a fixture config directory (two conversations
  under two old cwds, two projects with their own checkout directories, memory, settings, a
  login file) copies each where `--resume` finds it, leaves the login, says `imported already`
  the second time, becomes two stopped rows at `Mains`' next start, is refused a fresh start
  and resumes by name in the right checkout with its memory, and a third import while it runs is
  refused `{:running, ["app-epic"]}`; a checkout under the project's name, with a worktree, a
  conversation and memory, waits while a session on a dialog holds it (`old`, its name in the
  reason, a start refused), then renames once it ended, its conversation and memory moved, its
  memory link dropped, the worktree working, and the acts failed then verified; two projects in
  one directory are refused by `Mains` and by `Config.new/1` (`config_test.exs`). The import's
  `parse/1` and the checkout's naming functions are doctests.
- **Docs**: `docs/design.md` ("Concepts", "Main sessions": the directory, the rename, the
  import), `README.md` (Status, the apps' chart, step 4 of the example), and the moduledocs of
  `Mains`, `Mains.Checkout`, `Mains.Rename`, `Mains.Import`, `Sessions.import_main/4`,
  `Sessions.Table.imported/4` and `Config`.

## What was measured

- `bin/caf-import` run by hand through devenv against a home with no `caf.db`: it compiled,
  printed `refused: {:no_app_start, …}` and ended with status 3; the arguments after `--`
  reach `System.argv/0` as given.
- Not measured: the real Claude Code resuming a conversation copied under another cwd's
  directory (new-3).

## What I ran into

- TLC found `Made` violated at the initial state once it read `<>(~inOld) => <>[](final =
  "made")`, a property that holds there; written `<>[](~inOld) => …`, the same here since a
  session never comes back to the old checkout, it passes. I did not find why TLC read the
  first form so.
- `CaughtUp` failed `Checkout_Old` on a run where a session holds the old checkout for ever:
  nothing pulls it, by design, so the property now holds once no session holds it.
- A resume of an imported row was refused `{:missing, :model}`: see "Its first resume" above.
- Running one app's tests from its own directory fails on the umbrella's `only: :test` deps;
  `mix test apps/<app>/test/<file>` from the root works.

## Findings

### new-1. A resume picks its account by allowance, but the conversation is on one account

What happened: `Mains.resume_main/3` resumes on the account with the most allowance left
(`pick/1`), while a stopped main session's conversation, and an imported one's, is only in the
account it ran on, or was imported into. With two accounts, the resume may run `--resume <id>`
where Claude Code has no such conversation. Why: a resume was built when a move was the only
way between accounts, and the tests have one account. What I did: nothing; the imported row
keeps its account, as any row does. What the design should change: say that a resume runs on
the row's account, or that one on another account copies the conversation first as a move
does (its copy step, `Mover`'s `copied/2`).

### new-2. The import finds the app's tables by the surface's file name

What happened: `Mains.Import` reads `<home>/caf.db`, the name `CodingAgentFramework`'s tree
gives its tables, and takes the workstation's host name from the checkouts rows it finds there.
Why: the decided arguments name the home, not the app's config. What I did: so, refused by
name when the file or a row is missing. What the design should change: confirm, or give the
script the database path (`--db`), for an app that names its files otherwise.

### new-3. Claude Code's resume of a conversation whose lines name another cwd is not measured

What happened: a copied transcript's lines keep the old `cwd` field. Why: no step starts the
real Claude Code. What I did: copied the files unchanged, as `Mover` does between accounts.
What the design should change: the release check resumes one copied conversation under a new
checkout's directory and records whether it reads whole, and whether its first turn meets the
trust and imports dialogs as a new start does.

### new-4. "A session of that account runs" is read from the agent rows only

What happened: the import is refused while an agent row of the account may hold a process.
A Claude Code the person runs by hand on that config directory, or still on the source one
(whose transcript it may be appending), is not a row. What I did: read the rows only. What the
design should change: say whether the import also reads the account's and the source's
`sessions/<pid>.json` files with a live pid, as the `Registry` does, and refuses on one.

### new-5. Which of the person's settings an import copies

What happened: the brief says "settings and memory". What I did: `settings.json`, `CLAUDE.md`,
`agents/`, `commands/` and `skills/`, each whole and only where the account has none; never the
login, `.claude.json`, plugins or anything else. A `settings.json` may name paths of the old
host (hooks, `additionalDirectories`). What the design should change: name the entries, and
whether a setting that names an old path is refused, kept or rewritten.

### new-6. A rename leaves the old path in finished rows

What happened: a stopped main session's row keeps its old `cwd` until its next resume, which
runs in the new checkout; a delegate's row keeps the old `repo`. Why: `Sessions` is their one
writer, and a resume or a start writes both again. What I did: nothing more. What the design
should change: nothing, unless a view should show the new path before then.

### new-7. The script runs the framework's own repository

What happened: `bin/caf-import` runs `mix run` in this repository, compiling the umbrella, as
`bin/caf-example` does. An app that embeds the framework as a dependency calls
`CodingAgentFramework.Mains.Import.main/1` from its own release instead. What the design should
change: the packaging unit names how an app's release offers the import (a release command).

## Gates

Run with the machine's load average between 6 and 22, from other builders.

- `Checkout.tla` alone: `Checkout_Design` 526 distinct states and `Checkout_Old` 244, each in
  2 to 3 s; every `Break_Checkout_*` fails on the property it names, the three new ones
  (`RenameWhileRunning` on `NoSessionMoved`, `CloneBesideOld` on `OneCheckout`, `NoRepair` on
  `WholeCheckout`) and the five earlier ones.
- `devenv test`, three runs. The first failed in `SurfaceTest`'s checkout test, which pinned
  the old `checkouts/app` path (fixed: it reads the config's `repo`). The second failed once on
  a 60 s timeout, at load 16 to 21, in `MainsTest`'s "resume_main resumes a stopped main session
  under a lease of its own" (`start_main` waiting on its call). That test is main's and this
  unit does not change its path; the whole `mains_test.exs` then passed three times in a row.
  The third run passed every gate: versions, format, compile, deps, test (296 s), and the fast
  model set (1 281 s).
- `gate-test` three times in a row after it: no failures.
- The names check: the diff names no other company's or project's systems or people; it names
  GitHub in an example origin, as the repository did before.
