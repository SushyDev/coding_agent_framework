# F-89: `Services`, part 3: send and wait; the forward designed, not built

`Services` gains `send/5` and `wait/4`. The two design points the brief named are settled in
"Hosts" and the tools table first. The forward's design is written, but it is not built: its
life beside the service's is a protocol `Copy.tla` does not cover (see new-1).

## The design, settled

- **Send.** `Control` writes tmux panes on the workstation, and a service has no pane, so the
  table no longer says `service_send` goes through `Control`. Input goes by dtach's push mode,
  `dtach -p <socket>`, run on the service's host through `Shell` (the workstation too). One host
  shell reads the program's pid and start time, as an end does, and pushes only while they are
  still the row's, so input never reaches a program a restart put in its place. "Checked" for a
  service is: the row is `running`, the caller is the owner or the owner's parent, and that pid
  check. There is no turn and no input box. Answers: `{:ok, :sent}` once dtach handed every byte
  on; `{:refused, :not_held}` when the pid or the socket says the program is not the row's,
  and nothing went in; `{:unknown, {:send, _}}` on a drop or a timeout. Never resent.
- **Wait.** Polls the host: a whole line of the log matching a pattern (from an offset), or a
  port that listens on the host's `127.0.0.1` (`nc -z`), or the exit. The exit (the socket read
  dead) ends every wait, and the log is read after the socket in each round, so a line written
  before the exit is still found. At the timeout: `{:unknown, :timeout}`, or `{:unknown,
  :dropped}` when the last round's reads failed, as a job answers.
- **The forward.** An `ssh -N -L 127.0.0.1:<local>:127.0.0.1:<port>` with
  `ExitOnForwardFailure`, held by dtach on the workstation in the services' directory there,
  named for its service. `<local>` is the service's port unless the caller names another; a
  taken local port fails the forward's start, and so the service's start. The row reports
  `{port, local}`. The service's end ends the forward first and is done once both sockets read
  dead. A forward's socket read dead while its service runs is a loss `Recoveries` opens again
  once per state (the service's held process and the forward's open count). A workstation
  service needs no forward.

## What was built

- `Services.send/5`: the checks above, input refused when not a binary, with a NUL, or over
  64 KiB (it travels as one argument of the remote command line). One script does the pid check
  and the push.
- `Services.wait/4`: `{:line, pattern}`, `{:line, pattern, from}`, `{:port, port}` or `:exit`.
  A pattern may be a `Regex` or its source (as an MCP call would send it); a bad one is refused.
  A line answer carries the offset just after the line, so a caller waits for the next one from
  there. Rounds are 100 ms apart; each read's timeout is the time left, at most 5 s.
- `nc` is a new program name in `Programs`, needed on a host only for a port wait (a wait
  without it on that host is `{:refused, {:no_program, [:nc]}}`). devenv exports libressl's nc
  as `CAF_NC`; `TestHost.programs/0` includes it.

## Tests

`apps/caf_services/test/services_test.exs`, five new. The models do not cover send or wait, so
each is named `Send, Wait` or `Wait`:

- On `test` and on `box` (the stand-in ssh): a service that echoes each line it reads gets
  input from its owner and from the owner's parent (with a quote in it, through ssh's
  quoting), a sibling is refused, a wait finds each line and its offset, a wait for a line not
  there answers `{:unknown, :timeout}`, and a send after the stop is refused.
- The exit: the stand-in reads one line and exits; `:exit` and a line never written answer
  `{:ok, :exited}`, a line written before the exit is still found, and a send to the gone
  program is `{:refused, :not_held}`.
- A drop (the stand-in ssh's `down` file): the send answers `{:unknown, {:send, _}}` and the
  wait `{:unknown, :dropped}`; a NUL, port 0 and a bad pattern are refused.
- A port: a service runs `nc -l` on a port that was free a moment before, and a port wait ends.

No test for the forward, since it is not built. A test would stand in for `-L` as the brief
suggests: the stand-in ssh, seeing `-L a:b`, runs a relay between two local ports (an `nc -l`
piped into an `nc`), held by dtach like the real one.

## What I ran into

- A wait's last round has little time left, and a read the deadline itself cut first counted
  as a dropped connection, so a plain timeout answered `:dropped`. A read cut at the deadline
  now keeps the round before's verdict; a read cut by its own 5 s cap still counts as a drop.
- `Programs.new/2` refuses a name it does not know, so `nc` had to become a program name, not
  only a test path.

## Findings

### new-1. The forward's life beside the service's needs a model before it is built

What happened: the brief asks for the forward, and says to stop with a recommendation if its
protocol is not modeled. It is not: `Copy.tla` holds one process per service, and the forward is
a second held process whose start, loss, reopen and end interleave with the service's own
(a forward opened after the service's end began; a reopen racing a restart; an end that sees the
service dead but the forward live; a restart of the framework between the two ends). Why: each
of those is a step over time across two processes and the framework, which the design's rule
puts in `model/tla/` first. What I did: wrote the forward's design in "Hosts", marked "not built
yet", and built only send and wait. What the design should change: a unit that extends
`Copy.tla` with the forward (a variable per service: none, open, lost, ending) and checks
`ForwardOnlyWhileHeld` (no forward open once the service's end is written, past its own end),
`EndedIsEnded` over both sockets, and `ReopenOncePerState`; then a unit that builds it, with the
stand-in for `-L` above. The local port's choice (the service's port unless named, refused if
taken) needs no model.

### new-2. A forward over "the host's ssh connection" is its own ssh

What happened: the design says the forward goes "over the host's ssh connection", but `Shell`
runs one ssh per command; there is no connection per host to carry it. Why: no unit has built
one. What I did: the design now says the forward is its own `ssh -N -L`. What the design should
change: nothing now; if a connection per host is built (an ssh ControlMaster held by dtach, say),
the forward can ride it with `-O forward`, and the model of new-1 should allow that.

### new-3. A line wait from offset 0 finds lines from an earlier start

What happened: a restart appends to the same log (`>>`), so `wait(name, {:line, p}, t)` after a
restart finds the line the previous start wrote. Why: the row keeps no offset of its current
start's log. What I did: `wait` takes `from`, and a line answer carries the next offset, so a
caller who read the log first waits from its end. What the design should change: record the
log's size at each start in the row (`log_from`), and make that the default `from`, so a wait
after a restart waits for the new start's line.
