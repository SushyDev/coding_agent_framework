# F-100: `MCP`, part 6: the fix tools for delegates, under a claim

## What was built

The four fix tools of the design's table, in `CodingAgentFramework.MCP`, for a delegate target.
Each runs `Team.tla`'s claim path:

1. `Grants.may_fix?/3`: only the child's parent; a main session is refused `main_never_fixed`,
   a self-fix `no_self_fix`. This comes before the state is read, so no other agent learns it
   through a fix.
2. `Delegates.fix_state/3` reads the child's state (below).
3. `Grants.Claims.claim/6` claims that state with the caller and this start's `:start_id`
   (`ClaimTaken`). A second fix of the state is refused `{:claimed, by}` while the first is
   open and `{:already_claimed, by}` once it is settled.
4. `Delegates.fix/5` reads the state again in its own process and acts only if it is still the
   claimed one (`FixActs`); otherwise it answers `{:refused, {:moved, now}}` and nothing acts
   (`FixRefused`).
5. The state is read once more, and the claim is settled `verified` when the act answered
   `ok` and the state has moved, otherwise `not_verified`.

The tool answers `%{done: value, claim: id, settled: settle's answer}`, or the act's refusal or
unknown. A refusal before the claim (a bad argument, a bad label, a grant) writes no claim.

**The state, and which part numbers it.** `Delegates` owns the child, so `Delegates.fix_state/3`
numbers it. It reads `Stream` first (`Stream.read/2`), then builds a map from three rows:

- its own row: `id`, `status`, `resumes` and `report` (a new start of the same name has a new
  `id`; a finish, a resume or a delivered report moves the rest);
- `Stream`'s row of the process: `offset` (every event read moves it), `gone`, `ending`, and the
  sorted ids of the requests `held`;
- whether `Sessions`' row of the name has `ended` (see new-4).

`Claims` compares the map by equality. A stuck delegate writes no events, so its state holds
still and is fixed once. A working one's state moves with each event.

**The acts**, each through the part that owns it:

- `interrupt(agent)`: `Stream.interrupt/3`.
- `answer(agent, dialog, label)`: `dialog` is the `request_id` of the open `can_use_tool`
  request, and `label` is `allow` or `deny`. `MCP` checks the label before the claim. The act is
  the new `Stream.answer/5`, which maps the label to `Stream.write/4`'s `{:answer, id, :allow}` or
  `{:deny, "Your parent denied this."}` and refuses any other label as `{:bad, :label}`. The
  write's mark moves the request from `held` to `answering` at once, so a written answer settles
  `verified`.
- `resume(agent)`: when the process is gone, the row is `running`, `Sessions`' row has ended, and
  no resume was made, this is the path a cue takes (`exited/3`, then `resume/3`), which counts
  the one resume first. It answers `{:ok, :resuming}`; `Sessions` is answered later, as for a cue.
  It refuses `:resumed_once`, `:live`, `{:status, s}` or `:session_running`.
- `stop(agent)`: only once the report is `answered` (or `delivered`, once delivery is built).
  Otherwise it is refused `{:report, report}`. It then calls `Sessions.stop/4` with
  `:report_delivered`, which writes `end_session` through `Stream` and waits for the exit. That
  wait runs in its own task, which replies to the caller, so `Delegates` does not wait with it.

New functions, each with a test: `Delegates.fix_state/3` and `Delegates.fix/5`, tested through
`MCP` in `mcp_delegates_test.exs`, with the moved-state check called directly, and
`Stream.answer/5`, tested in `stream_test.exs`. `MCP` takes two new required options, `:claims`
and `:start_id`.

## Tests

`apps/caf_mcp/test/mcp_delegates_test.exs` runs a real `Delegates`, `Sessions`, `Stream` and
`Grants.Claims`, an MCP client with a token, and the headless stand-in:

- one fix per state, and never on a state that moved: only the parent may fix (a sibling is
  refused, a main session is never fixed, an unknown token is refused); a bad label writes no
  claim; `Delegates.fix/5` with a stale state is refused `{:moved, state}` and writes nothing; a
  refused resume (`live`) settles `not_verified`, and a later `stop` or `interrupt` of that state
  is refused `already_claimed`; an `answer` settles `verified`; a claim the test holds open
  refuses a `stop` as `claimed`;
- interrupt and stop: an interrupt goes in (the stand-in takes it, cancels the request and ends
  the turn), and its claim is settled one way or the other (see new-3). A stop of a delegate
  whose report is held is refused `["report", "held"]`. A stop of the delegate whose report
  `run_delegate` answered ends it (`end` is taken) and settles `verified`;
- resume: a dead delegate, after `Sessions`' row has ended and with no cue to `Delegates`, is
  resumed (`resuming`, `verified`); a second resume is refused `resumed_once`; the resumed
  process then finishes.

## What I ran into

- Each delegate holds its parent's cap until it ends, and the tests' project allows two. So
  each test uses at most two delegates and orders its fixes so that each new act finds a state
  that has moved.
- A gate run failed once: a second `resume` sent while the resumed process was still writing
  events was refused `moved`, as designed, not `resumed_once`. The test now waits for that
  process to finish first. Any fix of a working delegate can meet this, which is the claim's
  purpose; a caller that sees `moved` reads the state again.
- F-99 landed first. Its new options and tools sit beside these, and its test that used
  `interrupt` as an unknown tool now uses `start_main`, which is still unbuilt.
- `cue_until/2` in the test took the first row only. It now finds the row that satisfies the
  check, which leaves the earlier tests unchanged.

## Findings

### new-1. A wedged delegate is not resumed

What happened: the design's table says `resume` "starts a dead or wedged child again with
`--resume`". A wedged delegate's process is alive. `Sessions` refuses to start a name whose row
runs. `Delegates`' resume path waits for that row to end. `end_session` cannot go in while a
turn runs. So a wedged resume needs its live process ended first, and the design does not say
who ends it (`Recoveries`, by pid and start time?) or whether that counts as the one resume.
What I did: `resume` of a live delegate is refused `:live`, with its claim settled
`not_verified`. What the design should change: say that a wedged delegate gets `interrupt`, and
goes to a person when the interrupt does not help. Or, if `resume` should cover it, name the step
that ends the live process (`Recoveries`, by pid and start time) before the resume path, and say
whether that counts as the one resume.

### new-2. A parent's resume and the one automatic resume

What happened: `Delegates` resumes a dead delegate by itself at the next cue (`Delegate.tla`,
one resume). A parent's `resume` only gets there before that cue, and after the one resume it
is refused `:resumed_once`, though the table says "once per state". What I did: the parent's
resume takes the same path and counts against the same single resume. What the design should
change: say whether a parent's resume may go past `Delegate.tla`'s one resume (for example
after a `failed` report), and if so, what the row's status becomes.

### new-3. Whether an interrupt helped is read too early

What happened: an interrupt helps when the delegate ends its turn, and that comes as a `result`
event after the write. The single read after the act usually comes first, so an interrupt that
helped is often settled `not_verified`. The design allows no wait. What I did: settled it by
that one read, as the brief says. What the design should change: either define `verified` as
"the state had moved by the read after the act", or let the claim stay open until the next cue
that reads the delegate's state. That second option is a new mechanism, which I did not build.

### new-4. A fix of the wrong kind uses up the state

What happened: `Team.tla` derives the fix's kind from the state (`Kind(t)`: stuck → interrupt,
dead → resume, idle → stop). The tools let the caller choose the kind. A fix whose act is refused
(a `stop` of a working delegate whose report is not delivered, a `resume` of a live one) still
claims the state, so the right fix of that same state is refused `already_claimed` until the
state moves. A stuck delegate's state does not move. What I did: kept the claim before the act,
as the design orders. Argument checks (the label) come before the claim. `Sessions`' row
`ended` is part of the state, so a resume tried before `Sessions` sees the exit does not use up
the state the later resume needs. What the design should change: say whether a fix whose kind
does not fit the state (no delivered report for `stop`, a live process for `resume`) is refused
before its claim, as `Kind(t)` implies.

### new-5. `answer`'s arguments for a delegate

What happened: the table says `answer` acts "through its held hook, by label". That is a main
session's dialog, held by `Intake`. A delegate has no hook. It has a held `can_use_tool`
request with an id, and the answers are allow and deny. What I did: `dialog` is the request's
id, and `label` is `allow` or `deny`. What the design should change: give the delegate's form
in the table.

### new-6. A delegate started with `start_delegate` cannot be stopped yet

What happened: `stop` needs a delivered report. Until delivery is built (`Delegates.deliver/2`
is refused `:no_delivery`), only a report `run_delegate` answered counts as delivered. What I
did: `stop` accepts `answered` or `delivered`. What the design should change: nothing. This
ends once delivery is built.
