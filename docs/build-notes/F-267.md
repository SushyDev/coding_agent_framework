# F-267: a conversation read that does not fail on a busy store, reads from the end, and shows Claude Code's queue

## What was built

- **The store read.** `CodingAgentFramework.conversation/3` now reads the agent's row, on any
  host of the config, and the rows queued to it in one `Store.snapshot/2`: one read-only open
  and one read transaction, not one `read_only/4` per host plus one for the queue. No other
  caller's read changed.
- **Read from the end.** `Transcripts.conversation/3` with no cursor runs one shell script
  (`@ending`): the file's size from `wc`, then its last `max_bytes` bytes and the one byte
  before them, through `tail` and `head`. Of those bytes it reads every whole line and keeps
  the newest lines' entries within `limit`, a line's entries never split. It answers `next`,
  which reads forward from the last whole line as before, and `older`, which a call passes as
  `before:` to read back one block of at most `max_bytes` (and one byte) a call. An older read
  answers its own `older`, and `next` and `queue` nil. A cursor whose bytes changed, or of
  another file, now starts the file again from its end, not its start.
- **A line cut by a block's edge.** A block starts one byte before the first line it may keep,
  so a line that starts at the edge is kept whole. The bytes up to its first newline end a line
  that began before the block. They are not read here, and the older cursor ends where the
  oldest line kept begins, so the next older read has that line whole. The bytes after its
  last newline are a line not yet whole (the file's end) or, with the cursor's `skip`, the rest
  of a line too long to read. A line longer than `max_bytes` is one `unread_line` entry, once,
  with `offset` nil when read backward. The cursor keeps the first 64 bytes at its edge, so a
  rewritten file is seen, as the forward cursor keeps the 64 before its offset.
- **A call cut by a block's edge.** The newest lines are read again from the cut with the
  calls of the lines not kept as `open:`. So a kept result of a call not kept comes as a
  forward read gives it: again under its id, with its name and start. The older read gives the
  call `done: false`, and an app merges by `id`, the done one holding the result.
- **Claude Code's queue.** `Fold.queue_operation/1` is the one reading of a `queue-operation`
  line, `{op, text}`. The `waiter` transport's settle (`Transport.Waiter.seen/2`) uses it in
  place of its own match, so there is still one parser. `Fold.entries/2` folds those lines into
  `queue`: an `enqueue` adds its text, and a `dequeue` or `remove` takes the oldest entry of
  its text, or the oldest entry when it has none. At most 100 are kept. The forward cursor
  keeps the queue, as it keeps the open calls. The facade answers `queued` as the framework's
  rows, now each with `source: :framework`, then Claude Code's entries, each `%{source:
  :claude_code, text, at, offset, message}`; `message` is the uuid of a `[delivery <uuid>]`
  mark, so a row handed to the session is seen in both.

## Why (a), and what the store already did

The brief's choices were (a) a bounded busy timeout for `read_only/4`, or (b) reading the row
and the queue from the tree's memory. (b) does not fit: `Mailbox` keeps no queue in memory. It
reads `messages` from the file on each step, so the queue has no in-memory copy to read.

For (a), `read_only/4` already waits by the clock. Since F-216 every `Store.query/3` retries a
busy statement until `busy_bound/0` (2 s) has passed. `read_only/4` sets SQLite's own busy
timeout to 0 only because exqlite's handler overshoots its bound (F-215's new-2). So the
option the brief describes already exists as the store's one bound. I added no option.

I also measured a WAL reader against held locks, on this host: `read_only/4` answered the last
commit in about 85 to 90 ms with another connection inside `BEGIN IMMEDIATE`, the same inside
`BEGIN EXCLUSIVE`, and the same idle. A WAL reader does not wait for a writer. Only a lock that
shuts readers out (a file not in WAL with an exclusive lock, or WAL recovery) makes it wait.
Then it answers `{:refused, {:sqlite, :busy}}` within `busy_bound` and 500 ms. Both cases are
new tests in `caf_store`. See new-1 for what this means for the app's report.

## The model

No TLA+ spec changed. The read keeps no state between calls: the forward and older cursors
are the caller's. Each call is one bounded read of bytes that exist, and a changed file is
caught by the cursor's seam, as F-260's forward read is. Claude Code's queue is folded from
lines, as the open calls are, and nothing acts on it. `Delivery.tla` still models the waiter's
settle, which reads the same lines through the same parser.

## What was measured

- The first read of a stand-in transcript of over 4 MB (30,000 lines) with `max_bytes: 65_536`
  takes one shell run whose `head` reads 65,537 bytes, and answers the newest 20 entries. A
  stand-in `head` counts the bytes (`caf_transcripts`' "reads only its end" test).
- Paging back from the end of 120 lines, 7 entries a call in blocks of 1,500 bytes, then
  forward over 30 new lines, gives every entry once, in order.
- `caf_transcripts`: 43 tests (21 doctests), 16.8 s, at a load near 66 on 15 cores.
- `caf_surface`'s conversation test, a whole tree: 18.9 s at a load of 131.
- `gate-test`, six runs at loads of 45 to 90 on 15 cores: none passed whole. Each failed one to
  three tests, a different set each run. Each failed test passed alone: `mains_test.exs:339`,
  `:400`, `:437` and `:536` (60 s timeouts), `tree_main_test.exs:59` and `:105`,
  `console_test.exs:173`, `sessions_dialog_test.exs:270`, `surface_test.exs:730` (the tree's
  start met `{:sqlite, :busy}`), and `delegates_interactive_test.exs:382` (a 60 s timeout in
  `with_waiter`'s start, before any queue line; alone three times, and its file whole twice).
  `devenv test` failed three more the same way: `delegates_test.exs:383`, `mains_test.exs:380`
  and `:536`. `bin/check-model` passed, and the names check found nothing.

## What I ran into

- Holding the tree's own `caf.db` write lock in the surface test made the tree's writers fail
  `Store.Busy` after 2 s at a load of 66, as the store says they do. The read itself is tested
  against a held lock in `caf_store`, not by blocking a running tree.
- F-260's test read its first page from the file's start; it now reads the newest entry and
  pages back for the one before.

## Findings

### new-1. The app's busy refusal does not come from a reader meeting a write lock

What happened: the brief says `read_only/4` refuses at once when it overlaps a write. In the
code it waits up to 2 s, and a WAL reader does not meet the write lock at all (measured above).
Why: F-216 moved the busy wait into `Store.query/3`; WAL lets readers read the last commit.
What I did: made the read one snapshot, one open in place of two or more, and tested both
cases. What the design should change: find where the app's `{:refused, {:sqlite, :busy}}`
comes from before adding a mechanism. Candidates are a read during WAL recovery, after a VM
that held the file died, or the app's own call to another read path. The app's log of when it
saw the refusal would tell them apart.

### new-2. Claude Code's queue is folded only from the bytes read

What happened: a first read finds the queue only in its last `max_bytes`. An `enqueue` before
that block, still not taken, is not shown. Why: the read never folds the whole file. What I
did: documented it; a queue entry lives for seconds to one turn, so a 1 MB block normally holds
it. What the design should change: nothing, unless an app sees a long-queued text missed. Then
`Transcripts`' own fold could keep the queue per session, as it keeps the offset.

### new-3. Subagents are still read forward from their start

What happened: with `subagents: true` the first read reads each subagent's file from its start,
within what is left of `limit`, and a `before:` read reads only the session's own file. Why:
the brief named the session's transcript, and subagent files are bounded by their task. What I
did: documented it. What the design should change: decide whether a subagent's file is read
from its end too, with its own older cursor.
