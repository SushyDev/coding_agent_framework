# F-70: `Copy.tla`: a copy's sync, a job, a service on a host

A model and design unit: `model/tla/Copy.tla`, its configurations, its part of
`model/tla/READING.md`, and `docs/design.md`. No code changes.

## What was built

**Two decisions of the person, in the design first** (a commit of their own):

- A main session's **checkout** is the framework's own clone, `<home>/checkouts/<project>`, made
  once from the project's repository. The main session runs there on trunk, every worktree of
  the project is made from it, and the framework never runs git in the person's own clone.
  "Concepts" gained **Checkout**, and "Worktree", "Workstation", "Framework home", "Main
  sessions", "The worktree" (`Sessions`' `repo` is the checkout's path, and `git worktree list`
  is the checkout's) and the order of the units follow.
- A job can bring files back: `run(host, argv, timeout, opts)` takes `fetch: [paths]`, which
  rsync copies from the host's copy into the worktree after the job ends. Nothing comes back
  unless named. The tools table, "Hosts" and **Copy** in "Concepts" say so.

**`Copy.tla`** models `Copies`, `Jobs`, `Services` and `Shell` over ssh, with `Holder` on the
host: one worktree the agent edits at any time, one host with its copy, and an ssh connection
that drops at any step and comes back or not. A run (a job, or a service's start) takes the
copy's turn, syncs, sends its start, and gives the turn back once its start is settled. A job
is held by dtach, ends by its exit or by its timeout on the host, is read back from its socket
and its exit file, and fetches the named paths. A service is ended by its owner's end without
`keep`, or restarted (an end, then a start with its own sync). The framework restarts at any
step. READING.md has the walk-through.

**What the spec settles**, now in "Hosts" under "The spec settles (F-70)":

- The turn is durable and is held from the sync's start until the start is settled, by its reply
  or, after a cut, by a read of the host past the start's deadline. A turn held in memory, or a
  start settled before its deadline, lets a start that was still in flight land under the next
  run's sync (`Break_Copy_TurnInMemory`, `Break_Copy_SettleEarly`).
- A job's timeout is kept by its wrapper on the host. One the framework sends over ssh does not
  arrive while the connection is down, and the job runs on past it
  (`Break_Copy_TimeoutFromFramework`).
- A job's end is read socket first, then the exit file, which the wrapper writes before it
  exits. The other order answers a job that exited between the two reads as lost
  (`Break_Copy_ReadFileFirst`); a dead socket taken as success answers an exit code the job
  did not have (`Break_Copy_SocketAsExit`).
- A call has its own deadline, so it answers with the connection down for good
  (`Break_Copy_NoGiveUp`); a job's row is read by the framework, not by the call, so a restart
  still settles it (`Break_Copy_ReadInCall`).
- A service's end is a row, done only when its socket is read dead (`Break_Copy_EndOnce`,
  `Break_Copy_EndInMemory`); a restart's start waits for that (`Break_Copy_StartBeforeEnd`).

**The properties, and why in this form:**

- `StartsOnSyncedCopy` is a ghost set, `badStart`, filled in the step where a start lands on the
  host, not where it is sent: a start in flight across a drop or a restart lands later, and the
  copy then is what matters. "After the run asked" is `fresh[r]`: a sync that began after `r`
  asked has completed since. "Never partly synced" is `whole`: no sync is writing or was cut
  since the last one completed. Both are needed: `SkipSync` breaks only the first, `StartOnCut`
  and `NoTurn` only the second.
- `AnswerIsReal` compares each answer and each row with the host's exit file, so an `ok` that a
  drop (`DropAsExit`) or a restart's settle (`SocketAsExit`) made up shows as a code the file
  does not hold. A timeout answer needs the host to have ended the job, and lost needs it gone
  with no file.
- `FetchOnlyNamed` and `FetchOnlyAfterEnd` are over a ghost of every path the fetch wrote and
  whether the job's process was gone at that write.
- `JobEndsAtTimeout` is a liveness with no condition on the connection, since the timeout must
  hold with the connection down for good; `RunAnswered` too. `JobSettles` and
  `ServiceEndsWithOwner` need the host, so they hold under `<>[]up`, the connection back for
  good (`ConnectionReturns`). Drops are bounded, so that is the same as coming back again and
  again. This is how the spec reads "a run whose connection comes back gets its answer": the
  call answers in any case, and the job's row gets its real end from the host once the
  connection is back, across restarts and calls that answered unknown.
- `NoUntrackedProcess`, `OneProcess` and `EndedIsEnded` say every held process has a live row,
  a service has one process, and an ended row has none.

## What I ran into

- The first check of `Copy_Jobs` found a call that waited forever: the connection dropped after
  the job's end was read and before its fetch, and the call's deadline had been tied to the job
  running. The deadline now passes at any step after the ask, and at it the call answers the end
  it read with the fetch as cut.
- `OwnerEnds` was enabled in configurations with no service, which doubled their states; it now
  needs a service.
- The two open questions below are reachable in a few steps: `NoEditLost` fails in
  `Copy_Jobs`' constants (ask, sync begins, the agent edits `f1`, the job runs and exits, the
  fetch writes `f1`), and `NoChangeUnderRun` in `Copy_Turns`' (a service starts, then a job's
  sync begins under it). Neither is in a configuration.

## Findings

### new-1. A second run's sync changes files under a running job or service

What happened: runs take turns at the sync, and the turn ends with the start. So a later run's
sync writes the copy while an earlier run's job or service runs in it (`NoChangeUnderRun`).
"Hosts" says "so neither sees half of the other's files", which reads as more than the turn
gives.

Why: there is one copy per worktree, and an agent's runs overlap: a test runs beside the dev
server it tests.

What I did: the spec lets it happen and records it; `StartsOnSyncedCopy` speaks of the start.

What the design should change: allow it and say so. "A run starts on a whole sync of its own
time; a later run's sync changes files under a running job or service, as an edit in the
worktree changes them under a program on the workstation." The sentence in "Hosts" becomes "so
neither starts on half of the other's files". Making a run wait while another holds the copy
would stop a test from running beside its server.

### new-2. A fetch writes over an edit the agent made during the job

What happened: the agent, or its subagents, edits a path after the run's sync read it, and the
job's fetch of that path writes the copy's version over the edit (`NoEditLost`).

What I did: the spec writes it and records it in `clobbered`.

What the design should change: a fetch writes a path only while the worktree's file is still
what the run's sync sent (the sync records each named path's size, time and hash before it
sends; the fetch compares before it writes), and answers the others as
`{:conflict, paths}`, leaving the copy's version on the host. Nothing is written over blind.

### new-3. A sync is not a snapshot

What happened: rsync reads the worktree file by file, so an edit during a sync can come in for
one file and not another, and a job can start on a mix of files the worktree never held at
once. `StartsOnSyncedCopy` holds, as the brief states it; it says nothing of a mix.

What the design should change: say it in "Hosts": "a sync is not a snapshot: a file edited
while the sync runs comes in either version." No mechanism unless a person wants one.

### new-4. The host's side of a cut sync may write on

What happened: the spec assumes that once the local rsync has ended, by a drop or a restart,
nothing of that sync writes the copy again. After a drop, the host's rsync may run on until its
ssh session notices, and rename a file it had received into place after the next run's sync
began, or after the next job started.

What the design should change: make the assumption hold: the host's side of a sync holds a
lock of its copy on the host for its whole life, and the next sync waits for that lock under
its deadline. `Copy.tla` then gains a host-side writer the turn waits for.

### new-5. A run whose call ended before its job

What happened: a call that answered unknown (its deadline with the connection down, or a
restart) leaves its job running. The framework still reads the job's end into its row
(`JobSettles`), but no tool shows that row, and the fetch belongs to the call, so the named
paths never come back.

What I did: the spec reads the row and fetches only within the call.

What the design should change: as `run_delegate` does at its timeout, the unknown answer names
the job, and the job's end, once read, arrives to the caller as a message, saying that nothing
was fetched. A later `run` fetches nothing for an earlier job.

### new-6. `run`'s answers

What happened: the design gives `run` its exit code and the end of its log, or
`{:unknown, :timeout}`. The spec needs more: the call's deadline with the connection down, a
restart, a dead socket with no exit file, a cut sync (nothing ran), and a fetch cut after the
end was read.

What the design should change: `{:ok, %{exit: code, log: tail, fetch: :done | :none |
{:unknown, reason}}}`; `{:unknown, :timeout}` once the host ended the job, with the fetch's
outcome too; `{:unknown, :dropped}` at the call's deadline with the connection down;
`{:unknown, :no_exit}` for a dead socket with no exit file; `{:refused, {:sync, reason}}` for
a cut sync. A restart's answer is the MCP bridge's error. The spec's `answer` kinds are these.

### new-7. A job's end, and children left in its group

What happened: the spec takes a job's end as its command's exit, as `Shell` does. A child that
outlives the command keeps writing in the copy during the fetch and the next sync, and is past
the timeout's reach once its command exited.

What the design should change: say whether a held job's wrapper ends its group when its command
exits. If it does, it signals the group before it reaps the command, so the group's id cannot
have been reused: the same rule as `Shell`'s.

### new-8. The checkout's remote

What happened: the checkout is "made once from the project's repository". If a project declares
its repository as the person's own clone, a path, `git clone` makes that clone the checkout's
`origin`: the pull after a landing then pulls the person's trunk, and `gh stack` pushes the
delegates' branches into the person's clone.

What the design should change: a project's repository is the remote its stacks land on, and the
checkout is cloned from it. `Sessions`' `repo` is then the checkout's path, which the built
`Sessions` already takes; only the embedding app's data changes.

### new-9. A run on the workstation

What happened: a host may be the workstation, and `service_start` runs there by default. The
design does not say whether a run there has a copy or runs in the worktree itself. With a copy,
the turn, the sync and the fetch apply as on any host, and `Copy.tla` covers it with a
connection that does not drop; without one, a service sees each edit at once and a fetch has
nothing to do.

What the design should change: a copy on the workstation too, under the framework home, so a
job's build outputs and a service's files are kept apart from the agent's edits the same way on
every host, and one path of code serves them all.
