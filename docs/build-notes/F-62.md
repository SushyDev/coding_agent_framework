# F-62: `Delegates`, part 3: the kill path

## What was built

Part 3 of F-59 new-9's split, taken from the local branch `framework/f-59-delegates-code`
(commit `f44ac25`) and fitted to `main`, where F-60 built part 1 and F-61 settles a running
`Sessions` row whose process is gone:

- **`Delegates`** takes `transcripts:` (account to its `Transcripts`) and depends on
  `caf_transcripts`. At an exit before the turn's `result` (`Turn.next/2` answers `:exited`,
  the place F-60 left), `exited/3` reads the transcript (`Transcripts.read/3` of the `Stream`
  row's path, then `Transcripts.session/3`):
  - a transcript that ends with the last reply is a finish, its text the report;
  - a row already resumed once is `failed`, its report the second-kill text;
  - otherwise, once `Sessions`' row of the name has ended (`stopped` or `refused`, or no row),
    `resume/3` writes `resuming`, `resumes: 1`, `called_at`, `deadline` and `resume_uuid` (a
    new uuid when the brief was delivered, `nil` when it had not gone in) in one update, then
    asks `Sessions.resume/6` in a task, as a start is asked;
  - a read that fails, or a `Sessions` row still running, decides nothing.
- A refused resume (or one cut off past its deadline, as `interrupted`) is `failed`, and the
  refusal is its report; a refused start is `refused`, as before. A row a restart left
  `resuming` is settled by `Sessions`' row of its call and woken at its deadline, as a
  `starting` row is.
- **`Delegates.Turn`**: `message/1` (the brief under `brief_uuid`, or `resumed/0` under
  `resume_uuid`) and `resumed/0`; `next/2` waits for that message.
- `Delegates.Table`'s moduledoc no longer names the kill path as a later unit; its columns are
  unchanged. `docs/design.md` says the resume waits for `Sessions`' row to end (new-1). The
  README's status and graph, and `Delegate.tla`'s header, say what is built.

Tests, on the stand-ins, each killing only the pids its own stand-in recorded in `pids/`, and
waiting until dtach has removed the socket and `Stream` has read the exit:

- killed before its last reply: while `Sessions`' row still says running, a cue asks nothing
  (`resumes` 0); once `Sessions` settles it `stopped` and `Delegates` is cued, the delegate is
  resumed once with `Turn.resumed/0` under a uuid of its own and finishes with that turn's
  `result`;
- killed twice: the second kill is `failed` with the second-kill text held as its report, and
  no third message is taken;
- killed after its last reply (a transcript written by hand): a finish with the reply's text,
  without waiting for `Sessions`' row;
- `Turn`: a resumed process waits for its own message; the earlier turn's result does not
  count.

The first version of these tests failed on the code with either guard removed: without the
wait for `Sessions`' row (the resume is asked while that row runs), and without the second-kill
check (`ResumeAgain`). The tests then changed how they wait (new-5); I could not run the two
mutations again on them (see "Gates"). The assertions that catch each are unchanged: `resumes`
0 while `Sessions`' row runs, and `failed` at the second kill.

## What I ran into

- F-59's code asked the resume as soon as `Stream` read the exit. On `main` that is refused
  `{:exists, "running"}` whenever `Delegates` takes the cue before `Sessions` has settled its
  row, and a refused resume is the report: the delegate would fail for an ordering of two
  cues. Hence the wait (new-1).
- A transcript file that does not exist reads as a row with `problem: "no_file"` and no reply,
  so a process killed before it wrote one is resumed. That is what a kill before any reply is.
- `Transcripts.read/3` answers `{:ok, %{failed: [...]}}` for a shell that failed; F-59's code
  read the session's earlier row then. The code now decides nothing unless `failed` is empty.
- `MIX_ENV=test mix caf.deps` failed at first: the tests read the socket through `Holder`, so
  `caf_delegates` now declares `caf_holder`, `only: :test`.
- My first resume tests raced `Delegates`' own resume (new-5).
- Gate runs failed, outside this unit's tests, while other work loaded the machine (new-6).

## Findings

### new-1. The resume waits for `Sessions`' row; after F-61 new-3, that wait may be long

What happened: the host wires the same `Stream` cue to `Sessions` and `Delegates`. If
`Delegates` takes it first, `Sessions`' row of the killed process still says `running`, and
`Sessions.resume/6` would be refused. And F-61 new-3: a `Sessions` settle that meets a socket
dtach has not removed yet settles nothing until the next cue.

What I did: `Delegates` counts and asks the resume only once `Sessions`' row of the name has
ended. Until then it writes nothing and asks nothing: the row stays `running`, and each later
cue reads the transcript again (from its stored offset) and looks again. `Sessions`' write of
`stopped` cues `Delegates` through the host's wiring, so in the common order the resume follows
at once. When F-61 new-3's case happens, the delegate waits, unresumed, for the next cue that
reaches `Sessions` and then `Delegates`. No retry and no fixed wait were added. The design now
says the resume waits.

What the design should change: the answer to F-61 new-3 (a `Registry` interval read that cues
each time, or a `Holder` cue when a socket goes) also ends this wait; nothing else in
`Delegates` is needed.

### new-2. `Delegate.tla`'s `KillSeen` does not wait for `Sessions`' row

What happened: in the model, `KillSeen` asks the resume as soon as the process is dead, and
`SessionsDecides` may refuse any resume. The code takes `KillSeen` only once `Sessions`' row
has ended (new-1). This narrows the step, so the safety properties hold for the code as they
do for the model; what the model does not show is that a resume asked too early is refused
for certain, and that the code's wait depends on `Sessions` settling the row.

What I did: nothing in the model.

What the design should change: when `Start.tla` and `Delegate.tla` are composed, or
`Delegate.tla` gains `Sessions`' row of a killed process, guard `KillSeen`'s resume with that
row having ended, and state `RunningSettles` as what makes the resume possible.

### new-3. `ResumeBeforeRow` and `NewUuid` are what the code does

What happened: the brief asked me to check both guards against the code.

- `ResumeBeforeRow`: `resume/3` writes `resuming` and `resumes: 1` with `resume_uuid` in one
  `Table.update/3`, then starts the task that asks `Sessions`. A restart between the two leaves
  `resuming`, which `Settled` decides by `Sessions`' row written at or after `called_at`, or
  past its deadline as `failed` (`interrupted`); the call is never made again. A second exit
  meets `resumes` 1 and is the report.
- `NewUuid`: every write goes under a uuid read from the row (`Turn.message/1`), chosen and
  written before the write; `Stream` refuses a uuid a second time. One difference of detail:
  the model's `KillSeen` clears `marked` for every resume, while the code writes the brief again
  under `brief_uuid` when it had not gone in. That is a uuid `Stream` holds as `undelivered`,
  which it takes once more, so it is not a new uuid, and `OneMessagePerProcess` holds as the
  model has it.

What I did: nothing; no gap.

What the design should change: nothing.

### new-4. Since F-61, a `stopped` `Sessions` row does not mean a call was refused

What happened: `settle_row/2` reads `Sessions`' row of a cut-off call as `refused` when it says
`refused` or `stopped`. Since F-61, `stopped` with reason `exited` also means the process ran
and was killed. If `Delegates` restarts while a start or resume runs, and the process is then
killed before `Delegates` settles the row, a start is `refused` (`exited`) though its process
ran and may have taken the brief, and a resume is `failed` with "its resume was refused:
\"exited\"" though it was a second kill. In `Delegate.tla`, `sess` stays `running` after a
kill, so `Settled` writes `running` and `KillSeen` takes it from there.

What I did: nothing; the second case gives the same status with a misleading text, the first
refuses a delegate that should be resumed.

What I recommend: a unit that settles a `starting` or `resuming` row by a `Sessions` row that
says `stopped` with reason `exited` as `running` (it ran), so the exit path reads its
transcript and resumes or reports it, with a test that restarts `Delegates` during the
`slow` project's setup and kills the process before the next cue.

### new-5. A test cannot wait for `Sessions`' row to say `stopped` once `Delegates` resumes

What happened: this unit's resume tests first waited for `Sessions`' row of the killed process
to say `stopped`, cueing `Sessions` on each poll. They failed now and then: the row named the
resumed, live process. `Delegates` had taken an earlier cue after `Sessions` wrote `stopped`,
and resumed at once, so `stopped` lasted less than one poll. Waiting on `Delegates`' row
instead, but casting a cue to `Sessions` every 20 ms, failed another way: each cue is a settle
with a `ps`, the casts queued ahead of the resume's own work, and the row stayed `resuming`
past the wait.

What I did: the tests wait on what they check, `Delegates`' row counting its resume and
running again (`resumed/2`). Each poll cues `Sessions` and then `Delegates`, as the host's
wiring would, and after each cue makes a plain read of the same process (`Sessions.viewer_argv/2`,
`Delegates.held/2`), which answers only once the cue is handled, so cues never pile up.

What the design should change: nothing. A test of a resume should not wait on a `Sessions`
state that a resume ends.

### new-6. F-61's RunningSettled tests fail now and then under load

What happened: F-61's "a running delegate killed before its last reply is settled stopped,
then resumed" (`SessionsHeadlessTest`) failed in the first `devenv test` and in later
`gate-test` runs, and once with it "F-61: RunningSettled stops a running row whose process
was killed" (`SessionsTest`): each row stayed `running` for the 10 s wait after the test's one
`Sessions` cue. This branch does not change `caf_sessions`, and its tests run in their own app.
The runs that failed had load averages from 8 to 61, from other work on the machine; at such
loads `RegistryTest`'s property "state rules, over generated session files …" also timed out
at 60 s (twice), `CaptureScreenTest` read a blank capture once (F-51 new-11), and once F-60's
start test timed out at 60 s in `start_delegate`.

Why: not confirmed. The settle writes `stopped` only after a `ps` (5 s bound) reads the pid as
gone and the socket as dead, and the test cues once, so any read that decides nothing at that
cue leaves the row `running` (F-61 new-3). I checked one cause: dtach removes its socket as it
exits without reaping its child, so the killed process could stay listed (a zombie, with its
start time) for a moment. A script that killed a dtach-held `sleep` and ran `ps` once the
socket was gone saw the pid listed in 0 of 30 tries, at idle.

What I did: nothing in F-61's tests or `Sessions`; I ran the gates again once the load had
fallen (see "Gates").

What the design should change: nothing in the design. A unit of its own could have F-61's two
tests cue on each poll (with a read after each, as in new-5), and make a settle that decides
nothing for a gone process say why, so a run like these can be read afterward.

### new-7. The machine ran out of pseudo-terminals, and test runs leave held processes behind

What happened: the last round of gates failed everywhere `dtach` starts: `dtach: init_pty:
Device not configured`, 29 times in `devenv test` and 16 in the first `gate-test`, with 95
failures across the apps. The host allows 511 ptys (`kern.tty.ptmx_max`); 527 `/dev/ttys*`
existed, and 467 `dtach` processes were alive, each under a test VM's directory
(`/tmp/caf-<pid>/`), started from the night before onward. Five of those directories appear in
my own runs' logs (72 processes); their VMs had exited and their directories, with the
stand-ins' `pids/` records, were gone.

Why: not confirmed. A test VM's processes outlive it when its stand-ins are not ended by pid
before its directory goes: for example when a test times out while a start is in flight, so
the stand-in records its pid after `on_exit`'s `kill_all/1`, or when a VM is ended before its
`on_exit` runs.

What I did: nothing to the processes. Mine can no longer be found by a recorded pid, only by
their command lines, which the rules forbid, and the rest are other runs'. I stopped my queued
gate script, and no VM of mine runs.

What the design should change: a unit of its own should make a test VM leave no held process
behind: each test's stand-ins and `dtach` masters ended by recorded pid even when a start was
in flight at a timeout, and a check at the end of `gate-test` that no process under the VM's
directory is left. Until then, a machine that runs many gate runs needs its leftovers ended by
whoever owns them.
