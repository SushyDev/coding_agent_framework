# F-246: a trust press on a fresh start holds

## What was built

Every real run since F-239 failed at the first trust press of a fresh main session: `{:unknown,
{:still_shown, … selected: "No, exit", kind: :trust}}`. F-243's press records showed the marker
read on "Yes, I trust this folder", the Enter sent, and then "No, exit" selected again for 10 s.
Measured on the real program (below), the cause is a second draw of the dialog: Claude Code
2.1.322 draws the dialog again, on a timer, about 150 ms after its first draw, and sets the
selection back to "No, exit". A key before then moves the marker on the screen but not the
choice the program holds, and an Enter before then is dropped. With no key, the second draw
writes nothing, since nothing on the screen changes, so it cannot be read. The press went
within about 50 ms of the first draw, so its keys were lost.

A second item, from the main session, in the same path: on Linux a main stayed `dialog` after
its trust answer. Its session file's `procStart` is a start in clock ticks there, which the
liveness read judged `replaced`; a start in that form is now read from `/proc/<pid>/stat`
(below).

Built first from `main` before F-243 and F-245 landed, then rebased onto `main` at F-245
(9346a07), with F-243 (d1beeb9) under it; the settle is one more term of F-245's chain of
bounds (below).

### The press waits for the dialog to settle (`Inlet.settle/0`)

`Inlet.choose/5` reads the dialog, then reads it again every 20 ms until its reading has stayed
the same for `settle/0`, 1 000 ms, and only then sends its keys (or its Escape). The settle
starts again when the reading changes, and when a capture is caught mid-draw (unrecognized).
Another screen refuses at once, as the first read does. A dialog that never reads the same for
1 s within `see:` past it is refused `{:unsettled, reading}`: no key went. The rest of the press
is unchanged: keys, the marker read back, Enter, the leave read. Each key still goes once, and
nothing is pressed again.

1 s, from the measurements: the second draw came 147 to 153 ms after the first in 8 runs at
loads 21 to 40, and 214 ms once at load 47. 1 s is over six times the common case and over
F-238's x4 for a loaded host. The settle is a library constant, not a `Config` field, so the
press's bound and its wait come from one number (F-242's new-2).

### The settle in F-245's chain of bounds

The settle is one more read of the press, derived as F-245 derives its two others: it lasts up
to `settle/0` plus `see`, then the pause between captures, then one capture that may start just
before its deadline. So `@commands` goes from 6 to 7, and `Inlet.press_bound_at/2` is `3 * (see
+ 20) + settle + 7 * command + 1_000`. F-245's table, redone (ms; the changed rows marked):

| Bound | Derived as | At `see` 10 000 (default) | At `see` 2 000 |
| --- | --- | --- | --- |
| one tmux command, `Tmux.bound/1` (CLI: `Shell.bound/1` of the server's 5 000 timeout) | timeout + 500 (TERM to KILL) + 1 000 (the killed program's exit) | 6 500 | 6 500 |
| the settle's read (new, F-246) | `settle/0` (1 000) + `see` + 20 + one command | 17 520 | 9 520 |
| one read of a press, the marker's or the leave's | `see` + 20 (the pause between captures) + one command (a capture started just before the deadline) | 16 520 | 8 520 |
| the `Inlet`'s press, `Inlet.press_bound_at/2`, the `timeout:` `Sessions` passes (changed) | the settle's read + 2 reads + 4 commands outside them + 1 000 (its own work and reply) | 77 560 (was 60 040) | 53 560 (was 44 040) |
| `Sessions`' call, `Sessions.press_wait/1`, asked through `press_call/2` (changed) | the `Inlet`'s + 5 000 (calls ahead in `Sessions`, and the reply) | 82 560 (was 65 040) | 58 560 (was 49 040) |
| the inbox (`Prompts.answer/5`), `CodingAgentFramework.answer/4`, the operator's `answer_startup` (changed) | the call above: they run in the caller's process and add no bound | 82 560 | 58 560 |

An Escape's press runs one command and one read fewer than a choice's, so it stays inside the
same bound. F-245's test of the chain (`sessions_dialog_test.exs`, "the bounds that wait on a
press derive from the Inlet's see, up to the caller") now asserts the new terms and numbers.

### The model: `Press.tla`

A new spec models the press step by step against a program that draws its dialog and then
draws it again once by R ticks, setting the selection back: `phase` (`first`, `again`, `gone`),
the marker drawn (`sel`) and the option held (`held`), an Enter dropped on the first draw. The
Inlet's steps are Look, Keys (only once the dialog has read the same for S ticks), Unsettled,
Back, Enter and Leave. Invariants: `RightChoice` (no option but the one answered is taken),
`OkIsTaken`, `Once` (keys and Enter at most once), `RefusedSentNothing`; property `Answered`.

- `Press_Settle.cfg` (R 2, S 3): 65 distinct states, no violation.
- `Break_Press_FirstDraw.cfg` (keys at the first read): TLC finds `RightChoice` violated. The
  keys land on the first draw, the second draw sets the choice back, and the Enter confirms
  "no".

`Dialog.tla` and `Menu.tla` keep the press as one step; the header of `Press.tla` says so.

### The stand-in draws the trust dialog again (`redraw:`)

`ScreenStandIn.write!/4` takes `redraw: ms`: the trust dialog is drawn again once, `ms` after
its first draw. Until then a key moves the drawn marker only and an Enter is dropped. The second
draw puts both back on "No, exit". `redraw: {:every, ms}` draws it again every `ms`, the marker
on the other option each time, so it never settles. Each key the trust or imports dialog takes
goes to `<dir>/dialog_keys` (`dialog_keys/1`).

### The second item: a row left on `dialog` after its trust answer

The main session reported a run on Linux (2.1.322): the trust press verified, the main took its
first prompt and replied, its session file read `idle` in the `Registry`, yet `agents` kept the
main on `dialog` until the test's 180 s wait ended.

What moves the row off `dialog`, from the code: `agents` reads `dialog` exactly while
`Sessions`' row has status `dialog` (`Tracker.Tree`'s `state/2`, `Turn.interactive/3`). The
row goes `running` only in `settle_row/3` for a `dialog` row, called on each `look:` interval
(`handle_info(:look)`) and on each `registry:<host>:<account>` cue. It writes `running` when
`confirm/3` answers `{:ok, file}`: a session file in the `Registry` with the row's name, judged
`:live`, while the row's dtach socket is live. The `Registry` judges a file live by its `{pid,
procStart}` against `LC_ALL=C TZ=UTC ps -o pid=,lstart=` (F-7). A file whose `procStart` is in
another form reads `:replaced`, so `confirm/3` answers `{:live, :no_session_file}`, the pane
shows no dialog, and nothing moves the row, ever. Before its answer, the start's own call
confirms by the same rule.

On the stand-in, through the whole tree, the path holds: a new test in `tree_main_test.exs`
starts a main whose stand-in draws the trust dialog, sees `start_main` answer `{:unknown,
{:dialog, :trust}}`, answers the inbox's prompt with the trusting label, and reads `app-epic:
main of app, on one, idle` in the console's `agents` (2 of 2 in 12.3 s). A throwaway change, not
kept, made the stand-in write `procStart` as `"987654321"`: the same test then read `app-epic:
main of app, on one, dialog, on the trust dialog` until its 30 s wait ended. That is the
reported state exactly.

On this Mac the real 2.1.322's file holds `"procStart":"Tue Nov 24 12:28:23 2026"` (the `ps`
form, in UTC) and `"pidDomain":"darwin"`. The main session then read the Linux run's
`registry_sessions` row: `procStart` `"653385178"`, alive `replaced`. A bare integer: the
process's start in clock ticks since boot, field 22 of `/proc/<pid>/stat`. On the open question,
whether the Mac hides this behind the press failure: it does not. The same `confirm/3` confirms
a Mac start whose form matches, as F-243's step 13 showed (its resumed main reached `idle` with
a new pid).

### A start time in clock ticks is read from `/proc` (`Holder.Process.liveness/3`)

`liveness/3` reads each start in the form it is given, not by the host: a start that is all
digits is Linux's, and is judged by one `cat` of its `/proc/<pid>/stat` files under `env
LC_ALL=C`; any other is judged by `ps -o pid=,lstart=` as before. `judge_stat/2` (pure) reads a
stat line's start time as the 20th field after the line's last `)`, since the program's name in
field 2 may hold spaces and parentheses. A pid whose file `cat` reports missing is `:gone`; one
neither read nor reported missing, an unreadable line, or a `cat` that did not exit 0 or 1, is
`:unknown`, so a failed read never counts a live process gone. A start in ticks with no `:cat`
given is `:unknown`. The `Registry` already passes its programs, `cat` among them; `Sessions`
now takes `cat` too and passes it. This module's own records stay in the `ps` form.

No spec changes: this is how a liveness read is judged, not a step over time (F-7 kept none for
it either).

## Findings

### new-1. A pane gone after a trusting press reads as sent

What happened: in the sweep, an Enter after the reset confirmed "No, exit" while the press had
answered "Yes, I trust this folder", and the program exited. F-242's `left/6` reads a pane gone
as the dialog left, `{:ok, :sent}`. So a press lost this way before F-246 could answer `ok` for
a trust the program refused. Why: a pane gone is "No, exit" landed, whoever chose it. What I
did: nothing beyond the settle, which keeps the press off the first draw. What the design
should change: a pane gone should be `sent` only for a label that exits ("No, exit"), and
unknown for any other label.

### new-2. The settle is time only, and the Inlet is held for it

What happened: the second draw cannot be read when no key came, so the press waits 1 s on
every dialog, and the host's one `Inlet` writes nothing else meanwhile. Why: `choose/5` is one
step of the `Inlet`, by design. What I did: a 1 s settle in the step, and the press's bound
grows by `see` plus the settle. If a host's load stretched the program's timer past 1 s, the
press would be lost again: `Press.tla` assumes the settle is longer than the redraw (S > R).
What the design should change: if presses become frequent or a press is lost again, count the
settle from `Sessions`' first read of the dialog (its `at`), outside the `Inlet`'s step, or make
it a `Config` field derived as `press_see` is.

### new-3. A dialog that never settles is refused, not unknown

What happened: the brief asks for `{:unknown, …}` at the bound. No key has gone then. Why: by
the repository's rule, refused is the outcome when nothing went; `Sessions`' `pressed/3` takes
a refused press's mark back, so the prompt is open again for a person, where an unknown press
is never pressed again. What I did: `{:refused, {:unsettled, reading}}`. What the design should
change: nothing, unless a refused startup press should be withdrawn rather than reopened.

### new-4. Every press settles, not only a start's

What happened: the settle applies to every `choose/5`: a running session's menu (F-198), its
own question (F-230), an exit press (F-231), the usage limit menu. Each now takes 1 s more.
Why: whether 2.1.322 draws those again after their first draw was not measured; the trust
dialog's timer may belong to the dialog component they share. What I did: one rule for all.
What the design should change: measure a running session's menu the same way; if it is never
drawn again, the settle could apply to startup dialogs only.

### new-5. A session file's `procStart` has a form per operating system

What happened: on Linux a main stayed `dialog` after its trust answer: its file's `procStart`
was `"653385178"`, judged `replaced`. Why: `liveness/3` compared every start with `ps -o
lstart=`, a form F-7 saw on macOS only (its new-3). What I did: a start that is all digits is
read from `/proc/<pid>/stat`, chosen by the form the file holds, not by the host. What the
design should change: name `procStart`'s two forms, with `pidDomain`, in the "Claude Code"
rules, and add a Linux session file to the fixtures once one is captured.

### new-6. A row's start in ticks still reaches the checks made by `ps` in a shell

What happened: a main session's row takes its `proc_start` from its session file (`running/3`,
`confirm/3`), so on Linux it is in ticks. A delegate's comes from the holder's own record, in the
`ps` form, and is not touched. Besides `liveness/3`, a main row's start goes to shell steps that
check it against `ps -o lstart=` before they act: `end_reading/2` (`sessions.ex:1433`, the
record a main's stop or end signals by) and `limited_reading/4`'s record (`sessions.ex:1387`).
`Holder.Process.signal/4`'s shell answers `gone` for a start that `ps` prints otherwise, so on
Linux a main's stop or end would read `{:ok, :gone}` and send no signal while the process runs
on: a wrong answer, not an unknown one. `Mover`'s claim only records the start in its act. Why: they predate a second
form, and each checks and signals in one shell. What I did: nothing; this unit fixes the read
the brief named, and these change the held program's shell protocol (`Start.tla`'s `Signal`).
What the design should change: have those shells read a start in the form it is given, as
`liveness/3` now does; or keep a main row's start in the `ps` form, read by `ps` when the row is
confirmed, and use the file's form only to match the file.
