# F-8: every tool from devenv

## What was built

- **`devenv.nix`** exports each program's store path as `CAF_<NAME>`: tmux, dtach, claude, git,
  gh, sh, bash, rm, mv, env, kill, ps, cat, echo, tlc and java. All come from the nixpkgs in
  `devenv.lock`. `CAF_TOOLS_PATH` is a short `PATH` of coreutils, grep and sed for
  `bin/check-model`. `CAF_OTP_VERSION` and `CAF_ELIXIR_VERSION` name the lock's versions.
- **One JDK.** `tlaplus18` brought its own JDK in its `tlc` wrapper, apart from the
  `jdk21_headless` in the shell. It is now built against `jdk21_headless`.
- **Versions checked.** The `check-versions` script runs each program and compares what it prints
  with the lock's version: tmux, dtach, Claude Code, Erlang and Elixir. It names each one that
  differs. `test_helper.exs` calls `TestHost.check_environment!/0` before any test: it stops the
  suite when the VM's OTP or Elixir is not the lock's, or a `CAF_` variable does not name a file.
- **Gates.** `gate-format`, `gate-compile`, `gate-test` and `gate-model` run one gate each.
  `devenv test` runs `check-versions`, then the git hooks on every file, then the four gates.
  `gate-test` excludes the `:model` tag, since `gate-model` runs TLC itself.
- **Tests and `bin/check-model`** run programs only from the `CAF_` paths. `TestHost.program!/1`
  reads them. Every `/bin/sh`, `/bin/cat`, `/bin/echo`, `/bin/kill` and `mv` a test ran is now a
  `CAF_` path. `bin/check-model` takes `CAF_TLC` and runs with `PATH` set to `CAF_TOOLS_PATH`.
  The model test runs it with `CAF_BASH`, not through its `#!/usr/bin/env` line. `Shell`'s
  doctest that ran `/bin/echo` is now a plain example.
- **State in the checkout.** devenv puts `MIX_HOME` in `.devenv/state`. `HEX_HOME`,
  `REBAR_CACHE_DIR` and the Erlang shell history go there too. Hex and rebar3 come from the lock
  through `MIX_PATH` and `MIX_REBAR3`, so `mix local.hex` never downloads one.
- **Git hooks** (`git-hooks` input): `mix format --check-formatted` and `typos` with the `en-us`
  locale. `@behaviour` (Elixir's word) and `caf` (this project's prefix) are allowed.
- **`Programs`' doc** says the library reads no environment, that a host app can hand it the
  `CAF_` paths, and that a remote host's programs are found on that host.
- **`README.md`** says how to enter the environment and run the gates.

## Measured

On this laptop, under a load average of 22 to 46:

- Entering the shell takes 1.1 to 1.3 s once it is evaluated, and about 12 s the first time after
  `devenv.nix` changes.
- Each gate through `devenv shell -- <gate>`, entry included: `gate-format` 5.1 s,
  `gate-compile` 7.0 s, `gate-test` 12.8 s (50 tests, 3.6 s in ExUnit), `gate-model` 81 s.
- `devenv test`, everything: 48 to 62 s. `check-versions`: 2.0 s.

## What I ran into

- `git config --global --get core.hooksPath` found nothing inside the shell, though git used a
  global hooks path. `git config --show-scope --get core.hooksPath` finds it.
- `devenv test` hides the gates' output when they pass. A failing gate stops the run, and its
  output is shown.
- dtach has no version flag. `dtach --help` prints `version 0.9`, but the lock's dtach is the
  snapshot `0.9-unstable-2025-06-21`. The check compares `0.9` only, so a newer snapshot of 0.9
  passes it.
- `claude --version` may read its config directory. The check gives it one in `.devenv/state`.
- The Hex package's code lives in `lib/erlang/lib/hex-<version>/ebin`, not `hex/ebin`.
- `mix test` runs TLC through the model test, so running it and `bin/check-model` ran TLC twice.

## Findings

### new-1. The library still runs fixed system paths

What happened: tests now name programs only by `CAF_` paths. But the library runs `/bin/sh`
(`Holder` and `Programs.find/3`), `/bin/rm` (`Tmux.CLI`), `/bin/kill` (`Shell` on a timeout) and
`/usr/bin/env` (`Shell` over ssh). A test that calls these modules still runs the system's tools.

Why: these paths are fixed in the modules, and no constructor takes them.

What I did: nothing in the library. Changing the constructors is a host layer change, not a
devenv one.

What the design should change: `Programs` could name `sh`, `rm`, `kill` and `env` too, and
`Holder`, `Tmux.CLI` and `Shell` could take them from a host's `Programs`. Only `Programs.find/3`
would still start from the host's `/bin/sh`, since it must find the rest.

### new-2. Git hooks are not installed when `core.hooksPath` is global

What happened: devenv's hook installer (`prek`) refuses to install when git's `core.hooksPath`
is set outside the repository, as it is on this laptop. Its failure stopped `enterShell` on every
shell entry.

Why: git would run hooks from the global directory, not the repository's.

What I did: the install task's `status` skips it when the setting is not local, and says why.
`devenv test` still runs the hooks on every file. So on this laptop the hooks do not run on
commit.

What the design should change: the owner chooses one. A repository-local `core.hooksPath`
(shared by every worktree) lets devenv install them. Or the global hooks directory runs a
repository's own `pre-commit` when it has one.
