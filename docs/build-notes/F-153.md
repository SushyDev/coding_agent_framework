# F-153: what else the first end-to-end run found

The first end-to-end run (F-151) stopped on faults that break delivery itself and on smaller
ones. This unit takes seven of them, each decided before it started. F-152 takes the headless
start, which this unit does not touch. The branch was cut from F-151's commit and is rebased
onto `main` with F-151 and F-152 on it.

## What was built

1. **A `launch` row is settled by its own line, and is never due again while its process
   lives** (F-151's new-2).
   - *Why the settle missed it.* The run's own tables and transcripts say it. The interactive
     delegate `demo-unit-notes` was started at 09:17:53 (UTC); its start met the trust dialog
     and answered `unknown: {:dialog, :trust}`; `Mailbox.launched/3` set a timer at the start's
     deadline and the take bound, 10 s past it. The person answered the dialog at 09:42:50, 25
     minutes later, and the first turn's user line (the brief and its mark) was written then.
     By that time the bound had long passed with no line, so `Transport.Launch.settle/2` made
     the row due again; no typed write could take it while the dialog showed, and the waiter
     took it at the first turn's end (09:43:08.849): the brief went in twice, the second time
     `via waiter`. The bound stood for "Claude Code has taken it or never will", which holds
     for a waiter's answer and a typed line (about a second), but not for a start's prompt,
     which waits behind every startup dialog for as long as a person takes.
   - *What the model says.* `Delivery.tla`'s `SettleSeen` makes a row with no line due again
     only when no copy of it is on its way to a turn (`wire[i] = 0`) or its process is gone. A
     launch's prompt is on its way from the start until its first turn, so the model already
     allowed at most one delivery; the code read the bound as `wire[i] = 0` for the launch too.
     The new `Break_Delivery_LaunchBound` makes `SettleSeen` take the bound for a launch row
     (a row with no line due again while its process lives). TLC fails it on `AtMostOnce` in
     14 steps, the trace the code took: `Sends` (the brief), `Mark` (`launch`), `Launches`
     (the start; the prompt on its way), `SettleSeen` with no line (the bound), the mark undone
     and due again, `Mark` and `Handed` by another transport (`typed` in the model, the waiter
     in the run), `Takes` (the launch's first turn), `TurnEnds`, `Takes` again: twice in the
     transcript.
   - *The code.* `Transport.Launch.settle/2` has no bound: with no line, a launch row is due
     again only once no process of the start runs. Its evidence is its own line,
     `Transport.Launch.seen/2`: a user line whose text ends with the row's mark, as 2.1.322
     writes a start's first turn (`promptSource` `typed`), never a waiter's `Stop hook blocking
     error` line, whose mark sits inside a `system-reminder`. `Mailbox` sets no timer for a
     launch row any more and reads it at every cue (as a typed row is read), so its process's
     end, a `sessions` cue, settles it.
   - *The stand-in.* `ScreenStandIn` with `transcript: true` writes the first turn's lines in
     the run's shape (title, agent name, modes, a file-history snapshot, then the user line),
     only once its startup dialogs are answered. `MailboxLaunchTest`'s new test starts it on
     the trust dialog with a deadline already past, fires the bound, and sees the row stay
     `sending` by launch; then answers the dialog and sees it delivered by launch, its mark on
     one transcript line. On the old code the row goes due again at the bound.
2. **`Screen` reads a real main session at any width** (F-151's new-3). The cause was one
   line: 2.1.322 draws a session's `--name` inside the rule above the box (`──── capture-main
   ─`), so `Screen` found no rule above the box and read no box at all. The release's reading
   has `named_rule`, and only the box's upper rule may carry a name; the lower rule and a
   dialog's stay plain. The effort hint, the Remote Control notice and URL, the "Ctrl+Y to
   paste deleted text" hint and the footer's `· ← for agents` are all outside the box and its
   footer's running words, so they needed nothing. Fixtures `main-idle-120`, `main-idle-400`
   and `main-text-400` (each `.txt` and `.ansi`) come from the captures, the URL's session id
   and the path scrubbed. A new test reads every fixture with its rules redrawn at 80 and 400
   columns, and the box with a name in its upper rule at 80, 120 and 400; a name in the lower
   rule, or words with no closing `─`, are unrecognized. The stand-in draws the name in its
   upper rule whenever it is started with `--name`, as every interactive start is, so every
   `Inlet`, `Sessions` and `Mailbox` test that types into it reads the named rule now.
3. **`bin/caf-login` passes Claude Code's first run** (F-151's new-4). After the login it runs
   Claude Code once on the account in a scratch folder it removes after, for the person to
   pass the onboarding, the folder's trust dialog, then `/exit`; an account whose
   `.claude.json` records `hasCompletedOnboarding: true` is not run again. `--check` names

5. **The console never starts twice**: `Console.shell/2`, which the dot file calls, starts the
   app once per VM and gives a later shell (IEx evaluates the dot file again in each new one)
   the app the first started. `docs/e2e.md` says to wait on a long call or run it as a task,

6. **A running interactive session's turn state is read** (F-151's new-5). Two faults, both in
   `Tracker`: the fold's session entry kept no `proc_start`, which `Sessions.Turn.file/2`
   matches with the pid, and `Tracker.Tree` grouped the session files by `host` and `account`
   fields that a fold entry does not carry (its scope is the view's key), so no file was ever
   found. And an interactive delegate was read from `Stream`, which follows only headless
   ones. Now the entry keeps `proc_start`, the files are grouped by the view's key, and an
   interactive delegate is read by its session file as a main session is. Run against a copy
   of the run's `caf.db`, `demo-main` read `unread` before and `idle` after.
7. **A main session can end when a delegate's start never ran** (F-151's new-5). In the run,
   `demo-unit-hello`'s headless start waited for an init that never came (F-152); `Sessions`
   stopped its process (agent row `stopped`), and `Delegates` wrote its own row `refused`.
   Nothing ended the agent row: `Delegates` ends one only for `failed` or `finished` rows, and
   its stop refuses a row that never started. Of the two options the brief gave, this takes the
   first: such a delegate counts as ended, as a failed one does. `Delegates`' settle reads its
   latest `refused` rows too and asks `Sessions.ended/3` for one whose agent row is its own
   call's (started at or after the call) and free. `Team.tla` has `StartsRefused` (FALSE in
   every configuration before this unit), `StartRefused` (a delegate whose call reached
   `Sessions` and whose process went before its first turn took anything), `RefusedEnded` (the
   settle) and the property `RefusedEnds`; `Team_StartRefused` checks the design and
   `Break_Team_RefusedKept` (no settle) fails `RefusedEnds`. A `DelegatesTest` test writes the
   late refusal as the run's answer wrote it, ends the process by its own pid, and sees the
   agent row ended and the parent's cap free.
8. **An unknown main session's pane is read in a task.** F-151's fix read it in `Sessions`'
   own process, at each settle and each 5 s look, `Inlet.look` up to 5 s each, so under load
   its calls could wait behind it. Now a settle that finds the row still unknown sends
   `{:peek, name}`; that starts one task per name (`peeking`), linked to `Sessions`, as a

## Findings

### new-1. The capture script does not check the width it captured

What happened: the captures asked for at 200 columns came out at 120, and a "text" capture at
120 holds no text. Why: the window took another client's size, or the resize did not land
before the capture, and the draft was typed after the capture. What I did: used only the
captures that show what their name says. What the design should change: the capture script
should compare tmux's `pane_width` it read with the width it asked for, and the screen's box
with the text it typed, and refuse a capture that differs.

### new-2. A `launch` row whose start shows a dialog nobody answers holds every later row

What happened: with no bound, a launch row stays `sending` for as long as its process lives,
and one row in flight per addressee means every later row to that session waits behind it.
Why: a startup dialog holds the first turn until a person answers it, and that is what makes a
bound wrong. What I did: nothing more; `dialogs(caf)` shows the dialog, and an answer, or the
session's end, settles the row. What the design should change: `status(caf, id)` of a row
behind it could name the dialog its addressee waits on, so a person sees why a message waits.

### new-3. An interactive session's held requests are not in `agents()`

What happened: `waits_on` is read from a delegate's `Stream` row, so an interactive delegate
and a main session show no `waits on …` in `agents(caf)` even while a permission dialog holds
their turn (their state reads `waiting` from the session file). Why: their requests are
`PermissionRequest` rows `Intake` holds, which the view has as events but the tree does not
read. What the design should change: the tree reads an interactive session's held requests
from the view's `Intake` rows, as `requests(caf, name)` reads them from the table.

### new-4. The console's one start is kept in `:persistent_term`

What happened: the start must be once per VM, and IEx's new shell shares nothing with the old
one but the VM. What I did: `Console.shell/2` keeps the started app's pid in `:persistent_term`;
`Console.start/2`, which tests and the library's users call, keeps nothing. What the design
should change: say that the example app's console, an operator's IEx shell, holds one app per
VM, so this is not read as the global state the rules forbid inside the library.

### new-5. A start refused for its missing init is refused `"ended"`

What happened: `demo-unit-hello`'s row says `refused` with reason `ended`, the agent row's
reason, which says nothing of why the start failed. Why: `Delegates`' settle takes the agent
row's reason or status for a start whose agent row went free. What the design should change:
`Sessions` writes a reason that names the cause when it stops a start whose init never came
(F-152 may make it rare); `Delegates` passes it on as it does.
