# F-203: the loose ends of F-196, F-198 and F-201

Six findings of landed units, each decided in the brief. This unit builds them.

## What was built

- **An answered act whose state passed** (item 1, F-196's new-1). `Watch.pass/4` now passes an
  `answered` row whose answer is `act` by the `open` row's rule: its state not among those read
  now. The healer takes a person's act only on the state it still reads, so `acting/2` answers
  nil for a passed row, and the act is never taken. `Prompts` reads the answered and passed
  `act` rows: one whose act's row in `Acts` is open stays `answering`, whatever its state; one
  with no act's row stays only while it is `answered`, so a passed one leaves the inbox, its
  outcome "passed before its act". Any other answer stays the end of its prompt, never passed.
  `Heal.tla` holds no row of the prompt's life after the answer (its AnswerAct is one step, and
  its header already says a gap between the answer and the claim leaves no act), so no step
  changed there; the header now says the answered prompt passes with its state.
- **`run_delegate` of a waiting start** (item 2, F-196's new-3). A start that waits at a usage
  limit answers the tool `%{delegate: name, waiting: until}` at once, as `start_delegate`
  does; nothing is awaited, and the report comes later as a message. The tool's description
  and `MCP`'s doc say so. The await moved into its own function.
- **A waited resume's end reaches the fault ledger** (item 3, F-196's new-4). Modeled first:
  `Heal.tla`'s `Act` may answer `"later"` (an instancing spec's act whose outcome is read
  after; `Ended` does not count it), and `Settled` reads it `verified` or `refused`.
  `Remedies.tla`'s `ActWaits` is a main's resume that finds every account limited: the claim
  stays acted and a `waits` row opens. `WaitEnd` is that row's end (resumed, a new state;
  left; refused), and `SettleWait` the healer's settle from it. `WaitedEnd` (no wait left or
  refused is verified) and `WaitSettled` (each later outcome is read once its row ends) are
  checked, and `Break_Remedies_SettleAtWait` (the code before this unit: verified at once)
  fails `WaitedEnd`. A constant `MayWait` keeps `Remedies_Design` at its old size (59,700
  states, 27 s; with the wait it took 114 s, past the fast gate's 30 s), and the new
  `Remedies_Wait` (no delegate, a restart and a bound) checks every property with it. In the
  code, `AbsentMains` takes `mains_db:` (`Mains`' file, through `Mains.Starts`; `caf_recoveries`
  now declares `caf_mains`) and reads `mains` cues. A resume that answers `waiting` marks its
  claim `acted`, its detail naming the start's row (`start`). Each check first reads the acted
  resumes of its own actor, or of a person's claim that names it: a row `running` settles the
  claim `verified` (answer `["resumed", account]`), a row `refused` (a person's `leave`, or its
  pick refused at the reset) settles it `failed` with reason `["waited", reason]`, a fault, and
  asks, since the main is still absent. A row still `waiting` or `starting` decides nothing,
  and no second resume is made meanwhile (the state's claim holds it).
- **A start's menu is a startup dialog** (item 4, F-198's new-4). `Dialog.kinds/0` takes
  `Screen`'s `:menu` read before a session file as `:start_menu` (see new-1), kept with its
  `title`. `Dialog.startup?/1` reads it, `encode/1` writes it, `shown/1` reads the title back,
  and `press_kind/2` names it to the `Inlet` as `{:menu, title, options}`, so its press is
  the read back of F-198. `Sessions`' `shown/3` hands `decide/3` the encoded dialog, not the
  screen, and `decide/3` never asks the app's callback for a `:start_menu`: it waits on a
  person. `Config`'s `dialogs:` refuses the kind (`Dialog.preset_kinds/0`), so no default
  can be set ahead. Its prompt is `dialog:<agent>:<start>:start_menu`, kind `dialog`, its
  options with no `esc`, its text the title. The screen stand-in draws `dialogs: [:menu]` as a
  startup dialog, with no session file until it is answered. `Dialog.tla`'s header says why no
  step changes.
- **An `env` without `path` is refused for every tree** (item 5, F-201's new-2).
  `Config.new/1` answers `{:bad, :env}` for a config that runs agents too, and every doctest of
  `Config` and of the surface gives `env: %{path: "/bin"}`, but the one that shows the
  refusal. The design's config table and `Config`'s doc say so.
- **The Interventions test's race** (item 6). The reader has no interval; its only read of its
  own is the `:check` its `init` sends itself. The setup now takes that read first: its own
  `check/1`, which answers after the queued one has run, so each test's `check/1` is the only
  read of the rows that test writes. This covers all three tests, which each had the race.

## What I ran into

- The prompt id of a start's menu, had its kind been `menu`, is `dialog:<agent>:<start>:menu`,
  the shape of a running session's menu (`dialog:<agent>:<at>:menu`), and `Prompts` hands any
  id ending `:menu` to `Sessions.answer_menu/5`, which refuses a row that is not running. See
  new-1.
- The first `gate-test` failed two of `PromptsTest`'s running-menu tests: their session
  starts on a menu, its session file written first, and the start read the file, found none
  yet, then read the pane and took the menu as `start_menu`. A menu is now a start's only when
  a second read of the session file, after the pane's, still finds none (`before_file/3`); the
  trust and imports dialogs are never drawn with a file, so they need no second read.
- The model gate's fast configurations must each finish in 30 s; the wait in the design
  configuration took it to 114 s, hence `MayWait` and its own configuration.

## Findings

### new-1. A start's menu is kind `start_menu`, not `menu`

What happened: the brief names the start's menu `menu` in `Dialog.kinds/0`. Its prompt's id
would then be `dialog:<agent>:<start>:menu`, which `Prompts.answer/5` routes to
`Sessions.answer_menu/5` (a running session's menu) by its last word, so no answer could reach
it. Why: both ids put a millisecond time in the same place. What I did: the kind is
`start_menu` (`Screen`'s `:menu` read during a start), its prompt
`dialog:<agent>:<start>:start_menu`, answered by `answer_dialog/5`. What the design should
change: nothing more, unless the two menus should share one id shape; then the routing would
read the agent row's status, not the id.

### new-2. A second menu in one start reaches no person

What happened: a start's dialog answers are kept per kind, and a kind with a `sent` answer is
never pressed or asked again. A start that shows two menus no rule names one after the other
(a multi-step onboarding, say) shows the second as `start_menu` with its answer already
`sent`: the row waits on `dialog`, no prompt opens, and only its deadline's read or a person at
the viewer moves it. Why: the trust and imports dialogs each show once per start, and the
answers' key is the kind. What I did: nothing; the design text says it. What the design should
change: key a start's menu answer by its title (or its read), as a running menu's is keyed by
its read, if a start may show more than one.

### new-3. A waited resume a person left is asked again

What happened: an absent main's resume that waited at a limit and was left by a person
(`leave` on its `limit` prompt) settles `failed` and, the main still absent, opens the
absence's `remedy` prompt, `approve` or `leave`. Why: `Heal.tla`'s `Ended` asks every state
whose claim ended without a good outcome, and `ActedOrAsked` needs a state that stays to be
asked. What I did: as the model says, it is asked. What the design should change: if a
person's `leave` of the wait should also clear the absence, the settle could copy that answer
as the `Watch`'s clear (as `Recoveries` copies a `remedy` prompt's answer), and the model would
take a person's leave as asked.
