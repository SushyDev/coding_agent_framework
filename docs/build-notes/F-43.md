# F-43: a gate that each app declares every app it uses

## What was built

`gate-deps` (`MIX_ENV=test mix caf.deps`, run by `devenv test` after `gate-compile`) fails when
an app's code names a module of an umbrella app it does not declare directly, or when an app
declares an umbrella app that its code (or, for an `only: :test` entry, its tests) never names.
F-37's new-2 is why: Elixir accepts a module from any app in the dependency tree, so a use
reached through another declared app compiled.

- `CodingAgentFramework.DepsGate` (`caf_test`) is pure. `check/1` takes each app's declared
  umbrella deps, the modules it defines, and the modules its code and its tests name, and
  returns every problem sorted: `{:undeclared, app, :code | :test, module, owner}` or
  `{:unused, app, dep, :code | :test}`. Code may name only an app it declares for code. Tests
  may name an app it declares either way. `names_in/1` reads the modules a quoted test file
  names, through its aliases.
- `Mix.Tasks.Caf.Deps` (`caf_test`) only gathers and prints. For each app under `apps/` it reads
  the app's `mix.exs` deps (the `in_umbrella` ones; `only: :test` makes a test dep), the
  compile manifest `mix xref` reads (`Mix.Compilers.Elixir.read_manifest/1`: the modules the app
  defines, and every compile, export and runtime reference of its sources), and each file under
  `test/` through `names_in/1`. Hex packages are not checked.

Why `caf_test` and not the umbrella root: the root of an umbrella compiles no code of its own, so
a task there would have to live in `mix.exs` with no app to hold its tests. `caf_test` is the
app for test aids, compiles only for tests, and already has `stream_data` for the properties.
So the gate runs in the test env. It shares `_build/test` with `gate-test`.

The task gathers from the umbrella root, so a run from inside an app is refused with
`caf.deps runs from the umbrella root`.

The gate's own test (`deps_gate_test.exs`): 3 doctests, 6 properties and 1 test. The properties
generate an umbrella of two to six apps whose deps match their uses exactly, and check that it
passes in any order; that a removed dep is named once per module its code or tests use; that a
code dep made `only: :test` fails for each module the code names (and is unused when the tests
do not name it); that an extra dep is the only problem; that a module no app defines is not
checked; and that `names_in/1` reads grouped and `as:` aliases.

Lines apart from tests: `deps_gate.ex` 145, `caf.deps.ex` 93, and a few lines in `devenv.nix`,
`CLAUDE.md` and two `mix.exs` comments.

## What I ran into

- `Mix.Compilers.Elixir.read_manifest/1` has a `@doc` ("for external consumption"), but the
  `source` record it returns is Elixir's own. The task reads it through the record macro, so a
  changed field fails to compile rather than reading wrong. A manifest of another version reads
  as `{[], []}`: then every declared dep shows as unused and the gate fails; it does not pass.
- A test file is an `.exs` script: it has no manifest, and compiling one runs its module body.
  So the tests are read, not compiled (new-2).
- `devenv test` prints a gate's output only when one fails; a passing run shows `enterTest ...
  (no command)`. So I checked that a failing `gate-deps` fails it (above).
- StreamData refused my first generators (`FilterTooNarrowError`): with a one-app umbrella most
  apps had no dep to remove. The generator now makes at least two apps, each with a code use,
  and picks among the apps the property can act on.

## Findings

### new-1. `caf_stream`'s tests used `caf_accounts` without declaring it

What happened: the gate's first run failed: `stream_test.exs` builds an `Accounts.Account`, and
`caf_stream` reached `caf_accounts` only through its `only: :test` dep on `caf_cli`.

Why: F-37 read each app's uses from `mix xref graph`, which sees `lib/` only.

What I did: added `{:caf_accounts, in_umbrella: true, only: :test}` to `caf_stream`. No test
changed.

What the design should change: nothing; the gate keeps it so. F-42, which moves test cases
between apps, meets the same check when it lands.

### new-2. What a test names is read from its source, not from the compiler

What happened: a test file has no compile manifest, and compiling it runs code. So `names_in/1`
reads the quoted file: every alias, and every name written through one. It counts an alias to
the end of the file, not to the end of the module it stands in, and it does not see a module
built at run time (`Module.concat/1`) or written as an atom (`:"Elixir.…"`).

Why: the only compiler data for tests is `mix test --stale`'s manifest, which exists only after
such a run.

What I did: kept the reading syntactic, and documented the limits in `names_in/1`. No test here
names a module in any of those ways.

What the design should change: nothing now, but the gap is one way. A name the reading misses,
of an app the tests declare, can only make the gate fail (an unused `only: :test` dep). One of
an app they do not declare passes unseen, as it did before this gate; if that app is outside the
tree, the test itself fails when it runs.

### new-3. "The parts" still says a use that is not declared does not compile

What happened: "The parts" says "An app declares only the apps it uses, so a use that is not
declared does not compile". That holds only for an app the declared ones do not bring along.

Why: F-37's new-2.

What I did: left the design as it is. The root `mix.exs` comment, which said the same, now names
the gate.

What the design should change: say "An app declares, directly, every app it uses and only those;
`gate-deps` checks it, and a use outside the app's dependency tree does not compile."

## After the rebase onto F-42 (by the reviewer)

F-42 put setup that a part shares with a higher app's tests in the part's `test/support/`,
compiled in the test env. The manifest then holds those files, and the gate counted their
test-only uses as code: 11 findings, all from `test/support/`. The task now leaves sources under
`test/` out of the code it reads from the manifest; they are read with the other test files.
The gate then passes on all 16 apps, and removing `caf_shell` from `caf_stream` still fails it
(2 findings), as above.

The first run after editing the task still used its old compiled code: Mix loads the task
before its own `compile` step rebuilds `caf_test`. A second run used the new code. This matters
only when the task itself changes.
