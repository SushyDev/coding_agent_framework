# F-67: the settle tests that fail under load, and the registry property's time

## What was built

- **`Sessions` says when a settle decides nothing for a running row.** `settle_running/2` now
  writes one `Logger.debug` line, `sessions: settle of running <name> decided nothing: <why>`,
  for a row it could not settle: the `ps` failed, timed out or answered something unreadable
  (`process :unknown`), the process is gone but the socket reads live or failed
  (`process gone, socket {:ok, :live}`), or the row has no pid and start time. Nothing else in
  `sessions.ex` changed: the settle decides what it decided. `sessions.ex` reports other outcomes
  in its rows and in `notify`'s cue, which names rows and never says why, so a line was the shape
  a test can read without a new public API. `apps/caf_sessions/mix.exs` now lists `:logger` in
  `extra_applications`; that is the one file outside the brief's list, and it is what makes
  `--warnings-as-errors` accept the `Logger` macros.
- **`TestHost.await_cued/4`** (`caf_test`). Like `await/2`, but each poll first cues the server,
  then waits until the server has handled the cue, then checks. It is a helper in `caf_test`
  because two tests in two files need it. The wait on the server ends at the wait's own deadline
  and the answer is still `{:ok, value}` or `{:timeout, last}`.
- **The three waits cue on each poll.** `SessionsTest` "F-61: RunningSettled stops a running row
  whose process was killed; the name resumes", `SessionsTest` "new-9: StopTimedOut leaves the row
  stopping, late, for Recoveries" (the test just before it, whose last wait is
  `row_when(ctx, "deaf", &(&1.status == "stopped"))`) and `SessionsHeadlessTest` "a running
  delegate killed before its last reply is settled stopped, then resumed" each wait with
  `cued_row_when/4`, which is `row_when/3` with a cue (the Registry's or the Stream's, as the host
  wires it) at each poll, within the same 10 s. Each still ends with `{:timeout, row}` at its
  deadline. There is no sleep: the pause between polls is the cue and the settle it waits for.
- **A test of the mechanism.** `SessionsTest` "F-67: a ps that fails decides nothing and the log
  says why; the next cue settles": a `Sessions` whose `ps` exits 2 while a file exists leaves a
  killed delegate's row `running` at a cue and says `process :unknown`; with the `ps` running again
  the next cue settles the row `stopped`, reason `exited`.
- **`RegistryTest`'s generated-files property has `@tag timeout: 300_000`**, with the reason in
  a comment. See "What was measured".

## What was measured

### The cause of the two flakes: not shown

The brief's likely cause is a `ps` that fails or passes its 5 s under load, so that the settle
decides nothing for the one cue the test sends. I could not make the flake happen, and I did
not show that `ps` fails or is slow:

| What ran | Runs | Failures | One-minute load average at the runs |
|---|---|---|---|
| the three tests alone | 20 | 0 | 35 to 60 |
| the same, beside two streams of other apps' tests | 25 | 0 | 26 to 88 |
| the whole `caf_sessions` app, beside the same | 20 | 0 | 37 to 145 |
| the whole `gate-test`, beside the same | 6 | 0 | 33 to 68 |
| `devenv test` (every gate), beside the same | 3 | 0 | 36 to 48 |

That is 74 runs that included the tests, none red, with the debug line in place. The only
`decided nothing` lines in those logs came from tests that cause them on purpose: the `kept`
row of the F-61 test (its start time is set to another process's) and the `crashed` row of the
F-64 sampler-cue test (its socket is held live).

- The `ps` the settle runs: 5 ms at the median, 13 ms at the 95th percentile and 69 ms at the
  worst of 1 102 samples, taken while three streams of tests ran (load average about 27); 23 ms
  worst of 153 at 20. A 5 s bound is far from that.
- A killed stand-in as a zombie: `ps -p` lists a zombie as live, with its start time, so a
  settle that read between a process's death and its being reaped would see a live process and
  decide nothing, with no failed read. I killed 150 processes held under `dtach -n`, each by the pid
  it wrote, and polled the socket and the pid in a tight loop: in none was the socket gone while
  the pid was still found (load 14 to 17): the pid was gone no later than the socket, which is
  what `docs/design.md` ("A stop ends with the socket") says.
- The host was short of memory when I looked (6.1 of 7.0 GB of swap in use) and ran about 1 500
  processes. I did not look into either.

### The mechanism, forced

I patched `alive/2` for one experiment (reverted; not in the branch) so that the first `ps` read
of a `Sessions` answers `:unknown`, and ran the two tests as they were at `main`, and as they are
now:

| Tests | Result |
|---|---|
| as at `main`, one cue then `row_when` | both failed: `{:timeout, row}` after 10 s, the row `running`; the log had `settle of running killed decided nothing: process :unknown` and the same for `crashed` |
| now, a cue at each poll | both passed |

So one failed `ps` read produces exactly the failure in `docs/build-notes/F-64.md` and
`F-65.md`, the debug line names it, and a cue at each poll recovers from it. It does not show that
this is what happened in those runs.

### Under the load, after the change

Each of the four settle tests ("new-9", "F-61", "F-67", and the headless one), together in one
`mix test` run from the repository root, 30 runs in a row, twice:

| Run of 30 | Failures | One-minute load average at the runs |
|---|---|---|
| beside two streams of other apps' tests | 0 | 8 to 18 |
| beside five streams, three of them running `caf_sessions` | 0 | 16 to 71 |

The runs took 3.8 to 6.4 s, and 8.7 to 16.4 s in the second. These runs also passed before the
change (above), so they show that the change breaks nothing under load; the forced failure is what
shows it helps.

### The registry property

`mix test apps/caf_registry/test/registry_test.exs:183` alone, and a scratch copy of the property
that timed each step (deleted):

| Condition | Load average | Time |
|---|---|---|
| quiet machine (other sessions only) | 14 to 17 | 5.3, 6.4, 6.4, 5.6 s |
| beside other tests, one stream | 12 to 55 | 15.9, 25.8, 27.1, 33.1 s |
| beside two streams, 30 runs in a row | 11 to 28 | 7.7 to 23.5 s, median 14.2 s |
| beside five streams, three on `caf_sessions`, 30 runs in a row | 16 to 80 | 10.7 to 95.4 s, median 46.6 s, five past 60 s |
| in `gate-test`, F-65 | 7 to 26 | cut off at 60 s, twice in six runs |

In the scratch copy, 11.3 to 14.4 s of a 11.6 to 14.6 s run were the 45 `Registry.read` calls
(15 runs of 3 reads), about 250 to 320 ms each at load 40; on a quiet machine the whole property
took 5.3 to 6.4 s. Writing the generated files took 0.15 s in all, and the table reads 0.02 s.
The `ps` alone takes 5 ms, so `read` costs far more than its `ps`; I did not split the rest
(new-2).

**What I did: `@tag timeout: 300_000`, with the reason in a comment.** A smaller generator saves
nothing, since the cost is per read and not per file. Fewer runs would check less: 15 runs of 3
reads are the transitions the property compares. A bound of 300 s is three times the longest run
seen (95.4 s; five of those 30 runs passed 60 s, so the default would have failed them) and
finite. It passed in all 60 runs above (both sets of 30). I checked that the tag applies to a
`property` by shrinking it to 1.5 s for one run, which timed out "after 1500ms".

## What I ran into

- `mix test` from an app's directory fails in this umbrella (`the :only option for dependency
  caf_tmux … does not match`); the brief's `mix test …:176 from apps/caf_registry` does not work.
  From the root, `mix test apps/<app>/test/<file>.exs:<line>` does.
- Line 176 of `registry_test.exs` is now 183: the comment and tag came first.
- `/usr/bin/python3` is a shim that fails inside `devenv shell` ("tool 'python3' not found"), so
  the two measuring scripts ran outside it with the paths devenv exports.
- The tests print the debug line in a green run, for the two cases above. It is a line, not a
  failure.

## Findings

### new-1. The cause of the two settle flakes is still not shown; the tests now recover from it, and the log will name it

What happened: 74 runs under load (26 to 145) with the debug line, and none failed. A forced `ps`
failure reproduces the old failure exactly. A real `ps` was fast (worst 69 ms of 1 102) and the
zombie window did not appear in 150 kills.

Why: not shown. The mechanism in F-64's note is possible; I found no evidence that it happened. The
F-64 and F-65 failures came while the host ran short of pseudo-terminals and held leaked stand-ins
(F-64, new-5); I did not see that. It may be what those flakes need.

What I did: the debug line in `Sessions`, a cue at each poll in the three waits, and a test that a
failed `ps` decides nothing and a later cue settles. If a settle flake comes again, the failing
run's log says in one line what the settle saw (`process :unknown`, `socket {:ok, :live}`, or a
row with no pid and start time); with no such line, the cause is not a settle that decided
nothing, and the cue at each poll will not hide it for more than the wait's 10 s.

What the design should change: nothing yet. `docs/design.md` already says that a read that fails
decides nothing and that the next cue settles. The unit that sees the next red `row_when` on a
settle should read the `decided nothing` lines before it changes anything.

### new-2. `Registry.read` costs far more than the `ps` it runs

What happened: a read took about 250 to 320 ms at load 40, and the `ps` alone took 5 ms.

Why: not split. A read also starts the command through `Shell`, parses each file and writes each
row to SQLite.

What I did: nothing; it is not this unit's file. The property's time is the number of reads.

What the design should change: if a later unit needs reads to be cheap, measure the three parts
of a read first (the `Shell` start, the parse, the SQLite writes) and spend on the one that costs.

## Gates

Every exit status below is the command's own, and failures are counted by `^Failed:` lines and by
`Result: a/b` lines where a is not b.

- `devenv test`: exit 0, and its log ends with `devenv test: every gate ran: check-versions
  gate-format gate-compile gate-deps gate-test gate-model`. No `^Failed:` line. The one-minute load
  average read 54 before it and 36 after.
- `devenv shell -- gate-test`: three runs, each exit 0, with no `^Failed:` line, no `Result: a/b`
  line where a is not b, and 16 `Result:` lines adding up to 246 passing. The load average read
  38, 59 and 61 before them (other sessions' work).
- Before these, the same three settle tests passed 74 runs, the four after the change 60, and the
  registry property 60 (above); none of them is a measure of the cause (new-1).

What is left: the cause of the two settle flakes is not shown (new-1). If one comes again, its log
holds the `decided nothing` line.
