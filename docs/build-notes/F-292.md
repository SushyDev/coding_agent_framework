# F-292: heavy slots per host, and caf-run takes its slot on the host it runs on

## What was asked

F-280 let another host take jobs and services. Its item 3 was split out: the `Scheduler`
counted every heavy run against the workstation's slots, so a job on the second machine took the
workstation's slot. This unit gives each host slots of its own. During the build the operator
added one more item: `caf-run` took no wait of its own, so a heavy request ended at the class's
`max_wait`, and an app's wrapper that waits longer asked again at each class deadline and lost
its place.

## What was built

- **The model first**: `model/tla/HostSlots.tla`, a small spec of its own, since `Schedule.tla`'s
  seven shapes would each grow by a host for no new check of theirs. The workstation has one slot
  and another host two; three heavy runs are asked for on the other host and two on the
  workstation. Each host's pressure, and whether the other host is away, change at any step.
  `HostSlots_Design` checks `CapacityHolds` per host, `OwnHost` (a lease holds only its own
  host's slot), `OnlyGrantedHold`, `HostUnaffected` (a queued run whose own host has a free slot
  and admits it can be granted now, whatever the other host holds or reads, stated with
  `ENABLED`), `AwayRefusedAtOnce`, `NoHeavyUnderHigh` per host and `QueuedIsAnswered`. Three
  breaks each fail: `OtherHostSlot` (the brief's: a run on another host takes the workstation's
  slot, as the grant did before), `SharedPressure` (every grant reads the workstation's
  pressure) and `NoPlace` (a run asked for with no find of its host). `Schedule.tla`'s header
  names the new spec and `caf-run --wait`.
- **The `Scheduler`.** `resources:` takes `{name, host} => n` beside plain names. A name
  declared for any host is per host, and its plain name is the `Scheduler`'s own host's; a name
  declared only plain (a seat, a lock) is shared. A request names its host as `where: %{host:
  name}`, as `Jobs` names a job's; absent, it is the `Scheduler`'s own. On another host each
  per-host unit becomes that host's, and the request is refused at once `{:unknown_resource,
  {name, host}}` when the host has no such resource, or `{:unknown_host, host}` when it would
  take nothing of the host's, so it never falls back on the workstation's slot. The resolved
  units are what the queue, the hold and the grant count, and what the row keeps: another
  host's as `"<name>@<host>"` (`Scheduler.key/1`), so the count after a restart reads the rows
  alone. A key out of shape, or a name with `@`, stops the `Scheduler` `{:bad, :resources}`.
  Pressure gates only the `Scheduler`'s own host's requests.
- **`Jobs`** names its job's host in the request. A job placed on a host away is refused by
  `Hosts` before its row and its request (F-280), so it never queues.
- **`caf-run` and `Runs.Plug`.** The plug takes `host:`, and the tree gives it the
  workstation's name: the plug answers 127.0.0.1 alone, so every wrapper it serves runs on its
  own host. `caf-run` takes a wait, `--wait <seconds>` before its class or `CAF_RUN_WAIT=<seconds>`
  (the flag first), whole seconds from 1 to 99 999 999; anything else exits 64. The wrapper sends
  it as a field, its curl bound becomes that wait and 5 s, and the plug uses it as the request's
  `wait` and holds the ask 2 s past it. A wait over the plug's `max_wait:` (`Runs.max_wait/0`, an
  hour) is refused `long_wait` at once. Without a wait, the plug's `:wait` (600 s) is used as
  before.
- **The tree**: its view of `holds` reads another host's held slots by their row key; the
  config's `resources` doc names `{"slot", host}`.

## The choices

- **How a request names its host**: `where: %{host: name}`, the shape `Jobs.run/6` takes,
  absent for the `Scheduler`'s own host. The workstation's default (`"slot"`, plain) is as it was.
- **How caf-run learns its host**: from the plug's `host:`, the config's `workstation`, not an
  environment variable. The plug serves 127.0.0.1 alone, so the wrapper is always on the plug's
  own host; a variable the wrapper sent would let it name a host it does not run on.
- **Remote pressure**: another host is taken as unpressured, its heavy runs bounded by its slots
  alone. It is the smaller rule: reading it over ssh would cost an ssh per sample and a reading
  that fails while the host sleeps, and a static slot count is already how a macOS host's heavy
  runs are bounded. The model holds for every history of each host's pressure, so reading it
  later needs no new spec.
- **F-276's new-3** (a plug's wait equal to the caller's deadline raced the plug's own end):
  decided that the outcome at the wait is the `Scheduler`'s `caller_gone`, a refusal (exit 75),
  never a run without a lease. The plug holds 2 s past the wait, so that refusal reaches the
  wrapper first, and `unknown no_answer` now only says the `Scheduler` did not answer by then.

## Tests

- `caf_scheduler`: two heavy runs on a two-slot host are granted and a third queues; the
  workstation's one slot is granted beside them and its second request queues; a slot freed on
  one host goes to that host's queue only; a landing there takes that host's slot and the shared
  lock in one lease. A request on a host with no resources is `unknown_host`, one whose host
  lacks the per-host resource `unknown_resource`, and neither leaves a row; a bad `where`, a unit
  named with `@`, and a declared name with `@` are refused. The workstation's `high` pressure
  bars its own heavy run and not the other host's.
- `caf_surface/test/remote_host_test.exs`, the whole tree on the stand-in ssh: two heavy jobs on
  the other host hold its two slots while a third request queues; a job on the workstation runs
  at once meanwhile; once the two end, the third is granted that host's slot. The test of a host
  away now also finds no lease row.
- `caf_runs`: with a class `max_wait` of a minute and the plug's own wait 300 ms, a wrapper with
  `--wait 8` keeps its place past the plug's wait while one with no wait is refused `caller_gone`
  at 300 ms and one with `CAF_RUN_WAIT=1` at 1 s; the first is then granted the freed slot at
  position 1. `--wait 11` over a plug bound of 10 s is refused `long_wait`; `0`, `1.5`, `010` and
  `abc` exit 64.

## Findings

### new-1. caf-run cannot run a command on another host

What happened: F-280's brief says `caf-run` cannot use the second host's slots. It still cannot,
by design: the wrapper `exec`s the agent's command on the workstation, in the agent's worktree,
and its plug answers 127.0.0.1 alone. A slot on another host is only useful to work that runs
there, which today is `Jobs`.

Why: running an agent's native heavy command elsewhere needs the command placed there (the copy
synced, the job held, its output streamed back, its exit code returned), which is `Jobs.run/6`'s
whole path, not a lease.

What I did: `caf-run` takes the slot of the host it runs on, the workstation's, and the design
says so.

What the design should change: if agents' own `mix test` should run on the second machine, I
recommend a unit where the app's list of heavy commands may name a host, and the plug runs a
match there through `Jobs.run/6`, streaming the job's log to the wrapper and exiting with its
code (F-157's first idea). That is a mechanism of its own, so I did not build it.

### new-2. A host with no slot declared now refuses its jobs

What happened: an app that declared a host under F-280 and runs jobs there under a lease, with
no `{"slot", host}` in its resources, had those jobs take the workstation's slot. Now they are
refused `{:lease, {{:unknown_host, host}, _}}`.

What I did: made the refusal explicit rather than a fallback, and documented it in the config.

What the design should change: nothing, I recommend; the app declares its host's slots.

### new-3. The example's JSON config cannot write a host's resource

What happened: `Example.ConfigFile` reads `scheduler.resources` as a JSON object, whose keys are
strings, so `{"slot", "mac"}` cannot be written there.

What I did: nothing; the example declares no other host.

What the design should change: if the example should run another host, read `"slot@mac"` there
as `{"slot", "mac"}`, the row's own spelling.

### new-4. The tree's plug bounds are not in the config

What happened: the tree starts `Runs.Plug` with its defaults, `wait` 600 s and `max_wait` an
hour. A wrapper's wait of 1 800 s fits; an app that wants more cannot raise the bound, and an
app whose wrappers wait longer than 240 s also needs the class's `max_wait` raised, through
`parts: %{scheduler: [max_wait: …]}`.

What the design should change: if an app needs it, add the plug's `wait` and `max_wait` to
`parts` under a key of its own.
