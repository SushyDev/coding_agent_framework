# F-147: what the end-to-end run needs first

F-146 made the end-to-end run possible and found five things the run would meet. Its brief
decided each; this unit builds them, and changes the console and `docs/e2e.md` to match. No
test or step of it started the real Claude Code.

## What was built

- **A new home can start a session** (F-146's new-1). `Usage.pick/4` counts an account with no
  reading as assumed at 0 %, as a reset week is, so it comes after any account at the same
  share with a current reading. A reading of another shape (a row with only a problem), or one
  not reset but older than 6 hours, is still not known. `:unread` (no read yet) still refuses
  the start, in `Mains` and `Delegates`: nothing is known then, not even that a file is absent.
  `docs/e2e.md` no longer writes a reading by hand, and neither do `ExampleTest` and
  `ConsoleTest`: both now start on a new home.
- **The hooks' secret is kept per home** (new-2). `Intake.secret/1` reads it from
  `<home>/intake.secret`, or makes it there at the first start: 24 random bytes, URL-safe
  Base64. The file is opened exclusively, set to mode 0600 before a byte is written, and
  linked into place, so a start never reads half a secret and never replaces one; a name that
  is taken means another start made it first, and it is read. A file others may read is
  refused `{:secret_readable, path}`, and one that is not a secret `{:bad_secret, path}`; both
  are left as they are. `Example.start_link/1` reads it at every start. It changes only when a
  person removes the file.
- **The launch's `PATH` keeps `security`, and no `USER`** (new-3): `ClaudeCLI`'s doc and item
  15 say so. The config file's default `path` (F-146) already holds `/usr/bin`.
- **`Mailbox.reply/2` answers the reply's text** (new-4), beside the row's status, and the
  console's `status/2` prints it under the reply.
- **The operator answers a main session's held permission request** (new-5).
  `Mains.fix_state/3` now also names `held`, the ids of the `PermissionRequest` rows `Intake`
  holds for the session, so an answer moves the state. `Mains.answer/5` sends `allow` or a
  deny to `Intake.answer/4` only while the claimed state is still the session's and the request
  is held. `MCP`'s fixer routes the operator's `answer` of a main session there, as F-144 did
  its `resume`; its other fixes of one are still `{:not_built, :main_fix}`. The example app
  hands `Mains` its `Intake` and file. `Mains` is the second part to take `intake:` and
  `intake_db:`, so both now read them through one function, `Intake.reader/1`, and the read of
  a session's held requests is one, `Intake.Table.session/4`, which `Delegates` now uses too
  for an interactive delegate.
- **The console**: `answer_request/4` covers main sessions, and `requests/2` lists a main
  session's held requests, each with its tool and input from the hook's body, read through
  `Intake.Table` on a connection `Example.Run` opens.
- **Docs**: `docs/design.md` ("Allowance", the example app, "A permission request" of a main
  session, the reply's text, `Intake`'s transport and decider, item 15), `docs/e2e.md`, and
  `README.md`.

### The model

No spec changes. `Team.tla` already lets the operator fix any agent, a main session as its
parent, under a claim on its state (`ClaimTaken`, `CanAct`, `MainFixedByOperatorOnly`); an
answer is one more act on that claim, and the hold's single response stays `Intake`'s, as
`Hold.tla` and `Intake.tla` model it with "a person, or an agent's answer" as its decider. A
restart's protocol does not change either: no spec models the secret, and `Intake.tla` already
has a post after a restart taken, as the per-home secret now makes it.

- Removing the hand-written reading from `ExampleTest` also removed the only thing that made

- In `ExampleTest`, the operator's answer of the declared `app-main` right after its refused

  settled claim's state stays claimed (`Acts`). The test asks the answer after `end_main`,
  on a state of its own. See new-1.

## Findings

### new-1. A refused answer keeps the state claimed, so the right answer waits for it to move

What happened: `MCP` claims a fix's state before the fix checks its arguments against it, and a
settled claim's state stays claimed. An `answer` naming a request the target does not hold is
refused `{:not_held, id}` after its claim, so the next `answer` of that same state, with the
right id, is refused `{:already_claimed, by}` until the state moves. For a main session that
holds one request, nothing moves the state until a person answers on the screen or the hold
expires at 570 s. The same is true of an interactive delegate's answer. Why: `Team.tla`'s claim
is one act per state, and the check of the id belongs to the fix, which runs after the claim.
What I did: nothing in the code; `docs/e2e.md` tells the person to copy the id `requests/2`
prints, and to answer on the screen when this happens. What the design should change: check an
`answer`'s request against the state's `held` before the claim, as its label is checked, so an
id the state does not hold never takes the state.
