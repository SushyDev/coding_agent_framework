# F-99: `MCP`, part 5: `agents()`, the tree, read from the `Tracker`; `look` and `transcript`

## What was built

- `Tracker.DelegatesSource`: `Delegates`' table as a `Tracker` source, one per host, topic
  `delegates:<host>` (the one `Delegates` cues on), kind `:delegates`, scope
  `{host, "delegates"}`. `Delegates` writes as it acts, so a read's time is when the table was
  read, as `SessionsSource` does. `Delegates.Table` gained `rows/2` and `rows_by_id/3` for it.
- `Tracker.Tree.agents/1`: the tree as a pure and total function of the `Tracker`'s view, and
  `Tracker.agents/2`, which answers it from `view/2`. `MCP` keeps no copy. The answer is
  `%{agents: rows, sources: ages, problems: problems}`: each source's age (`:unread` before its
  first read), and the key of each delegate row of the wrong shape, the others still shown.
- `MCP`: the tools `agents()`, `look(agent)` and `transcript(agent, from)`. `MCP` takes three
  more required options: `:tracker` and `:stream` (`{module, server}`), and `:transcripts`
  (an account's name to its `{Transcripts, pid}`).
  - `agents()`: `Grants.may_use?/2`, then `Tracker.agents/2`, without the session id and host
    the tree keeps for the close reads.
  - `look` and `transcript`: `Grants.may_read?/3`, then the agent as the tree has it. A name
    `Grants` knows and the tree does not is `{:unknown, {:not_in_tree, name}}`; a delegate
    with no session yet is `{:refused, {:no_session, state}}`.
  - `look(agent)` for a delegate answers its state, its held requests (the tree's `waits_on`),
    the last lines of its event log and the last lines of its transcript. Each of the two reads
    answers its own refusal in its place, so a transcript not yet read does not hide the log.
    For a main session it answers `{:refused, :no_screen}`.
  - `transcript(agent, from)`: the transcript's whole lines from byte `from`, as
    `%{text, from, next}`. For a main session it answers `{:refused, :no_session}`.
  - An answer carries at most 16 KiB of whole lines. A partial last line, still being written,
    is left for the next read. A line longer than 16 KiB comes in pieces.
- `Stream.log/4` and `Transcripts.text/4`: a delegate's event log, and a session's transcript,
  from a byte offset or from `{:last, n}` bytes before the offset read so far, through the
  host's `tail` as the other reads go. They change no row. `MCP` cuts what they answer to whole
  lines.

### Where each field of `agents()` is read from

| Field | Read from |
|---|---|
| `name`, `project`, `parent`, `account` | the delegate's newest start in `Delegates`' rows that holds an agent (`starting`, `running`, `resuming`, `finished`, `failed`) |
| `kind` | `delegate` for those rows; `main` for a parent no such row names as a delegate, as `Grants` reads it, until `Mains` exists |
| a main session's `project` | its delegates' project |
| `state` | the delegate's `Stream` row, by session: `gone` once its exit is seen, `waiting` while a `can_use_tool` request is held, `working` while a turn runs, `idle` once it ended; `starting` while its `Delegates` row is `starting` or `resuming`; `unread` when its session has no `Stream` row |
| `waits_on` | the held requests in that `Stream` row: id, tool and input |
| `subagents` | the `Transcripts` row of the delegate's account and session: each subagent's type, description, state, status and tokens, oldest first |

### Left out of the answer

- `stuck`: nothing reads it yet. No row is ever `stuck`.
- A main session's `account`, `state`, `waits_on` and `subagents`: nothing reads a main
  session's session yet, so its row has only `name`, `kind`, `project` and `parent` (none).

## What I ran into

- The first version was 574 changed lines. It had its own test file with a setup nearly the
  same as `mcp_delegates_test.exs`, and the whole-line cut twice, in `Stream` and in
  `Transcripts`. The tests now share that setup, with a second project (`lib`, on the same
  repository) and its main session `lmain`; and the cut is once, in `MCP`.
- `Tracker.view/2` re-reads each source with no ids, which reads only its time, not its rows.
  So the tree is as fresh as the cues the `Tracker` was given. The embedding app must wire
  `Delegates`', `Stream`'s and each `Transcripts`' `notify` to `Tracker.cue/2`. The tests cue
  each topic with no ids, which reads it whole.
- `caf_tracker` now declares `caf_delegates`. Run alone (`mix test` in `apps/caf_tracker`),
  Mix refuses its test-only `caf_accounts` and `caf_tmux`, which other apps it declares use at
  run time. That was already so through `caf_usage` and `caf_recoveries`. The root run, which
  the gates use, is not affected.
- A delegate's name can have several starts (a refused one, then one that ran). The tree takes
  the newest start that holds an agent.

## Findings

### new-1. `look` answers the event log's raw lines, since no renderer exists
What happened: the design's `look` answers "a delegate's rendered event log". The renderer is a
later unit ("Headless delegates": `tail -F` until it exists). What I did: `look` answers the
log's last whole lines as written, JSON per line. What the design should change: when the
renderer is built, say that `look` answers its text, and that both read the same log through
one function, so the viewer and the tool never disagree.

### new-2. A start under way, or a delegate `Stream` has no row for, is none of the five states
What happened: the design names five states: working, waiting, idle, stuck and gone. A
delegate whose start or resume is under way has none of them yet, and one whose session has no
`Stream` row cannot be read. What I did: the tree answers `starting` and `unread` for these, as
"Unread is not empty" asks for the second. What the design should change: name both in the
tools' table, or say which of the five they map to.

### new-3. `Grants` and the `Tracker` read the tree each on their own
What happened: `Grants` reads the tree through a function the embedding app gives it (for now,
`Delegates`' table), and `agents()` reads it from the `Tracker`'s view, which moves on cues. For
a moment after a start, `Grants` can know a delegate the `Tracker` does not yet show. What I
did: a close read of such a name answers `{:unknown, {:not_in_tree, name}}`. What the design
should change: decide whether `Grants` should read the `Tracker`'s tree, so one read decides
both who may read and what is read.

### new-4. A read from an offset moves the whole rest of the file
What happened: `Stream.log/4`, `Transcripts.text/4` and F-93's `Services.logs/4` read through
`tail -c +N`, which prints everything from the offset to the end. A `transcript(agent, 0)` of a
large transcript moves the whole file through `Shell` to answer 16 KiB. What I did: kept the
pattern the other readers use, and cut in `MCP`. What the design should change: add `head` to
`Programs`, so each read is bounded on the host (`tail -c +N | head -c M`).
