# F-237: a subagent's transcript is read, so its tool calls show

Branch `framework/f-237-subagents`, from `main` at 6871f23 (F-234, F-235 and F-236 on it).
F-235's new-1: on Claude Code 2.1.322 a subagent's entries are in its own file, which
`Transcripts` did not read, so `Tracker.tool_calls(tracker, agent_id)` answered
`{:refused, :unknown_agent}` and a subagent's calls never showed.

## Measured

On Claude Code 2.1.322, read only: this builder's own session, with a watcher polling its
directory every 20 ms while one subagent ran two Bash calls, and the 123 subagent files of
earlier sessions in the same account.

- **Place.** `<config>/projects/<project>/<session id>/subagents/`, a directory named by the
  session id beside `<session id>.jsonl` (with a `tool-results/` next to it). The session's
  directory does not exist until its first subagent starts.
- **Names.** Two files per subagent: `agent-<agent id>.jsonl` and `agent-<agent id>.meta.json`.
  Every id seen is `a` and 16 hex digits, and is the `agentId` the parent's result names.
- **The meta.** One line of JSON: `agentType`, `description`, `toolUseId`, `spawnDepth`,
  `requestShape`, `model` and others; `finished: true` is added when the subagent ends (the
  file is written again). `toolUseId` was in 123 of 123, and each was the id of an `Agent`
  call in the parent's main file.
- **When.** The parent's `Agent` line has timestamp T. The meta was seen at T + 0.89 s and the
  `.jsonl` at T + 1.00 s, holding its first line (the prompt, stamped T + 0.78 s). The
  subagent's first Bash call started at T + 3.38 s. So both files are written when the
  subagent starts, before its first call.
- **Entries.** All 68,202 entries in the 123 files carry an `agentId` equal to the one in the
  file name. Every `user`, `assistant`, `attachment` and `system` line has `isSidechain: true`;
  the first is the prompt (`type: "user"`, `parentUuid: null`). The `api-request*` lines carry
  `agentId` but no `isSidechain`; the fold skips them by type.
- **Shape.** All 123 metas say `requestShape: "background"` and `spawnDepth: 1`. The Agent
  tool in this builder's session runs every subagent in the background, so a foreground one
  was not measured (new-1).

## The source of a running subagent's `agent_id`: its file's meta

Item 4 offered the subagent's file or `Intake`'s `SubagentStart` row. I chose the file. Its
name holds the agent id, and its meta's `toolUseId` names the parent's `Agent` call, so the
id lands on the same row as that call's description and type with no guess. Both are on disk
when the subagent starts, before its first call. A `SubagentStart` row carries `agent_id` and
`agent_type` but no call id, so matching it to one of two running `Agent` calls of the same
type would be a guess. It also exists only for a session whose app installed the hooks, and it
lives in another source the fold does not read.

## What was built

- **`Transcripts.Fold`** keeps `files`: each subagent file it has read, by agent id, with its
  own `offset`, `seam`, `tool_use_id` and `problem`. `take_file/3` folds a subagent file's
  bytes into the same fold, from its own offset, with the same seam check (`:rewritten`).
  Every entry of the file counts as that subagent's (`isSidechain` and `agentId` taken from the
  file name), so its calls go under its agent id in `agent_tools` and never into the session's
  prompts, replies or `last_event_at`. A line it cannot read is a problem with
  `file: "agent-<id>.jsonl"`. `file_meta/3` reads the meta's `toolUseId`, and `started/3` also
  looks it up for a call folded after the file. Either way, the subagent's row in `subagents`
  has its `agent_id` from its start. Also `file_read_from/2`, `file_offset/2`,
  `restart_file/2` and `file_problem/3`.
- **`Transcripts`** runs one more shell command per session on each read, after the main file:
  a `wc -c` over `<session>/subagents/agent-*.jsonl`. It finds the files by listing, never by
  id. Each file whose size is not its offset is read from its stored offset with the same
  `tail` and no byte bound, as the main file is. A file that is new or grew, and whose meta has
  not given a call id yet, has its meta read. A file that shrank or changed is read again from
  its start (`problem: "rewritten"`). A file that is gone keeps what was read of it, and its
  entry says `no_file`; one that comes back is read through its seam. A failed list or read
  leaves the whole session as it was and names it in `failed`, as a failed main read does. The
  host's programs must now name `wc`.
- **The bound** (framework-main's change to new-2, after the first review). A new file's meta is
  read before the file. A file the fold has never read, whose meta says `finished: true`, is not
  read: its calls are absent, its entry says `not_read: :finished`, and its `agent_id` comes
  from the meta, and later from the parent's result. Such a file is looked at again only when
  its size changes, and then only its meta is read, unless the meta no longer says finished.
  The first read of a running file, and the reread of a replaced one, take at most its last
  `first_read:` bytes (default 1 MB, a `Transcripts` option). The read starts one byte before
  that point and skips through the first newline, so the fold starts at a whole line. The
  entry then says `partial: true`, and the calls before that point are not known. The main
  file's fold has no read bound to reuse; the rule is `text/5`'s `{:last, n}`, which reads a
  main file's last bytes, here applied to a subagent's first read.
- **`Transcripts.Table`**: a row holds `files`, without the seams: by agent id, `offset`,
  `size` (set when a file is not read), `tool_use_id`, `finished`, `not_read`, `partial` and
  `problem`.
- **`Tracker.Tree`**: each subagent row carries `tool`, the newest call of its own file that
  has not ended, while its `state` is `:open` or `:background`, and its file's `not_read` and
  `partial`. `tool_calls/3` already answered by `agent_id` from `agent_tools`; it now has the
  calls to answer with, and answers `{:refused, {:not_read, :finished}}` for a subagent whose
  file was not read.
- Tests: in `transcripts_test.exs`, through a real shell over a temporary session directory,
  on lines of the measured shapes. A running foreground subagent's `agent_id` comes from its
  meta. Its file is found by listing. Its calls are under its agent id, not the parent's. A
  call that ends has its ms. A second file that appears after the first read is found, and its
  bad line is a problem naming that file. A removed file is `no_file` and its calls stay. A
  file made again shorter is `rewritten` and read from its start. In `tools_test.exs`: a
  subagent row's `agent_id`, description, type and `tool` while it runs, `nil` once the call
  or the subagent ends, and `tool_calls/3` by its id. For the bound: a subagent that
  finished before the first read is not read and has its id from its meta. It stays unread
  after its file grows. A running file longer than the bound is read from its last part,
  `partial`, keeping only the last call, and then goes on from its offset. In the tree, such a
  subagent row shows `not_read: :finished`, and `tool_calls/3` refuses it. Doctests on
  `take_file/3`, `take_file_from/4` and `file_meta/3`.

No model: like F-235's fold, this is a read of files already written, not a protocol over
time.

## What I ran into

- The brief says the id is in the file name. It is, but the name alone does not say which
  `Agent` call started the subagent. The meta beside it does, which I had not expected to find.
- Adding `files` changes the fold's keys again, so each stored fold is folded again from its
  start once, as F-235's new-5 describes.

## Findings

### new-1. A foreground subagent's files were not measured

What happened: every capture, and the probe run for this unit, was a background subagent
(`requestShape: "background"`). The Agent tool in this builder's session starts every subagent
in the background.

Why: the session's own setting, not a choice of this unit.

What I did: the code does not depend on the shape. It lists the directory and reads the meta,
and the tests use a foreground call (no result line). The claim that a foreground subagent
writes the same two files at its start is inferred from the code path, not measured.

What the design should change: `caf_real` should measure it once, in a session that runs
subagents in the foreground. That session should check that the meta is on disk before the
subagent's first call.

### new-2. A session's first read folded every subagent file whole (built after review)

What happened: a session seen in this account has 122 subagent files of up to 1.7 MB each. As
first built, the first read of such a session, or the first after a stored fold went stale,
read and folded all of them with no byte bound, as the main file is read.

Why: the brief asked for the same bounds as the main file, and the main file's fold has none.

What I did: framework-main read the finding and asked for the bound in this unit. It is built
as "The bound" above describes: a finished file never read is not read, and a running one's
first read takes at most its last 1 MB.

What the design should change: say that the main file's fold has no such bound. A main
transcript read for the first time is still folded whole. Also say whether a subagent that
is resumed after it finished writes a meta without `finished`. If it does not, a file marked
`not_read: :finished` stays unread while it runs again. This was not measured.

### new-3. Every read now runs a list for every session

What happened: each read of a known session runs one more shell command, the listing, even for
a session that never started a subagent.

Why: a foreground subagent's id is not in the main file while it runs, so only a listing finds
its file.

What I did: one `wc -c` run per session, however many files it has.

What the design should change: say whether a session whose fold has no `Agent` call should be
listed at all. An `Agent` line is written before the subagent's files are, so skipping that
listing would lose nothing measured here.

### new-4. A gone subagent file keeps its calls; a gone main file does not

What happened: a main file that disappears resets its fold. A subagent file that disappears
keeps its calls, and its `files` entry says `no_file`.

Why: the subagent's calls were real and its parent's row still names it. Dropping them would
leave a subagent with no calls.

What I did: kept them, and named the problem on the file's entry.

What the design should change: say which rule holds for both. A main file that is gone usually
means the whole session directory is gone, and then the subagent files go with it.

### new-5. A subagent whose meta never appears has no id until its result

What happened: a meta is read while its file is new or growing and no call id is known yet. A
meta that is missing or not yet whole is tried again on a later read, while the file grows.

What I did: no fold problem for a missing or unreadable meta. The subagent's calls are still
under its agent id, and its row gets the id from its result, as before.

What the design should change: nothing unless a release stops writing the meta. Then
`SubagentStart` is the fallback, if the design wants one.

### new-6. Nested subagents were not seen

What happened: every meta says `spawnDepth: 1`.

What the design should change: when a subagent can start its own, measure where that one's
file goes. The listing reads only `<session>/subagents/agent-*.jsonl`.
