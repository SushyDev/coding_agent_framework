# F-263: caf-login's gh step sets up git's credential helper, and its check reads it

Built by the main session.

## What happened

On a Linux host, after F-262, the first `bin/caf-login --setup` failed at the gh step, before
gh's git setup ran. On the rerun, the gh step said "the GitHub CLI is logged in already … its
login is kept" and skipped. Its check passed, and the git step reported done. But
`<home>/git` held only the signing key, no `config`, so a `git fetch` from a checkout in the home
failed with "could not read Username".

## Why

gh's login sets git up to take github.com's credentials from gh only when its question is
answered yes, and only during that login. A login kept from before, or one whose git setup failed,
leaves no helper. The gh step and its check read only gh's own status, the token's place and its
scope, never git's config.

## What was built

- `--check --gh` also reads `$GIT_CONFIG_GLOBAL` for gh's credential helper, and fails, naming
  the fix, when it is missing.
- `--gh` runs `gh auth setup-git -h github.com` after the login step whenever the helper is
  missing, and says it is kept when it is there. It does not run it twice.
- The login test's gh stand-in writes the helper at `auth login` and at `auth setup-git`. A new
  test covers a login kept with no helper: the check fails, `--gh` sets it up without logging in
  again, and a second run sets up nothing.

## Findings

None.
