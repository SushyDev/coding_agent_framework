# F-274: a session's holder leaves the app's cgroup on Linux, so the app's restart kills no agent

## What was built

- `Host` has a `scope`: `:none` (the default) or `:systemd_user`, given to `Host.local/3` and
  `Host.ssh/5` as `scope:`. `Host.scope_argv/3` gives the words that start a process in a scope
  unit: `systemd-run --user --scope --collect --quiet --expand-environment=no --unit=<unit>`,
  and none for `:none`.
- `Programs` knows `systemd_run` (`systemd-run`), found on the host's `PATH` as the others are.
- `Holder` on a scoped host needs `systemd_run` (`Holder.new/3` refuses `{:no_program,
  [:systemd_run]}` without it) and puts the scope's words before `env -i … dtach -n`. The unit is
  `Holder.unit/2`, `caf-<key>-<name>`, `<key>` the first twelve hex digits of the MD5 of the
  holder's directory. A name is at most 64 bytes of `[A-Za-z0-9_-]`, so the unit name is valid,
  and the directory is under one instance's home, so two instances on one host never share one.
  A `systemd-run` that fails answers `{:refused, {:scope, output}}`; nothing falls back to a hold
  without a scope. Every holder goes through `Holder.hold/4` (`Holder.Process`, `Services`,
  `Copies.Held`, `Sessions`), so a scoped host scopes them all: agents, services and jobs.
- `Tmux.CLI` on a scoped host runs `new_session/4`'s client through its own scope. The client
  that starts the server leaves it in that scope; a client that finds the server exits, and its
  empty scope is collected. Each such unit is new, `caf-<key>-tmux-<os time>-<n>`, since the
  scope that holds the server outlives the session it was started for.
- `Config` has `scope` for the workstation, `:none` by default. `:systemd_user` without
  `programs.systemd_run` is refused, `{:bad, :scope, {:no_program, :systemd_run}}`. The tree
  builds the workstation's `Host` with it.
- The example's config file takes `CAF_SYSTEMD_RUN` when it is set and requires every other
  program, since devenv brings no `systemd-run`.
- The design (`### Processes and restarts`) says what a scope changes: nothing for the
  framework's own stop, which still signals the held program's process group by its record, and
  on the app's restart the holders, sessions and tmux server live on and are re-adopted.

## What the embedding app sets to turn it on

1. `scope: :systemd_user` in the config.
2. `programs.systemd_run`: the host's own `systemd-run`, such as
   `/run/current-system/sw/bin/systemd-run` on NixOS or `/usr/bin/systemd-run` elsewhere.
3. In the app's own environment, `XDG_RUNTIME_DIR` (or `DBUS_SESSION_BUS_ADDRESS`), by which
   `systemd-run --user` finds the user bus. The user manager gives it to every user unit, so an
   app run as a user unit has it. `Holder` passes it on only to `systemd-run`: the held process
   still starts from `env -i`.
4. Lingering (`loginctl enable-linger <user>`) when the user manager must run with no login.
5. For a remote host, `scope: :systemd_user` in its `Host.ssh/5` and `systemd_run` in its
   programs. ssh's login session gives the remote `systemd-run` its runtime directory.

## The model

Unchanged. `Agent.tla`'s `AgentStarted` and `Start.tla`'s `Held` take the hold as one step: a
stale socket removed, then one `dtach -n` that binds the socket or is refused. The scope adds a
refusal before dtach runs, `systemd-run` failing, which leaves nothing bound, like the refusals
the specs already let a start answer. After a hold, the scope is not in the protocol: the
framework's stop signals the same process group, and a restart re-adopts by the same record and
socket. What the scope changes is which processes a stop of the app's unit reaches. No spec
models the app's unit, and the specs' restart already keeps every held process.

## Tests

- `apps/caf_holder/test/holder_scope_test.exs`, `HolderScopeTest`: the command with and without
  the scope; a scoped holder needs `systemd_run`; a stand-in `systemd-run` that fails as one
  with no user bus refuses the hold, and nothing is held; a stand-in that runs the rest of its
  words holds the process, and its words are the scope's.
- `apps/caf_tmux/test/tmux_scope_test.exs`: a scoped server needs `systemd_run`; each new
  session's client runs in a scope of its own, with two different units; a failing
  `systemd-run` refuses the start and no server runs.
- `HolderSystemdTest`, tagged `:systemd_user`, on the host's real user systemd: a transient
  service with `KillMode=control-group` stands in for the app's unit and runs the holder's
  command. Stopping the service ends an unscoped holder's process, and leaves a scoped one's
  process and live socket.
- How the gates run it: `apps/caf_holder/test/test_helper.exs` excludes `:systemd_user` unless
  `SystemdUser.available?/0` is true, that is, the host is Linux, `systemd-run` is on the
  `PATH`, and `systemd-run --user --scope true` exits 0. So `gate-test` runs it on this host and
  skips it on macOS. `SystemdUser` (in `caf_test`) names `XDG_RUNTIME_DIR` for each of its runs,
  `/run/user/<uid>` when the VM has none, as the test VM here has none.
- The `Config` doctest for a scope without `systemd_run`, and `Host`'s for `scope_argv/3`.

## Measured

On this host (systemd 261, load 3.6): ten `systemd-run --user --scope --collect --quiet
--expand-environment=no true` took 5 ms each, against 2 ms for `env -i true`. A hold costs
about 3 ms more.

## Findings

### new-1. `systemd-run --scope` expands `$` in the command it runs

What happened: the first real test held a script that wrote `"$$"`, and it wrote `$`.
`systemd-run` reads `$NAME`, `${NAME}` and `$$` in the command's words as its own variables,
with `--scope` as with a service, so a held script's `"$0"` or `"$@"` changes before it runs.
`Holder.Process`'s wrapper is such a script.

Why: systemd expands variables in command lines unless told not to (systemd 261 here).

What I did: every scope passes `--expand-environment=no` (`Host.scope_argv/3`), and the scoped
hold test runs a script with `$$` under the real `systemd-run`. A `systemd-run` too old to know
the flag would exit with its own usage error, which does not start "Failed to", so the hold
answers `{:unknown, {:dtach, 1, output, path}}`, not `{:refused, {:scope, _}}`.

What the design should change: nothing for this host. If an older systemd must be supported,
the design should say which and how its refusal reads.

### new-2. A new scope for each tmux client, since the client cannot know whether it starts the server

What happened: tmux starts its server from whichever client finds none, so `new_session/4`
cannot tell beforehand whether its client will start it. Each new session's client runs in a
new scope, and the ones that started nothing are collected at once (3 ms each, above).

What the design should change: if the tree started its tmux server once, at its start, with
one named scope (`caf-<key>-tmux`), the other clients would need none. That is a new step at
the tree's start, so I did not build it.

### new-3. A scope of the same name still running refuses the hold

What happened: a holder's unit is named from its socket's name. If dtach is gone but a process
it started still runs in the old scope, `systemd-run` refuses the new hold: "Unit … already
exists". The hold answers `{:refused, {:scope, output}}`.

Why: this is the one state where the socket is stale or absent but the scope lives on, a held
program that left dtach's process group.

What I did: nothing more. The refusal names it, and a person or the healer can stop the old
scope.

What the design should change: say whether the healer may stop a left-over scope of a stale
socket, and add it to the allow-list's remedies if so.
