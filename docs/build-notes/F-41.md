# F-41: `slow/Agent_Restarts` finishes, as two runs

`slow/Agent_Restarts` (two agents, three starts, two server deaths, one viewer death, two writes,
and liveness) never finished (F-23 new-11). It is now two slow configurations, and both finish:

- **`slow/Agent_RestartsWrites`**: its bounds with one write in place of two, and safety only.
  Every invariant, and `AgentOutlivesServer`.
- **`slow/Agent_RestartsLiveness`**: its bounds with no writes. Every invariant but the two about
  writes, and all three properties.

Both keep two agents, three starts and two server deaths. `Agent.tla` is unchanged.
`READING.md` and `bin/check-model`'s usage comment name the new configurations. The usage
comment also named `Agent_TwoAgents`, which no longer exists; it now names `Agent_Viewers`.

## What was cut, and what covers it

The brief preferred a safety run with no writes and a liveness run with one agent. I measured
both (below). The one-agent cut is not needed: the liveness run takes 57 s with two agents. One
write fits in the safety run. So the only bound cut is the writes, in two places:

- **Two writes to one, in `slow/Agent_RestartsWrites`.** In the design, a write changes only
  `writesAsked`, `delivered` and `pending`. No step reads `delivered`, and `pending` stays empty
  outside `CheckThenSend`. A lookup or a write is allowed while fewer writes are asked than the
  bound. So drop the first write of a two-write behavior and the steps that remain are still a
  behavior, with one write, that delivers the second write the same way. Every wrong delivery
  two writes reach, one write reaches too. This is an argument, not a check: two writes over two
  server restarts did not finish (below). `slow/Agent_WritesLarge` checks two writes with three
  starts over one restart, and `Agent_Writes` with two starts.
- **Two writes to none, in `slow/Agent_RestartsLiveness`.** The properties read `procs`,
  `panes`, `unviewed` and `repeating`, which no write step changes. A write step changes only
  `kept`, `pending`, `delivered` and `writesAsked`, which only write steps read, so it neither
  enables nor disables another step, and no write step is fair. `slow/Agent_RestartsWrites`
  checks the writes at these bounds.

## Findings

### new-1. Writes, not two agents, make the Agent state space large

What happened: with two agents, three starts and two server deaths, no writes give 352,948
states in seconds, one write 43,418,446 in under five minutes, and two writes ran past 139
million in 15 minutes, still growing. Liveness on two agents costs 57 s against 5 s for the same
states without it.

Why: each write adds `kept` (a pane id and an epoch per agent, re-read at any time) and the
`delivered` records, and these multiply every other variable. In the design, writes are
independent of each other, so a second write adds states but no new wrong delivery.

What I did: kept two agents and the liveness, cut to one write for the safety run and none for
the liveness run, and wrote the argument in the configuration and above.

What the design should change: when a spec's writes are independent of each other, a
configuration that adds other bounds can check one write. "The model" could say so, with the
reason written in the configuration.

### new-2. Two guards of `RecoveryClaims` each stand behind the other, and no check names either

What happened: deleting `a \notin claimed` alone from `RecoveryClaims` fails no Agent
configuration. `Agent_Claims` (with two restarts of `Recoveries`), `Agent_Viewers` and
`Agent_LateViewers` all pass, at 170,356, 736,748 and 43,074 states. Deleting
`a \notin opened` alone also passes all three. Deleting both makes `OneReopenPerLoss` fail at
once.

Why: for one reopen per loss, each guard is enough on its own. After an act, `opened` stops a
second claim until the next reading, and that reading names any loss still read as a new one. A
claim made twice before its act adds the same record to `acting`, a set. The header says more of
`a \notin claimed`: a claim cut off by a restart of `Recoveries` "is never acted on again". No
invariant or property states that, so nothing fails when a restarted `Recoveries` claims and
acts on that loss again. "The model" asks that a guard that cannot fail on its own be named in
the header as defense in depth, with the guard behind it. Neither guard is named.

What I did: nothing in `Agent.tla`. This unit does not change its behavior, and a builder does
not build a mechanism a finding suggests.

What the design should change: I recommend a step property for the header's rule, for example
"`RecoveryActs` never acts on a claim made before a restart of `Recoveries`" (a history variable
of the claims cut off by a restart). Add a `Break` value that drops `a \notin claimed`, and a
`Break_Agent_*` configuration with one `Recoveries` restart that fails it. Then name
`a \notin opened` in the header as defense in depth behind `a \notin claimed` for
`OneReopenPerLoss`. Otherwise, name both in the header as defense in depth, each behind the
other.

### new-4. `devenv test` runs no gate under devenv 2.4.0

What happened: `devenv test` exited 0 in seconds. Its last line was `Running devenv:enterTest
in 2.62µs (no command)`: the `enterTest` in `devenv.nix` (`check-versions` and the four gates)
did not run. Each gate passes when run by name in `devenv shell`.

Why: not found. This unit does not touch `devenv.nix`.

five commands in one `devenv shell`. A check that `devenv test` ran its gates (for example, a
line `gate-model` prints, looked for in the output) would stop a silent pass.
