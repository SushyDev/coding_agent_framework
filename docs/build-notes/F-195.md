# F-195: what an app's move onto the tree still wires by hand

An app that moved its tree onto `CodingAgentFramework.child_spec/1` found what it still wired by
hand or could not do. This unit builds the first four items of the brief and reports the fifth:
what the pinned Claude Code does with a `PostToolUse` answer could be read but not measured. No
test started the real Claude Code.

## What was built

- **A tree without agents** (`agents: false`, `true` by default). The tree starts only
  `Config.agentless/0`'s parts, in the tree's order: the reaper, the instance's `Registry`
  (`names`), `Cues`, `Acts`, the `Tracker`, the `Scheduler`, `Copies` and `Jobs`. `start_link/1`
  is split: what every tree takes (the home's directories, the programs, the tool state, `Jobs`'
  work reader) and what only the agents' parts take (`agents_wiring/2`: the tmux server, the
  accounts, the holder, the agent, delegate and main rows' readers, the allowance, the hooks'
  secret, the accounts' settings, the heavy commands' wrapper). The agentless tree makes none of
  the second. Its `Scheduler` has one holder, `"job"`, and no allowance. Its `Tracker` reads the
  `Scheduler`'s, `Acts`', `Jobs`' and `Copies`' tables only.
- **`agent_rows/1`**: the agent rows and delegate rows of the instance a config names,
  `{:ok, %{agents: rows, delegates: rows}}`. It opens the store read-only, reads, and closes it,
  so an app never names `caf.db` and never takes a writer's lock. It works whether or not the
  tree runs. Under it: `Store.read_only/4` (SQLite's read-only mode, no file made, `empty` for a
  table not made yet), and `Sessions.Agents.read_only/2` and `Delegates.Table.read_only/2` on it.
- **`tool_hooks` as `{module, opts}`**: the new `CodingAgentFramework.ToolHooks` behavior, an
  optional callback per hook (`pre_tool_use/3`, `post_tool_use/3`, `stop/3`), each given the
  event, `opts` and the tree's live `part` lookup, as an extension's `bundle/2` is. The hooks
  the module implements are the ones written into the accounts' settings (`Config.hooks/1`).
  `Config.new/1` refuses the old map of functions, a module with none of the callbacks, and a
  bare module as `{:bad, :tool_hooks, {:not_tool_hooks, value}}`, and options that hold a
  function, pid, port or reference as `{:bad, :tool_hooks, {:not_data, module}}`. The default is
  now `nil`, not `%{}`.
- **A restart at once** (`restart_wait`, 5,000 ms by default, a positive integer, so never
  `:infinity`). `unique/1` finds the instance's named `Registry`, monitors it, and goes on at its
  `:DOWN`. Past the bound it answers `{:refused, {:instance_running, name}}` as before.
  `start_link/1`'s doc says so. A second start of a running name now answers only after
  `restart_wait`, so the subscribe test that checks it passes a 100 ms bound.
- **Docs**: `Config`'s module doc for the three keys (a doctest for `restart_wait`,
  `agentless/0` and `hooks/1`), `ToolHooks`' module doc with an example, `start_link/1`'s and
  `agent_rows/1`'s docs, and the design's config table and "Built so far".

No spec changes. The wait at a start adds no state to any spec: every spec's whole restart
loses all memory and keeps the rows, and the wait only decides when that restart's first step
comes, after the old tree's last process ended or not at all.

## What was measured

- **The finding is real.** The new test kills a full tree under a parent of
  `max_restarts: 1`. With `restart_wait: 1` (no wait to speak of) it failed 3 times in 3: the
  parent's restart was refused, the parent ran past its budget and ended (`which_children`
  answered `noproc`). With the default it passes: the parent stays up and `subscribe/2` names
  the new tree. In every run the old tree's two ports were free by the time the new tree bound
  them; nothing waits on them, so a slower exit there would fail the new tree's endpoint.
- `SurfaceTest` and `ConfigTest`, run alone in `caf_surface`: 49 passed (17 doctests, 32 tests)
  in 10.8 s. New: the agentless tree (its parts are exactly `agentless/0`'s; a heavy job runs and
  its lease, held by `{"job", "heavy-1"}`, is released by the monitor; no `intake.secret`,
  `bin/caf-run` or `accounts/`; `agent_rows/1` answers none); the restart; the tool hooks as a
  module whose `post_tool_use/3` reaches the live `Mailbox` through `part`; and the config's
  checks of the three keys.
- **What Claude Code 2.1.322 does with a `PostToolUse` answer, read from its bundle, not
  measured.** A `PostToolUse` hook's `hookSpecificOutput` has two fields that replace a tool's
  output. `updatedToolOutput` ("Replaces the tool output before it is sent to the model") works
  for every tool, built-in ones such as `Bash` and `Edit` included. `updatedMCPToolOutput`
  ("Replaces the output for MCP tools only. Prefer updatedToolOutput") is used only for an MCP
  tool and only when `updatedToolOutput` is absent. An `http` hook's body goes through the same
  parse as a command hook's output, which keeps both fields. Neither replaces the output of the
  tools whose output hooks may not replace (a person's words and a plan among them). Hooks run in parallel on the original output, and the last rewrite wins. A
  separate path drops a replacement in "a hook's answer that came over the network"; it sits
  beside a remote transport's control responses, not the `http` hook's parse, so it reads as a
  remote session's relayed answers. I could not confirm that from the minified code. The
  model-in-the-loop measure the brief asks for needs a logged-in Claude Code (new-1).
- Gates: see "Gates" below.

## What I ran into

- `Jobs.run/6` needs its directory to be a git repository. The agentless tree runs no `Mains`,
  so no checkout is cloned, and the test runs its job in the project's own repository.
- The agentless test sets the config's `projects` and `mains` as every surface test does.
  Nothing reads them, since `Mains` does not start.
- The tool hooks' test sends to the test process. A pid is not data, so the test registers
  itself under a unique name and passes the name.
- The `Scheduler` asks about a lease only the owner named for its holder's kind and keeps the
  answer unknown for any other kind. So an agentless tree on a home that an agentful tree used
  keeps a delegate's, main's or run's lease unreclaimed. The doc of `holders/1` in the tree says
  so (new-2).

## Findings

### new-1. The `PostToolUse` measure needs a logged-in Claude Code

What happened: the brief asks to measure which `PostToolUse` output changes what the model reads,
with a stand-in hook in a scratch config directory. A scratch `CLAUDE_CONFIG_DIR` is not logged
in (`claude auth status`: `"loggedIn": false`). No API key or token is in the builder's
environment, and the repository's rules forbid touching any other Claude config directory. So
no model turn could run. Why: a login belongs to a person, and the macOS Keychain item is per
config directory. What I did: read the pinned bundle (above) and built nothing of item 5, as the
brief says to build only what the measure shows. What the design should change: nothing yet.
Either a person logs a scratch config directory in (`CLAUDE_CONFIG_DIR=<dir> claude auth
login`) for a builder's measure, or the main session measures on its own hooks, as F-171's
counts were. The run to make: a `PostToolUse` command hook that answers `updatedToolOutput`
(and, in a second run, `updatedMCPToolOutput` alone) for `Bash` running `echo ORIGINAL` and for
an MCP tool, the prompt asking the model to quote the output it read. Then the same as an `http`
hook on a local port. If `updatedToolOutput` is taken from an `http` hook, item 5 is: the
`PostToolUse` post held as a hold of its own kind, the app's `post_tool_use/3` asked within the
hook's timeout less a margin, its answer encoded as `updatedToolOutput`, and past the deadline an
empty body with the pass recorded in a row.

### new-2. An agentless tree leaves an agent's lease unreclaimed

What happened: a tree with `agents: false` asks only `Jobs` about a lease. A lease that a
delegate, a main or a heavy run took under an earlier agentful tree on the same home is asked of
no one, so the `Scheduler` keeps it unknown and never reclaims its units. Why: the owners that
answer for those holders read agent rows, and the agentless tree reads none. What I did: nothing
more than the doc. What the design should change: say that a home is agentful or agentless for
its life, or give the agentless tree the pure readers of the other holders' rows (they start no
process).

### new-3. `topics/1` lists the topics of parts that did not start

What happened: an agentless tree's `Cues` takes the whole tree's declarations, so `topics/1`
lists `sessions:*` and the rest, and `subscribe/2` takes them, though no part there writes them.
Why: `reads/0` and `writes/0` name every part, not the started ones. What I did: nothing.
What the design should change: whether a subscription to a topic no started part writes is
refused, or kept for the day the parts start.
