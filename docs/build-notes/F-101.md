# F-101: a read from an offset takes only what it answers

## What was built

- `head` joins `Programs` (its name, type and doc), `devenv.nix` (`CAF_HEAD`) and `TestHost`.
- `Jobs.log/4` and `Services.logs/4` take `:max` (bytes, default 16 KiB). The host runs
  `tail -c +N file | head -c M` as one `sh -c` script, with both programs from `Programs`. `next`
  is still `offset + byte_size(text)`.
- `Transcripts.text/4` takes `:max`. With it the host runs the same pipe; without it the read
  runs to the end, as before. `nofile` is still answered first.
- `MCP`: `service_logs` passes `max: 16384`; `transcript` and `look`'s transcript pass the
  window plus one byte. The extra byte keeps `lines/2` able to tell a line longer than the window
  from one that fits exactly, so a long line still comes in pieces.
- A pipe hides the tail's status, so each script checks `[ -r file ]` first (a log that cannot be
  read still answers `{:unknown, {:log, …}}` or `{:sh, 1, …}`). The tail's `2>/dev/null` keeps its
  broken-pipe complaint, once head has its bytes, out of the text: `Shell` merges stderr into the
  output.

## Reads that stay to the end, on purpose

- `Transcripts`' fold (`read_one`, and the fold again after a rewrite): it must see every new
  event to keep its offset right.
- `Transcripts.contains/6`: it looks for a prompt anywhere after the offset.
- `Services`' line wait (`met/3`): it must see every new line, and a bound would hide a match
  past it.
- `Jobs`' end answer (`tail -c N`): already bounded, from the end.

## What was measured

A 4,100,000-byte file read from its start, local host, best of five (`Shell.run`, in a throwaway
script):

| read | bytes through `Shell` | time |
| --- | --- | --- |
| before: `tail -c +1 file` | 4,100,000 | 7 ms |
| after: `tail -c +1 file 2>/dev/null \| head -c 16384` | 16,384 | 12 ms |

The bytes are the point: 250 times fewer here, and over ssh they are what crosses the network. Time
is no better locally, where a pipe is cheap and a local copy of 4 MB is cheap; the `sh` and `head`
starts cost a few ms.

## What I ran into

- The first version printed `tail: write error: Broken pipe` into the answer: `Shell` merges
  stderr into the output, and `tail` complains once `head` has closed the pipe. Tests with logs
  under the pipe's buffer (64 KiB) did not show it; the tests now use logs of 200 KB to 1 MB.
- A job's log is written by dtach's own process, so it can still be coming when the job's exit is
  known. The new `Jobs` test waits for the whole log before it reads.

## Findings

### new-1. `Stream.log` reads to the end of the event log

What happened: `Stream` (`caf_stream`) has the same `tail -c +N` read, and `MCP`'s `look` calls
it with `{:last, window}`, which still moves everything after that offset. The brief did not name
`Stream`, so it was not touched. Why: the same cause as F-99 new-4. What the design should
change: the same bound, as one more unit (`:max` on `Stream.log/4`, passed by `look`).

### new-2. A bound makes a line longer than it come in pieces

What happened: a read of `max` bytes may end inside a line, so a caller that answers whole lines
(`MCP`'s `lines/2`) trims it and sets `next` at the last newline; a log or transcript with a line
longer than the window is answered in window-sized pieces, as it was. Nothing to change; it is
noted so a later caller does not take a bounded read to end at a line.
