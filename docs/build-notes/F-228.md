# F-228: a permission dialog no reading names reaches a person

## What was built

The generic menu reading (F-198) takes the shape of a permission dialog that no reading names:
- **Footer:** one of the release's menu footers. On 2.1.322 these are "Enter to confirm · Esc
  to cancel" and the permission dialog's "Esc to cancel · Tab to amend" (`menu: %{footers:
  [...]}`; it was one `footer`).
- **Drawn in the box's place:** under its footer there may be only the box's named rule as the
  screen's last line, with no box.
- **Inner rules:** its rules of `╌`, around the tool and its input, are left out of the detail.

So the screen reads `%{state: :dialog, kind: :menu, title, detail, options, selected}`. A running
interactive session's menu reaches the inbox as F-198 built it (`Menu.tla`), with its options
and `esc`, no default and no deadline. The known dialogs (trust, imports, the permission dialog
titled "Do you want to proceed?", the usage limit's menu) read as before. A permission dialog
whose question no reading names is now a menu to a person, not an unrecognized screen. Its test
changed with it.

A fixture, `permission-read-outside.{ansi,txt}`: the last 18 lines of a live pane, with its
manifest entries. The read path and the session's name are replaced.

## What was measured

On 2026-11-23 about 15:15, a main session (2.1.322, a 168x46 pane) waited minutes on "Allow
this read outside the working directories?". Its tracker row read "Idle", and no ask reached the
inbox. The 2.1.322 reading missed it three ways: `:permission` needs the title "Do you want to
proceed?"; the menu fallback needed the footer "Enter to confirm · Esc to cancel"; and the
dialog takes the box's place, ending with the box's named rule. The embedding app reported it.

No model changed: this is a screen's reading. `Menu.tla` already models a menu's prompt and
its press.

## What I ran into

The first gate run failed `MoverTest`'s "a resume the first line cannot answer leaves the row
down at its deadline" (F-212), the same race F-227 fixed in a sister test: it passed the deadline
right after the first answer, then counted three asks. The test now cues and waits for three before
the deadline, and passed 16 of 16 six times. This change does not touch `Mover`.

## Findings

### new-1. The live session's own screen was the only capture

What happened: the dialog appeared on a working session, and its capture survived only because
it was copied before the person answered it. Why: no capture of an unknown screen is kept.
What I did: nothing beyond the fixture. What the design should change: when `Screen` reads a
running interactive session's pane as unrecognized for longer than a look or two, `Sessions`
could save that capture (scrubbed of the home's paths) under the home for a fixture, and raise a
symptom, so an unknown dialog is seen even when no person reports it.
