# F-51: `Stream.tla` models a resume and the end

**Stopped before the code.** The brief says to stop if the spec shows that the design's resend
rule cannot hold. It shows that: with a restart and a resume, the resend and a line from before
the exit go into the resumed process together and mix (new-1). This branch changes only the
spec, its configurations and `READING.md`. `Stream`, `Stream.Fold` and `docs/design.md` are
unchanged.

## What was built

- **`Stream.tla`** gains a resume, Claude Code's drop of a known uuid, and the end:
  - `FollowAgain` (the row followed again: `gone` and `seen` cleared, `idle` set, the offset,
    messages and requests kept) and `ProcStarts` (Sessions starts the resumed process on the same
    FIFO, log and transcript).
  - A message's lines are `<<m, gen>>`. One found undelivered is marked again, first, as a new
    line and a new spool under its same uuid (`UuidOf`). `heard` is the transcript across
    processes. `DropMsg` is `skipDuplicate`: a user line whose uuid `heard` holds is answered by
    its replay and starts no turn. 2.1.322's source shows the ack (`Sending acknowledgment for
    duplicate user message`, then `continue`): no `result` follows it.
  - A claim command writes a message line in two parts (`CatBegins`, `CatEnds`), since a
    message is longer than the pipe's atomic size, and a line put between them mixes with it.
    It opens the FIFO only while a process reads it. One left waiting at an exit goes into the
    next process that opens the FIFO, or is ended at its deadline (`ClaimTimesOut`).
  - `Mark` needs the write's live check (`alive`, which also sets `seen`), no end marked, and
    every earlier message delivered. `ExitSeen` needs `seen` and this run's claims ended (a
    claim is one synchronous call).
  - A replay of a row found undelivered settles it delivered and clears `idle`: it is a line that
    went in after the exit, and its turn runs.
  - The end: `EndMarked` once the turn ended, the report is delivered and no message is under
    way; `EndClaimed`; `TakeEnd` ends the process, and cuts a turn that runs. `ReportDelivered`
    is the parent's part, left abstract.
- **New checks**: `EndNeverCuts`, `EndAfterReport`, `ResentOrGone` and `IdleReturns`.
  `TakenOnce` is the invariant that no message is run twice, counting the drop. Before, it
  followed from `WrittenOnce`; now a resend is a second line, so `TakenOnce` holds only because
  of the drop. `UndeliveredWasNotTaken` now holds while the exit is seen (`gone`): after a resume,
  a line that was waiting may still go in.
- **Breaks**: `NewUuid` (the resend gets a new uuid: `TakenOnce`), `KeepIdle` (the follow again
  keeps `idle`: `IdleReturns`), `NoReportWait` (`EndAfterReport`). The end's wait for the turn
  is defense in depth behind its wait for the report, so it has no Break (see the header).
- **Configurations**: `Stream_Resume.cfg` (two messages, a request, a resume, no restart) and
  the three Break configurations. Every older Stream configuration has `MaxResumes = 0`, and the
  design ones also check the end's two invariants.

## What I ran into

- A claim command waits in `open` while no process reads the FIFO, and a later reader of the
  same path releases it. Checked on this Mac: a writer waiting on `in` writes to the next
  `cat in`, and it stays waiting on the old inode once `in` is removed and made again.
- `skipDuplicate` in 2.1.322 does more than drop: if the transcript holds the uuid but its turn
  went unanswered, it may run the line again (`turnUnanswered`, `leftToReRun`). See new-4.

## Findings

### new-1. A claim waiting at the exit goes into the resumed process beside the resend

What happened: TLC's trace, one message: `Mark`, the delegate exits, `Claim` (its command waits
on the FIFO, which no process reads), the framework restarts (the claim call is gone, so nothing
ends the command at its deadline; `Recoveries` ends it only later), `ExitSeen` (the transcript
lacks the uuid: undelivered), `FollowAgain`, `ProcStarts` (the resumed process opens the FIFO,
which releases the waiting command), `CatBegins`, then the resend's `Mark`, `Claim` and
`CatBegins`. Two message lines are in flight at once and mix, so the session ends
(`NeverMalformed`). Without `NeverMalformed`, a second trace: the waiting line goes in, the
resumed process takes it and exits before its replay is read, and the row stays undelivered
though Claude Code ran it (`UndeliveredWasNotTaken`). The same path would let an end left
waiting end the resumed process at its start (not modeled).

Why: "Writes are lines, claimed once" keeps one message line in flight per delegate. That holds
for one process: a claim's call waits for its command, and a dead process takes the pipe with
it. A resume reuses the FIFO's path, so a command from before the exit can write into the next
process. The drop of a known uuid stops a double run (`Break_Stream_NewUuid` fails without it),
but not the mix.

What I did: stopped before the code. `Stream_Resume.cfg` has no restart. The spec's header names
this as open.

What the design should change: give each process its own FIFO, and have a claim name the FIFO of
the process it was started for. For example, `in.<n>` with `n` the row's resume count: the
wrapper (which since F-53 also writes `pid`) takes the FIFO's path, and `Stream.follow/5`
makes the new one on a follow again. F-53's "A stop ends with the socket" does not cover
this: a stop waits for the process and its socket, not for claim commands. A
command from before the exit then waits on a FIFO no process reads until its deadline, and its
line never reaches the resumed process. Replacing `in` at the same path is not enough: a command
that has not reached its `open` yet would open the new FIFO. On a copy of the spec with this
change, every check passes (table above), and so does `NewUuid`. "Undelivered" is then final,
the resend is never a duplicate, and the drop is defense in depth. "Delivered once, seen" should
say so, and "Held, apart from the framework" should name the FIFO per process. This touches the
wrapper (`ClaudeCLI`) and `Sessions` as well as `Stream`. If the design keeps one FIFO instead,
a follow again must wait until no claim command of the session can still run.

### new-2. A cut line at the log's end joins the resumed process's first line

What happened: `Die` leaves a line cut without its newline (`Cut`). A resume appends to the same
log, so the resumed process's first event joins the cut line. Neither parses, so the fold
counts one problem, and that event is lost. In the stand-in that first event is `system`/`init`,
whose session id a resume in `Sessions` waits for (`{:live, :no_first_event}`), so the resume
would never settle. Whether Claude Code writes `init` first is the release check's to say.

What I did: `ProcStarts` drops the cut line, and the header names this as left abstract.

What the design should change: the follow again ends a cut last line with a newline before the
new process starts (the old process is gone, so no one else writes the log), so the cut line is
one problem and the next event is whole. Then model it in `ProcStarts`.

### new-3. A process that exits before a read sees it live is never seen gone

What happened: `ExitSeen` needs `live_seen`, which only a read that finds the socket live sets
(F-49). A resumed process that exits before such a read leaves the row neither live nor gone,
and a message undelivered at the earlier exit waits for good. TLC found it for `ResentOrGone`.

What I did: `Mark` sets `seen` (a write's check found the socket live), which the code does not
yet do. `ResentOrGone` and `IdleReturns` name this case as `Unseen`.

What the design should change: set `live_seen` from the hold, not from a read. `Sessions` knows
it held the process, so it can tell `Stream` (a follow after the hold, or a call after it). The
write's live check should set it too, as `Mark` does here.

### new-4. 2.1.322 may run a known uuid again when its turn went unanswered

What happened: `skipDuplicate` checks `persisted(uuid)` and the uuids received, and then
`turnUnanswered` and a re-run rule. A line whose turn the transcript shows cut off can be run
again. The design and this spec take the drop as plain.

What the design should change: add the drop to the check against each pinned release, with a
cut-off turn. Under new-1's FIFO per process, the framework does not rely on the drop.

### new-5. The end's wait for the turn is defense in depth behind the report

What happened: the report is delivered only while `idle`, and `Mark` clears both, so
`EndMarked` without its `idle` guard still never cuts a turn: no Break can fail on it. F-49's
`Fold.check/2` checks only the turn. Nothing in `Stream` knows the report: the parent's delivery
is `Delegate.tla`'s, and `ReportDelivered` here is abstract.

What the design should change: say who checks the report before a delegate's end (`Sessions`
when it stops a delegate, against the parent's row) and keep `Stream`'s turn check as defense
in depth. "Ending" should also say that an end refuses a message under way or found undelivered,
and that a message is refused once an end is marked. The spec has both; the code has neither.

### new-6. A follow again keeps `idle`, so a delegate that exited during a turn is never written

What happened: F-49's follow again clears `gone`, `live_seen` and the session id but keeps
`idle`. A process that exited during its turn leaves `idle` false, the resumed process starts
no turn, and every write is refused `:turn_running`. `Break_Stream_KeepIdle` is this.

What I did: the spec's `FollowAgain` sets `idle`. The code is unchanged (the stop).

What the design should change: nothing; the code change waits for new-1.
