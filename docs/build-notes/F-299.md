# F-299: the framework's busy processes in a live app cost less CPU

An embedding app's BEAM averaged 156% CPU on a loaded host. A snapshot of reductions put the
`Tracker` first (14.4M in 5 s), then `Transcripts` (5.0M), the `Scheduler` (1.7M) and
`HooksSilent` (1.1M). At load 40 a delegate start's `Scheduler.request` answered
`{:unknown, {:timeout, 5000}}` three times in 16 minutes, so no builder could start.

This unit measures the four on stand-ins and fixes three of them: the `Scheduler`, the
`Tracker` and `HooksSilent`. `Transcripts` is split out (new-4).

## Measured

All numbers are from one test VM on the shared host, under its load, so a time is a rough
guide; reductions and counts are the firm part. The measurement tests were scratch files and
are not committed. The committed tests count the work instead.

### The `Scheduler`

The stand-in had 20 granted leases, each monitored, whose owner answers `:live` at once, and
4 queued requests. It got 200 cues in a row.

| | main | F-299 |
|---|---|---|
| reductions per cue | 13,456 | 46 |
| µs per cue | 1,216 | 1–160 |
| owner asks per cue | 20.0 | 0.1 |
| statements prepared per cue | 21.0 | 0.01 |
| owner asks for 51 cues that queued behind one held check | 1,020 | 40 |

- **What fills the mailbox: cues.** `Scheduler.reads/0` takes every cue of `sessions`,
  `delegates`, `mains`, `jobs` and `usage`. On main each one was a full check: one `SELECT`
  per monitored lease (`Table.get/2`), one owner ask per lease, then a pass of the queue
  (`Table.held/1`, one more `SELECT`). So with 20 leases one cue cost 21 prepares and
  21 fetches, about 1.2 ms on this host. In the app the snapshot's 1.7M reductions in 5 s is
  about 25 cues a second at this cost. A request waits behind every cue queued before it.
- **The owners cost more than the stand-in.** A `"run"` lease's owner (`Runs.state/2`)
  runs `ps` through `Shell` for each lease on every check. A delegate's owner may read
  `Delegates.Table.latest/2` for the host. All of that runs inside the `Scheduler`
  (new-2).
- **Pressure re-checks** cost nothing here. A sample is read every 2 s, and the queue is
  served only when the level changes. **Waiting-queue passes** read the unreleased rows once
  per pass. A **request** costs 3 prepares and 7–21 ms on this host. Most of that is its
  row's write and commit. It was the same before and after.
- **Prepare.** Each `Store.query/3` prepares its statement again. Per check that was 21
  prepares; now it is 2. I did not add a statement cache. The repeat was in the number of
  queries, not in the prepare itself.

### The `Tracker`

The stand-in sources were memory sources (`Tracker.Source`): one of 28,000 event rows of
about 600 bytes, one of 40 agent rows, and 15 of 200 rows, all in one scope.

| | main | F-299 |
|---|---|---|
| a cue of 1 row of the 28,000-row source: reductions | 352,869–399,874 | 120 |
| a cue of 1 row of the 40-row source: reductions | 148,359–221,514 | 120 |
| `view/1` (the whole view): reductions in the `Tracker` | 1,129,318–1,189,712 | 490,700 |
| `view/1`: µs | 56,661–86,239 | 21,157 |
| `view/1`: words copied to the caller | 1,386,154 | 1,386,154 |
| `view(parts: [:agents])`: reductions / µs / words copied | (not an option) | 2,670 / 37 / 2,120 |
| `agents/1`: reductions in the `Tracker` / in the caller | 1,096,910 / 840,399 | 1,336,623 / 34 |
| `agents/1`: µs | 56,122 | 16,598 |
| `agents/1`: words copied to the caller | 1,386,154 (the view) | 20 (the tree) |

- **A read rebuilt what had not changed.** `Fold.read/4` found the changed keys by comparing
  every row of the topic, old against new, even for a read of one id. So each cue of one
  intake row compared all 28,000. `view/2` and `behind/3` first re-read each source's newest
  read with `ids: []`, so each one paid that for every source as well.
- **A view built and copied every row of every source.** Each call built an entry per row
  and copied the whole view to its caller (11 MB here; 17 MB of intake rows and 2.4 MB of
  transcripts in the app). `agents/2` did that too, then folded the tree in the caller.

### `HooksSilent` and `Transcripts`

`HooksSilent` checks at each cue of `transcripts` and `intake`, and an intake row is written
for every hook. Each check calls `Transcripts.text/5` once per running agent for the last
64 KB of its transcript. `Transcripts` runs `tail` through `Shell` for that, a spawned shell
whose output `Shell.collect/6` gathers. So `HooksSilent`'s queue in `gen:do_call` is the
cues that came while it waited in `Transcripts`. `Transcripts`' own queue is those calls,
behind its reads, each of which is a shell too.

In the stand-in test, seven checks at two offsets made seven `{:text, …}` calls on main and
make one now (the test in `hooks_silent_test.exs`).

## What changed

- **`Scheduler`** (`scheduler.ex`):
  - A `:check` cast drains the `:check` casts behind it. One check asks each owner afresh,
    and a cue is sent after the write it tells of, so it answers every cue queued before it.
    Only `{:"$gen_cast", :check}` is taken from the mailbox, so requests, deadlines and
    monitors keep their order. A cue whose owner answered `{:unknown, _}` is not re-asked
    until the next cue or tick, as before.
  - A check reads the unreleased rows once (`Table.unreleased/1`) instead of one
    `Table.get/2` per lease. A lease id not among them was released, and is forgotten.
  - `Schedule.tla` has no cue: `Release` and `Reclaim` are steps the scheduler may take at
    any time, with weak fairness. So fewer checks change no order the model checks.
- **`Tracker`**: I chose the `parts:` option over a view kept and updated from the cues,
  because the app reads only the agents and the tree, and the option keeps every view a
  plain function of the fold. A kept view would need a second copy of every row kept in step
  with it.
  - `Fold.read/4` compares only the ids it read and the keys of the rows it got. Nothing
    else can change on such a read. A read of `:all` compares every key, as before.
  - `Fold.view/3` takes the kinds to build; `Tracker.view/2` takes `parts:`. The asked
    kinds are built as the whole view builds them; `sources` and `age` are still every
    source's.
  - `Tracker.agents/2` and `tool_calls/3` fold in the `Tracker`, from a view of
    `Tree.kinds/0` (the kinds `Tree` reads), and reply with only their answer. A fold that
    raises answers `{:unknown, {:raised, message}}` and leaves the `Tracker` as it was.
  - With `groups:`, `agents/2` reads the running agents from a view of `[:agents]`, reads
    their groups in the caller as before, then asks for the tree. That is two calls, so an
    agent that starts between them shows no groups until the next read (new-3).
  - For a given fold, the view of a kind and the tree are the same as before. The property
    tests still pass, and the new tests check that the parts and the tree equal the whole
    view's.
- **`HooksSilent`**: it keeps each running agent's newest tool call with the offset
  `Transcripts.offset/4` answered when it was read. While the offset has not moved, the
  call is reused and no tail is read. `Transcripts.text/5` with `{:last, n}` reads the
  `n` bytes before that offset, so the same offset gives the same bytes. This is the use
  F-261 gave `offset/4`. An agent no longer running is dropped from the map.

## Tests

Each new test fails on main and passes now. Each counts the repeated work, not time.

- `scheduler_test.exs`, "cues queued while a check runs…": an owner holds one check while
  20 cues queue; the owners are asked 6 times (two checks of 3), 63 on main.
- `scheduler_test.exs`, "a request read after its caller timed out…": the F-289 hazard
  below. It passes on main too; it pins the release.
- `tracker_test.exs`: a cue's `Fold.read/4` on 5,000 rows costs fewer reductions than there
  are rows; a `parts: [:agents]` view has no other kinds, and its agents equal the whole
  view's; `Tracker.agents/2` equals `Tree.agents/2` of the whole view, and what the
  `Tracker` sends its caller is under a tenth of the view (traced on the test's own
  `Tracker`).
- `hooks_silent_test.exs`, "a transcript is read again only once…": seven checks at two
  offsets make one `{:text, …}` call into `Transcripts` (traced on the test's own process).

## The F-289 hazard: a request applied after its caller gave up

It can happen. `Scheduler.request/3` is a `GenServer.call` with a 5 s bound. When the call
waits in the mailbox past that bound, the caller gets `{:unknown, {:timeout, 5000}}`, and
`Delegates` refuses the start and writes its row `refused`. The `Scheduler` still reads the
request later. If it fits, the grant is written in that step with no requester yet, so
nothing reads whether the caller has gone. The request's `wait` is relative to when the
`Scheduler` read it, so it does not help.

The seat does not leak for good. The lease is monitored from its grant. At the next check (a
cue or the interval) `Delegates.Work.state/2` reads the refused row as ended once its agent
row is free, and the lease is released. The new test shows that: the late request is granted,
then released by the monitor at the next cue. Until then the seat is held, and on a host
slow enough to time a call out, the next check may also be slow.

`Schedule.tla` does not see this. `Ask` receives the request in the same step as the caller
asks, and `CallerGone` comes only after it, so `NoGrantToGone` holds in the model. It does
not hold for a call read after its caller's bound (new-1).

## Findings

### new-1. A call read after its caller's bound is granted to a caller that has gone

- **What happened:** a `Scheduler.request/3` that waited in the mailbox past its 5 s is
  granted, though its caller was told `unknown` and refused its start. The seat is held
  until the next check.
- **Why:** the request's deadline is counted from when the `Scheduler` reads it, not from
  when the caller sent it. `Schedule.tla` makes the receipt atomic with the ask, so the
  model cannot show the gap.
- **What I did:** nothing in the code. A test pins that the next check releases it. The
  drain makes the mailbox much shorter, so the gap is rarer.
- **What the design should change:** the call carries its caller's deadline: the monotonic
  time it was sent plus its timeout, both on one node. The `Scheduler` then refuses a call
  read past it with `caller_gone`, never granting it. Model it first: in `Schedule.tla`,
  split `Ask` into a send and a `Receive` with `CallerGone` allowed between them, and check
  `NoGrantToGone` there.

### new-2. A run lease's owner runs `ps` inside the `Scheduler` at every cue

- **What happened:** each check asks each `"run"` lease's owner, and `Runs.state/2` runs
  one `ps` through `Shell` per lease. It runs inside the `Scheduler`, at every cue of five
  topics, none of which tells of a run's end.
- **Why:** the design asks each owner "at each cue of the owner's rows", but every owner is
  asked at every cue, and a run's end is read only from its process.
- **What I did:** the drain bounds it to one check per backlog. Nothing else.
- **What the design should change:** ask the `"run"` owners on the interval only. Or give
  `holders:` a batch form, so all run leases are read in one `ps`:
  `Holder.Process.liveness/3` already takes a list. Either way, the owner asks belong in a
  task, not in the `Scheduler`'s own step. That last one is a protocol change, and would be
  modeled first.

### new-3. `Tracker.agents/2` with `groups:` reads the view twice

- **What happened:** to keep the groups read in the caller and the tree folded in the
  `Tracker`, `agents/2` makes two calls when `groups:` is given.
- **Why:** the design reads the groups in the caller's process (F-259), and only the tree
  should be copied out.
- **What I did:** two calls. An agent that starts running between them shows no groups
  until the next read, as one on a host with no reader does.
- **What the design should change:** if that is not acceptable, the groups read could run
  in a task the `Tracker` starts and awaits under the call's bound.

### new-4. `Transcripts` reads every tail through a shell

- **What happened:** every read of a transcript, a tail for `HooksSilent` or a
  subagent list, spawns `sh` with `tail`, `head` or `wc` through `Shell`, even on the
  local host. `Shell.collect/6` is where the snapshot found it.
- **Why:** the design reads a host over ssh the same way as the local one, so one path
  serves both.
- **What I did:** nothing in `Transcripts`. It is split out: `HooksSilent` no longer asks it
  for a tail whose offset has not moved. That was the repeated call.
- **What the design should change:** on the local host, read with `:file.pread/3` from the
  stored offset and keep `Shell` for other hosts. It is a decision about `Transcripts`'
  one path, so it is the design's to take.

### new-5. The tree is still rebuilt from every event row at each call

- **What happened:** `Tracker.agents/2` still builds an entry for each of the intake rows
  and folds them all, about 1.3M reductions per call on 28,000 rows. Only the copy is gone.
- **Why:** `Tree.agents/2` reads every event row: the newest per session and the `Stop` rows.
- **What I did:** nothing more. At the app's once per 2 s that is a small share.
- **What the design should change:** if it shows up again, keep each topic's built entries
  in the fold until its rows change, or have `Intake`'s source give the newest row and the
  `Stop` rows per session.
