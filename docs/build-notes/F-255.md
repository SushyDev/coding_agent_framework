# F-255: a worktree the framework makes is trusted before Claude Code starts in it

## What was built

Every first interactive start in a fresh worktree met Claude Code's trust dialog, which the
framework answered by a press (F-140, F-246's settle). Now an interactive start in a worktree
the framework made writes that folder's trust mark into its account's `.claude.json` before the
hold, so Claude Code shows no trust dialog there. The press stays as the fallback: a mark not
written leaves the dialog to it, as before.

### The mark (`Accounts.trust/3`)

`trust(account, root, path)` marks `path`, inside the worktrees' `root`, in
`<config>/.claude.json`: `projects[path].hasTrustDialogAccepted: true`, over the path's own
entry, every other key as it was. It takes Claude Code's own lock, `<file>.lock`, by mkdir;
reads the file; writes it whole to `.claude.json.framework.tmp` with the file's own mode and
renames it into place; removes the lock. It never waits on the lock. Answers:

- `{:ok, :trusted}`, or `{:ok, :already}` with nothing written;
- `{:refused, {:outside, path}}` for a path not strictly inside `root` (the root itself, a
  project's checkout, a path outside, a relative path, or one with `..`);
- `{:refused, :locked}` while the lock is held, the lock left as it was;
- `{:refused, {:no_state, file}}` when the file is not there: Claude Code never ran on the
  account, and `Accounts.login/2` reads the file's absence as logged out, so it is not made here;
- `{:refused, {:not_json, file}}` for a file that is not a JSON object, or whose `projects` is
  not one;
- `{:unknown, {file, reason}}` when a read or write fails, and `{:unknown, {:lock_left,
  reason}}` when the mark was written but the lock could not be removed.

### Where it is written (`Sessions`)

In the start's tree task, after Checked, Added and the setup passed, for an interactive start
only (its `way` has no `stream`): a headless delegate meets no trust dialog. The tree's place
now carries the worktrees' `root`, the physical path `Sessions` already makes, so the mark is
the worktree's real path, the form Claude Code reads. A start with `cwd:` writes nothing. Every
start and resume in a tree writes it (or finds it), on the account it starts on: a move's resume
is a `Sessions.resume/6` with the row's worktree on the new account, so the mark is written there
before that start. The row's `worktree` says what was done: `added; trusted`, `reused; trusted
already`, `added; not trusted: locked`, `added; not trusted: {:no_state, …}`, or `…; trust
unknown: …`. A setup that failed leaves `worktree` as before (`added`), with no mark.

### The model: `Trust.tla`

The framework's write and the program's writes on one file, the file as a set of keys. The
program writes two keys, each a locked read then write (whole file) then unlock; while the lock
is held it waits, and after K ticks it reads and writes without the lock, as measured. The
framework: mkdir (or refuse at once), read, write with the mark, rmdir, then its start. Its hold
is bounded by H ticks, H < K. Invariants: `NoKeyLost` (no key the program wrote is lost),
`MarkKept` (an ok write's mark stays past the program's later writes), `MarkBeforeStart`,
`RefusedWroteNothing`; property `Started`.

- `Trust_Lock.cfg` (H 1, K 2): 476 distinct states, no violation.
- `Break_Trust_Plain.cfg` (no lock): both `MarkKept` and `NoKeyLost` break, and TLC reports the
  one it reaches first (`NoKeyLost` in the gate run; each was checked alone).
- `Break_Trust_LongHold.cfg` (H 2, K 1, the lock held as long as the program waits): TLC finds
  `NoKeyLost` violated: the program's unlocked write meets the mark write.

### The stand-in honors the mark

Written with `marks: true`, `ScreenStandIn` draws no trust dialog in a folder whose real path
(`pwd -P`) `$CLAUDE_CONFIG_DIR/.claude.json` marks, the entry `{"hasTrustDialogAccepted":true}`
as `Accounts.trust/3` writes a new one (compact JSON). Without it the file is never read (new-6).

## What was measured

All on Claude Code 2.1.322 (devenv's), macOS, a tmux server of my own (`-L`), a fresh
`CLAUDE_CONFIG_DIR` per run, under the scratchpad, at host loads 40 to 65 from other builders.
A `.claude.json` of `{"hasCompletedOnboarding": true, "theme": "dark"}` makes the trust dialog
the first screen (F-246).

### Which mark the program honors

From the bundle: the trust check reads `projects[<key>].hasTrustDialogAccepted === true` in the
global config, where `<key>` is the git root (for a worktree, the main repository) and then the
cwd and its parents up to the cwd's own git root. No launch flag or setting trusts an
interactive session's folder: `--trust-workspace` belongs to `ultrareview` and to the
self-hosted runner, and `CLAUDE_CODE_IGNORE_PERSISTED_TRUST` only turns trust records off.

Then on the real program, each case a fresh repository with a worktree, the start in the
worktree reached through `/tmp` (a symlink to `/private/tmp` on macOS), the trust dialog shown
or not:

| Mark at | Dialog |
| --- | --- |
| none; the dialog answered "Yes" by a press | the mark was written under the **main repository's** real path, not the worktree's |
| the worktree's real path (`/private/tmp/…/wt`) | none |
| the worktree's path through the symlink (`/tmp/…/wt`) | shown |
| the folder above the worktree | shown |
| the main repository's real path | none |
| the worktree's real path, the start in a subfolder of it | none |

So the mark must be the real path, and a folder above the git root does not count. The dialog
itself shows the real path.

### How the program writes `.claude.json`

Watched every 2 ms through a session's start, idle time and exit:

- Each write replaces the whole file: a new inode every time.
- 12 writes in the first 2.5 s, none while idle (10 s), one at exit.
- `.claude.json.lock`, a directory, is there around most writes. From the bundle it is the
  `proper-lockfile` scheme (`lockfilePath`, `onCompromised`, stale 10 s, update 5 s). Under the
  lock the program reads the file again and applies its own change over what it read, merging
  `projects` (a project on disk but not in its change is kept). On a held lock it tries again
  (backoff 200, 400, 800, 1 600, 3 200, 4 000 ms), and then writes without the lock after reading
  the file again.
- An outside write while the session was idle (no lock, in place) survived the exit's write,
  both a `projects` key and a top-level key.

The race, a plain read-modify-write (read, 30 ms, write whole by rename) at 8 offsets across the
startup writes, against two control runs (19 keys each), load 45:

| Write | Program keys lost | Mark kept | Refused |
| --- | --- | --- | --- |
| plain | in 3 of 8 runs (1, 2 and 1 keys: `userID`, `changelogLastFetched`, `pluginUsage`) | 8 of 8 | – |
| locked (mkdir, refuse when held) | 0 of 8 | 6 of 6 written | 2 of 8 |

A read at 0.30 s and a write at 2.6 s, unlocked: 13 and 8 program keys lost (2 runs). Holding
the lock from before a session's start: the program's first write came at 1.73 s instead of
about 0.30 s, written without the lock, three more followed while it was held, and at 12.1 s
the program removed the lock as stale. So the lock excludes the program only while it is held
briefly: this is `Trust.tla`'s H < K.

### The built `Accounts.trust/3` on the real program

Session A on the account in a folder of its own, the mark written at an offset into A's start,
then session B started in the worktree (load 65), 6 runs: 4 `{:ok, :trusted}`, B showed no
dialog, no key lost by A's exit, the mark kept; 2 `{:refused, :locked}` (at 320 and 400 ms, A's
startup writes), B showed the dialog, nothing written. In one refused run `theme` was gone by
A's exit: the program drops keys equal to their defaults (`"theme": "dark"`), nothing of ours.
A first try of this probe started A in the repository itself, whose mark covers its worktrees,
so B showed no dialog even when refused; that run counts for nothing.

The lock's hold: 200 calls on a file growing to 12 kB, load 52: median 6.7 ms, p99 75 ms, max
183 ms, against the program's wait of about 1.4 s before its unlocked write.

## What the main session runs on the real program

With `CAF_REAL_SETUP=<home>`, on macOS and on Linux each:

1. `mix test.real` with an interactive delegate in a worktree (`caf_real`'s tests that start
   one), then in `<home>/records/` no `*-press-*` of kind trust for that delegate, and its row's
   `worktree` reading `added; trusted`.
2. `jq '.projects | to_entries[] | select(.key | startswith("<home real path>/worktrees/"))'
   <home>/accounts/<account>/claude/.claude.json`: each worktree's real path with
   `hasTrustDialogAccepted: true`, and the account's other keys (`oauthAccount`,
   `numStartups`) still there.
3. On Linux, where `/tmp` and the home are not behind a symlink, the same check: the path the
   row's `cwd` names is the key.
4. A move of an interactive delegate to another account: that account's `.claude.json` has the
   worktree's mark before its resume, and the resume shows no trust dialog.

## What I ran into

- The worktree had no `deps`: `mix deps.get` first.
- `python3` under `devenv shell` is the Xcode stub and fails; the probes used the system's own
  by its path, outside devenv's.
- `file` is a reserved key of an ExUnit context: the test's setup named it `state_file`.
- The first `devenv test` failed 16 of `caf_inlet`'s 18 tests (screens read `unrecognized`
  past their bound) and 3 of `caf_example`'s console tests, at load 73 to 81. Alone, at load
  110, `caf_inlet` failed the same; with `main`'s stand-in, at the same load, it passed 28 of 28.
  The cause was the stand-in: see new-6. Fixed, both passed alone (28 of 28, 10 of 10).
- A foreground `python3 -` with no input held a shell for 120 s before an edit; it was stopped
  and the edit made from a file.

## Findings

### new-1. The dialog's own answer trusts the whole repository

What happened: answered by a press, 2.1.322 writes the mark under the main repository's real
path, not the worktree's, and that mark covers every worktree of it and the checkout itself.
Why: the trust key is the git root, and a worktree's resolves to its main repository. What I
did: the framework's mark is the worktree's own real path, which the program also honors, and
never the checkout's. A press as fallback still trusts the whole repository, as it did before
this unit. What the design should change: say in "Startup dialogs" that a trust press marks the
project's checkout, or decline the press in favor of the mark only, once the mark has run.

### new-2. A start during another session's startup on the account is refused the mark

What happened: 2 of 8 locked writes in the sweep and 2 of 6 on the built code were refused
`locked`, each in the first 0.5 s of another session's start on the same account. Why: the
program holds the lock around each of its 12 startup writes, and the mark never waits. What I
did: refused at once, the press as the fallback, as the brief asks. What the design should
change: if refusals are frequent in practice, a bounded wait for the lock (one stated bound
below the start's deadline, an explicit answer at its end) would trust nearly every start.

### new-3. The mark rests on a bound the program sets

What happened: the program writes without the lock after about 1.4 s of waiting, and breaks a
lock older than 10 s. Why: its lock is advisory. What I did: the framework holds the lock for one
read and one write (183 ms at most in 200 calls at load 52), the model's H < K, and records it
in the module doc. A framework stopped between its mkdir and its rmdir leaves the lock until
the program breaks it as stale. What the design should change: re-measure the wait on each
pinned release, as the settle is (F-246's new-2).

### new-4. The move's case is tested at its resume step, not through the `Mover`

What happened: the brief asks that a move writes the mark on the new account. Why: the `Mover`'s
tests run a main session and a headless delegate, not an interactive delegate in a worktree, and
the mark is written in `Sessions`' start, which the move's resume goes through. What I did: a
test of `Sessions.resume/6` on a second account with the row's worktree, the call `Mover`
makes. What the design should change: nothing, unless a whole `Mover` run of an interactive
delegate in a worktree is wanted; the main session's item 4 above covers it on the real program.

### new-5. The design's rule on `.claude.json` changes

What happened: the "Claude Code" rules said the framework never writes `.claude.json`. Why: the
brief asks for the trust mark there, and 2.1.322 has no launch setting for it. What I did: one
exception in that rule, the trust mark of a worktree the framework made, under the program's
lock; `Accounts`' module doc says the same, and no longer says a write there is erased by the
next save, since the program reads the file again before each write. What the design should
change: nothing more; the rule now names the exception.

### new-6. A test VM inherits a Claude config directory that is not its own

What happened: the stand-in read `$CLAUDE_CONFIG_DIR/.claude.json` at every start. In tests that
set no `CLAUDE_CONFIG_DIR` (`caf_inlet`'s, the console's), the variable came from the environment
the tests ran in, a real account's config directory, and the stand-in read its large file and
matched it slowly in bash, so its first screen came past the tests' bounds. Why: `mix test`
passes its environment on to every program a test starts. What I did: the stand-in reads the
file only when written with `marks: true`, which only `sessions_trust_test.exs` does, and
matches it with one glob. What the design should change: the test VM could drop
`CLAUDE_CONFIG_DIR` (and the other `CLAUDE_*` variables) from its own environment at start, so no
stand-in or program a test starts can reach a config directory that is not the test's.
