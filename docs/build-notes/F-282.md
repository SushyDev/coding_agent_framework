# F-282: a launch's brief row settles once the delegate runs it

## What was seen

An interactive delegate was started with a brief, its launch row (`via: launch`). It ran the
whole brief over several turns and reported. Its launch row stayed `sending`, so its parent's
stop answered `{:refused, {:open, [id]}}`, and only the operator's forced stop could end it. Two
such rows were open in the embedding app's store, both `sending` since the same minute.

## Diagnosis

The store, read only, says what happened to both rows:

- each is `kind: brief`, a new start (not a word to go on), of a delegate whose branch had a
  delegate before: the first had been gone with no report, and a second start of the branch
  made a new delegate row under the same agent name (`Delegate.tla`'s StartAgain);
- `at` holds the new process's pid and `sent_at` equals `updated_at`: the start's answer was
  told (`launched/3`, `{:ok, _}`) and nothing wrote the row after it;
- `session_id` is the new session's, but `from_byte` is 2 292 792 and 2 509 811 bytes;
- the transcript reader's fold of each new session holds the brief's prompt as its first
  turn, at byte 26 264 and 25 791, its length the row's text with its mark;
- the earlier delegate's rows to the same agent name were delivered in another session, on
  another account, whose transcript was about that long.

So the mark (`Mailbox.launch/4`) read the offset of the session the agent row named before the
start, the earlier delegate's, and `launched/3` replaced the row's session with the new one but
kept that offset. The settle then read the new session's transcript from byte 2.3 million, past
its end: no line, the process alive, so `Transport.Launch.settle/2` kept the row, for good.

A restart of the tree before the start's answer has the same flaw in another place: with no
answer the row keeps the mark's session, the earlier one, and `launch_seen` read that session's
transcript, which the new start never writes.

The narrowed hypothesis in the brief (a confirm in flight at a restart) does not hold for these
two rows: both had their answer told 46 and 53 minutes before the restarts, and the restarts
changed nothing. Launches after the restarts settled because they went to agents with no
earlier session, or resumed the same session, whose offset is right. Neither of the brief's
other guesses holds either: F-277 changed only the typed transport's settle, and the brief's
line is in the transcript in the form `Transport.Launch.seen/2` reads.

## What was built

- `Mailbox.launched/3`, on `{:ok, %{session_id: sid}}`: the row's offset is kept only when
  `sid` is the session the mark read it in (a resume); else it is 0, the new transcript's first
  byte.
- `launch_seen`, the launch row's evidence: until the start's answer (a restart cut it, or the
  answer was unknown) the session read is the agent row's now, which the start rewrites; when it
  is not the mark's session, it is read from byte 0.
- `Delivery.tla`: `Break_Delivery_OldWindow` reads a launch's line in the window of the session
  before its start and keeps the row while its process lives, as the code did. TLC fails it on
  `SendingSettles` in 7 states. The rule itself does not change: the model's `has` was always
  the transcript of the process the row went to, and the code now reads that one.
- `docs/design.md`'s launch row in the transport table, the Mailbox moduledoc, the README's
  status line.

No bound for the launch row was built (see new-1).

  told or the Mailbox restarted before it; the new session's user line settles the row
  delivered. Both failed before the fix (the told one on the offset, the restart one stayed

  settled, and its stop goes": the app's case end to end. The first delegate reports, the
  parent's `run_delegate` takes the report, the parent stops it; a second start of the same
  branch makes a new delegate and session; its brief settles delivered, its report is taken, and
  the parent's stop answers `{:ok, :stopped}`. Before the fix its brief stayed `sending`.
- The limit test now also checks the word to go on, a resume's launch row in the same session,
  settles delivered by launch.

## Findings

### new-1. The brief asks for a bound after which a launch row settles `unknown`

What happened: the brief asks that a launch row settle `unknown` after a bound when no line
shows. The design decides the opposite (F-153's new-1, `Break_Delivery_LaunchBound`): a startup
dialog holds the first turn for as long as a person takes, so no bound stands for the take.

Why: the row in the app stayed open for a wrong read, not for a missing bound. With the read
fixed, a launch row settles by its line, or once its process is gone, and the operator's forced
stop settles one whose session never takes a turn (F-170).

What I did: built no bound.

What the design should change: nothing, I recommend. If a bound is wanted anyway, it should
settle `unknown` (never due again, so never sent twice) and run from the first turn's start, not
from the launch, so a dialog's wait does not count; that is a design decision, with its own
`Delivery.tla` step.

### new-2. A row stuck by the old read does not heal by this fix

What happened: the two rows in the app's store were written by the old `launched/3`: their
session is the new one and their offset the old one's. The fix reads a row's offset as it is
once the answer was told, so these two stay `sending`.

Why: the row no longer says which session its offset was read in.

What I did: nothing; the operator's forced stop of each settles its row `unknown`.

What the design should change: nothing for new rows. An app that wants such rows settled could
treat an offset past the end of the transcript as another file's and read from byte 0; it is not
built, since an old offset shorter than the new transcript would skip the line anyway.

### new-3. The mark reads an offset of a session the start may not write

What happened: `Mailbox.launch/4` reads the agent row's session's offset before every launch,
also for a new start, which writes a new session.

Why: the mark cannot tell a resume from a start; only the start's answer (or the agent row
after it) names the session.

What I did: the answer, or the agent row after a restart, decides which offset holds.

What the design should change: a launch could say at its mark whether it resumes (`resume:
sid`), and read the offset only then. That would remove the read for every new start; it
changes `launch/4`'s callers (`Delegates`, `Mains`, `Mover`), so it is left for a unit of its own.
