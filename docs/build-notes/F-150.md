# F-150: an idle delegate with no report, and a start idempotent per branch

The first and last mechanisms of item 14. `Delegate.tla` models both before the code. No test
or step of this unit started the real Claude Code.

## What was built

- **The model** (`Delegate.tla`). A delegate in `Stalls` may end a turn with nothing the
  framework reads as its report (`TurnEndsBare`, process `stalled`). That begins an idle state
  of its own (`idles`). `Delegates`' wake at the bound is in memory (`BoundPasses`, `overdue`):
  a restart clears it, so the bound starts again. Past the bound, `IdleTold` stores a notice
  under the state's key in `Mailbox`'s table (`keys`), and `Mailbox` takes a key once. The
  delegate is not touched. `IdleToldOnce`: at most one notice per idle state. `IdleNoticed`:
  while the state lasts, a notice comes. `Break_Delegate_IdleInMemory` keeps the notice's mark
  in memory, so a restart tells the parent twice (`IdleToldOnce` fails), and
  `Break_Delegate_IdlePerDelegate` keys the notice by the delegate only, so a second idle state
  after a kill and a resume is never told (`IdleNoticed` fails).
  `StartAgain` is a second start of a running row with no reply whose process is dead. It goes
  on as a new row: `starting`, its own brief, no resumes, no process until `Sessions` starts
  one, and the cap that already counts it. A second start of a live delegate answers it and
  writes nothing, so it is no step. `Break_Delegate_StartOverLive` lets the start go on while
  the process lives. `Sessions` then refuses the name, and the row is refused while its process
  runs on (`RefusedHoldsNothing` fails). Two constants keep the new behavior out of the
  earlier configurations: `Stalls = {}` and `MaxAgain = 0` there, so their state counts are
  the same as on `main`. `Delegate_Idle` (one delegate, one kill, one restart, `Stalls = {d1}`,
  `MaxAgain = 1`) checks every invariant and property with the new ones. The slow
  `Delegate_Large` sets both and checks the new invariant and property.
- **The idle notice** (`Delegates`, option `idle_bound:` in ms). At each settle, every latest
  row that is `running` with no call under way is read:
  - not moving;
  - its turn ended by its kind's rule: `Sessions.Turn.headless/2` is `:ended` for a headless
    delegate, and `turn_ended?/2`, the session file read through `registry:`, for an
    interactive one;
  - `Mailbox.open_to/3` empty.

  The idle state's key is the row's id with the fix state's offset (`followed/2`): the log's
  offset, or the newest hook event's id for an interactive delegate. Any event moves the key,
  so a turn that starts ends the state. The first read records the time on `clock` and sets
  one wake at the bound (`Process.send_after/3`, not a poll). Past the bound,
  `Mailbox.notify/4` stores a message from `framework` to the agent row's parent, under the key
  `idle:<host>:<row id>:<offset>`. A later read in the same state calls it no more. A read that
  fails keeps the state as it was. With no `idle_bound:` nothing is read.
- **The start idempotent per branch.** `Delegates.Turn.again/3`, a pure function of the name's
  latest row and its agent row, decides first, before the moving check, the cap and any write:
  - `:new`: no row, a refused one, or an agent that ended;
  - `:already`: its agent row `running` and not moving. The start answers `{:ok, %{id, name,
    session_id, account, brief_uuid, already: true}}`, writes nothing, and does not use the
    second brief or its options;
  - `:again`: a `running` row whose agent row is free (`stopped`). The cap counts the name once
    (`Agents.children(parent, [name | starting]) <= cap`, the same rule as before for a new
    name). The old start's brief and word to go on are settled `ended` through
    `Mailbox.settle_row/3`, and the start is refused `{:in_flight, name}` while one is
    `sending`. The old row gets `reason: "replaced"` once the new row is written;
  - refused: `{:starting, name}`, `{:other_parent, name}`, or `{:delegate, %{name, status,
    session}}`.

  `MCP`'s `start_delegate` answers `already: true` with the delegate's name.
- **The headless stand-in**: a message starting with `quiet` ends its turn with an empty
  `result` that names no message.
- **Tests**:
  - `delegates_test.exs`: the idle notice told once past the bound, not again after a later
    cue or a restart whose bound passes again, and once more for the new idle state a parent's
    message begins, with the delegate untouched. The second start, live then gone.
  - `delegates_interactive_test.exs`: an interactive delegate whose brief's turn has no reply.
  - `turn_test.exs`: every outcome of `again/3`.
- **Docs**: "The delegate protocol" and item 14 in `docs/design.md`, `README.md`'s Status, and
  the moduledoc and docs of `Delegates`, `Delegates.Turn` and `MCP`.

## What I ran into

- The first `StartAgain` left the old process `dead`. A new start that `Sessions` then refused
  broke `RefusedHoldsNothing` in every configuration. A process that is gone holds nothing, so
  the new row starts from `none`, and only the Break keeps a live one.
- A second start of a live branch, before this unit, wrote a new `starting` row. `Sessions`
  refused the name or the path, and the refusal called `Mailbox.ended/3` on the name, which
  settled `ended` every row queued to the live delegate. The new refused row was also the
  name's latest, so the live delegate's own row stopped moving and its report was never read.
  The lookup now answers before anything is written (see new-2).
- A baseline TLC run on `main` raced my first edits of the spec. The baseline in the table
  above came from a copy of `main`'s `model/tla` and `bin` in the scratchpad.

## Findings

### new-1. Which turn state of an interactive delegate counts as idle is not settled

What happened: item 14 calls the idle state "a value of `Sessions`' turn function".
`Sessions.Turn.interactive/3` is `:ended` only when the session file reads idle and `Intake`
holds the waiter, and `:idle` for the file alone. Why: the waiter's hold ends at 7 080 s. After
that the delegate reads `:idle` until another turn ends, so an idle state longer than two hours
would end on its own if only `:ended` counted. What I did: the notice takes the file alone, as
`Delegates` already does when it reads an interactive delegate's report (`turn_ended?/2`). The
notice decides no write into the delegate, so the second reading R8 asks for does not apply.
What the design should change: say which values count, per kind.

### new-2. The outcomes of a second start beyond "live" and "gone" are this unit's choice

What happened: item 14 settles two cases: a live session is answered, and a gone row with no
report starts again. Why: the lookup meets other cases. A start or resume of the name is under
way. Another parent's delegate holds the name. A report is on its way, a stop is under way, or
a move is. And the old start's rows in `Mailbox` would reach the new process. What I did: each
of the first three is refused (`starting`, `other_parent`, `delegate` with both statuses). The
old brief and word to go on are settled `ended` before the new row, and the start is refused
`in_flight` while one is `sending`. Messages the parent sent to the old process and that are
still queued go to the new one. What the design should change: confirm these outcomes, and say
whether queued messages to a replaced delegate go to its successor or end.

### new-3. The idle bound runs from the first read, and an app has no default

What happened: the notice comes at the bound past `Delegates`' first read of the idle state,
not past the turn's end, and a restart starts the bound again. Why: neither the `Stream` fold
nor the session file holds the time a turn ended. What I did: the bound is measured on
`Delegates`' clock from that read, as the model's `BoundPasses` has it. Without `idle_bound:`,
`Delegates` reads nothing for it. The example app sets no bound: its config file is checked
whole, and a new key is its own change. What the design should change: name the bound's start,
and say whether the example app's config should carry one.

### new-4. A headless turn with no report is a stand-in's shape, not a measured one

What happened: the headless test plays a turn that ends with no report as a `result` naming no
message (`quiet`). Why: a headless brief's turn has always ended with a `result` naming its
uuid, which is the report. No release has been seen to end a brief's turn otherwise. What I
did: nothing beyond the stand-in. The rule reads the fold, whatever ends the turn. What the
design should change: nothing now. A pinned release's check could record whether such a turn
exists.
