# F-185: usage limits, the rest: the readers, the screens, `limited`, held rows

The brief's item 1 (F-181's item 5) and item 2 (its item 6), against `Limit.tla`, every remedy on
F-182's healer. This unit lands the part of item 1 that does not depend on where the remedies
run, and stops before the remedies: the design names two places for them and one remedy per
kind where `limited` has three (new-1, new-2). No test started the real Claude Code, and nothing
was measured by hand: the fixtures are F-181's captures.

## What was built

- **Settings per account** (`Accounts.prepare/3`): both framework settings files set
  `autoContinueAtUsageLimit: true`, over whatever the app's settings say, and an agent's own
  options may not set it (`ClaudeCLI.Options`' own settings). The hooks need nothing new:
  `Intake.hooks/4` already posts every `StopFailure` and `Notification`, with no matcher, so
  the three `quota_auto_resume_*` and the `rate_limit` failure reach `Intake` today (new-3).
  The launch sets no `CLAUDE_CODE_RETRY_WATCHDOG*` (F-181's new-2, decided); the design says so.
- **The readers.**
  - `Transcripts.Fold` keeps `limit`, the last line with `apiError: "usage_limit_reached"`:
    its record (`quotaLimits`, or `apiErrorParams.rate_limit_info`), `uuid`, `at`, `offset`,
    and `followed`, true once a later prompt or a reply that is not an API error shows a turn
    ran after it. The line is never a reply (its `stop_reason` is `stop_sequence`). A fold
    stored before this build has other keys, so `Table.load_fold/1` reads its file again from
    the start, as for any fold it does not know.
  - `Usage` takes each transcript's last limit line once, by its uuid, on each
    `transcripts:<host>:<account>` cue, from `Transcripts`' table (`transcripts_db:`, the same
    file in the tree), with evidence `%{"source" => "transcript", "session", "line"}` and the
    line's own time. `StopFailure` is not one of its sources (F-181's new-1, decided).
  - `Stream.Fold`'s result keeps `api_error`: `"usage_limit_reached"` is the headless turn's
    evidence that it ended at a limit.
- **`Screen`'s two kinds.** `usage_limit_menu` is a dialog kind, its options read by label
  (`option_keys/2` finds "Stop and wait for limit to reset"); it is drawn under a rule of `▔`,
  not `─`, so a dialog kind now names its rule (`rule:`), and each kind is read below its own.
  `usage_limit_wait` is a state of its own, `%{state: :usage_limit_wait, at: time}`, read from
  the notice under the box before anything else there: the box under it is drawn empty, and
  read alone it would be an ended turn. So the `Inlet`'s box check refuses a typed row into
  the wait as it refuses one into a running turn.
- **Fixtures**: four states from F-181's captures, each with escapes and without
  (`usage-limit-menu`, `-wait`, `-stopped`, `-went-on`), scrubbed of the scratch path
  (`/work/repo`) and the time zone (`Etc/UTC`), in the manifest with their capture times. The
  wait's capture still holds Claude Code's own auto mode notice and its documentation link, as
  the imports fixtures hold theirs.
- **`limited` on the agent row.** `Sessions.Table` gains `usage_limit` (JSON: `until`, the reset
  in Unix seconds, `window`, `line`, `step`; a column added to an earlier file; `limit` is an
  SQL word, so the column is not named so). `Sessions.put_limit/4` writes it, or clears it with
  nil, and announces the row. `Sessions.Agents.limit/1` reads it. `Sessions.Turn` answers
  `:limited` for a running row that has one, interactive or headless: never idle, never an
  ended turn, so `Delegates` tells no parent its delegate is idle and `Mailbox` types nothing.
- **Held rows.** `Mailbox` marks no row to a `limited` agent while its reset has not passed
  (target `:limited`, as `:moving`); once it passed, `Sessions.Agents.unheld/2` drops the limit
  from the row it reads the turn from, so its rows go into its ended turn while the row still
  says limited (`Limit.tla`'s `Deliver` after `Passed`), at its three reads of a turn.
- **Docs**: "Usage limits" (the evidence, the code list's items 1 to 3, what this unit built
  and did not); the `usage_limit` column; `Mailbox`'s hold.

## Findings

### new-1. The design names two places for the limit's remedies

What happened: the code unit's list ("Usage limits", item 4) has `Sessions` hold the timer to
the reset plus the margin, read the turn and the screen, and act (the checked press, the
prompts). "Metrics and healing" says each limit remedy is an instance of the healer, never a
mechanism of its own, and the brief says every remedy is on F-182's healer. The two healers
built so far (`Recoveries`, `AbsentMains`) are processes of their own that act through
`Sessions`, `Holder` and `Mains`, and claim in `Acts` under their own actor. Why: the list was
written before F-182 made one shape for every remedy. What I did: built only what both readings
share: the row's field, its one writer (`Sessions.put_limit/4`), the turn state, and the hold.
What the design should change: the limit's reader and its remedies are one healer process,
`Limits`, in `caf_recoveries` beside `AbsentMains`, after `Sessions`, `Mailbox` and `Watch` in
the tree, reading `transcripts`, `stream`, `sessions` and `watch` cues and a timer of its own
to each reset plus the margin. It writes each phase through `Sessions.put_limit/4` (`Sessions`
stays the row's one writer, as `Mover` writes a move's phase through `move_phase/5`), presses
through `Sessions`' checked press of a dialog (`usage_limit_menu` as a kind beside the startup
dialogs), and stores the word through `Mailbox`. `Sessions` keeps only the turn function.

### new-2. The allow-list names one remedy per kind; `limited` has three

What happened: the design gives the symptom `limited` the remedies `press_stop`, `go_on` and
`move`, "each an entry on the list with its cap". The `Watch`'s list maps a kind to one remedy
(`%{remedy, cap}`), and a symptom state is keyed by its kind. Why: F-182 made the shape for one
remedy per symptom, and the limit has three phases, each its own state. What I did: nothing on
the list. What the design should change: three kinds, one per phase, each its own entry and
its own state key: `limit_menu` (the menu shown, the account unable to spend; `press_stop`),
`limit_reset` (the reset passed, no own wait went on; `go_on`), and `limit_far` (a delegate's
reset past `move_after`, another usable account with room; `move`); each state
`<kind>:<agent>:<until>`, so each acts once per limit. `limited` itself, the limit with its
window, its agents and the time each waited, is a kind with no remedy, shown only.

### new-3. The hooks already post what the code list asks matchers for

What happened: item 1 asks for the `StopFailure` hook with matcher `rate_limit` and the
`Notification` hook with three matchers. `Intake.hooks/4` writes one http hook per event with no
matcher, so every `StopFailure` and every `Notification` already reaches `Intake`. What I did:
nothing; the design says so. What the design should change: nothing more; the limit's healer
reads `Intake`'s rows of those events by `error` and `notification_type`.

### new-4. `Limit.tla`'s header still names `StopFailure` as the record

What happened: the spec's header says the record is "the same in a `StopFailure` hook's input";
F-181's new-1 (decided) says it is not. Why: the header predates the measure. What I did: left
the model alone; nothing it checks depends on where the record comes from. What the design
should change: the next unit that touches `Limit.tla` says "the transcript's line and, headless,
the stream's event" there.
