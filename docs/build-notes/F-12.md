# F-12: the repository's own pre-commit hook

## What was built

`devenv.nix` writes `$(git rev-parse --git-common-dir)/hooks/pre-commit` (executable) on every
shell entry. It runs `prek run` with the config `git-hooks` generates, both by store path, with
`PATH` set to git's store directory. So a plain `git commit` outside the shell, from any
worktree, runs the format check and `typos` on the staged files. The first lines carry a marker
comment; the writer replaces only a file with that marker and otherwise prints why it did not.
It also warns when `core.hooksPath` is set in this repository, since git then ignores the file.
The install task's old skip is now a plain skip: prek would write the same file.

## What was measured

From a worktree, with `env -i PATH=/usr/bin:/bin` and `core.hooksPath` pointed at the common
hooks directory (standing in for the global hand-off), on a throwaway branch (deleted):
an unformatted `.ex` file was refused, a British spelling in a Markdown file was refused, and a formatted
file with `color` committed. Overwrite refusal was shown with a foreign `pre-commit`.

## What I ran into

- `prek run` works by store path outside the shell, so the two checks are not called directly.
  The config is the store file `config.git-hooks.configFile`, not the checkout's
  `.pre-commit-config.yaml`, so a worktree whose shell never started still has it.
- The format check needs `deps/` (the formatter imports `stream_data`). A fresh worktree
  without `mix deps.get` is refused with a Mix error, not a format diff.
- `devenv.nix` changes rewrite the hook only at the next shell entry.

## Findings

### new-1. A worktree without `deps/` refuses every Elixir commit

What happened: in a new worktree the format check failed with "Unknown dependency
:stream_data", for any staged `.ex` file.

Why: `.formatter.exs` has `import_deps`, which needs fetched dependencies.

What I did: ran `mix deps.get` in the shell. Nothing else.

What the design should change: say that a builder's first step in a worktree is `mix deps.get`,
or have the hook print that hint.

### new-2. The hook is only as current as the last shell entry

What happened: the hook holds store paths fixed at the last shell start; a changed
`devenv.nix` or a garbage-collected store path breaks or stales it until a shell starts again.

Why: the file is written on shell entry, not on commit.

What I did: nothing; a missing store path fails the commit loudly.

What the design should change: decide whether a stale hook should be a refusal that names
`devenv shell` as the fix.
