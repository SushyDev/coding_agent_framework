# F-148: an answer's request is checked before its claim

F-147's new-1: `MCP` claimed a fix's state before the fix checked its arguments against it, and a
settled claim's state stays claimed. An `answer` naming a request the target does not hold was
refused `{:not_held, id}` after its claim, so the next `answer` of that state, with the right id,
was refused `{:already_claimed, by}` until the state moved. This unit checks the id first. No test
or step of it started the real Claude Code.

## What was built

- **`MCP` checks an answer's request before the claim.** `act/5` reads the state (`by.state.()`),
  then `held/2` checks `dialog` against the state's `held` (the ids `Delegates.fix_state/3` and
  `Mains.fix_state/3` both name), and only then calls `Acts.claim/6`. An id the state does not
  hold is refused `{:not_held, id}`; no claim is written, so the state is free and the next
  `answer`, with the right id, is taken. The label was already checked before the claim
  (`fix/2`). `Mains.answer/5` and the interactive delegate's `act` keep their own `not_held`
  check, which now only a direct caller of those reaches: the id is checked again on the state
  the fix acts on.
- **The model.** `Team.tla` had no answer: its fix kinds were `interrupt`, `resume` and `stop`,
  and the answer tool was left abstract (F-147 wrote "no spec changes", which took the answer for
  one more act of the claim; it is an act the model did not have). It has it now:
  - `held`, per agent, the ids of the requests Intake holds for its session, and `reqs`, how many
    were made (`MaxRequests`, a new constant). `Requests(a)` holds one while `a` works;
    `PersonAnswers(a)` answers one on the screen. Both move the agent's `epoch`, as `held` is part
    of the state `fix_state` reads.
  - `AnswerClaimed(c, t, i)` is the claim of an answer naming request `i`: `i` must be in
    `held[t]`, else no claim. Its act (`FixActs`) takes one request out and leaves the process as
    it is; `CanAct` needs a request still held, and does not apply "a row whose end is asked is
    never resumed" to an answer.
  - Two invariants: `AnswerClaimsHeld` (a ghost, as `FixOnClaimedState` is) and
    `AnswerStateHoldsRequest` (no claim on a state now stands on an answer with nothing held).
  - `Break_Team_AnswerNotHeld` takes the claim on any id: `AnswerClaimsHeld` fails in 5 steps.
  - `Team_Answers` (one project, a fault, one request, a restart) and `Team_AnswersTwo` (two
    requests held at once, a restart) check the design: every invariant above, `Team`'s claim
    invariants and `ClaimEnds`. `MaxRequests = 0` is added to the other 44 configurations, which
    leaves their state as it was (no request, `held` and `reqs` never change).
- **Tests.** `mcp_delegates_test.exs` has a test of an answer's wrong id (and an empty one): both
  refused `not_held` with `Acts.rows` still empty, then the right id taken under a claim and
  `verified`, then the same id again refused `not_held` with no second claim, and every call
  `answered`. `example_test.exs` asked the operator's answer of a declared main after its refused
  resume and expected `already_claimed`; it now asks a second resume for that, and the answer is
  refused `not_held` before any claim, claimed state or not; the answer of an ended one is asked
  twice and refused the same way both times.
- **Docs.** `docs/e2e.md` no longer tells the person to copy the id and answer on the screen after
  a wrong one. `docs/design.md`: "A permission request" of a main session, and the rule for a
  fix's claim ("a state once claimed stays claimed"), now say what is checked before it.

## What I ran into

- The first design configuration (one fault, two requests, a restart) was past 27 million
  distinct states and still growing after ten minutes, so it was stopped. A request moves the
  state twice (it arrives, it leaves), so each request multiplies the claims that can be taken.
  The two configurations above split it: a fault with one request, two requests with no fault.
- `CanAct` also holds "a row whose end is asked is never resumed" for every act, and `FixActs`
  names it `resume ending` for any. For an answer that would refuse a main session whose end is
  asked and flag it wrongly, so both now skip an answer. An answer to such a session is the code's
  (`Mains.answer/5` does not look at `end_asked`).

## Findings

### new-1. A fix refused when it acts keeps the state claimed, so any other fix of that state waits too

What happened: only the answer's id was moved before the claim. A `resume` refused `:live`
(a delegate) or `{:not_stopped, status}` (a main session), a `stop` refused `{:report, status}`,
and an `interrupt` that is refused when it acts still settle their claim and keep the state. The
next fix of that state, an `answer` of the request it holds included, is refused
`{:already_claimed, by}` until the state moves. The existing test of `mcp_delegates_test.exs` even
asserts it (`resume` → `live`, then `stop` → `already_claimed`). Why: `Claim.tla`'s `LetGo` ends the
claim with no act, and `OneClaimPerState` keeps the state claimed, so a fix tried on a state is
spent. What I did: nothing; F-148's brief decided the answer's id only. What the design should
change: decide whether a fix's other preconditions that `Delegates` and `Mains` check from the
claimed state (`live`, `not_stopped`, `report`) are checked before the claim too, as the answer's
id and label now are, or whether a refused fix spends its state by design. The operator's run in
`docs/e2e.md` meets it when it types `resume` at a session that is running and then answers.
