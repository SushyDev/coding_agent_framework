# F-214: a home keeps its kind, and a tree of the other kind is refused on it

F-195's new-2 said a home is agentful or agentless for its whole life, because an agentless tree
asks no owner of a delegate's, main's or run's lease and would leave an agentful tree's leases
unreclaimed. Nothing held to it: a home kept no mark of its kind, `start_link/1` started either
kind on a home the other had used, and `agent_rows/1` answered no rows for an agentless home and
for a new one alike. This unit records the kind once and makes the rule a check. No test started
the real Claude Code.

## What was built

- **The mark** (`CodingAgentFramework.Home`, in `caf_surface`). One row, `id = 1`, in the table
  `home` of the home's own database (`<home>/caf.db`): `kind` (`agents` or `agentless`, a
  `CHECK` holds it to those) and `marked_at`. `start_link/1` calls `Home.mark/1` right after
  `mkdirs/1` and before the programs, the tool home or any part, so a refused start has written
  nothing under the home that was not there. The first start on a home writes the mark, every
  later start reads it.
  - A home with no mark and no row in the `agents` table (a main session is one, of kind `main`)
    or the `delegates` table is new, and takes the starting tree's kind.
  - A home with no mark and such a row ran before this unit. Only an agentful tree writes those
    two tables, so it is marked `agents`, whatever kind of tree starts on it. The mark is the
    home's fact, so the first start after this unit writes it even when that start is the
    refused one (an agentless tree on an old agentful home); it writes nothing else.
  - The rows are read with no host: the home is one directory, and the check is not the
    config's `workstation`.
- **The check.** A tree of the other kind than the mark gets `{:refused, {:home_kind,
  recorded}}` from `start_link/1`, `recorded` being `:agents` or `:agentless`. Nothing starts.
  A write that fails is `{:refused, {:sqlite, reason}}` when the file will not open, and
  `{:unknown, {:home_mark, text}}` when a statement raised, since the mark may or may not be
  there.
- **The reader.** `CodingAgentFramework.home_kind/1` takes a config (it reads only its `home`),
  opens `caf.db` read-only in one snapshot, and answers `{:ok, :agents}`, `{:ok, :agentless}` or
  `{:ok, :new}`, or `{:refused, reason}` when the database cannot be read (`{:sqlite, reason}`,
  or `{:home_mark, text}` for a file that is no database). A home with no database file is
  `:new`, and the read makes none. An unmarked home with rows answers `:agents`, which is what
  the next start marks. `agent_rows/1`'s answers are as they were.
- **`Store.write/3`** (`caf_store`): opens the file as `open/3` does, runs a function in one
  immediate transaction as `transaction/2` does, and closes it. `Store` was the only module that
  could close a connection (no other app's code names `Exqlite`), and `Home` is a pure module
  that keeps none. It has a doctest.
- **Docs**: `Home`'s module doc, `start_link/1`'s and `agent_rows/1`'s, `home_kind/1`'s (a
  doctest for the new home, and the two other answers in prose), `Config`'s `agents` key, the
  comment on `holders/1` (it said an agentless tree could meet a home's old leases; it cannot
  now), the design's config table and "Built so far", and the README status line.

## The model

No spec in `model/tla/` describes a tree's start on a home. `Start.tla` models a session's
start and stop on a host and the framework's restarts between their steps; `start_id` and
`instance_running` appear in no spec. So I wrote none, as the brief says.

The lock the mark runs under: there is no lock of the home. The mark's read and write are one
`BEGIN IMMEDIATE` transaction, so they hold SQLite's write lock on `caf.db` for that one
transaction, never for the tree's life. That is enough for the one thing the mark decides: two
first starts of different kinds on one new home are told apart by it, and the second reads what
the first wrote. It does not keep two trees from starting on one home (new-1).

## Findings

### new-1. Nothing keeps two trees from starting at once on one home

What happened: the brief asks for the home's lock under which the mark is one read and one
write. The framework has none. `unique/1` looks for the instance's named `Registry` in this VM
only, and two starts of one name at the same moment both pass it before either's `Registry`
exists. Two instances that share a home in one VM, or two VMs, meet nothing at all. The only
`flock` in the framework is `Copies`' lock of a copy, and the hooks' secret is made once by a
link, which fails on a name that is taken. Why: a tree's start has always been one app's act on
its own home, and the names kept two instances in one app apart. What I did: built no lock, as
the brief says. The mark is one transaction, so a second tree reads the first one's kind, and
that is all it gives. What the design should change: decide whether a home belongs to one tree at
a time. If it does, that is a protocol over time (a held lock, its holder's death, a restart that
takes it again) and starts in `model/tla/` with a spec of its own, before the code.

### new-2. Two first opens of one new database can refuse "database is locked"

What happened: with two trees' first `Store.open/3` of one new `caf.db` at one instant, one of
them answered `{:refused, {:sqlite, "database is locked"}}`, in the first run of the race test
(it stopped at that pair). It comes from `open/3`, before the mark's transaction. I did not narrow it to the statement:
the journal-mode switch to WAL or the schema's first write, where SQLite may answer busy without
calling the busy handler. Why: only two starts at one instant can meet it, and every writer
opens its file the same way. What I did: nothing. The start is refused, explicitly, and nothing
of its own was started or written; the repository's rule is no hidden retry. What the design
should change: nothing while two starts at once on one home stay unsupported (new-1). If they
become supported, `Store.open/3` needs a bounded retry of its first statements, which the rule
against hidden waits has to decide.

### new-3. A home whose tables hold no row is new, though an agentful tree made them

What happened: an agentful tree that never wrote an agent or delegate row (it declared no main
session and ran no delegate) leaves the tables and no row. By the brief's rule that home is new,
so an agentless tree can take it, and then an agentful tree on it is refused. Why: the rule is
by rows, as the brief decided. Rows are enough for the leases: a delegate's lease names its row
in `delegates`, written `starting` before the lease is asked for, and a main's names a row of
`Mains.Starts` over its already declared agent row. I did not trace a run's lease the same way.
What I did: followed the brief. What the design should change: say in the design that the rule
is by rows because a lease follows its owner's row. If a table that exists should count too,
`Home` would read the table names it already reads, and the surface test that starts an
agentless tree on a home whose tables a setup made would make that home agentful.
