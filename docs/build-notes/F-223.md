# F-223: the end-to-end run as a real suite, `mix test.real`

The person running the framework decided: the end-to-end run becomes an Elixir suite against the real Claude Code,
outside the gates. This unit builds the suite and its first test. The main session built it,
since no builder could start after the switch.

## What was built

- **`caf_real`**, a new umbrella app with no code of its own (its moduledoc says what it is). Its
  tests are tagged `:real`; `test_helper.exs` leaves `:real` out, so the gates and every plain
  `mix test` skip them. The root alias `mix test.real` (`test --only real`, preferred env
  `:test`) runs only them.
- **`RealCase`** (`test/support/real_case.ex`):
  - the setup: `CAF_REAL_SETUP` names a home where `bin/caf-login --setup <home> one two` logged
    both accounts in. Without it every test is skipped, and the reason says what to run;
  - `start_tree!/1`: the example app's tree on that home, with its own instance, ports, project,
    origin (a bare repository named after the project) and main session name per run;
  - an exit hook that ends what the run started (it answers an open start dialog with its exit,
    stops the run's delegates, then ends its main by force, then stops the tree), with the tree
    unlinked from the test's process so the hook still reaches it after a failure;
  - bounded waits by the clock (`await!/5`), each failure naming the agent's screen, and readers
    over the surface the console uses: `agent/3` (the `agents` tree), `prompts/2`, `answer/3`,
    `op/3` (`Operator`), `transcript/2` (the agent's JSONL; a delivered notice is collapsed on
    the screen, so delivery is read there) and `screen/2`.
- **`MainAndDelegateTest`**: `docs/e2e.md` steps 1, 2, 3, 5 and 14 in one test, on Haiku, each
  step with its own bound:
  1. the checkout is ready, and the main session is declared;
  2. the main starts (any trust dialog is answered from the inbox) and replies;
  3. a headless delegate's Bash waits in the inbox as a permission prompt; it is allowed, a
     second answer is refused `:settled`, the request settles, and the report reaches the main
     session's transcript;
  4. (step 5) the main session's ask, through the caf `ask` tool, is answered, and a second
     answer is refused `:settled`;
  5. (step 14) its end is refused while its delegate lives, then the delegate stops and the main
     ends.
- `CLAUDE.md`'s testing rule, the design's rule and `docs/e2e.md` say which tests start the real
  Claude Code, and which steps the suite runs.

The suite, run on this Mac against the e2e home's accounts (`CAF_REAL_SETUP=/Users/<me>/caf-e2e`):

| 3 | failed at step 2 | the start answered `{:unknown, {:dialog, :trust}}` on a new checkout, as the doc says |

The first gate run failed `IntakeToolsTest`'s "at the deadline the response is empty…" once in

## Findings

### new-1. Two projects whose origins share a name share one checkout

A checkout's directory is its origin's last path part. A new project whose origin was also named
`demo.git` was given `checkouts/demo`, another project's clone of another origin, read `ready`,
and its main session ran there. A brief: `tmp/handoff/brief-f229.md` (one owner per directory,
and the origin checked before an existing directory is taken).

### new-2. A login is kept by its config directory's path on macOS

Claude Code keeps an account's login in the Keychain under a name made from the config
directory's path, so another home linking `accounts/<name>` to a logged-in one reads
`logged_out`. The suite runs its trees on the setup's home itself, one at a time.

### new-3. A main session at its start's dialog cannot be ended

`end_main`, even with `force: true`, answers `{:refused, {:starting, name}}` while a start waits
on its trust dialog. What the design should change: an end during a start answers the start's
open dialog with its exit, as a person would. The suite's exit hook does that itself.

### new-4. A failed run's agents hold their lease seats in the shared home

Four seats were held by earlier failed runs' agents, and the next delegate's start was refused at
its lease deadline. The exit hook now ends a run's agents.

### new-5. B10 is not built: a main session's `AskUserQuestion` reaches no inbox

Asked to use its ask tool, Haiku used `AskUserQuestion`. Its native dialog (footer "Enter to
select · ↑/↓ to navigate · Esc to cancel") waited on the screen, no prompt came, and the delegate's
report stayed queued behind it. The test names the caf `ask` tool. What the design should change:
until B10, the screen's menu reading could take this footer too, as F-228 does for the permission
dialog's, so it reaches a person as a menu.

### new-6. An act refused before it acted still uses up its target's state

A delegate's stop refused `["report", "queued"]` (settled `not_verified`) left that state claimed,
so every later stop answered `{:refused, {:already_claimed, "operator"}}` until the delegate's
state changed (a message to it). `Acts` never reopens a settled row, by design, but a refusal that
acted on nothing should not consume the state.

### new-7. `on_exit` runs after the test's process, which the tree was linked to

`Run.start` links the tree to its caller, so after a failure the tree was gone before the exit
hook could end its agents. The case unlinks the tree.
