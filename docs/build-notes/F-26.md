# F-26: `Intake`, built against `Intake.tla`, for the node's own host

## What was built

- **`Intake.Event`**: a pure, total parse of a hook post's body into a row: the event (one of
  the ten the design's Intake section lists), `session_id`, a `key`, the body as data when it
  is JSON, and a problem. A body that is not JSON, not an object, of an unknown event, or
  missing its ids is a row with its problem, and is never held. The key is `session_id` with
  the event's own id (`tool_use_id`, `prompt_id`, `source`, `agent_id`), else a hash of the body.
- **`Intake.Table`**: `intake_events`, unique by `{host, account, key}`, and `intake_starts`.
  `Intake` alone writes it. A host whose `Intake` never started is `:unread`.
- **`Intake`**: one process per instance, no name of its own. A post writes the row and cues
  `intake:<host>:<account>` before the reply that lets the plug send its 200 (`Stored`, then
  `Acked`); a second post of one key writes nothing. A `PermissionRequest` is written `held`
  (`HoldStored`) and the plug's process holds the request open. `answer/4` moves the row
  `answering` (`AnswerAsked`), sends the decision to the plug, which writes it as the response
  (`AnswerWritten`), and then marks it `answered` (`AnswerMarked`) and returns `{:ok, :sent}`.
  At the deadline (570 s, or `deadline:`) the row is `expired` and the plug answers an empty
  body (`HoldExpires`). A start turns `held` into `lost` and `answering` into `unknown`, and a
  plug process that ends while it holds does the same (`HoldSettled`). Each spec action is named
  in a comment where the code does it.
- **`Intake.Plug`**: only `POST /hooks/<account>` from 127.0.0.1 with the secret in
  `x-caf-secret`, compared with `Plug.Crypto.secure_compare/2`. Anything else gets 404, 405,
  403, 401, 413 or 503, and no row. The secret is kept behind a function in the options and the
  header is dropped from the conn, so neither a crash report nor `inspect` shows it.
- **`Tracker.IntakeSource`**: the table as a `Tracker` source, kind `:events`.
- **`Accounts.prepare/3`** takes `intake: %{port: p, secret: s}` and writes `Intake.hooks/3`
  into both role settings files: an `http` hook per event, PermissionRequest with `timeout`
  600 and the rest 10, `onFailure` left out so it stays at continue. Hooks the caller gives
  for the same event come first.
- `plug` 1.20 is a dependency; `bandit` 1.14 is for tests only. The moduledoc shows the host
  app's children.

## Measured

- `gate-test` alone, three times: 120 passed (32 doctests, 12 properties, 76 tests), 12-14 s.
- `devenv test` exit 0.
- About 850 changed lines apart from `mix.lock`, over the 500 aimed for: 620 in `lib/`, much
  of it docs, and 210 in tests. `Tracker.IntakeSource` and the hooks in `Accounts`, with their
  tests (about 90 lines), could have been their own unit.

## What I ran into

- Mix leaves `inets` off the test VM's code path, since the library does not list it; the
  HTTP test calls `Mix.ensure_application!(:inets)` before `:httpc`.
- `assert_receive`'s default 100 ms failed once under the full suite's load; the waits on
  cues now take 5 s.
- The plug waits up to the deadline plus 5 s, then answers an empty body itself. That is a
  bound on a wait, and fires only when the `Intake` neither answers nor stops. When the
  `Intake` stops, the plug's monitor lets the request go at once, and the next start marks the
  row `lost`.

## Findings

### new-1. The design does not name the secret's header

What happened: the Intake section says the secret goes "in a header" and names none.

What I did: `x-caf-secret`, in `Intake.hooks/3` and the plug, from one place each.

What the design should change: name the header.

### new-2. The secret is written in plain text in each account's settings

What happened: the hooks carry the secret as a header value in `parent.settings.json` and
`delegate.settings.json`, which any process of the user can read.

Why: Claude Code 2.1.322 lets a hook's `headers` name environment variables listed in
`allowedEnvVars` (F-24), but the launch would then have to carry the secret in its
environment, which a process listing shows on some systems.

What the design should change: say which is wanted. I recommend the file, with mode 0600 set
by `Accounts`, since the files sit in the account's own config directory.

### new-3. A key for an event with no id of its own is a hash of the body

What happened: Stop, StopFailure, Notification and SessionEnd have no event id. A second post
of the same body writes no row, and two real events with identical bodies would collapse into
one.

What the design should change: confirm F-24 new-4 (no part counts such rows), or name a key.

### new-4. A push reader's age is not a read's age

What happened: `Intake` is not polled, so its source's `read_at` is the later of its last start
and its newest row. An account with no events for a while shows an old age, and
`Tracker.behind/3` flags it.

What the design should change: say how freshness is measured for a reader that waits for
posts, for example the time of its last start, while it runs.

### new-5. `answer` names a row, not an agent's dialog

What happened: the design's `answer(agent, dialog, label)` checks the agent's claim on the
dialog (Team.tla). This unit's `Intake.answer(intake, id, decision)` takes the row id.

What the design should change: nothing here; the MCP tool that maps an agent's dialog to its
held row is the next unit's, and it must refuse a row of another agent.
