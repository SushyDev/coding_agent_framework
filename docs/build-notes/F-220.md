# F-220: one setup command, and only the steps a person must do

The first setup a person ran took ten commands: two logins, each with Claude Code's first run
closed by a typed `/exit`; `--gh`, then `--git`, which failed on a missing scope; a manual
`gh auth refresh`; `--git` again; and three checks. This unit makes it one command in which the
person does only the browser logins and Claude Code's onboarding screens.

## What was built

- **`bin/caf-login --setup`**. `--setup <config.json> [account …]` reads `home`, `accounts`
  and `git.signing_key` from the config (with `elixir -e` and Elixir's `JSON`, the keys
  `ConfigFile` names; the app still checks the whole file at its start). Accounts named after
  the config must be ones it lists; with none named, every account is set up.
  `--setup <home> <account> …` is the form for an app whose config is built in code.
  `--no-git` leaves out gh and the key. The setup runs the existing forms in order, each as a
  process of its own (`<home> <account>` per account, then `--gh`, then `--git --key <key>`),
  stops at the first that fails, and says to run the same command again.
- **Each step skips what is done, and ends with its own check.** The account form skips the
  login when `claude auth status --json` exits 0 with `"loggedIn": true`, skips the first run
  when `.claude.json` records the onboarding passed, and then runs `--check` itself. `--gh`
  keeps a login whose token is in the home and has the scope, and then runs `--check --gh`.
  `--git` keeps a key that GitHub lists already (`gh api --paginate user/ssh_signing_keys`),
  and checks the list again after adding it.
- **The first run closes by itself**: Claude Code runs as `claude /exit` in the scratch folder.
- **gh with the scope**: `--gh` logs in with `gh auth login -h github.com --insecure-storage
  -s admin:ssh_signing_key`. A login whose token is in the home but lacks the scope gets
  `gh auth refresh -h github.com -s admin:ssh_signing_key --insecure-storage`, not a new
  login. `--git` reads the scopes first (`gh auth status -h github.com -a`, its `Token scopes:`
  line); a missing scope stops it with status 1 and the exact command, before any key is made.
  It no longer asks "[y/N]" before adding the key: the person asked for the key by running it.
- **`--check --gh`** prints gh's own lines, then caf-login's reading of `hosts.yml`, which says
  gh's label does not count, and whether the token has the scope. A missing scope is status 1.
- **`bin/caf-example`** runs `mix deps.loadpaths --no-compile` first; when it fails (a lock
  mismatch, or deps not fetched), it says so and runs `mix deps.get`.
- **Docs**: `docs/e2e.md` step 0's items 3 and 4 are one item: `bin/caf-login --setup
  /Users/me/caf-e2e.json one two`, then what the person does on screen. The `mkdir` for
  `three` is gone: `Accounts.prepare` makes an account's directories at the app's start. The
  README's setup and `bin/caf-example` lines match.

## What was measured

All against the pinned programs: Claude Code 2.1.322, gh 2.103.3.

- **`claude /exit` after onboarding.** A scratch config directory, an `ANTHROPIC_API_KEY`
  that is no key (so no account is used), in a tmux server of my own. The screens were the
  theme picker, "Detected a custom API key" (a claude.ai login does not show this one),
  the security notes, then the folder's trust dialog. After the trust answer, Claude Code
  showed `❯ /exit` as the first prompt and exited with status 0 by itself; `.claude.json` read
  `"hasCompletedOnboarding": true`. The directory was removed after.
- **`claude auth status --json`** on a scratch directory: `"loggedIn": false`, status 1; with
  the env API key, `"loggedIn": true, "authMethod": "api_key"`, status 0. Its JSON is
  pretty-printed, one key a line, which the script's match allows.
- **gh, logged out** (an empty `GH_CONFIG_DIR`): `gh auth status -h github.com` prints "You are
  not logged into any GitHub hosts…" with status 1; `--json hosts` prints `{"hosts":{}}` with
  status 0, as its help says. gh's help for `auth refresh` says `--insecure-storage` saves
  "in plain text instead of credential store", so a refresh without it stores the token
  outside the home (new-1).
- **`bin/caf-example`'s deps check.** With `deps/mime/.hex` rewritten to name 2.0.6 against the
  lock's 2.0.7, `mix deps.loadpaths --no-compile` printed the first setup's "lock mismatch … run mix
  deps.get" and exited 1 in 0.4 s. When the deps match, it exits 0 in 0.4 s.

that print what the script reads and log each argv:

- `--setup <home> one two` from nothing runs exactly: per account `auth status --json`,
  `auth login`, `/exit`, `auth status --text`; then gh's status, `auth login … -s
  admin:ssh_signing_key`, the checks, the key list, `ssh-key add`, the list again. Run again,
  only the reads run, each step is said as kept, and the key's `.pub` is unchanged.
- `--setup <config>`: an account the config does not list is refused; `--no-git` with one
  account runs no gh and no other account; with none named, every account, and the config's

  key; `--check --gh` keeps gh's "(keyring)" line, reads the file, and says the scope is

- `--git` with gh logged out; `--setup` stopping at an onboarding not passed, with no step
  after; and `--setup`'s refusals.

## The model

No protocol changed: these are scripts a person runs once, in order, and no part of the
framework's runtime. No spec was added.

## What I ran into

- A first measurement of the real setup piped the script through `tee`; Claude Code then had
  no terminal for its output, ran without its screens, and answered `/exit isn't available in
  this environment`. Run on a terminal it works. A person who pipes `bin/caf-login` into a file
  meets the same; this was true before this unit too.
- The scratchpad's path was too long for a tmux socket (macOS's 104 bytes), so the measurement
  servers used a short folder of their own under `/private/tmp/claude-501`, removed after.

## Findings

### new-1. `gh auth refresh` without `--insecure-storage` moves the token out of the home

What happened: the brief names the refresh as `gh auth refresh -h github.com -s
admin:ssh_signing_key`, which the person ran by hand in the first setup. gh's help says `--insecure-storage` saves "in
plain text instead of credential store", so without it the refreshed token goes to the OS
keyring. That fits what the person saw after the manual refresh: gh's status labeled the token
"(keyring)". caf-login's reading looks for `oauth_token:` anywhere in `hosts.yml`, so a stale
entry left in the file (gh keeps a per-user section too) could make it read "in the home"
while gh reads the keyring.

Why: gh decides where to store at each login or refresh; only `--insecure-storage` keeps it in
the file. gh's source was not on this machine to check whether it removes both entries.

What I did: caf-login's refresh and the command it prints both pass `--insecure-storage`. The
check still prints the brief's line ("gh's label above does not count").

What the design should change: on the e2e home, check once whether macOS's Keychain holds an
item for gh (`security find-generic-password -s gh:github.com`) after that manual refresh.
If it does, caf-login's reading was wrong there, and the check should trust gh's
`tokenSource` (from `gh auth status --json hosts`) over the file's text.

### new-2. A setup step that needs a terminal waits when it has none

What happened: `--setup` run with stdin closed reached the real `gh auth login` and waited
until I stopped it; Claude Code without a terminal for its output does not show its screens.

Why: the steps a person does are interactive programs by nature.

What I did: nothing in the script; the docs say to run it in a terminal.

What the design should change: if an app or an agent will ever run `--setup`, it should
refuse at the start when stdin or stdout is not a terminal (`[[ -t 0 && -t 1 ]]`), with a line
saying so, rather than wait.
