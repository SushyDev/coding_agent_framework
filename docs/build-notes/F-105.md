# F-105: the capture script records a state the release does not show

## What was built

`bin/capture-screen` asked for the workspace trust dialog first, and the pinned Claude Code did
not show it in the script's new scratch folder: the account's `.claude.json` recorded the folder
as trusted with no dialog. A real run's prompt now takes `s` for a state the release does not
show; the manifest records it as `{"state": …, "shown": false, "description": …}` with no file,
and the run goes on to the next state. The dry run is unchanged.

## Findings

### new-1. The pinned release may start in a new folder with no trust dialog

What happened: in a real run, Claude Code started in a new git repository under the temporary
directory and recorded it as trusted without showing the dialog. Why: not known; the release may
show the dialog only for some folders. What the design should change: `Screen` and `Mains` must
treat the trust dialog as one that may not come: a main session's start answers it when it shows
and goes on when the input box shows first. The capture's manifest says which it was.

### new-2. Every Enter of a real run ended the script

What happened: in a real run, the first Enter at the prompt ended the script with no message.
Why: `await_state` ended with a bare `return`, which gives the status of the last test it ran,
the `elif`'s false; under `set -e` the caller then exited. The dry run, which the tests run,
returns from its own branch, so no test went this way. What I did: `return 0` by name, and
checked the real path with a stand-in for Claude Code under a pseudo-terminal (`s`, Enter, `q`:
steps 1 to 3, then stopped as asked). What the design should change: nothing; a test of the real
path, with a stand-in and a pseudo-terminal, would have caught it, and could be added to
`CaptureScreenTest`.

### new-3. Text and its Enter in one burst make a newline, not a send

What happened: in a real run, the `turn-running` step's `type_line` (the prompt's text and Enter
in one tmux command) left the text in the box with a new line under it; the turn did not start.
The person pressed Enter in the pane to send it. Why: likely the pinned Claude Code reads a burst
of input as a paste, and an Enter inside a paste is a newline. What I did: nothing during the
run. What the design should change: a write into a main session's input box (`Control`'s checked
write: a message, a report, `/exit`) sends its text, waits until the box shows the whole text,
then sends Enter as a key of its own, and confirms the send by the box emptying or the turn
starting; never text and Enter in one burst. The capture script does the same for its typed
steps.

### new-4. A launch built from nothing has no CA bundle, so Claude Code cannot reach its service

What happened: in a real run, Claude Code's `/login` failed with `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`.
Why: the script builds the launch's environment with `env -i` and a list of what it keeps, and
the list had no CA bundle; devenv names it in `NODE_EXTRA_CA_CERTS` and `NIX_SSL_CERT_FILE`. What
I did: the script keeps those (and `SSL_CERT_FILE`) when set. What the design should change: the
rule "build a held process's environment from nothing" keeps the CA bundle by name;
`ClaudeCLI`'s launch environment does not keep it either, so no agent the framework starts could
reach Claude's service: a unit of its own.
