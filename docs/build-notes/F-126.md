# F-126: R10, `Acts`: one ledger for claims, recoveries and faults

F-115's 1c and new-4 found one rule in two tables: `Grants.Claims` and `Recoveries`' table both
write a row keyed by a state before an act and refuse a second one, and differ in actor,
`start_id`, cue and index by accident. This unit puts both in one table, `acts`, behind one
part, `Acts`, in a new app `caf_acts`, as `model/tla/Claim.tla` already models it.

## What was built

- **`caf_acts`**: `Acts`, the one writer, and `Acts.Table`, its SQL and `meta/0`. A row is
  `{actor, target, state, act, start_id, status, outcome, reason, answer, detail}` with the
  times `claimed_at`, `acted_at`, `ended_at` and `cleared_at`. A unique index on
  `(target, state)` keeps one claim per state with no scan; the old `Claims` read every row per
  claim. The status is one of `skipped`, `claimed`, `acted`, `settled` (with an outcome) and
  `interrupted`. Functions: `claim/6`, `skip/7`, `acted/4`, `settle/5`, `record/7` (a start or
  an error: a settled row with no state, so no claim), `interrupt/3` (an actor that restarted
  closes its own open claims), `clear/3` (a person's clear), `get/3`, `rows/3`, and the fault
  ledger, `faults/3` with `fault?/1`: every interrupted row, and every row settled `failed`,
  `unknown` or `not_verified`. Each write cues `acts:<host>:<instance>`.
- **A restart** is `Claim.tla`'s: `Acts` keeps the `start_id` the embedding app makes once per
  start, stamps it on every row, and at open closes the rows of other starts still `claimed`.
  Callers no longer pass a `start_id`.
- **`Store.text/1`** (F-117's new-2): one rule for a term in a column: text and integers as they
  are, an atom as its name, anything else as canonical JSON with sorted map keys, so equal terms
  give equal text and the unique index can compare a fix's state. Only a pid, a reference, a
  port or a function falls back to `inspect`, inside a JSON string. `Acts` stores every term by
  it.
- **`Recoveries`** keeps no table: it writes its rows in `Acts` as actor
  `recoveries:<host>:<server>`, act `reopen` or `end`, state `<host>:<server>:<key>` with the key
  it made before. Its window, repeating losses and last opens are now functions of its rows,
  read once per check. It no longer cues: `Acts` does. Its `notify:` and `db:` options are
  replaced by `acts:`.
- **F-118's new-5**: an end that settles `unknown` waits for a person, as a repeating lost
  viewer does. The end's key carries the time of the agent's last cleared end, so its state
  stays claimed until `Recoveries.clear/2` clears it, and the next check tries it once more.
  `clear/2` now clears both kinds and answers `{:refused, :not_waiting}` when nothing waits.
  "The parts" says so in `Recoveries`' row.
- **`MCP`** takes each fix's claim with `Acts.claim/6`, the tool's name as the act, and settles it
  with the fix's answer, stamping the act's time unless the fix was refused (`LetGo`). Its
  `:claims` and `:start_id` options are one `:acts`. The operator's acts go through `MCP`, so
  they are rows of the same ledger under the operator's name.
- **F-120's new-2**: `Acts.Table.meta/0` makes its `Tracker` source from `Tracker.ReaderSource`;
  `Reader.source_read/4` reads a writer's table (`reads: nil`) now, and `Reader.columns/1` takes
  a table's own columns. `Tracker.RecoveriesSource` is gone.
- **Removed**: `Grants.Claims` and its test, `Recoveries.Table`, `Tracker.RecoveriesSource`.
  `caf_grants` uses no other app now. `caf_tracker` uses `caf_recoveries` and `caf_acts` only in
  tests.
- **`caf_example`** starts `Acts` before `Recoveries` and `MCP` with the start's id and the old
  `claims.db`, and reads it in the `Tracker` by its metadata.

## Migration

`Acts` takes the old rows when it opens, in each file's own transaction, then drops the old
table, so a second open takes nothing. They need taking: a state claimed before must stay
claimed (a `not_verified` fix, a repeating loss waiting for a person), or the first check after
an upgrade would act on it again.

- `recoveries` (same file): the key becomes the state behind host and server, as now;
  `opened` becomes `acted`; `recovered`, `failed` and `unknown` become `settled` with that
  outcome, and `unknown{interrupted}` becomes `interrupted`; `reason` and `open` (`inspect`
  text) are read back as literals by `Code.string_to_quoted/2`, with every atom kept as its
  name so no atom is made from the file, and stored by `Store.text/1` (`":repeating"` is
  `"repeating"`, `"{:sample_too_old, 31001}"` is `["sample_too_old",31001]`); text that is no
  literal stays as it was. The rows take `start_id` `""`, so one left `claimed` is closed
  `interrupted` at the same open.
- `claims` (the old `claims.db`, attached): target and state, stored as Erlang terms, become
  `Store.text/1`'s text (`{:service, owner}` as `service:<owner>`), act `fix`, and the start id
  they had, so an open claim of an earlier start is interrupted. The two files' halves are each
  atomic; one taken twice is the same state, which the unique index keeps once.

`ActsTest`'s last test writes both old tables as the earlier builds made them and checks the rows
taken, a claim refused on a taken state, and that a second open takes nothing.

## What I ran into

- A Recoveries restarted between a claim and its act used to leave the row `claimed` until the
  next sample, which ended it `unknown{interrupted}` (or `recovered` when the agent was viewed by
  then). Now the restarted `Recoveries` closes it `interrupted` at its start, as `Claim.tla`'s
  `Settle` has it; the state is never acted on either way.
- A fix's state is a map. Storing it as text needed one canonical form; JSON with sorted keys is
  readable in the ledger, where Erlang's binary format was not.
- The `Tracker`'s view wraps each row as `%{key:, row:}`; the source test reads it so.
- `mix test` inside one app's directory stops on `stream_data`'s `:only` (`caf_test` declares it
  for `:dev` too); it runs from the root. It was so before this unit.

## Findings

### new-1. Starts and raised errors are not rows yet

What happened: R10 says every recovery, kill, resume, start and raised error is a row. Recoveries,
kills (the end owed), and fixes (resume included) are; `Delegates`' own resume, a session's start
and a part's raised error are not.
Why: they are written in `Sessions` and `Delegates`, which R7 changes: its part 1 (F-125) landed
while this unit was built, and this branch is rebased on it; its part 2 is still to come.
What I did: `Acts.record/7` writes such a row, already settled with no state, and `faults/3` shows
it when it failed. Nothing calls it yet.
What the design should change: name the unit that wires them (after R7), and say what a "raised
error" is: a part's `{:unknown, reason}` to its caller, or a process's crash seen by the app.

### new-2. `Store.update/4` still stores a term as `inspect` text

What happened: F-117's new-2 asked for one rule. `Acts` follows `Store.text/1`; `Store.update/4`
still uses `inspect` for every other writer.
What I did: nothing beyond `Acts`, to keep this unit to its tables.
What the design should change: move `Store.update/4` to `Store.text/1` when R9 rewrites the agent
row, converting the reasons stored before.

### new-3. A failed end and its clear are not in the model

What happened: `Start.tla`'s `Kill` always ends the process, so the end that fails, waits for a
person and is tried once more after a clear (F-118's new-5) is checked only by tests.
What the design should change: give `Start.tla` (or `Agent.tla`, which has `PersonClears`) a
`Kill` that can fail, with a clear that makes the state new, so `OneActPerState` covers it.

### new-4. A service's fix takes no row in `Acts`

What happened: the tools table says `service_restart` and `service_stop` act "under a claim".
`Grants.Claims` could hold `{:service, owner}`, but nothing called it: `Services` keeps its own
check of the row's state (`Copy.tla`'s forward). So a service's restart or stop is not in the
ledger.
What the design should change: say whether a service's fix is a row of `Acts` (act
`service_restart`, state the held process and restart count), and if so, which unit moves it.

### new-5. `Recoveries` reads all its rows each check

What happened: its window, repeating losses and last opens are computed from every row it ever
wrote, read once per check. The ledger keeps every row.
What the design should change: nothing yet; when the ledger grows, a query by actor and time (the
`acts_actor` index is there) or a retention rule for settled rows.
