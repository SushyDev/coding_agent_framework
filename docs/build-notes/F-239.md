# F-239: the real suite checks what F-230 and F-233 modeled

Branch `framework/f-239-real`, from `main` at 6d4f4b9. F-233's reload result line and F-230's
question menu were built on screens nobody had seen on the real Claude Code 2.1.322, and an
interactive delegate (`docs/e2e.md` step 4) had no real test. This unit writes those tests in
`apps/caf_real`. It changes no library code and no model.

## What was built

- **`RealCase` helpers.** `capture/3` reads an agent's whole pane, plain or with escapes.
  `records_dir/0` is the suite's records folder, `<CAF_REAL_SETUP>/records` (new-1).
  `record_screen!/4` writes a pane there as `<project>-<what>.txt`, `.ansi` and `.meta` (the
  pane's width and a note). `step/2` prefixes a failed assertion with the step's name.
  `answer_trust/2` moved here from the existing test. `start_main!/4` is step 2, `end_main!/1`
  is step 14 for a run with no delegate left, and `allow_all/2` allows an agent's open permission
  requests and answers their ids.
- **`ReloadTest`** (`reload_test.exs`, instance `real2`). An idle main session's
  `Operator.reload_plugins` runs twice. Each must answer `{:ok, %{done: :reloaded}}` (new-2).
  Each reload's pane, answer and time in ms are recorded as `<project>-reload-<n>` whatever it
  answers. Then the main session ends.
- **`QuestionMenuTest`** (`question_menu_test.exs`, instance `real3`). The main session is told
  to call `AskUserQuestion` once, with the question "Which fruit should the demo use?", header
  "Fruit", and options exactly `Apple` and `Pear`. When the footer "Enter to select" shows, or
  after 180 s without it, the pane is recorded as `<project>-ask-question`. That is F-230's real
  fixture. The test then requires these:
  - the inbox holds one `dialog:<main>:<at>:menu` prompt;
  - its text holds the question;
  - its options are exactly `["Apple", "Pear", "Chat about this", "esc"]`, and "Type
    something." is not among them;
  - `Apple` answers ok, and a second answer is refused `:settled`;
  - the inbox empties;
  - the main session's transcript then holds `chosen: Apple`, the reply the brief asked for,
    and the session goes idle.
- **`InteractiveDelegateTest`** (`interactive_delegate_test.exs`, instance `real4`). This is step
  4 as `docs/e2e.md` has it:
  - `unit/notes` starts with `interactive: true`;
  - its trust dialog, if one comes, is answered from the inbox, and the prompt's `parent` must
    be the main session;
  - every permission request on the way is allowed from the inbox;
  - its report reaches the main session's transcript as `From <name> on <account> (report):`,
    once, holding a commit's hash;
  - the main session was told of each answered prompt exactly once, `(prompt <id>)`;
  - a later turn ("Reply in one line with the word hello.") is answered by the delegate, and the
    report stays the brief's one;
  - then step 14: `end_main` is refused `{:delegates, [name]}`, the stop answers `:stopped`, and
    the main session ends.
- Each step has its own bound and its own name, so a failure says where the run stopped. Each
  module has its own instance, project and main session. The exit hook ends what a failed run
  left.
- `docs/e2e.md`'s opening and the README's status line name the new tests.

## What the main session must run

With a logged-in setup (`bin/caf-login --setup <home> one two`):

```sh
CAF_REAL_SETUP=<home> devenv shell -- mix test.real
# or one module at a time:
CAF_REAL_SETUP=<home> devenv shell -- mix test.real apps/caf_real/test/reload_test.exs
CAF_REAL_SETUP=<home> devenv shell -- mix test.real apps/caf_real/test/question_menu_test.exs
CAF_REAL_SETUP=<home> devenv shell -- mix test.real apps/caf_real/test/interactive_delegate_test.exs
```

Then, in `<home>/records/` (each file starts with the run's project name, `real2r…`, `real3r…`
or `real4r…`):

- **`*-reload-1.{txt,ansi,meta}` and `*-reload-2.*`.** These hold the pane after each reload.
  Read the line under `❯ /reload-plugins`: is it `  ⎿  Reloaded…`, as 2.1.322's reading models
  it? Read `ms:` in the `.meta` against the 10 s bound (F-233's new-1). If a reload answered
  `{:unknown, {:not_seen, _}}`, the box held the text with the command menu open (F-233's
  new-3). The `.txt` shows what the box drew.
- **`*-ask-question.{txt,ansi,meta}`.** This is the question dialog as it first showed. It
  replaces `apps/caf_screen`'s `ask-question.{txt,ansi}`: scrub the session's name to
  `capture-main`, and check the width in `.meta` against the 200 columns of the drawn fixture.
  Check that the dialog has the shape F-230 reads: the header, the question, numbered options,
  then the inner rule, "Type something." and "Chat about this". If the test failed at "the
  inbox shows the menu", this file is what the reading met.
- On any failure, read the failure's message and the screen it prints. Each names its step.

## What I ran into

- The brief speaks of "the records directory the suite uses". The suite had none. Only
  `docs/e2e.md`'s person-run steps keep a records folder (new-1).
- The main session's first real run of the three tests failed each at step 2 within 0.4 s:
  `start_main` answered `{:refused, {:checkout, "cloning"}}`. `start_main!/4` had skipped
  step 1. It now waits for the checkout to be ready on `main` (120 s bound) before the start,
  as `main_and_delegate_test.exs` does.
- `assert x in [{:ok, %{delegate: name}}, …]` compares the whole map, so a start's answer with
  more keys would fail. The delegate's start is matched with a `case` instead.
- A commit's hash is read from the report's text only, up to 400 bytes after its label. The
  check skips hex that touches a hyphen, so a delivery mark's uuid is not read as a hash.

## Findings

### new-1. The real suite had no records folder

What happened: the brief asks the tests to write captures to "the records directory the suite
uses". `apps/caf_real` had none. Only `docs/e2e.md` step 0 names one, for a person's run.
Why: F-223 printed screens on failure and kept none.
What I did: `RealCase.records_dir/0` is `<CAF_REAL_SETUP>/records`. Each file name starts with
the run's project name, so runs never overwrite each other.
What the design should change: say where a real run's records live. Either keep them in the
setup's home, as here, or give them a path of their own beside `CAF_REAL_SETUP`, so they can be
kept apart from the account directories.

### new-2. The reload's answer is `%{done: :reloaded}` at the operator, not `:reloaded`

What happened: the brief says `Operator.reload_plugins` answers `{:ok, :reloaded}`. That is
`Inlet`'s answer. The operator answers `{:ok, %{done: :reloaded, act: id}}`, as its doc and
F-233's note say.
What I did: the test matches the operator's shape.
What the design should change: nothing. Briefs could quote the operator's doc.

### new-3. F-233's new-3 screen cannot be captured through the framework

What happened: F-233's new-3 wants the screen with `/reload-plugins` typed and not yet sent.
The `Inlet` types the text and presses Enter in one step, and nothing else may type into a
pane. So the test captures only the screen after the reload.
What I did: the reload's record holds the pane after the reload. If the menu kept the text in
the box, the answer is `{:unknown, {:not_seen, _}}` and the `.txt` shows what the box drew.
What the design should change: `bin/capture-screen` gains a state with `/reload-plugins` typed
and not sent, for a person's run.

### new-4. The first label's press settles neither of F-230's two guessed keys

What happened: per the brief, the test presses `Apple`, the first option. That press crosses
neither "Type something." nor "Chat about this". So the run does not check whether Down visits
"Type something." or whether Enter on "Chat about this" closes the dialog (F-230's new-1). The
captured screen settles only the shape.
What I did: nothing more than the brief asked.
What the design should change: a second real test, or one more step in this one, that asks
again and presses "Chat about this". That press crosses "Type something." and checks both
keys: the press answers ok and the menu settles.

### new-5. The transcript lines a check counts are assumed

What happened: two checks read the main session's transcript JSONL. "Told once of each prompt"
and "one report" count lines that are not Claude Code's own replies (`"type":"assistant"`). The
real shape of a delivered line was not seen here, and one delivered text may appear on more
than one line (the hook's feedback and the queued message, say).
What I did: identical report texts are counted once. A notice's id is counted per non-assistant
line, so a text written twice would read as told twice.
What the design should change: if the run fails "told once" with a count of 2, read the main
session's transcript before reading it as a double delivery. The check could then count
`Mailbox`'s delivered rows (its marks) instead of transcript lines.

### new-6. Step 4's typed turn is a message here, not a person's typing

What happened: `docs/e2e.md` has a person type "Say hi." on the delegate's screen after its
report. A test can only send it through the operator's `message`, which `Mailbox` stores and
the `Inlet` types into the same box.
What I did: the test sends "Reply in one line with the word hello.", waits for the delegate's
reply, and checks that the report is still the brief's one.
What the design should change: nothing for the suite. `docs/e2e.md`'s person-run step 4 still
checks typing on the screen itself.
